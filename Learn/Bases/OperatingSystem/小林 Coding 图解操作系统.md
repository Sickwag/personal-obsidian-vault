# 硬件结构篇
计算机基本结构为 5 个部分，分别是**运算器、控制器、存储器、输入设备、输出设备**，这 5 个部分也被称为**冯诺依曼模型**。
![冯诺依曼模型](../../../Files%20&%20LongText/Attachments/%E5%86%AF%E8%AF%BA%E4%BE%9D%E6%9B%BC%E6%A8%A1%E5%9E%8B.webp)
## CPU
### 一次计算
- 32 位 CPU 一次可以计算 4 个字节；
- 64 位 CPU 一次可以计算 8 个字节；
"一次计算"指的是: **CPU 内部通用寄存器的宽度**，以及 **算术逻辑单元（ALU）单次处理整数数据的最大位宽**。
"一次"指
- 32 位系统中，ALU 在**一个时钟周期里**，能从内存中读取 4 个字节放进运算器里算，运算器执行一条单周期或单发的整数运算指令。
- 时钟周期时间为 CPU 主频的的倒数。所以 CPU 的**理论上数据吞吐量由主频 * CPU 位宽得到**，但这需要几个前提:
	- 一个时钟周期执行一条指令（显示是大多数指令包括四则运算都需要多个时钟周期完成，乘除更多。现在还有 SIMD 技术）
	- 这种算法仅能描述理论上 **CPU 内部缓存到寄存器的带宽**，实际上数据从寄存器到 CPU 还有一些额外的工作，达不到这么高的速度
- 但实际上数据吞吐量还需要考虑和内存交换数据的效率，内存读写吞吐量: 理论带宽 = 内存总线频率 x 内存总线位宽 x 通道数。内存总线的位宽**固定是 64 位**（即 8 字节），双通道就是 128 位。还要考虑木桶效应
"计算"特指对整数的运算（加减，位移和逻辑运算），**不包含浮点数**（浮点数有专门的协处理器或向量单元处理）。
- 32 位 CPU 处理 64 位数据需要分别对高位和低位做一次运算并合并结果
### 寄存器
重要的寄存器
- _通用寄存器_，用来存放需要进行运算的数据，比如需要进行加和运算的两个数据。
- _程序计数器_，用来存储 CPU 要执行下一条指令「所在的内存地址」，注意不是存储了下一条要执行的指令，此时指令还在内存中，程序计数器只是存储了下一条指令「的地址」。
- _指令寄存器_，用来存放当前正在执行的指令，也就是指令本身，指令被执行完成之前，指令都存储在这里。
CPU 执行指令的流程:
- 第一步，CPU 读取「程序计数器」的值（指令的内存地址），然后 CPU 的「控制单元」操作「地址总线」指定需要访问，接着通知内存设备准备数据，数据准备好后通过「数据总线」将指令数据传给 CPU，CPU 将这个指令数据存入到「指令寄存器」。
- 第二步，顺序执行时程序计数器（PC）更新为下一条指令的地址。地址增量由指令编码长度和指令集架构决定，不由 CPU 位宽决定：x86/x86-64 指令是可变长度，AArch64 指令固定为 4 字节；
- 第三步，CPU 分析「指令寄存器」中的指令，确定指令的类型和参数，如果是计算类型的指令，就把指令交给「逻辑运算单元」运算；如果是存储类型的指令，则交由「控制单元」执行；
Linux ELF 程序的机器指令通常位于 `.text` 代码段，加载后映射到进程的虚拟地址空间。PC 是取指地址，不是环形缓冲区下标：顺序执行到下一条指令时地址前进，分支、调用、返回和异常会把 PC 改到其他目标地址；访问未映射或不可执行的地址会触发异常，不会按 RingBuffer 规则绕回地址 0。
### 指令
汇编代码专成机器码之后形式变为二进制，不同的指令集对一段相同的二进制编码的解释方式不一样，这里使用 MIPS 指令集
MIPS 的指令是一个 32 位的整数，高 6 位代表着操作码，表示这条指令是一条什么样的指令，剩下的 26 位不同指令类型所表示的内容也就不相同，主要有三种类型 R、I 和 J。
![MIPS指令集](../../../Files%20&%20LongText/Attachments/MIPS%E6%8C%87%E4%BB%A4%E9%9B%86.webp)
- R 类型用于逻辑和算术运算
	- shamt 用于计算逻辑位移操作的参数
	- func 用于 opcode 不够时的拓展
- I 指令，用在数据传输、条件分支等，简单的语义让只需要地址参数就可以
- J 指令，用于跳转，target address 表示跳转目的地
现代大多数 CPU 都使用来流水线的方式来执行指令，所谓的流水线就是把一个任务拆分成多个小任务，于是一条指令通常分为 4 个阶段，称为 4 级流水线
![CPU指令周期](../../../Files%20&%20LongText/Attachments/CPU%E6%8C%87%E4%BB%A4%E5%91%A8%E6%9C%9F.webp)
编译时程序将指令编码，Decode 表示 CPU 读取指令并按照指令集规定解释，叫做解码
1. CPU 通过程序计数器读取对应内存地址的指令，这个部分称为 **Fetch（取得指令）**；
2. CPU 对指令进行解码，这个部分称为 **Decode（指令译码）**；
3. CPU 执行指令，这个部分称为 **Execution（执行指令）**；
4. CPU 将计算结果存回寄存器或者将寄存器的值存入内存，这个部分称为 **Store（数据回写）**；
四个步骤称之为*指令周期*，不同的阶段其实是由计算机中的不同组件完成的：
![指令周期工作组件](../../../Files%20&%20LongText/Attachments/%E6%8C%87%E4%BB%A4%E5%91%A8%E6%9C%9F%E5%B7%A5%E4%BD%9C%E7%BB%84%E4%BB%B6.webp)

> [!Info]  32 位的操作系统可以运行在 64 位的电脑上吗？反之如何？
> 64 位和 32 位软件，实际上代表指令是 64 位还是 32 位的
> - 32 位指令在 64 位机器上执行，需要一套兼容机制，由操作系统提供。
> - **64 位指令在 32 位机器上执行，就比较困难了，因为 32 位的寄存器存不下 64 位的指令**；在硬件上，也没有执行长指令的硬件电路，32 位 CPU 的 ALU 也是 32 位的，大数计算导致溢出
> - 操作系统其实也是一种程序，我们也会看到操作系统会分成 32 位操作系统、64 位操作系统，其代表意义就是操作系统中程序的指令是多少位，比如 64 位操作系统，指令也就是 64 位，因此不能装在 32 位机器上。

#### 指令长度与取指地址

「64 位模式」指通用寄存器、指针和运算宽度的扩展，不等于每条指令占 64 位：x86-64 仍使用可变长编码，同一段代码在兼容模式与 64 位模式下的差异是寄存器、寻址和操作数宽度，不是把指令统一拉长到 8 字节。

| 架构 | 指令长度 | 编码特征 |
| --- | --- | --- |
| x86 / x86-64 | 1~15 字节，可变 | 前缀、opcode、ModR/M、SIB、位移、立即数按指令组合；上限 15 字节（Intel SDM） |
| AArch64 | 固定 4 字节 | 定长编码，跳转多用 PC 相对偏移 |
| RISC-V | 基础 4 字节，C 扩展 2 字节 | 编码低位标识长度 |
| MIPS32 | 固定 4 字节 | 与上文 32 位指令格式一致 |

```text

0x400000    B8 2A 00 00 00     mov eax, 42          0x400005
0x400005    83 C0 01           add eax, 1           0x400008

```

- PC 寄存器的位宽大于架构实际使用的有效虚拟地址位数；x86-64 常用 48 位虚拟地址（开启 LA57 为 57 位），回绕不是程序循环机制。
- 取指访问未映射页触发缺页异常，访问已映射但不可执行的页触发取指保护异常，非规范地址触发通用保护异常；CPU 不会跳回地址 0 继续执行。
- 现代处理器取指先查 L1 指令缓存，未命中才逐级向下，不是每条指令都访问一次 DRAM；教材「通过地址总线通知内存」描述的是缓存缺失后的路径。

### 寄存器
寄存器的数量通常在几十到几百之间，每个寄存器可以用来存储一定的字节（byte）的数据。比如：
- 32 位 CPU 中大多数寄存器可以存储 `4` 个字节；
- 64 位 CPU 中大多数寄存器可以存储 `8` 个字节。
性能很高，一般要求在半个 CPU 时钟周期内完成读写
### CPU cache
CPU Cache 用的是一种叫 **SRAM（_Static Random-Access_ Memory，静态随机存储器）** 的芯片。
在 SRAM 里面，一个 bit 的数据，通常需要 6 个晶体管，所以 SRAM 的存储密度不高，同样的物理空间下，能存储的数据是有限的，不过也因为 SRAM 的电路简单，所以访问速度非常快。

#### store buffer 和 load buffer
即使写 L1 cache 也要 3-10 周期。如果 CPU 每写一次都要等 cache 完成，流水线就卡死了。所以 CPU 加了一个写缓冲区（store buffer）。写操作先进入 store buffer（只要 1 周期），CPU
  立刻继续执行后面的指令，store buffer 里的内容再异步刷入 L1 cache。
- 当 CPU 执行 store 指令（将数据写入内存操作）时，数据先写入 store buffer，而非立即写入 L1 缓存
- 允许 CPU 乱序执行：在等待存储操作完成时继续执行后续指令
- 实现 store-to-load forwarding（存储转发），加速数据传递
*条目*的数据结构为:
```md
// store buffer
┌─────────────────────────────────────┐
│  Entry N                            │
├─────────────────────────────────────┤
│  Valid Bit (有效位)                  │
│  Memory Address (地址)               │
│  Data (数据，通常 8-64 字节)          │
│  Size/Length (写入大小)              │
│  Sequence Number (序列号)            │
└─────────────────────────────────────┘

// load buffer
┌──────────────────────────────────────────┐
│  Valid │ Address │ Waiting Instructions │
│   ✓    │ 0x5678  │ [load1, load2, ...]  │
└──────────────────────────────────────────┘
```
不同 CPU 的 store buffer 条目容量不同，在 48~72 条之间，store buffer 满时，CPU 必须等待（stall）才能继续执行新的 store，当 CPU 执行
```asm
mov [rdi], rax    ; store: 写地址 A，值 X
mov rbx, [rdi]    ; load: 从地址 A 读数据
```
此时 CPU 不需要等待 store 写入 L1 cache，而是直接从 store buffer 中读取最新值，这个过程叫 store-to-load forwarding。没有他的存在就会导致 CPU 与 L1 速度差距过大引起 CPU 空转
由于指令重排的问题，load buffer 同理

> [!note] buffer 机制和内存序
> - 两个 buffer 在 CPU 核心与 L1 之间，程序员不可见
> - Store buffer = "我要写什么"，Load buffer = "我在等什么"。两者结构相似但语义相反。
> - 两个 lbuffer 的结构在**物理上支持了**内存屏障技术，[[Modern C++#Note：内存序|C++的内存序机制]]就是通过控制两个 buffer 的刷新与否保证内存屏障
#### L1 cache
L1 高速缓存的访问速度几乎和寄存器一样快，通常只需要 `2~4` 个时钟周期，而大小在几十 KB 到几百 KB 不等
指令和数据在 L1 是分开存放的，所以 L1 高速缓存通常分成**指令缓存**和**数据缓存**。
```bash
 ~  cat /sys/devices/system/cpu/cpu0/cache/index0/size # 查看数据缓存大小
48K
 ~  cat /sys/devices/system/cpu/cpu0/cache/index1/size # 查看指令缓存大小
32K
```
#### L2 cache
不分指令和数据缓存，一般在几百 K 到 2MB 之间，IO 速度在 `10~20` 个时钟周期。
#### L3 cache
几 MB 到几十 MB 不等，速度在 `20~60` 个时钟周期。
#### 数据结构
CPU Cache 是由很多个 Cache Line 组成的，Cache Line 是 CPU 从内存读取数据的基本单位，而 Cache Line 是由各种标志（Tag）+ 数据块（Data Block）组成
![Cache的数据结构](../../../Files%20&%20LongText/Attachments/Cache%E7%9A%84%E6%95%B0%E6%8D%AE%E7%BB%93%E6%9E%84.webp)

[CPU Cache伪共享问题：原理与优化指南](https://chengxumiaodaren.com/docs/performance/cpu-cache/) 这篇文章很明显地展示了根据 cache line 作用机制优化带来的性能提高，得到结论为:

> - 如果我们写单线程程序，最好保证访问的数据能够相邻，在一个 Cache line 上，可以尽可能的命中 Cache。（空间局部性）
> - 如果写多线程程序，最好保证访问的数据有间隔，让它们不在一个 Cache line 上，减少 False Sharing 的频率。（防止多 CPU 的多线程场景下的缓存失效）
> - 二维数组按行遍历由于按列遍历
```cpp
┌─────────────────────────────────────────────────────────┐
│  有效位 │  标记位（Tag）   │           数据（Data）         │
│   1bit │    N bits      │       Cache Line Size         │
│        │                │        (如 64 字节)            │
└─────────────────────────────────────────────────────────┘
标记位
┌──────────┬──────────┬──────────┐
│   Tag    │ Set Index│ Block Offset│
│ (高位)    │ (中间)   │   (低位)   │
└──────────┴──────────┴──────────┘
```
- 有效位（Valid Bit）表示该缓存行当前是否装有可参与命中判断的数据。`Valid = 0` 表示无效/空行，访问请求仍携带完整地址，不需要从无效行中找回地址。
- 标记位（Tag）保存地址高位，用于区分映射到同一组的不同内存块。Tag、Index、Offset 是完整访问地址的位字段划分，不会缩小 CPU 可寻址的内存范围；Tag 保留了区分不同内存块所需的高位。
- 教材常用物理地址说明映射。实际处理器可能在地址转换过程中并行查询 TLB 和 L1 Cache；不同 Cache 层级可使用不同的索引/标记方式，不能把某一种实现推广为所有 CPU 的固定电路。

| 地址分段           | 作用                          |
| -------------- | --------------------------- |
| **低位（Offset）** | 块内字节偏移；若一行是 64 字节，需要 6 位 |
| **中位（Index）**  | 选择一个 Set（组）；直接映射时每组只有一行 |
| **高位（Tag）**    | 与该组中各路保存的 Tag 比较，确认目标内存块 |
通用组相联 Cache 由多个 Set 构成，每个 Set 有多条 Cache Line。下图中 `E` 表示每组的行数，地址的 Tag、Set Index、Block Offset 分别用于识别内存块、选择组和选择行内字节；完整地址的每一位都参与划分。

#### 映射方式与地址位域
来源：对话记录2（ChatGPT 导出，2026-10）
Cache 的容量限制的是同一时刻能缓存多少内存块，不限制 CPU 可寻址的范围；完整地址仍然参与寻址，只是其中连续的一段被用作组索引和行内偏移。

以 32 位物理地址、32 KiB L1 数据缓存、64 字节 Cache Line、8 路组相联为例：

- Cache Line 总数 = 32 KiB / 64 B = 512
- Set 数 = 512 / 8 = 64，因此 Index 占 6 位
- Offset = log2(64) = 6 位
- Tag = 32 - 6 - 6 = 20 位

| 映射方式 | 组数 × 路数 | Tag / Index / Offset | 一次查找比较的 Tag 数 | 冲突未命中 |
| --- | --- | --- | --- | --- |
| 直接映射 | 512 × 1 | 17 / 9 / 6 | 1 | 多 |
| 8 路组相联 | 64 × 8 | 20 / 6 / 6 | 组内最多 8 | 较少 |
| 全相联 | 1 × 512 | 26 / 0 / 6 | 512，需并行比较器 | 无映射位置冲突 |

全相联把 Index 去掉、把 Tag 扩到 26 位，没有组冲突未命中但仍可能容量缺失，代价是比较器、选择逻辑、面积和功耗随行数增长；Index 的作用就是先把候选从 512 条缩小到 1 组，再用少量并行比较器完成命中判断。硬件比较是并行的，不是软件遍历 Set。

地址 `0x12345678` 的拆分与查找数据流：

```text
0x12345678
  Tag    = 0x12345678 >> 12        = 0x12345
  Index  = (0x12345678 >> 6) & 0x3F = 25
  Offset = 0x12345678 & 0x3F       = 56
  → Set 25：并行比较 8 路的 Valid 和 Tag
  → Way 0: Valid=1, Tag=0x12345 → 命中，从行内第 56 字节开始按指令宽度取数
  → 无匹配：按行对齐取块，装入该组某一路并写 Tag/Valid
```

未命中装入示例：请求 `0x12347678` 时 `Tag=0x12347`、`Index=25`、`Offset=56`，缺失后装入的连续块是 `0x12347640 ~ 0x1234767F`，而不是从地址 0 或变量起始处开始的一段。首次访问与第十次访问同一地址的 Tag/Index/Offset 拆分完全相同，变化的只是 Cache 中的内容。

- 地址由访存指令计算，例如 `mov eax, [rbx+8]` 由寄存器值加偏移得到虚拟地址，再经 MMU/TLB 转成物理地址；Cache 不知道下一条指令会访问哪里，只对已经给出的地址做查找。
- 教材用物理地址讲映射。实际 L1 常用 VIPT（虚拟索引、物理标记）在 TLB 转换完成前先并行索引，再用物理 Tag 校验；具体是否 VIPT、索引位宽和路数限制随微架构不同（待验证：查对应厂商优化手册）。
- 把未命中一律写成「去内存取」不准确：在读缺失路径上，请求先向下一级 Cache 发出；若目标行被其他核心以 M 状态持有，可由该核心转发；DRAM 只在下级缓存也缺失或脏行被驱逐时参与。依据是缓存层级与 MESI/目录协议的所有权和转发规则。

#### 缓存行读取过程
CPU 访问数据时，先在当前 Cache 层级查询；未命中后才从下一层 Cache 或内存层级取得所需数据。Cache 的查找由访问地址和 Cache 的映射参数决定，地址本身不是根据 Cache 的槽位重新构造出来的。
- Cache 与下一级之间以 Cache Line（缓存行/块）为单位填充，通常是一段固定长度、连续且按行大小对齐的内存区域；具体行大小由处理器实现决定，常见值是 64 字节。
- `Index` 选中一个 Set，硬件检查该组中各路的 `Valid` 和 `Tag`；存在有效且 Tag 匹配的行才命中。组相联结构通常并行比较组内多路，但路数和 Cache 组织方式由处理器决定，不固定为 8 路。
- `Offset` 只定位数据在缓存行中的字节位置，不记录变量的类型或长度。要读取多少字节由 CPU 执行的 load/store 指令决定；编译器根据 C++ 类型和表达式生成相应宽度的指令。
- 未命中时，硬件按行大小将请求地址向下对齐，取得包含该地址的完整行并更新 Tag/Valid；若目标组没有空行，则按替换策略选择受害行。脏行需要按写策略写回下一级。

Cache Line 与 C++ 对象边界没有绑定。读取 `struct S { int a, b, c; };` 中的 `s.b` 时，通常装入包含 `b` 地址的整条缓存行；同一行中相邻的 `a`、`c` 或其他对象字节也会随行一起缓存。若对象跨越两行，只访问其中一个字段通常只需访问包含该字段的行，CPU 不会因为它们属于同一对象而自动装入所有行。

操作系统按页映射内存，分配器按对象/字节块分配；这并不意味着所有对象都按 Cache Line 边界切分或对齐。普通 C++ 对象遵循类型对齐要求；缓存行对齐是单独的性能布局选择，相关工具见 [[Modern C++#9.4 内存对齐]]。
#### 缓存行写入过程
写直达（Write Through）和写回（Write Back）描述缓存数据何时向下一级传播，与 L1/L2/L3 是私有还是共享、是否包含式组织是不同维度；这些层级关系由处理器实现决定。
- 写直达（_Write Through_）：每次写操作都把数据更新到 Cache，并向下一级传播；写未命中时是否分配缓存行由另一项策略决定。
![350](../../../Files%20&%20LongText/Attachments/%E5%86%99%E7%9B%B4%E8%BE%BE.webp)
- 写回（_Write Back_）：数据先在缓存层级中更新并标记为脏，通常在缓存行被驱逐时写回下一级；一致性协议需要转移数据时也可能发生缓存间传递。
![写回1](../../../Files%20&%20LongText/Attachments/%E5%86%99%E5%9B%9E1.webp)
写回缓存中，CPU 的 Store 会先取得该缓存行的写权限，再修改指令指定的字节。脏状态表示本级缓存的内容比下一级更新；它可以由独立元数据或一致性状态表达，不能据此断言所有处理器都没有单独的 Dirty Bit。
在典型的写分配策略下，写未命中会先取得包含目标地址的缓存行，再更新其中对应字节。如果映射到的组已满，需要驱逐受害行；受害行若为脏行，则先写回下一层。具体读入、分配和写回步骤取决于处理器的写策略与一致性协议。
#### 有效位、脏位与驱逐
来源：对话记录2（ChatGPT 导出，2026-10）
Valid 和 Dirty 是两条独立信息：Valid 决定这一行能否参与命中比较，Dirty 决定这一行被替换或转移时是否需要保住数据；不能从其中一个推断另一个。

| 事件 | Valid | 数据动作 | 说明 |
| --- | --- | --- | --- |
| 上电或复位 | 全部为 0 | 无 | 行内容不可用于命中 |
| 缺失填充 | 0 → 1 | 写入数据并记录 Tag | 命中条件是 Valid=1 且 Tag 匹配 |
| 干净行被替换 | 该路复用 | 可直接丢弃 | 下一级已有相同数据 |
| 脏行被替换 | 该路复用 | 写回或转移给请求方 | 下一级可能仍是旧值 |
| 一致性失效消息 | 1 → 0 | 可能需先提供数据，再失效 | 其他核心取得写权限 |
| 显式缓存维护指令 | 1 → 0 | 按指令语义刷出或失效 | 如 x86 `clflush` 系列、ARM DC 维护操作 |

```text
写命中   → 修改行内字节，置 Dirty=1，写回策略下不立即下发
写缺失   → 写分配：取得整行 → 修改目标字节 → Dirty=1
组已满   → 选受害行 → 干净则丢弃 / 脏则写回下一级 → 填入新行
行被驱逐 → 旧 Tag + Index + Offset=0 重建块基址 → 脏行写回
```

- 改写 Valid 的是 Cache 控制逻辑：填充、替换、一致性协议消息、缓存维护指令；普通用户程序通过维护指令间接影响，不直接读写这些标志位。
- `Valid=1` 且 `Dirty=1` 表示本行是最新版本、下一级可能落后。把「内存永远正确、Cache 只是副本」当成前提会得出错误结论；写回缓存里权威副本可以在 Cache 中。
- Cache Line 没有按时间到期的过期机制：失效通常只来自一致性协议或缓存维护指令，驱逐主要由容量、组冲突与替换策略触发。
- 驱逐脏行时，控制器不需要保存完整地址，可以用「旧 Tag + 该路所在 Set 的 Index + 全零 Offset」重建块基址：`基址 = (Tag << (index_bits + offset_bits)) | (Index << offset_bits)`。这正是地址位域复用的结果。
- 驱逐（eviction）与失效（invalidation）是两种事件：前者主要由容量、组冲突、替换策略触发，频繁访问只影响替换优先级，不能保证不被驱逐，只读行同样可能因容量或冲突被淘汰；后者由一致性协议或缓存维护指令触发。
#### 缓存一致性问题
写回缓存可能让 DRAM 暂时保留旧值，但不能据此推断其他 CPU 核心会一直读到旧副本。对可缓存、具备硬件一致性的普通内存，Cache Coherence 协议会协调各核心缓存行的有效性和写入权限；最新数据也可能由其他核心的 Cache 提供，不一定先写入 DRAM。
![400](../../../Files%20&%20LongText/Attachments/%E7%BC%93%E5%AD%98%E4%B8%80%E8%87%B4%E6%80%A7%E9%97%AE%E9%A2%98%E4%BE%8B%E5%AD%90.webp)
缓存一致性协议按缓存行协调副本与写权限，使同一缓存行不会在缺少协调时出现可同时写入的互相矛盾副本。实现可以使用总线侦听或目录等机制，不一定向所有 CPU 广播。
缓存一致性不等于 C++ 内存序，也不等于数据库事务串行化：它不保证不同地址上的操作都按源码顺序被其他线程观察。C++ 的 `std::memory_order` 用于定义原子操作的排序与同步关系；跨多个变量维护一个整体不变量通常还需要互斥锁或其他同步协议，详见 [[原子操作]]。
#### MESI 协议
- `M — Modified`：本地缓存持有有效、已修改且具备独占写权限的行；其他核心不能直接使用旧副本。
- `E — Exclusive`：本地独占且干净。若本地开始写入，可直接转为 `M`，不需再使其他副本失效。
- `S — Shared`：缓存行有效且干净，其他核心可能也有副本。写入前要取得独占权限并使其他副本失效。
- `I — Invalid`：该缓存行不能用于命中。

`M` 与 `E` 都具有独占写权限，差别是数据是否已修改；`S` 表示可以共享读取，不保证此刻一定有多个副本。真实处理器可能采用 MESIF、MOESI、目录协议或额外瞬态状态，教材中的 MESI 状态图是简化模型。

#### MESI 的写入权限与实现差异
来源：对话记录2（ChatGPT 导出，2026-10）
MESI 是写失效（write-invalidate）协议，核心不变量是「读可以共享，写必须独占」：同一 Cache Line 在所有核心中最多只有一个可写副本，写入前先让其他副本失效，而不是把新值广播给所有核心。

| 状态 | 本地可读 | 本地可直接写 | 与下一级数据关系 | 其他核心有效副本 |
| --- | --- | --- | --- | --- |
| M | 是 | 是 | 本行最新，下一级可能滞后 | 无 |
| E | 是 | 是，转为 M | 一致 | 无 |
| S | 是 | 否，先取得独占权限 | 干净 | 可能有 |
| I | 否 | 否，需重新取数 | 不适用 | 不适用 |

E 相对 MSI 的价值：核心读入一行且确认无其他副本后处于 E，随后写入可直接 E → M，不必再发一次独占请求；代价是协议要能区分「无其他副本」和「可能有副本」。E 与 M 都有独占权，差别只在数据是否已被修改。

```text
初始 | A=I, B=I, 内存 x=10
A 读 x | 独占装入 | A=E, B=I
B 读 x | A 降级为 S，数据由 A 或下级提供 | A=S, B=S
A 写 x | 取得独占权并让其他副本失效 | A=M, B=I
A 再写 x | 已是 M，不再发请求 | A=M, B=I
A 的脏行被驱逐 | 写回下一级或转移给请求方 | 该行离开 A 的 Cache
```

教材状态图常把流程画成「读缺失 → 从内存读」「M 被他人读/写 → 先写回内存」，这是简化：

| 示意图说法 | 更准确的表述 | 依据 |
| --- | --- | --- |
| 缺失一律从内存取数 | 先向下一级缓存请求；其他核心持有 M 时可 cache-to-cache 转发 | 缓存层级与一致性协议 |
| M 状态被其他核心读取就先写回内存 | 数据可 cache-to-cache 转发；共享化后由下级缓存或写回保证干净状态 | 写回缓存加转发实现 |
| M 状态被其他核心写入就先写回内存 | 可由持有 M 的核心转发数据并把写权限转给请求方，DRAM 不必先更新 | 所有权转移 |
| 写前向所有核心广播失效 | 总线侦听只适用于侦听型系统；目录协议只通知记录在案的共享者 | snooping / directory |
| 四状态完整描述硬件 | 实际实现有 MESIF、MOESI 与瞬态状态，事务可能经过中间态 | 厂商协议扩展 |

- 协议协调的单位是 Cache Line，不是 C++ 变量。同一行里的两个独立变量共享同一个状态，这也是伪共享的根源。
- MESI 只解决「同一地址的副本和写权限」。它不保证不同地址的访问按源码顺序被观察，也不提供跨多个原子操作的事务语义。
- 三个层次要分开：原子性保证单次读改写不可分割；缓存一致性保证同一行的值不打架；内存序保证原子操作之间的可见顺序。`fetch_sub` 与 `fetch_add` 各自原子，组合起来仍可能被观察到中间状态，需要互斥锁；各内存序语义见 [[Modern C++#Note：内存序|C++ 内存序]]。
#### 分支预测器
对于 if 条件语句，意味着此时至少可以选择跳转到两段不同的指令执行，也就是 if 还是 else 中的指令。那么，如果分支预测可以预测到接下来要执行 if 里的指令，还是 else 指令的话，就可以「提前」把这些指令放在指令缓存中，这样 CPU 可以直接从 Cache 读取到指令，于是执行速度就会很快。
当数组中的元素是随机的，分支预测就无法有效工作，而当数组元素都是是顺序的，分支预测器会动态地根据历史命中数据对未来进行预测，这样命中率就会很高。
#### 多核 CPU 提高缓存命中率（cache hit）
虽然 L3 共享，但是最快的 L1/L2 是每个 CPU 独有的，**如果一个线程在不同核心来回切换，各个核心的缓存命中率就会受到影响**，在 Linux 上提供了 `sched_setaffinity` 方法，来实现将线程绑定到某个 CPU 核心这一功能
```cpp
int sched_setaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);
```
### CPU 如何执行任务
#### Cache 伪共享
伪共享（False Sharing）指不同核心访问不同变量，但这些变量落在同一缓存行，并发访问中至少有一个写入。写入需要取得整条缓存行的独占权限，可能使其他核心持有的副本失效，产生一致性流量。
真共享（True Sharing）是多个核心访问同一变量；它是否构成 C++ 数据竞争取决于访问是否使用原子操作或其他同步。伪共享本身也不等同于数据竞争，是性能问题。
缓存行大小由硬件实现决定，常见为 64 字节，但不应把这个值视为所有平台的固定常量。隔离字段、每线程/每 CPU 私有计数后批量汇总、分离热点可变字段与只读字段等方法见 [[架构设计#虚假共享（False Sharing）]]；C++ 对齐工具见 [[Modern C++#9.4 内存对齐]]。
#### 伪共享的消除手段
来源：对话记录2（ChatGPT 导出，2026-10）
「数据被频繁读取就不会被换出，因此不会伪共享」这个因果关系不成立。频繁读取只影响替换策略的优先级，不能阻止容量不足或组冲突导致的驱逐；伪共享的直接原因是另一核心写入同一 Cache Line 时使本地副本失效，而不是本地行被换出。Padding 隔离的是写者的失效范围，不是驱逐。

Disruptor 例子里目标字段前后各放 7 个 `long`（每侧 56 字节），目的是把只读元数据与频繁写入的 cursor 分到不同行；Java 字段顺序、对象头和填充由 JVM 决定，`final` 只限制引用重赋值（`entries[0]` 仍可改），这段布局要在具体 JVM 上验证，不能当成跨实现保证。

| 手段 | 做法 | 适用场景 | 代价与边界 |
| --- | --- | --- | --- |
| 对齐与填充 | 热点字段独立按行对齐，或前后加 padding | 同结构体内不同线程写不同字段 | 内存占用增加；行大小是实现定义值 |
| `alignas` 加干扰尺寸 | `alignas(std::hardware_destructive_interference_size)`，定义于 `<new>` | C++17 及以上 | 常量由实现给出，不是运行时探测实际行大小 |
| 每线程或 per-CPU 数据 | 线程本地累加，定期汇总 | 高频计数、统计 | 汇总需同步，读到的是近似值 |
| 批量与延迟发布 | 合并写、降低共享变量更新频率 | 状态发布类业务 | 不替代同步，语义可能延迟 |
| 冷热分离 | 只读元数据与高频写状态拆成不同对象 | 读多写少混合结构 | 需要重构对象与访问路径 |
| 所有权转移 | 单写者加队列把结果传给其他线程 | 生产者消费者 | 需要设计消息协议与背压 |
| Java `@Contended` | JVM 自动填充 | JVM 性能敏感代码 | JDK 内部 API，受模块与 JVM 参数限制 |

```cpp
#include <atomic>
#include <cstdint>

struct alignas(64) PaddedCounter {      // 64 取自目标平台的行大小假设
    std::atomic<uint64_t> value{0};     // 8 B 有效数据，其余是尾部填充
};
// sizeof(PaddedCounter) 是 64 的倍数且不小于 64；两个实例的 value 不会落在同一 64 B 行
```

- `alignas` 只把对象起始地址对齐到边界；对结构体类型，编译器会把 `sizeof` 补到对齐值的整数倍。它不会让结构体内的每个成员各自独占一行，多字段场景要逐字段标注或拆对象。
- Linux 的 `__cacheline_aligned_in_smp`（对象）与 `____cacheline_aligned_in_smp`（成员）只做缓存行对齐，不会自动拆分结构体的所有成员；内核态宏不能直接用于用户态，细节见 [[Modern C++#9.4 内存对齐]]。
- 填充不是越多越好：内存占用上升会降低有效缓存容量、预取覆盖和 TLB 覆盖率，行大小也不是所有平台都等于 64 字节。
- 定位手段：`perf c2c record -- ./program` 加 `perf c2c report` 可看 Cache-to-Cache 争用最严重的行和代码位置，依赖 CPU PMU 与内核支持（具体机器支持情况待验证）。
#### 进程调度
- 调度策略 = 用户给线程"贴的标签"（我想让它怎么被调度）
- 调度类 = 内核根据标签把线程归到哪一类（这类用哪个算法）
- 调度算法 = 类内部的具体规则（怎么排、怎么抢）
- 运行队列 = 每个 CPU 上存放"等着跑的任务"的数据结构
- 调度器 = 每次切换时，从运行队列里挑下一个该跑的线程
```md
用户态看到的：   调度策略 (Scheduling Policy)
                    SCHED_NORMAL / BATCH / FIFO / RR / DEADLINE
                         │  用户通过 sched_setscheduler() 设置
                         ▼
内核中间层：     调度类 (Scheduling Class)
                    fair / rt / dl / stop / idle
                         │  一个类实现一个算法族，暴露统一接口
                         ▼
内核核心：       调度器 (Scheduler)  →  调度算法 (Algorithm)
                    遍历所有调度类，按优先级挑下一个任务
                         │
                         ▼
数据载体：       运行队列 (Run Queue)
                    每个 CPU 一套，内部按类分区存放可运行任务
```
 Linux 系统中，根据任务的优先级以及响应要求，主要分为两种，其中优先级的数值越小，优先级越高，一般分为实时任务（高优先）和普通任务（相对低优先）。为了保障高优先级的任务能够尽可能早的被执行，于是分为了这几种调度类


| 优先级 | 调度类              | 调度器          | 调度策略                                    | 算法        | 用途                 | 运行队列   |
| --- | ---------------- | ------------ | --------------------------------------- | --------- | ------------------ | ------ |
| 最高  | stop_sched_class | 停止调度器        | -                                       | 特殊        | 迁移线程/CPU 停机，必须立即执行 | -      |
| 高   | dl_sched_class   | Deadline 调度器 | SCHED_DEADLINE                          | EDF + CBS | 硬实时带宽保证            | dl_rq  |
| 中   | rt_sched_class   | RT 调度器       | SCHED_FIFO / SCHED_RR                   | 实时固定优先级   | 软实时                | rt_rq  |
| 低   | fair_sched_class | CFS 调度器      | SCHED_NORMAL / SCHED_BATCH / SCHED_IDLE | CFS       | 通用分时               | cfs_rq |
| 最低  | idle_sched_class | 空闲调度器        | -                                       | 特殊        | 空闲任务（CPU 没事干）      | -      |
Deadline 和 Realtime 这两个调度类，都是应用于实时任务的，这两个调度类的调度策略合起来共有这三种，它们的作用如下：
- _SCHED_DEADLINE_：是按照 deadline 进行调度的，距离当前时间点最近的 deadline 的任务会被优先调度；任务声明三个参数：
    - runtime：每周期最多运行多少
    - deadline：相对截止时间（从周期开始算）
    - period：周期
- _SCHED_FIFO_：高优先级可以"插队"在低优先级前面，同优先级按照 FIFO 执行，没有冲突
    - 一旦运行，一直占用 CPU，直到自己主动阻塞（sleep/I/O）、让出（sched_yield）或退出
    - 没有时间片！同优先级 FIFO 任务之间不会互相抢占
- _SCHED_RR_：对于相同优先级的任务，每个任务都有一定的时间片，当用完时间片的任务会被放到队列尾部，以保证相同优先级任务的公平性，高优先级的任务依然可以抢占低优先级的任务；
Fair 调度类是应用于普通任务，都是由 CFS 调度器管理的，分为两种调度策略：
- _SCHED_NORMAL_：绝大多数普通任务使用的调度策略，调度算法是 CFS 完全公平调度
- _SCHED_BATCH_：后台任务的调度策略，不和终端进行交互，因此在不影响其他需要交互的任务，可以适当降低它的优先级，一般是大批量，长时间的数据计算，如编译，计算等
	- 减少唤醒抢占（不因"醒了就立刻抢 CPU"）
	- 更倾向于让当前任务跑完一个较长的时间片再切换（减少切换开销）
	- 可以设 sched_autogroup 等做进一步优化

**三类调度策略对比：**

| | NORMAL/BATCH | FIFO/RR | DEADLINE |
| --- | --- | --- | --- |
| 调度类 | fair | rt | dl |
| 能否被普通任务抢占 | - | 否（普通抢不过它） | 否 |
| 能否被同类抢占 | 能（按 vruntime） | FIFO 否 / RR 能 | 能（按 deadline） |
| 是否保证带宽 | 否 | 否（可能饿死低优先级） | 是（CBS 保证） |
| 优先级表达 | nice -20~19 | sched_priority 1~99 | runtime / deadline / period |
| 主要风险 | 无 | 死循环且不 sleep 会卡死系统 | 带宽算错导致延迟 |

**FIFO vs RR 对比：**

| | SCHED_FIFO | SCHED_RR |
| --- | --- | --- |
| 时间片 | 无 | 有（默认 ~100ms，`sched_rr_get_interval` 可查） |
| 同优先级抢占 | 不抢占 | 时间片到期则放到同优先级队列末尾 |
| 自己让出 CPU | 阻塞 / `sched_yield` | 同左 + 时间片到期 |

**时效性：Linux 6.6（2023）起 fair 类 CFS 被 EEVDF 取代**
- CFS 取 vruntime 最小；EEVDF 取"虚拟截止时间"（lag + 分配的 slice）最近
- EEVDF 在 vruntime 基础上增加"期望调度延迟"维度（`sched_setattr` 的 `sched_runtime`），可精确控制每个任务的延迟与公平
- Ubuntu 24.04 内核 6.8 已是 EEVDF；但 CFS 的 vruntime / 权重 / nice 概念仍是理解 EEVDF 的基础

#### 任务调度算法
##### 完全公平调度（Completely Fair Scheduling）
算法的理念是设备是一台"理想的多任务 CPU"--假设 CPU 能以无限快的速度同时运行所有任务，每个任务分到与它权重成正比的时间。CFS 用软件模拟这个理想，让每个任务尽量接近它应得的份额。
它为每个任务安排一个虚拟运行时间 vruntime，如果一个任务在运行，其运行的越久，该任务的 vruntime 自然就会越大，而没有被运行的任务，vruntime 是不会变化的。
**在 CFS 算法调度的时候，会优先选择 vruntime 少的任务**，以保证每个任务的公平性
```
虚拟运行时间   vruntime += 实际运行时间   delta_exec * NICE_0_LOAD / 权重
```
权重值由 nice 值映射而来（可以为负数），权重越大，nice 越小，vruntime 增长越慢，运行时间越长
![优先级](../../../Files%20&%20LongText/Attachments/%E4%BC%98%E5%85%88%E7%BA%A7.webp)
我们可以在启动任务的时候，可以指定 nice 的值，比如将 mysqld 以 -3 优先级：
```bash
$ nice -n -3 /usr/sbin/mysqld
```
如果想修改已经运行中的任务的优先级，则可以使用 renice 来调整 nice 值：
```bash
$ renice -10 -p <进程pid>
```
nice 调整的是普通任务的优先级，所以不管怎么缩小 nice 值，任务永远都是普通任务，如果某些任务要求实时性比较高，那么你可以考虑改变任务的优先级以及调度策略，使得它变成实时任务，比如：
```bash
# 修改调度策略为 SCHED_FIFO，并且优先级为 1
$ chrt -f 1 -p 1996
```
**CFS 数据结构与复杂度：**
- 每 CPU 一棵红黑树，键 = vruntime，最左节点 = 下一个运行任务
- 取最左节点（vruntime 最小）：O(1)；任务入队/出队（enqueue/dequeue）：O(log n)

**切片（slice）计算：**
```c
slice = sched_latency_ns x (task_weight / cfs_rq 总权重)
```
- `sched_latency_ns` 默认 ~6ms（sysctl_sched_latency），目标是让所有可运行任务在一个周期内都轮到一次
- 任务过多时周期被拉长，用 `min_granularity`（默认 ~0.75ms）设下限，避免切换过于频繁
- 周期 = max(sched_latency_ns, nr_running x min_granularity)

**抢占逻辑：**
- 唤醒新任务时若其 vruntime 比当前任务小、且差值超过 `wakeup_granularity`（~1ms）→ 标记 `need_resched`
- 真正切换发生在从内核返回用户态的安全点（延迟抢占），所以线程切换总发生在"系统调用返回"时
#### 任务队列
每个 CPU 都有自己的**运行队列**，多任务的数量基本都是远超 CPU 核心数量，因此这时候就需要**排队**
![CPU队列](../../../Files%20&%20LongText/Attachments/CPU%E9%98%9F%E5%88%97.webp)
由于[[#进程调度|进程调度]]中，调度类也是有优先级的，Linux 选择下一个任务执行的时候，先从 `dl_rq` 里选择任务，然后从 `rt_rq` 里选择任务，最后从 `cfs_rq` 里选择任务。因此，**实时任务总是会比普通任务优先被执行**。（完整顺序为 stop → dl → rt → fair → idle，此处简写了其中可调度部分）
CFS 把可运行任务存在一个 per-CPU 的红黑树，以 vruntime 为键，最左节点就是下一个要运行的任务
**每个 CPU 的运行队列（`struct rq`）内部按调度类分区：**
```
CPU N 的运行队列 (struct rq)
├── stop 类   （迁移线程，最高）
├── dl_rq     → SCHED_DEADLINE（红黑树按 deadline 排序）
├── rt_rq     → SCHED_FIFO/RR（100 个优先级链表）
├── cfs_rq    → SCHED_NORMAL/BATCH（红黑树按 vruntime 排序）
└── idle 任务  （空闲，最低）
```
- 运行队列是 per-CPU 的，调度器只在当前 CPU 的 rq 里挑任务
- 任务在 CPU 间迁移 = 从 A 的 rq 出队（dequeue_task）+ 加入 B 的 rq（enqueue_task）
- 调度类的接口（`enqueue_task` / `dequeue_task` / `pick_next_task` / `check_preempt_curr`）就是对这组子队列的操作
## 内存和硬盘
DRAM 存储一个 bit 数据，只需要一个晶体管和一个电容就能存储，但是因为数据会被存储在电容里，电容会不断漏电，所以需要「定时刷新」电容，才能保证数据不会被丢失。内存速度大概在 `200~300` 个时钟周期之间。
内存的读写速度比 SSD 大概快 `10~1000` 倍，比机械硬盘快 `10w` 倍左右

"为了弥补 CPU 与内存两者之间的性能差异，就在 CPU 内部引入了 CPU Cache，也称高速缓存"，实际需要密闭的底层原因有这些:
- SRAM/DRAM 物理结构完全不一样，SRAM 造价极高，全 SRAM 的电脑毫无商业价值
- 光速物理极限，**电信号的传输速度（约等于光速的 2/3**，主板上的内存条和 CPU 距离限制了数据从两者之间往返会消耗 15~30 纳秒，期间 CPU 空转 50~100 个时钟周期
- 程序的"局部性原理"，**内存数据的读取不是完全随机的**，使用 cache 可以明显提高速度
### 内存分配单位与缓存行边界
来源：对话记录2（ChatGPT 导出，2026-10）
内核、分配器和 Cache 用三种粒度管理内存，操作系统不会按 64 字节把内存分组，也不会在分配时保证对象不跨 Cache Line。

| 层次 | 典型单位 | 职责 | 是否感知 Cache Line |
| --- | --- | --- | --- |
| 内核页管理 | 4 KiB 页，大页 2 MiB / 1 GiB（x86-64 常见） | 物理页分配、虚拟地址映射、换页 | 否，按页管理 |
| 分配器 | 字节块、对象（`malloc`/`new`） | 复用、合并、减少碎片 | 默认否 |
| CPU Cache | Cache Line，常见 64 字节 | 搬运、命中判断、一致性 | 是 |

- 对象可以跨行。跨行访问由硬件拆成两次行访问，部分架构有额外延迟或对齐限制；内核页映射和分配器都不负责把对象边界对齐到行边界。
- 对齐的目的有两个：满足 ISA 的访问要求（某些指令、原子操作或 SIMD 访问要求地址对齐），以及减少跨行访问和伪共享。普通 C++ 对象按类型的对齐要求分配，不默认按 64 字节对齐。
- Linux slab 分配器的 `SLAB_HWCACHE_ALIGN` 可按缓存行对齐对象，属于可选的性能优化，可能以增加内存占用为代价，不是所有分配的默认行为（[Memory Management APIs](https://cdn.kernel.org/doc/html/latest/core-api/mm-api.html)）。
- 对齐工具分三类：查询用 `alignof` / `std::max_align_t`；指定或调整用 `alignas` / `std::align`；压缩布局用 `__attribute__((packed))` / `#pragma pack` / 位域。`std::max_align_t` 满足标量类型的通用对齐，不等于 Cache Line 对齐；`std::align` 是在已有缓冲区里找对齐地址，不分配内存。
- `packed` 与 padding 方向相反：`struct { char a; int b; }` 常见布局是 `sizeof=8`、`b` 偏移 4、`alignof=4`，加 `packed` 后常见为 `sizeof=5`、`b` 偏移 1、`alignof=1`；取得 packed 成员的地址并按 `int*` 访问可能产生未对齐访问，部分架构上变慢或触发异常。位域的位序和存储单元由 ABI 决定，不适合直接作为网络协议或持久化格式。详细语法与示例见 [[Modern C++#9.4 内存对齐]]。
# 系统结构篇
## 中断
CPU 默认是顺序执行的，但现实世界充满异步事件，CPU 只能通过**轮询或者中断**的方式处理这些异步事件，轮询无疑是低效的。
中断的定义就是: **一种硬件机制**，让 CPU 在执行当前指令流的过程中，被一个异步事件"打断"，跳去执行一段专门的代码，处理完再回来接着原来的指令继续。
### 中断和异常的区别

|          | 中断（Interrupt） | 异常（Exception）    |
| :------- | :------------ | :--------------- |
| **触发方式** | 异步，外部硬件事件     | 同步，当前指令本身导致      |
| **例子**   | 网卡、定时器、键盘     | 除零、缺页、非法指令       |
| **谁发起**  | 外部设备 / 其他 CPU | 指令执行过程中 CPU 自己发现 |
| **能否恢复** | 能，处理完继续       | 多数能（缺页），部分致命（除零） |
两者在 x86 上共用同一套机制（IDT 中断描述符表），Linux 把它们统称为"中断/异常"统一处理
### 中断处理
  每个中断有一个中断向量号（0~255），对应 IDT 里的一项。完整流程：
```md
  设备发出中断请求 → 中断控制器（PIC/APIC）→ 给 CPU 发中断信号
                                                      │
                                                      ▼
  1. CPU 执行完当前指令（指令边界）                       │
  2. 检查 IF 标志（中断使能位）                           │
     中断使能 → 开始处理                                 │
  3. 把当前程序的现场压栈：                               │
     - RFLAGS（标志寄存器）                             │
     - CS / RIP（下一条指令地址）-- 这样处理完能回来        │
     - （若发生特权级切换还压 SS/RSP）                    │
  4. 根据向量号查 IDT，找到处理函数地址                    │
  5. 跳转到处理函数执行                                  │
     （中断门会清 IF，暂时屏蔽同级中断，防嵌套）            │
  6. 处理完毕执行 IRET（中断返回指令）                    │
     - 从栈上恢复 RFLAGS / CS / RIP                    │
     - 回到被打断的指令继续执行                           │
                                                      ▼
```
被中断的程序自己不知道发生了中断--它只是"暂停-恢复"，现场被硬件自动保存和恢复
### 中断处理程序
为了避免由于中断处理程序执行时间过长，而影响正常进程的调度，Linux 将中断处理程序分为上半部和下半部：
```md
┌─────────────────────────────────────────────────────────┐
│  上半部（硬中断）                                         │
│  · 立即执行，处理最紧急的事                             │
│  · 由硬件触发中断，用来快速处理中断；、读设备状态              │
│  · 把要做的重活"登记"给下半部                           │
│  · 必须极快返回（微秒级）                               │
│  · 运行在"中断上下文"，不能 sleep                        │
├─────────────────────────────────────────────────────────┤
│  下半部（软中断）                                          │
│  · 延迟执行真正的工作，由内核触发中断，用来异步处理上半部未完成的工作 │
│  · 三种实现：softirq / tasklet / workqueue                │
│  · 可以（在合适条件下）sleep、被调度                         │
└─────────────────────────────────────────────────────────┘
```
硬中断中**不能 `sleep`**，因为 sleep 是调用系统调度器，将当前进程的线程**切换出去**，而中断处理程序的代码在**借用的内核线程栈**中运行，运行硬中断时**屏蔽了所有中断和抢占**，不在任何可调度线程的上下文里，sleep 结束后无法通过上下文恢复现场，内核崩溃
底层实现是在内核太使用 spinlock 自旋锁执行程序
Linux 中的软中断包括网络收发、定时、调度、RCU 锁等各种类型，可以通过查看 `/proc/softirqs` 来观察软中断的累计中断次数情况，如果要实时查看中断次数的变化率，可以使用 `watch -d cat /proc/softirqs` 命令。

每一个 CPU 都有各自的软中断内核线程，用 ps 命令查看内核线程，一般名字在中括号里面的，都认为是内核线程。
![ksoftirqd](../../../Files%20&%20LongText/Attachments/ksoftirqd.webp)
现代系统每个 CPU 都能接收中断，由 APIC（高级可编程中断控制器） 决定投递目标：
```
中断源
├── 本 CPU 本地中断（LAPIC）：定时器、本地设备 → 投递给本地 CPU
├── I/O APIC：外部设备（网卡等）→ 可编程路由到任意 CPU
└── IPI（处理器间中断）：一个 CPU 主动打断另一个 CPU
	 ├── 用于 TLB 刷新（改页表后通知所有核）
	 ├── 用于调度（让别的核重新选任务）
	 └── 用于函数调用（call_function）
```
**上半部"借用"线程栈**，中断处理程序不是线程，它是在接收中断的那个 CPU 上，直接打断当前正在跑的线程，借用它的内核栈执行：
```md
CPU 0 正在跑用户线程 X（用户态）
	  │
	  ▼  网卡中断到达 CPU0
	  │
	  ▼  CPU 硬件压栈，切换到内核态
	  │
	  ▼  执行中断上半部（借用线程 X 的内核栈）
	  │
	  ▼  登记下半部，IRET 返回
	  │
	  ▼  线程 X 继续运行（完全无感知）
```
"跨线程"的本质： 中断处理程序抢占了当前线程，而不是"在另一个线程里运行"。被中断的线程是谁完全随机--取决于中断那一刻哪个线程在跑。
**下半部：真正的"跨线程跨 CPU"桥梁**

| 下半部类型         | 运行上下文                   | 能否 sleep | 能否跨 CPU         |
| :------------ | :---------------------- | :------- | :-------------- |
| **softirq**   | 中断上下文（或 ksoftirqd 内核线程） | 否        | 本 CPU 上执行       |
| **tasklet**   | 中断上下文                   | 否        | 只在本 CPU（谁调度谁执行） |
| **workqueue** | 进程上下文（kworker 内核线程）     | 能        | 可迁移到其他 CPU      |
```
中断上半部（CPU0）
  │
  ▼  把工作丢进 workqueue
  │
  ▼  唤醒 kworker 内核线程（一个真正的、可被调度的线程）
  │
  ▼  kworker 可能被调度到 CPU2 上执行！
  │
  ▼  在那里完成真正的工作（读数据、唤醒用户进程等）
现代内核支持 request_threaded_irq，把中断处理整个变成一个内核线程：

传统模式：                          中断线程化模式：
设备中断                            设备中断
  │                                    │
  ▼                                    ▼
CPU 硬件打断（借用线程栈）            唤醒内核线程 irq/24-driver
  │                                    │
  ▼                                    ▼
上半部：快，不能 sleep              处理线程：一个真正可调度的线程
  │                                    │  可以 sleep、可以被抢占、
  ▼                                    ▼  可以跨 CPU 迁移
下半部（workqueue 等）                在线程里完成全部工作

代价：多一次线程调度延迟
收益：处理逻辑可以复杂化，不必拼性能
```
整个中断处理逻辑
```

用户线程 X 运行在 CPU0
        │
        ▼  中断发生（异步）
        │
        ▼  ┌── 硬件层：APIC 决定投递到 CPU0 ──┐
        │  │  IRQ affinity 可手动控制         │
        │  └────────────────────────────────┘
        ▼
        ▼  ┌── 上半部：借用线程X的内核栈 ──────┐
        │  │  不能 sleep、极快返回            │
        │  │  "跨线程"= 抢占线程X，不是新线程  │
        │  └────────────────────────────────┘
        ▼
        ▼  ┌── 下半部（三种策略）────────────┐
        │  │  softirq/tasklet：本 CPU，上下文│
        │  │  workqueue：kworker 线程        │
        │  │   → 可 sleep、可迁移到 CPU2     │
        │  │   → 这才是真正的"跨线程跨CPU"    │
        │  └────────────────────────────────┘
        ▼
IRET 返回，线程 X 继续
```

## 内核
计算机是由各种外部硬件设备组成的，比如内存、cpu、硬盘等，如果每个应用都要和这些硬件设备对接通信协议，**让内核作为应用连接硬件设备的桥梁**，应用程序只需关心与内核交互，不用关心硬件的细节。内核，就是硬件的一种低级抽象
内核一般会提供 4 个基本能力：
- 决定哪个进程、线程使用 CPU，也就是进程调度的能力；
- 内存的分配和回收，也就是内存管理的能力；
- 为进程与硬件设备之间提供通信能力，也就是硬件通信能力；
- 如果应用程序要运行更高权限运行的服务，那么就需要有系统调用，它是用户程序与操作系统之间的接口。

## 虚拟内存
操作系统是管理虚拟地址与物理地址的映射关系，主要有**内存分段和内存分页**方式
### 内存结构
![575](../../../Files%20&%20LongText/Attachments/4956918c43e186d49df7b9802f080de8%201.webp)
通过内存地址划分，虚拟内存地址的高 16 位全部为 0 ，那么我们就可以直接判断出这是一个用户空间的虚拟内存地址，如果高 16 位全为 1，就是内核地址虚拟空间
![400](../../../Files%20&%20LongText/Attachments/532e6cdf4899588f8b873b6435cba2d8-20230309233823236.webp)
内核通过 `task_struct` 管理虚拟内存空间的所有区域，将不同的区域抽象为指针，其中 `mm_struct` 是用户空间的抽象
![675](../../../Files%20&%20LongText/Attachments/2b2dbb2b6ea19871152a3bf6566df205.webp)
每个分段通过 `vm_area_struct` 结构体表示，其中 `vm_start/vm_end` 用于标记开始和结束位置，vm_page_prot 和 vm_flags 都是用来标记 vm_area_struct 结构表示的这块虚拟内存区域的访问权限和行为规范，由一个标识位通过*位掩码技术*标记权限
![525](../../../Files%20&%20LongText/Attachments/600ef23c454d9f3653ece44debaaf3a7.webp)
### 分段机制
分段机制下的虚拟地址由两部分组成，**段选择因子**和**段内偏移量**
![a9ed979e2ed8414f9828767592aadc21](../../../Files%20&%20LongText/Attachments/a9ed979e2ed8414f9828767592aadc21.webp)
- **段选择因子**保存在段寄存器里面。段选择子里面最重要的是**段号**，用作段表的索引。**段表**里面保存的是这个**段的基地址、段的界限和特权等级**等。
- 虚拟地址中的**段内偏移量**应该位于 0 和段界限之间，如果段内偏移量是合法的，就将段基地址加上段内偏移量得到物理内存地址。
- ***段表存放在普通物理内存中，由段存器中存储指针***
![c5e2ab63e6ee4c8db575f3c7c9c85962](../../../Files%20&%20LongText/Attachments/c5e2ab63e6ee4c8db575f3c7c9c85962.webp)
又是 TLV 结构的布局，记录起始位置，长度和偏移量
存在的问题:
- 内存碎片，每个应用程序占用长度动态变化，且长度不一，不同内存块之间必然会有"空隙"，这就需要内存交换技术解决，安装系统时的交换分区就用来做这个
- 内存交换效率低，内存和硬盘上的速度差距导致大程序数据交换到硬盘中耗时长
### 内存分页机制
分页把虚拟地址空间和物理内存都切成固定大小的**页**（默认 4KB），通过**页表**记录虚拟页 → 物理页的映射，由 **MMU（内存管理单元，硬件）** 完成翻译。

**分页与分段的本质区别：**

|       | 分段        | 分页               |
| ----- | --------- | ---------------- |
| 划分单位  | 逻辑段（大小不一） | 固定页（4KB）         |
| 碎片问题  | 外部碎片严重    | 无外部碎片（内部碎片 ≤1 页） |
| 交换/回收 | 整段交换，低效   | 按页交换，高效          |
| 保护粒度  | 段级        | 页级（R/W/X/U-S）    |

> [!note] 与 mmap 的关系
> `mmap` 返回虚拟地址时物理页并不存在，第一次访问触发缺页才填充--所以 mmap 文件是**懒加载**的

换入换出的单位是 4kb 固定大小，且排列紧密，不再需要一次性都把程序加载到物理内存中。在进行虚拟内存和物理内存的页之间的映射之后，并不真的把页加载到物理内存里，而是**只有在程序运行中，需要用到对应虚拟内存页里面的指令和数据时，再加载到物理内存里面去**，形成了虚拟地址+页表+物理地址+硬盘四级结构
![388a29f45fe947e5a49240e4eff13538-20230309234651917](../../../Files%20&%20LongText/Attachments/388a29f45fe947e5a49240e4eff13538-20230309234651917.webp)
分页方式的虚拟地址和物理地址映射关系相对于[[#分段机制|分段机制]]省去了基地址和长度，因为这两者都是固定的，只需要页号和页内偏移量即可定位
![7884f4d8db4949f7a5bb4bbd0f452609](../../../Files%20&%20LongText/Attachments/7884f4d8db4949f7a5bb4bbd0f452609.webp)

**页表存储在普通物理内存中，由寄存器定位：**
- 页表基址存在 **CR3 寄存器**，四级页表（PML4/PDPT/PD/PT）每一级都是一张内存中的表
- 进程切换 → OS 换 CR3 → 新页表 → TLB 全部失效（上下文切换贵的硬件原因）
- 段表同理：GDT 基址在 GDTR，内核启动时建立、全局唯一；x86-64 Linux 已基本不用段（base 全 0），只留 FS/GS 给 TLS

**为什么地址要分"页号 + 页内偏移"：**
程序访问的最小单位是**字节**而非页。页号决定"哪一页"，偏移决定"页内第几个字节"，两者缺一不可。页内偏移**原封不动透传**（映射页对齐，物理页起点永远在 4KB 边界）：
```
虚拟地址 0x1234_5678
  偏移 = 0x678（低 12 位）
  页号 = 0x12345（高 20 位）
页表：0x12345 → 物理页号 0x9ABCD
物理地址 = 0x9ABCD000 | 0x678 = 0x9ABCD678
```

简单分页的缺陷:
在 32 位的环境下，虚拟地址空间共有 4GB，假设一个页的大小是 4KB（2^12），需要有 `4MB` 的内存来存储页表。而虚拟内存每个进程一个，所以 100 个进程需要 400MB 存储页表，这不现实
### 多级页表机制
![19296e249b2240c29f9c52be70f611d5](../../../Files%20&%20LongText/Attachments/19296e249b2240c29f9c52be70f611d5.webp)

每个进程都有 4GB 的虚拟地址空间，由于*空间局部性原理*，而对于大多数程序来说用到的空间远未达到 4GB，因为会存在部分对应的页表项都是空的，根本没有分配。所以多级页表对于没有用到的内存**不分配/创建次级页表**，这部分空间只是在逻辑上存在，只在用到时才会创建。
对于已分配的页表项，如果存在最近一定时间未访问的页表，在物理内存紧张的情况下，操作系统会将页面换出到硬盘

> [!question] 为什么不分级的页表就做不到这样节约内存？
> 从页表的性质来看，保存在内存中的页表承担的职责是将虚拟地址翻译成物理地址。假如虚拟地址在页表中找不到对应的页表项计算机系统就不能工作。所以**页表一定要覆盖全部虚拟地址空间**，不分级的页表一定会造成大量空间浪费
**x86-64 四级页表翻译：**
```
虚拟地址 48 位划分：
┌─────┬─────┬─────┬─────┬────────┐
│ PML4│ PDPT│  PD │  PT │ 偏移    │
│  9b │  9b │  9b │ 9b  │ 12b    │
└─────┴─────┴─────┴─────┴────────┘
- 全局页目录项 PGD（Page Global Directory）；
- 上层页目录项 PUD（Page Upper Directory）；
- 中间页目录项 PMD（Page Middle Directory）；
- 页表项 PTE（Page Table Entry）；

每级 512 项；页大小 4KB
也支持 2MB / 1GB 大页（少遍历级数，TLB 命中率更高）
```
![四级分页](../../../Files%20&%20LongText/Attachments/%E5%9B%9B%E7%BA%A7%E5%88%86%E9%A1%B5.webp)

**TLB（Translation Lookaside Buffer）：** 页表翻译结果在 CPU 中的缓存，用于解决多级页表带来的跳转开销，因翻译问题也可以称为**页表缓存、转址旁路缓存、快表**
- 命中：1 周期拿到物理地址
- 未命中：遍历 4 级页表（数百周期）
- **为什么上下文切换贵：** 切换进程 → 换页表 → TLB 失效 → 新进程首次访问全部 miss
**按需分页（Demand Paging）与缺页中断：**
```
进程访问某虚拟地址
  ▼
MMU 查页表：存在位 = 0（虚拟页在，物理页未分配）
  ▼
缺页中断（page fault）→ 内核处理：
  ├─ 匿名页：分配物理页并清零
  ├─ 文件映射页：从磁盘读内容到物理页（懒加载！）
  ├─ 写时复制（COW）：fork 后父子共享只读页，谁先写谁复制
  └─ 换页（swap）：物理内存不足时把页写回磁盘腾空间
  ▼
建立映射，返回用户态重新执行该指令
```
![四级分页](../../../Files%20&%20LongText/Attachments/%E5%9B%9B%E7%BA%A7%E5%88%86%E9%A1%B5.webp)
进程虚拟地址空间一般是 2 的 48/57 次幂**字节**的原因：
- 多级页表因为**地址太大会降低缓存命中效率**
- 深度太深（虚拟地址空间大到必须要纵向拓展，5 级页表最多支持 2 的 57 次幂字节地址空间）也会导致多次跳转的开销，完整 64 位寻址需要更好的 CPU
### 段页式内存管理
![f19ebd6f70f84083b0d87cc5e9dea8e3](../../../Files%20&%20LongText/Attachments/f19ebd6f70f84083b0d87cc5e9dea8e3.webp)
- 先将程序划分为多个有逻辑意义的段，也就是前面提到的分段机制；
- 接着再把每个段划分为多个页，也就是对分段划分出来的连续空间，再划分固定大小的页；
很自然，地址结构就由**段号、段内页号和页内位移**三部分组成。
段页式地址变换中要得到物理地址须经过三次内存访问：
- 第一次访问段表，得到页表起始地址；
- 第二次访问页表，得到物理页号；
- 第三次将物理页号与页内位移组合，得到物理地址。
需要注意:
- 每个进程有自己的页表，无法访问其他人的，因为虚拟内存是逻辑上相互隔离的
- 页表里的页表项中除了物理地址之外，还有一些标记属性的比特，比如控制一个页的读写权限，标记该页是否存在等
### linux 内存管理模型
![3a6cb4e3f27241d3b09b4766bb0b1124-20230309234553726](../../../Files%20&%20LongText/Attachments/3a6cb4e3f27241d3b09b4766bb0b1124-20230309234553726.webp)
每个进程都各自有独立的虚拟内存，但是**每个虚拟内存中的内核地址，其实关联的都是相同的物理内存**。这样，进程切换到内核态后，就可以很方便地访问内核空间内存。
![48403193b7354e618bf336892886bcff](../../../Files%20&%20LongText/Attachments/48403193b7354e618bf336892886bcff.webp)
### 进程虚拟地址空间的隔离与共享
每个进程通过自己的页表把虚拟地址映射到物理页。同一个虚拟地址在不同进程中可以映射到不同物理页，实现隔离；多个进程的虚拟页也可以映射到同一物理页，实现共享内存、共享库映射或写时复制。隔离与共享使用的是同一套页表映射机制。

常见系统会划分用户空间和内核空间。内核映射在进程切换到内核态后供内核访问，页表权限仍阻止用户态直接读写内核地址。具体映射边界受体系结构、内核配置和安全缓解措施影响；例如启用 KPTI 时，用户态页表可能不保留完整内核映射。
#### ELF 映射、线程与写时复制
ELF 加载器主要按 program header 映射 segment；`.text`、`.data`、`.bss` 等 section 是文件组织概念，不能简单视作运行时独立区域。程序映射、堆、共享库和文件映射区、线程栈等共同组成进程虚拟地址空间。共享库的只读代码页可映射到多个进程。

同一进程的线程共享代码、全局数据、堆和多数映射；每个线程有独立栈、寄存器上下文和线程局部存储（TLS），但这些区域仍位于同一进程地址空间。`fork()` 后父子进程可暂时共享物理页；写入时内核复制相应页并更新页表，形成写时复制（Copy-on-Write，COW）。
## malloc/free 如何管理内存
### malloc 申请内存
malloc 申请内存的时候，会有两种方式向操作系统申请堆内存。申请的空间在进程内存模型中，所以申请的是虚拟内存
- 方式一：通过 brk() 系统调用从堆分配内存
![brk申请](../../../Files%20&%20LongText/Attachments/brk%E7%94%B3%E8%AF%B7.webp)
- 方式二：通过 mmap() 系统调用在文件映射区域分配内存；
![mmap申请](../../../Files%20&%20LongText/Attachments/mmap%E7%94%B3%E8%AF%B7.webp)
malloc 分配内存并**不会按照传入参数的大小分配对应大小内存**，`malloc(1)` 会分配大约 132K，而且起始地址（`malloc()` 返回值的指针指向的位置，通过取地址得到）和 `/proc/pid/maps` 中记录的内存起始地址不一致，取地址得到的会比文件中记录的大 16 字节，这个区域用来存储内存块头部信息
![2b8f63892830553ec04c5f05f336ae8b](../../../Files%20&%20LongText/Attachments/2b8f63892830553ec04c5f05f336ae8b.webp)
`/proc/pid/maps` 中记录的内存信息可以看到分配在堆上还是 mmap 区域
![cb6e3ce4532ff0a6bfd60fe3e52a806e 1](../../../Files%20&%20LongText/Attachments/cb6e3ce4532ff0a6bfd60fe3e52a806e%201.webp)
头部信息中存储了内存块长度，这也就是为什么 free 函数在**仅仅传入指针时可以知道需要释放多少空间**
### free 释放内存
使用 free 函数后，如果这块内存是 malloc 通过 `brk()` 申请的，那么 free 后堆内存**依然存在**，只会先缓存着放进 malloc 的内存池里，如果是 `mmap()` 申请的就会将内存还给操作系统，通过 `munmap()`
### 为什么不全使用 mmap 分配内存
**mmap 开销大：** 每次调用都要进内核态：找空闲地址空间、设置页表项、清空内存页、更新内核结构，外加系统调用与 TLB 刷新开销。小块内存频繁分配/释放时性能极差。
**brk 的价值：** 本质是挪动 `program break` 指针伸缩堆区。malloc 预先用 `brk` 一次扩大一大块，在用户空间像"切豆腐"一样切小块分配；free 不立即还系统，而是记入空闲链表复用，只有当堆顶整块连续空闲才用 `brk` 缩回。大量频繁小内存申请在用户态完成，系统调用开销摊薄。
**brk 的局限：** 堆区连续，中间被小块占满时即使总空闲足够也找不到连续大块（内部碎片）；且堆只能向一个方向（向上）生长。

**malloc 的组合策略：**

| 请求 | 方式 | 原因 |
| ---- | ---- | ---- |
| 小内存、频繁 | `brk` 堆区 | 用户态搞定，速度快 |
| 大内存（超阈值 ~128KB） | `mmap` 单独映射 | 避免堆区大洞（外部碎片），释放立即归还系统 |

小结：`mmap` 灵活干净但开销大，`brk` 快但对大块和碎片敏感。全用 `mmap` 则小内存频繁分配慢；全用 `brk` 则大内存或长期运行碎片化可能分配不出。所以 malloc 混合使用，各取所长。
### 为什么不全部使用 brk 来分配？
堆的生长方向固定，且由于其延迟归还的特性，free 的内存还在堆中存在会导致空闲内存块和有效内存块交织产生内存碎片，在频繁 malloc 和 free 的场景下会导致内存泄漏
![75edee0cb75450e7987a8a482b975bda](../../../Files%20&%20LongText/Attachments/75edee0cb75450e7987a8a482b975bda.webp)
### 如何判断内存分配在堆（brk）还是 mmap 区域
- **看 `/proc/<pid>/maps`**：brk 堆在低地址（紧跟可执行文件段，标签 `[heap]`）；mmap 在高地址（靠近栈，匿名映射无标签）
- **按大小判断**：glibc 默认 `M_MMAP_THRESHOLD = 128KB`，超过走 mmap，以下走 brk
- **代码判断**：返回地址在 `sbrk(0)`（program break）之下即 brk 堆
```cpp
#include <unistd.h>
bool isOnHeap(void* p) { return p < sbrk(0); }
```
### mmap 分配的内存有块头部吗？能双向生长吗？
**头部信息：** mmap 分配的内存**没有堆区那种参与空闲链表管理的块头部**。内核层面整块映射由 VMA（vm_area_struct）管理，长度记录在内核结构里；glibc 只在块起始处写一个标记头（记录长度 + mmap 标志），free 时据此**整块 `munmap` 归还**，不参与用户态空闲链表合并。
**生长方向：**
- brk 堆：**只能单向**向高地址生长（program break 只有一个）
- mmap 区域整体：可以双向找空闲地址（每次独立映射）
- **单个 mmap 映射：大小固定，不能生长**（要更大必须重新 mmap），与 brk"尾巴可伸缩"本质不同
## 内存满了会怎么样
### 内存分配的过程
应用程序通过 malloc 函数申请虚拟内存，此时不会实际上分配内存（不会在页表中链接到实际的物理内存地址）
当应用程序读写了这块虚拟内存，CPU 访问时会发现虚拟内存没有映射到物理内存， CPU 就会产生**缺页中断**，进程会从用户态切换到内核态，并将缺页中断交给内核的 Page Fault Handler （缺页中断函数）处理。
如果有空闲的**物理**内存就分配，在页表中记录映射关系，没有则开始内存回收（注意这不是 gc），有两种回收方式:
- **后台内存回收**（kswapd）：唤醒 kswapd 内核线程来回收内存，这个回收内存的过程**异步**的，不会阻塞进程的执行。
- **直接内存回收**（direct reclaim）：如果后台异步回收跟不上进程内存申请的速度，就会开始直接回收，这个回收内存的过程是**同步**的，会阻塞进程的执行。
如果回收后还是无法满足申请要求，进入 OOM 处理机制
OOM Killer 机制会根据算法选择一个占用物理内存较高的进程，然后将其杀死，不断杀死进程直到满足
![2f61b0822b3c4a359f99770231981b07](../../../Files%20&%20LongText/Attachments/2f61b0822b3c4a359f99770231981b07.webp)
### 哪些内存可以被回收？
- **文件页**（File-backed Page）：内核缓存的磁盘数据（Buffer）和内核缓存的硬盘文件数据（Cache）都叫作文件页。**回收干净页的方式是直接释放内存，回收脏页的方式是先写回磁盘后再释放内存**。
- **匿名页**（Anonymous Page）：这部分内存没有实际载体，比如堆、栈数据等。这部分内存很可能还要再次被访问，所以不能直接释放，**回收的方式是通过 Linux 的 Swap 机制**，Swap 会把不常访问的内存先写到交换分区，然后释放这些内存，需要时再次读入
回收内存**在没有磁盘 IO 的情况下不会影响性能**，决定那些页被回收使用的是 LRU 算法，为了尽量避免内存回收带来的性能印象，可以通过这些方式优化:
- Linux 提供了一个 `/proc/sys/vm/swappiness` 选项（范围是 0-100），用来调整文件页和匿名页的回收倾向。
- 尽早触发 kswapd 内核线程异步回收内存，内核定义了三个内存阈值（watermark，也称为水位），用来衡量当前剩余内存（pages_free）kswapd 会定期扫描内存的使用情况是否充裕或者紧张，并作出决策：
	- 页最小阈值（pages_min），小于这个值触发*直接回收*
	- 页低阈值（pages_low），小于这个值触发*后台回收*
	- 页高阈值（pages_high）
![166bc9f5b7c545d89f1e36ab8dd772cf](../../../Files%20&%20LongText/Attachments/166bc9f5b7c545d89f1e36ab8dd772cf.webp)
页低阈值（pages_low）可以通过内核选项 `/proc/sys/vm/min_free_kbytes` （该参数代表系统所保留空闲内存的最低限）来间接设置。
- 如果关注延迟那就适当地增大 min_free_kbytes
- 如果关注内存的使用量那就适当地调小 min_free_kbytes。
### 如何保护一个进程不被 OOM 杀掉
Linux 内核里有一个 `oom_badness()` 函数，它会把系统中可以被杀掉的进程扫描一遍，并对每个进程打分，得分最高的进程就会被首先杀掉。
得分的结果受两者影响：
- 进程已经使用的物理内存页面数。
- 每个进程的 OOM 校准值 oom_score_adj。可以通过 `/proc/[pid]/oom_score_adj` 来配置的。可设置 `-1000~1000` 整数，调整进程被 OOM Kill 的几率。
算法为:
```cpp
// points 代表打分的结果
// process_pages 代表进程已经使用的物理内存页面数
// oom_score_adj 代表 OOM 校准值
// totalpages 代表系统总的可用页面数
points = process_pages + oom_score_adj*totalpages/1000
```
### 申请内存超过物理内存会怎么样
malloc 申请的是虚拟内存，在 CPU 没有访问这些内存地址时是不会触发缺页中断关联物理内存的，所以理论上没有申请满虚拟内存就不会触发 OOM。
但实际上 linux 中申请内存有限制，和 overcommit_memory 参数有关，可以使用 `cat /proc/sys/vm/overcommit_memory` 来查看这个参数，这个参数接受三个值：
- 如果值为 0（默认值），代表：Heuristic overcommit handling，它允许overcommit，但过于明目张胆的overcommit会被拒绝，比如malloc一次性申请的内存大小就超过了系统总内存。Heuristic的意思是"试探式的"，内核利用某种算法猜测你的内存申请是否合理，大概可以理解为单次申请不能超过free memory + free swap + pagecache的大小 + SLAB中可回收的部分 ，超过了就会拒绝overcommit。
- 如果值为 1，代表：Always overcommit. 允许overcommit，对内存申请来者不拒。
- 如果值为 2，代表：Don’t overcommit. 禁止overcommit。
并且，如果没有开启 swap 交换分区，申请物理内存大小超过了空闲物理内存大小，程序就会直接 OOM，否则程序可以正常运行。
Linux 提供了两种不同的方法启用 Swap，分别是 Swap 分区（Swap Partition）和 Swap 文件（Swapfile），开启方法[参考](https://support.huaweicloud.com/trouble-ecs/ecs_trouble_0322.html)：
- Swap 分区是硬盘上的独立区域，该区域只会用于交换分区，其他的文件不能存储在该区域上，我们可以使用 `swapon -s` 命令查看当前系统上的交换分区；
- Swap 文件是文件系统中的特殊文件，它与文件系统中的其他文件也没有太多的区别；
所以问题的结论是:

- 在 32 位操作系统，申请**超过 3GB 的内存一定会 OOM**
- 在 64 位位操作系统，申请的小于 128TB 的空间在 `overcommit_memory = 1` 时不会有问题。如果这块虚拟内存被访问了，要看系统有没有 Swap 分区：
    - 如果没有 Swap 分区，因为物理空间不够，进程会被操作系统杀掉，原因是 OOM（内存溢出），报错 `cannot allocate memory`
    - 如果有 Swap 分区，即使物理内存只有 4GB，程序也能正常使用 8GB 的内存，进程可以正常运行；
## 预读失效和缓存污染
![提问](../../../Files%20&%20LongText/Attachments/%E6%8F%90%E9%97%AE.webp)
系统级（Linux 页缓存）和数据库（InnoDB Buffer Pool）都以页为基本单元、用 [[常用算法和情景处理#LRU|LRU 算法]] 管理缓存，都会遇到**预读失效**和**缓存污染**两个问题
### 预读机制
Linux 操作系统为基于 Page Cache 的读缓存机制提供**预读机制**（readahead，`mm/readahead.c`）
- 应用程序只想读取磁盘上文件 A 的 offset 为 0-3KB 范围内的数据，操作系统至少会读 0-4KB 的内容，这恰好可以在一个 page 中装下。
- 但是操作系统出于空间局部性原理，选择将磁盘块 0~16kb 位置的页都加载到内存，额外在内存中申请了 3 个 page；
![ae8252378169c8c14b8b9907983f7d8b](../../../Files%20&%20LongText/Attachments/ae8252378169c8c14b8b9907983f7d8b.webp)
如果预读进来的页**从来没有被访问**，预读就白做了，称为**预读失效**：白占磁盘 I/O 带宽，预读页还占据缓存，把可能活跃的页挤出去。

预读会让大量**暂时无关**的页进入 LRU，纯 LRU 分不清「新进来但马上会反复访问」和「只用一次」的页，Linux 改用**双链表 LRU**（`mm/vmscan.c`）：
- **active list**：活跃页（最近被访问过、访问次数 ≥ 2）；
- **inactive list**：不活跃页（新读入/预读页先放这里）；
- 新页**先进 inactive**，第二次被访问（`PG_referenced` 标志，`mark_page_accessed()`）才提升到 active；
- 回收时**优先回收 inactive**，预读页和一次性页很快被换出，不会挤掉 active 里的热页（「两次机会」策略）。

> [!info] 延伸：refault distance
> Linux 还用 shadow entry 记录页被换出前的访问历史（`mm/workingset.c`），若某页换出后**很快又被访问**（refault 距离小），说明它是热页，会被提前调回并保护。
### 缓存污染
即使按「被访问一次就放入活跃 LRU 头部」处理，仍存在**缓存污染**：
- 本质：**只访问一次就不再访问**的数据（全表扫描、大文件一次性遍历）占据缓存，把有局部性、会被反复访问的**热数据**挤出，命中率骤降；
- 预读失效是污染的**重要来源之一**，但污染不限于此：真正被访问过、但只用一次的数据同样污染缓存。
Linux 操作系统和 MySQL Innodb 存储引擎分别是这样提高门槛的：
- **Linux 操作系统**：在内存页被访问**第二次**时，从 inactive list 升级到 active list
- **MySQL Innodb**：在内存页被访问**第二次**的时，并不会马上将该页从 old 区域升级到 young 区域，因为还要进行**停留在 old 区域的时间判断**：
    - 如果第二次的访问时间与第一次访问的时间**在 1 秒内**（默认值），那么该页就**不会**被从 old 区域升级到 young 区域；
    - 如果第二次的访问时间与第一次访问的时间**超过 1 秒**，那么该页就**会**从 old 区域升级到 young 区域；

### 对比

|     | 预读失效                    | 缓存污染              |
| --- | ----------------------- | ----------------- |
| 本质  | 预读的页从未被访问               | 只用一次的数据把热数据挤出缓存   |
| 触发  | readahead 预测错误（稀疏/跳跃访问） | 扫描型访问（全表扫描、大文件遍历） |
| 危害  | 浪费磁盘 I/O + 占据缓存         | 命中率骤降、热页被换出       |
| 关系  | 是污染的来源之一                | 范围更广（含「用过一次」的数据）  |

# 零碎知识
## 内存屏障：thread_fence 与 signal_fence
**`std::atomic_thread_fence`（跨线程，可能发射 CPU 指令）：** 独立于原子操作的围栏，用于跨线程同步。可与 relaxed 原子操作配对：
```cpp
// 线程 1
data = 42;                                              // 普通写
std::atomic_thread_fence(std::memory_order_release);    // 独立 release 围栏
ready.store(true, std::memory_order_relaxed);           // relaxed 写标志
// 线程 2
while (!ready.load(std::memory_order_relaxed)) {}       // relaxed 读标志
std::atomic_thread_fence(std::memory_order_acquire);    // 独立 acquire 围栏
use(data);   // 保证读到 42
```
- 围栏与原子操作**分离**，这是"操作附着 acquire/release"的等价写法
- x86 上 `seq_cst` 围栏 → `mfence`；`acquire/release` 围栏 → 通常无额外指令（x86 TSO 已保证）

**`std::atomic_signal_fence`（同线程被信号打断，纯编译器屏障）：**
- **只阻止编译器重排，不发射任何 CPU 指令**（GCC/Clang 上等价于 `asm volatile("" ::: "memory")`）
- **为什么不需要 CPU 指令？** 信号处理函数与主程序运行在**同一线程/同一 CPU**，无跨核 cache 一致性问题，只需阻止编译器把共享变量写入重排

**对比：**

| | `atomic_signal_fence` | `atomic_thread_fence` |
|---|---|---|
| 作用对象 | 同线程 + 信号处理函数 | 不同线程 |
| 发射 CPU 指令 | 否（纯编译器屏障） | 可能（seq_cst → `mfence`） |
| 编译器屏障 | 是 | 是 |

**一句话：** thread_fence 管"CPU 间的可见性"，signal_fence 只管"编译器别乱排"

## DMA（直接内存访问）
**问题：** 无 DMA 时（PIO 方式），CPU 收到中断后要逐字节从设备寄存器搬到内存，1500 字节的包占满 CPU。

**DMA = 设备通过 DMA 引擎/控制器，绕过 CPU 直接在设备与内存之间搬数据：**
```
网卡收包（现代模式）：
1. 驱动启动时分配 DMA 缓冲区，填好描述符环（RX Ring）
2. 网卡收到包 → 内部 DMA 引擎直接把包写入内存（CPU 不参与！）
3. 网卡发中断给 CPU："DMA 完成"
4. CPU 处理中断，直接读内存里的包
```
**关键细节：**
- **总线主控（Bus Master）：** DMA 引擎能主动读写内存，无需 CPU 代为访问
- **DMA 缓冲区：** 必须物理连续或经 IOMMU/散射表映射，驱动用 `dma_alloc_coherent` 分配
- **Cache 一致性：** 设备写内存后 CPU cache 可能还是旧值 → 需要 coherent DMA 或手动刷 cache
- **与中断的关系：** DMA 完成 → 设备发中断通知 CPU
- **与 mmap 的关系：** "mmap 零拷贝"本质就是让应用直接访问 DMA 写入的物理页

**一句话：** DMA 让"设备→内存"的数据搬运不占用 CPU，CPU 只在搬运完成时被中断唤醒

## 进程内存模型由谁定义
结论：既不是 x86 定义的，也不是 C++ 定义的--是"OS ABI + 工具链（编译器/链接器）+ 可执行文件格式 + OS 加载器"共同约定的平台惯例。

| 层 | 管什么 | 不管什么 |
|---|---|---|
| C++ 标准 | 存储期（static/thread/automatic/dynamic）、生命周期 | 不管地址、不管布局 |
| x86 ISA | MMU、特权级、分页机制、指令集 | 不管进程布局 |
| ABI（Linux x86-64 用 System V psABI） | 栈增长方向、调用约定 | 不管 ELF 段 |
| ELF 格式 | 定义 `.text`/`.data`/`.bss`/`.rodata` 段 | 不管具体地址 |
| OS 加载器 | 读 ELF → 映射段 → 设栈/堆 → ASLR 随机化 | - |

**C++ 存储期 ↔ ELF 段 ↔ 地址映射：**

| C++ 存储期 | ELF 段 | 谁初始化 |
|---|---|---|
| static（已初始化） | `.data` | 加载器从文件拷贝 |
| static（零初始化） | `.bss` | 加载器清零 |
| static（thread_local） | `.tdata`/`.tbss` | 线程创建时 |
| automatic | 栈（高地址向下增长） | 编译器/栈指针 |
| dynamic | 堆（中地址向上增长） | brk/mmap |

**关键：** C++ 只保证生命周期语义（局部变量出作用域销毁、static 程序结束才销毁），至于落在哪个地址、栈往哪长，是平台的事。同一份代码在 Linux/Windows/macOS 布局完全不同，C++ 标准对此一无所知

## 无 OS 的单片机如何执行 C++ 程序
**烧录是什么：** 把编译好的固件二进制从 PC 写进 MCU 内部 Flash（非易失）。通过下载器（ST-Link/J-Link，SWD/JTAG）或 bootloader（UART/USB）。

**为什么必须烧录：** 单片机 RAM 极小且易失，无文件系统、无动态加载器，程序必须预先固化在 Flash，上电直接取指执行（XIP，就地执行）。

**上电执行流程：**
```
上电复位 → 从固定地址读向量表（STM32: 0x08000000）
  ├─ 第 0 项 = 初始栈指针 SP
  ├─ 第 1 项 = Reset_Handler 入口
→ 跳转 Reset_Handler（启动代码）
  ├─ 把 .data 从 Flash 拷到 RAM（RAM 才可写）
  ├─ 把 .bss 清零
  ├─ 调 __libc_init_array（执行全局对象构造函数）
→ main()（死循环，永不返回）
无 MMU → CPU 访问的就是物理地址，链接脚本（.ld）固定各段地址
```

**MCU 内存映射（STM32 为例）：**
```
0x08000000  Flash（.text/.rodata，非易失）
0x20000000  SRAM（.data 运行副本/.bss/堆/栈，易失）
0x40000000  外设寄存器（GPIO、UART、定时器）
```

**C++ 依赖如何解决（无 OS 无 libc）：**

| C++ 依赖 | 单片机方案 |
|---|---|
| `operator new`/`delete` | 用户实现，内部包 `malloc`/`free`（newlib） |
| `memcpy`/`printf` 等 | 静态链接 newlib/nanolibc（裸机 C 库） |
| `printf` 输出到哪 | 重定向 `_write` 到 UART 寄存器 |
| 全局对象构造函数 | 启动代码 `__libc_init_array()` 在 `main()` 前执行 |
| 异常/RTTI | 编译期禁用（`-fno-exceptions -fno-rtti`）省 Flash |
| `iostream` | 尽量不用（体积大），改用 `printf` |
| 动态链接 | 不存在，全部静态链接，链接器编译期解决所有符号 |

**无 OS vs 有 OS：**

| | PC（有 OS） | 单片机（无 OS） |
|---|---|---|
| 地址 | 虚拟地址（MMU 翻译） | 物理地址（无 MMU） |
| 程序来源 | 运行时动态加载 | 烧录固化在 Flash |
| 标准库 | OS 提供/动态链接 | 静态链接 newlib + 重定向 |
| 多任务 | OS 调度 | 裸机主循环/中断 |

**"依赖问题"的本质：** PC 上 libc 和运行时由 OS/动态链接器在运行时提供；单片机没有，所以所有依赖必须在编译期静态链接进固件，标准库函数重定向到具体硬件（printf→UART、malloc→预分配堆区）
## C++ 中如何体现中断处理程序
用户态 C++ 无法直接写真正的 ISR（那是内核/驱动层的事），但有三个层面：
1. 嵌入式 / 裸机 C++：真正的 ISR
```cpp
extern "C" void TIMER1_IRQHandler() __attribute__((interrupt));
extern "C" void TIMER1_IRQHandler() { flag = true; }
```
- `extern "C"` 避免名字修饰，链接到中断向量表
- `__attribute__((interrupt))` 告诉编译器这是 ISR：进出场保存全部寄存器、用 IRET 返回
2. Linux 内核模块：`request_irq(irq, handler, ...)`，handler 上半部极快返回 `IRQ_HANDLED`，可用 `IRQ_WAKE_THREAD` 唤醒中断线程
3. 用户态 C++ 对应物：**信号（Signal）= 软件中断**
```cpp
#include <csignal>
void handler(int sig) {
    std::atomic_signal_fence(std::memory_order_seq_cst);  // 编译器屏障
    // 只能调用 async-signal-safe 函数
}
std::signal(SIGINT, handler);  // 多线程用 sigaction + pthread_sigmask
```
**与硬中断的对应：**

| 概念 | 硬件中断 | 信号（软中断） |
| --- | --- | --- |
| 触发 | 设备 / 定时器 | 内核 / 其他进程 |
| 处理函数 | ISR | signal handler |
| 打断对象 | 正在跑的线程 | 接收信号的线程 |
| 处理时能做的事 | 极少 | 受限（只能 async-signal-safe） |

**为什么 `atomic_signal_fence` 是编译器屏障而非 CPU 屏障？**
信号处理函数与主程序运行在**同一线程 / 同一 CPU**，无跨核可见性问题，只需阻止编译器重排

### 小数的二进制表示
浮点数的表示借鉴了科学计数法，比如在十进制中 311.56 可以表示成 3.1156∗10^2 。类似地，浮点型数据的二进制存储结构也可以被划分成：**符号位 s + 指数位 e + 尾数位（有效数字位）m**。按照国际标准 IEEE 754，任意一个二进制浮点数可以表示成： 𝑉=(-1)^𝑠x𝑀x2^𝐸   其中：

- (-1)^𝑠 表示符号位， 𝑠=0 表示正数， 𝑠=1 表示负数
- 𝑀 表示有效数字， 1≤𝑀<2
- 2^𝐸 表示指数位

> 指数部分决定了数的大小范围，有效数字部分决定了数的精度。

在位运算中，n 进制数\*进制基数（即 n） 表示将所有数字向右移动一位，如 1010 二进制数\*得 10100

|十进制|二进制|二进制科学计数法|S|E|M|
|---|---|---|---|---|---|
|3.0|11.0|1.1 x 2^1|0|1|1.1|
|-5.0|-101.0|-1.01 x 2^2|1|2|1.01|

计算机中小数的表示按照小数点的位置是否固定可以分为浮点数和定点数。为了方便和 float 32 浮点数做对比，我们构造一个 32 位精度的定点数，其中小数点固定在 23 bit 处：
![v2-cb2ae52724d3d8c4b2d52934ca495f18\_720w.webp](../../../Files%20&%20LongText/Attachments/v2-cb2ae52724d3d8c4b2d52934ca495f18_720w.webp)

其中 IEEE 754 的规定为：

- 因 M 的取值一定是 1<=M<2，因此规定 M 在存储时舍弃第一个 1，只存储小数点后的数字，这样可以节省存储空间（以 float 32 为例，可以保存 23 位小数信息）
- 指数 E 是一个无符号整数，因此它的取值范围为 0255，但指数可以是负的，所以规定在存入 E 时在它原本的值加上 127（使用时减去中间数 127），这样 E 的取值范围为-127~128
- E 不全为 0，不全为 1：正常的计算规则，E 的真实值就是 E 的字面值减去 127（中间值），M 加回 1
- E 全为 0：指数 E 等于 1-127 为真实值，M 不加回 1（此时 M 为 0. xxxxxx），这样是为了表示 0 和一些很小的数
- E 全为 1：M 全为 0 表示正负无穷大（取决于 S 符号位）；M 不全为 0 时表示不是一个数（NaN）

`𝑉=(-1)^𝑠x𝑀x2^𝐸`  e 为 0 表示 e 的 0-127=-127 次方乘以一个 1<=M<=2 的数值，得到一个非常小的数。正负无穷大

#### 有精度损失
十进制中 0.5（代表分数 1/2）表示二进制中 0.1（等同于分数 1/2），我们可以把十进制中小数部分乘以 2 作为二进制的一位，然后继续取小数部分乘以 2 作为下一位，直到不存在小数为止。

以 0.2 这个无法精确表示成二进制的浮点数为例：

0.2x2=0.4→
00.4x2=0.8→
00.8x2=1.6→
10.6x2=1.2→
10.2x2=0.4→
0...... (0.2) 10=(0.00110...) 2 
因此十进制下的 0.2 无法被精确表示成二进制小数，这也是为什么十进制小数转换成二进制小数时会出现精度损失的情况。

## 屏幕密度和像素概念区分
基本概念铺垫
### 像素
像素 (pixel) 为图像的基本单位，是一个抽象的采样，在很多情况下，它们采用点或者方块显示。每个像素可有各自的颜色值，可以采用 RGB 表示。单位面积内的像素越多代表分辨率越高，所显示的图像就会接近于真实物体。
### 屏幕尺寸
屏幕尺寸 (Screen size) 指屏幕的物理尺寸，一般用屏幕对角线长度表示，单位英寸 (1 英寸 = 2.54 厘米)。如小米 4 是 5 英寸。
### 宽高比率
宽高比率 (Aspect Ratio) 指的是实际屏幕的物理尺寸宽高比，如 16：9，4：3 等等。
### 屏幕密度
屏幕密度 (Screen density) 指的是屏幕里像素值浓度，分辨率/屏幕尺寸可以反映出手机密度。为了方便，Android 将屏幕密度分为 6 种，low, medium, high, extra-high, extra-extra-high, and extra-extra-extra-high.
### 分辨率
分辨率 (Resolution) 和电脑的分辨率概念一样，指手机屏幕纵、横方向像素个数。如 `1920*1080`，它表示纵向一列有 1920 个像素，横向一行有 1080 个像素。
### DPI
DPI (dot per inch)，每英寸像素数，可以反映屏幕的清晰度，可用于缩放 UI。
例如，如果一个 320x240 分辨率的屏幕之物理尺寸为 2 inchx1.5 inch，
那么 DPI = 320/2 = 240/1.5 =160。一般的，计算的方法为对角线像素值/对角线长度 (屏幕尺寸)。如计算 WVGA (`800*480`) 分辨率，3.7 英寸的密度 DPI 为 sqrt (800^2 + 480^2)/3.7 = 252。密度（字面意思）
### dip (dp)
DIP = Density-independent pixel，与密度无关像素，亦称为设备独立像素 (Device independent pixel)，是一个虚拟的像素的单元，其等价于 160 dpi 屏幕的一个实际物理像素。这种 160 dpi 的屏幕的屏幕密度是系统假设一个基准密度 (也就是 medium 级别的密度)，在运行时，系统会将 DP 值根据不同 DPI 的屏幕转化具体的物理的像素。公式为 px = dp * (dpi / 160)。如一个 240 dpi 的屏幕，1 dp 在其上实际等于 1.5 个物理像素 px。在布局时应该使用 dp 作为单位以方便适配
### Android 对手机屏幕尺寸和 dpi 分级的情况

## 字节序
来源：对话记录2（ChatGPT 导出，2026-10）
字节序描述多字节数值在内存中的字节排列，不改变数值本身：大端把最高有效字节放在低地址，小端把最低有效字节放在低地址。x86/x86-64 是小端，Internet 协议的多字节整数字段按网络字节序（大端）传输。

| 项目 | 大端（Big-Endian） | 小端（Little-Endian） |
| --- | --- | --- |
| `0x12345678` 的内存字节（低地址到高地址） | `12 34 56 78` | `78 56 34 12` |
| 典型平台 | POWER（大端模式）、SPARC 等服务器 | x86、x86-64、多数 ARM 配置 |
| 转换成本 | `htonl` 等通常为空操作 | 需要字节交换 |

- `htons` / `htonl` 把 16/32 位主机序转成网络序，`ntohs` / `ntohl` 反向；函数名里的 n 表示 network，h 表示 host。大端机器上这些函数可能什么都不做（[byteorder(3)](https://man7.org/linux/man-pages/man3/byteorder.3.html)）。
- 通信不需要每次先交换双方的字节序信息，双方按协议规定的字段格式编解码即可；不是所有应用协议都使用大端，文本协议和不依赖主机字节序的序列化格式（如 Protobuf 的 varint）不受影响。
- `inet_pton` 写入的 IPv4 地址已经是网络序，之后再调用 `htonl` 会二次交换；端口仍需 `htons`。相关接口细节见 [[Linux高性能服务器编程#5.1.1 主机字节序和网络字节序]]。
