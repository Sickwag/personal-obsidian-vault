# 设计模式总览
设计模式（Design Pattern）是前辈们对代码开发经验的总结，是解决特定问题的一系列套路。它不是语法规定，而是一套用来提高代码可复用性、可维护性、可读性、稳健性以及安全性的解决方案。
## 模式分类
### 创建型模式（Creational Pattern）
对类的实例化过程进行了抽象，能够将软件模块中对象的创建和对象的使用分离。

（5 种）[[#工厂模式|工厂模式]]、[[#抽象工厂模式|抽象工厂模式]]、[[#单例模式|单例模式]]、[[#建造者模式|建造者模式]]、[[#原型模式|原型模式]]
### 结构型模式（Structural Pattern）
关注于对象的组成以及对象之间的依赖关系，描述如何将类或者对象结合在一起形成更大的结构，就像搭积木，可以通过简单积木的组合形成复杂的、功能更为强大的结构。

（7 种）[[#适配器模式|适配器模式]]、[[#装饰者模式|装饰者模式]]、[[#代理模式|代理模式]]、[[#外观模式|外观模式]]、[[#桥接模式|桥接模式]]、[[#组合模式|组合模式]]、[[#享元模式|享元模式]]
### 行为型模式（Behavioral Pattern）
关注于对象的行为问题，是对在不同的对象之间划分责任和算法的抽象化；不仅仅关注类和对象的结构，而且重点关注它们之间的相互作用。

（11 种）[[#策略模式|策略模式]]、[[#模板方法模式|模板方法模式]]、[[#观察者模式|观察者模式]]、[[#迭代器模式|迭代器模式]]、[[#责任链模式|责任链模式]]、[[#命令模式|命令模式]]、[[#备忘录模式|备忘录模式]]、[[#状态模式|状态模式]]、[[#访问者模式|访问者模式]]、[[#中介者模式|中介者模式]]、[[#解释器模式|解释器模式]]

# 设计原则（SOLID）
设计模式背后是面向对象设计原则，面试常直接问 SOLID，也会问「这个模式体现了什么原则」。
## 五原则速览
| 原则 | 含义 | 体现该原则的模式 |
|---|---|---|
| 单一职责（S） | 一个类只负责一件事 | 访问者（操作从元素类剥离）、命令（请求从调用者剥离） |
| 开闭原则（O） | 对扩展开放，对修改关闭 | 工厂、策略、观察者、装饰者 |
| 里氏替换（L） | 子类能替换父类且不破坏正确性 | 所有多态用法的前提 |
| 接口隔离（I） | 客户端不依赖用不到的接口 | 组合模式安全式（add/remove 只放容器类） |
| 依赖倒置（D） | 依赖抽象，不依赖具体 | 工厂、策略、桥接 |
## 开闭原则是主线
面试官最常拿开闭原则问模式。判断设计好坏的快捷方式：加一个新需求，要改几处已有代码？理想是 0 处，只新增类或实现。
- 策略加一种算法 = 加一个类
- 装饰者加一种职责 = 加一个装饰者类
- 工厂加一种产品 = 加产品类 + 工厂类
## 组合优于继承
- 继承是编译期静态绑定，组合是运行期动态组合
- 继承打破封装，子类依赖父类实现细节，父类一变子类跟着变
- 组合 + 接口天然满足开闭与依赖倒置
- C++ 体现：`unique_ptr<Interface>` 成员、Pimpl、装饰者、桥接
- 例外：模板方法模式用继承，骨架固定、步骤变化的场景下继承更合适

# 生产者-消费者模式
## 边生产边消费
一种流水线形式，不断生产和消费，**两者都不会停下**
![[PixPin_2026-01-23_13-22-15.png]]
- 最重要的是将 `notify_all()` 放在 while 循环之外，因[[DevFoundations#施磊手写线程池#线程的状态|线程的状态]]决定了线程在 wait 时被挂起，被 notify 时被阻塞，获取到锁后开始执行，从阻塞到执行阶段有时间空隙，`producer()` 仍有可能被调用并且**先抢到锁**，为了解决这一情况就**允许生产者者一直生产到 vector 满**，满了后通知消费者，通知完出作用于一定会解锁，允许消费者获取锁
- 这样即使生产者通知消费者后下一次仍是生产者被调用，那么也会进入 while 中，`cv.wait()` 强制将生产者挂起，解锁保证再下一次生产者不会抢占锁。
- 消费者这一方同理
- 主要逻辑是消费者主导，消费者一直要消费，所以驱动生产者一直生产
## 生产一个消费一个
如果生产是间断性且不确定执行时间的操作，并不需要一直消费和生产，只是借助生产者消费者模式作为一种缓冲区。常用于一些负载在时间上不均衡的场景（如 [[FastLog]] 打日志）
![[PixPin_2026-01-23_13-22-25.png]]
- [[FastLog#logger.hpp]] 中使用到这个模式，日志打印完全不可预测并负载不均衡
- 这种形式不需要两者都不停工作，反而有可能两者都不工作
- 或者也可以将[[#边生产边消费|边生产边消费]]中，生产者的 `while(vector.full())` 改为 `while(vector.size() == 1)`，让生产者生产一个后就提前挂起放弃工作，引起消费者消费完现有内容后再发送生产请求。但仍是两者不停工作，只是没缓冲区

# 单例模式
## 实现方式
### 配合 shared_ptr 实现单例模式
[[AzzatoChat#单例模式]]
```cpp
template <typename T>
class Singleton {
  protected:
	Singleton()									 = default;

	// avoiding Singleton obj be copied
	Singleton(const Singleton<T>& other)		 = delete;
	Singleton& operator=(const Singleton<T>& st) = delete;

	static std::shared_ptr<T> _instance;

  public:
	static std::shared_ptr<T> getInstance();
	void					  printAddress() const;
	~Singleton();
};

template <typename T>
std::shared_ptr<T> Singleton<T>::_instance = nullptr;

template <typename T>
std::shared_ptr<T> Singleton<T>::getInstance() {
	static std::once_flag onceFlag;
	std::call_once(onceFlag, [&]() { _instance = std::shared_ptr<T>(new T); });
	return _instance;
}
```
这种实现方式在使用方式上需要配合
- 继承 Singleton 的类需要 public 继承才能调用 `getInstance()`
- 如果派生类的构造函数在 private 中，派生类必须 `friend Singleton<T>` 
	- [[C++ Runoob Tutoral#继承方式|任何继承关系都无法让子类看到父类的private]]
	- 派生类由于继承关系可以看到父类 Singleton 中的 public+protect 内容，protect 中保证了派生类无法被复制（子类调用**会隐式调用父类的相同函数**，比如构造函数），而 public 保证了能够使用 `getInstance()` 得到单例，而基类看不到派生类的内容
	- 继承了 `Singleton<T>` 的派生类 `getInstance()` 需要 `new T`，这个操作需要 `getInstance()` 函数所在作用于能够访问到 T 的构造函数，**非 private**继承无法看到 private 中的**编译器生成的 `Singleton<T>` 类型的构造函数**
- 如果派生类的构造函数在 public 中，**派生类不必使用 `friend Singleton<T>`，但添加了也没关系**
	- 放在 public 中并且继承自 `Singleton<T>` 的做法是一种*不严谨的单例模式实现*，因为 public 构造函数允许多种创建对象方式，这是一种保险实现，防止以后将构造函数移动到 private 中之后需要大改代码
```cpp
DBManager::GetInstance()->query(...); 	// 所用方式都允许，这也是单例模式想要严格确保全局唯一性所需的
DBManager mgr;              			// 在构造函数为 private 时会产生编译错误，public 时不会
auto mgr = new DBManager(); 			// 同上
```
- 为什么不干脆所有类都是用 private 构造函数+friend 实现？
	- 测试环境中想要临时创建只有功能接口，没有实际实现的测试类（比如一个不连接真实数据库数据库数据的数据库类），只要在类中添加了 friend，就会连接真实数据库，没有就会因为 new 无法访问 private 函数报错，想要批量创建需要改动代码，非常麻烦
	- 测试环境中，可能要同时测多个不同作用的实例的功能，这一般使用工厂函数**批量创建单例对象**
	- 易用性，上面已经提到
```cpp
auto db1 = std::make_shared<Database>("config1");
auto db2 = std::make_shared<Database>("config2");
auto dbDefault = DatabaseMgr::GetInstance();
```
- 一般来说，public 构造常用于编写外部库，便于其他人不需要了解某个类是不是单例对象，内部实现细节是什么的情况下通过直觉得到一个单例对象（但是调用者并不需要知道这个对象其实是单例的，比如 boost.asio 的 `io_context` 对象）
无论什么实现方式，都应该使用单例模式推荐的 `getInstance()`（在 public 构造函数场景下一般通过 CI 规范和 code review 约束），简单来说，public 构造是一种 "信任开发者正确使用" 的设计哲学，private 构造是**编译器强制你正确使用**

> [!note] 这种设计本质上不是单例模式
> 使用 shared_ptr 只是在模仿单例模式的行为，每次调用/销毁单例对象都会**原子地**修改引用计数，高频调用可能会导致性能问题。 Meyer Singleton 设计中直接返回引用，编译器会优化这个引用调用，零开销。
### 懒汉式实现（Meyer Singleton 实现）
```cpp
// C++11中的单例模式（自动线程安全）
Singleton& getInstance() {
    static Singleton instance;  // 编译器保证线程安全初始化
    return instance;
}

// 编译器生成的伪代码类似：有些编译器中使用call_once保证
Singleton& getInstance() {
    static std::atomic<bool> initialized = false;
    static std::aligned_storage_t<sizeof(Singleton)> storage;

    if (!initialized.load(std::memory_order_acquire)) {
        std::lock_guard<std::mutex> lock(global_mutex);
        if (!initialized.load(std::memory_order_relaxed)) {
            // 构造对象
            new (&storage) Singleton();
            initialized.store(true, std::memory_order_release);
        }
    }
    return *reinterpret_cast<Singleton*>(&storage);
}
```
主要特点是在**首次调用时实例化对象，并在以后的调用时直接返回引用**，由于 C++ 有一个著名陷阱：不同翻译单元（.cpp文件）中的全局/类静态变量，初始化顺序是未定义的。假设写成：
```cpp
// config.h
class Config {
  static ConfigVarMap s_datas;       // 声明
  static RWMutexType  s_mutex;
};
// config.cc
ConfigVarMap Config::s_datas;          // 定义
Config::RWMutexType Config::s_mutex;
```
如果某个其他 .cpp 文件在全局作用域定义了一个对象，其构造函数调用了 `Config::Lookup(...)`，此时 s_datas 可能还没被构造——UB。这种 bug 极难排查。
函数局部静态变量没有这个问题：C++11   保证第一次进入函数时线程安全地初始化，且只在真正用到时才构造（lazy initialization）。C++11 之前，使用**饿汉式静态变量生命不是线程安全的**，需要加锁，，C++11 通过编译器保证多线程操作中不多次初始化 static 变量
### 饿汉式实现
特点：程序启动时立即创建实例（无论是否使用）。
```cpp
class Singleton {
public:
    static Singleton& getInstance() { return instance; }
private:
    Singleton() = default;
    static Singleton instance; // 静态成员声明
};
// 在 cpp 文件中定义并初始化（程序启动时构造）
Singleton Singleton::instance;
```
- 线程安全：无竞态条件。类加载时就创建实例，在类中声明静态成员导致 main 函数启动之前就创建单例。C++11 **以前就是线程安全的**，但可能浪费资源（如果从未使用）并延长启动时间
- 无性能开销：调用 `getInstance()` 直接返回引用。
### C++11 之前的单例做法
#### 静态指针+双重检查锁定
```cpp
Singleton* getInstance() {
    static Singleton* instance = nullptr;
    static pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

    if (instance == nullptr) {
        pthread_mutex_lock(&mutex);
        if (instance == nullptr) {            // 二次检查
            instance = new Singleton();
        }
        pthread_mutex_unlock(&mutex);
    }
    return instance;
}
```
`static Singleton instance` 在不同编译器上的初始化顺序不保证线程安全，所以通常改用指针 + 外部互斥锁。
#### Boost 实现
```cpp
#include <boost/thread.hpp>

Singleton& getInstance() {
    static Singleton instance;
    static boost::once_flag flag = BOOST_ONCE_INIT;

    boost::call_once(flag, [] /* 初始化逻辑 */ {});
    return instance;
}
```
#### 平台相关
linux 使用 pthread_once
```cpp
Singleton& getInstance() {
    static pthread_once_t onceControl = PTHREAD_ONCE_INIT;
    static Singleton instance;

    pthread_once(&onceControl, [] { new (&instance) Singleton(); }); // 这里用回调函数实现，C++11之前没有lambda
    return instance;
}
```
windows 使用 InitOnceExecuteOnce
```cpp
#include <winbase.h>

Singleton& getInstance() {
    static Singleton instance;
    static INIT_ONCE initOnce = {};
    PVOID context;

    if (!InitOnceExecuteOnce(&initOnce, [](PINIT_ONCE, PVOID, PVOID*) -> BOOL {
            new (&instance) Singleton();
            return TRUE;
        }, nullptr, &context)) {
        // 处理错误
    }
    return instance;
}
```
## 存储单例的方式
1. 函数局部 static 对象: 单例对象被**存储至静态区**，通过 C++11 特性保证生命周期\=程序运行生命周期
2. 成员 static 对象+ new: 单例对象存储至堆，需要 `call_once`，现代 C++更提倡方法 1 的 [[AzzatoChat#std once_flat 和 std call_once 保证多线程单例|Magic static]] 方式创建单例，而这种方法常用于多线程中保证某些**操作**只执行一次，不再用于单例对象的创建
3. 成员 static 对象 + 栈对象: 不常用
4. `static shared_ptr<T> instance` 方法一般用于需要手动控制生命周期或者复杂的自定义删除器的情况，比如游戏关卡中，每一关结束之后删除这一关的所有资源，而不是用 static 在整局游戏中保留每一关的数据
# 工厂模式
## 解决的问题
创建对象时如果直接 `new` 具体类，客户端与具体类耦合：更换实现要改所有调用点，创建逻辑（参数校验、资源获取、日志）散落各处无法复用。工厂模式把"创建对象"这一职责集中或抽象出来，客户端只依赖抽象产品接口。
## 简单工厂
不属于 GoF 23 种模式，是一种约定：用一个静态函数按参数决定创建哪个产品。
```cpp
enum class ProductType { A, B };

class Product {
public:
    virtual ~Product() = default;
    virtual void use() = 0;
};
class ProductA : public Product { public: void use() override {} };
class ProductB : public Product { public: void use() override {} };

class SimpleFactory {
public:
    static std::unique_ptr<Product> create(ProductType type) {
        switch (type) {
            case ProductType::A: return std::make_unique<ProductA>();
            case ProductType::B: return std::make_unique<ProductB>();
        }
        return nullptr;
    }
};
```
缺点：新增产品要改 `create()` 的 switch，违反开闭原则（OCP）。所有产品创建逻辑集中在一处，函数会随产品增多而膨胀。
## 工厂方法模式
把"创建哪个对象"的决策延迟到子类。基类定义创建接口，具体工厂负责实例化具体产品。
```cpp
class Product { public: virtual ~Product() = default; virtual void use() = 0; };

class Creator {
public:
    virtual ~Creator() = default;
    virtual std::unique_ptr<Product> createProduct() = 0;  // 工厂方法：子类决定
    void run() {  // 模板方法：使用产品，不关心具体类型
        auto p = createProduct();
        p->use();
    }
};

class ProductACreator : public Creator {
public:
    std::unique_ptr<Product> createProduct() override {
        return std::make_unique<ProductA>();
    }
};
```
新增产品只需新增产品类 + 对应工厂类，不改已有代码，满足 OCP。缺点：每个产品对应一个工厂子类，类数量膨胀。
## 工厂 vs 直接 new
| 维度 | 直接 new | 工厂模式 |
|---|---|---|
| 耦合 | 客户端依赖具体类 | 客户端依赖抽象接口 |
| 扩展 | 改所有调用点 | 加产品类 + 工厂类 |
| 创建逻辑复用 | 无法复用 | 集中或抽象 |
| 代价 | 无 | 类数量增加、一层间接 |
## 实际应用
- 依赖注入容器、对象池用工厂创建对象
- 序列化框架按类型标签创建对象
- `std::make_unique` 本身就是工厂函数（同时保证异常安全）

# 抽象工厂模式
## 解决的问题
需要创建"一族"彼此相关或依赖的对象，并保证族内对象协同工作。跨平台 UI 是典型场景：不同平台下要生成一套风格统一的控件（按钮、复选框必须同属 Win 或 Mac 风格，不能混用）。
```cpp
class Button   { public: virtual ~Button() = default; virtual void render() = 0; };
class CheckBox { public: virtual ~CheckBox() = default; virtual void render() = 0; };

class WinButton : public Button   { public: void render() override {} };
class WinCheckBox : public CheckBox { public: void render() override {} };
class MacButton : public Button   { public: void render() override {} };
class MacCheckBox : public CheckBox { public: void render() override {} };

// 抽象工厂：定义一族产品的创建接口
class GUIFactory {
public:
    virtual ~GUIFactory() = default;
    virtual std::unique_ptr<Button>   createButton() = 0;
    virtual std::unique_ptr<CheckBox> createCheckBox() = 0;
};

class WinFactory : public GUIFactory {
public:
    std::unique_ptr<Button> createButton() override { return std::make_unique<WinButton>(); }
    std::unique_ptr<CheckBox> createCheckBox() override { return std::make_unique<WinCheckBox>(); }
};
// MacFactory 同理
```
客户端只依赖 `GUIFactory` 抽象，运行期替换一个工厂即切换整个产品族，且族内产品不可能混搭。
## 工厂方法 vs 抽象工厂
| 维度 | 工厂方法 | 抽象工厂 |
|---|---|---|
| 创建对象数 | 单一产品 | 一族产品 |
| 组织方式 | 一个产品一个工厂子类 | 一个工厂聚合多个工厂方法 |
| 新增产品类型 | 加类即可，OCP 友好 | 必须改抽象工厂接口，违反 OCP |
| 新增产品族 | 加类即可 | 加类即可，OCP 友好 |
| 关系 | 工厂方法可看作一族只有一个产品的抽象工厂 | |

## 实际应用
- Qt/GTK 等跨平台 GUI 控件工厂
- 数据库访问层：连接、语句、事务由同一工厂产出，保证同一厂商实现
- 游戏皮肤/主题：不同主题对应不同资源工厂

# 建造者模式
## 解决的问题
对象字段多、可选参数多时，构造函数会出现大量重载（"望远镜构造函数"），可读性和可扩展性都差。建造者把复杂对象的构建过程分解为多个步骤，逐步设置，最后一次性产出对象，将复杂对象的**构造**与**表示**分离。
## 流式建造者（Fluent Builder）
C++ 中最常用的变体，配合值语义返回避免堆分配：
```cpp
class Computer {
public:
    void setCpu(const std::string& cpu) { cpu_ = cpu; }
    void setGpu(const std::string& gpu) { gpu_ = gpu; }
    void setRam(int gb) { ram_ = gb; }
private:
    std::string cpu_, gpu_;
    int ram_ = 0;
};

class ComputerBuilder {
public:
    ComputerBuilder& setCpu(const std::string& cpu) { comp_.setCpu(cpu); return *this; }
    ComputerBuilder& setGpu(const std::string& gpu) { comp_.setGpu(gpu); return *this; }
    ComputerBuilder& setRam(int gb) { comp_.setRam(gb); return *this; }
    Computer build() { return std::move(comp_); }
private:
    Computer comp_;
};

// 链式调用，只设置需要的字段
auto pc = ComputerBuilder{}.setCpu("M3").setRam(32).build();
```
GoF 原版还有 **Director（指挥者）**角色：流程固定但产物多样时（如制作流程固定、口味可选的菜品），由 Director 按固定顺序驱动 Builder。
## 建造者 vs 工厂
| 维度 | 工厂模式 | 建造者模式 |
|---|---|---|
| 构建方式 | 一步创建，组装在工厂内部 | 分步设置，客户端控制每个步骤 |
| 关注点 | 返回**哪种**对象 | 怎么**装配**一个复杂对象 |
| 产物 | 通常为多态对象 | 通常为值类型/不可变对象 |
| 灵活性 | 创建逻辑对客户端隐藏 | 客户端可跳过或定制步骤 |
## 实际应用
- 解析器：解析步骤固定，产物可以是 AST 或字节码（同流程多产物 → Director）
- SQL 查询构造器、配置对象、HTTP 请求组装
- `std::stringstream` 分步拼装输出是建造者思想的体现

# 原型模式
## 解决的问题
创建对象成本高（大对象、需重连外部资源），或运行时才能确定具体类型时，直接 `new` 不划算或不可行。原型模式以已有实例为"原型"，通过克隆生成新实例，避免重新初始化。
```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual std::unique_ptr<Shape> clone() const = 0;  // 原型：克隆自身
    virtual void draw() = 0;
};

class Circle : public Shape {
public:
    std::unique_ptr<Shape> clone() const override {
        return std::make_unique<Circle>(*this);  // 走拷贝构造
    }
    void draw() override {}
private:
    int radius_ = 0;
};

std::unique_ptr<Shape> proto = std::make_unique<Circle>();
auto copy = proto->clone();  // 无需知道具体类型
```
`clone()` 是**虚拷贝**，通过拷贝构造函数实现，深/浅拷贝语义在原型类里定义。成员含 `std::unique_ptr` 等不可拷贝成员时需手动实现深拷贝。
## 为什么不用直接拷贝构造
- 拷贝需要编译期知道具体类型（`Circle copy(*proto)`）
- 原型模式通过多态在**运行期**复制，客户端只依赖抽象
- 适合批量创建"状态相同但相互独立"的对象（游戏子弹、文档模板）
## 深拷贝 vs 浅拷贝
| 维度 | 浅拷贝 | 深拷贝 |
|---|---|---|
| 指针成员 | 共享同一资源 | 各自复制一份 |
| 修改影响 | 互相影响 | 相互独立 |
| 实现 | 默认拷贝构造 | 手动实现或对成员递归克隆 |
## 实际应用
- 游戏实体批量生成（以模板实体为原型克隆）
- 编辑器复制粘贴（以选中对象为原型）
- 文档/配置模板实例化

# 适配器模式
## 解决的问题
已有类的接口与客户端期望的接口不一致，又不能或不想修改已有类。适配器在不改动原类的前提下，把一个接口转换成客户端期望的另一个接口。
## 对象适配器（组合，推荐）
```cpp
// 已有类：老接口，无法修改
class LegacyRect {
public:
    void draw(int x, int y, int w, int h) {}
};

// 客户端期望的新接口
class Shape {
public:
    virtual ~Shape() = default;
    virtual void draw() = 0;
};

class RectAdapter : public Shape {
public:
    explicit RectAdapter(std::shared_ptr<LegacyRect> r) : legacy_(std::move(r)) {}
    void draw() override { legacy_->draw(0, 0, w_, h_); }
private:
    std::shared_ptr<LegacyRect> legacy_;
    int w_ = 100, h_ = 50;
};
```
适配器持有被适配者（组合），把旧接口调用翻译成新接口。
## 类适配器（多继承）
```cpp
class RectAdapter : public Shape, private LegacyRect {
public:
    void draw() override { LegacyRect::draw(0, 0, w_, h_); }
};
```
类适配器直接继承适配者，不需要组合成员，但要求两个接口都能继承，且 C++ 多继承 + 私有继承可读性差。**组合优于继承**，一般优先对象适配器。
## 实际应用
- 第三方库接口与业务接口不一致时加一层薄壳
- 旧 API 包成新 API 而不动旧代码（兼容层）
- `std::function` 把任意可调用对象适配成统一签名

# 装饰者模式
## 解决的问题
需要给对象动态添加职责，若用继承，功能组合会产生子类爆炸（如"带缓冲的加密压缩文件流"是 3 个特性的笛卡尔积）。装饰者用**组合**在运行期一层层包裹对象，每个装饰者只增加一种职责。
```cpp
class Stream {
public:
    virtual ~Stream() = default;
    virtual void write(const char* data, size_t n) = 0;
};

class FileStream : public Stream {
public:
    void write(const char* data, size_t n) override {}
};

// 装饰者基类：持有被装饰对象并转发
class StreamDecorator : public Stream {
public:
    explicit StreamDecorator(std::unique_ptr<Stream> s) : inner_(std::move(s)) {}
protected:
    std::unique_ptr<Stream> inner_;
};

class BufferedStream : public StreamDecorator {
public:
    using StreamDecorator::StreamDecorator;
    void write(const char* data, size_t n) override {
        /* 缓冲逻辑 */
        inner_->write(data, n);
    }
};

class EncryptedStream : public StreamDecorator {
public:
    using StreamDecorator::StreamDecorator;
    void write(const char* data, size_t n) override {
        /* 加密 */
        inner_->write(data, n);
    }
};

// 运行期自由组合，包裹顺序即处理顺序
std::unique_ptr<Stream> s =
    std::make_unique<EncryptedStream>(
        std::make_unique<BufferedStream>(
            std::make_unique<FileStream>()));
```
`EncryptedStream` 先处理再交给 `BufferedStream` 再写文件。新增一种职责只需新增一个装饰者类，取代笛卡尔积子类。
## 装饰者 vs 继承 vs 代理
| 维度 | 继承 | 装饰者 | 代理 |
|---|---|---|---|
| 方式 | 编译期静态绑定 | 运行期组合包裹 | 运行期组合包裹 |
| 目的 | 复用/特化 | **增强功能** | **控制访问** |
| 组合关系 | 子类是基类 | 装饰者与被装饰者同接口 | 代理与被代理者同接口 |
| 数量 | 子类爆炸 | 线性叠加 | 一对一 |

装饰者和代理结构几乎一样，区别在**意图**：装饰者给对象加职责，代理给对象挡访问。
## 实际应用
- `std::iostream` 体系（streambuf 逐层包装）
- 日志系统加时间戳、格式化、过滤
- HTTP 中间件：`addHeader` → `log` → `compress` 逐层包裹

# 代理模式
## 解决的问题
不适合直接访问目标对象时（创建昂贵、位于远程、需权限控制、需附加资源管理），提供与目标同接口的**代理**占位，控制对目标的访问时机和方式。
## 常见种类
| 类型 | 作用 | 例子 |
|---|---|---|
| 虚代理 | 延迟创建真实对象 | 大图片真正显示时才读文件 |
| 远程代理 | 屏蔽网络细节 | RPC 桩 |
| 保护代理 | 控制访问权限 | 检查权限再放行 |
| 智能引用 | 附加资源管理 | `std::shared_ptr` 引用计数 |
## 虚代理：懒加载
```cpp
class Image {
public:
    virtual ~Image() = default;
    virtual void show() = 0;
};

class RealImage : public Image {
public:
    explicit RealImage(const std::string& path) : path_(path) {
        loadFromDisk();  // 昂贵
    }
    void show() override {}
private:
    void loadFromDisk() {}
    std::string path_;
};

class ImageProxy : public Image {
public:
    explicit ImageProxy(std::string path) : path_(std::move(path)) {}
    void show() override {
        if (!real_) real_ = std::make_unique<RealImage>(path_);  // 用到才加载
        real_->show();
    }
private:
    std::string path_;
    std::unique_ptr<RealImage> real_;
};
```
`ImageProxy` 与 `RealImage` 同接口，客户端无感知；真实对象创建推迟到首次调用。
## 实际应用
- `std::shared_ptr`：引用计数代理，自动管理生命周期
- RPC/gRPC 客户端桩：本地调用外观 = 网络请求
- 懒加载、缓存、访问控制、日志埋点（AOP 的一种实现）

# 外观模式
## 解决的问题
子系统由大量类组成，客户端逐个调用繁琐且与子系统内部结构耦合。外观提供一个**统一的高层接口**，屏蔽子系统内部细节。
```cpp
class CPU    { public: void execute() {} };
class Memory { public: void load() {} };
class Disk   { public: void read() {} };

// 外观：把启动流程封装成单个方法
class ComputerFacade {
public:
    void start() {
        cpu_.execute();
        memory_.load();
        disk_.read();
    }
private:
    CPU cpu_; Memory memory_; Disk disk_;
};

int main() {
    ComputerFacade pc;
    pc.start();  // 客户端只看到 start()
}
```
外观不限制客户端直接访问子系统，它只提供一个更简单的入口（非强制封装）。
## 外观 vs 适配器 vs 中介者
| 模式 | 方向 | 目的 |
|---|---|---|
| 适配器 | 一对接口转换 | 让不兼容的接口能用 |
| 外观 | 多对一的统一入口 | 简化对子系统的访问 |
| [[#中介者模式|中介者]] | 多方交互（双向） | 解耦对象间的网状依赖 |
## 实际应用
- 编译器前端：`compile(source)` 封装词法/语法/语义分析
- 网络库：`HttpClient::get()` 封装 DNS、连接、重试、超时
- 复杂 SDK 的简化封装层

# 桥接模式
## 解决的问题
一个类有**两个维度**的变化（形状 × 绘制方式），用继承会让类数量爆炸（N 形状 × M 绘制 = N×M 个子类）。桥接把抽象部分与实现部分分离，各自独立变化，通过组合关联。
```cpp
// 实现部分：绘制 API
class Drawer {
public:
    virtual ~Drawer() = default;
    virtual void drawLine(int x1, int y1, int x2, int y2) = 0;
};
class OpenGLDrawer : public Drawer {
public:
    void drawLine(int x1, int y1, int x2, int y2) override {}
};
class VulkanDrawer : public Drawer {
public:
    void drawLine(int x1, int y1, int x2, int y2) override {}
};

// 抽象部分：形状，持有实现（组合）
class Shape {
public:
    explicit Shape(std::shared_ptr<Drawer> d) : drawer_(std::move(d)) {}
    virtual void draw() = 0;
protected:
    std::shared_ptr<Drawer> drawer_;
};

class Circle : public Shape {
public:
    using Shape::Shape;
    void draw() override { drawer_->drawLine(0, 0, 10, 10); }
};
class Square : public Shape {
public:
    using Shape::Shape;
    void draw() override { drawer_->drawLine(0, 0, 5, 5); }
};

auto c = std::make_shared<Circle>(std::make_shared<OpenGLDrawer>());  // 2×2 组合，无需 4 个子类
```
新增一个形状 = 加一个 `Shape` 子类；新增一种绘制 = 加一个 `Drawer` 子类，独立扩展，只增加类数量而非笛卡尔积。
## 桥接 vs 适配器
- 适配器解决**已有接口不匹配**，是事后补救，让旧代码能一起工作
- 桥接是**设计时**就把抽象与实现分离，避免继承爆炸，是事前设计
## 实际应用
- Pimpl 惯用法：`std::unique_ptr<Impl>` 藏实现，头文件与实现解耦，是桥接在接口/实现分离上的体现
- 跨平台图形层：抽象图形操作，实现分 OpenGL、Vulkan、DirectX
- 驱动层：设备抽象 + 厂商实现

# 组合模式
## 解决的问题
对象呈**树形**部分-整体结构，希望客户端对叶子对象和容器对象一视同仁。文件系统是典型例子：文件是叶子，目录是容器，两者都有 `name`、`size`、`print`。
```cpp
class Node {
public:
    virtual ~Node() = default;
    virtual void print(int indent) = 0;
};

// 叶子：文件
class File : public Node {
public:
    explicit File(std::string name) : name_(std::move(name)) {}
    void print(int indent) override { /* 打印 name_ */ }
private:
    std::string name_;
};

// 容器：目录，可包含子节点
class Directory : public Node {
public:
    explicit Directory(std::string name) : name_(std::move(name)) {}
    void add(std::unique_ptr<Node> child) { children_.push_back(std::move(child)); }
    void print(int indent) override {
        /* 打印 name_，递归打印 children_ */
        for (auto& c : children_) c->print(indent + 1);
    }
private:
    std::string name_;
    std::vector<std::unique_ptr<Node>> children_;
};

auto root = std::make_unique<Directory>("root");
root->add(std::make_unique<Directory>("etc"));
root->add(std::make_unique<File>("README.md"));
root->print(0);  // 对整棵树统一操作
```
客户端只面对 `Node` 一个接口，递归遍历对叶子与容器透明。
## 透明式 vs 安全式
| 维度 | 透明式 | 安全式 |
|---|---|---|
| `add/remove` 定义位置 | 基类 `Node` | 只在容器子类 |
| 叶子接口 | 冗余但类型统一 | 干净，叶子不可误加子节点 |
| 误用防护 | 叶子调 add 需运行时检查/抛错 | 编译期杜绝 |
## 实际应用
- 文件系统、XML/DOM 树、菜单系统（菜单项嵌套子菜单）
- 渲染场景图：节点/组节点递归绘制
- UI 组件树（Qt/Widget 的父子结构）

# 享元模式
## 解决的问题
大量细粒度对象重复占用内存（游戏里上万个相同外观的子弹、文本里重复的字符）。享元把对象状态分成两类，共享内在状态，外在状态由客户端传入：
| 状态 | 含义 | 存储位置 |
|---|---|---|
| 内在状态（intrinsic） | 不随场景变化的公共部分 | 享元对象内部，多对象共享 |
| 外在状态（extrinsic） | 随场景变化的坐标等 | 客户端持有，使用时传入 |
```cpp
struct CharInfo { int fontId; int size; };  // 内在状态：可共享

class CharFlyweight {
public:
    explicit CharFlyweight(CharInfo info) : info_(info) {}
    void render(int x, int y) { /* 用 info_ + 外在状态(x,y) 绘制 */ }
private:
    CharInfo info_;  // 内在状态只存一份
};

class CharFactory {
public:
    std::shared_ptr<CharFlyweight> get(const CharInfo& info) {
        auto key = info.fontId * 1000 + info.size;
        auto& slot = pool_[key];  // 相同内在状态复用同一实例
        if (!slot) slot = std::make_shared<CharFlyweight>(info);
        return slot;
    }
private:
    std::unordered_map<int, std::shared_ptr<CharFlyweight>> pool_;
};
```
一屏文本有上万个字符实例，但字体+字号组合只有几十种，享元把实例数降到几十个，坐标（外在状态）由绘制循环传入。
## 享元 vs 单例 vs 对象池
| 模式 | 实例数 | 关键点 |
|---|---|---|
| [[#单例模式|单例]] | 全局唯一 1 个 | 控制全局状态 |
| 享元 | 按内在状态区分，每类共享 1 个 | 降低同类对象内存 |
| 对象池 | 固定数量可复用 | 复用昂贵对象（连接、线程） |
## 实际应用
- 字符串池（字符串常量去重）、字符字形缓存
- 游戏中的粒子、子弹、渲染字符
- 文本编辑器字符渲染

# 策略模式
## 解决的问题
同一算法有多个实现，且需**运行期**选择或替换（排序策略、支付方式）。策略模式把每种算法封装成独立单元，通过组合注入，避免大量 if-else 和算法代码侵入业务类。
## 传统实现：策略类
```cpp
class SortStrategy {
public:
    virtual ~SortStrategy() = default;
    virtual void sort(std::vector<int>&) = 0;
};
class QuickSort : public SortStrategy {
public:
    void sort(std::vector<int>& v) override {}
};
class MergeSort : public SortStrategy {
public:
    void sort(std::vector<int>& v) override {}
};

class Sorter {
public:
    explicit Sorter(std::shared_ptr<SortStrategy> s) : strategy_(std::move(s)) {}
    void setStrategy(std::shared_ptr<SortStrategy> s) { strategy_ = std::move(s); }
    void run(std::vector<int>& v) { strategy_->sort(v); }
private:
    std::shared_ptr<SortStrategy> strategy_;
};
```
## 现代实现：std::function
C++ 里策略常常不需要类层次，直接用 `std::function` 注入更轻量：
```cpp
class Sorter {
public:
    using Strategy = std::function<void(std::vector<int>&)>;
    explicit Sorter(Strategy s) : strategy_(std::move(s)) {}
    void setStrategy(Strategy s) { strategy_ = std::move(s); }
    void run(std::vector<int>& v) { strategy_(v); }
private:
    Strategy strategy_;
};

Sorter sorter([](std::vector<int>& v) { /* 快排 */ });
sorter.setStrategy([](std::vector<int>& v) { /* 归并 */ });
```
策略粒度小、无状态时优先 `std::function`；策略需自带状态（如带缓存的策略）或需要复杂类层次时用传统类。
## 策略 vs 状态
| 维度 | 策略模式 | [[#状态模式|状态模式]] |
|---|---|---|
| 切换 | 由客户端主动选择 | 对象内部自动流转 |
| 关系 | 算法之间平等，无转移关系 | 状态之间有转移关系 |
| 客户端 | 知道并选择策略 | 不感知状态 |
| 类比 | 换一套做法 | 对象自己"变身" |
## 实际应用
- 排序、压缩、校验算法可插拔
- 支付、计费、权限校验的策略切换
- 标准库 `std::sort` 的策略参数、回调式设计

# 模板方法模式
## 解决的问题
多个流程**骨架相同**，只有部分步骤的实现不同。模板方法在基类定义算法骨架（步骤顺序固定），把变化的步骤声明为虚函数，由子类实现或覆写。
```cpp
class DataProcessor {
public:
    virtual ~DataProcessor() = default;
    void process() {  // 模板方法：固定骨架，不打算被子类覆写
        auto data = read();                // 抽象方法：必须实现
        auto cleaned = sanitize(data);     // 默认实现：可覆写
        save(cleaned);                     // 抽象方法：必须实现
        if (logEnabled()) log("done");     // 钩子：默认不做事
    }
protected:
    virtual std::string read() = 0;
    virtual std::string sanitize(const std::string& s) { return s; }
    virtual void save(const std::string& s) = 0;
    virtual bool logEnabled() const { return false; }  // 钩子
};

class CsvProcessor : public DataProcessor {
protected:
    std::string read() override { return "csv"; }
    void save(const std::string& s) override {}
};
```
基类控制"何时调用什么"，子类控制"怎么做"。**钩子（hook）**是默认空实现的虚函数，子类可选覆写，给算法加扩展点而不破坏骨架。
## 模板方法 vs 策略
| 维度 | 模板方法 | 策略 |
|---|---|---|
| 复用方式 | 继承：子类覆写步骤 | 组合：注入算法对象 |
| 骨架位置 | 基类固定 | 上下文调用策略接口 |
| 扩展时机 | 编译期继承覆写 | 运行期替换策略实例 |
| 调用方向 | 父类调用子类 | 上下文调用策略 |
## 实际应用
- 框架生命周期：App 启动流程、游戏循环、测试框架 `setUp/run/tearDown`
- CRTP 变体：基类模板用 `static_cast<Derived&>(*this)` 调派生方法，零虚函数开销
- `std::copy` 等算法与迭代器组合是模板方法思想的体现

# 观察者模式
## 解决的问题
一个对象（主题）状态变化时需通知多个依赖对象（观察者），但主题不想知道观察者是谁。观察者建立一对多依赖，状态变化自动广播。
## 传统实现
```cpp
class Observer {
public:
    virtual ~Observer() = default;
    virtual void update(const std::string& msg) = 0;
};

class Subject {
public:
    void attach(std::shared_ptr<Observer> o) { observers_.push_back(std::move(o)); }
    void detach(const Observer* o) { /* 移除 */ }
    void notify(const std::string& msg) {
        for (auto& o : observers_) o->update(msg);
    }
private:
    std::vector<std::shared_ptr<Observer>> observers_;
};
```
注意：观察者在 `update` 中修改列表会导致遍历时迭代器失效，需拷贝副本或延迟处理。
## 现代实现：信号槽
用 `std::function` 列表替代 `Observer` 子类，主题不依赖任何观察者类型：
```cpp
class Subject {
public:
    using Slot = std::function<void(const std::string&)>;
    std::size_t connect(Slot s) { slots_.push_back(std::move(s)); return slots_.size() - 1; }
    void disconnect(std::size_t id) { /* 按 id 移除 */ }
    void notify(const std::string& msg) {
        for (auto& s : slots_) s(msg);
    }
private:
    std::vector<Slot> slots_;
};

Subject subj;
subj.connect([](const std::string& m) { std::cout << m; });
subj.notify("hello");
```
## 观察者 vs 发布-订阅
| 维度 | 观察者 | 发布-订阅 |
|---|---|---|
| 耦合 | 主题与观察者仍互相认识 | 经消息代理完全解耦 |
| 通知方式 | 直接调用 update | 投递消息，可异步 |
| 代表 | GUI 事件、信号槽 | 消息队列、事件总线 |
## 实际应用
- GUI 事件系统（按钮点击 → 处理函数）
- Qt 信号槽、Boost.Signals2
- 游戏成就系统监听玩家行为（[[#生产者-消费者模式|与生产者消费者模式]]配合做事件流水线）

# 迭代器模式
## 解决的问题
需要顺序访问容器内元素，但不暴露容器内部表示（数组、链表、树）。迭代器把"遍历"从容器分离，统一访问接口。
## C++ 标准库是迭代器模式的最大实践
```cpp
std::vector<int> v{1, 2, 3};
for (auto it = v.begin(); it != v.end(); ++it) {
    std::cout << *it;
}
```
STL 迭代器本质是**指针的泛化**，通过 `operator*`、`operator++`、`operator!=` 重载让算法与容器解耦：`std::sort`、`std::find` 只依赖迭代器，不关心容器是 `vector` 还是 `deque`。
## 迭代器分类（C++ 五种）
| 类别 | 能力 | 容器 |
|---|---|---|
| Input | 单向只读一次 | `std::istream_iterator` |
| Output | 单向只写 | `std::ostream_iterator` |
| Forward | 单向可多遍 | `std::forward_list`、`unordered_*` |
| Bidirectional | 可前可后 | `std::list`、`set`、`map` |
| RandomAccess | 下标跳跃 `it + n` | `std::vector`、`deque`、数组 |
不同容器提供不同能力的迭代器，算法用**标签分派（tag dispatch）**选择最佳实现：`std::distance` 对随机访问迭代器是 `O(1)`，对单向是 `O(n)`。
## 迭代器失效
修改容器可能导致迭代器失效，是 C++ 常见 bug 来源：
| 操作 | vector | list/set/map |
|---|---|---|
| 插入/删除 | 失效（可能重分配或移动元素） | 其他迭代器不受影响（指向被删节点的除外） |
| 扩容 | 全部失效 | 无扩容概念 |
> [!warning] 失效的迭代器是悬垂指针，解引用是 UB。循环内删除元素要用 `erase` 的返回值，或 `std::remove_if` + `erase` 惯用法。
## 实际应用
- STL 全部容器与算法
- 数据库游标（遍历查询结果）
- 树/图自定义遍历（前序、后序、BFS 迭代器）

# 责任链模式
## 解决的问题
多个处理器都可能处理同一请求，但不确定谁处理、顺序如何。责任链把处理器串成链，请求沿链传递，直到某个处理器处理并终止（或全部不处理）。
```cpp
class Handler {
public:
    virtual ~Handler() = default;
    void setNext(std::shared_ptr<Handler> next) { next_ = std::move(next); }
    void handle(const std::string& req) {
        if (canHandle(req)) process(req);
        else if (next_) next_->handle(req);  // 向下传递
    }
protected:
    virtual bool canHandle(const std::string&) = 0;
    virtual void process(const std::string&) = 0;
private:
    std::shared_ptr<Handler> next_;
};

class DebugHandler : public Handler {
protected:
    bool canHandle(const std::string& req) override { return req == "debug"; }
    void process(const std::string&) override {}
};
// InfoHandler / ErrorHandler 同理

auto error = std::make_shared<ErrorHandler>();
auto info = std::make_shared<InfoHandler>();
info->setNext(error);
auto debug = std::make_shared<DebugHandler>();
debug->setNext(info);
debug->handle("info");  // 未被 Debug 处理，传给 Info
```
两种终止策略：**一处理即终止**（日志级别、路由）；或**每个节点都处理并继续**（拦截器/过滤器，请求经过每层做横切逻辑）。
## 实际应用
- 日志级别链：DEBUG → INFO → ERROR 逐级检查
- Web 中间件/拦截器链（Spring Interceptor、Express 中间件）
- GUI 事件冒泡（子控件不处理则传给父控件）
- try-catch 层层上抛是责任链思想的语言级体现

# 命令模式
## 解决的问题
把"请求"封装成对象，从而可以参数化、排队、记录日志、支持撤销。调用者（Invoker）不直接操作接收者（Receiver），而是发送一个命令对象。
```cpp
class Command {
public:
    virtual ~Command() = default;
    virtual void execute() = 0;
    virtual void undo() = 0;  // 支持撤销
};

class TextEditor;  // 接收者

class InsertTextCommand : public Command {
public:
    InsertTextCommand(TextEditor& ed, std::string text) : ed_(ed), text_(std::move(text)) {}
    void execute() override { ed_.insert(text_); }
    void undo() override { ed_.removeLast(text_.size()); }
private:
    TextEditor& ed_;
    std::string text_;
};

// Invoker：维护命令历史，支持撤销
class EditorApp {
public:
    void execute(std::unique_ptr<Command> cmd) {
        cmd->execute();
        history_.push_back(std::move(cmd));
    }
    void undo() {
        if (!history_.empty()) {
            history_.back()->undo();
            history_.pop_back();
        }
    }
private:
    std::vector<std::unique_ptr<Command>> history_;
};
```
撤销栈压入已执行命令，undo 弹栈调用 `undo()`。**宏命令**（复合命令）是命令的容器：一个命令内部持有多个子命令，批量执行/撤销。
## 现代实现：std::function
命令只有 `execute`、不需要撤销或状态时，直接用 `std::function<void()>`：
```cpp
std::vector<std::function<void()>> jobs;
jobs.push_back([&] { editor.insert("hi"); });
for (auto& j : jobs) j();
```
## 命令 vs 策略
| 维度 | 命令 | 策略 |
|---|---|---|
| 关注 | 把操作参数化、延迟、撤销 | 选择算法 |
| 附加能力 | 排队、日志、撤销 | 运行期换算法 |
| 关系 | 命令持有接收者 | 策略本身是算法 |
## 实际应用
- 编辑器撤销/重做（与备忘录配合：存 before/after 状态或逆操作）
- 任务队列、宏录制、事务（多个命令组成一个事务，全部成功或回滚）
- 菜单/按钮动作：每个菜单项就是一个命令对象

# 备忘录模式
## 解决的问题
需要保存对象某一时刻的状态以便恢复（快照/回滚），又不破坏封装（不能把私有字段暴露给外部保存）。
```cpp
// 备忘录：保存状态，内容对发起人之外的对象不可见
class Memento {
public:
    explicit Memento(int hp, int x, int y) : hp_(hp), x_(x), y_(y) {}
private:
    int hp_, x_, y_;
    friend class GameCharacter;  // 只有原主能读写
};

// 发起人：产生/恢复备忘录
class GameCharacter {
public:
    Memento save() const { return Memento(hp_, x_, y_); }
    void restore(const Memento& m) { hp_ = m.hp_; x_ = m.x_; y_ = m.y_; }
private:
    int hp_ = 100, x_ = 0, y_ = 0;
};

// 看护人：只保存备忘录，不读内容
class Caretaker {
public:
    void push(Memento m) { history_.push(std::move(m)); }
    Memento pop() { auto m = std::move(history_.top()); history_.pop(); return m; }
private:
    std::stack<Memento> history_;
};
```
三个角色：
| 角色 | 职责 |
|---|---|
| Memento | 存放快照，内容对发起人之外不可见 |
| Originator（发起人） | 生成快照 / 从快照恢复 |
| Caretaker（看护人） | 管理快照生命周期（何时存、何时恢复） |
## 与序列化/深拷贝的区别
| 维度 | 备忘录 | 序列化 |
|---|---|---|
| 目的 | 内存内状态回滚 | 跨进程/存储传输 |
| 存储 | 内存对象 | 字节流（文件/网络） |
| 可见性 | 不暴露内部结构 | 常需结构可读 |
备忘录存大量快照时内存开销大，通常只保留**增量**（记录变化字段），或用命令模式的撤销栈替代。
## 实际应用
- 游戏存档点/检查点回滚
- 编辑器撤销（与命令模式结合）
- 数据库事务回滚日志的思想来源

# 状态模式
## 解决的问题
对象在不同状态下行为不同（TCP 连接的 ESTABLISHED、LISTEN、CLOSED），用 if-else 判断状态会让代码随状态增多而难以维护。状态模式把每个状态的行为封装成独立类，状态切换即替换内部状态对象。
```cpp
class Context;
class State {
public:
    virtual ~State() = default;
    virtual void handle(Context& ctx) = 0;
};

class StateA : public State { public: void handle(Context& ctx) override; };
class StateB : public State { public: void handle(Context& ctx) override; };

class Context {
public:
    void setState(std::shared_ptr<State> s) { state_ = std::move(s); }
    void request() { state_->handle(*this); }
private:
    std::shared_ptr<State> state_ = std::make_shared<StateA>();
};

void StateA::handle(Context& ctx) { ctx.setState(std::make_shared<StateB>()); }  // A→B
void StateB::handle(Context& ctx) { ctx.setState(std::make_shared<StateA>()); }  // B→A
```
状态转移逻辑从 if-else 中移出，落在各状态类内部。新增状态 = 新增状态类 + 定义转移，符合 OCP。
## 状态模式 vs 表驱动状态机
| 维度 | 状态模式 | 表驱动 FSM |
|---|---|---|
| 组织 | 每个状态一个类 | 转移表 `[当前态][事件] → 下一个态` |
| 扩展 | 加类 + 改转移代码 | 加一行表项 |
| 适用 | 状态内行为复杂时 | 状态多、行为简单时 |
| 代表 | OOP 风格 | 数据驱动，可配置文件化 |
状态多且行为简单用转移表（词法分析器）；状态行为复杂用状态模式。
## 实际应用
- 网络协议状态机（TCP、HTTP 连接）
- 游戏角色状态（待机、行走、攻击、死亡），与[[#命令模式|命令模式]]配合处理输入
- UI 控件状态、电梯/门禁等硬件状态机

# 访问者模式
## 解决的问题
对稳定的对象结构（AST 节点集合、文档元素）不断增加新操作（求值、打印、类型检查）。如果每次加操作都改元素类，会频繁违反开闭原则。访问者把**操作**从元素类分离：新增操作 = 新增访问者类，元素类不动。
## 双重分派
普通虚函数是**单分派**：运行期只按"调用对象"的类型选择函数。访问者需要同时按"元素类型 + 访问者类型"选择行为：`accept` 触发第一重分派，访问者方法触发第二重分派。
```cpp
class Visitor;
class Element {
public:
    virtual ~Element() = default;
    virtual void accept(Visitor& v) = 0;  // 第一重分派：把自身类型交给访问者
};

class Num : public Element {
public:
    void accept(Visitor& v) override;  // 调用 v.visitNum(*this)
    int value() const { return val_; }
private:
    int val_ = 0;
};
class Add : public Element {
public:
    void accept(Visitor& v) override;  // 调用 v.visitAdd(*this)
};

class Visitor {
public:
    virtual ~Visitor() = default;
    virtual void visitNum(Num&) = 0;  // 第二重分派：按元素类型选择方法
    virtual void visitAdd(Add&) = 0;
};

class Evaluator : public Visitor {
public:
    int result = 0;
    void visitNum(Num& n) override { result = n.value(); }
    void visitAdd(Add& a) override { /* 递归求值 */ }
};
```
新增操作：写一个新的 `Visitor` 子类，元素类不动。**代价**：新增元素类型时要给所有访问者加方法，元素结构必须稳定。
## 现代 C++ 替代：std::variant + std::visit
元素类型固定且全集已知时，`std::variant` 内置多态访问，是访问者模式的安全替代：
```cpp
using Node = std::variant<Num, Add>;
int eval(const Node& n) {
    return std::visit([](auto&& e) { return e.value(); }, n);
}
```
## 访问者 vs 迭代器
| 维度 | 迭代器 | 访问者 |
|---|---|---|
| 目的 | 遍历元素 | 在元素上执行操作 |
| 结构变化 | 换容器 | 换操作 |
| 组合方式 | 迭代器 + 算法 | 结构 + 访问者 |
## 实际应用
- 编译器：AST 的求值、打印、类型检查、代码生成 = 多个 Visitor
- 图形文档导出：同一对象图导出成 JSON、XML、SVG 各一个 Visitor
- 字节码分析、报表计算

# 中介者模式
## 解决的问题
多个对象互相直接引用形成**网状依赖**，任一变化都牵动其他对象。中介者用一个中介对象封装一组对象的交互，把网状结构变成星型结构：对象只与中介者通信。
```cpp
class Mediator;
class Colleague {
public:
    virtual ~Colleague() = default;
    void setMediator(Mediator* m) { mediator_ = m; }
protected:
    Mediator* mediator_ = nullptr;
};

class Mediator {
public:
    virtual ~Mediator() = default;
    virtual void send(const std::string& msg, Colleague* from) = 0;
};

// 聊天室中介者：把消息转发给其他成员
class ChatRoom : public Mediator {
public:
    void send(const std::string& msg, Colleague* from) override {
        for (auto* c : members_) if (c != from) /* 转发给 c */;
    }
    void join(Colleague* c) { c->setMediator(this); members_.push_back(c); }
private:
    std::vector<Colleague*> members_;
};

class User : public Colleague {
public:
    void send(const std::string& msg) { mediator_->send(msg, this); }
    void receive(const std::string& msg) {}
};
```
对象间不再互持引用，只依赖中介者接口，新增成员不影响其他成员。**代价**：中介者可能膨胀成"上帝对象"，需控制其复杂度。
## 中介者 vs 外观
| 维度 | 中介者 | 外观 |
|---|---|---|
| 通信 | 双向协调，对象间互不直接交互 | 单向统一入口 |
| 方向 | 各方 → 中介者 → 各方 | 客户端 → 外观 → 子系统 |
| 关系 | 对象互相认识中介者 | 子系统不感知外观 |
## 实际应用
- 聊天室、GUI 对话框内控件互相联动（一个控件变化影响其他控件）
- 飞机塔台调度（各飞机不直接通信，统一由塔台协调）
- 消息队列/事件总线本质是中介者的异步实现

# 解释器模式
## 解决的问题
需要解析并执行一种**文法/语言**（自定义配置表达式、查询语句、DSL），且文法简单、频繁变化。解释器把每种文法规则映射为一个类，用对象组合表示文法结构（AST），解释即遍历求值。
```cpp
class Expr {
public:
    virtual ~Expr() = default;
    virtual int eval() const = 0;
};

// 终结符表达式：数字
class Num : public Expr {
public:
    explicit Num(int v) : v_(v) {}
    int eval() const override { return v_; }
private:
    int v_;
};

// 非终结符表达式：二元运算
class BinaryOp : public Expr {
public:
    BinaryOp(char op, std::unique_ptr<Expr> l, std::unique_ptr<Expr> r)
        : op_(op), left_(std::move(l)), right_(std::move(r)) {}
    int eval() const override {
        int l = left_->eval(), r = right_->eval();
        return op_ == '+' ? l + r : l - r;
    }
private:
    char op_;
    std::unique_ptr<Expr> left_, right_;
};

// 构建 AST：2 + (3 - 1)
auto expr = std::make_unique<BinaryOp>('+',
    std::make_unique<Num>(2),
    std::make_unique<BinaryOp>('-', std::make_unique<Num>(3), std::make_unique<Num>(1)));
int result = expr->eval();  // 4
```
文法每增加一条规则 = 增加一个表达式类，解释器通过递归求值遍历 AST。
## 解释器 vs 编译
解释器"边解析边执行"，编译先生成中间表示/机器码再执行。解释器实现简单、便于动态修改文法，但性能差；文法复杂或性能敏感时应考虑正则表达式、解析器生成器（ANTLR/Bison）或直接编译方案。
## 实际应用
- 表达式求值器、规则引擎（如优惠规则 DSL）
- 数据库查询解释
- 配置文件的表达式解析（nginx 变量、Prometheus 查询）
