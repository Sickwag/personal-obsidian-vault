# Ragel 学习笔记
## 前置基础
### 状态机是什么
有限状态机 = 状态集合 + 输入 + 转移规则（+ 初始状态 + 接受状态）。核心动作是查表：当前状态 + 输入 → 下一个状态。地铁闸机是经典例子：Locked 投币 → Unlocked，Unlocked 通过 → Locked，非法输入（强闯）状态保持不变。
四种等价表达：状态转移图（圆点状态 + 箭头输入）、状态转移表（行列式查表）、switch 代码、形式化定义（Q/Σ/δ/q0/F）。
作用：把处理流程显式化，非法输入被拒绝，状态不会走到没定义的分支。应用：TCP 连接状态机（LISTEN、ESTABLISHED）、协议解析器、游戏 AI。
### 正则表达式与状态机的关系
正则描述一类字符串的集合，叫正则语言（Regular Language）。正则给描述，状态机给执行，是一体两面。
- 回溯来源：正则直接翻译成 NFA（非确定有限自动机），读入同一字符可能同时处于多个状态，朴素匹配走一条路失败要退回重试（如 `a|ab` 匹配 `ab`）
- DFA：子集构造把「读入某字符后可能到达的所有状态」打包成一个状态，每个输入唯一确定一个状态，无回溯，逐字符 O(1)
- 代价：DFA 状态数可能指数级膨胀，但每个字符处理 O(1)
- 等价关系只对标准正则成立；反向引用 `\1`、环视等扩展超出有限状态机能力
### 面试回答框架
正则描述一类字符串，状态机是识别它的执行器；正则可转 NFA，NFA 可转等价 DFA；DFA 每输入只走一条路，匹配无回溯，代价是状态数可能膨胀。
### 深问与澄清
- 状态互斥：FSM 任意时刻恰好一个状态，状态集合互斥且穷尽；NFA 的「多状态」是候选路径的抽象，真实运行的机器任一时刻只在一个状态
- 子集构造：NFA 读入字符后可能处于 `{s1, s2}`，子集构造把该集合打包成 DFA 的单个状态 S′，作为原子整体参与转移；n 个 NFA 状态最多产生 2^n 个 DFA 状态；DFA 同一时刻也是一个状态，只是其「值」是 NFA 状态的一个子集
- 编译期 vs 运行时：NFA 和 DFA 的构造都可在编译期完成；差别在运行时——NFA 要遍历所有可能状态（等于现场做子集构造，最坏指数级），DFA 一次数组查表 O(1)。「运行时正则引擎」指把 NFA 或回溯留给运行时执行的引擎（`std::regex`、PCRE）
- 反向引用：`(a+)b\1` 匹配 `a^n b a^n`，需记住随输入变长的子串，超出 FSM 的固定大小记忆 → 非正则语言，只能靠回溯引擎
- 环视：`(?=...)` 零宽断言，子模式本身正则时可折叠进状态机、不改变可识别语言类；常与反向引用组合（`(?=(a+)\1)`）借其超纲能力
- 面试口径：为什么正则不总能编译成状态机 → 反向引用需要与输入等长的记忆，有限状态机做不到
## 定位
Ragel 是状态机编译器，它在编译期用正则风格的 DSL 生成 DFA 查表代码（C/C++/Java/Go/Ruby 等），运行时逐字符查表匹配，单步 O(1)，无回溯。
## 工作流
```
scanner.rl ──ragel -C──> scanner.cpp ──g++──> scanner
```
数据流：描述（编译期）→ DFA 状态机代码 → 运行时逐字符查表。
## 核心原理
- 生成的 `.cpp` 里是 `_trans_targs`（转移目标表）、`_trans_actions`（转移动作表）、`_actions`（动作函数表）等大数组
- 状态是整数，转移靠数组下标查表，不靠 `if/switch` 逐层判断
- 每个 token 在扫描器模式下通过 `ts`（token 起始）与 `te`（token 结束）指针定位，`std::string(ts, te)` 取出词法单元文本
- scanner 构造 `|* ... *|` 逐条尝试模式，`=> 动作名` 在匹配完成时执行，动作 `{ }` 内是原生 C++，直接嵌入生成代码
### 生成代码结构
- `.rl` 文件两半：`%%{ }%%` 内是 Ragel DSL，`%%{ }%%` 外是原样透传的 C++，生成代码 = 透传 C++ + 插入的生成段
- 三个 write 插入点：`data`（静态表）、`init`（`cs = scanner_start; ts = 0; te = 0; act = 0;`）、`exec`（主循环），顺序不可颠倒
- exec 骨架：`_resume`（进入状态动作，state 0 时 `ts = p`）→ 查表 → `_match`（更新 cs + 执行转移动作）→ `_again`（离开状态动作，回 state 0 时 `ts = 0`）→ `++p` → `_test_eof`
- 数据表编码：`_trans_keys` 存字符/字符区间（key_offsets 定位每个状态）、`_indicies` 存转移号（每个状态末尾多一个 no-match 槽）、`_trans_targs` 转移号→目标状态、`_trans_actions` 转移号→动作偏移、`_actions` 动作程序（数量 + id）
- `#line N "file"`：C 预处理指令，把编译错误/调试器行号映射回 `.rl` 源文件，没有它错误会报在生成的 `.cpp` 行号上
- 数组分行是排版，每行 8 个值，行切分与状态边界无对应关系
- `te = p; p--`：扫描器多读一格再回退，实现最长匹配；破坏 token 的字符在 token 边界重新处理，单字符 token 用 `te = p + 1` 不回退
### 运行时接口变量
| 变量 | 角色 | 初始化 |
|---|---|---|
| p | 读头，指向下一个要读的字符 | 用户赋值 |
| pe | 输入结束位置，p == pe 表示读完 | 用户赋值 |
| cs | 当前状态编号 | write init |
| eof | 输入末尾指针，用于 EOF 收尾 | 用户赋值（通常 = pe） |
| ts | 当前 token 起点 | 生成代码 |
| te | 当前 token 终点 | 生成代码 |
| act | 当前最长匹配属于哪条规则 | write init |
作用域：`write init` / `write exec` 的展开代码引用这些变量，必须在同作用域先声明（函数局部变量最安全）；`write data` 在文件作用域生成静态表，不需要这些变量。
变量集合按需声明（名字固定，生成代码按名引用）：
- 普通机器只要 p、pe、cs（已实测：`'a' 'b'*` 只声明三个变量即可编译）
- scanner 模式必须 eof + act（token 可能在输入末尾结束，需 eof 收尾；act 被 init 引用；实测不声明 eof 报编译错）
- ts/te 在 scanner 模式或动作里用到 token 边界时声明
- stack/top 用于 `fcall` / `fret`（子状态机调用）；data 用于输入分段的流式解析
声明原则：加到编译通过为止 ，多余的变量会有 unused 告警，用 `(void)x` 消除
### 动作嵌入点
| 操作符和 action | 名字       | 触发时机                                                                                                   |
| ----------- | -------- | ------------------------------------------------------------------------------------------------------ |
| `e > act`   | entering | 表达式匹配开始时，执行一次                                                                                          |
| `e $ act`   | every    | 表达式内每消费一个字符                                                                                            |
| `e @ act`   | final    | 到达表达式的可接受位置，在 `a+` 表示一个或多个的情况下对字符流解析时，并不知道下一个字符是否仍然符合正则规则，所以 `aa`，`aaa`，`aaa...` 每次读取一个字符时表达式仍成立就会执行一次 |
| `e % act`   | leaving  | 匹配完成离开表达式，发现**当前读入的字符**如果和之前读入的内容放在一起算一个 token 就不满足表达式了，执行一次。（注意这里已经读入了不符合匹配规则的字符）<br>这个符号常用作收尾处理，清理状态 |
| `p => act`  | scan     | scanner 提交整个 token 时，即在确认当前读取当前字符串后会导致正则规则失效之后，通过回溯判断当前字符之前的 token 是我这个正则规则能够匹配的**最长字符**时触发            |
实测（`[a-z]+`，输入 ab）：触发顺序 >enter →（逐字符 $ 和 @）→ %leave → =>scan；`@` 在 `+` 模式里每个可接受位置都触发（每个前缀都是完整匹配），这是它和 `%` 的区别
面试口径：action 定义具名代码，嵌入点决定触发时机——进入 `>`、逐字符 `$`、可接受位置 `@`、离开 `%`、scanner 提交 `=>`
### scanner 构造语义
- `|* ... *|` 是扫描器构造：一张从上到下的规则表，最长匹配，平局时先定义的规则优先
- 规则 `模式 => 动作` 在匹配被确认时执行动作
- act 用于「一条规则的完整匹配是另一条更长规则的前缀」场景（如 ab 与 abc）；规则间无前缀关系时 act 只初始化、不真正使用
- 内建字符类：digit（0-9）、alpha（A-Z a-z）、alnum、space、any（单字符）；运算符 `+` `*` `|` `-`（集合差）`( )`，相邻即拼接（`ab` ≡ `a.b`）
- 定义块四层：machine 命名 → action 动作 → 模式定义 → `main := |* ... *|`
- `any` 兜底规则必须放最后，否则没有规则覆盖的字符会导致扫描失败
### 普通状态机 vs scanner
| 维度 | 普通 | scanner |
|---|---|---|
| 定义 | `main := expr;` | `main := \|* ... *\|;` |
| 语义 | 匹配单个表达式，走到接受状态即成功 | 规则表 + 最长匹配 + 提交 token |
| 变量 | 最少 p/pe/cs | 还要 ts/te/act/eof |
| 用途 | 格式校验（如 HTTP 方法） | 词法分析，切成 token 流 |
区别：普通回答「这段输入匹配吗」，scanner 回答「由哪些 token 组成」。
### fcall/fret 子状态机调用
- `fcall A` 压栈返回点并跳入子机器 A；子机器 `fret` 弹栈返回主机器，类比 C++ 函数调用；fcall 不「生成」子机器，子机器独立用 `:=` 定义
- 子机器必须用 `:=` 定义入口（实测 `=` 定义的模式作为 fcall 目标报「could not resolve state reference」）
- 需要 `stack`（调用栈数组）与 `top`（栈顶指针），top 需用户置 0
- 坑（实测）：fret 用 `@`（进入终态触发）挂才执行；用 `%`（离开终态触发）挂，子机器终点没有后续转移不会自己触发；`@` 挂 `[a-c]+` 会在每个可接受位置提前触发，挂确定的 `'a' 'b'` 只在匹配完成后触发一次
- 面试几乎不问，知道存在即可
### 三种机器类型
| 类型 | 写法 | 用途 |
|---|---|---|
| 普通状态机 | `main := 正则;` | 匹配单个表达式，识别/校验（可引用子机器、`|` `*` 组合任意复杂） |
| scanner | `main := \|* 规则; 规则; *\|;` | 规则表 + 最长匹配，切 token 流 |
| 状态图 | `name = label: expr, expr -> label, ...;` | 手动搭状态转移：`,` 并列拼接、`label:` 贴标签、`expr -> label` epsilon 转移、`start:` 入口、`-> final` 隐式终态 |
state chart 用于正则表达不了的控制流（手册：drop down one level of abstraction），可和正则混用；面试几乎不问
state chart 是同一台机器的底层画法（正则=用语言描述，状态图=用图描述），管的是机器内部状态关系，不是「管理多台机器的元状态机」
带类型 token 流：`struct Token { Tok type; std::string text; };` + scanner 规则表 + 动作里 `tokens.push_back({Tok::ID, std::string(ts, te)});`（已实测 code/08-machines/lexer.rl）
### data 与流式解析
- 核心机制：DFA 的下一步只由「当前状态 + 下一个字符」决定，不需要看到全部输入，所以可读一块喂一块增量解析
- 标准循环：读块 → p/pe 指向块 → 非末尾块 `eof = 0`、末尾块 `eof = pe` → `%% write exec`（从当前 cs 继续）→ 用 ts/te 保留未完成 token 前缀，下一块接上
- 缓冲必须不小于最长 token，否则报 TOKEN TOO BIG
- 已实测 code/09-stream/streamlex.rl：8 字节缓冲下 `counter`、`12345` 跨块解析仍正确
- data 变量指向当前数据块
- 流式增量解析是 Ragel 相对 std::regex 的核心优势，面试「Ragel 能处理流式输入吗」的答案
### 模型修正要点
- DFA 状态 ≠ action：状态由模式结构编译而来，action 是挂在转移/状态上的代码
- 输入是运行时数据；DFA 开销 O(n) 线性查表（每字符 O(1)），消除的是回溯（最坏指数级 → 线性）
- 内建字符类等价预定义正则：digit ≡ `[0-9]`、alpha ≡ `[a-zA-Z]`、alnum ≡ `[0-9a-zA-Z]`，可等价替换

## 与正则引擎对比
| 维度 | Ragel | 运行时正则（std::regex/PCRE） |
|---|---|---|
| 匹配方式 | 编译期构建 DFA，查表 | 运行时回溯，最坏指数级 |
| 流式解析 | 支持增量（读一段停一段） | 通常需整体输入 |
| 可验证性 | 编译期报错，生成固定状态集 | 运行时才知道 |
| 适用场景 | 协议解析、词法分析、高性能校验 | 一次性小文本匹配 |
## 选型对比
| 方案 | 匹配方式 | 流式 | 维护成本 | 适用 |
|---|---|---|---|---|
| 手写状态机 | 手写 switch/表 | 可以 | 高，状态一多难改 | 状态少到数得清 |
| std::regex | 运行时回溯 | 通常不行 | 低 | 一次性小文本匹配 |
| flex | 生成 DFA | 可以 | 中 | 经典词法分析 |
| Ragel | 编译期 DFA 查表 | 可以（增量） | 低 | 协议解析、词法、高性能 |
Ragel 与 flex 都生成 DFA，Ragel 额外提供多语言代码生成、嵌入任意 C++ 逻辑、可混用的状态图
## 为什么比手写状态机好
手写状态机问题：状态多、边界多（EOF、空输入、非法字符）、分支相互影响、难维护难测试。Ragel 把「描述」和「实现」分离，你写规则，工具生成可验证的状态机。
## 面试要点
- 高频链：Ragel 和正则的区别 → 为什么生成的状态机快 → DFA 怎么来的 → 用过的场景
- 回答骨架：Ragel 把正则描述在编译期编译成 DFA，运行时查表匹配，无回溯，适合流式高性能解析
- 三个必背回答：
  - 是什么：状态机编译器，正则风格 DSL → 编译期 DFA → 生成 C/C++ 查表代码，运行时逐字符查表无回溯
  - 和正则区别：正则描述模式、状态机识别模式，一体两面；区别在编译期（Ragel）vs 运行时（std::regex 回溯）
  - 为什么快：DFA 每字符唯一转移 O(1)，总 O(n)；编译期子集构造把 NFA 的路径探索提前做完，运行时只剩查表
- 常考九题要点：
  - DFA/NFA 区别：确定 vs 不确定；子集构造转换，代价状态数最多 2^n
  - 正则都能编译成状态机吗：标准正则可以；反向引用 `\1` 需随输入增长的记忆，超出 FSM，只能回溯
  - 流式解析：DFA 只依赖当前状态+下一字符，块间保留 cs 增量走；跨块 token 用 ts/te 保留前缀；缓冲≥最长 token
  - 现场写词法分析器骨架：enum Token 类型 + scanner 规则表 + 动作 push_back；关键字排前（平局优先）、最长匹配、scanner 需声明 ts/te/act/eof
  - Ragel vs flex：都生成 DFA；Ragel 多语言、可嵌任意代码、可混用状态图
  - 手写 vs 生成：状态少手写，状态一多手写难维护（边界多、分支互相影响），用生成工具
- 语法速查：`%%{ }%%` 嵌入块、`machine` 命名、`main :=` 主状态机、`action` 定义、`write data/init/exec` 插入点
- 简历话术：用 Ragel 写词法分析器/协议解析器，.rl 定义规则和动作，编译期生成 DFA 查表代码，处理流式增量输入，对比过手写状态机可维护性
