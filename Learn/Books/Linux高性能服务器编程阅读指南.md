最值得迁移的结构是统一事件源、增量解析、定时器组织和任务型并发。它们让框架能够把“发生了什么”与“谁执行、何时释放”分开，但必须补上错误路径。

| --- | --- | --- |
| 信号转为 `socketpair` 可读事件 | 将处理工作移入正常事件循环 | 信号安全、通知丢失恢复、读至 `EAGAIN`、标准信号合并 |

以下是围绕本书的独立角色分析，区分作者教学选择、正文代码事实和工程推断。主线程独立审查者参与了第二轮回应；没有将单个代理的多种语气当作多代理辩论。

| 命题 | 机制学习者的最强支持 | 可靠性或性能角色的质疑 | 独立审查后的裁决 |
| --- | --- | --- | --- |
| ET 减少重复通知，适合高并发 | 非阻塞循环可批量取尽数据，减少返回复用器的频率 | 一个持续发送的热连接可能占满执行时间，吞吐改善不保证尾延迟 | ET 处理预算必须搭配用户态 ready 队列或显式重调度；未读尽就直接等待可能永久停顿 |
| `EPOLLONESHOT` 避免多个线程同时处理连接 | 收到通知后暂时禁止继续通知，完成后由处理者重新启用 | 不约束已排队任务、正在执行的裸指针或关闭后复用的 fd | 保留稳定对象所有权或 generation token；通知串行与释放安全分别验收 |

| 共享内存读者无需锁 | 单写者减少写写冲突，避免通过控制通道传整块数据 | 读者仍可能读到被下一次写覆盖的记录，通知编号不能形成快照 | 需版本/槽位所有权、确认或不可变消息；单写者不是读写一致性证明 |

独立审查提出的验收场景：一个高热连接与多个低速连接同时运行，注入半关闭、短写、任务执行期间关闭并立即重连；记录每连接 p99 与内存错误。只提高平均吞吐不能反驳公平性质疑；只跑正常退出不能证明线程池析构安全。上述问题依本地代码静态核验，实验结果尚未获得。
## TCP/IP 协议族
对应第 1 章。核心是把应用数据经过哪一层封装、由哪一个字段分用、交给哪一跳发送讲清楚。网络故障不能只从 `recv` 返回值解释，还要区分地址解析、路由、传输与应用协议。
### 核心机制与重点
调用链：应用调用 `send` → socket 发送缓冲 → TCP 添加端口、序号等 → IP 查询路由 → 对直连目的或网关执行 ARP（Address Resolution Protocol，地址解析协议） → 链路帧发送。接收则按以太类型、IP 协议号、传输层端口逐层分用。跨网段 ARP 解析的是下一跳，不是互联网远端服务器的 MAC。
精读 1.2“封装”、1.3“分用”、1.5.2“ARP 高速缓存的查看和修改”、1.5.3“使用 tcpdump 观察 ARP 通信过程”、1.6.3 的 DNS 抓包和 1.7“socket 和 TCP/IP 协议族的关系”。1.4 的实验网络图用来识别捕获位置；1.1 的协议清单知道层次即可，不必平铺背诵。
有价值之处是从同一段包的不同首部识别分用边界。书中 DNS（Domain Name System，域名系统）的报文长度与查询路径属于传统实验环境，不能据此断言所有 DNS 数据报都小于 512 字节或只能经 UDP 查询。
### 引申与校正
- 字段语义：正文 1.3 将 IPv4 协议字段写成 16 位，与 2.2 的 8 位说明矛盾；按 IPv4 标准核对。IPv4 首部、TCP 与 ICMP 的 Internet checksum 不是 CRC；不能把以太帧 FCS 的 CRC 算法移植过去。[IPv4 RFC 791](https://www.rfc-editor.org/rfc/rfc791.html)
- 故障归因：抓包前先写“预期哪个接口、哪一跳、哪个协议号出现什么包”。没有 ARP 响应与 TCP 端口未监听的证据不同；缓存命中也会导致本次请求没有 DNS 或 ARP 包，不能直接判定工具漏包。
### 输出思考题
1. 设计两台跨网段主机的访问过程，分别写出 IP 目的地址、帧目的 MAC、ARP 查询对象。若网关替换但远端 IP 不变，哪些缓存必须重新建立？给出抓包预测。
2. 一个域名首次访问失败，第二次成功。列出三个处于不同层次的解释，并为每个解释设计能排除其余两种的证据。
3. 如果应用改为直接连接 IP，哪些协议开销消失，哪些仍然存在？说明直接 IP 为何可能破坏 HTTPS 或虚拟主机语义。
## IP 协议详解
对应第 2 章。IP 提供尽力交付与路由，不负责为应用恢复丢失字节。重点是从 MTU（Maximum Transmission Unit，最大传输单元）、分片、TTL 与路由决策解释“包为什么没到”。
### 核心机制与重点
发送路径：选出站接口与下一跳 → 判断报文大小及分片限制 → 填写 TTL 与首部 → 交链路层。转发设备更新跳数并再次路由；目的主机按标识、片偏移和 MF 位重组 IPv4 分片，片偏移以 8 字节为单位。任一片丢失都可能使整个原始报文失效。
精读 2.2.1“IPv4 头部结构”、2.3“IP 分片”、2.4.1“IP 模块工作流程”、2.4.2“路由机制”、2.5“IP 转发”和 2.7.2“IPv6 扩展头部”。2.6 的重定向案例理解机制与信任边界，不复制旧网络中的主机和路由配置。
书中按主机路由、网络路由、默认路由组织推演容易入门；现代查找须按最长前缀匹配理解，策略路由可使源地址或规则参与选表。书中的具体路由缓存展示不能当作所有现代内核都存在同一缓存接口的依据。
### 引申与校正
- 路径 MTU：IPv4 分片与 IPv6 源端分片不同；IPv6 路由器不替发送方分片，过大报文依靠 Packet Too Big 等机制反馈。RFC 8200 已取代书中提到的 RFC 2460。[IPv6 RFC 8200](https://www.rfc-editor.org/rfc/rfc8200.html)
- 观测边界：网卡分段与接收聚合会使主机捕获的包大小不同于线上实际帧；判断分片前记录捕获接口、方向和 offload 条件。TOS 的旧位图也不能直接替代现代 DSCP/ECN 字段含义。
### 输出思考题
1. 一条路径小请求成功，大响应长期停顿。提出分片、PMTU 反馈被阻断、应用发送状态三种假设，写出各自的抓包差异和排除顺序。
2. 给定总长、首部长度与 MTU，自行构造至少三个 IPv4 分片，计算每片长度、MF 位和偏移；若中间一片丢失，解释 TCP 与 UDP 应用会怎样获知失败。
3. 给出两个重叠前缀和默认路由，预测匹配结果；加入源地址选路规则后，解释为什么只查看目的地址无法完整复现决策。
## TCP 协议详解
对应第 3 章。TCP 的可靠字节流、全双工、流量控制与拥塞控制是不同职责。应用消息边界、业务确认和资源生命周期仍需自己定义。
### 核心机制与重点
状态链：监听/主动连接 → 握手交换序号与选项 → 已建立状态下按序交付 → 一侧 `shutdown` 写方向 → 对端读到 EOF 但另一方向可继续 → FIN 握手与可能的 `TIME_WAIT`。发送端受接收窗口与拥塞窗口共同约束；确认号描述下一期待字节，不是对每一个段都无条件加一。
精读 3.2.2“TCP 头部选项”、3.3.2“半关闭状态”、3.4.1“TCP 状态转移总图”、3.4.2“TIME_WAIT 状态”、3.5 的三类 RST、3.9“TCP 超时重传”和 3.10.3“快速重传和快速恢复”。3.6 的交互数据流与 Nagle 行为结合应用小包实验；3.8 的带外数据理解历史语义，常规业务不要用它替代协议控制帧。
`send` 返回成功只表示字节已被本机接收处理，不表示对端应用读到、持久化或执行业务。应用要有自己的响应和幂等语义。`TIME_WAIT` 约束连接四元组与旧段隔离，不意味着某服务端口从此不能监听。
### 引申与校正
- 协议字段：SACK（Selective Acknowledgment，选择确认）块描述已收到的非连续字节区间，书中“丢失数据边沿”的解释会反向理解恢复过程；SYN 和 FIN 各占一个序号位置。[SACK RFC 2018](https://www.rfc-editor.org/rfc/rfc2018.html)
- 控制算法：3.10 适合建立 Reno 类机制模型，不能认定所有当前 Linux 连接都运行该算法。重传超时、握手重试总时长和初始窗口都受实现与参数影响；正文抓到的 63 秒属于实验事实，不是 TCP 永久常数。[TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)
### 输出思考题
1. 设计“服务器已经处理请求，但客户端超时重试”的时间线，标出内核确认、应用响应、业务提交的不同时间点；说明 TCP 可靠性为何不能阻止重复业务。
2. 对同一段序号空间给出累计 ACK 与两个 SACK 块，推导哪些字节可重传。若将 SACK 当成缺失区间，算法会造成什么后果？
3. 将半关闭用于上传结束后等待处理结果，画双方状态与 `recv`/`send` 返回值；对端 RST 与正常 FIN 在错误处理上应怎样区分？
4. 频繁短连接耗尽端口时，提出不修改内核参数的三种设计改进，并分析对时延、负载分配和故障隔离的影响。
## 访问 Web 服务器的通信案例
对应第 4 章。把 DNS、ARP、代理和 HTTP 放进一个抓包序列，训练从交错事件恢复因果链，而不是把包号当成线性调用栈。
### 核心机制与重点
正文案例经 Squid 代理访问互联网。链路是浏览器解析或连接代理 → 浏览器与代理建立 TCP → 代理识别目标、必要时解析域名 → 代理与上游建立另一条 TCP → HTTP 请求与响应跨两段连接传递。代理终结并重建连接，不是把原 TCP 报文原封不动地像 IP 路由器一样转发。
精读 4.2.1“HTTP 代理服务器的工作原理”、4.3“使用 tcpdump 抓取传输数据包”、4.4“访问 DNS 服务器”、4.5“本地名称查询”和 4.6 的请求/应答。对正文的 43 个包，先按连接与协议分组，再以序号、确认号和时戳恢复顺序；4.2.2 的旧 Squid 安装操作只作为实验背景。
HTTP 的无状态指协议层不自动保存会话；Cookie 和服务端会话可实现应用状态。缓存命中、DNS 缓存、连接复用都会让一次浏览行为不再对应完整四层序列。HTTPS 下不能默认从普通抓包直接读出明文请求。
### 引申与校正
- HTTP 边界：当前 HTTP/1.1 消息长度由规范确定，不能依 TCP 包长度划分；请求转发涉及目标形式、首部和连接管理，不是只复制正文。[HTTP/1.1 RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html)
- 解析位置：名称查询依赖当前解析器/NSS 配置，旧 `host.conf` 示例不是所有系统的唯一顺序。NAT 与代理也会改变地址，不能把正文“IP 地址不变”的简化推广至任意路径。
### 输出思考题
1. 同一浏览操作包含两条 TCP 连接，设计仅凭五元组、请求时序和载荷长度区分直连、代理、NAT 的证据；哪些情形仅凭单点抓包无法判定？
2. 当代理命中缓存但客户端发生 DNS 查询时，如何判断查询是否服务于这次 HTTP 请求？提出能证伪“先出现就是因果”的方法。

## Linux 网络编程基础 API

## 高级 I/O 函数
对应第 6 章。高级 I/O 解决散布聚集、内核内转移与映射访问，核心代价是减少用户态缓冲搬运；它们不豁免短写、页缺失或生命周期约束。
### 核心机制与重点
`writev` 将多个缓冲作为一条逻辑字节序列发送；一次返回可能落在某个 `iovec` 中间，需保存总进度并推进基址和长度。`sendfile` 的 offset 明确区分显式游标与共享文件偏移。`splice` 经管道转移，`tee` 复制管道数据引用；每一步返回的实际数量决定下一步可处理多少字节。
精读 6.2“dup 函数和 dup2 函数”、6.3“readv 函数和 writev 函数”、6.4“sendfile 函数”、6.5“mmap 函数和 munmap 函数”、6.6“splice 函数”和 6.8“fcntl 函数”。6.7 的双路转发案例用于推演背压，不必先扩成通用代理。
书中 `dup2` 的“返回大于等于目标”的说法错误：成功时精确使用目标 fd；`dup` 才挑最低未用 fd。复制 fd 共享 open file description，因此文件偏移与 `O_NONBLOCK` 等状态可共享，`FD_CLOEXEC` 是每个 fd 的标志。[dup 手册](https://man7.org/linux/man-pages/man2/dup.2.html)
### 引申与校正
- 传输进度：清单 6-4 不能无视首次 `splice` 返回值，再固定搬 32768 字节；须分清读入数量、管道余量和下游阻塞。清单 6-2 的失败路径需检查未初始化指针、文件 fd 回收与 `writev` 短写，不复制其资源管理习惯。

## Linux 服务器程序规范
对应第 7 章。程序规范解决长期运行时的权限、日志、限制与进程管理；性能实现若无法启动、排错和退出就不构成完整服务。

## I/O 复用
对应第 9 章。核心是从“可等待多少 fd”转为“准备就绪后谁推进状态、何时再次等待”。每个事件都须结合连接状态与生命周期解释。
### 核心机制与重点
调用链：`epoll_ctl` 注册 → 内核记录兴趣与就绪 → `epoll_wait` 返回本轮事件 → 验证连接身份 → 非阻塞读取/写入/接受 → 更新状态与兴趣 → 保留活跃任务或再次等待。ET（Edge Triggered，边缘触发）要求处理已知就绪，通常读到 `EAGAIN`；若设置公平预算，未耗尽连接必须保留在用户态 ready 队列继续调度。

| 机制 | 通知与维护 | 主要边界 |
| --- | --- | --- |
| `select` | 每次传集合并扫描，返回后重建 | `FD_SETSIZE` 与集合覆盖，不能只提高 fd 上限 |
| `poll` | 每次传数组并检查返回项 | 无同样位图上限，但扫描与复制成本仍在 |
| `epoll` LT | 长期兴趣表，返回就绪项 | 未处理会重复通知，应避免永久注册无需求的写事件 |
| `epoll` ET/ONESHOT | 边缘通知或通知后禁用待重启 | drain、公平性、重置失败与所有权需要显式设计 |
精读 9.1.2 的就绪条件、9.3.3“LT 和 ET 模式”、9.3.4“EPOLLONESHOT 事件”、9.5“非阻塞 connect”、9.6 聊天室错误路径、9.7“同时处理 TCP 和 UDP 服务”。9.8 的 `xinetd` 了解交接模型即可。
### 引申与校正
- 教学代码：9-3 对 ET 监听 fd 只 `accept` 一次可能留下已就绪连接；读到 EOF 后关闭却继续循环会触碰已关闭 fd。9-4 将循环局部参数地址交给 `pthread_create`，存在参数失效/复用；9-5 的 fd 集合初始化对象需逐行核对。聊天转发把接收缓冲指针借给多个发送方，还要解决后续覆盖与短写。
- 复杂度与身份：`epoll_wait` 返回 k 个事件仍需 O(k) 用户处理；`maxevents` 是本次输出容量，不是监控总数。ONESHOT 禁用通知后由 `MOD` 重启，不是删除 fd，更不是连接所有权。复制 fd 与 open file description 的关联也影响移除语义。[epoll 手册](https://man7.org/linux/man-pages/man7/epoll.7.html)

## 信号
对应第 10 章。信号是异步控制输入，不适合在处理函数中直接修改复杂业务结构；统一事件源将它转为事件循环可以正常处理的工作。
### 核心机制与重点

## 定时器
对应第 11 章。定时器管理截止时间与取消，不只是每秒调用一次回调。连接释放、刷新活动时间与超时触发可能相互竞争。
### 核心机制与重点
排序链表按到期顺序维护；时间轮用槽位和轮数定位；最小堆以最近截止时间决定事件循环等待上限。调度链：创建 deadline → 注册结构 → 计算下一次等待 → 被 I/O 或时间唤醒 → 读取当前时钟 → 取出所有已到期项 → 校验对象仍有效 → 执行或取消。

| 结构 | 插入/维护 | 到期处理 | 适用条件 |
| --- | --- | --- | --- |
| 排序链表 | 查找插入通常 O(n) | 从头弹出到期项 | 数量小、实现直观 |
| 时间轮 | 定位槽位可很便宜 | 单槽需检查本槽元素与轮数 | 分辨率可接受、分布不严重聚集 |
| 最小堆 | 插入和弹出 O(log n) | 根据堆顶计算等待 | 大量不均匀精确 deadline |
精读 11.2.1“基于升序链表的定时器”、11.2.2“处理非活动连接”、11.3“I/O 复用系统调用的超时参数”、11.4.1“时间轮”、11.4.2“时间堆”。11.1 的 socket 超时与非阻塞事件循环不是同一超时机制，不相互替代。
### 引申与校正
- 时间来源：相对超时应优先单调时钟，不能被系统校时影响。正文 11.3 只扣除等待时间会漏算处理时间；必须每轮从真实当前时间与 deadline 推导余量。`timerfd` 可接入同一 fd 循环。[timerfd 手册](https://man7.org/linux/man-pages/man2/timerfd_create.2.html)
- 取消与释放：时间堆置空回调属于惰性取消，可能延迟释放；时间轮的单槽集中到期仍是线性工作，不能称整个 tick 恒定 O(1)。清单 11-3 的局部 `epollfd` 遮蔽全局变量，回调可能用错 epoll fd；对象释放后旧 timer 还需失效机制。
### 输出思考题
1. 对轮大小 N、精度 T，推演 0、T、N×T、(N+1)×T 四种超时如何分槽与计轮；明确“不会过早”与“延迟不超过一格”的取整条件。
2. 一万条连接同时到期时，时间轮和堆各有什么尾延迟风险？设计到期处理预算，并解释不能按时全部关闭时如何保证语义。

对应第 12 章。重点学习成熟库如何组织注册、激活、超时、后端与跨线程唤醒；不能把结构体字段背下来当成掌握事件循环。
### 核心机制与重点
本章源码基线为 Libevent 2.0.19。注册链：`event_new` → `event_add` → `event_add_internal` → `evmap_io_add` → `eventop.add` → 进入登记结构。循环链：`event_base_loop` → `timeout_next` → 后端 `dispatch` → 激活队列 → 回调执行 → 一次性移除或持久事件再次等待。
精读 12.2.3“event 结构体”、12.2.4“往注册事件队列中添加一个事件”、12.2.5“往事件多路分发器中注册事件”、12.2.6“eventop 结构体”、12.2.7“event_base 结构体”、12.2.8“事件循环”。12.2.2 的目录分类辅助定位 `event.c`、`evmap.c`、`epoll.c`、`minheap-internal.h`、`signal.c`，先追一条路径，不从头浏览所有文件。
同一事件可能同时属于 I/O 登记、超时结构与已激活队列，状态变化是本章真正的难点。跨线程插入更早 deadline 时，不能只修改堆顶，还需唤醒正在等待的循环，否则新截止时间会被错过。
### 引申与校正
- API 演进：按当前公共 API 使用 `event_base_new` 等接口，尽量不依赖内部结构布局。书中基线供源码学习，官方书用于校验今天的事件与循环语义。[Libevent 事件生命周期](https://libevent.org/libevent-book/Ref4_event.html)
- 线程边界：线程支持保护库状态不意味着同一个 `event_base` 的回调自动并行。长回调仍会阻塞该循环，优先级还可能造成低优先事件饥饿；回调预算与 worker 卸载需显式设计。[Libevent 循环与优先级](https://libevent.org/libevent-book/Ref3_eventloop.html)
### 输出思考题
1. 为同一事件画出已登记、有超时、已激活、回调中、已释放的可达状态；若一个触发来源已消失，其他来源是否仍可使其激活？
2. 事件循环准备等一秒，另一线程添加五毫秒后到期的事件。追踪需要修改的数据结构与唤醒链，说明只加锁为什么不能保证按时处理。
3. 对比自研协程框架和该章 Libevent 的 ready 队列、定时器、取消与资源释放，选择一个机制迁移，写出迁移前后的不变量与验收方法。
## 多进程编程
对应第 13 章。多进程隔离地址空间，但 fd 的内核对象和显式共享内存仍可共享。隔离效果取决于哪些状态复制、哪些状态共享、谁负责收尸。
### 核心机制与重点
`fork` 形成独立地址空间，通常使用写时复制；继承的 fd 指向相同 open file description。`exec` 替换程序映像，保留未设置 close-on-exec 的 fd。父进程通过控制通道通知工作，子进程通过共享内存或自己的连接 fd 执行；退出后由 `waitpid` 回收状态。
精读 13.1“fork 系统调用”、13.3“处理僵尸进程”、13.5.2 至 13.5.4 的 System V 信号量、13.6.4“共享内存的 POSIX 方法”、13.6.5 的聊天实例、13.9“在进程间传递文件描述符”。消息队列 API 按需查阅，重点辨认消息优先/类型选择和返回长度。
孤儿不是僵尸：前者父进程已退出但自身可活着，后者已退出但状态尚未回收。`fork` 后信号处置是继承，不是全部重置；不要将 `exec` 的规则混入 `fork`。[fork 手册](https://man7.org/linux/man-pages/man2/fork.2.html)
### 引申与校正
- 共享消息：聊天样例按用户槽存数据，通知只传编号；“只有一个写者”仍无法阻止其他读者看到被下一条消息覆盖的内容。还需确认槽版本、确认/引用计数、容量或不可变消息；父进程压缩用户索引后也要检查子进程保存的编号是否一致。
- fd 传递：`SCM_RIGHTS` 传递内核引用，接收方获得自己的 fd 编号，不是转发一个整数就完成共享。清单 13-5 的辅助缓冲区不能只放 `cmsghdr` 而继续写一个 `int`，需正确容量、对齐，并验证 `MSG_CTRUNC`、level 与 type。[UNIX socket 辅助数据](https://man7.org/linux/man-pages/man7/unix.7.html)
### 输出思考题
1. 共享内存只有一个写者，两个读者不同速。构造读到混合消息的时间线，再设计不依赖“读者应该足够快”的一致性协议。
2. 主进程将 socket 传给 worker 后自身是否立即关闭？设计明确的交接确认、worker 崩溃和发送辅助数据失败流程，证明不会丢连接或重复处理。
3. 多进程共享同一文件偏移时出现错误日志顺序，解释地址空间隔离为何没有帮助；给出独立打开、追加写与专用日志进程的取舍。
4. 子进程快速退出、父进程繁忙且信号合并时，设计可回收并恢复池容量的状态机，避免把 PID 固定范围数组当作永久成立的限制。
## 多线程编程
对应第 14 章。线程共享状态，核心不是 API 数量而是同一不变量由谁保护、阻塞与唤醒是否围绕同一谓词、何时允许销毁资源。
### 核心机制与重点
条件变量链：持有保护业务状态的 mutex → 循环检查谓词 → `pthread_cond_wait` 原子释放并等待 → 被唤醒后重新获得同一 mutex → 再检查谓词。通知不是消息存储；先通知后等待也不应依赖唤醒“记得发生过”。POSIX 线程函数通常直接返回错误码，不能统一从 `errno` 取失败原因。
精读 14.2“创建线程和结束线程”、14.5.3“死锁举例”、14.6“POSIX 条件变量”、14.7“线程同步机制包装类”、14.8.1“可重入函数”、14.8.2“线程和进程”、14.8.3“线程和信号”。属性列表按需查阅；线程模型用来理解运行实体和调度，不要求记住历史库年代。
14.7 的条件变量封装内部自带 mutex，却未让调用者围绕业务谓词使用同一把锁，接口难以保证检查与等待之间没有丢唤醒窗口。资源包装还应禁用复制，避免重复销毁 mutex/semaphore。
### 引申与校正
- 内存模型：停止位和业务状态都需有 happens-before；`volatile` 不替代 mutex 或原子同步。条件变量的虚假唤醒要求循环检查谓词，唤醒多个线程还要检查工作是否已被别人领取。[POSIX 条件变量规范](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3p.html)
- 进程交叉：多线程 `fork` 后只保留调用线程，其他线程持有的锁可能永久不可用。`pthread_atfork` 仅能协调已知锁，不能自动恢复任意库内部锁；子进程通常尽快走符合安全要求的 `exec` 路径。
### 输出思考题
1. 用两线程时间线证明“检查队列为空后释放锁，再 wait”会丢唤醒；重设计包装接口，要求从类型和参数看得出同一谓词 mutex。
2. 设计任务取消、正常完成和线程池析构同时发生时的返回语义；哪些状态可以原子变量表达，哪些必须组合在同一锁保护下？
3. 两个线程分别持有锁 A/B 后请求另一把锁，给出可以静态规定的全局锁序；加入回调调用外部代码后，原先锁序为何仍可能不够？
4. 比较 `join`、`detach` 与外部共享状态三种回收方案，说明哪种情况下线程本身回收了但仍存在对象悬空访问。
## 进程池和线程池
对应第 15 章。这是全书最值得做审查式精读的一章：把池、事件循环、HTTP FSM 和发送缓存组合起来后，局部正确无法保证整体生命周期与协议正确。
### 核心机制与重点
进程池路径：父进程监听 → 轮询通知一个子进程 → 子进程从继承监听 fd 接受连接 → 子进程自己的 `epoll` 分派。此路径不是父进程接受后通过 `SCM_RIGHTS` 传 fd。线程池路径：主线程读取 → `append` 入队 → semaphore 唤醒 → worker 取 `T*` → `process` → 调整事件。
HTTP 链：主循环读入 `http_conn` → worker 执行 `process_read` 增量 FSM → `do_request` 检查并映射文件 → `process_write` 创建响应头和 `iovec` → 主循环 `write` → 发送完成后关闭或复用。沿 `http_conn.h`、`http_conn.cpp` 和主函数追 `m_read_idx`、`m_checked_idx`、`m_iv`、`m_file_address`，不用只看类接口。
精读 15.2“处理多客户”、15.3“半同步/半异步进程池实现”、15.5“半同步/半反应堆线程池实现”和 15.6 的两小节。15.4 CGI 用来理解 `fork`/`exec` 与输出重定向；按客户端提供路径执行程序只能当隔离实验，不能作为面向网络的生产 CGI 方案。
### 失败模式与修复目标

| 本地代码位置 | 失败机制 | 修改时必须证明的条件 |
| --- | --- | --- |
| `threadpool` 析构与 `run` | detached worker 仍访问 `this`；普通 `m_stop` 读写无同步，等待者未唤醒 | 停止状态同步、唤醒所有 worker、等待结束后销毁队列和同步对象 |
| `append` 与主循环调用 | 容量检查用 `>` 放入越界的一项；调用者忽略拒绝返回 | 上限严格；拒绝后连接不永久停在禁用 ONESHOT 的状态 |
| `http_conn::write` | 只按响应头计待发字节、不推进 `iovec`、跨 `EAGAIN` 进度重置 | 总长含文件；游标跨调用持久保存；成功条件为剩余字节零 |
| `do_request` 与映射 | 文件打开/映射失败及初始化需检查；路径与长度缺少完整边界 | `MAP_FAILED`、零长度、目录穿越、长度溢出与资源释放逐条处理 |
| 连接数组与 close | 按 fd 下标并不保证小于数组上限；旧 worker 可触及关闭后复用项 | 身份校验、稳定所有权；关闭与处理有明确协调 |
| ET 监听处理 | 每次通知只接受一次 | 非阻塞 accept drain 或保留未完成接受任务 |
这些判断不依赖全角符号是否可编译，直接来自控制流和状态维护。重写时先定义停止、拒绝、发送完成、关闭四个不变量，再引入 RAII。构造中创建一部分线程后失败，也要停止并回收已启动线程，不能只释放线程 ID 数组。
### 引申与校正
- 有状态请求：正文说迁移线程后请求必须无状态，约束过强；若状态属于稳定连接对象，且每次访问已串行和同步，不同 worker 可以处理同一有状态会话。问题是线程局部状态、对象身份和访问协议。
- 流量治理：有界队列需要拒绝、读兴趣暂停或限速策略；池不是把无限任务藏起来的容器。HTTP 长度与剩余数据必须依消息边界处理，不能因为读到了某一包就结束请求。[HTTP/1.1 消息框定](https://www.rfc-editor.org/rfc/rfc9112.html)
### 输出思考题
1. 重设计线程池停止契约，区分 graceful drain 与立即取消；对排队任务、执行中任务和后续 `append` 分别规定结果，并证明析构不会访问已释放内存。
2. 创建短写与 `EAGAIN` 可重复触发的最小测试，验证响应头加大文件的字节完整性；写出导致原 `write` 实现重复发送或提前完成的返回值序列。
3. worker 正在解析时主线程收到半关闭并关闭连接，随后 fd 复用。至少提出两种所有权设计，比较内存、同步开销和取消及时性。
4. 请求队列满但连接还有输入数据，设计“暂停读”“明确拒绝”“关闭”三种策略，说明各自如何影响已有请求与公平性；选择一种并给出可测指标。
5. 对 HTTP 解析器构造负长度、超大长度、两请求粘连、CRLF 拆分与路径穿越输入，定义应返回的协议结果及资源上限，不能只要求“不崩溃”。
## 服务器调制、调试和测试
对应第 16 章。调制是根据测量修改约束，测试必须回答业务目标是否达成。放大内核上限不会修复数组越界、处理速度不足或无限排队。
### 核心机制与重点
链路：定义工作负载与 SLO（Service Level Objective，服务等级目标） → 固定环境与基线 → 产生负载 → 同时采集客户端结果和服务器资源 → 提出瓶颈假设 → 一次改变一个变量 → 复验并记录副作用。吞吐、延迟分布、错误率和内存必须一同观察。
精读 16.1“最大文件描述符数”、16.2.1“与文件相关的内核参数”、16.2.2“与网络相关的内核参数”、16.3.1“用 GDB 调试多进程程序”、16.3.2“用 GDB 调试多线程程序”、16.4“压力测试”。旧数值、旧参数名与固定比例只作历史背景，不复制到当前系统。
`RLIMIT_NOFILE`、系统文件表与 `epoll` watch 配额是不同资源；提升 fd 上限后还要检查 `users[fd]` 的界限。`somaxconn` 限制完成连接队列，`tcp_max_syn_backlog` 管半连接记录，不能互换解释。[内核 TCP 参数](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html)
### 引申与校正
- 负载模型：清单 16-4 建连接时 `sleep(1)`，读取一次就把响应当完成，遇 `EAGAIN` 的策略也需复核；适合展示事件客户端，不足以证明服务器高性能。必须解析完整响应并统计失败，不仅记录成功返回。

| 模型 | 到达方式 | 优势 | 必须解释的盲区 |
| --- | --- | --- | --- |
| 闭环 | 收到响应再发下一请求 | 模拟固定并发客户端，实施简单 | 服务变慢后自动少发请求，可能掩盖排队压力 |
| 开环 | 按计划独立产生请求 | 观察过载、排队与到达率约束 | 客户端也可能达不到目标速率，需要记录实际到达 |
- 排错顺序：GDB 观察会暂停线程并改变调度，不能单靠断点证明没有竞态。吞吐提升后仍需复查 p99、资源峰值与失败率，避免把积压转移到其他队列后误判成功。
### 输出思考题
1. 设计固定并发与固定到达率的两组测试，注入 1% 慢请求；预测为何同一服务器可能在两个测试中显示不同尾延迟与错误率。
2. 提高 fd 上限后程序更容易崩溃，沿内核限制、连接数组、内存与队列四层给出假设及证据，说明为什么回滚参数不能代替修复。
3. 如何证明压力来自服务器而不是负载客户端、网络或文件缓存？给出基线、预热、机器分离和饱和点确认方案。
4. 多线程偶现 use-after-free，制定无需“恰好断在错误点”的取证方案；明确对象身份日志、检测器与最小时间线分别提供哪种证据。
## 系统监测工具
对应第 17 章。工具分别观察包、fd、系统调用、内存、网络与 CPU，任何单一视图都不是完整因果解释。
### 核心机制与重点
证据链：客户端慢请求的标识和时段 → socket 地址/连接身份 → `tcpdump` 的传输变化 → `strace` 的系统调用及等待 → `lsof` 的 fd 与映射 → `vmstat`、`ifstat`、`mpstat` 的同时间资源变化 → 验证程序内队列与生命周期假设。连接日志最好包含稳定对象 ID 或 generation，不仅 fd 数值。
精读 17.1“tcpdump”、17.2“lsof”、17.4“strace”、17.6“vmstat”、17.7“ifstat”、17.8“mpstat”。17.3 的 `nc` 用于最小协议探测，具体参数随实现变化；17.5 的旧 `netstat` 示例映射到现代 `ss` 使用，不假设列名与选项完全相同。
不能由一次 `futex` 调用直接认定发生互斥锁争用：无竞争锁常在用户态完成，书中栈附近也可能对应 semaphore 唤醒。系统调用时间、运行等待和应用处理时间需要分开统计。`strace` 本身改变执行成本，附加前后应确认现象仍在。
### 引申与校正
- CPU 解释：整体利用率低仍可能有单核或单线程满载，按核与线程关联观察。`%steal` 是虚拟化中被宿主拿走的时间，不能只按物理核配对解释；`%nice` 不能简单说成“负 nice 值进程”的占比。
- 内存与网络：空闲内存少不等于泄漏，页缓存与可回收内存需单独解释；网络平均速率低不排除短时突发与队列拥塞。抓包统计与程序传输量差异还可能由 offload、重传、采样位置与应用压缩产生。
### 输出思考题
1. CPU 总利用率 20%、某连接 p99 升高、网卡平均利用率低，构造三个不同根因，并规定下一步最小观测，避免一次收集所有工具输出。
2. fd 数不断上涨、RSS 也上涨，但吞吐稳定。设计区分连接积压、映射文件保留、真正泄漏与缓存增长的证据链。
3. 一个 `futex` 等待很长的线程是否一定是锁瓶颈？分别构造正常空闲 worker、条件变量漏唤醒、真实锁竞争的日志与系统调用差异。
4. 抓包看见大量重传但应用无错误，解释为何仍可能影响 SLO；定义能连接传输层恢复与业务长尾的时间对齐方案。
