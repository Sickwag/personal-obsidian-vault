## 全书解决的问题
作者观点：高性能来自能够解释的工作负载、合理的数据访问路径和完整的运维闭环，而不是一组通用参数。第 2、3 章提供测量方法，第 4—7 章减少不必要的数据工作，第 8、9 章匹配资源，第 10—15 章处理规模、故障和应用层代价，第 16 章与附录提供观察手段。
值得保留的知识链：业务目标 → 响应时间分布 → 请求中的服务时间与等待时间 → 查询模式 → Schema 与索引 → 执行计划 → 内存及 I/O → 复制一致性 → 故障切换与恢复验证。只有这条链路解释通，参数调整才有意义。

### 有价值的观点与实现

| 观点或机制 | 书中位置 | 为什么值得读 | 可以怎样验证 |
|---|---|---|---|
| 性能定义为完成任务的响应时间 | 3.1—3.4 | 资源使用率只是解释变量，CPU 上升也可能意味着更有效利用资源 | 保持负载与错误率一致，比较延迟分布、吞吐量与 CPU |
| 剖析汇总会丢失细节 | 3.1、3.3、3.4 | 总耗时榜适合选候选项，不能解释时间相关的停顿 | 同时看指纹聚合和秒级时间序列 |
| 三星索引：聚集、顺序、覆盖 | 5.2—5.4 | 联合索引同时影响过滤、排序和回表，并非“选择性最高放第一” | 对多种谓词组合比较读取量、排序量与写开销 |
| 索引也是锁范围设计 | 5.3.11、附录 E | 同一业务谓词不同访问路径，可能具有不同并发行为 | 两会话复现范围更新与阻塞，记录实际锁对象 |
| 汇总表与条带化计数器 | 4.4 | 热点可从一个行锁拆到多个槽位；性能提升要求另行定义汇总语义 | 测不同槽数的吞吐量、准确性与读代价 |
| 复制节点也承担全部复制写入 | 10.5 | 读副本容量不能只按查询数除以节点数估算 | 把重放写入和业务读取一起纳入副本压测 |
| 有效容量受响应时间目标约束 | 11.1 | 最大吞吐量并非可交付容量，排队已经可能失控 | 定义延迟阈值，在加压曲线上寻找容量边界 |
| 冗余需要配合可执行的故障转移 | 12.3—12.5 | 节点存在不代表可以正确选主、隔离旧主和切换客户端 | 演练断网而非仅杀进程，检查双写与重试 |
| 备份有效性由恢复证明 | 15.2—15.6 | 复制会传播误删，备份成功也不代表恢复能满足时限 | 从隔离备份重建并校验业务不变量 |

## 多视角审视作者主张
以下是围绕原书命题的角色分析，不伪装为作者原话或真实专家采访。证据来自对应章节；外部实现变化参见上述核验地图。

| 核心命题 | 支持视角的最强理由 | 反向视角与隐含前提 | 暂定判断与可证伪条件 |
|---|---|---|---|
| 应优先从响应时间出发 | 性能工程师：用户等待直接反映工作与排队，3.1 避免“降低 CPU 就是优化”的误判 | 批处理维护者：月末任务还受截止时间、成本、能耗约束；单条查询变快却可能降低整体吞吐 | 把工作负载、延迟/期限、成本和正确性共同写成目标；同负载改善用户关键路径才成立 |
| 简单 Schema、短小类型通常更好 | 存储工程师：4.1、5.3 的页空间、缓存容量、主键传播解释了实在收益 | 业务建模者：值域增长和未知状态是语义约束；把未知改成 0 或缩窄到未来不足的类型会增加迁移与错误成本 | 先保持语义和值域，再优化表示；负载收益须超过迁移风险 |
| 查询拆分有时比复杂关联更好 | 架构师：6.3 的分解可以缓存、分布处理并减少重复数据传输 | 一致性审查者：多次往返、多个快照、连接池争用以及 N+1 查询会反转收益；书中局域网、简单查询条件不能普遍外推 | 同时比较完整请求延迟、读取一致性和请求数；不凭单个 SQL 快慢选方案 |
| 高性能系统经常由应用维护关联完整性 | 扩展维护者：7.3 指出额外查找、索引、锁和跨节点关联的成本 | ERP 数据负责人：删父插子竞态不能靠两次普通查询消除；跨多个写入口的应用约定很容易失守 | 同库事务边界内优先验证数据库约束；移到应用层必须给出竞态防护、校验和修复证据 |
| 反范式、缓存能显著减少读取工作 | 读服务工程师：4.4、14.3 将重复计算移到更新/后台，成本由请求路径移走 | 审计负责人：成本也转移到失效、重建、修复、权限与陈旧数据；高命中率不保证业务正确 | 为派生数据定义权威源、过期窗口、重建机制；压力下降而错误上升不能称优化成功 |
| 复制能扩展服务能力 | DBA：10.1、11.3 的副本分担读、备份和容灾工作 | 分布式系统审查者：复制不自动扩写、不保证读己之写，也不阻止双主冲突 | 用写入传播、读取路由、故障切换时序证明能力；追赶能力不足时加副本只增加表面容量 |
| 优化收益不足时应该停止 | 项目负责人：3.1 与 13.2 的机会成本高于无界追求性能 | 容量负责人：短期不值得的观测能力或容灾演练可能对罕见严重事故关键 | 对日常延迟优化和安全容量/恢复工程分别估值；不能用低频否定高损失风险 |
### 讨论时必须保留的分歧
事实分歧：瓶颈在哪里、缓存究竟减少多少数据库工作、是否存在复制追赶余量，可以测量解决。价值分歧：是否容忍 2 秒旧数据、是否允许丢失一笔订单、节省多少钱才值得增加维护复杂性，需要业务明确。优化讨论应先写允许的语义，再争论工程方案。
### Arena：外键与应用完整性
本轮由书籍研究 agent 与独立的业务一致性 agent 交换论证；以下为协作分析，不是另一个书评来源，也没有实测数值。
- 原书最强版本：`7.3` 指出外键产生额外查找、索引和锁，也承认在确保关联完整性时可能比应用检查更高效。该节末尾更偏向在应用维护纯约束，但明确没有给出相应基准数据，依赖咨询案例；因此不能把它扩展成“取消外键普遍更优”。
- 书籍研究 agent 的支持：跨分片关联无法直接由单实例外键保护，集中控制写入口的应用协议可能更适配扩展；如果确实测到外键查找/锁等待占关键路径，应比较替代协议的完整成本。
- 业务一致性 agent 的反驳：事务 A 检查父记录存在 → B 删除父记录并提交 → A 插入子记录并提交，已经证明两次普通查询不闭合“不存在孤儿”的不变量。仅把操作放进事务也不自动提供足够隔离；导入脚本、后台任务和重试还可能绕过统一入口。
- 书籍研究 agent 的修正：外键不能保证库存非负或订单金额合计等全部业务规则，应用校验也不能替代所有关系约束；两者可互补。只有明确锁/隔离、原子边界和所有写入口后，应用替代方案才具有可比较性。
- 判别实验：分别测试数据库外键、普通应用检查、严格锁/写入协议；并发删父插子，注入客户端重试和旁路 SQL。报告残留孤儿数量、成功吞吐、P99、死锁、维护清理与修复成本，不只测单次插入延迟。
- 条件化结论：单库 ERP 优先保留能表达的数据完整性；跨分片场景需要显式一致性协议、补偿和审计，不以“更快”预设取消约束。未经测量不能把咨询案例上升为通用定律。
## MySQL 架构与历史
原书第 1 章，`part0008.xhtml`；优先级：必读。核心问题是 SQL 服务层、存储引擎和事务并发分别负责什么。
### 核心思想与机制
- `1.1` 将连接认证、查询处理和存储引擎分层。调用链为客户端请求 → 认证/权限 → 解析与优化 → 存储引擎 API → 数据及索引访问 → 结果返回。引擎提供访问与成本信息，SQL 解析并不由 InnoDB 完成。
- `1.2` 的锁粒度取舍不是越细越好：粒度细通常减少互斥范围，却增加管理成本；要区分服务层锁和引擎锁，不能用一个“行锁”覆盖所有等待。
- `1.3` 的 Atomicity、Consistency、Isolation、Durability（ACID）解释事务边界；业务不变量仍需要正确 SQL、约束与隔离，不能仅用 `BEGIN` 包住多句查询便声称库存永不负数。
- `1.3.2` 把死锁视为并发系统需要处理的正常失败路径。回滚、重试和幂等属于应用协议，不应把重试藏成无上限循环。
- `1.3.3` 事务日志把提交持久化与脏页最终写回分开；`1.4` 的多版本并发控制（Multi-Version Concurrency Control，MVCC）减少读写互阻，但没有消除写写冲突或版本维护。
### 着重阅读
精读 `1.1.2 优化与执行`、`1.3.1 隔离级别`、`1.3.2 死锁`、`1.3.3 事务日志`、`1.3.4 MySQL 中的事务`、`1.4 多版本并发控制`、`1.5.1 InnoDB 存储引擎`。为每种读写动作标明它需要版本可见性、数据锁还是日志持久化。
`1.5.2 MyISAM` 用于理解不同引擎的边界；其他历史引擎及 `1.6—1.7` 可跳读，不将某个旧引擎的行数统计、锁行为套到 InnoDB。
### 外部引申与质疑
- 分支一：把书中 MVCC 简化图替换为事务 ID、undo、Read View 的可见性链。RR 和 RC 的快照时机不同，事务开始不等于所有场景已经固定快照。[一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)
- 分支二：连接到 C++ 服务的事务对象生命周期。线程/协程挂起时连接和事务仍占有资源；RAII 自动回滚能处理作用域失败，无法自动证明业务操作可安全重试。
### 思考题与输出
1. 两个请求分别先读取库存、再扣减库存，都放在事务中，为什么仍需讨论读取方式？提交两会话交错表、一个失败反例和两套修复方案，比较锁范围与吞吐代价。
2. 把“读不阻塞写”改写成有边界的命题。提交 RC/RR、普通读/加锁读四格表，并用长事务推导 undo 保留及空间压力。
3. 客户端发出提交后断网，没有收到结果，能否直接重试扣款？提交客户端—服务器时序图，区分未提交、已提交未确认两种执行历史，并给出可区分的业务标识方案。
## MySQL 基准测试
原书第 2 章，`part0009.xhtml`；优先级：必读。解决“如何判断改变有效，以及容量结论能否外推”的问题。
### 核心思想与机制
- `2.1—2.2` 区分集成式与单组件测试。测数据库隔离变量较容易，测完整系统才暴露连接池、网络、缓存和业务处理之间的反馈。
- `2.2.1` 同时测吞吐、响应时间、并发与扩展能力。吞吐翻倍不能推出业务容量翻倍，因为数据规模、热点和交互也可能改变。
- `2.3` 要求数据量、分布、用户行为、预热和运行时长匹配问题。测试从加载数据 → 预热 → 施加负载 → 收集数据库/OS 状态 → 多轮复测 → 对照分析，不能只取最好一次结果。
- 书中 `dbt2` 曲线案例显示周期性脏页刷新导致吞吐低谷；平均值甚至较高分位可能仍掩盖时间集中发生的停顿。图形的价值是揭示时间结构，不能用一张均值柱状图替代原始时间序列。

### 外部引申与质疑
- 分支一：延伸到开放到达模型和封闭并发模型。固定工作线程遇到系统停顿时会减少新请求，可能低估真实持续到达时的排队；需把请求计划到达时间与实际完成时间一并保存，这是本指南的测量设计引申。
- 分支二：连接到 IM 的长连接与 ERP 的突发批量写入。相同 QPS 的事务大小、热点键和读写比例可能完全不同；基准测试应由业务操作定义，而不只由 SQL 次数定义。

2. 方案 A 平均延迟更低但每分钟停顿一次，方案 B 平稳但均值更高，如何选择？提交用户体验目标、时间序列、分位指标及允许错误率，不得仅以均值判断。
3. 一次压测 TPS 增加 30%，错误也增加 20%，还能称为优化吗？提交成功业务吞吐的计算方式及结果校验计划，说明重复成功、超时成功如何计数。
## 服务器性能剖析
原书第 3 章，`part0010.xhtml`；优先级：必读。解决“资源指标很多，却无法说明用户为什么等”的问题。
### 核心思想与机制
- `3.1` 以响应时间定义性能，分解工作时间与等待时间。降低 CPU 不是独立目标；若更高 CPU 使用换来更短等待与更多有效工作，可能就是改善。
- `3.2` 从应用向下剖析，跟踪请求入口 → 外部依赖 → 连接获取 → SQL 往返 → 结果解析 → 响应，避免数据库成为所有慢请求的默认归因。
- `3.3.1` 将查询指纹汇总为次数、总耗时、平均值等，用于优先级排序；`3.3.2` 再钻入候选查询。低频高代价与高频低代价都可能值得优化，但总耗时榜不会自动发现最差用户群。
- `3.4` 诊断间歇性问题要在事件发生时捕获证据。持续轻量监测 → 阈值触发 → 收集进程、状态、OS 指标或栈 → 时间对齐 → 验证假说，比随机调参更可控。
- `strace` 与 CPU 采样观察对象不同；系统调用墙钟时间可以包含等待，CPU 采样不会按相同比例反映休眠线程。不能混合两类比例做耗时分摊。
### 着重阅读
精读 `3.1.1—3.1.2`、`3.3.1—3.3.3`、`3.4.1—3.4.3`、`3.5.2 使用 strace`。`3.2.1` 的 PHP 工具可以跳过具体安装，保留埋点开销、调用计数与完整请求追踪的思想。
旧版 `SHOW PROFILE` 留作历史对照，现代练习以 Performance Schema 和当前执行计划工具为主；不要把某一状态名机械解释成真实物理动作。
### 外部引申与质疑
- 分支一：Performance Schema 的 statements、stages、waits 是不同粒度；instrument 与 consumer 的配置会影响可见性。没有记录不等于没有执行或等待。[Performance Schema](https://dev.mysql.com/doc/refman/8.4/en/performance-schema.html)
- 分支二：把 Amdahl 的局部收益约束用于选优化项，但不要直接把数据库总耗时比例当成单个用户请求串行比例；并发任务的总耗时可能大于观察窗口。
### 思考题与输出
1. 数据库 CPU 只有 20%，接口 P99 却明显恶化，如何定位？提交四个可区分假说及对应证据，至少覆盖锁、连接池、外部依赖和 I/O。
2. “总耗时第一的 SQL 一定优先优化”有哪些反例？提交两个负载分布与用户群反例，给出预算、收益、风险三维排序。
3. 设计间歇性停顿的捕获方案。提交触发条件、采集项、时间戳精度、保存窗口与观测扰动评估，说明如何避免采集器自身制造停顿。
## Schema 与数据类型优化
原书第 4 章，`part0011.xhtml`；优先级：必读。Schema 同时决定业务表示和页、缓存、比较及迁移成本。
### 核心思想与机制
- `4.1` 的短小、简单类型减少存储与比较工作，但前提是完整表达真实值域。整型标识比长字符串常有成本优势，关联列类型不一致会增加转换与优化难度。
- `4.2` 警惕超宽表、EAV（Entity-Attribute-Value）造成的大量关联、随意的特殊值。作者不是要求拒绝 NULL：未知值真实存在时，魔法常数可能更危险。
- `4.3` 范式降低冗余与修改异常，反范式减少关联与重复读取；混合方案需明确哪张表是权威源，谁更新派生字段。
- `4.4` 汇总表将昂贵实时聚合转为后台计算；条带化计数器把同一行争用拆到多个随机槽，读取时汇总。写路径变短不等于全流程成本消失，维护与查询复杂度会增加。
- `4.5` 老版本 ALTER 常以复制表实现。理解重建、同步新增写入、切换和回滚四个阶段，比背“在线变更”名称更关键。
### 着重阅读
精读 `4.1.3 字符串类型`、`4.1.4 日期和时间类型`、`4.1.6 选择标识符`、`4.2`、`4.3.3 混用范式化和反范式化`、`4.4.2 计数器表`、`4.5` 的影子拷贝思想。
`4.5.1 只修改 .frm 文件` 仅作为实现历史阅读，不能作为现版实践步骤。价格、金额要保证精确语义，不能因浮点计算快便牺牲账务不变量。
### 外部引申与质疑
- 分支一：现代在线 DDL 区分 `INSTANT`、`INPLACE`、`COPY`，支持情况取决于操作与表条件；在线也不代表零元数据锁或无需额外空间。[在线 DDL 操作表](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)
- 分支二：ERP 的商品现价和订单成交价语义不同。成交价快照不是待同步的冗余缓存，不能机械套用“只保存一次事实”的口号。
### 思考题与输出
1. 给订单设计金额、时间、标识符与可选字段，如何同时控制空间与语义风险？提交字段决策表、值域依据、两个跨时区/未知状态反例。

## 创建高性能的索引
原书第 5 章，`part0012.xhtml`；优先级：最高。索引设计需要同时匹配过滤、排序、覆盖、写入与锁竞争。
[[/Chores/JobInterviews/面试题合集.md|已有索引与锁的面试问题，可与实验结果对照]]
### 核心思想与机制
- `5.1` 区分不同索引结构与能力；联合 B-Tree 的列顺序塑造可用前缀，不等于几个单列索引的简单相加。
- `5.2` 的三星评价要求相关记录集中、顺序满足查询、索引覆盖输出。三者未必可同时满足；要在实际数据分布和多类查询之间选择。
- `5.3.2—5.3.4` 选择性与列顺序不能脱离谓词。等值前缀、范围、排序、热点分布及列间相关性一起影响代价；“高基数列永远第一”只是未经条件限定的经验。
- `5.3.5` InnoDB 聚簇索引的叶子记录包含行数据，二级索引带有主键；主键宽度会传播到多个二级索引。二级定位 → 取得主键 → 聚簇查询是回表路径，覆盖索引可减少这条工作。
- 自增与随机 UUID 案例解释局部性、页分裂和主键宽度。该结果不能独立证明所有 UUID 设计都慢，需区分表示长度、生成顺序和多写节点需求。
- `5.3.11` 锁与访问路径关联；减少扫描不止节省读取，还可能缩小锁影响范围。InnoDB 的索引记录锁与表级锁不是简单的自动升级关系。
### 着重阅读
逐例精读 `5.3.2 前缀索引和索引选择性`、`5.3.3 多列索引`、`5.3.4 选择合适的索引列顺序`、`5.3.5 聚簇索引`、`5.3.6 覆盖索引`、`5.3.7 使用索引扫描来做排序`、`5.3.9—5.3.11` 和全部 `5.4`。
`5.4` 的约会网站案例要重建每个过滤组合为何改变索引选择，尤其区分连续范围与离散 IN 列表。`5.5.2` 理解统计估计；修复损坏表不能直接套用 MyISAM 的 `REPAIR TABLE` 到所有引擎。
### 外部引申与质疑
- 分支一：用当前 `EXPLAIN ANALYZE` 比较估计行数、实际行数和循环次数，检查优化器选错是否源于分布/相关性误判；它会执行语句，不作为零成本静态查看。[执行计划与实际执行](https://dev.mysql.com/doc/refman/8.4/en/explain.html)
- 分支二：C++ 内存局部性与 B+Tree 页局部性共享“减少昂贵访问”的动机，却不能把数据库页读取次数等同于物理 I/O 次数；缓冲池命中和预读必须纳入解释。
### 思考题与输出
1. IM 消息列表按会话、时间排序分页，允许状态过滤，怎样选联合索引？提交两套列顺序、四类查询、各自排序/回表/写放大分析，不得只写最左匹配。

4. 同一范围 UPDATE 添加索引后延迟改善，如何证明不是运气？提交访问计划、数据锁/等待变化及多次并发对照，说明隔离级别如何影响结论。
## 查询性能优化
原书第 6 章，`part0013.xhtml`；优先级：最高。查询优化的根本是“不做、少做、做得更快”，而不是语法替换清单。
### 核心思想与机制
- `6.1—6.2` 从请求、扫描和返回的行/列开始。结果只有 10 行不能证明只做了 10 行工作；扫描、过滤、排序和网络输出可能消耗大量时间。
- `6.3` 拆分大删除可以缩短锁持有、减轻复制尖峰；分解关联可能提升缓存复用，却增加往返与跨查询一致性责任。
- `6.4` 追踪协议 → 解析/预处理 → 成本优化 → 引擎访问 → 排序聚合 → 返回。代价模型依赖统计信息；估计最便宜的计划不等于实测总是最优。
- `6.5` 的关联子查询、UNION、hash join 等限制属于当时实现。保留“识别实际执行方式再重写”的方法，不把旧版结论变成永久 SQL 禁令。
- `6.7` 区分 `COUNT(*)` 与 `COUNT(col)`，关注 NULL 语义；深分页需要先扫描并舍弃前缀，延迟关联能减少宽行回表，游标分页则改变访问路径与产品语义。
- `6.8.1` 队列表通过领取、处理、完成三个状态协调消费者。锁竞争只是一个问题，还存在消费者崩溃、外部副作用和重试后的重复执行。
### 着重阅读
精读 `6.2.1—6.2.2`、`6.3.2 切分查询`、`6.3.3 分解关联查询`、`6.4.1`、`6.4.3—6.4.5`、`6.7.1`、`6.7.4—6.7.7`、`6.8.1`。对每次改写同时验证结果等价性、快照范围和完整请求延迟。
用户变量技巧、旧 hint 仅按需读；不要依赖未保证的表达式求值顺序。`Using filesort` 不自动意味着磁盘排序或错误方案，需比较实际代价。
### 外部引申与质疑
- 分支一：8.4 的 hash join 已使 `6.5.6` 历史限制失效；不同算法仍要比较输入规模、内存和条件，不推出 hash join 必优。[Hash Join](https://dev.mysql.com/doc/refman/8.4/en/hash-joins.html)
- 分支二：现版加锁读支持 `SKIP LOCKED`，可用于减少队列消费者等待，但返回的是跳过锁定行的非完整视图；它不保证端到端恰好一次。[加锁读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

## MySQL 高级特性
原书第 7 章，`part0014.xhtml`；优先级：分区、字符集、约束与 XA 精读，其余按需。高级特性主要改变工作位置和边界，功能存在不代表性能更好。
### 核心思想与机制
- `7.1` 分区把筛选先粗化到分区集合，再在分区内访问；是否分区裁剪取决于条件。分区并非全局索引，也不会让所有单行点查更快。
- `7.2` 视图简化接口，却可能被合并或物化；对视图的 WHERE 是否下推、是否生成临时表，要看实际计划。
- `7.3—7.5` 外键、触发器、存储程序将逻辑放到数据库内。它们能减少往返，也会带来隐含查找、锁和逐行处理；外键的完整性收益不能只按额外访问评价。
- `7.6` 绑定变量通过先准备后执行减少重复解析及传输成本，应区分服务器端预处理和客户端模拟；参数安全与性能也需分别证明。
- `7.7—7.8` 原生 UDF 与插件扩展能力强，但进入数据库进程意味着 C/C++ 内存错误可能破坏整个服务，不能把插件视为免费性能提升。
- `7.9` 字符集控制表示，collation 控制比较与排序；连接、列与表达式转换可能改变语义和索引使用。
- `7.11` 区分引擎与 binlog 协调的内部提交，以及跨参与者的外部 XA。协调者决定与参与者持久状态必须能在故障后恢复；准备成功并不等于事务已提交。
- `7.12` Query Cache 的表级失效与全局竞争案例保留为历史设计研究，现代 MySQL 不再配置这套功能。
### 着重阅读
精读 `7.1.1—7.1.5`、`7.3`、`7.6.1—7.6.3`、`7.9.1—7.9.3`、`7.11.1—7.11.2`、`7.12.3` 的成本分析。`7.4` 着重看触发器隐含工作；`7.5` 看打开游标与只消费少量结果是否造成浪费。
`7.10` 的 MyISAM 限制不直接代表 InnoDB 全文行为；`7.7` 旧 UDF 示例的接口类型、编译选项和 ABI 需要现版文档核验。

- 分支一：现版全文索引与 `utf8mb4` 是旧实例迁移的重要补课点；书中的字符集默认值和全文引擎选择不作为新项目模板。[InnoDB 全文索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-fulltext-index.html)

## 优化服务器设置
原书第 8 章，`part0015.xhtml`；优先级：必读。配置应该匹配已确认的负载、内存上限和数据安全要求。
### 核心思想与机制
- `8.1` 区分配置文件、命令行、全局/会话作用域与动态生效。参数在文件中出现不代表当前连接正在使用该值，变量修改还可能伴随重分配或等待。
- `8.2` 拒绝按固定命中率、通用公式或所谓最佳模板调参。缓存命中率由负载分布影响；98% 命中可能仍产生无法承担的绝对 I/O，低命中也可能只对应很少请求。
- `8.4` 先确定可用总内存，再扣除连接工作内存、OS 与其他进程，才分配共享缓存。每连接内存不是固定常数，排序、关联与临时表的触发条件和并发重叠很关键。
- `8.5` 的持久性链为事务修改 → redo/相关日志 → 提交确认 → 脏页后台写回。刷日志、刷数据和崩溃恢复作用不同，不把提高 TPS 的关闭同步设置当作等价优化。
- `8.6` 并发并非越高越好，过多执行线程可能引起锁争用和调度开销。限制并发需观测等待迁移，避免仅把数据库内部队列移到不可见的应用队列。
- `8.7—8.10` 负载、排序、大字段和安全配置决定具体设置；完整配置应尽量少、可解释，并保留默认行为与改动依据。
### 着重阅读
精读 `8.1.1 语法、作用域和动态性`、`8.1.2 设置变量的副作用`、`8.2`、全部 `8.4`、`8.5.1 InnoDB I/O 配置`、`8.6.1`、`8.9 安全和稳定的设置`。旧 `8.10` 的 InnoDB Plugin 切换历史不作为现代部署步骤。
每个参数记录“解决的假说—生效范围—观测指标—回退值”；专用数据库机器和数据库/应用混部机器不能共用一个内存比例模板。
### 外部引申与质疑
- 分支一：8.4 通过 `innodb_redo_log_capacity` 管理 redo 总容量；容量、刷盘频率与可容忍丢失窗口是不同决策，不能混成“大日志更安全”。[redo 配置](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)
- 分支二：现版内部临时表路径与旧 MyISAM 模型不同，特别关注单表限制和全局 TempTable 资源限制；临时表磁盘计数也可能无法完整反映 mmap 溢出。[内部临时表](https://dev.mysql.com/doc/refman/8.4/en/internal-temporary-tables.html)
### 思考题与输出
1. 为 32 GB 的数据库/应用混部主机设计内存预算，为什么最大连接数乘固定缓冲区公式不够？提交常态/突发两份预算与按需分配假设。
2. 降低日志同步要求使 TPS 翻倍，应如何报告这次变化？提交进程崩溃、OS 崩溃、掉电三种失败假设和业务允许窗口，区分语义变化与同语义优化。
3. 提高并发参数后 QPS 增长而 P99 恶化，怎样定位队列？提交应用连接池等待、数据库锁/执行等待与 CPU 调度对照，设计准入控制试验。
## 操作系统和硬件优化
原书第 9 章，`part0016.xhtml`；优先级：机制精读、历史硬件选型跳读。解决硬件资源怎样形成瓶颈，以及表面 I/O 问题是否源于工作集不合适。
### 核心思想与机制
- `9.1—9.3` 从限制因素向根因追踪。内存不足会让热页频繁被逐出再读回，表面磁盘繁忙却不一定应该先买更快的盘。
- `9.2` 比较频率与核心数时区分单次执行路径和并发工作；增加核数无法直接缩短所有单条查询，甚至可能暴露共享锁争用。
- `9.3.3` 工作集用被反复访问的缓存单元表示，而不是表的总字节数；访问一行可能加载一个页，随机散落的小对象可对应很大的热页集合。
- `9.4—9.7` SSD、RAID、SAN/NAS 的吞吐、延迟、持久化与故障行为不同。存储控制器缓存可隐藏写延迟，但是否在断电后保持承诺需要明确硬件保护与刷新语义。
- `9.9—9.15` 网络、文件系统、I/O 调度、线程和交换空间一起影响等待；`vmstat`、`iostat` 用于关联 CPU、阻塞、设备队列与分页，不能拿单个利用率解释全部故障。
### 着重阅读
精读 `9.1`、`9.2.1`、`9.3.1—9.3.4`、`9.4.3 闪存的基准测试`、`9.5 为备库选择硬件`、`9.6.3 RAID 配置和缓存`、`9.9 网络配置`、`9.14 内存交换区`、全部 `9.15`。
Flashcache、当年的 PCIe 产品、旧内核调度器和设备建议只作历史参考；真实采购或部署前另查当前内核、文件系统与设备资料。本章网络传播速度的一处数值表述不适合直接摘记，应另以可靠物理事实核验后计算 RTT。
### 外部引申与质疑
- 分支一：连接 C++ 程序的缓存局部性、NUMA 与线程迁移；共享数据跨 socket 访问可能使更多核心收益下降。这是机制引申，必须在当前硬件用亲和性对照实验验证。
- 分支二：副本硬件不能仅按平时读取量配置。故障后要承担主库的写、原读负载和缓存预热，必须把“降级状态可服务容量”写进预算。

1. 数据库磁盘等待高，怎样区分工作集失配与设备能力不足？提交缓冲池大小阶梯、热页分布、读 I/O 与延迟的判别实验。

## 复制
原书第 10 章，`part0017.xhtml`；优先级：必读。复制增加读取与容灾选项，同时增加日志传播、重放、延迟和切换责任。
### 核心思想与机制
- `10.1` 的链路为主库修改与 binlog → 日志发送 → 副本接收并写 relay log → 应用事务 → 副本可见。收到日志、日志持久化和业务查询可见是三个不同状态。
- `10.2` 初始化不能只“复制文件后启动”；一致数据快照与相匹配的复制起点必须配对，否则有漏放或重放问题。
- `10.3` 基于语句复制依赖环境与执行的确定性，基于行复制记录实际数据变化，减少某些不确定性但可能增加日志量。过滤规则还可能让数据依赖断裂。
- `10.4` 一主多备、主主和级联改变路由与故障域；双主拓扑不自动解决业务冲突，自增 ID 避撞也不解决同一实体状态竞争。
- `10.5` 所有副本都要执行复制写入。20% 写、80% 读的原负载翻倍时，要先从每个副本总容量中扣去翻倍后的写重放，再安排读。
- `10.6—10.7` 日常工作包括延迟、数据一致性、重建和安全改主；跳过一个错误事务不是完整性证明。延迟积压后必须有净追赶能力，否则永远无法恢复到及时状态。

精读 `10.1.2 复制如何工作`、`10.2.4 从另一个服务器开始复制`、`10.3.1—10.3.3`、`10.3.6`、全部 `10.5`、`10.6.2—10.6.6`、`10.7.1`、`10.7.13—10.7.18`、`10.9`。
旧命令和文件仓库实现按实际服务器核验，保留时序与容量思想；单线程重放不再是现代复制的普遍假设。
### 外部引申与质疑
- 分支一：GTID 标记已执行事务集合并支持定位，解决部分位点管理，但不是冲突解决机制，也不自动意味着零数据丢失。并行重放的提交顺序需结合相应配置理解。[GTID 生命周期](https://dev.mysql.com/doc/refman/8.4/en/replication-gtids-lifecycle.html)
- 分支二：半同步副本确认发生在事务事件进入 relay log 并刷盘后，不意味着副本已应用、立即可查询；超时还可能退回异步。[半同步复制](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)

1. 用户发出消息后立即从副本查历史却找不到，应该怎样处理？提交读己之写协议、等待条件、超时路由和依赖主库的代价。

## 可扩展的 MySQL
原书第 11 章，`part0018.xhtml`；优先级：必读。扩展性要求增加资源后，仍能以可接受成本完成更多有效工作。
### 核心思想与机制
- `11.1` 区分性能、容量和可扩展性；容量需要受延迟目标约束。Universal Scalability Law（USL，通用可扩展性定律）用串行争用和交互一致性开销解释收益递减或倒退。
- `11.2` 的向上、向外、多实例与向内扩展解决不同限制；归档减少工作量，分片分散数据与写入，读副本只转移符合一致性要求的读取。
- 分片链路为业务键 → 分片映射 → 节点路由 → 本地事务 → 必要时跨分片聚合；热点、动态迁移、全局约束与分布式事务是随之出现的责任。
- `11.3` 负载均衡的粒度可能是连接而非语句。长连接、长事务和会话状态使均匀分连接不等于均匀分工作，平均 QPS 也不代表各节点都健康。

精读 `11.1.1 正式的可扩展性定义`、`11.2.1 规划可扩展性`、`11.2.2 为扩展赢得时间`、`11.2.4 向外扩展`、`11.2.7 向内扩展`、`11.3.1—11.3.3`。

- 分支一：连接到 IM 会话分片与 ERP 租户分片，分片键应该同时服务访问局部性、事务边界和热点控制；按用户数平均未必按工作量平均。

## 高可用性
原书第 12 章，`part0019.xhtml`；优先级：必读。高可用性必须由用户能否正确完成操作定义，而不只由进程存活定义。
### 核心思想与机制
- `12.1` 可用性目标是成本与业务损失的取舍；启动成功但缓存冷导致大面积超时，也可能处于不可用状态。
- `12.2` 作者的宕机分类来自其客户历史案例，展示运行环境、性能、复制等方面的重要性；不能据此推断当今所有系统的普遍事故比例。
- `12.3` 从提高 Mean Time Between Failures（MTBF，平均失效间隔）与降低 Mean Time To Recovery（MTTR，平均恢复时间）两个方向改善；磁盘空间、变更错误和告警失效往往比复杂选主更先需要治理。
- `12.4—12.5` 故障链为发现问题 → 确认并隔离旧节点 → 选择具备数据资格的候选 → 提升 → 改路由 → 重连/重试 → 检查数据与恢复旧节点。缺少任何阶段都可能把故障转移变为故障扩大。
- 同一电源、交换机、可用区、运维账号或错误发布形成共同故障域；多节点不能只按独立失效概率计算可用性。

## 应用层优化
原书第 14 章，`part0021.xhtml`；优先级：必读。优化边界回到完整请求，数据库最快的工作常常是无需再次发给它的工作。
### 核心思想与机制
- `14.1` 的常见问题包括获取后丢弃大量数据、无意义的初始化查询和不理解框架后台操作。连接池既能降低连接成本，也能限制或扩大压力。
- `14.2.1` 寻找最优并发度；数据库之外的等待不能无限累积在 Web/应用进程中，否则连接、内存和调度会相互放大。
- `14.3` 缓存层越接近消费者，可能节省越多下游工作，但缓存粒度、过期和更新协议决定正确性。读路径为缓存查询 → 未命中 → 请求权威源 → 生成对象 → 缓存 → 返回；失败恢复必须覆盖每个步骤。
- 缓存不是只有被动取回，还可主动更新、预生成和分层。把内容缓存成一个大对象减少访问次数，却可能增加更新、失效和权限分隔复杂度。
- `14.4—14.5` 数据库扩展与替代品应按负载选择；旧 HandlerSocket、memcached 接口例子用于理解绕过 SQL 层的收益与丢失的能力，不直接当新项目默认组件。
### 着重阅读
精读 `14.1`、`14.2.1 寻找最优并发度`、`14.3.2 应用层缓存`、`14.3.3 缓存控制策略`、`14.3.4 缓存对象分层`、`14.3.5 预生成内容`。Apache/PHP 专属配置可以跳读具体指令，保留慢客户端与应用工作进程隔离思想。
### 外部引申与质疑
- 分支一：连接到 C++ 协程服务。能挂起大量请求并不代表应该同时发出同量 SQL；连接池等待、超时传播和背压要保持可观测，取消请求也不应遗留事务。
- 分支二：缓存失效与重建协议考虑并发回填、热点过期与重建失败；单次删除缓存不等于数据库/缓存最终必一致，需定义版本或可修复窗口。
### 思考题与输出
1. 协程数量扩到十万后数据库连接池该有多大？提交服务能力测量、等待队列上限、超时预算与拒绝策略，不以协程数推导连接数。
2. 先删缓存再写 DB、先写 DB 再删缓存分别有哪些反例？提交两读一写时序图、可接受旧值窗口及版本化/补偿方案。
3. 缓存命中率 99% 仍发生数据库雪崩，如何解释？提交过期聚集、流量绝对量、重建放大三个假说及区分它们的时间序列。
## 备份与恢复
原书第 15 章，`part0022.xhtml`；优先级：最高，运维实践前读。备份的目标是恢复符合业务要求的状态，而不是产生一个文件。
### 核心思想与机制
- `15.2` 先写 Recovery Point Objective（RPO，恢复点目标）与 Recovery Time Objective（RTO，恢复时间目标），再选择技术。备份时长短不代表导入、重建索引和恢复服务短。
- `15.3` 比较在线/离线、逻辑/物理。逻辑备份便于检查和迁移，恢复可能受重建成本限制；物理备份保留物理布局，需要确认一致性、版本和工具兼容。
- `15.4—15.6` 时间点恢复链为一致基础备份 → 与其匹配的日志起点 → 连续完整的 binlog → 恢复到指定边界 → 校验。日志有缺口时不能靠更近的一份不一致备份弥补。
- 副本、RAID 和快照不等价于独立备份。误删或错误写入会复制；共享设备和同一管理权限也会形成共同失败条件。
- `15.7—15.8` 工具和脚本承担备份锁、一致性坐标、出错清理和输出校验；“进程退出 0”只是必要条件之一。应演练整个恢复流程，而不只演练下载备份文件。
### 着重阅读
精读 `15.2`、`15.3.2—15.3.4`、全部 `15.4`、`15.5.1—15.5.2`、`15.6.1—15.6.5`、`15.7.2 Percona XtraBackup`、`15.7.6 mysqldump`、`15.8` 的错误处理。
具体工具版本、热备权限和服务器兼容矩阵另核验，不照抄 2012 年的工具参数。在线备份的长快照可能增加 undo 保留压力，需和备份窗口一同评估。
### 外部引申与质疑
- 分支一：官方时间点恢复使用基础备份加后续 binlog；日志和备份保留窗口需互相覆盖。[时间点恢复](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery.html)
- 分支二：ERP 恢复验收包括余额、库存、订单关联等业务不变量；IM 包括消息标识去重与会话顺序。数据库能打开只是物理恢复完成，不等于业务一致性完成。
### 思考题与输出
1. RPO 为 5 分钟、RTO 为 30 分钟，怎样推导备份和日志方案？提交时间线、容量估算、恢复操作阶段及演练验收条件。
2. 误删发生后一小时所有副本都同步了，如何恢复正确数据且保留之后合法写入？提交时间点恢复隔离方案、数据辨别与合并策略，说明仅停止复制为何太晚。
3. 物理快照为何不一定是可恢复的事务备份？提交文件一致性、日志配对和恢复测试要求，列举恢复失败或恢复后不完整的条件。
4. 备份脚本如何应对磁盘满、网络中断和锁未释放？提交失败状态表、清理与报警动作，设计能验证错误不会被管道吞掉的测试。
## MySQL 用户工具
原书第 16 章，`part0023.xhtml`；优先级：方法精读、工具目录查阅。工具价值来自观测和变更能力，不能用名字代替能力判断。
### 核心思想与机制
- `16.1` 接口工具帮助执行与管理；`16.2` 的工具包覆盖日志分析、校验、同步和归档；`16.3` SQL 实用集把管理逻辑放进数据库，使用时同样需检查额外工作。
- `16.4` 区分健康告警与历史指标采集：前者发现现在不可用，后者解释趋势与容量；只有当前状态的监控很难定位之前的间歇问题。
- 工具调用链为采集器 → 目标服务器 → 样本/日志 → 聚合与可视化 → 告警 → 操作；权限、采样损失、工具自身开销和故障隔离都可能改变结论。
- `16.5` 建议先收集服务器摘要再深入问题。日志分析、数据校验与修复属于不同风险级别，不应把运行诊断工具的授权扩大成自动修改数据。
### 着重阅读
精读 `16.2 命令行工具集`、`16.4 监测工具`、`16.4.3 Innotop 的命令行监控` 与 `16.5` 的初始观察流程。旧版本工具清单可跳读介绍，按真实任务选择少量工具。
Performance Schema 已提供丰富原生信息；本书中的监控产品、Google Code 链接和老包安装路径不保证仍有效，不以书龄推断所有工具都已废弃。
### 外部引申与质疑
- 分支一：以“要回答的问题”组织监控：延迟来源、热点查询、锁阻塞、复制积压、空间、恢复准备，分别定义必要信号，避免采集更多却无判断标准。
- 分支二：监控本身需要独立检查；采集停止、告警无人响应和全节点共享采集器故障是不同失败，业务探针应验证完整链路。

1. 如果只能保留十个监控项，怎样支持慢请求、复制和空间故障定位？提交选择理由、告警阈值依据与仍然无法回答的问题。

### MySQL 分支与变种
附录 A，`part0024.xhtml`。作者比较 Percona Server、MariaDB 和 Drizzle，核心是兼容性、特性、维护支持与控制权。作者参与维护的产品是重要经验来源，也要求读者区分技术能力与供应商立场。
重点看每个分支与官方版本的兼容假设、选择理由和支持关系。2012 年的“替换兼容”不能自动用于现代 MariaDB 与 MySQL，不在本指南做未经当前版本矩阵核验的迁移推荐。
引申：把供应商选择写成可迁移性与修复控制权评估，不只比较功能列表；协议、SQL、存储格式、复制和工具兼容要分开验收。
思考题：提交一份分支选型表，列出五项必须实际验证的兼容条件与迁回方案；指出作者在相关产品上的经验优势和可能的评价偏重，但不要仅凭商业关联否定证据。
### MySQL 服务器状态
附录 B，`part0025.xhtml`。解决配置、累计计数、瞬时状态与 InnoDB 内部输出怎样转换为可检验解释。
重点看系统变量与状态变量的区分、全局/会话范围、增量采样，以及 `SHOW ENGINE INNODB STATUS` 的事务、锁、日志与缓冲池部分。累计值要除以观察区间，重启或计数重置后不能继续做普通差分。
引申：现代 Performance Schema 的时间事件能补足单纯计数，但仪表开启与采集覆盖仍是解释前提；旧 SHOW 输出格式不可作为跨版本稳定解析 API。
思考题：提交一个两次采样差分的指标解释表，覆盖负载变化、服务器重启和计数重置；另设计“CPU 低但锁等待高”的证据组合，不能只贴状态输出。
### 大文件传输
附录 C，`part0026.xhtml`。复制备份的实际路径是读盘 → 可选压缩 → 加密/网络 → 解压 → 写盘 → 完整性验证，流水线速度受最慢阶段约束。
重点看压缩收益随网络与 CPU 瓶颈改变，以及并行度增加可能反而变慢。书中百兆网络测试结果不作为现代传输选型结论。
引申：原书把压缩 CRC 当作检测损坏的理由；CRC 不能保证任何错误都能发现，也不提供对恶意篡改的认证。重要备份需保留独立校验及身份/传输保护，验证仍应覆盖恢复可用性。
思考题：提交带宽、读写速度和压缩速度的预算，比较压缩/不压缩的两组完成时间；设计截断、位翻转和中途失败的验收，说明“文件存在”与“可恢复”之间的差别。
### EXPLAIN
附录 D，`part0027.xhtml`。解释输出表达优化器选择的访问方式与估计，不直接证明实际执行时间或数据正确性。
重点看 `id`、`select_type`、`type`、`possible_keys`、`key`、`key_len`、`ref`、`rows` 与 `Extra`，以及复杂子查询如何对应计划节点。区分全表扫描和全索引扫描；`Using index` 与 `Using index condition` 不可混读。
引申：在 8.4 以静态计划和实际执行计划对照，实际行数、循环次数、首行与完成时间帮助定位估计偏差；父子迭代器的时间不能无条件相加。[EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)
思考题：提交一条多表查询的计划树，解释哪些节点重复执行；再给出估计行数错十倍但查询仍快、估计准确但等待很久两个反例。
### 锁的调试
附录 E，`part0028.xhtml`。解决“谁等谁、等什么、阻塞者为什么不结束”的问题；重点不是先 KILL，而是先重建等待关系。
重点看服务器级锁与引擎锁的区分、长时间空闲事务、等待图及事务关联。原书对全局锁/read_only 的简化表述不应记成它们完全等价；权限、事务与内部线程的行为必须按实际版本确认。
引申：现代观察数据锁使用 `performance_schema.data_locks` 与相应等待表；数据锁、元数据锁和应用命名锁分别定位，不能把没有数据锁等待误解成没有阻塞。[数据锁表](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-locks-table.html)
思考题：提交三会话等待图，设计一个 idle-in-transaction 阻塞链；解释杀等待者和杀阻塞者的不同后果，并估计回滚期间为何可能继续占用资源。
### 在 MySQL 上使用 Sphinx
附录 F，`part0029.xhtml`。作者把全文搜索系统当作 MySQL 补充，不只做文本匹配，还用于分布式搜索、排序、属性过滤和预计算关联。
重点看数据源抽取 → 建索引 → searchd 查询 → 候选文档 ID → 回数据库取展示字段的路径；再读 Grouply 案例中的多值属性、预构建 JOIN 与跨分片聚合。具体安装命令和产品性能不作为当前推荐。
引申：将搜索索引视为可重建的派生状态，需要定义增量变更、删除传播、重建切换和陈旧窗口；搜索找不到不直接等于权威数据库不存在。
思考题：提交 IM 消息搜索的数据同步与重建状态机，覆盖修改、删除和乱序到达；比较数据库全文索引与独立搜索服务在事务可见性、相关性、扩展性和维护成本上的取舍。
