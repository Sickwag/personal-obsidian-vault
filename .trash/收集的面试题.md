## 基础
### 指针和引用的区别
![[cpp-05-pointer-reference-memory-zh-cartoon-38c09b9a.webp]]
**回答话术：**
指针是持有地址的独立对象，可重指向、可为空、可多级；
引用是已绑定对象的别名，必须初始化、不可重绑定、不可为空、只有一级。
- 实现上编译器常按 `T* const` **不可变指向的指针**实现。在局部代码块场景下会被编译器优化为不占用内存空间的别名，而函数调用的压栈行为，作为类成员时会被视为指针，占用空间
- 引用是"编译期固定的别名约束"--所以没有像指针一样嵌套，多级引用一般用于元编程，触发引用折叠，用于支持移动语义和完美转发特性
- 不能引用数组、不能放进 STL 容器作为元素（因为STL 容器元素由 2 个概念: 可赋值&可赋值构造控制，引用不满足），函数重载时 `T&` 与 `T*` 是不同签名
- 引用虽然也是地址，但能够自动解引用，sizeof 引用返回对象大小，sizeof 指针返回指针长度
**知识点讲解：**

| | 指针 | 引用 |
|--|------|------|
| 是否可变 | 可重指向 | 绑定后不可变 |
| 是否占内存 | 占独立空间 | 语义不占（实现常为指针） |
| 是否可为空 | 可为 nullptr | 必须绑定对象 |
| 多级 | 可多级 | 仅一级（折叠除外） |
| 初始化 | 可不初始化 | 必须初始化 |

> [!Info] 可能的追问:
> - Q: 引用底层真的不占内存吗？
> - A: 几乎所有编译器把引用实现为 const 指针，机器码层面占 8 字节。"不占内存"是标准给的语义承诺（不可对引用取地址、`sizeof(引用)` 得到被引对象大小），而非实现承诺。局部引用常被优化寄存器化，**但作为类成员或参数一定占空间**。
> - Q: 右值引用和左值引用的区别？
> - A: `T&&` 只能绑右值，目的是延长临时对象生命周期并支持移动语义；`T&` 只能绑左值，`const T&` 可绑右值但不可改。引用折叠 `T& && -> T&` 是完美转发 `std::forward` 的基础。

### 函数指针和数据指针有什么区别？为什么指针还分类型？
**回答话术：**
指针的本质就是存储内存地址的整数（64 位系统占 8 字节），从存储形式上看函数指针和数据指针没有区别。
C/C++ 在指针上附加类型信息是为了**保证内存访问安全**：`int*` 告诉编译器按 4 字节访问，`char*` 按 1 字节，类型决定解引用时读多少字节、如何解释。

函数指针和数据指针的区分有历史和安全两方面原因：
- **历史**：冯·诺依曼架构代码和数据在同一地址空间，但哈佛架构下代码区和数据区是分开的地址空间（8051 单片机）
- **标准规定**：`void*` 可以存储任意数据指针，但不保证能存储函数指针；函数指针和数据指针大小可以不同（现代 64 位系统上都是 8 字节，但标准不保证）
- **POSIX**：明确函数指针和 `void*` 之间的转换是安全的（实现保证），但 C/C++ 标准不保证

```cpp
// 函数指针声明
typedef int (*binary_op_t)(int, int);
int add(int a, int b) { return a + b; }
binary_op_t op = add;         // 函数指针赋值
int result = op(1, 2);        // 通过函数指针调用

// 函数指针不能随意转 void*（需要显式转换，不可移植）
void* p = reinterpret_cast<void*>(add);  // 不保证安全
```

不同类型的指针不能随意相互转换是为了防止误用：如果 `int*` 能随意转 `double*`，解引用时按 8 字节读取 4 字节数据就会读到相邻内存的垃圾值。
**知识点讲解：**
函数指针常用于回调机制和策略模式，C++11 后 `std::function` 和 lambda 是更安全、更方便的替代，但底层仍然是函数指针或仿函数对象。
> [!Info] 可能的追问:
> - Q: `void*` 能存储函数指针吗？
> - A: C/C++ 标准不保证。`void*` 保证能存储任意对象指针，但函数指针大小可能不同于 `void*`（虽然现代 64 位系统上都是 8 字节）。POSIX 系统上可以安全转换，但不可移植。C++ 推荐用 `std::function` 或模板代替 `void*` 传递函数。
> - Q: 为什么 C 不允许函数指针和数据指针互转？
> - A: 哈佛架构下代码区和数据区地址空间不同，函数指针指向代码区、数据指针指向数据区，地址域不重叠，互转没有意义。现代 x86/ARM 统一编址，实际上转换是安全的，但标准为了兼容性不做保证。

### 全局变量、局部变量、静态全局变量、静态局部变量的区别
**回答话术：**
按作用域 + 生命周期 + 链接性三个维度切：
- 全局变量：外部链接，跨编译单元可见，其他单元用 `extern` 声明即可用，链接时找定义，找不到报 LNK2019
- 静态全局变量：内部链接，仅当前编译单元可见，现代 C++ 推荐用匿名命名空间替代
- 局部变量：仅在代码块内，栈上分配，块结束销毁
- 静态局部变量：可见性同局部，但生命周期贯穿程序、只初始化一次，C++11 起初始化线程安全（可做单例）

内存布局：全局/静态全局/静态局部在 `.data`（已初始化）或 `.bss`（未初始化）段，局部变量在栈。
**知识点讲解：**

| 变量类型   | 作用域  | 生命周期 | 链接性  | 存储区        |
| ------ | ---- | ---- | ---- | ---------- |
| 全局变量   | 全程序  | 程序结束 | 外部链接 | .data/.bss |
| 静态全局变量 | 当前文件 | 程序结束 | 内部链接 | .data/.bss |
| 局部变量   | 当前块  | 块结束  | 无    | 栈          |
| 静态局部变量 | 当前块  | 程序结束 | 无    | .data/.bss |

> [!Info] 可能的追问:
> - Q: 静态局部变量的初始化如何保证线程安全？
> - A: C++11 起编译器为每个静态局部变量生成隐藏的原子标志位（`__cxa_guard_acquire/__cxa_guard_release`），首次进入时加锁初始化，后续调用直接跳过。所以 Meyers 单例 `static T& inst() { static T t; return t; }` 是线程安全的。
> - Q: 静态全局变量和匿名命名空间里的变量有什么区别？
> - A: 语义几乎等价（都内部链接），但匿名命名空间可包含类型/函数更通用，且在模板参数推导、ADL 中行为不同。C++ 标准建议用匿名命名空间替代 `static` 限制文件作用域。

### 变量定义在头文件中有什么问题？
**回答话术：**
关键看头文件里是声明还是定义：
- 声明（`extern T g_x;`）被多源文件包含没问题，只告诉编译器符号在某处定义、检查延迟到链接期
- 定义（`T g_x;`）被多源文件包含则每个编译单元生成一份定义，链接时违反 ODR 报重复定义
解决：
- C++17 用 `inline T g_x;` 修饰后允许多份通链接接器等价定义合并为一份
本质：ODR 要求每个非 inline 实体在整个程序中只能有一个定义，详见 [[#ODR（One Definition Rule）]]。
**知识点讲解：**
> [!Info] 可能的追问:
> - Q: ODR 的具体规则是什么？inline 为什么能绕过？
> - A: 详见 [[#ODR（One Definition Rule）]]。简言之：所有需要知道内存布局的符号在所有编译单元中有且只能有一份相同的定义；inline 实体允许多份等价定义，链接器合并。类的定义在每个编译单元都要可见（头文件包含），所以类天然遵循"一份定义、多处可见"的 ODR 例外。
> - Q: 头文件里定义 static 变量会怎样？
> - A: include 指令的本质是复制粘贴文本，这就会导致每个包含该头文件的编译单元都生成一份独立的 static 变量，每个变量内存地址不同
> - Q: 在头文件中全局作用域定义 static 变量会引起报错吗？
> - A: **不会报错**，但会造成**每个包含该头文件的编译单元都各自独有一份变量**，内存地址各不相同。`#include` 是文本替换，`a.cpp` 和 `b.cpp` 都 `#include "header.h"` 后各自有自己的 `static int counter = 0;`，修改一个不影响另一个，语义上容易引起误解。
> 正确做法：要共享用 `extern int counter;`（头文件声明，.cpp 定义）；C++17 可用 `inline int counter = 0;`（头文件定义，多编译单元共享同一个变量）。
### extern C 的作用是什么？
**回答话术：**
`extern "C"` 是链接指示符，告诉编译器按 C 规则编译和链接大括号内的符号--即关闭 name mangling（C 不支持重载，函数名原样作为符号名）。
核心场景：
- C++ 调 C 库
- 给 C 调用方提供 C 接口
- 动态库导出跨语言 ABI（Python/Go 想要使用 C/C++编译的库，那么需要使用 extern C 导出符合 C ABI 的动态库）

机制详见 [[#Name Mangling]]。典型写法用 `__cplusplus` 宏包裹，使同一头文件 C/C++ 都能用。
> [!Info] 可能的追问:
> - Q: extern "C" 块内能用 C++ 特性吗？
> - A: 能。它只影响链接（mangling），不影响函数体语义--函数体内可用模板、异常、STL。但该函数本身不能重载（C 不允许同名函数），且不能是类的成员函数（C 无类成员概念）。
> - Q: 一个函数既要 C 又要 C++ 调用怎么写？
> - A: 头文件用 `__cplusplus` 宏判断：C++ 环境用 `extern "C"` 包裹声明，C 环境直接声明。标准库 `<cstdio>` 就这么做。实现写在 .c 或 .cpp 都行，但 .cpp 实现需在头文件 extern "C" 声明覆盖下编译。

### sizeof(1\=\=1) 在 C 和 C++ 中结果为什么不一致？
**回答话术：**
- C 中 `1==1` 类型是 `int`（C89 没有内置 bool，**标准中规定**关系运算结果按 int 处理），`sizeof(int)` 通常 4
- C++ 中 `1==1` 类型是 `bool`（C++ 引入了内置 bool 类型），`sizeof(bool)` 是 1

根因：C++ 的类型系统把关系/逻辑运算结果定为独立的 bool 类型，而 C 定为 int。
这也解释了 `true` 的差异：C 里是宏（`#define true 1`，int），C++ 里是关键字（bool 字面量）。

> [!Info] 可能的追问:
> - Q: C99 不是也有 _Bool 吗？为什么 sizeof 还是 4？
> - A: C99 引入了 `_Bool` 和 `<stdbool.h>`（`bool` 是 `_Bool` 的宏别名），但 C 的关系运算结果仍是 `int`（标准规定），不会因引入 _Bool 而改变。C++ 从一开始就把关系运算结果定为 bool，这是语言设计层面的差异。
> - Q: bool 在 C++ 里真的占 1 字节吗？
> - A: `sizeof(bool)` 是 1。但 bool 数组每元素仍占 1 字节（未做位压缩），要压缩用 `std::vector<bool>`（特化版按 bit 存）或 `std::bitset`。

### define 和 const 在定义常量时区别是什么？
**回答话术：**
`#define` 是预处理阶段的纯文本替换：
- 无类型、不进符号表、不可调试
- 每处使用都展开（占代码段、多份副本）
- 无作用域（从定义处到文件尾或 `#undef`）

`const` 是编译期的类型化常量：
- 有类型检查、进符号表可调试
- 通常只一份（放 .rodata）
- 有作用域、能取地址（是真正的实体而非文本）

对于 const 定义常量的场景，现代 C++ 优先用 `constexpr`（编译期求值，比 const 更强：可用于常量表达式上下文）替代两者。
**知识点讲解：**

| 维度  | define         | const / constexpr |
| --- | -------------- | ----------------- |
| 阶段  | 预处理替换          | 编译期确定             |
| 类型  | 无，纯文本          | 有类型，类型检查          |
| 调试  | 不可（已展开）        | 可（进符号表）           |
| 内存  | 多份副本，占代码段      | 一份，.rodata        |
| 作用域 | 文件尾到  undef | 遵循 C++ 作用域        |
| 取地址 | 否              | 是（真实实体）           |

> [!Info] 可能的追问:
> - Q: const 和 constexpr 的区别？
> - A: `const` 表示"运行期不可改"，但其值不一定能在编译期确定（如 `const int x = read()` 是运行期值）。`constexpr` 表示"编译期可求值"，强制编译器在编译期计算，可用于数组大小、模板参数等常量表达式上下文。`constexpr` 是 const 的超集（constexpr 一定 const，反之不然）。
> - Q: define 定义函数式宏有什么坑？
> - A: 无类型检查、参数多次求值（`#define MAX(a,b) ((a)>(b)?(a):(b))` 对 `MAX(i++, j++)` 会自增多次）、无作用域、运算符优先级需手动加括号。C++ 推荐用 inline 函数或 constexpr 函数替代。

### define 和 typedef 的区别是什么？
**回答话术：**
- `typedef`：编译期关键字，给已有类型起别名，有类型检查、有作用域、占符号线索（调试可见），不能定义带有模板参数类型的别名
- `#define`：预处理文本替换，无类型检查、无作用域（定义后到文件尾有效）、纯文本故可定义常量/编译开关/类型别名
现代 C++ 推荐用 `using P = int*;`（别名模板，C++11）替代 typedef，更好地支持模板语法
> [!Info] 可能的追问:
> - Q: typedef 和 using 有什么区别？
> - A: `using` 是 C++11 引入的类型别名语法，`using P = int*` 等价 `typedef int* P`。但 `using` 支持别名模板（`template<class T> using V = std::vector<T>;`），typedef 不支持。此外 using 语法更直观（别名在左），且可用于命名空间成员引入。
> - Q: typedef 定义的类型别名能用于模板参数吗？
> - A: **可以**。`typedef int MyInt; vector<MyInt>` 完全合法。但 `typedef` 不能定义**带模板参数的类型别名**：
> ```cpp
> template<typename T> typedef vector<T> Vec;  // 编译错误
> template<typename T> using Vec = vector<T>;  // C++11 合法（别名模板）
> ```
> `typedef` 语义是"给已有完整类型起名字"，不能有未绑定的模板参数。`using` 别名模板打破了这个限制。
> 另外，`typedef` 定义的数组类型会保留数组大小（`typedef int Arr[5];` -> `Arr a` 就是 `int a[5]`），比 `#define` 更安全。
### volatile 的作用？是否具有原子性，对编译器有什么影响？
**回答话术：**
`volatile` 告诉编译器该对象的值可能在程序控制之外被改变（硬件寄存器、中断 ISR、信号处理函数），禁止相关优化：
- 不缓存到寄存器
- 不把 `while(flag)` 优化成死循环，flag 变量的值可能会被外部操作
- 不把连续读合并成一次读

**volatile 不保证**：原子性、内存可见性、happens-before 关系--它只防编译器优化，不插 CPU 内存屏障。
所以多线程共享变量不能用 volatile 做同步，要用 `std::atomic` 或 mutex。
volatile 真正的用武之地：嵌入式/驱动里映射到内存的硬件寄存器（MMIO）和信号/中断处理中被异步修改的变量。
可与 const 共存：`const volatile` 表示"本程序不能改（const）但外部硬件会改（volatile）"，典型如只读硬件状态寄存器。
详见 [[#volatile、atomic 与内存屏障]]。
**知识点讲解：**
```cpp
volatile int flag;       // 每次从内存读，防 while(flag) 被优化成死循环
const volatile uint32_t* hw_reg = (const volatile uint32_t*)0x4000;
// const: 程序不写; volatile: 每次都真正读硬件, 不缓存
```
> [!Info] 可能的追问:
> - Q: 为什么 volatile 不能保证多线程可见性？Java 的 volatile 可以啊？
> - A: C++ 的 volatile 只防编译器优化，不插 CPU 内存屏障，所以核心 A 写了 volatile 变量，核心 B 的缓存行可能还是旧值。C++ 要可见性用 `std::atomic<T>` 或 `atomic_thread_fence`。
> - Q: 什么场景必须用 volatile？
> - A: 
> 	1) 内存映射 IO 寄存器（每次读写都要真正打到硬件，不能合并/缓存）；
> 	2) 信号处理函数中修改、主程序读取的标志变量（防止编译器把读提到循环外）；
> 	3) setjmp/longjmp 跳转后被修改的局部变量。这三类都是"程序控制流之外被改"，编译器优化会破坏语义。

### 虚函数和纯虚函数的区别？
**回答话术：**
- 虚函数：有默认实现的动态绑定函数，用 `virtual` 声明，派生类可选择性重写，虽然不强制使用 `override` 关键字，但是不写就没与编译期检查可能触发函数覆盖排查起来比较困难
- 纯虚函数：强制派生类必须重写，可以有实现体但需要在类外定义，目的是给派生类提供骨架实现

含纯虚函数的类是抽象类，不能实例化。两者都走虚函数表动态分发。
**知识点讲解：**
```cpp
class Shape {
    virtual void draw() { /* 默认实现 */ }      // 虚函数
    virtual void area() const = 0;               // 纯虚函数，无定义
    virtual ~Shape() = 0;                        // 纯虚析构
};
Shape::~Shape() {}                               // 纯虚函数的类外定义（合法）
// Shape s;        // 错误：抽象类不可实例化
class Circle : public Shape {
    void area() const override {}                // 必须重写，否则 Circle 仍是抽象类
};
```
> [!Info] 可能的追问:
> - Q: 纯虚函数为什么还能有实现体？有什么用？
> - A: 语法允许纯虚函数在类外提供定义，派生类可通过 `Base::func()` 调用。典型用途是纯虚析构：基类想成为抽象类但没有其他纯虚函数可声明，就把析构声明为纯虚，然后必须类外给定义（否则链接失败，因为派生类析构会调用基类析构）。
> - Q: 虚函数和模板方法模式的关系？
> - A: 模板方法模式靠虚函数实现：基类用非虚的 `templateMethod()` 定义算法骨架，内部调用虚函数 `step()` 作为扩展点，派生类重写 `step()` 定制细节。`step()` 设为纯虚就是强制子类实现，设为虚函数就是提供默认实现可覆盖。
> - Q: 纯虚函数有实现体到底有什么用？能否详细说明？
> - A: 核心价值：**声明接口（纯虚）+ 提供可被显式调用的默认实现（类外定义），同时强制派生类重写接口**。典型场景是纯虚析构函数：
> ```cpp
> class Base {
> public:
>     virtual ~Base() = 0;   // 纯虚析构：强制抽象，阻止直接实例化
> };
> Base::~Base() {}           // 必须！派生类析构隐式调用基类析构，无实现则链接错误
> ```
> 此外，如果希望某接口既有默认实现又强制派生类重写（避免忘记重写导致悄悄调用基类默认行为），可以纯虚声明 + 类外定义默认实现，派生类想用默认行为时显式调用 `Base::func()`。

### 构造函数和析构函数能否被设置为纯虚函数？
**回答话术：**
构造函数连虚函数都不能是，更别提纯虚。两方面原因：
1. 存储角度：虚函数靠对象的 vtable 指针分发，但构造时对象还没实例化、vtable 指针还没建立，无法通过 vtable 调用构造函数
2. 使用角度：虚函数的意义是"通过基类指针/引用调用时落到派生类版本"，而构造函数是创建对象时自动调用，不存在"通过基类指针调用构造"的场景

析构函数则**可以**是纯虚的（用于把基类变成抽象类），但必须类外提供定义体，否则派生类析构调用基类析构时链接失败。
实践中更推荐直接把析构声明为普通虚函数（`virtual ~Base() = default;`）而非纯虚，除非真的需要抽象类且没有其他纯虚函数。
**知识点讲解：**
```cpp
class Base {
public:
    virtual ~Base() = 0;     // 纯虚析构：让 Base 成为抽象类
};
Base::~Base() {}             // 必须！派生类析构会调用，无定义则链接失败

class Derived : public Base {};
// Base b;    // 错误：抽象类
Derived d;    // OK：纯虚析构的特殊性使派生类只要能链接就可用
```
> [!Info] 可能的追问:
> - Q: 为什么构造函数不能是虚函数，但析构函数可以且推荐是虚函数？
> - A: 构造时对象尚未成型（vtable 指针由构造函数负责设置，鸡生蛋问题）。析构时对象已成型、vtable 指针有效，可分发到派生类析构。多态删除（`delete base_ptr`）时若析构非虚，只调用基类析构，派生类成员泄漏--所以带多态用途的基类析构必须是虚函数。
> - Q: 构造函数里调用虚函数会发生什么？
> - A: 不会触发多态，而是调用当前类的版本。因为构造时派生类部分还没构造，vtable 指向当前类的虚表。这是 C++ 比 Java 隐患更小的设计（Java 构造里调虚函数会调到子类未初始化的版本，易出 bug）。

### 什么是 void 类型指针？
**回答话术：**
`void*` 是通用指针，可指向任意类型对象但不带类型信息，不能直接解引用，不能做指针算术（步长未知）必须先显式转型到具体类型才能用

C 的 `malloc` 返回 `void*`，靠用户手动转型；C++ 的 `new` 返回正确类型指针故不需转型。
`void*` 的价值是 C 实现泛型容器/回调（如 `qsort`、`pthread_create` 的参数）的底层手段；C++ 有模板，基本不需要 `void*`，用它就放弃了类型安全。
任何对象指针都能隐式转 `void*`，但 `void*` 转回具体类型必须显式且由开发者保证类型正确，否则未定义行为。
**知识点讲解：**
```cpp
void* p = malloc(64);          // C: void* 需手动转
int* ip = (int*)p;
// C++ 推荐
int* ip2 = new int[16];        // 直接是 int*，无需 void*
// C 的泛型回调示例
qsort(arr, n, sizeof(int), [](const void* a, const void* b) {
    return *(int*)a - *(int*)b;   // void* 必须先转型
});
```
> [!Info] 可能的追问:
> - Q: 函数指针能转 void* 吗？
> - A: 不保证。C 标准允许数据对象指针互转，但函数指针和数据指针是两类，`void*` 是数据指针，转函数指针在 POSIX 上可行但非可移植。C++ 中 `std::function`/函数指针应单独处理，不要塞 `void*`。

### memcpy 函数的底层原理是什么？
**回答话术：**
memcpy 按字节搬运内存块，不关心数据类型。高性能实现不是逐字节循环，而是按对齐优化：
1. 先把未对齐的首尾用单字节补齐到对齐边界
2. 中间对齐部分用更大的字长（8/16/32 字节，甚至 SIMD `rep movsb`/AVX）批量复制
关键：**memcpy 不处理 src 和 dst 重叠的情况，重叠是未定义行为**。
处理重叠的是 `memmove`，它通过判断 src 与 dst 的前后位置决定从前向后还是从后向前拷贝，避免覆盖尚未读取的源数据。
**知识点讲解：**
```c
void* memcpy(void* dst, const void* src, size_t n);    // 不处理重叠，UB
void* memmove(void* dst, const void* src, size_t n);   // 处理重叠
// memmove 的方向选择：
// dst < src 且需避免覆盖 -> 从前向后
// dst > src 且需避免覆盖 -> 从后向前
// 这样保证重叠区源数据在被覆盖前已读出
```
> [!Info] 可能的追问:
> - Q: memcpy 和 memmove 怎么选？性能差异？
> - A: 不重叠用 memcpy（少一次方向判断，略快）；可能重叠用 memmove。现代 glibc 的 memmove 内部复用 memcpy 的对齐+批量路径，只多一个方向判断，性能差距很小，所以不确定时优先 memmove 保安全。

### C-style 一些函数的作用和有的缺陷
**回答话术：**
C 字符串/格式化函数的通病是不带缓冲区大小参数，靠调用者保证空间足够，极易缓冲区溢出：
- `strcpy` 逐字节拷贝源串到 dst 直到遇 `\0`，不管 dst 多大--源串超长就溢出覆盖相邻内存（经典栈溢出攻击向量）
- `memcpy` 则是通用的内存块拷贝函数，只负责拷贝字节
- `sprintf` 同理把格式化结果往 dst 写，无边界检查

安全替代是带 `_s`/`n` 的版本：`strncpy`/`snprintf` 限制长度，`_s` 系列（C11 Annex K）还强制传 dst 大小并在运行时检查。
但 `strncpy` 有坑--不保证补 `\0`、目标大时填零浪费。
C++ 里直接用 `std::string`/`std::format`（C++20）彻底规避这类问题。
**知识点讲解：**

| 函数 | 作用 | 缺陷 | 安全替代 |
|------|------|------|----------|
| strcpy | 拷贝字符串 | 不检查 dst 边界 | strncpy / strcpy_s |
| sprintf | 格式化写 dst | 不检查 dst 边界 | snprintf / sprintf_s |
| gets | 读一行 | 经典溢出漏洞 | fgets / gets_s |
| strcat | 拼接 | 不检查 dst 边界 | strncat / strcat_s |
| scanf | 格式化读 | %s 无长度限制 | %ns 指定长度 / scanf_s |

> [!Info] 可能的追问:
> - Q: strncpy 为什么不算完全安全？
> - A: `strncpy(dst, src, n)` 在 src 长度 >= n 时不补 `\0`，导致 dst 可能不是合法 C 字符串；src 短于 n 时用 `\0` 填满剩余空间（浪费）。C++ 推荐用 `std::string` 或 C11 的 `strcpy_s`（带完整大小检查且保证 `\0` 结尾）。
> - Q: _s 系列函数为什么没普及？
> - A: `_s` 是 C11 Annex K 的可选部分，编译器可不实现（GCC/Clang 多未实现，MSVC 实现了）。跨平台代码不能依赖它，所以工业界更多用 `snprintf`/`strncpy` 或直接上 C++ 的 `std::string`。

### C++程序的编译过程
![[cpp-19-compile-pipeline-zh-cartoon-2f0d6663.webp]]
**回答话术：**
四阶段：
1. 预处理：展开宏/条件编译/删注释/处理 `#pragma`，产出纯 C++ 源码
2. 编译：词法/语法/语义分析 + 优化，翻译成汇编
3. 汇编：汇编转机器指令，生成目标文件 .o/.obj
4. 链接：符号解析 + 地址重定位，合并多个目标文件和库，生成可执行文件

关键在链接阶段：编译器为每个编译单元生成独立符号表，链接器把跨单元的符号引用绑定到定义；目标文件里地址还是相对的（段内偏移），链接时重定位成最终的虚拟地址。
符号表和重定位细节见 [[#符号表与地址重定位]]。
**知识点讲解：**
```bash
g++ -E main.cpp -o main.ii    # 预处理
g++ -S main.ii -o main.s      # 编译（生成汇编）
g++ -c main.s -o main.o       # 汇编（生成目标文件）
g++ main.o -o main            # 链接
```
> [!Info] 可能的追问:
> - Q: 什么是符号表？存放在哪？
> - A: 详见 [[#符号表与地址重定位]]。简言之：符号表记录每个符号（函数/全局变量）的名字、类型、所在段、段内偏移、绑定性（本地/全局）。目标文件 `.o` 的符号表可通过 `nm`/`objdump -t` 查看；可执行文件运行时符号表通常不加载（除非带 `-g` 调试信息），调试信息单独存在 `.debug` 段。
> - Q: 什么是地址重定位？
> - A: 编译单元独立编译时编译器不知道外部符号的最终地址，先填 0 或占位符，并在重定位表（`.rela.text`）记录"这里需要修正、引用哪个符号"。链接器合并所有段后确定每个符号的最终虚拟地址，回头修正这些占位符--这就是重定位。动态库还有运行时重定位（由动态链接器 ld.so 处理 PLT/GOT）。
### 如何理解 C++ 是面向对象编程？
**回答话术：**
面向过程以"过程+数据分离"组织代码，数据结构一变所有操作它的函数都要改；面向对象把"数据+操作数据的函数"绑成一个对象单元（封装），通过继承复用、多态扩展。
本质是用类把状态和变换状态的逻辑收敛到一起，让数据结构的变更影响面局限在类的接口内。
 C++ 的 OOP 是"可选的，手动控制堆栈内存分配，参数的值和引用传递可以控制，多继承，通过 friend 破坏封装这些违反 OOP 的设计都可以手动控制是否使用
这个多范式+值语义的视角见 [[#面向对象的独到理解]]。
**知识点讲解：**
- 三大特性：封装（数据+行为绑定，访问控制隐藏实现）、继承（is-a 复用）、多态（同一接口不同行为，靠虚函数动态绑定）
- 面向过程 vs 面向对象：过程是"动词驱动"（函数为中心，数据被动传递），对象是"名词驱动"（数据为中心，行为附属于数据）
> [!Info] 可能的追问:
> - Q: C++ 的 OOP 和 Java 的 OOP 有什么本质区别？
> - A: 详见 [[#面向对象的独到理解]]。核心：Java 是引用语义+一切对象堆分配+单根继承（Object），对象身份靠引用；C++ 是值语义+对象可栈分配+多继承，对象身份就是它自己。C++ 的拷贝/移动/析构是 Java 没有的核心复杂度，也是性能和灵活性的来源。
> - Q: 多态在 C++ 里有哪些形式？
> - A: 静态多态（编译期）：函数重载、模板、CRTP；动态多态（运行期）：虚函数。静态多态零运行开销但代码膨胀，动态多态有 vtable 间接调用开销但灵活解耦。

### 继承链条中，什么是函数隐藏？
**回答话术：**
函数隐藏（name hiding）指派生类中只要有一个同名函数（**不管参数列表是否相同，也不管是否有 `override`**），就会把基类所有同名函数在派生类作用域里隐藏掉--这是按"名字"而非"签名"作用域查找的结果，名字查找先于重载决议。

用 `using Base::f;` 重定义别名可以把基类版本引入派生类作用域，恢复重载集。
注意隐藏和重写（override）不同：
- 重写：虚函数同签名覆盖，走动态绑定
- 隐藏：非虚/签名不同时，按静态类型查找
**知识点讲解：**
```cpp
class Base {
public:
    void f(int);
    void f(double);
};
class Derived : public Base {
public:
    void f(std::string);   // 隐藏 Base::f(int) 和 Base::f(double)
    using Base::f;         // 引入基类重载集，恢复 f(int)/f(double) 可见
};
Derived d;
d.f(3);        // 无 using -> 编译错误; 有 using -> 调 Base::f(int)
```
> [!Info] 可能的追问:
> - Q: 函数隐藏、重写、重载三者的区别？
> - A: 重载（overload）同一作用域同名不同参数；重写（override）派生类虚函数与基类同签名，运行期动态绑定；重定义/隐藏（redefine/hide）派生类同名函数（无论签名）遮蔽基类同名函数，按静态类型编译期查找。override 需要 virtual+同签名，hide 不需要 virtual 且签名可不同。
> - Q: 为什么 C++ 设计函数隐藏而不是自动合并重载集？
> - A: 防止"远距离意外覆盖"：派生类作者可能不知道基类有哪些重载，自动合并会让 `d.f(3)` 意外调用到语义完全不同的基类 `f(int)`，埋下 bug。强制用 `using` 显式声明"我要继承这些重载"是更安全的设计，代价是略显繁琐。

### 是否允许类的构造函数和 operator()拥有相同的参数列表？
**回答话术：**
允许，两者不冲突。构造函数名是类名，`operator()` 是函数调用运算符，名字不同、作用域规则不同，重载决议按函数名区分，所以同参数列表完全合法。
语义陷阱：
- `T x(args);` 是构造对象 x
- `x(args);` 是对已构造对象调用 `operator()`

两者靠"是否新对象声明"区分。
真正会出问题的是声明语境下的 most vexing parse：`T x(U());` 会被解析为函数声明而非对象构造。
所以同参列表本身没事，但构造和 `operator()` 都涉及 `()` 语法，要小心声明语境下的歧义，C++11 后用花括号统一初始化规避。
**知识点讲解：**
```cpp
class Func {
public:
    Func(int x);            // 构造
    void operator()(int x); // 函数调用运算符，可同参
};
Func f(1);    // 构造对象 f
f(1);         // 调用 f.operator()(1) -- 合法且常见（仿函数模式）

// Most Vexing Parse：
std::vector<int> v(std::istream_iterator<int>(in), std::istream_iterator<int>());
// 被解析为函数声明，而非构造 vector -- 用花括号规避：
std::vector<int> v{std::istream_iterator<int>(in), std::istream_iterator<int>{}};
```
> [!Info] 可能的追问:
> - Q: 什么是 Most Vexing Parse？怎么避免？
> - A: C++ 规定"能解析为声明的就解析为声明"。`T x(U());` 中 `U()` 可解析为"返回 U 的函数指针"参数，于是整个被解析为名为 x 的函数声明，而非构造对象。避免：用花括号初始化 `T x{U{}};`（C++11 统一初始化），或加括号 `T x((U()));`。

### 单继承和多继承的虚函数表结构是怎样的？
![[cpp-28-single-inheritance-layout-zh-cartoon-65270f1b.webp]]
![[cpp-29-multiple-inheritance-layout-zh-cartoon-2b54a3be.webp]]
**回答话术：**
- 单继承：对象头部一个 vptr 指向一张虚表，虚表按声明顺序存各虚函数指针；派生类重写某虚函数就在虚表对应槽位替换为自己的地址，未重写的保留基类指针
- 多继承：对象按继承顺序拼合多个基类子对象，每个含虚函数的基类子对象各有一个 vptr 和对应虚表，所以多继承对象有多个 vptr；派生类自己的新虚函数追加在第一张虚表（主虚表）末尾

覆盖现象和无覆盖布局见 [[#单/多继承虚函数表布局与覆盖]]。
**知识点讲解：**
```cpp
class Base1 { virtual void f(); virtual void g(); };   // vptr -> [Base1::f, Base1::g]
class Base2 { virtual void h(); };                     // vptr -> [Base2::h]
class Derived : public Base1, public Base2 {
    void f() override;        // 覆盖 Base1::f
    void h() override;        // 覆盖 Base2::h
    virtual void k();         // 新虚函数，追加到主虚表(Base1)末尾
};
// Derived 内存布局: [Base1子对象(vptr1)] [Base2子对象(vptr2)] [Derived成员]
// vptr1 -> [Derived::f, Base1::g, Derived::k]   (主虚表)
// vptr2 -> [Derived::h]
```
> [!Info] 可能的追问:
> - Q: 单继承中虚函数覆盖现象是什么？多继承无覆盖时呢？
> - A: 详见 [[#单/多继承虚函数表布局与覆盖]]。单继承覆盖：派生类重写的虚函数在虚表槽位被替换，未重写的继承基类指针，虚表长度不变。多继承无覆盖：派生类不重写任何基类虚函数，则它的多张虚表就是各基类虚表的拷贝（thunk 调整 this 指针），每张表对应一个基类子对象，对象有多个 vptr。
> - Q: 多继承下 Base2 指针指向对象内部偏移，怎么调整？
> - A: `Base2* p = &derived;` 时编译器把指针调整到 Derived 内 Base2 子对象的偏移（this + sizeof(Base1 子对象)）。调用 `p->h()` 通过 vptr2 查表。若派生类覆盖了 `h()`，vptr2 表中对应槽位指向一个 thunk--先调整 this 回到 Derived 起始，再调 Derived::h。

### 如何判断结构体是否相等？能否用 memcmp 函数判断结构体相等？
**回答话术：**
不能用 `memcmp` 比较结构体相等。原因：
- 结构体有内存对齐，对齐填充字节的内容是未定义的（随机垃圾值），即使两个结构体所有成员都相等，填充字节可能不同，`memcmp` 逐字节比较会得到"不相等"的错误结论
- 含指针/浮点的结构体语义相等也不等于字节相等（如 NaN != NaN、指针指向内容相同但地址不同）

正确做法是逐成员比较，C++ 重载 `operator==` 显式比较每个成员；C++20 可用 `=default` 让编译器自动生成逐成员比较（`bool operator==(const T&) const = default;`）。
> [!Info] 可能的追问:
> - Q: 什么情况下 memcmp 比较结构体是安全的？
> - A: 几乎没有可靠场景。即使先 `memset(&s, 0, sizeof(s))` 清零填充字节，含指针/浮点/含虚函数（vptr）的结构体仍不可靠（vptr 不同类实例可能不同，浮点 NaN 不等于自身）。唯一可接受的是 POD 类型且已 memset 清零且无指针浮点，但这是脆弱依赖，不推荐。
> - Q: 结构体能不能直接用 == 比较？
> - A: C 语言不能（struct 不支持 \=\=，需手写函数或 memcmp）。C++ 默认也不行，需重载 `operator==`；C++20 起可 `=default` 让编译器生成逐成员比较，这是最省事且类型安全的方式。

### STL 容器是线程安全的吗？
**回答话术：**
STL 容器默认**不是**线程安全的，标准只保证：
- 多个线程读同一容器安全
- 对不同容器各自操作安全

但对同一容器并发写、或一读一写，行为未定义，需用户自己加锁。
原因：容器内部维护迭代器、size、节点指针等状态，并发修改会破坏不变式（如 vector 扩容时另一线程读会读到已释放的旧内存）。
STL 选择不内置锁--锁粒度无法满足所有场景（粗锁低并发，细锁高开销），把同步责任交给用户更高效。
例外：`std::shared_ptr` 的引用计数操作是原子的（但指向对象的访问不是）。
实践中要么用 `std::mutex` 包裹容器，要么用并发容器库（Intel TBB `concurrent_hash_map`、Folly `ConcurrentHashMap`）。
**知识点讲解：**

| 场景 | 线程安全 |
|------|----------|
| 多线程只读同一容器 | 安全 |
| 多线程操作不同容器 | 安全 |
| 多线程并发读写同一容器 | 不安全（UB） |
| `shared_ptr` 引用计数增减 | 原子安全 |
| `shared_ptr` 指向对象的访问 | 不安全 |

> [!Info] 可能的追问:
> - Q: 如何安全地并发用 STL 容器？
> - A: 
> 1) 粗粒度：一把 `std::mutex` 包整个容器；
> 2) 读写分离：`std::shared_mutex` 读多写少用共享锁；
> 3) 无锁：单生产者单消费者用 `std::atomic` +环形缓冲；
> 4) 直接上并发容器（TBB/Folly）。
> - Q: 什么是"并发容器"？和 STL 容器有什么区别？
> - A: 并发容器是指**内部自带线程同步机制的容器**，多线程同时读写无需外部加锁。STL 容器内部无锁，必须由调用者外部加锁。标准库不提供并发容器（零开销抽象原则，内置锁会影响单线程性能），常见实现有：
> 	1. **分段锁**：每个桶/段一把锁，不同段不冲突（`ConcurrentHashMap`）
> 	2. **无锁设计**：原子操作（CAS）代替锁，读多写少场景
> 	3. **读写锁**：读共享锁，写排他锁
> 三方库：`boost::concurrent_flat_map`、`tbb::concurrent_hash_map`、`folly::ConcurrentHashMap`

### std::map 和 std::unordered_map 的底层数据结构和算法实现是什么？
**回答话术：**
- `std::map`：底层红黑树（平衡二叉搜索树），key 必须可比较（`operator<`）
- `std::unordered_map`：底层哈希表（拉链法，bucket 数组+每桶链表），查找/插入/删除平均 O(1) 最坏 O(n)（全冲突退化），key 必须可哈希（`std::hash`）且可判等

选择：需要有序遍历/范围查询用 map；只要快速点查用 unordered_map。
迭代器稳定性：map 迭代器稳定（节点不搬动，插入不失效其他元素），unordered_map 在 rehash 时迭代器失效。
unordered_map 扩容：负载因子（size/bucket_count）超 `max_load_factor`（默认 1.0）时 rehash 到更大桶数。
**知识点讲解：**

| | std::map | std::unordered_map |
|--|----------|---------------------|
| 底层结构 | 红黑树 | 哈希表（拉链法） |
| 查找复杂度 | O(log n) | 平均 O(1)，最坏 O(n) |
| 有序性 | 按 key 有序 | 无序 |
| key 要求 | operator< | std::hash + operator== |
| 迭代器失效 | 插入不失效，删除仅失效被删元素 | rehash 时全部失效 |
| 内存 | 节点分散，缓存不友好 | 桶数组+链表，较紧凑 |

> [!Info] 可能的追问:
> - Q: 为什么 unordered_map 用拉链法而不是开放寻址？
> - A: 标准要求 unordered_map 的迭代器和引用在插入时不失效（除 rehash 外），且 `erase` 不失效其他元素--拉链法（链表节点）天然满足，开放寻址插入会挪动元素难保证。开放寻址缓存更友好但删除复杂、易聚集。标准选拉链，性能略低但语义干净。
> - Q: 红黑树 vs AVL 树，map 为什么选红黑？
> - A: AVL 严格平衡（高度差<=1），查询略快但插入/删除旋转多；红黑弱平衡（最长路径<=2 倍最短），插入/删除最多 3 次旋转，综合更适合频繁修改的通用 map。Linux 内核、STL 都选红黑。

### std::deque 的数据结构是什么？
**回答话术：**
deque 是分段连续的双端队列--既不像 vector 那样整体连续，也不像 list 那样完全离散（list 在 libstdc++ 中是带哨兵节点的循环双向链表）。
它由一块称为 map 的主控连续空间（不是 STL 的 map 容器）管理，map 中每个节点是一个指针，指向一段固定大小的连续缓冲区，缓冲区才是真正存元素的地方。
- 元素在缓冲区内连续，缓冲区间通过 map 串接
相比 vector 它首部插入快（vector 首部 O(n)），相比 list 它能随机访问。迭代器是"分段连续"的复杂迭代器，跨缓冲区跳转靠 map 节点。

> [!Info] 可能的追问:
> - Q: deque 的随机访问为什么是 O(1) 但比 vector 慢？
> - A: deque 随机访问要两次解引用（先查 map 拿缓冲区指针，再进缓冲区取元素），且缓存不友好（跨缓冲区跳跃）。频繁随机访问选 vector。
> - Q: deque 和 vector 的扩容机制有什么不同？
> - A: vector 扩容是整体搬迁（新配连续空间+拷贝+释放旧空间，O(n)，迭代器全失效）；deque 扩容分两步--缓冲区满就新配一段挂 map 头/尾（O(1)），map 满了才整体扩容 map（O(n) 但频率低）。所以 deque 首尾插入摊还 O(1) 且迭代器不因缓冲区扩容失效。
### priority_queue 既可以 vector/queue 作为底层数据容器是如何做到的？
**回答话术：**
priority_queue 是容器适配器（container adapter），不是独立容器，它包装一个底层序列容器并用堆算法（`make_heap`/`push_heap`/`pop_heap`）维护堆序。
能换底层容器是因为它只要求底层容器提供：
- 随机访问迭代器（算父子节点下标）
- `front()`（取堆顶）
- `push_back()`/`pop_back()`（加删元素）

vector 和 deque 都满足，所以都行。list 不行--不能随机访问（无法用下标算父子关系）。
本质是 priority_queue 通过"算法（堆）+ 适配器模式"解耦了数据存储，只要存储满足堆算法所需的操作集即可替换。详见 [[#容器适配器对底层容器的约束]]。

> [!Info] 可能的追问:
> - Q: 依赖的底层容器需要有什么特征？
> - A: 详见 [[#容器适配器对底层容器的约束]]。简言之：随机访问迭代器（堆算法用下标 `i*2+1`/`i*2+2` 找父子）+ `front()` 取堆顶 + `push_back()`/`pop_back()` 增删尾元素。vector、deque 满足；list 无随机访问不满足；array 无 push_back 不满足。
> - Q: 为什么内存不连续的 deque 也能作为底层容器？
> - A: 堆算法只需"随机访问迭代器"，deque 虽缓冲区分段但迭代器重载了 `operator[]`/`operator+` 提供 O(1) 随机访问（内部跨缓冲区跳转），满足堆算法要求。是否连续内存不重要，重要的是迭代器是否支持随机访问语义。
> - Q: 是什么支持了 priority_queue 允许多种底层容器？
> - A: 两个设计：1) 适配器模式--priority_queue 不自己存数据，持有 Container 成员，对外只暴露堆接口；2) 泛型模板参数 `template<class Container>` 让用户指定容器，编译期生成对应版本。stack/queue 也是同机制，故 stack 可用 deque/list/vector。
> - Q: 除了 priority_queue，标准库还有什么容器适配器？
> - A: 共 3 个容器适配器：
> 	1. **stack**（LIFO）：默认底层 `deque`，只暴露 `push`/`pop`/`top`/`empty`/`size`。底层要求：`back()`/`push_back()`/`pop_back()`，可用 `deque`/`vector`/`list`
> 	2. **queue**（FIFO）：默认底层 `deque`，只暴露 `push`（入队）/`pop`（出队）/`front`/`back`/`empty`/`size`。底层要求：`back()`/`push_back()`/`pop_front()`，可用 `deque`/`list`，**不能用 `vector`**（无 `pop_front`）
> 	3. **priority_queue**：默认底层 `vector` + 堆算法
> 	三者都不是独立容器，只是封装底层容器接口并限制操作方式，给使用者明确的数据结构语义（栈/队列），避免误用。

### 非比较排序算法
**回答话术：**
只靠两两比较的排序下界是 Ω(n log n)（通过数学上的决策树可严格证明），要突破就得利用数据的数学特性（整数、范围已知、可按位拆分），即非比较排序：
- 计数排序：按值建计数数组+前缀和定位，O(n+k)，要求数据是整数且范围 k 不大
- 桶排序：按映射分桶+桶内排序，平均 O(n+k)，要求分布均匀
- 基数排序：按位稳定排序，通常以计数排序为子程序，O(d·(n+k))≈O(n)，要求可按位拆分
- 计时排序：将所有数据的值视为倒计时，同一时间开始计时，知道所有倒计时归零，根据计时结束的先后顺序判断大小

它们都空间换时间（O(n+k) 额外内存）、且对数据有强假设（必须整数/可映射/分布均匀），所以泛型能力弱、最坏退化。
`std::sort` 不用它们是因为：泛型（只要 `operator<`）、原地（O(log n) 栈空间）、最坏稳定 n log n（Introsort）。
详细原理见 [[#非比较排序算法详解]]。
**知识点讲解：**

| 算法 | 时间 | 空间 | 适用 | 局限 |
|------|------|------|------|------|
| 计数排序 | O(n+k) | O(n+k) | 整数、k 不大 | k>>n 时退化 |
| 桶排序 | 均 O(n+k) | O(n+k) | 分布均匀 | 分布不均退化 |
| 基数排序 | O(d·(n+k)) | O(n+k) | 可按位拆分 | 需稳定子程序 |

> [!Info] 可能的追问:
> - Q: std::sort 用的是什么算法？
> - A: Introsort（内省排序）：正常用快排，递归深度超 2log n 时切到堆排防最坏 O(n²)，元素数 <16 时切插入排序（小数组常数低）。最坏 O(n log n)、平均 O(n log n)、原地。
> - Q: 基数排序为什么必须用稳定排序做子程序？
> - A: 基数排序从低位到高位排，高位排序时若不稳定，相同高位的元素会打乱低位已排好的相对顺序，导致整体错误。稳定性是基数排序正确性的前提。

### 对 weak_ptr 有什么理解？
**回答话术：**
weak_ptr 是 shared_ptr 的非拥有（弱）引用，不增加引用计数，访问前必须 `lock()` 提升为 shared_ptr（提升失败说明对象已销毁，返回空）。
三大用途：
1. 打断 shared_ptr 循环引用--环上的 shared_ptr 计数永远到不了 0 导致泄漏，把环中一条改成 weak_ptr 即可
2. 表达临时所有权--对象随时可能被别人销毁，需要用时才提升 shared_ptr 延长生命周期，用完释放
3. 观察者/缓存场景--持有弱引用避免阻止对象析构

weak_ptr 依赖 shared_ptr 的控制块（存放强引用计数和弱计数），weak_ptr 增加的是弱计数，弱计数>0 时控制块不释放，所以即使对象已析构，weak_ptr 仍能安全 lock（返回空）而不悬空。
**知识点讲解：**
```cpp
auto sp = std::make_shared<int>(42);
std::weak_ptr<int> wp = sp;        // 不增引用计数
if (auto p = wp.lock()) {          // 原子地"检查存活+提升"
    use(*p);                       // 提升成功，对象仍存活
} else {
    // 对象已被销毁
}
sp.reset();                        // 强引用归零，对象析构
wp.lock();                         // 返回空 shared_ptr，不悬空
// 循环引用破解:
struct Node { std::shared_ptr<Node> next; std::weak_ptr<Node> prev; };
```
> [!Info] 可能的追问:
> - Q: weak_ptr 为什么不会悬空？控制块什么时候释放？
> - A: shared_ptr 的控制块同时存 strong count 和 weak count。对象在 strong count 归零时析构，但控制块在 weak count 也归零时才释放。所以 weak_ptr 只要还存在，控制块就活着，`lock()` 能安全检查 strong count 是否为 0 并返回空 shared_ptr，不会访问已释放内存。
> - Q: weak_ptr 能不能直接访问对象？
> - A: 不能，必须先 `lock()` 提升为 shared_ptr。直接访问的话访问期间对象可能被其他线程析构，造成 data race。lock 是原子的"检查存活+提升"，提升成功就持有一份引用，对象在该 shared_ptr 存活期不会被析构。
> - Q: make_shared 和 new+shared_ptr 在 weak_ptr 场景下有区别吗？
> - A: `make_shared` 把对象和控制块分配在同一块内存，对象析构后内存要等所有 weak_ptr 销毁（weak count 归零）才释放--大对象+长寿命 weak_ptr 会延迟释放内存。`shared_ptr<T>(new T)` 是两次分配，对象析构立即释放对象内存，控制块单独等 weak。大对象+弱引用多场景要权衡。

### 对虚拟内存的理解
**回答话术：**
虚拟内存是操作系统为每个进程提供的独立、连续、规整的虚拟地址空间，核心价值三点：
1. 按需换页--基于局部性原理，只把活跃页加载进物理内存，不活跃页换出到 swap，使进程可用内存远超物理内存
2. 地址隔离--每个进程有独立页表，虚拟地址经页表翻译成物理地址，进程无法访问他人页表，杜绝跨进程地址冲突和越界
3. 权限保护--页表项除物理地址外还有读写执行、存在位、脏位等标记，硬件 MMU 翻译时检查，违规触发缺页/段错误

本质是"虚拟地址空间 + 页表 + MMU + 换页"的一套机制，把磁盘当物理内存的延伸。
深入到内核空间、线程地址空间、段含义见 [[#虚拟内存深入：内核空间、线程与内存分区]]。
> [!Info] 可能的追问:
> - Q: 为什么每个进程的地址空间里都有一块内核空间？
> - A: 详见 [[#虚拟内存深入：内核空间、线程与内存分区]]。简言之：进程进入内核态（系统调用、中断）时 CPU 切换到内核栈执行内核代码，把内核映射进每个进程的高地址区可避免切换进程时重换页表基地址，只需切换用户态部分。内核空间在所有进程的虚拟地址里映射到同一片物理页，是"共享"而非"每进程一份"。
> - Q: 每个线程有独立的地址空间吗？线程堆栈指的是什么？
> - A: 线程不拥有独立地址空间--同进程线程共享同一虚拟地址空间（同一份页表）、共享 .text/.data/堆/全局变量。线程私有的是：线程栈（在共享地址空间内划一段，默认 8MB）、线程局部存储 TLS、寄存器上下文。"线程堆栈"就是这块私有栈区，不是独立的地址空间。
> - Q: .text 代码段存放的"代码"是什么？是机器指令吗？
> - A: 是机器指令（CPU 直接执行的二进制）。.text 段是编译后的可执行指令序列，通常只读+可执行（防代码被篡改）。调试信息、符号表不在 .text 里（在 .debug/.symtab 等独立段）。
> - Q: 符号表存放在内存分区模型的什么位置？
> - A: 符号表不在进程运行时内存分区的常规段（.text/.data/.bss/堆/栈）里。它是 ELF 文件的一个 section（.symtab 静态符号表、.dynsym 动态符号表），加载到内存时默认不映射（运行时用不到）。调试器通过单独读取 ELF 文件的 .symtab/.debug 段获取符号信息。所以"符号表在内存分区里"这个说法不成立--它是文件结构，不是运行时内存段。

### C++11 新特性都有什么？谈谈你对他们的理解
**回答话术：**
- 语法糖和规范性上的特性有: 自动类型推断（auto），范围 for 循环，nullptr/nullopt 代替 NULL，-1 等可能引起类型转化的特殊值，{}初始化列表，强类型枚举
- 更方便的构造函数: 允许=default 和=delete 声明构造函数，引入拷贝/移动构造运算符函数
- **移动语义和右值引用**：通过引入右值引用（&&）和移动构造函数，避免默认值传递的参数传入行为而改为手动调整
- **智能指针**：引入智能指针，避免内存泄漏和悬挂指针等问题。
- **Lambda 表达式和 functional 库**：更方便地使用函数对象
- **多线程和异步支持**：thread/mutex多线程支持库，future/promise 支持异步原语
- **泛型编程优化**：constexpr 关键字，允许在编译时计算表达式
> [!Info] 可能的追问:
> - Q: 移动语义为什么不能让所有拷贝都自动变成移动？
> - A: 移动必须满足
> 	- 显式触发（`std::move` 或传入的参数本身为将亡值）
> 	- 类型有移动构造函数。编译器不会自动把 `T b = a;` 优化成移动
> 	- 参数为非 const 对象，因为移动要修改源，按值传参时 const T& 形参会阻止移动。
> - Q: constexpr 和 const 的区别？
> - A: constexpr 是编译期求值，const 只是运行期不可改。C++11 的 constexpr 函数只能有单条 return
> - Q: lambda 的本质是什么？和仿函数什么关系？
> - A: lambda 是仿函数的语法糖--编译器为每个 lambda 生成唯一闭包类，捕获列表变成类成员，lambda 体变成 `operator()`。无捕获 lambda 可转函数指针。所以 `[](int x){return x;}` 等价于一个含 `int operator()(int) const` 的匿名类。
> - Q: `new classname(args)` 调用的是构造函数还是 `operator()`？
> - A: **构造函数**，永远不可能是 `operator()`。`new` 表达式是两步：1) 调用 `operator new` 分配原始内存；2) 在这块内存上调用构造函数。`classname(args)` 本身是构造临时对象，也调用构造函数。只有当对象已存在、对它使用 `()` 时才触发 `operator()`。
> ```cpp
> Adder a(10);       // 构造函数
> int r = a(5);      // operator()
> Adder(10)(5);      // 先构造临时对象（构造函数），再对临时对象调 operator()
> // new Adder(10)   // 只调用构造函数，不可能调 operator()
> ```

### auto 推导和 decltype 推导有什么区别？
**回答话术：**
`auto` 按"值传递初始化"推导：忽略顶层 cv 修饰符和引用，`auto a = rx;`（rx 是 const int&）推导出 int 而非 const int。要保留 const/引用需显式写 `const auto&`。
`decltype(expr)` 按"表达式确切类型"推导：完整保留 const 和引用，且能区分左值/右值表达式：
- `decltype((x))`（带括号）推导出引用（因为 `(x)` 是左值表达式）
- `decltype(x)` 推导出 x 的声明类型

所以 auto 适合"我要一个局部变量存这个值"的简化，decltype 适合"我要精确返回这个表达式的类型"（模板返回类型 `auto f() -> decltype(expr)` 或 C++14 `decltype(auto)`）。推导规则细节见 [[#auto 与 decltype 推导规则]]。
> [!Info] 可能的追问:
> - Q: decltype((x)) 为什么是引用？
> - A: C++ 规定 decltype 对"带括号的标识符"按左值表达式处理，左值表达式加引用。所以 `decltype(x)` 是 x 的声明类型（int），`decltype((x))` 是 `(x)` 这个左值表达式的类型（int&）。这是著名的坑，写 `decltype(auto) f() { return (x); }` 会返回引用而非值。
> - Q: auto 推导和模板参数推导一样吗？
> - A: 几乎一样，auto 推导就是模板参数推导的语法糖。唯一区别：`auto x{1,2,3};` 曾推 `std::initializer_list`，但模板参数推导不会自动认 initializer_list。C++17 后 `auto x{1};` 推 int（单元素），`auto x{1,2};` 才报错。
> - Q: 什么时候用 auto 什么时候用 decltype？
> - A: 局部变量简化用 auto（`auto it = m.begin();`）；需要精确类型（保留引用/const，或转发返回类型）用 decltype。C++14 的 `decltype(auto)` 用于函数返回类型完美转发，避免 auto 丢掉引用。

### 谈谈 Linux 环境下 C++程序崩溃应该怎么定义问题
**回答话术：**
分三步定位：
1. 看现象--程序输出/日志粗略定位，配合 core dump 精细定位。开启 core dump（`ulimit -c unlimited`）后崩溃生成 core 文件，`gdb ./a.out core` 然后 `bt` 看调用栈精确到崩溃行
2. gdb 调试--稳定复现的崩溃用 `-g -O0` 编译，`gdb ./a.out` -> `run` -> 崩溃时自动停在位置，`bt`/`frame N`/`print var` 查现场
3. 静态/动态工具--cppcheck 静态扫常见缺陷，valgrind/AddressSanitizer（`-fsanitize=address`）动态查内存问题（泄漏、越界、use-after-free）。ASan 比 valgrind 快一个数量级，是现代 C++ 首选

先确认崩溃类型（段错误/abort/未捕获异常），再选对应手段。
> [!Info] 可能的追问:
> - Q: 没有 core 文件怎么排查？
> - A: 
> 1) 确认 `ulimit -c` 是否 unlimited、core_pattern 是否被 systemd-coredump 接管；
> 2) 用 ASan 重编，崩溃时直接打印栈和内存上下文，不依赖 core；
> 3) 看系统日志 `/var/log/syslog` 或 `dmesg` 找段错误记录；4) 在可疑处加日志缩小范围。

### MySQL 中有长连接和短连接，他们是什么？
**回答话术：**
- **短连接**：每次执行完 SQL 就断开连接，下次再连。省资源但频繁建立/销毁连接开销大（TCP 握手 + 认证）
- **长连接**：建立后长期保持复用，减少连接建立开销，是生产环境主流

**注意**：长连接使用久后内存占用持续增长（每个连接维护会话状态：临时表、排序缓冲、变量等），MySQL 8 小时空闲会自动断开（wait_timeout）。
> [!Info] 可能的追问:
> - Q: 如何解决长连接过多占用内存高问题？
> - A: 1) **定期重置连接**：调用 `mysql_reset_connection()` 释放连接占用的内存（清空临时表、变量、缓存），**不需要断开重连**，最推荐；2) 定期断开重连；3) 控制最大连接数 `max_connections`；4) 用连接池复用 + 池内定期重置。
> - Q: `mysql_reset_connection` 在做什么？有什么用？
> - A: 重置连接会话状态：清除临时表、回滚未提交事务、重置用户变量/会话变量、清空 Prepared Statement 缓存，但**保留已认证的登录状态和连接本身**。作用：解决长连接内存累积问题，比"断开重连"开销小（省去 TCP 握手 + 认证），是 MySQL 官方推荐的长连接内存治理方案。

### 如果添加 explain 关键字，sql 会返回的表中，各个字段代表了什么意思？
**回答话术：**
`EXPLAIN` 显示查询执行计划，关键字段：
- `id`：查询中 select 的执行顺序（id 越大越先执行，id 相同从上到下）
- `select_type`：查询类型（SIMPLE 简单查询 / PRIMARY 最外层 / SUBQUERY 子查询 / DERIVED 派生表）
- `table`：操作的表
- `type`：**访问类型，性能关键**——`ALL`（全表扫描，最差）< `index`（全索引扫描）< `range`（范围）< `ref`（非唯一索引等值）< `eq_ref`（唯一索引等值）< `const`（主键/唯一等值，最优）
- `possible_keys`：可能用到的索引
- `key`：实际使用的索引
- `key_len`：使用的索引长度（越短越优，太长说明用了复合索引后几列）
- `ref`：索引匹配的列/常量
- `rows`：预估扫描行数（越小越好）
- `filtered`：过滤后剩余比例
- `Extra`：额外信息——`Using index`（覆盖索引，优）、`Using filesort`（额外排序，慢）、`Using temporary`（临时表，慢）、`Using where`

**知识点讲解：**
```sql
EXPLAIN SELECT * FROM user WHERE age > 18 ORDER BY id DESC;
-- 关注 type（ALL 就要优化）、rows（预估行数）、Extra（filesort/temporary 要避免）
```
> [!Info] 可能的追问:
> - Q: type 从快到慢的顺序？
> - A: `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。目标至少到 `range`，`ALL`（全表扫描）是优化重点。索引失效（函数、隐式类型转换、前导通配符 %）会让 type 退化到 ALL。
> - Q: Extra 中哪些信号需要优化？
> - A: `Using filesort`（排序没用上索引，加排序字段索引）、`Using temporary`（临时表，优化 group by/去重）、`Using index` 是好的（覆盖索引避免回表）。

### MySQL 架构的 Server 层的执行过程？
**回答话术：**
MySQL 分 **Server 层** 和 **存储引擎层**：
- Server 层：连接管理、查询缓存（8.0 移除）、解析、优化、执行、权限、日志
- 存储引擎层：负责数据存储/索引/事务（InnoDB/MyISAM 等，可插拔）

**Server 层执行流程**：
1. **连接器**：验证身份、分配权限、管理连接
2. **查询缓存**：命中直接返回（8.0 移除，因表更新即失效，维护成本高）
3. **分析器**：词法/语法分析，生成语法树，校验语法
4. **优化器**：选索引、决定表连接顺序，生成**执行计划**
5. **执行器**：按计划调用引擎接口取数，逐行处理（where/排序/聚合），返回结果
6. 日志：binlog（Server 层，逻辑日志）、redo/undo log（引擎层）

**知识点讲解：**
```text
连接器 -> 查询缓存(8.0删) -> 分析器(词法/语法) -> 优化器(执行计划) -> 执行器 -> 存储引擎
```
> [!Info] 可能的追问:
> - Q: 优化器生成的"执行方案"是什么？
> - A: 是 SQL 的执行计划：选哪个索引、表连接顺序、join 算法（NLJ/Hash Join）、是否用临时表/排序等。同一 SQL 多种执行路径，优化器按代价估算（行数、索引区分度）选最优。`EXPLAIN` 能查看它选的结果。执行方案不是固定的，数据分布/统计信息变化会改变。
> - Q: 执行器和优化器区别？
> - A: 优化器**决定怎么做**（选执行计划），执行器**执行计划**（调用存储引擎 API 逐行取数、做过滤/排序/聚合）。优化器是决策，执行器是落地。

### 常用存储引擎？InnoDB 与 MyISAM 的区别？
**回答话术：**
**InnoDB**（默认，推荐）：
- 支持事务（ACID）、行级锁、外键
- 聚簇索引（主键索引即数据，B+树叶子存完整行）
- 支持 MVCC（多版本并发控制）
- 崩溃恢复（redo log）

**MyISAM**（旧默认）：
- 不支持事务、不支持行锁（表级锁）、无外键
- 非聚簇索引（索引和数据分开存储）
- 支持全文索引（InnoDB 5.6 后也支持）
- 读快、写慢，适合读多写少

**核心区别**：
| | InnoDB | MyISAM |
|--|--------|--------|
| 事务 | 支持 | 不支持 |
| 锁 | 行级锁 | 表级锁 |
| 外键 | 支持 | 不支持 |
| 索引 | 聚簇（数据在索引叶子） | 非聚簇（索引+数据分离） |
| 崩溃恢复 | 支持（redo log） | 不保证 |
| 全文索引 | 5.6+ 支持 | 支持 |
| 适用 | OLTP 事务型 | 读多写少/数据仓库 |

**知识点讲解：**
```sql
SHOW ENGINES;  -- 查看可用引擎
CREATE TABLE t (...) ENGINE=InnoDB;  -- 指定引擎
```
> [!Info] 可能的追问:
> - Q: 为什么 InnoDB 主键索引叶子存整行（聚簇索引）？
> - A: 聚簇索引按主键排序组织数据，主键查询一次 B+树就能拿到整行（无需回表），顺序主键插入高效。代价是二级索引叶子存主键值，非主键查询要"回表"（先查二级索引得主键，再查主键索引得数据）。所以 InnoDB 必须要有主键（无则隐式生成），且主键最好有序（自增）。

### 事务的 ACID 与实现原理？
**回答话术：**
ACID 四特性 + 实现机制：
- **原子性（Atomicity）**：事务要么全成功要么全回滚。实现：**undo log**（记录回滚前的数据，回滚时恢复）
- **一致性（Consistency）**：事务前后数据完整约束不被破坏。由原子性+隔离性+约束共同保证
- **隔离性（Isolation）**：事务间互不干扰。实现：**锁 + MVCC**（多版本并发控制）
- **持久性（Durability）**：提交后数据不丢失。实现：**redo log**（先写日志，崩溃后重放恢复）+ buffer pool 双写

**核心机制**：
- **redo log**：物理日志，记录修改，崩溃恢复用（WAL：先写日志后写磁盘）
- **undo log**：逻辑日志，回滚 + MVCC 版本链
- **MVCC**：读不加锁，通过版本链 + ReadView 实现快照读，提高并发
- **binlog**：Server 层逻辑日志，主从复制/数据恢复用（和 redo 是两个日志）

**知识点讲解：**
```text
原子性 <- undo log（回滚）
持久性 <- redo log（WAL 先写日志再落盘）
隔离性 <- 锁 + MVCC
一致性 <- 前三者 + 约束
```
> [!Info] 可能的追问:
> - Q: redo log 和 binlog 的区别？
> - A: redo log 是 InnoDB 引擎层的**物理日志**（记录页的修改），循环写，用于崩溃恢复；binlog 是 Server 层的**逻辑日志**（记录 SQL/行变更），追加写，用于主从复制和数据恢复。事务提交要"两阶段提交"协调两者保证一致性。
> - Q: 隔离级别和 MVCC 的关系？
> - A: MVCC 实现读已提交（RC）和可重复读（RR）两个隔离级别的快照读。RC 每次读生成新 ReadView（能看到已提交的最新），RR 事务内用同一个 ReadView（保证重复读一致）。串行化靠锁不用 MVCC。

### 数据库中的锁机制？
**回答话术：**
按**粒度**分：
- **表级锁**：锁整个表，简单但并发差（MyISAM）
- **行级锁**：锁一行，并发高但开销大（InnoDB）
- 页级锁：锁一个页（MySQL 不常用）

按**类型**分：
- **共享锁 S**（读锁）：可共享读，禁止写
- **排他锁 X**（写锁）：独占，读写都禁止
- **意向锁**（IS/IX）：表级标记，表示事务要/已在行上加 S/X 锁，用于快速判断表是否能加表级锁

**InnoDB 行锁实现**：基于**索引**加锁（锁的是索引记录）。无索引的 where 会退化成表锁（全表扫描逐行加锁）。还支持间隙锁（Gap Lock）和 next-key lock（记录+间隙）解决幻读。

**知识点讲解：**
```sql
-- 共享锁/排他锁
SELECT * FROM t WHERE id=1 LOCK IN SHARE MODE;   -- S 锁
SELECT * FROM t WHERE id=1 FOR UPDATE;            -- X 锁
```
> [!Info] 可能的追问:
> - Q: 什么是间隙锁和 next-key lock？
> - A: 间隙锁锁一个范围（记录之间），防止其他事务在范围内插入（防幻读）。next-key lock = 记录锁 + 间隙锁，是 InnoDB RR 隔离级别下防幻读的默认手段。范围条件会锁范围，所以大范围更新容易死锁。
> - Q: 如何减少锁竞争/死锁？
> - A: 1) 尽量走索引（缩小锁范围）；2) 事务保持短小（快提交快释放）；3) 固定操作顺序；4) 合理隔离级别（RC 比 RR 锁少）；5) 控制范围更新（limit 分批）。

### MySQL 索引的实现原理？
**回答话术：**
MySQL 默认索引是 **B+树**。为什么选 B+树：
- **矮胖**：每节点多叉（扇出大），树高矮（几百万数据 3-4 层），**磁盘 I/O 次数少**（每层一次 I/O）
- **叶子节点有序链表**：范围查询/排序高效（顺序扫描）
- **数据都在叶子**：非叶子只存索引键，节点可容纳更多键，扇出更大；查询路径稳定

对比：B 树所有节点存数据（范围查询需中序遍历回溯），二叉树太高（I/O 多）。内存场景（红黑树/哈希）适合，磁盘场景 B+ 树最优。

**聚簇 vs 非聚簇索引**（InnoDB）：
- **聚簇索引**（主键）：叶子存整行数据，主键查询免回表
- **二级索引**：叶子存主键值，查询需回表（先二级索引得主键，再回表查数据）
- **覆盖索引**：查询列都在索引里，免回表（Extra 显示 Using index）

**知识点讲解：**
```text
B+树结构：
        [键1][键2][键3]        <- 非叶子（只存键）
       /    |    \    \
   [叶子][叶子][叶子][叶子]    <- 叶子存数据/主键，双向链表串联
```
> [!Info] 可能的追问:
> - Q: 为什么索引要建在常用 where/order by/join 列上？
> - A: 索引本质是"排好序的查找结构"。建在 where 条件列能避免全表扫描（type 从 ALL 变 range/ref）；建在 order by 列避免 filesort；建在 join 关联列加速连接。但索引有维护成本（写入要更新索引），不是越多越好。
> - Q: 什么情况下索引会失效？
> - A: 1) 对索引列用函数/运算（`WHERE YEAR(create_time)=2024`）；2) 隐式类型转换（字符串列传数字）；3) 前导通配符（`LIKE '%abc'`）；4) 复合索引违反最左前缀；5) OR 连接非索引条件；6) 优化器判断全表扫描更快（数据量小/区分度低）。

### 索引为什么要使用 B+树而不是二叉树或 B 树？
**回答话术：**
核心是**磁盘 I/O 优化**：
- **二叉树**：树高 = O(log2 n)，100 万数据要 20 层，每次下探一次磁盘 I/O，太慢
- **B 树**：多叉，但非叶子节点也存数据，每节点能存的键少，扇出小，且范围查询要回溯中序遍历
- **B+树**：非叶子只存键（扇出大，树矮），叶子有序链表（范围/排序高效），数据都在叶子（查询路径稳定）

结论：B+树**树矮（I/O 少）+ 范围查询高效 + 顺序扫描快**，最适合磁盘数据库索引。
**知识点讲解：**
```text
B+树：3 层可存约 2000*2000*2000=80 亿条（每节点约 2000 键，扇出大）
二叉树：80 亿需 log2(8e9)≈33 层，33 次磁盘 I/O
```
> [!Info] 可能的追问:
> - Q: 为什么非叶子节点不存数据（B 树 vs B+树）？
> - A: 叶子存数据 vs 非叶子存数据，影响每节点能容纳的**键数量（扇出）**。B+ 树非叶子只存键，同样 16KB 页能存更多键 -> 树更矮 -> 磁盘 I/O 更少。且数据集中在叶子让范围查询走叶子链表顺序扫描，比 B 树回溯快。

### SQL 优化、索引优化、表结构优化？
**回答话术：**
**SQL 优化**：
- 避免 `SELECT *`（只取所需列）
- 避免函数/运算在索引列上（索引失效）
- 避免 `LIKE '%xx'` 前导通配符
- 避免大表子查询，用 JOIN；避免 `OR` 用 `IN`/`UNION`
- 分页深翻页优化（`LIMIT 100000,10` 慢，用游标/子查询优化）

**索引优化**：
- 建在 where/order by/join 列
- 复合索引遵循**最左前缀**（`(a,b,c)` 支持 a、a,b、a,b,c）
- 避免冗余索引（`(a,b)` 已含 a 的效果）
- 区分度高的列优先（性别这种低区分度建索引收益低）

**表结构优化**：
- 选择合适数据类型（int 比 varchar 好，datetime 比字符串好）
- 避免过度 TEXT/BLOB（过大占用磁盘 I/O）
- 避免 NULL（索引效率/存储）
- 拆分大表（垂直拆列/水平拆行/分库分表）

**知识点讲解：**
```sql
-- 最左前缀
INDEX idx(a,b,c)  -- WHERE a=?  ✓  WHERE a=? AND b=?  ✓  WHERE b=?  ✗（未用最左）
-- 覆盖索引
SELECT a,b FROM t WHERE a=1;  -- 若 (a,b) 建索引，Using index 免回表
```
> [!Info] 可能的追问:
> - Q: 如何定位慢 SQL？
> - A: 慢查询日志（slow_query_log）记录超阈值 SQL；`EXPLAIN` 分析执行计划（看 type/rows/Extra）；`SHOW PROFILE`/`performance_schema` 看耗时分布。先 EXPLAIN 找全表扫描/filesort/temporary，再针对性加索引或改写。
> - Q: 深分页为什么慢？怎么优化？
> - A: `LIMIT 100000,10` 要扫描前 10 万行再丢弃。优化：1) 用上一页最后 id 做条件（`WHERE id > 上次id LIMIT 10`，走索引）；2) 延迟关联（先查 id 子查询再 join）；3) 基于游标分页。

### MySQL 的主从复制？
**回答话术：**
主从复制：一个主库（写）+ 多个从库（读），从库复制主库数据。
**原理**：
1. 主库写操作记录到 **binlog**（二进制日志）
2. 从库的 **IO 线程**连接主库，拉取 binlog 写入从库的 **relay log**（中继日志）
3. 从库的 **SQL 线程**读取 relay log 重放到本地，实现数据同步

**注意**：复制是**异步**的（主库提交不等待从库），有延迟；从库是只读的。
**应用**：读写分离、数据备份、容灾、负载均衡。
**知识点讲解：**
```text
主库(master) --binlog--> 从库IO线程 --relay log--> 从库SQL线程 --重放--> 从库数据
```
> [!Info] 可能的追问:
> - Q: 主从复制有哪些模式？
> - A: 1) 异步复制（默认，主库不等待从库）；2) 半同步复制（主库等至少一个从库确认）；3) 组复制/GTID（全局事务标识，主从一致性强）。异步延迟可能数据丢失，强一致场景用半同步/GTID。
> - Q: 主从延迟如何解决/检测？
> - A: 检测 `SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`。解决：1) 半同步复制；2) 读不到就等/读主库（关键业务强制主库读）；3) 从库硬件/配置优化；4) 减少主库写入压力。延迟是无法彻底消除的，通过架构（读写分离 + 缓存）缓解。

### 读写分离？
**回答话术：**
读写分离：**写操作走主库，读操作走从库**，降低主库读压力。
**实现**：
- 应用层：代码判断读写，路由到不同数据源（或通过代理/中间件如 MyCat、ShardingSphere）
- 配合主从复制（从库从主库同步数据）

**优点**：主库专注写（写入性能好）、读能力水平扩展（加从库）、主库故障读仍可用
**缺点**：**数据延迟**（主从异步，读到旧数据）、配置复杂、写仍单点
**知识点讲解：**
```text
写: 应用 -> 主库(master)
读: 应用 -> 从库1/从库2/... (只读，从主库复制)
```
> [!Info] 可能的追问:
> - Q: 主从延迟导致读不到刚写的数据怎么办？
> - A: 1) **关键数据强制主库读**（写后紧跟读走主库，如登录后立刻查用户信息）；2) 引入缓存（写主库同时更新缓存，读优先缓存）；3) 半同步复制缩短延迟；4) 接受最终一致（非关键业务）。原则：对一致性要求高的读，绕过从库。

### 分库分表（垂直分表、垂直分库、水平分表、水平分库）？
**回答话术：**
四种拆分方式：
- **垂直分表**：一张表按列拆多张（大字段单独放），减少单表宽度
- **垂直分库**：不同业务放不同库（订单库/用户库/商品库），按业务隔离
- **水平分表**：同一张表按行拆分（按 id 取模/范围）到多个表，单表数据量下降
- **水平分库**：数据按规则（hash/范围）分布到多个库，解决单库容量/连接压力

**核心问题**：水平拆分后的**路由**（怎么定位数据在哪个表/库）、**全局唯一 id**、**跨分片查询/join/事务**。
**知识点讲解：**
```text
水平分表：user_0 / user_1 / user_2 ...（按 user_id % N 路由）
全局id：雪花算法（Snowflake）/号段模式，不能自增（各分片会冲突）
```
> [!Info] 可能的追问:
> - Q: 什么时候需要分库分表？
> - A: 单表数据量过大（千万级以上）导致 B+树深度增加/索引维护/写入变慢，或单库连接数/IO 成为瓶颈。先考虑：索引优化、缓存、读写分离、冷热分离，最后才是分库分表（复杂度最高）。
> - Q: 分片键怎么选？分片后怎么查非分片键条件？
> - A: 选高频等值查询且分布均匀的列（如 user_id/order_id）。非分片键查询：1) 广播查询所有分片合并；2) 建立映射表（非分片键->分片键）；3) 冗余一份按另一键分片的表（ES 等）。没有银弹，按业务选。

### 数据分区是什么？
**回答话术：**
分区（Partition）是**表内**的逻辑拆分：一张表的数据按规则存到多个物理分区文件，但逻辑上仍是**一张表**（对应用透明）。
分区类型：
- **范围分区**：按范围（如时间/价格）`PARTITION BY RANGE`
- **列表分区**：按值列表
- **哈希分区**：按 hash 均匀分布
- **键分区**：类似 hash 但基于列
- 复合分区

**优点**：单个分区数据量小（查询只扫相关分区）、旧数据可 drop 分区删除、分区级归档
**缺点**：分区键查询才有效、跨分区查询/唯一索引限制
**知识点讲解：**
```sql
CREATE TABLE t (
    id INT, created DATE
) PARTITION BY RANGE (YEAR(created)) (
    PARTITION p0 VALUES LESS THAN (2023),
    PARTITION p1 VALUES LESS THAN (2024),
    PARTITION p2 VALUES LESS THAN MAXVALUE
);
-- 查询条件带分区键时只扫对应分区（分区裁剪）
```
> [!Info] 可能的追问:
> - Q: 分区和分表区别？
> - A: 分区是**单库内一张表的物理拆分**（对应用透明，连接管理简单），分表是**拆成多张逻辑表**（应用需感知路由）。分区适合单库能放下但单表太大、需要按时间归档删除的场景；分表用于数据量超出单库能力/多库分布。分区无法解决单库连接数瓶颈。

### 主键一般用自增 ID 还是 UUID？
**回答话术：**
**自增 ID**：
- 优点：有序（B+树插入高效，叶子顺序追加不用页分裂）、存储小（int 4 字节/bigint 8 字节）、查询快
- 缺点：分布式下冲突、可预测（安全/竞品分析）、迁移合并麻烦

**UUID**：
- 优点：全局唯一（分布式友好）、不可预测
- 缺点：**无序**（B+树随机插入导致页分裂，性能差）、存储大（36 字符/varchar 或二进制 16 字节）

**结论**：单机/MySQL 环境用**自增**；分布式、需要全局唯一用 **雪花算法**（Snowflake：时间戳+机器号+序号，**有序且全局唯一**）或号段模式，不用原生 UUID。

**知识点讲解：**
```text
雪花算法 64 位：
[时间戳41位][机器ID10位][序列号12位] -> 单调递增、全局唯一
比 UUID 好在：有序（索引友好）、长度短（bigint 8字节）
```
> [!Info] 可能的追问:
> - Q: 为什么自增主键对 InnoDB 聚簇索引好？
> - A: InnoDB 聚簇索引按主键排序存数据，自增主键新记录追加到 B+树最右叶子，无需页分裂（高效）。UUID 随机，插入落在任意位置，频繁页分裂 + 移动数据，性能下降。这是"有序主键 vs 无序主键"的本质区别。
> - Q: 分库分表后怎么生成全局唯一主键？
> - A: 自增会冲突（各分片都从 1 开始）。方案：1) 雪花算法（有序全局唯一，主流）；2) 号段模式（从中心取一段 id，如 Redis/DB 发号）；3) UUID（但索引差）。生产常用雪花/号段。

### 视图 View？
**回答话术：**
视图是一张**虚拟表**，本身不存数据，本质是**保存的 SELECT 查询**。查询视图时实时执行底层 SQL 取数。
**优点**：
- 简化复杂查询（封装多表 join）
- 数据安全（只暴露需要的列，隐藏敏感字段/表结构）
- 逻辑独立（底层表结构变化，视图可保持不变）

**注意**：视图不存储数据，更新视图实质更新底层表（有限制）；频繁查询的复杂视图仍要每次都执行，可能慢。

**知识点讲解：**
```sql
CREATE VIEW user_orders AS
SELECT u.name, o.amount FROM user u JOIN orders o ON u.id = o.user_id;
SELECT * FROM user_orders WHERE amount > 100;  -- 像表一样查
```
> [!Info] 可能的追问:
> - Q: 视图和临时表区别？
> - A: 视图是**永久保存的 SQL 定义**（虚拟，每次查询时执行，不占存储），临时表是**实际存数据的表**（会话结束/手动 drop 删除，占存储）。视图适合复用查询逻辑/权限控制，临时表适合中间计算。
> - Q: 视图能提高查询性能吗？
> - A: 一般不能——视图不缓存结果，每次查询都执行底层 SQL（除非物化视图，MySQL 不支持）。视图的主要价值是**复用 + 权限 + 抽象**，不是性能。性能问题仍要从索引/查询本身优化。

### 存储过程 procedure？
**回答话术：**
存储过程是**预编译的 SQL 程序**，封装一组 SQL 逻辑，可带参数、流程控制、异常处理，保存在数据库端。
**优点**：
- 减少网络开销（一次调用执行多语句）
- 预编译执行更快
- 封装业务逻辑，复用性好
- 权限控制（只给执行权限不给表权限）

**缺点**：
- 调试难、版本管理难、可移植性差（绑定具体数据库）
- 逻辑在数据库端，应用层难维护/测试
- 可能掩盖 SQL 问题

**现代实践**：简单 CRUD 不用存储过程（用 ORM/应用层逻辑，易测试维护）；复杂批处理/数据密集操作才考虑。
**知识点讲解：**
```sql
DELIMITER //
CREATE PROCEDURE get_user(IN uid INT, OUT uname VARCHAR(50))
BEGIN
    SELECT name INTO uname FROM user WHERE id = uid;
END //
DELIMITER ;
CALL get_user(1, @name);
```
> [!Info] 可能的追问:
> - Q: 存储过程和触发器、视图的区别？
> - A: 存储过程是**手动调用**的程序；触发器是**事件触发**自动执行（表 insert/update/delete 时）；视图是**虚拟表**（封装查询）。存储过程主动调用，触发器被动触发，视图是查询抽象。

### 触发器 Trigger？
**回答话术：**
触发器是绑定在表上的**自动执行**的存储过程，在表的 INSERT/UPDATE/DELETE 操作**之前或之后**自动触发。
**用途**：数据约束/校验、审计日志、数据同步、级联更新。
**缺点**：
- 隐式执行（应用层不知道，难排查）
- 性能开销（每次 DML 都执行）
- 调试/维护难
- 触发器里的操作可能引发连锁触发

**现代实践**：尽量少用，用应用层逻辑/数据库约束替代（可测试、可控）。
**知识点讲解：**
```sql
CREATE TRIGGER user_audit AFTER INSERT ON user
FOR EACH ROW
BEGIN
    INSERT INTO audit_log(action, user_id) VALUES ('INSERT', NEW.id);
END;
```
> [!Info] 可能的追问:
> - Q: 触发器、存储过程、事件（event）区别？
> - A: 触发器 = 表 DML 事件自动触发；存储过程 = 手动 CALL 调用；事件（event） = 定时任务自动执行（类似 cron，如定期清理/汇总）。三者都是数据库端逻辑，但触发时机不同。

### SQL 注入原理？如何避免 SQL 注入？
**回答话术：**
SQL 注入：把用户输入**直接拼接进 SQL**，攻击者通过特殊输入改变 SQL 语义，窃取/篡改数据。
```sql
-- 注入示例：用户输入 ' OR '1'='1
SELECT * FROM user WHERE name = '' OR '1'='1';  -- 恒真，返回全部
-- 更严重：'; DROP TABLE user; -- 拼接执行删除
```
**防范**：
1. **参数化查询（Prepared Statement）**：`?` 占位 + 绑定参数，数据库将输入当**数据**而非**SQL**处理，根治注入
2. 输入校验/白名单（类型、长度、格式）
3. 最小权限（应用账号只给必要权限）
4. 转义特殊字符（`mysql_real_escape_string`，仅兜底）

**知识点讲解：**
```cpp
// 错误：字符串拼接
QString sql = "SELECT * FROM user WHERE name='" + input + "'";
// 正确：参数化
QSqlQuery q;
q.prepare("SELECT * FROM user WHERE name=?");  // ? 占位
q.addBindValue(input);                          // 输入当数据绑定
q.exec();
```
> [!Info] 可能的追问:
> - Q: 为什么参数化能防注入？
> - A: 参数化后 SQL 结构在**预编译时确定**，用户输入作为参数值传入（数据库端转义/序列化），输入中的引号/关键字不会被解释为 SQL 语法。拼接式 SQL 把输入直接嵌入语句文本，结构随输入变化。这就是"数据 vs 代码"分离的核心。
## 计算机组成原理面试题
### CPU 内部组件都有什么？
**寄存器、控制单元和逻辑运算单元**等。其中，控制单元负责控制 CPU 工作，逻辑运算单元负责计算，而寄存器可以分为多种类，每种寄存器的功能又不尽相同。
- _通用寄存器_，用来存放需要进行运算的数据，比如需要进行加和运算的两个数据。
- _程序计数器_，用来存储 CPU 要执行下一条指令「所在的内存地址」，注意不是存储了下一条要执行的指令，此时指令还在内存中，程序计数器只是存储了下一条指令「的地址」。
- _指令寄存器_，用来存放当前正在执行的指令，也就是指令本身，指令被执行完成之前，指令都存储在这里

## C++专题
### 什么是多态？意义是什么？
**回答话术：**
多态通俗讲就是‘一个接口，多种表现’。它是让程序能根据‘对象的实际类型’来决定执行哪段代码的机制。
多态的核心意义是**接口与实现分离**，让调用方通过统一接口操作不同类型的对象，而不依赖具体类型。分为：
- **静态多态**（编译期）：模板、重载、CRTP，零运行时开销但代码膨胀
- **动态多态**（运行期）：虚函数，通过 vtable 间接调用，灵活但多一次跳转
- 一些设计模式上的多态，参考 [[C++ Runoob Tutoral#C++的多态形式]]
从 CPU 指令层面上分析静态/动态多态性能差异:
相比普通函数（直接 `call` 地址），虚函数调用需要 ：
1. **流水线停顿**：虚函数是**间接跳转**。CPU 的分支预测器，难以精准预测间接跳转的目标地址，一旦预测失败，会导致流水线排空，造成数十个时钟周期的延迟。
2. **缓存不友好**：vtable 存储在数据段，vptr 在对象堆内存中，函数代码在代码段。调用虚函数涉及多次非连续内存读取
3. **阻碍编译器优化**：由于目标函数地址在运行期才确定，编译器无法跨函数进行常量折叠、死代码消除等激进优化。

**一句话总结**：C++ 通过 **vptr + vtable** 实现运行时多态；其核心开销不在于几次内存寻址，而在于**间接跳转导致的 CPU 分支预测失败**以及**无法进行编译器内联优化**。

> [!Info] 可能的追问:
> - Q: 静态多态和动态多态怎么选？
> - A: 性能敏感、类型在编译期确定的场景用静态多态（模板/CRTP）；需要运行时灵活切换、类型在运行期才能确定的场景用动态多态（虚函数）。静态多态零开销但类型是编译期绑定的，动态多态有 vtable 间接开销但可以在运行时改变行为。
### 栈内存分配和堆内存分配在 C++中有什么区别？
- 管理方式
手动与自动管理，栈变量通过 RAII 和编译器保证生命周期，栈对象需要手动释放内存，忘记释放导致内存泄漏。
引出: 智能指针避免泄漏，ulimit 命令返回线程的栈大小，CPU 位数反映了虚拟内存大小（2 的 48/57 字节），线程栈和进程栈，进程堆和线程堆
- 空间大小与增长方向
引出内存模型（堆从低地址向高地址生长，**但不是线程栈的最低地址开始**）
- 分配效率
栈分配极快。仅涉及 CPU 指令对栈指针的移动。
堆：相对慢。需要操作系统在堆中寻找合适大小的空闲块，涉及复杂的分配算法和可能的系统调用。

### final 和 override 关键字的作用分别是什么？
override 是一个显式声明当前类是子类，要重写基类中的虚函数。底层编译器会在编译器进行类型检查和重写匹配，必须签名完全一致的函数才能接受重写，否则报错
final 修饰类用来显式声明禁止任何类继承当前类，修饰函数用来表示这个函数不支持再被重写
两者在编译器层面: 允许编译器进行更激进的优化。在工程层面防止一些不规范的操作导致预期之外的行为（比如继承链末端的类想要调用上游父类的方法，中游的类却误重写了不该被重写的方法导致调用了错误的实现）
### 多态产生的各种特性在实际工程中有哪些用途？
**回答话术：**
动态多态在实际工程中的典型应用：
1. **策略模式**：`std::sort` 的比较器，运行时决定排序规则
2. **工厂模式**：基类指针指向具体产品，客户端不依赖具体产品类
3. **模板方法模式**：基类定义算法骨架，派生类实现扩展点
4. **观察者模式**：Qt 信号槽的核心机制
5. **插件系统**：加载动态库后通过基类接口调用插件功能
**知识点讲解：**
```cpp
// 策略模式：std::sort 的比较器
std::sort(v.begin(), v.end(), [](int a, int b) { return a > b; });  // lambda 是仿函数语法糖
// 工厂模式
std::unique_ptr<Shape> createShape(const std::string& type) {
    if (type == "circle") return std::make_unique<Circle>();
    if (type == "rect")   return std::make_unique<Rect>();
    return nullptr;
}
```
> [!Info] 可能的追问:
> - Q: 多态在 Qt 信号槽中怎么体现？
> - A: 信号槽本质上是一对多的多态通知——信号发送者不关心谁在监听，槽函数接受者不关心谁在发送，通过 MOC 生成的元对象系统解耦。这是动态多态在事件驱动架构中的典型应用。

### 为什么需要虚函数？
**回答话术：**
没有虚函数时，基类指针/引用调用成员函数是**静态绑定**的，编译器根据指针的**静态类型**（声明类型）决定调用哪个函数，永远只会调用基类版本。
虚函数让 C++ 在运行期根据对象的**实际类型**（动态类型）决定调用哪个版本。这是运行时多态的基础设施。
```cpp
Base* p = new Derived();
p->func();     // 无 virtual：调 Base::func()（静态绑定）
               // 有 virtual：调 Derived::func()（动态绑定，走 vtable）
```
没有虚函数，面向对象设计中的"接口抽象、多态替换"就无法实现，C++ 就退化为带类的 C 语言。
**知识点讲解：**
虚函数的底层靠 vtable（虚函数表）实现：每个含虚函数的类有一张函数指针表，每个对象存一个 vptr 指向该表。调用时通过 vptr->vtable->函数指针找到正确实现。详见 [[#单/多继承虚函数表布局与覆盖]]。
> [!Info] 可能的追问:
> - Q: 静态绑定和动态绑定的区别？
> - A: 静态绑定在编译期根据静态类型确定函数地址，直接调用，零开销。动态绑定在运行期根据对象的 vptr 查虚表，通过函数指针间接调用，多一次内存跳转且编译器无法内联。性能上静态绑定更优，灵活性上动态绑定更优。
### 为什么类内指针成员的长度和普通指针长度不一样？
**回答话术：**
类内指针成员的长度和普通指针**没有不同**，在 64 位系统上都是 8 字节。你的困惑可能来自：
- 空类 sizeof 为 1（为区分不同对象地址，编译器插入 1 字节占位）
- 含虚函数的类多了 vptr（8 字节），但 vptr 不是指针成员，是编译器插入的隐藏成员
- 内存对齐导致 sizeof 看起来比"成员之和"大

所以"类内指针成员长度不同"是错觉——指针本身长度不变，变的是**类对象的总大小**。
**知识点讲解：**
```cpp
class Empty {};           // sizeof = 1（占位字节）
class WithVFunc {         // sizeof = 8（vptr 占 8 字节）
    virtual void f();
};
class WithPtr {           // sizeof = 8（64 位）
    int* p;
};
class Mixed {             // sizeof = 16（vptr 8 + int* 8，经对齐）
    virtual void f();
    int* p;
};
```
> [!Info] 可能的追问:
> - Q: 空类为什么有 1 字节？
> - A: 标准要求不同对象必须有不同地址。如果 sizeof 空类为 0，数组 `Empty arr[10]` 中所有元素地址相同，违反标准。所以编译器插入 1 字节占位。EBO（空基类优化）例外：空基类作为基类时可以不占 1 字节，这正是 `std::vector` 等用空分配器时的优化。

### 多态中指针的行为
**回答话术：**
- **基类指针指向子类对象**：允许，这是多态的基础。`Base* p = new Derived();` 编译器自动将 Derived* 转换为 Base*。意义：通过基类接口操作派生类对象，实现"对扩展开放、对修改封闭"。
- **子类指针指向基类对象**：**不允许**，编译器报错。因为基类对象不包含派生类成员，如果允许，子类指针访问不存在的成员会越界。强制转换（`Derived* p = (Derived*)base_ptr;`）可以编译通过，但若基类对象本身不是派生类实例，访问派生类成员是未定义行为。

```cpp
Base b;
Derived* p = (Derived*)&b;  // 强制转换可编译，但 p->derived_member 是 UB
Base* pb = new Derived();   // 安全，多态的基础
```
**知识点讲解：**
多态转换的安全检查用 `dynamic_cast`：`Derived* p = dynamic_cast<Derived*>(base_ptr);` 失败返回 nullptr。
> [!Info] 可能的追问:
> - Q: 为什么基类指针可以指向子类对象？编译器怎么做到的？
> - A: 派生类对象包含基类子对象（在对象头部），所以基类指针指向派生类对象头部时，访问的是基类子对象，完全合法。多继承时编译器需要调整指针偏移指向正确的基类子对象，详见 [[#单/多继承虚函数表布局与覆盖]] 中的 this 调整与 thunk 部分。

### 继承多个虚类时的内存布局
**回答话术：**
多继承下对象按继承顺序拼合各基类子对象，每个含虚函数的基类子对象各带一个 vptr（虚表指针）。派生类新增的虚函数追加到**第一个基类的虚表**末尾，不会为派生类单独创建新 vptr。

布局示意：
```text
+--[Base1 子对象]--+--[Base2 子对象]--+--[Derived 自身成员]--+
| vptr1 (8B)       | vptr2 (8B)       | Derived 数据成员     |
+------------------+------------------+---------------------+
```
- vptr1 指向的虚表：`[Base1::f, Base2::g, Derived::k]`（k 是新增，追加到末尾）
- vptr2 指向的虚表：`[Base2::h]`
- 指针偏移：`B* ptr = new C();` 时编译器自动将 ptr 偏移到 B 子对象起始位置
- 覆盖：派生类覆盖了哪个基类的虚函数，就在对应基类的虚表槽位替换
**知识点讲解：**
详见 [[#单/多继承虚函数表布局与覆盖]]，其中包含 this 调整与 thunk 的详细解释。
> [!Info] 可能的追问:
> - Q: 为什么派生类的新虚函数不单独建一个 vptr？
> - A: 派生类新虚函数只能用派生类指针/引用调用，而派生类指针指向对象头部（第一个基类位置），所以追加到主虚表末尾即可。不需要新 vptr，因为调用时派生类指针已经在主虚表能访问到的位置。

### 虚指针行为
**回答话术：**
vptr 指向 vtable，vtable 是函数指针数组，按虚函数声明顺序排列。核心行为：
- 子类覆盖某虚函数时，对应槽位被替换为子类版本
- 未覆盖的槽位保留父类函数地址
- 子类调用父类普通函数：直接按名字查找，不涉及 vtable（静态绑定）
- 子类调用父类中被自己重写的虚函数：用 `Base::func()` 显式指定作用域，走静态绑定绕过 vtable
- 父类调用子类方法：**不行**——父类不知道子类存在。但可以用 CRTP（奇异递归模板模式）模拟：子类继承父类模板，父类通过 `static_cast<T*>(this)->func()` 调用子类方法

**vptr 长度**：64 位系统上 8 字节（一个指针大小）。
**vtable 共享**：同一个类的所有对象共享同一张 vtable，不同子类各有自己的副本。即 `Derived1` 和 `Derived2` 的对象各有各的虚表，vptr 指向各自的类虚表，互不干扰。
**性能代价**：vptr -> vtable -> 函数指针，多一次内存跳转，且通过指针调用的函数编译器无法内联。
**知识点讲解：**
```cpp
class Base {
    virtual void f() { cout << "Base::f"; }
};
class Derived : public Base {
    void f() override { cout << "Derived::f"; }
    void callBaseF() { Base::f(); }  // 显式调用基类版本，静态绑定
};
// CRTP 模式：父类调用子类方法
template<class T>
class BaseCRTP {
    void interface() { static_cast<T*>(this)->impl(); }
};
class DerivedCRTP : public BaseCRTP<DerivedCRTP> {
    void impl() { cout << "Derived::impl"; }
};
```
> [!Info] 可能的追问:
> - Q: 如何调用父类中被自己重写的虚函数？
> - A: 使用 `Base::func()` 显示指定作用域，这会强制编译器走静态绑定，直接调用 Base::func 而不经过 vtable。这在"在子类实现中扩展父类行为"时很常见：`void Derived::func() override { Base::func(); /* 扩展代码 */ }`。
> - Q: 虚类的 vptr 长度是多少？
> - A: 64 位系统上是 8 字节（一个指针宽度）。无论类有多少虚函数，vptr 始终是一个指针大小。vtable 可以很大（函数指针数组），但 vptr 只是指向它的指针。
### 什么叫做函数的覆盖和函数的隐藏本质区别是什么？
**回答话术：**
本质区别在**作用域解析**和**绑定时机**：
- **覆盖（override）**：派生类重写基类的**虚函数**（同签名），走**动态绑定**。运行期通过 vptr 查虚表，调用派生类版本。要求：`virtual` + 同签名 + 派生类。
- **隐藏（hide）**：派生类定义同名函数（不管签名、不管是否 virtual），**遮蔽**基类所有同名函数，走**静态绑定**。编译期名字查找先于重载决议，派生类作用域中找到了名字就不再往基类找。
```cpp
class Base {
public:
    virtual void f(int);     // 虚函数
    void g();                // 非虚
};
class Derived : public Base {
public:
    void f(int) override;    // 覆盖（override）：Base::f(int) 的虚表槽位被替换
    void g();                // 隐藏（hide）：Base::g() 被遮蔽，d.g() 调 Derived::g()
    void g(int);             // 隐藏：重载都算，Base::g() 被遮蔽
};
```
**知识点讲解：**

| 特性 | 覆盖（override） | 隐藏（hide） |
|------|-----------------|--------------|
| 函数性质 | 虚函数 | 任意 |
| 签名要求 | 必须相同 | 任意 |
| 绑定时机 | 动态（运行期） | 静态（编译期） |
| 作用域 | 派生类作用域 + 替换虚表槽位 | 名字查找遮蔽 |
| 访问基类版本 | `Base::func()` | `using Base::f;` 恢复重载集 |
> [!Info] 可能的追问:
> - Q: 覆盖和隐藏的底层实现机制？
> - A: 覆盖靠 vtable——派生类构造时，编译器把重写的虚函数地址填入虚表对应槽位，替换基类地址。隐藏靠名字查找规则——编译器先在派生类作用域中查找名字，找到就停止，不再去基类作用域找。这是 C++ 的两阶段名字查找导致的。

### std::map 为什么选择红黑树而不是 AVL 树
**回答话术：**
std::map 需要有序 + O(log n) 操作，必须用平衡二叉搜索树。AVL 和红黑树都是平衡树，但选择红黑树是因为**插入/删除的性能更稳定**：
- AVL：严格平衡（左右子树高度差 <= 1），查询略快，但插入/删除后需要多次旋转恢复平衡，旋转次数 O(log n)
- 红黑树：弱平衡（最长路径 <= 2 倍最短路径），查询略慢，但插入/删除后最多只需 2 次旋转（插入）或 3 次旋转（删除）就能恢复平衡，旋转次数 O(1)

std::map 是通用的关联容器，插入/删除和查询同样频繁。红黑树的综合性能更优。
**知识点讲解：**
```text
红黑树 5 条性质：
1. 节点是红色或黑色
2. 根是黑色
3. 叶子（NIL）是黑色
4. 红色节点的子节点必须是黑色
5. 任一节点到其每个叶子的路径上，黑色节点数相同
```
> [!Info] 可能的追问:
> - Q: 为什么不直接用哈希表（unordered_map）？
> - A: map 需要有序性（顺序遍历、范围查询、第 k 个元素等），哈希表无序。如果你不需要有序，用 unordered_map（平均 O(1)）。map 和 unordered_map 的选择是有序 vs 无序、O(log n) vs O(1) 的权衡，详见 [[#std::map 和 std::unordered_map 的底层数据结构]]。

### 为什么如果析构函数不是虚函数，就只调用基类析构函数？
**回答话术：**
因为析构函数没有走动态绑定，是**静态绑定**的。当 `delete base_ptr;` 时，编译器根据指针的**静态类型**（Base*）决定调用哪个析构函数：
- 析构非虚：编译器静态绑定到 Base::~Base()，只析构基类部分
- 析构虚函数：编译器通过 vptr 查虚表，找到派生类的析构函数，先调派生类析构再调基类析构
派生类资源泄漏的原因：析构非虚时，派生类的析构函数从未被调用，派生类成员（如 `std::vector`、`std::string`、`new` 分配的内存）不会被释放。
**知识点讲解：**
```cpp
class Base { ~Base(); };            // 非虚
class Derived : public Base {       // 派生类有 string, vector 等成员
    std::string s;
    std::vector<int> v;
};
Base* p = new Derived();
delete p;          // 只调 Base::~Base()，Derived 的成员未析构 -> 泄漏
```
正确的做法：带多态用途的基类析构函数必须声明为 `virtual ~Base() = default;`。
> [!Info] 可能的追问:
> - Q: 析构函数在虚表中的位置？
> - A: 析构函数在虚表中占据一个槽位（放在虚函数列表最后）。多继承下，每个基类子对象的虚表中都有析构函数的条目。派生类析构函数的地址会被填入所有基类虚表的析构槽位，保证无论通过哪个基类指针 delete，都能调用到派生类析构。
> - Q: 为什么不把所有析构函数默认设为虚？
> - A: 虚函数有额外开销——每个对象多一个 vptr（8 字节），每次调用多一次间接跳转且无法内联。如果类没有多态用途（不需要通过基类指针删除），虚析构就是纯浪费。C++ 零开销原则：不为不用之物付费。
### operator new 函数是否可以重载？
**回答话术：**
**可以**重载 `operator new`，但注意重载的是**全局**或**类专属**的 `operator new`，不是 `new` 表达式本身（`new` 表达式行为不可改变）。重载意义：
1. **自定义内存分配策略**：使用内存池预分配、对齐要求、特定内存区域（如共享内存、DMA 内存）
2. **调试/追踪**：统计内存分配次数、大小，检测内存泄漏
3. **性能优化**：避免频繁的系统调用，减少分配开销

重载格式：
```cpp
class MyClass {
public:
    void* operator new(size_t size) {            // 普通 new
        return custom_alloc(size);
    }
    void* operator new(size_t size, int extra) { // placement new（带额外参数）
        return custom_alloc(size + extra);
    }
    void operator delete(void* ptr) {            // 对应的 delete 必须重载
        custom_free(ptr);
    }
};
MyClass* p = new MyClass();           // 调自定义 operator new
MyClass* p2 = new(42) MyClass();      // 调 placement new
```
**知识点讲解：**
重载 `operator new` 时，第一个参数必须始终是 `size_t`（分配大小），多出来的参数构成 placement 版本。对应的 `operator delete` 也必须重载（否则分配失败时编译器不知道如何释放）。
> [!Info] 可能的追问:
> - Q: 重载 operator new 和重载 new 表达式的区别？
> - A: 只能重载 `operator new`（内存分配函数），不能重载 `new` 表达式（分配内存 + 调用构造函数）。`new` 表达式的两步行为是语言标准规定的，不可改变。重载 `operator new` 只影响"分配内存"这一步。

### C 语言与 C++中结构体的区别是什么
**回答话术：**
C 的 struct 仅仅是**不同 POD 数据类型的集合**，C++ 在此基础上扩展了完整面向对象支持：
- 访问修饰符（public/protected/private，C 没有）
- 成员函数（C 只能写函数指针模拟）
- 构造/析构函数（RAII 支持）
- 继承和多态（C 只能通过函数指针表 + 手动传递 this 模拟）
- 模板支持
- 移动语义

实际上 C++ 的 struct 和 class 只有默认访问权限的区别：struct 默认 public，class 默认 private。
**知识点讲解：**
```cpp
// C 模拟面向对象
struct Shape {
    void (*draw)(struct Shape*);  // 函数指针模拟虚函数
    int type;
};
// C++ 直接支持
struct Shape {
    virtual void draw() = 0;      // 纯虚函数，编译器自动处理 vtable
    virtual ~Shape() = default;
};
```
> [!Info] 可能的追问:
> - Q: C 中如何模拟 C++ 的虚函数机制？
> - A: 用函数指针成员 + 手动传递 this。Linux 内核的 `file_operations` 结构体就是典型例子——每个文件系统注册自己的操作函数表，通过这个表模拟多态分发。C++ 的虚函数表本质上是编译器自动生成的函数指针表，原理一致。

### vector 的实现？有哪些方法可以避免 vector 的反复扩容？
**回答话术：**
vector 底层由**连续内存**管理，通过三个指针实现：start（数据起始）、end（已用数据末尾）、capacity（分配内存末尾）。
- 当 `end - start == capacity` 时触发扩容：向系统申请更大内存（GCC 2 倍，MSVC 1.5 倍），将旧数据移动/拷贝过去，析构旧元素，释放旧内存，更新三个指针
- **扩容时是移动还是拷贝**取决于元素的移动构造函数是否 `noexcept`。STL 的 `std::move_if_noexcept` 在移动构造函数 noexcept 时用移动，否则用拷贝（保证异常安全）

避免反复扩容的方法：
1. `reserve(n)` 提前预留空间，避免多次扩容
2. `shrink_to_fit()` 在不需要大容量时释放多余内存（和避免反复扩容无关，可以提到）
3. `emplace_back()` 就地构造元素，避免临时对象拷贝/移动（和避免反复扩容无关，可以提到）

**知识点讲解：**
```cpp
std::vector<int> v;
v.reserve(1000);        // 提前预留 1000 个元素空间，不构造
v.push_back(1);          // 不触发扩容
v.shrink_to_fit();       // 将 capacity 缩减到 size

// emplace_back vs push_back
v.push_back(MyClass(1, 2));     // 构造临时对象 + 移动（或拷贝）
v.emplace_back(1, 2);           // 直接在 vector 内存中构造，无临时对象
```
> [!Info] 可能的追问:
> - Q: 扩容时旧数据是移动还是拷贝？
> - A: 取决于移动构造函数是否 `noexcept`。STL 用 `std::move_if_noexcept` 判断：如果移动构造函数是 noexcept 的，移动；否则拷贝。因为移动后源对象状态未定义，如果移动中抛出异常，vector 已扩容的新内存中的部分移动元素处于无效状态，无法回滚。拷贝构造如果抛出异常，新内存还没写入，旧内存完好，可以安全回滚。所以 noexcept 移动是安全的，non-noexcept 移动回退到拷贝以保证异常安全。
> - Q: 为什么 GCC 2 倍扩容、MSVC 1.5 倍？
> - A: 2 倍扩容的摊还分析保证每次插入 O(1) 摊还，但最多浪费 50% 空间（最后一次扩容后利用率 50%-100%）。1.5 倍扩容内存利用率更高（约 67%-100%），且 1.5 倍增长允许旧内存块被后续分配重用（因为 1.5^2 ≈ 2.25，不是整数倍，不太可能与旧内存块大小完全对齐）。这是时间（扩容次数）和空间（内存利用率）的权衡，没有绝对优劣。

### 讲讲移动语义和完美转发
**回答话术：**
**移动语义**的核心目的是消除不必要的深拷贝开销。实现方式：
- 通过 `std::move()` 或传入右值，触发类的**移动构造函数**和**移动赋值运算符**重载
- 移动操作通常只是"steal"资源（指针交换），不涉及深层复制
- 移动构造函数必须声明为 `noexcept`，否则 STL 容器扩容时不会用移动（用 `std::move_if_noexcept` 判断）

**完美转发**的目的是在模板函数中保持参数的原始值类别（左值/右值）不变：
- 通过 `T&&`（万能引用）+ `std::forward<T>()` 实现
- 引用折叠规则：`T& & -> T&`，`T& && -> T&`，`T&& & -> T&`，`T&& && -> T&&`
- 只有右值引用 + 右值引用折叠为右值引用，其他组合都折叠为左值引用
> [!Info] 可能的追问:
> - Q: 为什么移动构造函数必须是 noexcept 的？
> - A: 因为 STL 容器（如 vector）扩容时使用 `std::move_if_noexcept`：如果移动构造函数是 noexcept 的，移动旧数据到新内存；否则拷贝。如果移动构造函数可能抛异常，一旦移动过程中抛异常，新内存中的部分移动元素处于无效状态，无法回滚到旧内存（旧内存已被修改）。拷贝的异常安全：拷贝失败时，旧内存完好无损，可以安全回滚。
> - Q: std::move 和 std::forward 的区别？
> - A: `std::move(x)` 无条件将 x 转为右值引用（`static_cast<T&&>(x)`）。`std::forward<T>(x)` 有条件地转换：如果 T 是左值引用则保留左值，否则转为右值。所以 move 用于"确定要转移资源"，forward 用于完美转发中保持原始值类别。
### 线程不安全的容器应该如何保证线程安全？
**回答话术：**
STL 容器默认线程不安全，保证并发安全的方法（按推荐优先级）：
1. **互斥锁**：包裹整个容器操作，最通用但并发度低
2. **读写锁**：读多写少时用，比互斥锁并发度高
3. **原子变量**：主要用 CAS 在简单计数器场景下操作避免锁，无法保护复杂数据结构
4. **空间换安全**：对于**不扩容且使用者数量固定**的容器，提前分配好空间，划分区域给不同读写者使用（无冲突）
5. **线程局部存储**：每个线程持有一份副本，完全无锁，但内存开销大、数据同步需额外处理
6. **并发容器**：直接用 TBB/Folly 的并发容器，内部已集成同步机制
7. **无锁队列**：将操作转化为向一个无锁队列发送任务或数据，由单线程专门负责从队列取出数据并写入，性能和可维护性最好，但需要注意 [[架构设计#无锁队列#ABA 问题与解决方案|ABA问题]] 
> [!Info] 可能的追问:
> - Q: 无锁队列的底层原理是什么？
> - A: 基于 CAS（Compare-And-Swap）原子操作，不使用互斥锁。典型实现是循环缓冲区 + 原子索引（生产者写索引、消费者读索引），通过 `std::atomic::compare_exchange_weak` 实现无锁的入队/出队。性能比互斥锁高一个数量级，但实现复杂，ABA 问题是常见陷阱。

### C++为什么能够对性能和硬件进行更精确的控制？
**回答话术：**
核心原因在于 C++ 的设计哲学和实现机制：
- **零成本抽象**：使用抽象（类、虚函数、模板）时，不为不用到的特性付费，使用的特性也不会比手写汇编更慢
- **直接编译为机器码**：C++ 编译器直接将源代码翻译为**对应架构的机器码**，没有解释器/虚拟机中间层（如 Java JVM、Python 解释器）
- **内存精确控制**：允许开发者直接操作内存地址（指针）、精确控制对象生命周期和内存布局，包括对齐、填充、位域
- **操作粒度可到"位"**：通过位域（bit-field）、位运算（`& | ^ ~`）、`std::bitset` 等，可以在最低的二进制位级别操作数据

Python 等语言之所以不能进行系统级编程，是因为它们运行在解释器/虚拟机上，开发者无法直接控制内存分配和释放，无法操作指针，有垃圾回收器介入，每个操作都有运行时开销。这些抽象提高了开发效率，但牺牲了底层控制能力。
> [!Info] 可能的追问:
> - Q: 零成本抽象的具体含义是什么？
> - A: 由 Stroustrup 提出："what you don't use, you don't pay for. What you do use, you couldn't hand-code any better." 即使用 C++ 特性不产生额外开销，且编译器的优化效果通常超过手写。例如虚函数调用只比普通函数调用多一次间接跳转，模板的编译期计算完全零运行时开销，RAII 的析构函数在作用域退出时自动调用，与手写 delete 的机器码相同。
> - Q: std::bitset 是按位操作的方法吗？
> - A: 是的，`std::bitset<N>` 是编译期固定大小的位集合，内部用一个或多个 unsigned long long 存储，通过位运算实现 `set/test/flip` 等操作。是比手动位运算更安全、可读性更好的替代方案。

### 析构函数为什么不能抛出异常？
**回答话术：**
析构函数抛出异常会导致**双重异常**和**栈展开冲突**，最终调用 `std::terminate` 终止程序。具体流程：
1. `try` 块中抛出异常，开始栈展开
2. 栈展开过程中，**try 中的局部对象**的析构函数被自动调用
3. 如果某个析构函数再抛出异常（甚至析构函数中包含嵌套的异常），导致栈展开是需要同时处理两个异常
4. 本质是因为如果析构函数能够抛出异常，局部作用域中所有对象析构有多少个嵌套异常就需要多少个嵌套 try-catch 捕获，否则就 `std::terminate` 终止程序

C++11 起析构函数**默认隐式声明为 noexcept**，如果确实需要析构函数抛出异常，必须显式声明 `noexcept(false)`，但强烈不推荐。
**知识点讲解：**
```cpp
struct Bad {
    ~Bad() noexcept(false) { throw 1; }  // 显式允许析构抛异常
};
try {
    Bad b;
    throw 0;    // 抛出异常，栈展开调用 b 的析构，析构又抛出异常 -> terminate
} catch(...) {}
```
> [!Info] 可能的追问:
> - Q: 怎么处理析构函数中可能发生的错误？
> - A: 1) 记录日志，不抛出异常；2) 调用 `std::terminate` 前完成必要的清理；3) 将可能抛出的操作分离到普通成员函数中，让调用者显示调用并处理异常。基本准则是：析构函数**绝不往外抛异常**。

### vector 和 array 的使用场景分别是什么
**回答话术：**
- `std::vector`：动态大小，元素在运行时才确定数量，需要随机访问和在尾部增删。vector 对象本身在栈上，数据在堆上分配
- `std::array`：固定大小，编译期确定，**数据在栈上分配**，是 C 风格数组的零成本抽象包装。适用于性能要求极高、不需要动态增长的场景
两者都支持随机访问迭代器、提供 `data()` 方法与 C API 交互、与 STL 算法兼容。选择依据：大小在编译期可知用 array，否则用 vector。
> [!Info] 可能的追问:
> - Q: array 和 C 数组有什么区别？
> - A: array 有 STL 接口（迭代器、算法库兼容）、知道自己的大小（不会退化为指针）。C 数组会退化为指针（`sizeof(arr)` 只在定义域内有效），作为参数传递时丢失大小信息。array 是 C 数组的零成本替代。

### 纯虚函数是否可以写定义体？
**回答话术：**
**可以**，但有两个关键限制：
1. **必须在类外定义**（类内写 `= 0` 声明，类外写实现体）
2. **不能直接调用**——不能通过 `Base::func()` 在类外直接调用，需要通过 `Base::func()` 在基类/派生类中显式调用，但**不能通过对象直接调用虚函数机制**来调用它

作用：多个派生类继承同一个基类，需要执行相同的初始化操作时，在基类纯虚函数中提供默认实现，派生类重写后通过 `Base::func()` 调用基类版本，减少冗余代码。
> [!Info] 可能的追问:
> - Q: 纯虚函数有定义体，那这个类还是抽象类吗？
> - A: 是的，仍然是抽象类，不能实例化。纯虚函数的定义体不影响抽象性，`= 0` 才是关键。定义体只是一个"可被显式调用的默认实现"，派生类仍然必须重写该纯虚函数才能实例化。

### 打破内存对齐的方法有哪些？
**回答话术：**
C++ 中打破/控制内存对齐的方法：
1. **`#pragma pack(n)`**：设置结构体最大对齐字节数，n 通常为 1/2/4/8。所有成员按 min(n, 成员自身对齐) 对齐。`#pragma pack(push, 1)` 后结构体紧密排列，常用于网络协议包头、二进制文件格式
2. **`__attribute__((packed))`**：GCC/Clang 扩展，告诉编译器使用最紧凑的对齐方式（1 字节对齐），消除所有填充字节
3. **`alignas(n)`**（C++11）：指定变量或类型的对齐方式，`alignas(64) int arr[100];` 将数组对齐到 64 字节边界（适合 SIMD 对齐要求）
4. **`std::align`**（C++11）：在给定的缓冲区中查找满足对齐要求的指针，用于手动实现内存池中的对齐分配
5. **位域（bit-field）**：`struct Flags { unsigned int a:1; unsigned int b:3; };` 精确到 bit 级别的布局控制，不按字节对齐
> [!Info] 可能的追问:
> - Q: 位域和 `#pragma pack(1)` 的区别？
> - A: 位域控制的是 bit 级别的布局，精确到二进制位，适合标志位、协议头等紧凑场景。`#pragma pack(1)` 控制的是字节级别的对齐，消除填充但不改变成员本身的字节数。位域可以做到一个 int 存 32 个标志位，pack(1) 做不到。

### 什么是 RTTI？什么情况下需要使用 RTTI？
**回答话术：**
RTTI（Run-Time Type Information，运行时类型信息）允许在运行期识别对象的实际类型。可通过 typeid 和 dynamic_cast 调用 RTTI，在以下场景中使用
- `typeid`：返回 `std::type_info` 对象，包含类型信息，`typeid(*ptr).name()` 输出对象的实际类型名
- `dynamic_cast`：安全地将基类指针/引用转换为派生类类型，转换之前的类型检查
- `try-catch` 块中 catch 块的异常类型判断
**不推荐滥用 RTTI**，能用虚函数解决的问题不要用 RTTI（性能代价 + 设计上的多态替代）。
**知识点讲解：**
```cpp
Base* p = new Derived();
if (typeid(*p) == typeid(Derived)) { /* 是 Derived 类型 */ }

// dynamic_cast 安全向下转型
if (Derived* d = dynamic_cast<Derived*>(p)) {
    d->derivedMethod();
}
```
**关闭 RTTI**：编译器选项 `-fno-rtti` 会省略 vtable 中的 type_info 指针，此时 `typeid` 和 `dynamic_cast` 不可用，vtable 体积缩小，但失去运行时类型识别能力。
> [!Info] 可能的追问:
> - Q: RTTI 的底层实现机制是什么？
> - A: 见下方 "vtable 与 type_info" 知识点。RTTI 依赖 vtable，每个含虚函数的类的虚表头部或负偏移处存放指向 `type_info` 对象的指针，`typeid` 通过 vptr 找到 vtable，再从中取出 type_info。`dynamic_cast` 遍历继承链，通过比较 type_info 确定是否为目标类型，并正确调整指针偏移。

### vtable 数据而结构
**回答话术：**
这是 RTTI 的底层实现机制。每个含虚函数的类，其虚表（vtable）**不仅仅**是一个函数指针数组，在 vtable 的**首部之前（负偏移）**或**首部**通常还存放着指向 `std::type_info` 对象的指针。

具体布局（以 Itanium C++ ABI 为例，Linux 上 GCC/Clang 使用）：
```text
vtable 布局（Itanium ABI）：
[-1] offset_to_top (到对象顶部的偏移)
[0]  typeinfo_ptr (指向 std::type_info 的指针)
[1]  virtual ~Base()   ← 虚函数从这里开始
[2]  virtual void func()
...
```
- `typeid(*p)` 通过对象的 vptr 找到 vtable，再从 vtable 的 `typeinfo_ptr` 位置获取 `type_info` 对象
- `dynamic_cast` 也通过类似机制遍历继承链，在运行时比较类型信息，同时调整指针偏移

> [!Info] 可能的追问:
> - Q: 为什么 vtable 中需要 type_info 指针？
> - A: `typeid` 和 `dynamic_cast` 需要在运行期获取对象的类型信息，但对象本身只有一个 vptr，没有显式的类型信息。**vtable 是类级别的，每个类一张表**，所以在 vtable 中存 type_info 是最自然的——既不需要每个对象额外存储类型信息，又能在运行时通过 vptr 找到 vtable 然后获取类型信息。这是空间（vtable 多一个指针）和功能（运行时类型识别）的权衡。

### 什么是 ABI？
**回答话术：**
ABI（Application Binary Interface，应用二进制接口）是定义**二进制级别**兼容性的规范，与 API（源代码级别）不同。它定义了：
- 函数调用约定（参数传递顺序、用栈还是寄存器、谁清理栈帧）
- 数据结构的内存布局（成员对齐规则、虚函数表布局）
- 名称修饰规则（name mangling）
- 异常处理机制、RTTI 布局

ABI 不一致的代码（如不同编译器版本编译的目标文件）链接在一起会导致运行时崩溃，导致了跨编译器/跨平台的二进制文件不能共用
**知识点讲解：**
```text
API 层面：函数签名不变即可兼容（源代码兼容）
ABI 层面：调用约定、成员布局、虚函数表布局一致才能兼容（二进制兼容）
```
> [!Info] 可能的追问:
> - Q: ABI 和 API 的区别？
> - A: API 是代码层面的接口约定（函数名、参数类型），只要不改签名，代码可以编译通过。ABI 是二进制层面的（调用约定、内存布局），即使 API 没变，换了编译器版本可能二进制不兼容。Linux 上 GCC 和 Clang 编译的 .so 可以互相调用（都遵循 Itanium C++ ABI），但 Windows 上 MSVC 不同版本 Debug/Release 混用可能崩溃。

### 值传参，指针传参和引用传参有什么区别？
**回答话术：**
核心区别在**语义**和**性能**：
- 值传参：拷贝实参，函数内修改不影响原值。性能上，小对象（<=16 字节）可用寄存器传递，效率高；大对象拷贝开销大
- 指针传参：传递地址，函数内可修改原值，需检查 nullptr。额外一次解引用
- 引用传参：传递别名，语义上可修改原值，不能为空。实现上常按指针处理，回调函数中慎用引用传参，因为生命周期问题可能导致引用悬空

**16 字节以下结构体值传递可能比引用更快**：Linux System V ABI 允许将 <=16 字节的结构体拆成两个 8 字节分别用寄存器传递，省去引用传参的访存开销。
> [!Info] 可能的追问:
> - Q: 什么时候用值传递什么时候用引用传递？
> - A: 内置类型和小 POD（<=16 字节）值传递；大对象用 `const T&` 避免拷贝；需要修改原值用 `T&` 或 `T*`；可能为空用 `T*`。谷歌代码规范中简易传入参数用引用，传出用指针

### lambda 表达式实现原理
**回答话术：**
lambda 表达式的本质是**仿函数（functor）的语法糖**。编译器为每个 lambda 生成一个未命名的闭包类，类名经过 name mangling：
- 捕获列表中的引用捕获 -> 类中的引用成员
- 值捕获 -> 类中的值成员
- 构造函数参数和捕获列表一致，根据变量捕获类型决定传参方式
- `operator()` 参数列表和 lambda 参数列表一致，函数体就是 lambda 体
- 编译器提供 `operator auto(*)()` 重载方便将**没有捕获列表的 lambda**转为函数指针
- 可以在函数体之前添加 `mutable` 表示值捕获的变量可以作为副本在 lambda 内修改

无捕获 lambda 还可以转换为函数指针（因为 `operator()` 可以是非成员函数形式的）。
**知识点讲解：**
```cpp
// 编译器将 lambda 转换为：
[](int x, int y) -> int { return x + y; }
// 等价于：
class __lambda_12345 {
public:
    int operator()(int x, int y) const { return x + y; }
};
// 捕获变量的 lambda：
int base = 10;
auto add = [base](int x) { return x + base; };
// 等价于：
class __lambda_12346 {
    int base;  // 值捕获：成员变量
public:
    __lambda_12346(int base) : base(base) {}
    int operator()(int x) const { return x + base; }
};
```
> [!Info] 可能的追问:
> - Q: 无捕获 lambda 为什么能转函数指针？
> - A: 无捕获 lambda 的闭包类没有成员变量，`operator()` 不依赖任何对象状态，可以生成一个非成员函数版本的调用。编译器提供一个转换函数 `operator auto(*)()`, 返回对应的函数指针。有捕获的 lambda 不能转，因为其行为依赖捕获的变量。
> - Q: mutable lambda 的作用？
> - A: 默认 lambda 的 `operator()` 是 const 的，值捕获的变量不可修改。加 `mutable` 去掉 const，允许修改值捕获的副本。但注意修改的是捕获的副本，不影响原变量。
### shared_ptr 是否是线程安全的？
**回答话术：**
需要分三个层面讨论：
1. **引用计数操作**：线程安全。引用计数增减是原子操作，多个线程同时拷贝/销毁 shared_ptr 不会导致计数错乱
2. **shared_ptr 对象本身**：**不安全**。同一个 shared_ptr 对象被多个线程同时读写（如一个线程 `p = p2;` 另一个线程 `p.reset();`），会产生竞态条件，导致指针状态不一致甚至崩溃
3. **所指向的资源**：**不安全**。shared_ptr 不管理资源的并发访问，访问资源需用户自己加锁

> [!Info] 可能的追问:
> - Q: 为什么 shared_ptr 的引用计数是原子的？
> - A: shared_ptr 的控制块使用 `std::atomic<int>` 存储引用计数，拷贝/析构时用原子操作增减。这是 shared_ptr 能在多线程环境下安全传递的基础。但注意：控制块中还有一个 weak_count，同样原子操作。

### 拿到虚函数表地址后，是否可以改写虚函数表的内容？
**回答话术：**
默认**不可以**，直接写入会导致段错误。因为虚函数表存放在进程虚拟地址空间的**只读数据段**（`.rodata`），操作系统用 MMU 为该内存页设置只读权限，强行写入会触发 MMU 异常，进程崩溃。

但可以通过 `mprotect`（Linux）等系统调用将内存页权限修改为可写，从而改写虚函数表。这种技术被称为 **vtable hook**，用于：
- 安全保护：拦截对隐私数据的暴力访问，将虚函数替换为自定义处理函数
- 性能监控：Hook 关键虚函数，统计调用次数、耗时
- 逆向工程：修改程序行为
> [!Info] 可能的追问:
> - Q: 修改虚函数表有什么风险？
> - A: 如果同一个类的多个对象共享同一张虚表，修改一个对象的虚表会影响所有同类对象，可能导致意外的全局行为。此外虚函数表是编译器生成的，编译器可能做某些优化假设（如虚函数表内容不变），修改后行为未定义。

### 什么是 SegmentFault？什么情况下会出现？通常排查/解决方法是什么？
**回答话术：**
SegmentFault（段错误，信号 SIGSEGV）是操作系统在 MMU 检测到**非法内存访问**时发送给进程的信号。常见触发场景：
1. 解引用空指针/野指针：`int* p = nullptr; *p = 1;`
2. 访问已释放的内存：`delete p; *p = 1;`
3. 缓冲区溢出：栈/堆溢出
4. 写只读内存：修改 `.rodata` 段或代码段
5. 栈溢出：递归过深、局部变量过大

排查方法：
1. **core dump**：`ulimit -c unlimited` 开启，崩溃后 `gdb ./a.out core` -> `bt` 看调用栈
2. **AddressSanitizer**：`g++ -fsanitize=address` 重编，崩溃时直接定位到越界/UAF 行
3. 静态检查可以通过 cpp-check 和 clang-tidy 在 ide 警告提示中就能看到
4. **valgrind**：`valgrind ./a.out` 检测内存访问错误
5. 在可疑处加日志缩小范围
> [!Info] 可能的追问:
> - Q: 段错误和 abort 的区别？
> - A: 段错误是硬件异常（MMU 检测非法访问）触发的 SIGSEGV 信号。abort 是软件主动调用 `std::abort()` 或 `assert` 失败触发的 SIGABRT 信号。段错误通常意味着代码有内存访问 bug，abort 意味着逻辑检查失败（如断言失败、未捕获异常）。
### delete this 是什么操作？能用在什么场景下？
**回答话术：**
`delete this;` 在成员函数中调用，会销毁当前对象并释放其内存。关键是：**调用 delete this 的对象必须是通过 `new` 动态分配的**，如果对象是栈上分配的，调用 `delete this` 是未定义行为。
注意事项：
- 调用 `delete this` 后，不能再访问任何成员变量或调用任何成员函数
- 这种操作通常用于**引用计数对象**：当对象发现自己引用计数为 0 时，自己销毁自己
- 典型场景：`shared_ptr` 的控制块对象、COM 接口的 `Release()` 实现

**知识点讲解：**
```cpp
class RefCounted {
    int ref_count_;
public:
    void release() {
        if (--ref_count_ == 0)
            delete this;  // 引用计数归零，自己销毁
    }
};
// 注意：delete this 后，任何成员访问都是 UB
void RefCounted::release() {
    if (--ref_count_ == 0) {
        delete this;
        // 此时不能再访问任何成员
    }
}
```
> [!Info] 可能的追问:
> - Q: delete this 之后还能访问成员变量吗？
> - A: 不能。`delete this` 调用析构函数释放内存，之后 `this` 指针指向已释放的内存，访问成员是 UB。任何在 `delete this` 之后访问成员变量的代码都是 bug，可能"看起来正常"也可能崩溃，取决于编译器优化和内存是否被重用。

### union 和 std::variant 有什么区别？
**回答话术：**
核心区别：**类型安全**。
- `union`：所有成员共享同一块内存，程序需自行跟踪当前存储的是哪个成员。C++11 起 union 可以包含有非平凡构造/析构函数的成员，但必须手动管理其生命周期（显式调用构造/析构）
- `std::variant`（C++17）：类型安全的联合体，内部通过一个**足够大的内存块**（大小由最大成员类型决定）+ 一个**索引块**（记录当前存储的类型）实现。访问用 `std::visit` 或 `std::get`，编译器检查类型安全

"手动管理生命周期"是指：如果 union 包含 `std::string` 等有非平凡构造/析构的成员，编译器不会自动为其调用构造/析构，需要你显式用 placement new 和手动析构调用来管理：
**知识点讲解：**
```cpp
union U {
    int n;
    std::string s;  // 非平凡类型
    U() {}  // 不自动构造 s
    ~U() {} // 不自动析构 s
};
// 使用时：
U u;
new (&u.s) std::string("hello");  // 手动构造
u.s.~basic_string();              // 手动析构
```
> [!Info] 可能的追问:
> - Q: std::variant 的运行时开销？
> - A: 主要开销在索引检查。`std::get` 运行时检查当前类型是否匹配，匹配不上抛异常。`std::visit` 通过索引查函数指针表（类似虚表），O(1) 但有一次间接跳转。空间上，`sizeof(variant)` 比最大成员略大（存索引），比 union 多一个 int 的开销。

### lock_guard 和 unique_lock 的区别
**回答话术：**
- `lock_guard`：最简单 RAII 封装，构造时加锁，析构时解锁，**不能手动控制加解锁**，**不能转移所有权**。适合需要整个作用域加锁的场景
- `unique_lock`：更灵活的 RAII 封装，**允许延迟加锁、手动解锁、条件变量配合**，**允许转移所有权**（`release()` 交出互斥体所有权，不释放锁）。适合需要精细控制锁粒度的场景

> [!Info] 可能的追问:
> - Q: 为什么条件变量必须配合 unique_lock 而不是 lock_guard？
> - A: 因为 `wait()` 需要：
> 	1) 解锁互斥体（让生产者能进入临界区）；
> 	2) 等待条件变量；
> 	3) 被唤醒后重新加锁。`unique_lock` 提供 `unlock()`/`lock()` 接口，可以在 `wait` 内部实现"解锁-等待-加锁"的语义。`lock_guard` 没有 `unlock()`，无法满足这个需求。

### jthread 和 thread 的区别
**回答话术：**
- `thread`：C++11 引入，需手动管理线程生命周期（`join()` 或 `detach()`），若析构时线程仍可 join 则 `std::terminate`
- `jthread`（C++20）：自带**协作式中断机制**和**自动 join**。析构时自动调用 `join()`（RAII 风格），不需要手动管理。提供 `get_stop_source()`/`request_stop()` 等接口实现协作式中断

**知识点讲解：**
```cpp
std::jthread jt([](std::stop_token st) {
    while (!st.stop_requested()) {
        // 执行工作
    }
});
// jt 析构时自动调用 stop_requested() + join()，无需手动管理
// 对比 thread：
std::thread t([](){ /* work */ });
t.join();  // 必须手动 join，否则析构 terminate
```
> [!Info] 可能的追问:
> - Q: jthread 的协作式中断和线程强制终止的区别？
> - A: 协作式中断是线程内部自愿检查停止标志，可以做清理工作（释放资源、写日志等）。强制终止（如 `pthread_cancel`）在任意位置杀死线程，可能持有锁时被杀导致死锁，或资源未释放。jthread 的 `request_stop()` 只设置标志位，不强制终止，线程需要在合适的位置检查 `stop_requested()` 并自行退出。

### 什么是虚继承？
**回答话术：**
虚继承是解决菱形继承的方案。最终派生类在内存中会包含**两份**基类子对象，导致歧义和浪费。
虚继承使用 `virtual` 关键字在中间层声明，保证最终派生类中只保留**一份**共享基类实例。
**知识点讲解：**
```cpp
class GrandParent { int data; };
class Parent1 : virtual public GrandParent {};  // 虚继承
class Parent2 : virtual public GrandParent {};  // 虚继承
class Child : public Parent1, public Parent2 {};
// Child 对象中只有一份 GrandParent::data，无歧义
// 如果不用虚继承，Child 会有两份 data，Child::data 访问歧义
```

> [!Info] 可能的追问:
> - Q: 虚继承怎么实现的？
> - A: 编译器在对象布局中为每个虚继承的中间类引入一个或多个 vbptr（虚基类指针），指向 vbtable（虚基类表），表中记录共享基类在当前对象中的偏移。这样通过 `this + 偏移` 就能找到共享基类，不依赖具体继承层次。
> - Q: 虚继承有什么开销？
> - A: 
> 	1) 空间：每个虚继承类多一个 vbptr（8 字节）；
> 	2) 时间：访问共享基类成员需通过 vbptr -> vbtable -> 偏移计算，多一次间接跳转；
> 	3) 构造复杂度：虚基类由最终派生类直接初始化，构造顺序为"虚基类优先于普通基类"。
> - Q: 什么时候用虚继承？
> - A: 很少直接使用。标准库 `std::iostream` 通过虚继承 `std::ios` 解决菱形继承（`istream` 和 `ostream` 都继承 `ios`）。正常开发中，菱形继承本身就很少见，而且虚继承的复杂度（内存布局、构造顺序、指针偏移）往往比组合替代方案更不值得。推荐优先用组合（成员对象）代替继承。
### if constexpr 用法
**回答话术：**
`if constexpr`（C++17）允许在**编译期**对常量表达式进行分支选择，只有满足条件的分支会被编译（实例化），不满足的分支被丢弃。
关键规则：
- 丢弃的分支**不进行实例化**（不生成具体代码），但**基本语法检查**仍会执行
- 依赖模板参数的部分在丢弃分支中**不检查**（如 `T.method()` 不会检查 method 是否存在）
- 不依赖模板参数的代码在丢弃分支中**会进行语法/语义检查**
- 配合 trait_type 头文件中的模板类可以实现 SFINAE

> [!Info] 可能的追问:
> - Q: if constexpr 和普通 if 有什么区别？
> - A: 普通 if 的两条分支都会编译，运行时根据条件选择执行哪条。`if constexpr` 的分支在编译期评估，不满足条件的分支不生成代码（不实例化模板）。普通 if 在模板中要求所有分支都能通过编译，`if constexpr` 在丢弃分支中只做限制性语法检查，避免编译错误，如果 if constexpr 中传入非编译期常量会报错

### 什么是 SFINAE？
**回答话术：**
SFINAE（替换失败并非错误）是 C++ 模板重载决议中的一条规则：
- 当编译器尝试匹配某个模板函数时，如果模板参数替换导致无效代码（如尝试访问不存在的类型），编译器不会立即报错，而是**继续尝试其他可用的重载版本**
- 只有当**所有**重载版本都匹配失败时，编译器才最终报错

SFINAE 的主要用途是**在编译期根据类型特性启用或禁用某些模板函数**，是一种"以函数/类为基本单元的条件编译"（`#ifdef` 是以代码行/文件为单元的条件编译）。
标准库中的 `std::begin` 就用了 SFINAE，用于匹配不同的迭代器类型
> [!Info] 可能的追问:
> - Q: SFINAE 和 concept 的区别？
> - A: SFINAE 通过模板元编程技巧（如 `enable_if`、`decltype`）在模板参数替换失败时静默选择其他重载，代码可读性差。C++20 的 concept 提供了更清晰、更直接的方式来表达类型约束，错误信息也更容易理解。Concept 是 SFINAE 的"语法糖"，但更强大（可约束非模板函数、可做约束推导）。

### weak_ptr 的实现原理
**回答话术：**
weak_ptr 基于 shared_ptr 的**控制块**实现，不直接管理资源。控制块包含三个关键信息：
- 实际资源指针
- **强引用计数（shared count）**：记录指向该资源的 shared_ptr 数量
- **弱引用计数（weak count）**：记录指向该控制块的 weak_ptr 数量

行为：
- 当 shared count 归零时，资源被释放（析构指向的对象），但控制块不释放
- 当 weak count 也归零时，控制块才被释放
- `weak_ptr::lock()` 检查 shared count > 0 则返回一个 shared_ptr（增加 shared count），否则返回空

**这会导致延迟释放**: 当使用 `std::make_shared` 时，对象和控制块被分配在同一块内存中。对象析构后，这块内存要等到所有 weak_ptr 销毁（weak count 归零）才释放。所以大对象 + 长寿命 weak_ptr 会延迟释放内存。
**知识点讲解：**
```cpp
auto sp = std::make_shared<LargeObject>();  // 对象和控制块在同一内存
std::weak_ptr<LargeObject> wp = sp;
sp.reset();  // 对象析构，但内存不释放（weak count > 0）
// 此时 LargeObject 占用的内存仍在，直到 wp 也销毁
wp.reset();  // weak count 归零，控制块释放，内存释放
```
> [!Info] 可能的追问:
> - Q: weak_ptr 延迟释放的原因是什么？
> - A: 原因在于 `std::make_shared` 的优化——它将对象和控制块分配在同一块内存中（一次分配）。对象析构后，内存不能立即释放，因为控制块还在（weak_ptr 需要它来安全执行 `lock()`）。只有当 weak_count 也归零时，内存才能释放。所以 `make_shared` + 长寿命 weak_ptr 会延迟大对象的内存释放。

### std::make_shared 和 std::shared_ptr 的区别
**回答话术：**
- **`std::make_shared<T>(args)`**：一次内存分配（对象和控制块一起），更高效，异常安全。如果构造对象时抛出异常，不会泄漏内存
- **`std::shared_ptr<T>(new T(args))`**：两次内存分配（对象一次、控制块一次），略慢，且如果**new 成功但构造 shared_ptr 抛出异常**，对象会泄漏

使用 `shared_ptr` 的构造函数而不使用 `make_shared` 的场景：
- 需要自定义删除器
- 构造函数是 private 的（`make_shared` 不是 T 的友元）
- 管理的是原始内存数组（`shared_ptr<int[]>` 等）

> [!Info] 可能的追问:
> - Q: make_shared 的缺点？
> - A: 
> 	1) 对象和控制块在同一内存，大对象 + 长寿命 weak_ptr 会导致内存延迟释放；
> 	2) 不能自定义删除器；
> 	3) 不能用于管理数组（`shared_ptr<int[]>` 需要使用 `shared_ptr(new int[n])` 和自定义删除器）。

### std::string 内存结构
**回答话术：**
`std::string` 的对象本身在栈上（或作为成员在所在对象内存中），但管理的字符串数据通常在堆上。但大多数实现使用**短字符串优化（SSO）**：当字符串长度较短时（通常 < 16 字节），数据直接存储在对象内部（栈上），避免堆分配。

### 介绍标准库的异步框架
future、promise、packaged_task 和 async 这些都是 C++11 引入的，用在并发编程中：

### 什么是 RVO 优化？
它避免了从函数返回时创建临时对象。函数按值返回匿名临时对象时，编译器直接把对象构造在调用者的**栈帧内存**里，跳过临时对象的拷贝 / 移动和析构。
函数返回语句中如果返回的是**匿名对象/纯右值**，触发 RVO，如果函数返回的是函数作用域中的**命名局部变量**，触发 NRVO
多返回分支的函数可能不会触发 RVO
C++17 之后 RVO 是强制执行的，NRVO 是可选项，拷贝构造被 delete 也能编译；C++11/14 是可选优化
### 如何实现单例模式？
懒汉式
- 在程序创建时就创建单例对象，实现方法一般是在 main 函数所在文件中的全局作用域中创建 static 对象，或者直接在 main 函数的开头初始化对象并暴露接口给外部访问这个单例对象
- 缺点是即使他没被使用，也在程序生命周期中一直占用资源
饿汉式
- 用一个类封装单例对象或者指针
- 类的构造函数设置为 private，并将拷贝构造函数/拷贝构造运算符重载删除
- 在一个 public 函数 getInstance 中返回使用 static 创建单例对象并返回
- 这是 Effective C++中 scott mayer 提出的单例模式，在 C++11 以后由编译器保证单例性
还有一种借助 std::shared_ptr 的伪单例模式
- 和饿汉式大差不差，但是单例成员是 `std::shared_ptr` 包装的指针
- 不同位置的访问单例操作只是增加了引用计数
- 生命周期不合 static 变量一样，但行为上和单例模式完全一致，继承该类的类就是单例类
- 常用于闯关游戏中，每一关卡特有的资源用这种单例封装，切换关卡时引用计数清零释放资源，不用在游戏初期加载所有资源
### C++成员变量的初始化时间和顺序
普通成员变量: 
按照**在类中出现的顺序进行初始化**，与构造初始化列表顺序不一致，在有依赖关系的成员变量之间初始化顺序不对可能会引起UB，这个问题可以通过 clang-tidy 静态检查，编译器 `-Wreorder` 给出警告
有继承关系的成员变量:
先初始化基类，按**在类中出现的顺序进行初始化**，然后是子类
静态变量:
- 没有依赖关系的，值为编译期可知常量的会在编译期初始化，确定在 `.data` 
- 全局静态变量，有依赖关系或值在运行期确定，在main 函数之前，在 `.bss`
- 类内静态变量属于前两者
- 局部静态变量在第一次被调用时初始化
### 迭代器和指针有什么区别？
1.功能上:迭代器是指针上的抽象,它可以模拟指针,还可以用于遍历复杂的数据结构,而指针主要是为了访问和操作内存地址。
2.安全性上:迭代器通常附带更多的类型，边界和异常检查,比直接使用指针更安全。
3.灵活性上:迭代器可以通过多态性和模板来适应不同的容器类型,而指针只能指向特定类型的内存块。
4.类型:迭代器有多种类型,如输入迭代器、输出迭代器、向前迭代器、双向迭代器和随机访问迭代器。
迭代器使用 `operator++/--` 等运算符重载实现遍历功能，这也是它通过策略模式适配各种容器的原因，最经典的例子是 std::deque 使用中控器连接不连续的内存但还能支持随机访问的原因
### auto 和 decltype 有什么区别？
decltype 有个不可替代的使用场景: C++11 版本时返回值根据参数类型变化时，需要用 auto 做返回值，后置 decltype 返回类型
```cpp
template<typename T1, typename T2>
auto func(T1 t1, T2 t2) -> decltype(t1 + t2) { return t1 + t2； }
```
因为编译器是从左到右读取代码建立语法树的，如果没有后置返回类型，读取完整签名后无法得知函数调用时需要的内存布局。auto 作用仅仅是将类型判断推迟到了读取完整签名之后

### 什么是 CPU cache 的伪共享？
伪共享（False Sharing）是指：两个毫无关系、各自独立的变量，因为恰巧被存放在同一个缓存行（Cache Line，通常 64 字节）里，导致多核 CPU 在分别修改它们时，被迫不停地互相“踢出”对方的数据，从而引发严重的性能雪崩
## Qt 题库
### Qt 信号槽机制的底层实现原理是什么？
**回答话术：**
信号槽靠 MOC（元对象编译器）实现。MOC 扫描含 `Q_OBJECT` 宏的类，为每个信号生成一个函数体（内部只调用 `QMetaObject::activate`），并把信号/槽信息存进 `staticMetaObject`，按声明顺序建立索引。
调用链路：`emit` -> 信号函数 -> `activate` -> 在连接列表（双向链表）中找到匹配的槽索引 -> 调用槽。
连接的本质是**索引配对**：`connect` 把发送者元对象 + 信号索引 与 接收者元对象 + 槽索引 存进一个连接节点。直接连接通过函数指针调用，队列连接通过事件投递。
**知识点讲解：**
```cpp
// 信号函数体（MOC 生成）类似：
void Button::clicked(bool checked) {
    QMetaObject::activate(this, &staticMetaObject, 0, &checked);
}
// connect 本质：建立 (sender, signal_index) -> (receiver, slot_index) 的映射
```
> [!Info] 可能的追问:
> - Q: 信号为什么是函数？它没有函数体，MOC 怎么处理的？
> - A: 信号声明为函数，MOC 自动生成函数体（内部调用 activate）。信号函数体为空是语法要求，开发者不能实现。调用信号（emit）实际是调用这个 MOC 生成的函数，它负责分发。
> - Q: 信号槽比直接调用慢在哪？
> - A: 1) emit 时遍历接收者连接列表找匹配槽；2) 参数需打包/解包（跨线程走 QVariant 类型擦除），编译器无法内联；3) 队列连接还有事件排队延迟。但相比 new/delete 的开销，信号槽损耗可忽略。

### 信号函数发送的参数传递到槽函数中的方式是值传递还是引用传递？为什么？
**回答话术：**
**默认值传递**。跨线程（QueuedConnection）时参数必须可拷贝，通过 `QVariant` 序列化打包进事件队列，接收线程解包调用槽——所以必须值传递。
同线程（DirectConnection）参数以 const 引用传递（直接函数调用），但仍要求参数可拷贝（连接建立时做类型检查）。
自定义类型需 `qRegisterMetaType<T>()` 注册，否则队列连接无法传递。
**知识点讲解：**
```cpp
// 自定义类型跨线程传递必须先注册
qRegisterMetaType<MyStruct>("MyStruct");
connect(a, &A::sig, b, &B::slot, Qt::QueuedConnection);
```
> [!Info] 可能的追问:
> - Q: 为什么要求可拷贝？
> - A: 队列连接要把参数塞进事件队列，队列是线程间共享的，参数必须复制一份（避免悬空引用）。`QVariant` 存储的是值的副本。所以信号参数类型必须可拷贝构造，不可拷贝类型（如 `std::unique_ptr`）不能直接跨线程传信号。

### 描述 Qt 的 TCP 通信流程，以及其中涉及到的类的作用
**回答话术：**
服务端（`QTcpServer`）：
1. 创建 `QTcpServer`，`listen()` 监听地址+端口
2. 有新连接触发 `newConnection` 信号
3. 槽函数中 `nextPendingConnection()` 获取 `QTcpSocket`
4. 连接该 socket 的 `readyRead` 信号，槽中用 `read()` 读数据
5. `write()` 发送数据

客户端（`QTcpSocket`）：
1. 创建 `QTcpSocket`
2. `connectToHost(地址, 端口)` 连接服务器
3. 成功触发 `connected` 信号
4. 槽中 `write()` 发送、`readyRead` 槽中 `read()` 接收

类作用：`QTcpServer` 监听/接受连接，`QTcpSocket` 代表一条 TCP 连接。
**知识点讲解：**
```cpp
// 服务端
QTcpServer server;
connect(&server, &QTcpServer::newConnection, [&] {
    QTcpSocket* sock = server.nextPendingConnection();
    connect(sock, &QTcpSocket::readyRead, [sock] {
        qDebug() << sock->readAll();
    });
});
server.listen(QHostAddress::Any, 8888);
```
> [!Info] 可能的追问:
> - Q: 为什么服务端用 nextPendingConnection 而不是自己 new socket？
> - A: 每个 TCP 连接需要一个独立的 QTcpSocket 实例管理。`nextPendingConnection` 从内核连接队列取出一个已接受的连接，封装成 QTcpSocket。它带父对象（QTcpServer）或需自行管理生命周期。
> - Q: 如何处理粘包/半包？
> - A: TCP 是字节流无消息边界。方案：1) 定长消息；2) 消息头带长度字段（先读 4 字节长度再读 body）；3) 特殊分隔符。生产常用"长度前缀"协议。

### 描述 Qt 的 UDP 通信流程，以及其中涉及到的类的作用
**回答话术：**
UDP 用 `QUdpSocket`，无连接，面向数据报：
1. 创建 `QUdpSocket`
2. 接收数据必须先 `bind()` 绑定端口
3. 发送用 `writeDatagram(data, host, port)`
4. 接收在 `readyRead` 槽中用 `readDatagram(buf, size)` 读取数据报

**知识点讲解：**
```cpp
QUdpSocket socket;
socket.bind(QHostAddress::Any, 8888);
connect(&socket, &QUdpSocket::readyRead, [&] {
    QByteArray buf(1024, 0);
    QHostAddress from; quint16 port;
    qint64 n = socket.readDatagram(buf.data(), buf.size(), &from, &port);
    // from/port 记录数据报来源
});
socket.writeDatagram("hello", QHostAddress("127.0.0.1"), 8888);
```
> [!Info] 可能的追问:
> - Q: UDP 和 TCP 的 Qt 类使用有什么关键差异？
> - A: UDP 无连接：不需要 connect，直接 writeDatagram；必须 bind 才能接收；readDatagram 一次读一个完整数据报（有边界），无粘包问题。TCP 面向字节流，有连接建立/断开，有粘包。UDP 快但不可靠（丢包/乱序），适合音视频实时传输。

### 说一下你对 Qt connect 函数连接方式的理解
**回答话术：**
connect 第五个参数控制连接类型，6 种：
1. `Qt::AutoConnection`（默认）：同一线程用 Direct，跨线程用 Queued
2. `Qt::DirectConnection`：信号发出时立即同步调用槽，槽在发送者线程执行；跨线程用可能造成数据竞争
3. `Qt::QueuedConnection`：信号入队，槽在接收者线程事件循环中异步执行
4. `Qt::BlockingQueuedConnection`：跨线程同步等待槽执行完，发送者阻塞；收发同线程会死锁
5. `Qt::UniqueConnection`：按位或组合，避免重复连接
6. `Qt::AutoCompatConnection`：Qt4 兼容，等同 Auto

**知识点讲解：**
```cpp
// 同一线程同步：默认即可
connect(a, &A::sig, b, &B::slot);
// 跨线程异步
connect(a, &A::sig, b, &B::slot, Qt::QueuedConnection);
// 跨线程同步等待结果
connect(a, &A::sig, b, &B::slot, Qt::BlockingQueuedConnection);
// 防止重复连接
connect(a, &A::sig, b, &B::slot, Qt::UniqueConnection);
```
> [!Info] 可能的追问:
> - Q: Direct 和 Queued 的本质区别？
> - A: Direct 是同步函数调用（同线程直接调，跨线程是"在错误线程执行"很危险）。Queued 是异步事件投递：参数序列化入队，接收线程事件循环取出后调用。所以 Queued 天然支持跨线程，Direct 跨线程是危险的。
> - Q: BlockingQueuedConnection 什么时候用？
> - A: 需要跨线程"同步等待槽执行完再继续"的场景，如工作线程通知 UI 线程处理完数据后再继续。注意收发必须在不同线程，否则死锁（发送者在等自己）。

### 槽函数在什么线程中执行？
**回答话术：**
由 connect 的连接类型决定：
- `DirectConnection`：槽在**发送者**线程执行（立即同步调用）
- `QueuedConnection`：槽在**接收者**线程执行（异步，接收者线程事件循环）
- `AutoConnection`：同线程=Direct（发送者线程），跨线程=Queued（接收者线程）

**知识点讲解：**
```cpp
// 跨线程时，槽在接收者对象所在线程执行
// 所以 moveToThread 决定槽的执行线程
worker->moveToThread(&thread);
connect(this, &MainWin::start, worker, &Worker::doWork);  // Auto -> Queued，doWork 在 thread 执行
```
> [!Info] 可能的追问:
> - Q: 如何让槽固定在某线程执行？
> - A: 用 `moveToThread()` 把接收者对象移动到目标线程，再用 AutoConnection 连接。槽的执行线程 = 接收者对象所在线程（Queued 时）。这是 Qt 官方推荐的工作线程模式：QThread 本身只承载事件循环，业务对象 moveToThread 后通过信号槽驱动。

### 信号槽是同步的还是异步的？分别如何实现？
**回答话术：**
取决于连接类型：
- `DirectConnection`：**同步**。`emit` 语句后的代码在所有槽执行完才继续。槽调用类似直接函数调用。
- `QueuedConnection`：**异步**。`emit` 发出信号后立即返回，槽被投递到接收者线程事件队列，等接收者事件循环取出才执行。
- `AutoConnection`：同线程=同步，跨线程=异步。

**知识点讲解：**
```cpp
// 同步：emit 后代码等槽执行完
emit signal();  // 直接连接，槽执行完才到下一行
// 异步：emit 立即返回，槽稍后执行
emit signal();  // 队列连接，立即返回，槽排队等待
```
> [!Info] 可能的追问:
> - Q: 为什么跨线程默认异步？
> - A: 如果跨线程同步调用，需要阻塞发送线程等待槽在接收线程执行完，可能死锁（接收线程正等待发送线程做别的事）。异步投递让发送线程不阻塞，接收线程在自己的事件循环处理，是线程安全的通信方式。需要同步时才用 BlockingQueuedConnection。

### MVD 模型是什么？
**回答话术：**
Qt 的 Model/View/Delegate（MVD）架构，三部分各司其职：
- **Model（模型）**：保存数据，负责增删改查，提供数据给视图
- **View（视图）**：负责展示数据
- **Delegate（代理）**：负责 Item 的绘制样式和编辑交互

三者通过信号槽通信：Model 数据变化发信号通知 View 刷新；View 编辑数据时 Delegate 把编辑状态发回 Model。
基类：`QAbstractItemModel` / `QAbstractItemView` / `QAbstractItemDelegate`。默认实现：`QTableWidget`、`QListWidget`、`QTreeWidget`。
**知识点讲解：**
```cpp
// 自定义模型最少实现：
class MyModel : public QAbstractTableModel {
    int rowCount(...) override;
    int columnCount(...) override;
    QVariant data(...) override;          // 提供数据给视图
    bool setData(...) override;           // 编辑数据
    Qt::ItemFlags flags(...) override;
};
// 用 QTableView + 自定义 delegate 控制编辑控件
```
> [!Info] 可能的追问:
> - Q: MVD 相比直接放控件有什么好处？
> - A: 解耦数据与显示：同一份数据可挂多个视图（表格+图表），数据变更自动刷新所有视图；大数据量下视图只加载可见部分（性能）；Delegate 可自定义编辑控件而不改模型。
> - Q: Model 数据变化如何通知 View？
> - A: 通过信号槽。模型用 `beginInsertRows`/`endInsertRows`、`dataChanged` 等信号通知视图。视图收到后局部刷新对应区域，而不是全量重绘。

### Qt 事件过滤级别
**回答话术：**
Qt 事件处理有 5 个层级（功能从弱到强）：
1. **重载特定事件处理函数**：`mousePressEvent()`、`keyPressEvent()` 等，最常用
2. **重载 `event()` 函数**：在特定处理函数之前处理，可处理无对应处理函数的罕见事件
3. **给 Qt 对象安装事件过滤器**：A 对象 `installEventFilter` 监视 B 对象，B 的事件先经 A 的 `eventFilter()` 处理
4. **给 QApplication 安装事件过滤器**：所有事件发往任何过滤器前都先经 qApp 的过滤器
5. **继承 QApplication 重载 `notify()`**：在任何过滤器之前拿到所有事件，最终极手段

**知识点讲解：**
```cpp
// 事件过滤器：A 监视 B
B->installEventFilter(A);   // A 是 QObject*
bool A::eventFilter(QObject* watched, QEvent* event) override {
    if (watched == B && event->type() == QEvent::KeyPress) {
        // 拦截处理
        return true;   // true=已处理，不再分发；false=继续传递
    }
    return QObject::eventFilter(watched, event);
}
```
> [!Info] 可能的追问:
> - Q: 事件过滤器返回 true/false 的区别？
> - A: 返回 true 表示事件已被处理，停止继续分发（事件不会到目标对象的 event() 和特定处理函数）。返回 false 表示不处理，事件继续走正常分发链路。注意过滤器链是逆序的（后安装的先执行）。
> - Q: 什么时候用 event() 重载 vs 事件过滤器？
> - A: 重载 event() 用于"本类自己处理自己事件"，事件过滤器用于"一个对象监视另一个对象的事件"（如父窗口拦截子控件事件），或在不改子类代码的情况下拦截第三方控件事件。

### Qt 事件循环
**回答话术：**
Qt 事件循环是一个 while 循环，从事件队列中取出事件并分发给对应对象。核心概念：
- 主事件循环由 `QCoreApplication::exec()` 启动，`exit()` 结束
- 本地事件循环可用 `QEventLoop` 构建（如 `QDialog::exec()` 内部跑一个局部事件循环）
- 事件来源：窗口系统事件、定时器、信号槽队列连接、`postEvent` 投递的自定义事件
- `sendEvent` 同步立即分发；`postEvent` 异步投递到队列

**知识点讲解：**
```cpp
QCoreApplication app(argc, argv);
app.exec();   // 进入事件循环，阻塞直到 quit()
// 局部事件循环：
QEventLoop loop;
connect(&timer, &QTimer::timeout, &loop, &QEventLoop::quit);
timer.start(1000);
loop.exec();  // 阻塞 1 秒后退出局部循环
```
> [!Info] 可能的追问:
> - Q: exec() 会阻塞主线程吗？UI 为什么会响应？
> - A: exec() 阻塞的是"当前函数往下执行"，但内部在循环处理事件队列，所以 UI 仍能响应。这就是为什么 UI 线程不能做耗时操作——exec() 循环被占用就无法处理绘制/输入事件，界面卡死。
> - Q: 为什么 deleteLater 依赖事件循环？
> - A: deleteLater 是投递一个 `DeferredDelete` 事件，只有回到事件循环处理这个事件才真正 delete。如果对象所在线程没有事件循环在跑，deleteLater 不会执行，对象泄漏。

### 如果一个信号的处理方法一直未被执行有哪些可能性？
**回答话术：**
1. **连接被断开**：`disconnect` 或对象被销毁（接收者销毁自动断连）
2. **连接失败**：信号/槽签名不匹配、接收者对象不存在、自定义类型未注册
3. **跨线程排队**：QueuedConnection 下槽在接收者线程事件队列等待，若接收者线程阻塞（耗时操作/死锁）或事件循环未启动，槽永远不会执行
4. **连接类型问题**：BlockingQueuedConnection 同线程导致死锁
5. **信号没发出来**：发射条件未满足、信号被 `blockSignals` 阻塞

**知识点讲解：**
```cpp
// 排查思路
qDebug() << connect(...);  // connect 返回 bool，false=连接失败
// 检查接收者线程是否有 exec()
// 检查是否 blockSignals(true)
```
> [!Info] 可能的追问:
> - Q: connect 返回 false 的常见原因？
> - A: 1) 信号或槽不存在/签名不匹配；2) 函数指针重载歧义（需 qOverload）；3) 接收者对象是 nullptr；4) 自定义参数类型未注册（跨线程时）。

### Qt 信号和槽的本质是什么？
**回答话术：**
信号槽是 Qt 实现的**观察者模式**，本质是**编译期类型安全、运行期动态连接的对象间通信机制**。核心特性：
- 信号是 MOC 生成的函数（无函数体），槽是普通函数/成员函数/lambda
- 连接在运行期建立（connect），可动态断开
- 一对多：一个信号可连多个槽，多个信号可连同一槽
- 与回调函数比：类型安全（签名检查）、自动管理生命周期（接收者销毁自动断连）
**知识点讲解：**
信号槽比普通回调强在哪：普通回调（函数指针）不检查参数类型、不跟踪对象生命周期，悬挂回调是致命问题。信号槽通过 MOC 的索引机制 + QObject 生命周期管理，避免这些问题。
> [!Info] 可能的追问:
> - Q: 信号槽和直接函数调用/回调的本质区别？
> - A: 直接调用是编译期绑定、强耦合；回调是运行期绑定但无类型安全和生命周期管理；信号槽是运行期绑定 + 类型安全 + 自动断连，解耦发送者与接收者。这是它成为 Qt 核心通信机制的原因。

### Qt 5 的信号槽与 Qt 4 相比有什么改进？
**回答话术：**
Qt5 的信号槽相比 Qt4 的改进（主要是类型安全）：
1. **编译期检查**：Qt5 用函数指针连接，信号/槽存在性和签名在编译期检查，Qt4 的 `SIGNAL`/`SLOT` 宏是字符串，只能在运行期报错
2. **支持连接任意函数**：Qt5 可以连接普通函数、成员函数、lambda（Qt4 只能连接信号和槽）
3. **参数类型灵活**：参数可用 typedef、不同 namespace 修饰；允许自动类型转换（信号和槽参数类型不必完全匹配）
4. **重载处理**：函数指针连接遇到重载信号需用 `qOverload` 指定

**知识点讲解：**
```cpp
// Qt4（字符串宏，运行期检查）
connect(a, SIGNAL(valueChanged(int)), b, SLOT(update(int)));
// Qt5（函数指针，编译期检查，类型安全）
connect(a, &A::valueChanged, b, &B::update);
// Qt5 + lambda
connect(a, &A::valueChanged, this, [=](int v) { /* ... */ });
// 重载信号需指定
connect(a, qOverload<int>(&A::valueChanged), b, &B::update);
```
> [!Info] 可能的追问:
> - Q: Qt4 和 Qt5 连接方式的兼容性？
> - A: Qt5 仍支持 Qt4 的字符串宏语法（`SIGNAL`/`SLOT`），但推荐函数指针。Qt6 中字符串宏已移除。函数指针方式的好处：编译期就能发现信号/槽拼写错误、签名不匹配，避免运行期"连接没生效"的隐性 bug。
> - Q: 为什么 Qt5 允许槽参数少于信号参数？
> - A: 槽可以忽略多余的信号参数（槽参数是信号参数的前缀子集即可）。这是连接规则：信号可以"携带"更多信息，槽只取需要的前 N 个。Qt4 字符串连接不检查，Qt5 函数指针连接在编译期就允许这种"参数子集"匹配。

### 槽函数参数、信号的参数
**回答话术：**
信号与槽的参数匹配规则：
- 槽的参数可以**少于**信号参数（取信号参数的前缀子集），多余的信号参数被忽略
- 槽的参数不能多于信号参数
- 参数类型需兼容（可隐式转换）
- 槽的返回值被忽略，所以槽一般声明为 `void`
- 信号的返回值必须是 `void`（信号没有函数体）

**知识点讲解：**
```cpp
signals:
    void sig(int a, int b, int c);
public slots:
    void slot1(int a);            // 合法：少于信号参数
    void slot2(int a, int b);     // 合法
    void slot3(int a, int b, int c);  // 合法：等于
    // void slot4(int a, int b, int c, int d);  // 非法：多于信号
```
> [!Info] 可能的追问:
> - Q: 信号槽签名匹配是编译期还是运行期检查？
> - A: Qt5 函数指针连接是编译期检查签名，Qt4 字符串连接是运行期检查（不匹配只在 connect 时报 warning）。但"槽参数少于信号"这种子集匹配，Qt5 编译期就允许。
> - Q: 为什么信号必须返回 void？
> - A: 信号是"广播"通知，可能有多个槽响应，无法定义"返回值"（哪个槽的返回值？）。所以信号强制 void，槽的返回值也设计为被忽略。

### Qt 信号槽的四种写法？
**回答话术：**
1. **字符串宏（Qt4 风格）**：`connect(a, SIGNAL(clicked()), this, SLOT(close()));`，运行期检查，Qt6 移除
2. **函数指针**：`connect(a, &A::clicked, this, &W::close);`，编译期类型安全
3. **qOverload 指定重载**：`connect(a, qOverload<int>(&A::sig), this, &W::slot);`
4. **lambda**：`connect(a, &A::clicked, this, [=]() { ... });`

连接方式（第五参数）：Auto/Direct/Queued/BlockingQueued/Unique + 组合。
**知识点讲解：**
```cpp
// 1. 宏（不推荐，运行期检查）
connect(a, SIGNAL(clicked()), this, SLOT(close()));
// 2. 函数指针（推荐）
connect(a, &QPushButton::clicked, this, &QMainWindow::close);
// 3. 重载
connect(a, qOverload<int>(&QComboBox::currentIndexChanged), this, &W::onIndex);
// 4. lambda（适合简单逻辑）
connect(a, &QPushButton::clicked, this, [=](bool checked) { /* ... */ });
```
> [!Info] 可能的追问:
> - Q: 为什么推荐函数指针而非字符串宏？
> - A: 函数指针连接在编译期检查信号/槽是否存在、签名是否匹配，拼写错误/签名错误直接编译报错。字符串宏是运行期用字符串匹配，错误只在运行时 warning（且易被忽略），还引入额外字符串查找开销。

### 多个信号如何关联一并处理？
**回答话术：**
多个信号连到同一槽函数，槽内需要区分来源时有两种方式：
1. **信号带标识参数**：发送信号时附带一个 int/枚举标识，槽内根据标识区分是哪个信号
2. **`sender()` 函数**：槽内调用 `sender()` 获取发射信号的 QObject 指针，判断是哪个对象发的

**知识点讲解：**
```cpp
// 方式1：信号带标识
connect(a, &A::sigA, this, &W::handle);   // sigA 内部 emit sig(1)
connect(b, &B::sigB, this, &W::handle);   // sigB 内部 emit sig(2)
void W::handle(int id) { /* 根据 id 区分 */ }
// 方式2：sender()
connect(a, &A::clicked, this, &W::onAnyClicked);
connect(b, &B::clicked, this, &W::onAnyClicked);
void W::onAnyClicked() {
    if (sender() == a) { /* A 触发 */ }
    else if (sender() == b) { /* B 触发 */ }
}
```
> [!Info] 可能的追问:
> - Q: sender() 的注意事项？
> - A: `sender()` 返回的指针在槽被调用时有效，但可能为 nullptr（信号由非 QObject 发出，如直接函数调用）。且信号槽连接中如果用 lambda 且不指定接收者，`sender()` 仍可工作但 lambda 里要注意捕获。不要保存 sender() 返回值供槽返回后使用（对象可能已销毁）。

### 对 QObject 的理解
**回答话术：**
QObject 是 Qt 对象模型的核心基类，几乎所有 Qt 类都继承它。它提供的能力：
- **信号槽**：`connect`/`disconnect` 建立/断开对象通信，`blockSignals` 临时阻塞信号
- **对象树**：父对象管理子对象生命周期，父析构时自动删除子对象，通过 `children()` 访问子对象列表
- **对象元信息**：`objectName()`、`metaObject()`（类名）、`inherits()`（判断继承关系）
- **事件系统**：`event()` 接收事件，`installEventFilter`/`eventFilter` 过滤事件
- **定时器**：`QTimer` 及底层事件支持
- **跨线程**：`moveToThread()` 改变线程依附性，`deleteLater` 延迟销毁

**要点**：任何要用信号槽/属性/元对象能力的类都要继承 QObject 并加 `Q_OBJECT` 宏（触发 MOC）。QObject **不可拷贝**（拷贝构造/赋值被禁用），因为其身份唯一、有父子关系。
**知识点讲解：**
```cpp
class MyWidget : public QWidget {
    Q_OBJECT   // 必须：MOC 识别信号槽/属性
    // Q_OBJECT 使类拥有 staticMetaObject、元方法表
};
```
> [!Info] 可能的追问:
> - Q: QObject 为什么禁止拷贝？
> - A: QObject 有唯一身份（objectName）、父子关系、信号槽连接。如果可拷贝，拷贝出的对象会共享连接/父子关系，语义混乱。所以 QObject 拷贝构造和赋值运算符被声明为 private（或删除）。这也是 Qt 控件不能按值传递的原因——要用指针或引用。
> - Q: Q_OBJECT 宏的作用？
> - A: Q_OBJECT 声明了 MOC 需要的元对象结构：`staticMetaObject`、虚函数 `metaObject()`、信号/槽的索引表、`qt_static_metacall` 分发函数。没有 Q_OBJECT，信号槽（尤其是跨类连接）无法工作。它还声明了 `tr()` 翻译函数等。

### 详解 Qt 中的内存管理机制
**回答话术：**
Qt 内存管理基于**对象树（父子关系）**：
- 继承 QObject 的对象，new 时**指定父对象**，父对象析构时自动删除所有子对象
- 顶层对象（无父）需自行管理，或由 QApplication 等持有
- **`deleteLater()`**：投递 DeferredDelete 事件，等事件循环处理完当前事件后再 delete，避免"事件处理期间删除对象"导致 use-after-free；多次调用安全
- 不建议直接 delete 有父对象的孩子，Qt 会从父对象列表移除，但若对象正在处理事件则危险

**注意**：Qt 对象树管理的是 **QObject 继承者**，普通 C++ 对象（非 QObject）不在此机制内，需自行管理或用手撕智能指针。
**知识点讲解：**
```cpp
QWidget* parent = new QWidget;
QPushButton* btn = new QPushButton(parent);  // btn 归 parent 管
// parent 析构 -> 自动 delete btn
// 安全删除：不要 delete btn，用 btn->deleteLater() 或直接删 parent
```
> [!Info] 可能的追问:
> - Q: 为什么 Qt 对象树不会 delete 两次？
> - A: 父对象析构时遍历 children 逐个 delete，同时从自己的 children 列表移除。每个子对象只被父对象删除一次。如果手动 delete 了子对象，其析构函数会自动从父对象 children 列表移除自己，避免父析构时再次删除（双重删除）。
> - Q: deleteLater 和直接 delete 的区别？
> - A: 直接 delete 立即析构释放内存，若对象正在处理事件（如槽函数中 delete 发送者）会 use-after-free。deleteLater 把析构推迟到事件循环，等当前事件处理完再删，安全且多次调用无害。没有事件循环在跑时 deleteLater 不生效。

### Qt 对象树
**回答话术：**
对象树是 Qt 管理 QObject 生命周期的机制：每个 QObject 可指定父对象，父对象通过 children() 维护子对象链表；父析构时递归删除所有子对象，保证没有对象被 delete 两次。
- 创建子对象时传入父指针，自动加入父的 children() 列表
- 子对象析构时自动从父列表中移除自己
- 手动回收建议 `deleteLater` 而非 `delete`

**知识点讲解：**
```cpp
QObject* root = new QObject;
QObject* child = new QObject(root);       // 自动加入 root->children()
// root 析构 -> 递归删除所有子对象
// 查找子对象
QList<QObject*> kids = root->children();
QWidget* w = root->findChild<QWidget*>();          // 深度优先找一个
QList<QWidget*> ws = root->findChildren<QWidget*>(); // 找所有
```
> [!Info] 可能的追问:
> - Q: 对象树的父子关系和 C++ 继承的父子关系一样吗？
> - A: 完全不一样。C++ 继承是类型层次关系（is-a），对象树的父子是**所有权/生命周期**关系（has-a 的归属）。一个 QPushButton 的 C++ 父类是 QWidget，但它的 Qt 父对象（owner）可以是任何 QObject，比如某个布局或窗口。
> - Q: 什么情况下对象树管理会失效？
> - A: 1) 子对象所在线程事件循环未运行时 deleteLater 不执行；2) 顶层对象（无父）不被任何对象树管理；3) 全局/静态 QObject 在程序退出时析构顺序不确定。开发中顶层窗口常由 QApplication 或 main 栈上变量管理。

### Qt 的 d-pointer 和 q-pointer 设计是什么？
**回答话术：**
这是 Qt 大量使用的 **PIMPL（Pointer to IMPLementation）** 模式，也叫 Opaque Pointer：
- **D 指针**：类头文件中只有一个指向私有实现结构体的指针 `QScopedPointer<WidgetPrivate> d;`，所有私有数据成员都在 `WidgetPrivate` 里，定义在源文件
- **Q 指针**：私有结构体里保存一个指向公有类的指针，让私有实现能访问公有类

**优点**：头文件不含实现细节（ABI 稳定，可作为 API 发布）；修改私有成员不触发整个工程的重新编译（编译速度）；隐藏实现细节。
```cpp
// widget.h（对外）
class Widget : public QObject {
    QScopedPointer<WidgetPrivate> d;   // D 指针
};
// widget.cpp（内部）
class WidgetPrivate {
    QWidget* owner;      // Q 指针
    int data;
};
```
> [!Info] 可能的追问:
> - Q: d-pointer 和直接放私有成员的区别？
> - A: 直接放私有成员，改动任何私有数据都要改头文件，导致所有包含该头文件的文件重新编译（工程大时几分钟到十几分钟）。d-pointer 把实现藏进 cpp，头文件稳定，改动私有数据只编译对应 cpp。这是 Qt 保证二进制兼容（添加私有成员不破坏已编译的库用户）的关键。
> - Q: 为什么 Qt 用 QScopedPointer 存 D 指针？
> - A: QScopedPointer 是所有权唯一的局部智能指针，对象析构时自动 delete D 对象，避免内存泄漏。相比裸指针，它提供 RAII 保证且不可拷贝。Qt 的 d 指针生命周期与公有类绑定。

### 说说 Qt 内定义的指针类型（智能指针全对比）
**回答话术：**
Qt 提供多套指针，各有用途：
- `QPointer<T>`：QObject 专用弱引用，对象析构自动置空。只适用于 QObject 子类
- `QScopedPointer<T>`：作用域独占指针，类似 `std::unique_ptr`，析构自动释放，不可拷贝
- `QSharedPointer<T>`：引用计数共享指针，类似 `std::shared_ptr`，支持自定义删除器
- `QWeakPointer<T>`：配合 QSharedPointer 的弱引用，解决循环引用，类似 `std::weak_ptr`
- `QSharedDataPointer<T>`：**写时复制（COW）**指针，多个对象共享同一份数据，修改时才深拷贝。`QString`、`QByteArray`、`QVariant` 的底层机制

与标准库对比：`QSharedPointer` 和 `std::shared_ptr` 类似但 QSharedPointer 支持 QObject（可在 QObject 析构时清理），std 版本更通用。`QSharedDataPointer` 是 std 没有的（COW 语义）。

**知识点讲解：**
```cpp
// QPointer：对象析构自动置空（弱引用）
QPointer<QWidget> wp(new QWidget);
delete wp;          // 外部 delete 后
if (wp) { /* 不执行，wp 已自动置空 */ }

// QSharedDataPointer：写时复制
QString s1 = "hello";        // 底层共享数据
QString s2 = s1;             // 共享同一份数据，无拷贝
s2[0] = 'H';                 // 修改时触发深拷贝，s1 不受影响
```
> [!Info] 可能的追问:
> - Q: QSharedPointer 和 std::shared_ptr 的区别？
> - A: 1) QSharedPointer 可以配合 QObject（QWeakPointer 可检测 QObject 销毁）；2) QSharedPointer 是 Qt 类，std::shared_ptr 是标准库；3) 类型转换：QSharedPointer 用 `qSharedPointerCast`，std 用 `std::dynamic_pointer_cast`；4) 默认删除器都是 delete。跨 Qt/STL 边界时优先 std::shared_ptr（更通用）。
> - Q: QSharedDataPointer 写时复制怎么实现的？
> - A: 内部维护一个引用计数。拷贝时只复制指针并递增计数（浅拷贝），修改数据前检查计数：若计数 >1 才深拷贝一份再修改（写时复制）。这保证了值语义（s2 改不影响 s1）的同时避免不必要的深拷贝。Qt 容器（QString/QByteArray 等）都基于此实现"隐式共享 + COW"。
> - Q: QSharedDataPointer 线程安全吗？
> - A: 引用计数的增减是原子的（线程安全），但"修改数据"本身不是——多个线程同时写同一个隐式共享对象仍需要外部同步。Qt 的隐式共享保证"不同对象共享数据时的并发读"安全。

### 详解 Qt 中的 QObject 线程依附性
**回答话术：**
每个 QObject 属于一个线程（创建它的线程）。规则：
- **线程安全**：QObject 及其子类都不是线程安全的，但**可重入**（不同实例可在不同线程用，同一实例不能多线程同时访问）
- **改变依附性**：`moveToThread()` 把对象及其子对象移动到另一线程，但**必须在对象当前所在线程内调用**
- **跨线程调用**：不要直接跨线程调 QObject 的方法，用**队列连接信号槽**或 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`
- 要求被调函数是槽或 `Q_INVOKABLE` 标记（元对象能识别）

**知识点讲解：**
```cpp
QThread thread;
Worker* worker = new Worker;          // 创建于主线程
worker->moveToThread(&thread);        // 必须在主线程调用
connect(this, &Main::sig, worker, &Worker::work, Qt::QueuedConnection);
thread.start();
// 跨线程调用其他接口：
QMetaObject::invokeMethod(worker, "setValue", Qt::QueuedConnection, Q_ARG(int, 42));
```
> [!Info] 可能的追问:
> - Q: 为什么 QObject 不是线程安全的？
> - A: QObject 内部维护事件队列、连接列表、子对象树等共享状态，没有内置锁。多线程同时访问同一对象会数据竞争。Qt 的设计哲学是"对象归线程所有，跨线程用消息传递（事件/信号槽）"，而不是给每个对象加锁（那样单线程场景也损失性能）。
> - Q: moveToThread 之后对象还能直接用吗？
> - A: 对象逻辑上属于新线程，应该只通过队列信号槽/invokeMethod 调用。直接调用其方法是在"调用者线程"执行，若方法操作了对象内部状态，就破坏了"对象归线程所有"的约束，造成数据竞争。正确做法是把对象当作"只属于新线程"，外部通过事件驱动。

### QObject 是否是线程安全的？
**回答话术：**
QObject 及其子类**不是线程安全的，但都是可重入的**：
- 可重入：不同实例可在不同线程各自使用（如两个 QWidget 分别在两个线程？不行，UI 只能主线程）
- 非线程安全：同一个 QObject 实例不能同时被多线程访问（除非内部数据已序列化加锁）
- UI 类（QWidget）只能主线程操作

**知识点讲解：**
"可重入" vs "线程安全"：线程安全 = 任何实例可被任意线程同时访问；可重入 = 不同实例可被不同线程同时访问（同一实例不行）。QObject 属可重入非线程安全。
> [!Info] 可能的追问:
> - Q: 那如何在多线程中用 QObject？
> - A: 每个对象归一个线程所有，跨线程通过事件（信号槽队列连接、postEvent、invokeMethod）通信。对象在线程 A 创建，moveToThread 到线程 B 后，B 的代码通过事件驱动它。绝不在两个线程直接读写同一对象。

### Qt 编程当中，多线程的两种使用方法？
**回答话术：**
1. **继承 QThread，重写 `run()`**：把要在线程执行的代码写进 `run()`，创建子类对象后 `start()`。简单但把"线程"和"任务"耦合在一起，QThread 子类做业务逻辑是不推荐的
2. **继承 QObject + moveToThread**（推荐）：业务逻辑放 QObject 的槽函数，主线程创建 QThread 和业务对象，`moveToThread(&thread)` 把业务对象移动到工作线程，连接信号槽驱动。QThread 只承载事件循环，业务对象通过事件驱动

**注意事项**：
- 业务对象构造时不能指定父对象（否则 moveToThread 会带上父对象）
- 子线程不能操作 UI
- 推荐用 QtConcurrent（线程池）处理无状态计算任务

**知识点讲解：**
```cpp
// 方法1（简单但耦合）
class MyThread : public QThread {
    void run() override { /* 线程代码 */ }
};
// 方法2（推荐）
class Worker : public QObject {
    Q_OBJECT
public slots:
    void doWork() { /* 线程代码 */ }
};
QThread thread;
Worker* worker = new Worker;   // 不能指定父对象！
worker->moveToThread(&thread);
connect(&thread, &QThread::started, worker, &Worker::doWork);
thread.start();
```
> [!Info] 可能的追问:
> - Q: 为什么推荐 moveToThread 而不是继承 QThread？
> - A: 继承 QThread 时 run() 里的业务逻辑和线程耦合，无法复用业务类；且如果 run() 里也用了信号槽，对象在错误线程。moveToThread 把"线程（QThread 承载事件循环）"和"业务（QObject 槽函数）"解耦，业务类可复用、可测试，多任务用多个槽函数驱动。这是 Qt 官方推荐模式。
> - Q: 子线程真的不能操作 UI 吗？
> - A: 不能直接操作（QWidget 只能在主线程）。要更新 UI 用信号槽：工作线程 emit 信号，UI 线程的槽（QueuedConnection）里更新界面。或者用 `QMetaObject::invokeMethod(uiObj, ..., Qt::QueuedConnection)`。

### 多线程下，信号槽分别在什么线程中执行，如何控制？
**回答话术：**
通过 connect 第五参数控制，见前述连接方式。核心规则：
- **DirectConnection**：槽在**发送者线程**立即同步执行（跨线程危险）
- **QueuedConnection**：槽在**接收者线程**事件循环异步执行（安全跨线程）
- **AutoConnection**：同线程 Direct，跨线程 Queued

多线程场景：跨线程通信用 QueuedConnection（或 Auto 默认），槽在接收者线程执行；需要跨线程同步等待用 BlockingQueuedConnection。
**知识点讲解：**
```cpp
// 跨线程：槽在 worker 所在线程执行
connect(this, &Main::start, worker, &Worker::run, Qt::QueuedConnection);
// 等价于 AutoConnection（跨线程时自动 Queued）
connect(this, &Main::start, worker, &Worker::run);
```
> [!Info] 可能的追问:
> - Q: 队列连接的参数是怎么跨线程传的？
> - A: 信号参数被 `QVariant` 序列化打包，投递一个事件到接收者线程的事件队列，接收线程的事件循环取出事件后反序列化调用槽。所以参数必须可拷贝、需 `qRegisterMetaType` 注册自定义类型。这是线程间"消息传递"而非"共享状态"，天然安全。

### Qt 的多线程，哪些是只有 QThread 能实现，QtConcurrent 办不到的？
**回答话术：**
1. **信号槽机制**：QThread 线程内可用信号槽驱动业务，QtConcurrent 是纯函数式（无 QObject）
2. **线程优先级**：QThread 可设置优先级，QtConcurrent 线程池不可控
3. **线程生命周期管理**：QThread 可控制线程启动/停止/等待，QtConcurrent 只是提交任务到全局线程池
4. **复杂交互**：QThread + moveToThread 适合有状态、需要信号槽交互的对象；QtConcurrent 适合无状态计算任务（并行 map/filter/reduce）

**知识点讲解：**
```cpp
// QtConcurrent：适合并行计算
QFuture<int> f = QtConcurrent::run([] { return heavyCalc(); });
int result = f.result();   // 阻塞等待结果
// 或用 mapped/reduce 并行处理容器
QFuture<Type> f = QtConcurrent::mapped(list, [](T t) { return process(t); });
```
> [!Info] 可能的追问:
> - Q: QtConcurrent::run 和 std::async 区别？
> - A: QtConcurrent::run 用 Qt 全局线程池（默认与 CPU 核数相关），返回 `QFuture` 可用 `QFutureWatcher` 接信号槽（跨线程通知）。std::async 用标准线程（或平台线程池），返回 `std::future`，结果同步等待或轮询。Qt 生态内用 QFuture + QFutureWatcher 能融入事件循环。

### Qt 如何安全地在另外一个线程中调用 QObject 对象的接口？
**回答话术：**
不能直接跨线程调用（QObject 非线程安全）。安全方式：
1. **队列连接信号槽**：跨线程 emit 信号，槽在接收者线程事件循环执行
2. **`QMetaObject::invokeMethod(..., Qt::QueuedConnection)`**：把调用作为事件投递到对象所在线程
3. 要求目标函数是槽或 `Q_INVOKABLE` 标记（元对象能识别）
4. 确保接收者线程有事件循环在运行

**知识点讲解：**
```cpp
// 方式1：信号槽（槽需是 Q_INVOKABLE 或 slots）
emit someSignal();   // 跨线程 QueuedConnection，槽在目标线程执行
// 方式2：invokeMethod
QMetaObject::invokeMethod(obj, "updateUI", Qt::QueuedConnection);
// 带参数
QMetaObject::invokeMethod(obj, "setValue", Qt::QueuedConnection,
                          Q_ARG(int, 42), Q_ARG(QString, "hello"));
```
> [!Info] 可能的追问:
> - Q: invokeMethod 和直接调用的区别？
> - A: DirectConnection 是直接函数调用（在调用线程执行，有线程安全问题）。QueuedConnection 的 invokeMethod 是投递事件到目标线程，在目标线程执行，线程安全。跨线程场景永远用 Queued 版。
> - Q: 为什么要求槽函数或 Q_INVOKABLE？
> - A: 因为 invokeMethod 要通过元对象系统按函数名查找并调用，只有被 MOC 记录的槽函数和 Q_INVOKABLE 标记的普通函数能被元对象系统识别。普通成员函数不在元对象表中，无法被 invokeMethod 调用。

### 创建 signal 类？ QVariant 应用？
**回答话术：**
**信号类**：继承 QObject，用 `signals:` 关键字声明信号，MOC 生成信号函数。信号类只是"信号声明容器"，信号本身无函数体。
**QVariant**：Qt 的类型擦除容器，可存储任意注册类型（int、QString、QList、自定义类型）。应用场景：
- 信号槽跨线程参数传递（序列化）
- 属性系统（Q_PROPERTY 值）
- 数据库字段值
- QSettings 配置存取

**知识点讲解：**
```cpp
class MySignals : public QObject {
    Q_OBJECT
public:
signals:
    void mySignal(int value);
    void anotherSignal(QString text, int count);
};
// QVariant 使用
QVariant v = 123;
int n = v.toInt();                 // 类型转换
QVariant m = QVariant::fromValue<MyStruct>(s);  // 自定义类型
bool ok = m.canConvert<MyStruct>();             // 检查可转换
```
> [!Info] 可能的追问:
> - Q: QVariant 是如何存储任意类型的？
> - A: 内部用联合（union）存内置类型值（int/double/void* 等），复杂类型存 `void*` 指向堆上对象。通过注册的类型信息（QMetaType）做类型识别和转换。`Q_DECLARE_METATYPE` 宏让自定义类型可被 QVariant 存储，`qRegisterMetaType` 让它可以跨线程信号槽传递。
> - Q: QVariant 和 std::variant 区别？
> - A: QVariant 是**类型擦除 + 运行期转换**（存的值可运行时转任意注册类型，失败返回默认），允许隐式转换，效率低一点。std::variant 是**编译期类型安全**（只能存声明的那几种类型），用 std::get/visit 访问，无转换。QVariant 灵活但慢，std::variant 严格但快。

### QString 与基本数据类型如何转换？
**回答话术：**
- **QString -> 数值**：`str.toInt()`、`str.toDouble()`、`str.toFloat()`、`str.toLongLong()` 等；可传 `bool* ok` 判断转换是否成功
- **数值 -> QString**：`QString::number(int)`、`QString::number(double)` 静态函数，可指定进制/精度
- **QString -> QByteArray**：`str.toUtf8()` / `toLocal8Bit()`（注意编码）
- **QString -> std::string**：`str.toStdString()`

**知识点讲解：**
```cpp
QString s = "123";
bool ok;
int n = s.toInt(&ok);            // ok 判断是否转换成功
QString s2 = QString::number(3.14159, 'f', 2);  // "3.14"
QString s3 = QString::number(255, 16);           // "ff"
// 编码注意
QString utf8 = QString::fromUtf8(bytes);
```
> [!Info] 可能的追问:
> - Q: QString 和 std::string 转换的编码问题？
> - A: `toStdString()` 默认按 UTF-8（Qt5+）转成 std::string。中文必须注意两边编码一致，否则乱码。`fromStdString` 假定输入是 UTF-8。跨平台建议统一用 UTF-8。
> - Q: QString 内部存储是什么编码？
> - A: QString 内部用 UTF-16（QChar 是 2 字节），与编码无关；输入输出时通过 `toUtf8`/`fromUtf8` 等转换。所以 QString 能正确处理任何 Unicode 字符，不受本地编码影响。

### 自定义控件的方法主要是哪些？
**回答话术：**
自定义控件从两个维度切入：
1. **外观（视觉）**：
   - **QSS 样式表**：用 CSS 语法设置颜色/边框/圆角等（最常用，无需重写代码）
   - **重写绘制函数**：`paintEvent()` 用 QPainter 自绘
   - **继承 QStyle 相关类**：定制系统级绘制风格（Qt6 起样式表统一走 QStyle 分支）
   - **组合拼装**：把多个现有控件组合成复合控件
2. **功能（行为）**：
   - 重写事件函数（`mousePressEvent` 等）
   - 添加/修改信号槽
   - 继承 QWidget 或其子类实现自定义逻辑

**知识点讲解：**
```cpp
// QSS 方式（简单）
btn->setStyleSheet("QPushButton { border-radius: 10px; background: red; }");
// 自绘方式（灵活）
class MyWidget : public QWidget {
    void paintEvent(QPaintEvent*) override {
        QPainter p(this);
        p.setBrush(Qt::blue);
        p.drawRect(rect());
    }
};
```
> [!Info] 可能的追问:
> - Q: QSS 和自绘 paintEvent 怎么选？
> - A: 简单静态样式用 QSS（快、易维护、可换肤）；需要动态绘制/复杂图形/动画用 paintEvent 自绘；需要系统级统一风格用 QStyle。QSS 底层最终也走 QStyle 分支（Qt6 样式表由 QStyleSheetStyle 实现），但语法更简洁。
> - Q: 如何用 Qt Designer 做自定义控件？
> - A: 通过插件机制：实现 `QDesignerCustomWidgetInterface` 接口，把自定义控件编译成插件，Designer 就能拖拽使用。这是 Qt Designer 的扩展机制，方便可视化编辑自定义控件。

### 什么是 QML？QWidget 和 QML 的技术本质区别？
**回答话术：**
**QML** 是基于 JavaScript 的声明式 UI 语言，用于定义界面；**QWidget** 是基于 C++ 的命令式 UI 框架。
区别：
- **语言**：QML 是声明式（描述界面长什么样，数据绑定自动更新），QWidget 是命令式（代码控制每个控件）
- **运行环境**：QML 由 QQuick/QtQuick 渲染（场景图 + GPU），QWidget 用 QPainter（CPU 光栅化）
- **性能**：QML 动画/复杂界面更流畅（GPU 加速），QWidget 简单界面开发快
- **适用**：QWidget 适合桌面工具类软件（VS Code 插件、小工具）、传统桌面应用；QML 适合现代 UI、移动端、富动画界面
- **数据绑定**：QML 内置属性绑定（声明式），QWidget 需手动 connect/更新

**知识点讲解：**
```qml
// QML 声明式：界面 + 数据绑定
Rectangle {
    width: 200; height: 100
    color: mouseArea.pressed ? "blue" : "gray"
    Text { text: "Hello"; anchors.centerIn: parent }
    MouseArea { id: mouseArea; anchors.fill: parent }
}
```
> [!Info] 可能的追问:
> - Q: 什么时候用 QWidget 什么时候用 QML？
> - A: 复杂表格/文本编辑器/传统桌面业务（QWidget 成熟、控件丰富）；移动端、触摸交互、动画转场、复杂自定义 UI（QML + Qt Quick 更高效）。两者可混用（QQuickWidget 嵌入 QWidget）。
> - Q: QML 怎么和 C++ 交互？
> - A: 通过 `QObject` 暴露给 QML：`engine.rootContext()->setContextProperty("obj", &cppObj);` 或注册类型 `qmlRegisterType<MyClass>("MyLib", 1, 0, "MyClass")`。C++ 对象的信号/属性/槽/`Q_INVOKABLE` 方法可被 QML 直接使用（元对象系统）。

### 常用的 Qt 布局有几种？如何自适应缩放？
**回答话术：**
Qt 布局管理器：
1. `QHBoxLayout` 水平布局
2. `QVBoxLayout` 垂直布局
3. `QGridLayout` 栅格布局（表格，支持跨行跨列）
4. `QFormLayout` 表单布局（标签+字段）
5. `QStackedLayout`/`QStackedWidget` 堆叠布局（一次显示一个页面）

**自适应缩放**：布局管理器根据窗口大小自动调整控件尺寸和位置；用 `setSizePolicy()` 设置控件伸缩策略，`setStretchFactor()` 设置伸缩因子控制比例。

**知识点讲解：**
```cpp
QVBoxLayout* main = new QVBoxLayout;
QHBoxLayout* row = new QHBoxLayout;
row->addWidget(label, 0);             // 0 = 不伸缩
row->addWidget(edit, 1);              // 1 = 拉伸系数，占据剩余空间
row->addWidget(btn, 0);
main->addLayout(row);
widget->setLayout(main);
```
> [!Info] 可能的追问:
> - Q: 不用布局手动 setGeometry 有什么问题？
> - A: 手动定位在窗口大小变化时不会自动调整，控件会重叠/超出；且不同平台字体/DPI 差异导致布局错乱。布局管理器自动处理大小策略、最小尺寸、窗口缩放，是 Qt 推荐方式。
> - Q: setSizePolicy 的策略有哪些？
> - A: `Fixed`（固定）、`Minimum`、`Maximum`、`Preferred`、`Expanding`、`MinimumExpanding`、`Ignored`。它告诉布局管理器控件如何响应空间变化。配合 `setStretchFactor` 控制控件在多余空间中的分配比例。

### 使用样式表要注意的点
**回答话术：**
QSS 关键注意点：
1. **属性会传递到子控件**：父控件设样式后子控件继承（除非子控件自己覆盖），最小尺寸等属性无法用 `setFixHeight` 撤销，必须用 QSS 重新设置
2. **选择器**：类选择器 `QPushButton`、对象名 `#btn`、状态 `QPushButton:hover`、属性选择器
3. **优先级**：子类/对象名选择器 > 类选择器 > 通配符；后设置的覆盖先设置的
4. **不支持所有属性**：QSS 只支持 QStyle 能处理的属性（部分 CSS 属性无效）
5. **动态修改**：改样式后需 `widget->style()->unpolish(widget)` + `polish(widget)` 或 `setStyleSheet("")` 刷新

**知识点讲解：**
```css
QPushButton#okButton {           /* 对象名选择器 */
    background: green;
}
QPushButton:hover {              /* 状态选择器 */
    background: lightgreen;
}
QPushButton[checked="true"] {    /* 属性选择器 */
    background: blue;
}
```
> [!Info] 可能的追问:
> - Q: 样式表优先级怎么算？
> - A: 选择器 specificity 高的优先：ID/对象名 > 类 > 类型；同优先级后声明的覆盖先声明的。子控件选择器（`QComboBox::drop-down`）优先级高于类型选择器。!important 也可用。
> - Q: QSS 和传统 QStyle 什么关系？
> - A: QSS 是 QStyle 的配置语言。Qt 用 `QStyleSheetStyle` 这个包装样式解释 QSS，最终仍走 QStyle 绘制。所以 QSS 能改的属性 = QStyle 暴露的可配置项，超出范围的不生效。

### Qt 绘制原理：双缓冲机制
**回答话术：**
双缓冲：绘制先画到**离屏缓冲（绘制缓冲区）**，画完一次性整体刷新到**显示缓冲区（屏幕）**，避免绘制过程中的闪烁（每次局部重绘导致背景闪烁）。
Qt 中 QWidget 默认自动启用双缓冲（Qt 内部用 QBackingStore 实现）。自绘时：
- 重写 `paintEvent`，用 QPainter 绘制，Qt 自动管理双缓冲
- 需要自定义离屏缓冲可用 `QPixmap`（内存中绘图，再 blit 到窗口）

**知识点讲解：**
```cpp
void MyWidget::paintEvent(QPaintEvent*) {
    QPainter p(this);            // Qt 自动双缓冲
    p.drawLine(...);             // 画到缓冲，不闪烁
    p.drawPixmap(rect(), cachedPixmap);
}
// 自定义离屏：
QPixmap buffer(size());
{
    QPainter b(&buffer);
    b.drawRect(...);             // 先在离屏画
}
QPainter(this).drawPixmap(0, 0, buffer);  // 一次性上屏
```
> [!Info] 可能的追问:
> - Q: 为什么自绘会闪烁？
> - A: 没有双缓冲时，窗口系统在清空背景和绘制内容之间有空窗，用户看到"闪白/闪黑"。双缓冲把整帧画好在内存，一次交换到屏幕，消除闪烁。QWidget 默认已开，但 `setAttribute(Qt::WA_OpaquePaintEvent)` 或自绘复杂场景需注意。
> - Q: QWidget 的双缓冲和 QML 的场景图有什么区别？
> - A: QWidget 双缓冲是"离屏 QPixmap + blit"，CPU 光栅化。QML/Qt Quick 用场景图（scene graph）+ OpenGL/Vulkan GPU 渲染，绘制节点合并提交，动画更流畅。所以复杂动画/大量元素用 QML。

### Graphics View 图形视图框架结构
**回答话术：**
Graphics View 是 Qt 的 2D 图形框架，核心三件套：
- **`QGraphicsScene`（场景）**：管理所有图形项（`QGraphicsItem`），维护它们的坐标、Z 序、选中状态
- **`QGraphicsItem`（图形项）**：可显示/交互的图形元素基类（矩形、椭圆、文本、Pixmap、自定义）
- **`QGraphicsView`（视图）**：显示场景的可滚动窗口，支持缩放、平移、旋转

其他：`QGraphicsWidget`（可放控件的图形项）、`QGraphicsProxyWidget`（把 QWidget 嵌入场景）、`QGraphicsItemGroup`（组合项）、`QGraphicsEffect`（特效）。

**知识点讲解：**
```cpp
QGraphicsScene scene;
scene.addRect(0, 0, 100, 100);           // 添加矩形项
scene.addText("hello");                   // 文本项
QGraphicsView view(&scene);
view.setRenderHint(QPainter::Antialiasing);   // 抗锯齿
// 自定义项：
class MyItem : public QGraphicsItem {
    QRectF boundingRect() const override;
    void paint(QPainter*, const QStyleOptionGraphicsItem*, QWidget*) override;
};
```
> [!Info] 可能的追问:
> - Q: Graphics View 和直接 QWidget 自绘区别？
> - A: Graphics View 适合大量图形项（几百上千个）：场景管理项的生命周期、碰撞检测、选择、层级；视图提供缩放/平移/滚动。直接 QWidget 自绘适合固定/少量图形。Graphics View 每个 item 是独立对象，可单独响应事件，交互性强。
> - Q: 坐标系统？为什么鼠标坐标要转换？
> - A: 三套坐标：场景坐标（QGraphicsScene 的全局坐标）、项坐标（每个 item 的本地坐标）、视图坐标（QGraphicsView 窗口坐标）。缩放/旋转后三者不同，交互时用 `mapToScene`/`mapFromScene` 转换。

### Qt 当中如何读写文件？
**回答话术：**
用 `QFile` + `QTextStream`/`QDataStream`：
- **文本读写**：`QFile` 打开 + `QTextStream`（`<<`/`>>`/`readLine`/`readAll`）
- **二进制读写**：`QFile` 打开 + `QDataStream`（可写任意 Qt 类型，跨平台一致）
- **一次性读取**：`QFile::readAll()` 返回 QByteArray
- 打开模式：`QIODevice::ReadOnly`/`WriteOnly`/`ReadWrite`/`Append`/`Text`/`Truncate`

**知识点讲解：**
```cpp
// 文本读
QFile f("test.txt");
if (!f.open(QIODevice::ReadOnly | QIODevice::Text)) return;
QTextStream in(&f);
QString line;
while (!in.atEnd()) { line = in.readLine(); /* 处理 */ }
// 文本写
QFile f2("out.txt");
if (!f2.open(QIODevice::WriteOnly | QIODevice::Text)) return;
QTextStream out(&f2);
out << "Hello" << '\n';
```
> [!Info] 可能的追问:
> - Q: QTextStream 和 QDataStream 读写文件的区别？
> - A: QTextStream 按文本读写（可读性强，人类可看），用于配置文件、日志、源码等；QDataStream 按二进制读写（紧凑、可存任意 Qt 类型、跨平台一致），用于序列化、程序数据交换。文本便于调试/编辑，二进制更紧凑高效且类型丰富。
> - Q: 大文件如何读？
> - A: 不要 `readAll()` 一次读入内存。用流式：`readLine()` 逐行、或 `read(buffer, maxSize)` 分块读。配合 `seek()` 随机访问。异步读可用 `QFileDevice` + `readChannelFinished` 信号。

### Qt 操作 INI 文件、JSON 文件、XML 文件？
**回答话术：**
三种配置/数据格式的 Qt 操作方式：
- **INI**：`QSettings(filename, QSettings::IniFormat)`，`setValue`/`value` 存取键值
- **JSON**：`QJsonDocument`（`fromJson`/`toJson`）+ `QJsonObject`/`QJsonArray`/`QJsonValue`
- **XML**：`QXmlStreamReader`/`QXmlStreamWriter`（流式，快）、或 DOM 风格 `QDomDocument`（已过时）

**知识点讲解：**
```cpp
// INI
QSettings s("app.ini", QSettings::IniFormat);
s.setValue("General/Name", "Tom");
QString name = s.value("General/Name").toString();
// JSON
QJsonObject obj; obj["name"] = "Tom"; obj["age"] = 20;
QJsonDocument doc(obj);
QByteArray data = doc.toJson();
QJsonDocument back = QJsonDocument::fromJson(data);
// XML 流式
QXmlStreamWriter w(&file);
w.writeStartElement("person");
w.writeAttribute("name", "Tom");
w.writeEndElement();
```
> [!Info] 可能的追问:
> - Q: INI/JSON/XML 怎么选？
> - A: INI 最简单（键值），适合简单配置；JSON 轻量、层级清晰、跨语言通用，是配置和 API 数据的主流；XML 表达力最强（属性+嵌套+命名空间+DTD/Schema），适合复杂文档/标准协议，但冗长。现代开发默认 JSON，简单配置用 INI。
> - Q: QSettings 默认存哪？
> - A: 不指定文件时用平台默认位置：Linux `~/.config/<app>/<app>.conf`，Windows 注册表或 AppData，macOS plist。指定 `QSettings::IniFormat` + 路径则用自定义 INI 文件。

### Qt 常用控件与容器类
**回答话术：**
**常用控件**：`QLabel`、`QPushButton`、`QLineEdit`、`QTextEdit`、`QComboBox`、`QCheckBox`、`QRadioButton`、`QSpinBox`、`QSlider`、`QProgressBar`、`QTableView`/`QListView`/`QTreeView`。
**Qt 容器类**（对应 STL）：
- `QList`（类似 std::list 语义但实现是数组+指针，Qt6 已与 QVector 合并）、`QVector`（连续数组，类似 std::vector）
- `QMap`（红黑树，类似 std::map）、`QHash`（哈希表，类似 std::unordered_map）
- `QLinkedList`（双向链表，已废弃）、`QSet`（类似 std::set）、`QStack`、`QQueue`

**注意**：Qt 容器是**隐式共享（COW）**的（拷贝便宜，修改才深拷贝），且可能比 std 版本更方便与 Qt 类型互操作。但遍历时隐式共享会失效（detach），有性能注意点。

**知识点讲解：**
```cpp
// Qt 容器迭代（Java 风格或 STL 风格）
QList<int> list {1, 2, 3};
foreach (int v, list) { /* Java 风格 */ }
for (int v : list) { /* C++ 风格 */ }
// 隐式共享：拷贝很便宜
QList<int> a = list;   // 共享数据，不拷贝
a[0] = 99;             // 修改触发 detach 深拷贝
```
> [!Info] 可能的追问:
> - Q: QList 和 std::vector 区别？
> - A: QList（Qt6 前）是"数组存储 + 指针间接"，小对象（<=8 字节）直接存数组，大对象存指针数组，插入删除快但内存间接。Qt6 后 QList 已与 QVector 统一为连续数组。std::vector 是标准连续数组。Qt 容器带隐式共享（COW），std 容器值语义（拷贝即深拷贝）。
> - Q: Qt 容器线程安全吗？
> - A: 不线程安全。隐式共享保证"拷贝共享数据的并发读"安全（引用计数原子），但同一容器实例并发修改不安全，需要外部锁（QMutex）或 QtConcurrent 场景用其它方案。

### 描述 Windows 下一个消息从触发到处理的整个路由过程
**回答话术：**
Windows 消息机制（与 Qt 事件循环类比）：
1. 程序启动，Windows 为进程创建**消息队列**
2. 用户操作（鼠标/键盘）产生消息，Windows 捕获后投递到对应进程的消息队列
3. 程序的消息循环 `GetMessage()` 从队列取消息，`TranslateMessage` 转换虚拟键消息，`DispatchMessage` 派发给窗口过程 `WndProc`
4. `WndProc` 处理消息（switch 分派给处理函数）

对应 Qt：Qt 的事件循环（`exec()`）等价于消息循环，`QApplication::notify()` 等价于 DispatchMessage 的分发，QObject 的 `event()` 等价于 WndProc。

**知识点讲解：**
```cpp
// Windows 消息循环（简化）
MSG msg;
while (GetMessage(&msg, NULL, 0, 0)) {
    TranslateMessage(&msg);
    DispatchMessage(&msg);   // 调 WndProc
}
// Qt 对应：app.exec() 内部就是这样的循环 + 事件分发
```
> [!Info] 可能的追问:
> - Q: Qt 的事件和 Windows 消息什么关系？
> - A: Qt 是跨平台框架，Windows 上用 Win32 消息作为底层输入，Qt 把系统消息翻译成 `QEvent`（鼠标/键盘/绘制等）分发到 QObject。所以 Qt 事件机制是对平台消息机制的抽象，上层统一。`QApplication::notify()` 是分发入口，事件过滤/event() 都是在这条链路上。
> - Q: 队列消息和投递消息区别？
> - A: Windows 消息分两种：队列消息（`PostMessage` 投递到队列，异步）和直通消息（`SendMessage` 同步直接调用窗口过程）。类似 Qt 的 `postEvent`（异步入队）和 `sendEvent`（同步立即分发）。

### 如何实现一个三角形按钮？窗口圆角如何实现？
**回答话术：**
**三角形按钮**：继承 QPushButton/QAbstractButton，重写 `paintEvent` 用 QPainter 画三角形路径，并重写 `hitTest`/`mousePressEvent` 判断点击是否在三角形内（否则矩形角落也响应）。
**圆角窗口**：
- 用 QSS：`QWidget { border-radius: 10px; }`
- 真正无边框圆角窗口：`setWindowFlags(Qt::FramelessWindowHint)` + 设置半透明背景 + 在 paintEvent 画圆角路径并 `setMask()`（或 `QPainterPath` + `setClipping`）

**知识点讲解：**
```cpp
// 三角形按钮绘制
void TriangleBtn::paintEvent(QPaintEvent*) {
    QPainter p(this);
    QPainterPath path;
    path.moveTo(width()/2, 0);
    path.lineTo(0, height());
    path.lineTo(width(), height());
    path.closeSubpath();
    p.fillPath(path, QColor("red"));
}
// 圆角无边框窗口
setWindowFlags(Qt::FramelessWindowHint);
setAttribute(Qt::WA_TranslucentBackground);
// paintEvent 里：
QPainterPath path;
path.addRoundedRect(rect(), 15, 15);
p.setClipPath(path);       // 裁剪圆角
p.fillRect(rect(), color);
```
> [!Info] 可能的追问:
> - Q: setMask 和 setClipPath 区别？
> - A: `setMask` 设置窗口的可见区域掩码（窗口系统级，掩码外区域完全不可见、不接收鼠标），适用于真正需要非矩形窗口（如异形窗口）。`setClipPath` 只是绘制裁剪（绘图级），窗口本身还是矩形。非矩形窗口交互（鼠标）用 setMask，仅视觉圆角用绘制裁剪 + 半透明。
> - Q: 如何做窗口翻转/动画？
> - A: 用 `QPropertyAnimation` 对 `geometry`/`pos`/自定义属性做动画。翻转效果可以分两步（左右压缩到 0 再展开）或用 `QGraphicsRotation`/`QTransform` 做 3D 变换。窗口翻转常用 `QPropertyAnimation` 改 geometry 模拟。

### Qt 操作数据库
**回答话术：**
Qt 数据库模块（QtSql）核心类：
- `QSqlDatabase`：管理数据库连接（addDatabase/setDatabaseName/open）
- `QSqlQuery`：执行 SQL（exec/next/value）
- `QSqlTableModel`：表模型（与 MVD 配合显示）
- `QSqlError`：错误信息
- `QSqlDriver`：驱动层（SQLite/MySQL/PostgreSQL 等插件）

流程：添加驱动连接 -> 打开 -> QSqlQuery 执行 SQL 或 QSqlTableModel 绑定 -> 操作数据。

**知识点讲解：**
```cpp
QSqlDatabase db = QSqlDatabase::addDatabase("QSQLITE");  // 驱动
db.setDatabaseName("app.db");
if (!db.open()) { qDebug() << db.lastError().text(); return; }
QSqlQuery q;
q.exec("CREATE TABLE IF NOT EXISTS user(id INT, name TEXT)");
q.prepare("INSERT INTO user VALUES (?, ?)");
q.addBindValue(1); q.addBindValue("Tom");   // 参数化防注入
q.exec();
q.exec("SELECT * FROM user");
while (q.next()) { q.value(0).toInt(); }
```
> [!Info] 可能的追问:
> - Q: 为什么用 prepared statement 而不是拼接 SQL？
> - A: 防 SQL 注入：参数通过绑定传递，数据库驱动转义，用户输入不可能改变 SQL 结构。同时预编译语句可复用，减少解析开销。这是生产环境必须的。
> - Q: Qt 的数据库连接是线程安全的吗？
> - A: 一个 `QSqlDatabase` 连接只能被创建它的线程使用。多线程访问数据库要为每线程创建独立连接（`QSqlDatabase::addDatabase(..., connectionName)` 用不同连接名）。连接池：多线程 + 数据库连接池管理连接复用。

### Qt Remote Object 的序列化与反序列化
**回答话术：**
Qt Remote Objects（QtRO）用于进程间共享 QObject，跨进程调用槽/信号/属性。序列化基于 `QDataStream`：
- 支持序列化基础 C++ 类型、`QVariant`、`QObject` 子类的属性
- 自定义类型实现 `QDataStream` 的 `operator<<`/`operator>>` 即可支持
- 跨进程时把远程对象的方法调用/属性变化打包成数据流传输，接收端还原

**知识点讲解：**
```cpp
// 自定义类型可序列化
QDataStream &operator<<(QDataStream& out, const MyType& t);
QDataStream &operator>>(QDataStream& in, MyType& t);
// 远程对象：注册到 Source 端，Replica 端透明调用
```
> [!Info] 可能的追问:
> - Q: QtRO 和普通信号槽跨线程有什么区别？
> - A: 信号槽跨线程是同一进程内线程间通信（事件队列）。QtRO 是跨进程（甚至跨主机，走网络传输），需要序列化参数。所以 QtRO 只支持可序列化类型、性能低于线程内信号槽，适合进程间解耦通信。
> - Q: 为什么属性变化也能同步？
> - A: 远程对象复制了 Source 端的属性，Source 属性变化发信号，QtRO 把变更通过数据流同步到 Replica。这是"分布式属性"设计，Replica 端属性变化也能反向推送。

### QFrame 与 QWidget 的区别
**回答话术：**
QFrame 继承自 QWidget，是在 QWidget 基础上**增加了边框/框架能力**：
- QWidget：所有 UI 控件的基类，提供基础功能（尺寸、位置、事件、父子）
- QFrame：QWidget 的子类，额外提供 `setFrameShape`（Box/Panel/Stadium...）、`setFrameShadow`（凹/凸）、边框样式，可绘制简单线条/分隔

**知识点讲解：**
```cpp
// 常见用法：分隔线、带边框容器
QFrame* line = new QFrame;
line->setFrameShape(QFrame::HLine);      // 水平分隔线
QFrame* box = new QFrame;
box->setFrameShape(QFrame::Box);
box->setLineWidth(2);
```
> [!Info] 可能的追问:
> - Q: 什么时候用 QFrame 而不是 QWidget？
> - A: 需要边框/分隔线/立体框架视觉效果时用 QFrame；纯容器无边框需求直接用 QWidget。QWidget 本身没有边框绘制能力。

### show() 和 exec() 的区别
**回答话术：**
- `show()`：显示**非模态**窗口，立即返回，不阻塞，用户可操作其他窗口
- `exec()`：显示**模态**窗口，进入**局部事件循环**阻塞直到窗口关闭，期间阻塞调用者；用于对话框（QDialog::exec）
- `open()`：半模态，阻塞其他窗口响应但不阻塞后续代码

模态窗口：`QDialog::exec()` 或 `setModal(true)` + show。

**知识点讲解：**
```cpp
// show：非模态
QDialog dlg; dlg.show();   // 立即返回，可继续操作主窗口
// exec：模态阻塞
QDialog dlg;
if (dlg.exec() == QDialog::Accepted) { /* 用户点了确定 */ }
```
> [!Info] 可能的追问:
> - Q: exec() 内部怎么实现的？
> - A: exec() 内部创建一个局部 `QEventLoop`，进入循环处理事件，直到对话框关闭触发 `accept()`/`reject()` 退出循环。所以 exec() 期间窗口事件仍被处理（能响应点击），但调用者被阻塞。
> - Q: 模态和非模态的本质区别？
> - A: 模态通过 `QApplication` 的模态窗口栈（modal window stack）阻塞其他窗口的输入，只允许操作模态窗口。非模态窗口之间可自由交互。

### Qt 的插件机制是什么？
**回答话术：**
Qt 插件机制是把功能模块化、运行时动态加载的机制：
- 插件是动态库（.dll/.so），实现特定接口（继承 `QPluginInterface` 或特定抽象类）
- `QPluginLoader` 加载插件、`QPluginLoader::instance()` 获取插件对象
- 高版本 Qt 用 `QPluginLoader` + 元对象接口；`QFactoryLoader` 管理按类型查询的插件工厂
- 用 `Q_DECLARE_INTERFACE`/`Q_PLUGIN_METADATA` 声明接口与元数据

用途：应用扩展、控件库插件（Qt Designer 自定义控件）、数据库驱动、图片格式等。

**知识点讲解：**
```cpp
// 插件接口
class IPlugin {
public:
    virtual ~IPlugin() = default;
    virtual QString name() const = 0;
};
Q_DECLARE_INTERFACE(IPlugin, "com.example.IPlugin")
// 加载
QPluginLoader loader("path/to/plugin.dll");
IPlugin* p = qobject_cast<IPlugin*>(loader.instance());
if (p) qDebug() << p->name();
```
> [!Info] 可能的追问:
> - Q: 插件机制和动态库直接调用区别？
> - A: 直接调动态库需要运行时知道符号名并手动 `dlsym`/`GetProcAddress` 加载函数指针，类型不安全。Qt 插件通过抽象接口 + qobject_cast，运行时按接口类型安全获取实例，且支持按元数据（JSON 元信息）查询匹配的插件。设计上是"按能力查找"，而非"按符号链接"。
> - Q: 插件和普通动态库如何选？
> - A: 只需一组导出函数、无扩展需求用动态库；需要运行时按能力/类型发现多个实现、支持第三方扩展、插件热插拔，用 Qt 插件机制。

### 创建的对象有几种方式，有什么区别
**回答话术：**
Qt 创建对象的方式：
1. **构造函数直接创建**：`new QWidget`、`new QPushButton`，指定父对象入对象树
2. **元对象系统动态创建**：`QMetaObject::newInstance()` / `invokeMethod`，运行期按类名字符串创建，可调用其槽/属性（需继承 QObject + Q_OBJECT）

区别：构造函数是编译期类型安全、静态创建；元对象创建是运行期动态创建（插件/脚本/配置驱动），但要求类有 Q_OBJECT 且可默认构造。

**知识点讲解：**
```cpp
// 编译期创建（类型安全）
QPushButton* btn = new QPushButton("OK", parent);
// 运行期动态创建
const QMetaObject* mo = QMetaType::metaObjectForType(typeId);
QObject* obj = mo->newInstance();   // 调用默认构造
```
> [!Info] 可能的追问:
> - Q: 什么时候需要元对象动态创建？
> - A: 运行时才知道要创建什么类（配置文件/插件/脚本场景）、无法在编译期引用具体类时。代价是只能调用默认构造函数 + 通过属性/信号槽访问，且不能访问非元对象成员。

### 描述 Windows 下窗口刷新机制，是立即还是异步？
**回答话术：**
Windows 窗口刷新是**异步 + 合并**的：
- `InvalidateRect` 标记区域无效（不立即重绘），WM_PAINT 在消息队列中
- 多个无效区域合并成一次 WM_PAINT，系统空闲时才派发重绘
- 所以"每次刷新请求不一定立即刷新"，会批量合并
- 强制同步刷新用 `UpdateWindow`（立即发送 WM_PAINT）

Qt 对应：`QWidget::update()` 是异步（合并多次调用为一次重绘），`repaint()` 是同步立即重绘。
**知识点讲解：**
```cpp
// Qt：update 异步合并（推荐），repaint 同步（可能闪烁）
widget->update();     // 合并多次为一次 paintEvent
widget->repaint();    // 立即重绘，阻塞
```
> [!Info] 可能的追问:
> - Q: 为什么 update 要异步合并？
> - A: 一次交互（拖动、输入）可能触发多次重绘请求，如果每次都立即重绘会重复劳动且闪烁。合并成一次在事件循环空闲时统一重绘，提高效率。这是 Qt 和 Windows 共同的优化。
> - Q: update 和 repaint 什么时候用？
> - A: 一般用 update（异步、高效、不闪烁）。只有必须立即同步重绘（如绘制中间帧、要求立刻看到结果）才用 repaint，且 repaint 在子线程/非 UI 上下文不可用。

Qt Multimedia 模块：

QMediaPlayer player;

### Qt 中的兄弟窗口重叠部分如何刷新？
**回答话术：**
兄弟窗口（同一父窗口下的多个子窗口）重叠时，刷新流程是窗口系统/合成器负责的：
- 上层窗口移动/关闭后，被遮挡的兄弟窗口区域需要重绘
- 流程：窗口系统检测到重叠区域无效 -> 发 WM_PAINT/Qt 绘制事件给被遮挡窗口 -> 该窗口 paintEvent 重绘可见部分
- Qt 中 `update()` 会安排重绘，事件循环统一处理

**知识点讲解：**
兄弟窗口各自独立，重叠区域的重绘由系统合成/事件分发完成。Qt 层面：调用 `update()` 触发自身重绘，被覆盖窗口会自动补绘（系统保证）。
> [!Info] 可能的追问:
> - Q: 为什么 Qt 里窗口重叠不会"漏绘制"？
> - A: 窗口系统（Windows WM_PAINT / Qt backing store）会跟踪无效区域，重叠部分变化时向受影响窗口发送绘制事件。Qt 的 `QBackingStore` 负责把各窗口内容合成上屏，保证遮挡关系正确。所以开发者只需在 paintEvent 画自己内容，重叠由框架处理。

### 面向对象的三大特征？C++ 空类有哪些成员函数？
**回答话术：**
三大特征：**封装**（数据+行为绑定、访问控制）、**继承**（代码复用、is-a）、**多态**（同接口不同实现，静态=重载/模板，动态=虚函数）。

**空类**（无任何成员）编译器会**隐式生成** 6 个成员函数：
1. 默认构造函数
2. 析构函数
3. 拷贝构造函数
4. 拷贝赋值运算符
5. 移动构造函数（C++11）
6. 移动赋值运算符（C++11）

空类 `sizeof` 为 1（为区分不同对象地址）。注意：C++11 起这些是"按需生成"（odr-used 时才生成），且定义了拷贝/移动之一会抑制其他默认生成（规则复杂，需注意）。

**知识点讲解：**
```cpp
class Empty {};
// 编译器隐式生成：
// Empty(); Empty(const Empty&); ~Empty();
// Empty& operator=(const Empty&);
// Empty(Empty&&); Empty& operator=(Empty&&);
Empty a;              // 默认构造
Empty b = a;          // 拷贝构造
```
> [!Info] 可能的追问:
> - Q: 什么时候编译器不会生成默认构造函数？
> - A: 类定义了任何构造函数（哪怕一个带参构造），编译器就不再生成默认构造。此时需要 `Empty() = default;` 显式要求。同样，声明了拷贝构造/析构会抑制隐式移动构造的生成（三/五法则）。
> - Q: 什么是三/五法则？
> - A: 如果类需要自定义析构/拷贝构造/拷贝赋值三者之一，通常三者都要自定义（三法则）；C++11 加入移动后是五法则（+移动构造+移动赋值）。因为资源管理类的默认拷贝是浅拷贝，会造成 double-free。

### 继承与组合，什么场景用哪个？
**回答话术：**
- **继承（is-a）**：子类是父类的一种，"能替代父类使用"。用父类接口操作子类，需要多态时
- **组合（has-a）**：类持有另一个类的对象，"包含/拥有"关系，委托其功能

**设计原则：组合优于继承（Composition over Inheritance）**。原因：
- 继承破坏封装（子类依赖父类实现细节）、层次僵化（改父类影响所有子类）、深继承难维护
- 组合灵活（可运行时更换组件）、解耦、可测试（注入 mock）

**场景判断**：语义上是"是一种"用继承（需要多态/接口）；"有一个/用到了"用组合。能组合就不要继承。
**知识点讲解：**
```cpp
// 继承：是
class Button : public QWidget {};   // Button 是一种 Widget，需要多态
// 组合：有
class Window {
    QLineEdit* edit;   // Window 拥有编辑框（组件）
    QPushButton* btn;
};
```
> [!Info] 可能的追问:
> - Q: 什么情况必须用继承？
> - A: 1) 需要运行时多态（通过基类指针/引用操作派生类）；2) 需要继承接口并实现（纯虚基类/接口）；3) 需要访问 protected 成员或覆写虚函数。其他情况优先组合。
> - Q: 继承的代价？
> - A: 1) 破坏封装（子类与父类强耦合，父类改动可能破坏子类）；2) 深继承树难维护、难测试；3) 虚函数有 vptr 开销；4) 菱形继承复杂度。现代 C++ 倾向"组合 + 接口（纯虚类）+ 模板"。

### 如何避免"野指针"？
**回答话术：**
野指针 = 指向已释放/无效内存的指针。避免方法：
1. 指针**初始化为 nullptr**（不要留未初始化指针）
2. **释放后置空**：`delete p; p = nullptr;`
3. **优先智能指针**：unique_ptr/shared_ptr/weak_ptr 自动管理生命周期，杜绝裸指针 delete 后继续使用
4. **避免越界**：用 STL 容器/迭代器代替裸数组指针算术
5. **不保存栈对象地址**：函数返回后局部变量销毁，指向它的指针成野指针

**知识点讲解：**
```cpp
int* p = new int(5);
delete p;
p = nullptr;          // 释放后置空，防止悬垂
if (p) { /* 安全 */ }
// 智能指针杜绝
std::unique_ptr<int> up(new int(5));
up.reset();           // 释放，up 变空，不会悬垂
```
> [!Info] 可能的追问:
> - Q: 野指针和悬垂指针区别？
> - A: 野指针是"未初始化/指向随机地址"的指针；悬垂指针（dangling）是"曾经有效、指向的对象已释放"的指针。悬垂更隐蔽（初看有效）。释放后置空 + 智能指针都能避免悬垂。
> - Q: 如何定位野指针问题？
> - A: ASan（AddressSanitizer）编译期插桩能检测 use-after-free/越界；valgrind 运行期检测。崩溃时 core dump + gdb bt 看调用栈定位。智能指针从源头避免。

### 一般什么情况下会出现内存泄漏？如何尽量避免？
**回答话术：**
内存泄漏 = 申请的内存（new）未释放（delete），程序失去对该内存的引用。常见场景：
1. **new/delete 不配对**：new 了忘记 delete，或 new[] 用 delete（应 delete[]）
2. **指针被重新赋值**：`int* p = new int; p = new int;` 第一次的内存泄漏
3. **异常路径**：new 之后、delete 之前抛异常，delete 不执行
4. **容器存裸指针**：容器销毁只析构元素（指针本身），不 delete 指向对象
5. **循环引用**：shared_ptr 互相引用计数到不了 0

**避免方法**：
- **RAII + 智能指针**（唯一根治）：unique_ptr 独占、shared_ptr 共享、weak_ptr 破环
- new/delete 配对、new[]/delete[] 配对
- 容器存智能指针
- 不用裸指针管理资源

**知识点讲解：**
```cpp
// 泄漏：
int* p = new int(1);
p = new int(2);          // 第一块内存泄漏
// 异常路径泄漏：
void f() {
    int* p = new int(5);
    g();                 // g 抛异常，delete 不执行
    delete p;
}
// 正确：RAII
void f() {
    auto p = std::make_unique<int>(5);  // 任何路径离开作用域都释放
    g();
}
```
> [!Info] 可能的追问:
> - Q: 怎么检测内存泄漏？
> - A: 1) ASan `-fsanitize=address`（快速，开发期）；2) valgrind `--leak-check=full`（慢但全）；3) Windows 用 CRT 调试堆 `_CrtDumpMemoryLeaks`；4) 代码层面计数 new/delete。Qt 程序用系统工具检测到的"泄漏"可能是对象树还没释放的正常现象，需甄别。
> - Q: 智能指针能完全避免泄漏吗？
> - A: 能避免绝大多数。但 shared_ptr 循环引用仍泄漏（需 weak_ptr 破环）；智能指针持有非内存资源（文件句柄/锁）需自定义删除器；全局/静态对象的构造顺序问题需注意。智能指针 + RAII + 避免循环引用基本消除手动泄漏。

### 分别写出饿汉和懒汉线程安全的单例模式（设计要点）
**回答话术：**
**单例模式**：确保一个类只有一个实例，提供全局访问点。
- **饿汉式**：类加载时就创建实例（静态成员），天然线程安全（静态初始化在 main 前完成），但启动即占用资源
- **懒汉式**：第一次使用时才创建，需考虑线程安全

**线程安全实现**：
1. **Meyers 单例（C++11 推荐）**：`static T& get() { static T t; return t; }`——静态局部变量初始化线程安全（编译器加锁保证一次初始化），最简洁
2. **双检锁（double-checked locking）**：加锁前先检查，加锁后再次检查，避免每次 get 都加锁（需 memory 序/atomic，易错）
3. **饿汉式**：静态成员在 main 前初始化，天然安全

**知识点讲解：**
```cpp
// Meyers 单例（推荐，C++11 线程安全）
class Singleton {
public:
    static Singleton& instance() {
        static Singleton inst;   // 首次进入线程安全初始化
        return inst;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() = default;
};
// 饿汉式（main 前初始化，天然安全）
class SingletonHungry {
    static SingletonHungry instance_;   // 静态成员，main 前构造
};
```
> [!Info] 可能的追问:
> - Q: 为什么 C++11 静态局部变量初始化是线程安全的？
> - A: 编译器为每个静态局部变量生成隐藏的 guard 标志（原子操作 + 锁，`__cxa_guard_acquire/release`），第一个线程进入时初始化并置标志，后续线程看到标志直接跳过。所以 Meyers 单例无需额外加锁。
> - Q: 双检锁为什么需要 volatile/atomic？
> - A: 双检锁 `if (!p) { lock; if (!p) p = new T; }` 中，`p = new T` 有三步（分配/构造/赋值），CPU 可能重排导致其他线程看到未构造完成的 p。需 `std::atomic` + acquire/release 序或 `std::call_once` 保证。C++11 后直接用 Meyers 单例或 `call_once` 更简单安全。

### 深拷贝和浅拷贝的区别？什么时候产生默认拷贝构造函数？
**回答话术：**
- **浅拷贝**：只拷贝成员值，指针成员只复制地址（两个指针指向同一块内存），可能 double-free/悬挂
- **深拷贝**：拷贝时为新对象分配独立的内存（指针成员重新 new），互不影响

**默认拷贝构造函数生成时机**：类没有定义任何拷贝构造函数、且成员都可拷贝（或没有不可拷贝成员）时，编译器自动生成。默认拷贝构造执行**逐成员浅拷贝**（对成员调用各自的拷贝构造/赋值）。

所以：类含裸指针/资源成员时，默认浅拷贝会导致问题，必须自定义深拷贝（遵循三/五法则）。

**知识点讲解：**
```cpp
struct Shallow {
    int* data;
    Shallow(const Shallow& o) : data(o.data) {}   // 浅拷贝：共享指针
};
struct Deep {
    int* data;
    Deep(const Deep& o) : data(new int(*o.data)) {}  // 深拷贝：独立内存
};
```
> [!Info] 可能的追问:
> - Q: 什么时候必须自定义拷贝构造？
> - A: 类持有**非内存资源**或需要深拷贝语义时（裸指针、文件句柄、锁、自定义 buffer）。默认浅拷贝会让两个对象共享资源，析构时 double-free。遵循三/五法则：定义了析构/拷贝之一就要定义全部。
> - Q: 移动构造和拷贝构造的区别？
> - A: 拷贝深拷贝资源（新内存+复制），移动转移资源所有权（指针转移，源对象置空），省一次深拷贝开销。移动构造是否 noexcept 决定 STL 容器扩容用移动还是拷贝。

### 虚析函数的作用？Vector 底层实现原理？
**回答话术：**
**虚析函数**：基类析构声明 `virtual`，通过基类指针 delete 派生类对象时，能调用派生类析构（先派生后基类），避免派生类资源泄漏。不带多态用途的类不需要虚析构（省 vptr 开销）。

**Vector 底层**：连续内存 + 三指针（start/end/capacity），扩容时申请更大内存（GCC 2 倍、MSVC 1.5 倍）移动/拷贝旧数据。详见收集文件 vector 题。
**知识点讲解：**
```cpp
class Base { public: virtual ~Base() = default; };  // 虚析构
class Derived : public Base { std::string s; };
Base* p = new Derived;
delete p;   // 虚析构 -> 调 Derived::~Derived 再 Base::~Base
```
> [!Info] 可能的追问:
> - Q: 为什么不默认所有析构都虚？
> - A: 虚析构给每个对象加 vptr（8 字节），且调用多一次间接。只有类要被继承作多态基类（通过基类指针 delete）才需要。纯虚析构则让基类成为抽象类。C++ 零开销原则：不为用不到的特性付费。

### static 和 const 的使用
**回答话术：**
**static**（静态）：
- 局部静态变量：函数内、静态存储区、只初始化一次、生命周期贯穿程序
- 全局静态变量：内部链接（文件作用域），现代用匿名命名空间替代
- 类静态成员变量：所有对象共享一份，需类外定义
- 类静态成员函数：属于类非对象，无 this，只能访问静态成员

**const**（常量）：
- 修饰变量：不可修改
- 修饰成员函数：不修改对象状态（const 对象只能调 const 成员函数）
- const 和 static 不能同时修饰成员函数（static 无 this，const 约束 this）

**知识点讲解：**
```cpp
class Demo {
    static int count_;          // 类静态成员（声明）
    static void f();            // 静态成员函数，无 this
    void g() const;             // const 成员函数
};
int Demo::count_ = 0;           // 类外定义
```
> [!Info] 可能的追问:
> - Q: 为什么 static 成员函数不能是 const？
> - A: const 修饰的是"不修改 this 所指对象"，但 static 成员函数没有 this 指针。两者语义矛盾，不能共存。static 函数访问静态成员不需要对象。
> - Q: static 局部变量和全局变量区别？
> - A: static 局部变量作用域限函数内但生命周期贯穿程序；全局变量作用域整个程序（外部链接）。static 局部变量是"局部作用域 + 全局生命周期"，常用于缓存/计数/Meyers 单例。

### 说出观察者模式类关系和优点
**回答话术：**
观察者模式定义**一对多依赖**：一个主题（Subject/被观察者）状态变化时，自动通知所有观察者（Observer）。
**类关系**：
- Subject：维护观察者列表，提供 attach/detach，状态变化时 notify 所有观察者
- Observer：抽象接口（update 方法）
- ConcreteSubject/ConcreteObserver：具体实现

**优点**：
- 抽象耦合：观察者和被观察者只依赖抽象接口，易扩展
- 广播通信：一个通知发给所有注册的观察者，需要就注册

**缺点**：
- 依赖链长：观察者过多时通知耗时
- 循环通知：观察者更新又触发主题变化，可能死循环（需防重入）
- 被观察者不知道观察者是否存活（Qt 用 QPointer/自动断连解决）

**知识点讲解：**
```cpp
// Qt 信号槽就是观察者模式的实现，且解决了"观察者销毁"问题
class Subject : public QObject {
    Q_OBJECT
public:
signals:
    void changed();   // 通知观察者
    void notify() { emit changed(); }  // 主题变化广播
};
// 观察者 connect 到信号即可注册/取消注册
```
> [!Info] 可能的追问:
> - Q: 观察者模式和信号槽的关系？
> - A: Qt 信号槽是观察者模式的具体实现：一个信号可连多个槽（一对多广播），connect 即注册、disconnect 即取消注册。Qt 信号槽比传统观察者强在：1) 编译期类型安全；2) 接收者销毁自动断连（不会悬挂）；3) 支持跨线程队列分发。
> - Q: 观察者模式的缺点在 Qt 中如何缓解？
> - A: 传统观察者"通知已销毁观察者"是致命问题（悬挂指针）。Qt 用 QPointer 检测对象存活 + 对象析构自动断开连接（connect 建立的连接在 receiver 销毁时移除），避免了悬挂通知。循环通知用 `blockSignals`/标志位防重入。

### 说出代理模式类关系和优点
**回答话术：**
代理模式：为对象提供一个**替身/代理**控制对原对象的访问。
**类关系**：
- Subject（抽象接口）：定义真实对象和代理的共同接口
- RealSubject（真实对象）：实际业务
- Proxy（代理）：持有 RealSubject 引用，实现同接口，在转发调用前后做额外处理

**优点**：
- 保护真实对象（控制访问权限）
- 延迟加载（代理暂不创建真实对象，需要时再建）
- 增强功能（日志、缓存、鉴权，不修改原类）
- 解耦（客户端只依赖抽象接口）

**缺点**：类数量增加、多一层间接调用。

**知识点讲解：**
```cpp
// 远程代理 / 虚拟代理 / 保护代理 是常见变体
class Image {
public: virtual void draw() = 0;
};
class RealImage : public Image { void draw() override { /* 加载并绘制 */ } };
class ProxyImage : public Image {   // 代理
    RealImage* real_ = nullptr;
    void draw() override {
        if (!real_) real_ = new RealImage();  // 延迟加载
        real_->draw();                        // 转发
    }
};
```
> [!Info] 可能的追问:
> - Q: 代理模式和其他模式区别？
> - A: 代理与装饰器结构相似（都持有目标对象），但意图不同：代理**控制访问**（何时创建、能否访问），装饰器**动态添加功能**（叠加多个装饰）。代理与适配器也不同：适配器**改变接口**，代理**保持接口不变**。

### 说出工厂模式概念和优点
**回答话术：**
工厂模式把**对象创建的职责**从客户端剥离，由工厂统一负责。三种层次：
1. **简单工厂**：一个工厂类根据参数返回不同产品实例（不是 GoF 模式，是惯例）
2. **工厂方法**：定义创建对象的接口，由子类决定实例化哪个产品（每产品一个工厂子类）
3. **抽象工厂**：创建一组相关产品（产品族），客户端不依赖具体类

**优点**：
- 创建和使用分离（解耦）
- 扩展性好（新增产品只加新类，不改客户端）
- 统一创建逻辑（集中控制构造/初始化）

**缺点**：类数量膨胀、抽象增加复杂度。

**知识点讲解：**
```cpp
// 简单工厂
class ShapeFactory {
public:
    static std::unique_ptr<Shape> create(const std::string& type) {
        if (type == "circle") return std::make_unique<Circle>();
        if (type == "rect")   return std::make_unique<Rect>();
        return nullptr;
    }
};
// 工厂方法：基类定义工厂接口，子类决定产品
class Creator {
public:
    virtual std::unique_ptr<Product> create() = 0;
};
```
> [!Info] 可能的追问:
> - Q: 三种工厂怎么选？
> - A: 产品类型少、创建逻辑简单用简单工厂；产品类型多、需要扩展用工厂方法（每类一个工厂）；需要创建"产品族"（互相配套的一组对象）用抽象工厂。工厂模式本质是"把 new 收敛到一处"，配合多态实现"开闭原则"。

### 说出建造者模式概念
**回答话术：**
建造者（Builder）模式：**将一个复杂对象的构建与其表示分离**，同样的构建过程可以创建不同表示。
适合：对象构造参数很多、构造步骤固定但每步实现可变（如复杂文档、配置、请求构造）。

**类关系**：
- Director（指挥者）：定义构建步骤顺序
- Builder（抽象建造者）：定义每步构建接口
- ConcreteBuilder：实现每步（返回不同产品）
- Product：被构建的复杂对象

**知识点讲解：**
```cpp
class QueryBuilder {          // 建造者
public:
    QueryBuilder& from(const std::string& t) { from_ = t; return *this; }
    QueryBuilder& where(const std::string& c) { where_ = c; return *this; }
    std::string build() const { return "SELECT * FROM " + from_ + " WHERE " + where_; }
private:
    std::string from_, where_;
};
// 链式调用（流式建造者）
std::string sql = QueryBuilder().from("users").where("age>18").build();
```
> [!Info] 可能的追问:
> - Q: 建造者模式和其他创建型模式区别？
> - A: 工厂模式关注"创建什么"（直接返回成品），建造者模式关注"如何一步步构建"（分步 + 返回不同表示）。构造参数过多时，建造者/链式调用比长参数构造更可读。现代 C++ 常用链式 Builder 替代多参数构造函数。

### 说出适配器模式概念
**回答话术：**
适配器（Adapter）模式：**将一个类的接口转换成客户端期望的另一个接口**，让接口不兼容的类能一起工作。
两种实现：
- **类适配器**：多继承，继承目标接口 + 适配者类
- **对象适配器**：组合，持有一个适配者对象，包装其接口

**知识点讲解：**
```cpp
// 对象适配器：持有被适配对象，包装成目标接口
class Target { public: virtual void request() = 0; };
class Adaptee { public: void specificRequest() { /* 旧接口 */ } };
class Adapter : public Target {
    Adaptee* adaptee_;
public:
    void request() override { adaptee_->specificRequest(); }  // 转换调用
};
```
> [!Info] 可能的追问:
> - Q: 适配器 vs 代理 vs 装饰器的区别？
> - A: 适配器改变接口（A->B），代理保持接口控制访问，装饰器保持接口叠加功能。三者都持有一个对象做转发，但意图完全不同。适配器常用于兼容旧代码/第三方库接口。

### 23 种设计模式应用场景
**回答话术：**
设计模式分三大类：
- **创建型**（5）：单例、工厂方法、抽象工厂、建造者、原型——如何创建对象
- **结构型**（7）：适配器、装饰器、代理、外观、桥接、组合、享元——如何组合对象
- **行为型**（11）：策略、模板方法、观察者、迭代器、责任链、命令、备忘录、状态、访问者、中介者、解释器——如何协作

**高频面试重点**：单例（Meyers）、工厂/抽象工厂、观察者（Qt 信号槽）、策略（std::sort 比较器）、模板方法（框架骨架+虚函数扩展点）、适配器、代理。

**知识点讲解：**
设计模式不是银弹：过度使用增加抽象和复杂度。C++ 中很多模式被语言特性替代（策略→lambda/std::function，观察者→信号槽，迭代器→STL 迭代器）。面试重点讲清意图 + 应用场景 + 一两个亲自用过的。
> [!Info] 可能的追问:
> - Q: 你在项目里实际用过哪些设计模式？
> - A: 结合简历项目举例：日志库用单例（全局一个日志器）；网络服务器用 Reactor + 观察者（事件分发）；组件库用工厂（创建不同类型组件）+ 策略（不同排序/压缩策略可替换）。重点说明"为什么用"和"解决什么问题"，比背 23 种定义更有说服力。
> - Q: C++ 哪些模式已被语言特性替代？
> - A: 策略模式→lambda/std::function；观察者→Qt 信号槽/std::function 回调；迭代器→STL 迭代器；工厂→模板/自动注册；单例→静态局部变量（Meyers）。设计模式是思想，C++ 用现代特性实现更简洁安全。

### 进程和线程的区别？
**回答话术：**
- **进程**：操作系统**资源分配**的基本单位，拥有独立地址空间（代码段/数据段/堆/栈/打开的文件），进程间隔离
- **线程**：**CPU 调度**的基本单位，是进程内的一条执行流，共享进程资源（地址空间、文件、全局变量），每个线程有独立栈和寄存器

**关系**：进程 = 线程 + 共享资源（地址空间、文件表）。进程是资源容器，线程在容器内跑。

**差异**：
| | 进程 | 线程 |
|--|------|------|
| 资源 | 独立地址空间 | 共享进程地址空间 |
| 开销 | 创建/切换重（页表切换） | 创建/切换轻（栈切换） |
| 通信 | 需 IPC（管道/共享内存/Socket） | 直接共享内存（快） |
| 隔离 | 强（一进程崩溃不影响他人） | 弱（线程崩溃可能带崩进程） |
| 并发 | 多核可多进程 | 多线程共享资源需同步 |

**知识点讲解：**
```text
进程：独立虚拟地址空间 + 页表
线程：共享页表，各自 PC/栈/寄存器
切换成本：进程切换要换页表（TLB 失效），线程切换只换栈帧和寄存器
```
> [!Info] 可能的追问:
> - Q: 什么时候用多进程什么时候用多线程？
> - A: 需要强隔离/容错（崩溃隔离）、多语言组件、安全边界（浏览器 tab）用多进程；需要高并发共享数据、频繁通信（消息系统/网络服务器）用多线程。线程快但需同步，进程安全但 IPC 慢。
> - Q: 为什么说线程切换比进程切换快？
> - A: 进程切换要切换虚拟地址空间（换 CR3/页表，TLB 失效，下次访问重走页表）+ 内核栈等；线程切换同进程内只需切换栈/寄存器/内核栈，不换地址空间。但同进程多线程竞争同一 CPU 时切换仍需内核，不是零成本。

### 信号和信号量的区别是什么？
**回答话术：**
同名不同概念：
- **信号（Signal）**：UNIX 进程间**异步通知**机制（SIGINT/SIGTERM/SIGSEGV），内核发送给进程，进程注册处理函数响应；用于"通知某事件发生"，是软件中断
- **信号量（Semaphore）**：**同步互斥**原语，是计数器，用于多进程/线程协调对共享资源的访问；`P/V` 操作（acquire/release），计数>0 可继续否则阻塞

**区别**：
| | 信号 Signal | 信号量 Semaphore |
|--|-------------|------------------|
| 本质 | 异步事件通知（软件中断） | 计数器（同步原语） |
| 方向 | 内核->进程 | 进程/线程间互操作 |
| 用途 | 通知（Ctrl+C、段错误） | 互斥/流量控制 |
| 行为 | 触发处理函数 | P 减 V 增，阻塞/唤醒 |

**知识点讲解：**
```cpp
// 信号：注册处理函数
signal(SIGINT, handler);   // Ctrl+C 触发 handler
// 信号量：同步
std::counting_semaphore<10> sem(5);   // C++20
sem.acquire();  // P，计数-1，为 0 则阻塞
sem.release();  // V，计数+1
```
> [!Info] 可能的追问:
> - Q: 信号量和互斥锁区别？
> - A: 互斥锁（mutex）是二值（0/1），同一时刻只能一个线程持有，且必须由持有者释放；信号量可计数 N（允许多个资源/多并发），release 不要求持有者。信号量适合"资源数量"控制（连接池、限流），互斥锁适合"临界区独占"。
> - Q: 信号量在项目里怎么用？
> - A: 线程池限制并发数（初始 N，acquire 占用、release 归还）、生产者-消费者（缓冲满/空阻塞）、连接池控制连接数量。Qt 用 `QSemaphore`，C++20 有 `std::counting_semaphore`。

### 知道死锁吗？死锁是如何产生的？
**回答话术：**
死锁：多个线程/进程**互相持有对方需要的资源并等待对方释放**，导致都永远阻塞。
**四个必要条件**（缺一不可）：
1. **互斥**：资源一次只能被一个进程占用
2. **占有且等待**：持有资源的同时还在请求其他资源
3. **不可剥夺**：资源只能由持有者主动释放
4. **循环等待**：形成等待环（T1 等 T2 的资源，T2 等 T3...，Tn 等 T1）

**预防/解决**：破坏任一条件——统一加锁顺序（破循环等待）、一次性申请所有资源（破占有等待）、锁超时、检测并回滚。
**知识点讲解：**
```cpp
// 死锁示例：两个线程两把锁交叉获取
// T1: lock(A); lock(B);
// T2: lock(B); lock(A);
// 预防：全局统一加锁顺序，都先 A 后 B
```
> [!Info] 可能的追问:
> - Q: 如何避免死锁？开发中的规范？
> - A: 1) **固定加锁顺序**（最有效，都按相同顺序获取锁）；2) 用 `std::lock`/`std::scoped_lock` 一次锁多个（C++17 内部处理顺序）；3) 减少锁粒度/持锁时间；4) 避免锁中调用户代码/嵌套锁；5) 锁超时机制（try_lock + 回退）。
> - Q: 死锁和活锁/饥饿的区别？
> - A: 死锁：互相等待不前进（阻塞）。活锁：线程都在尝试（让锁/重试）但没人能成功（都在忙但无进展）。饥饿：某个线程一直得不到资源（其他线程总抢先）。活锁/饥饿进程仍在运行，死锁是永久阻塞。

### 动态库和静态库的区别？
**回答话术：**
- **静态库**（.a/.lib）：链接期把目标文件打包进可执行文件。优点：部署简单（单文件）、运行快（无加载开销）；缺点：体积大、多程序重复复制、升级需重编
- **动态库**（.so/.dll）：链接期只记录符号引用，运行期由动态加载器加载。优点：体积小、多进程共享（省内存）、可独立升级/热更新；缺点：部署复杂（缺 dll 报错）、运行期加载开销、版本兼容问题

**静态库 .lib vs 动态库 .lib**：动态库的 .lib 是**导入库**（只有符号地址表，代码在 .dll），静态库 .lib 含实际代码。
**知识点讲解：**
```bash
# 静态库
g++ -c foo.cpp -o foo.o
ar rcs libfoo.a foo.o
g++ main.cpp libfoo.a -o app
# 动态库
g++ -shared -fPIC foo.cpp -o libfoo.so
g++ main.cpp -lfoo -L. -o app    # 运行时需 LD_LIBRARY_PATH
```
> [!Info] 可能的追问:
> - Q: 动态库的 .lib 和静态库 .lib 区别？
> - A: 动态库配套的 .lib 是导入库（import library），只含导出函数符号表/地址，链接时用于解析符号，实际代码在 .dll/.so。静态库 .lib 本身就含编译好的代码，链接时整体拷入可执行文件。
> - Q: 动态库版本兼容（ABI）问题？
> - A: 动态库升级不能破坏 ABI（导出函数签名、类内存布局、调用约定），否则旧程序崩溃。所以动态库的公开接口用 C ABI（extern "C"）+ 版本管理（libfoo.so.1.2）。这也和 name mangling、ODR 相关。

### TCP 三次握手的过程/为什么不可以两次握手？
**回答话术：**
**三次握手**（建立连接）：
1. 客户端发 **SYN**（seq=x）请求连接
2. 服务端回 **SYN+ACK**（seq=y, ack=x+1）确认并同步
3. 客户端发 **ACK**（ack=y+1）确认，连接建立

**为什么两次不行**：
- 防止**已失效的连接请求**突然到达服务端造成资源浪费。例：客户端第一次 SYN 在网络滞留，超时重发建立连接传输后关闭；此时滞留的旧 SYN 到达服务端，若两次握手服务端会误建连接（浪费资源）并收不到数据；三次握手服务端等客户端确认，客户端发现是旧请求不响应，服务端超时放弃。
- 保证双方都确认**对方收发能力正常**：三次才能互相确认"我能发你收到、你能发我收到"。

**知识点讲解：**
```text
C -> S: SYN, seq=x
S -> C: SYN+ACK, seq=y, ack=x+1
C -> S: ACK, ack=y+1     （此后可传数据）
```
> [!Info] 可能的追问:
> - Q: 三次握手的本质要解决什么？
> - A: 解决**双方确认序列号同步 + 防历史连接**。TCP 是可靠字节流，连接建立必须同步 ISN（初始序列号）。三次握手让双方都确认对方的序列号和收发能力。两次只能让服务端确认客户端，无法防止旧 SYN 造成半连接。
> - Q: 三次握手可以携带数据吗？
> - A: 前两次（SYN/SYN+ACK）不能带数据（此时序列号未确认，带数据有风险），第三次 ACK 可以携带数据。因为第三次时客户端已确认连接可用。

### TCP 四次挥手的过程？TCP 是如何保证可靠性？
**回答话术：**
**四次挥手**（关闭连接）：
1. 主动方发 **FIN**（不再发数据）
2. 被动方回 **ACK**（确认收到，但被动方还可发数据）
3. 被动方发完数据后发 **FIN**（关闭自己的发送）
4. 主动方回 **ACK**（确认关闭）

**为什么四次**：TCP 是全双工，两个方向独立关闭。被动方收到 FIN 后可能还有数据要发，先 ACK 确认、发完再 FIN。所以多了一次（ACK 和 FIN 分开）。

**TCP 可靠性机制**：
- **序列号 + 确认应答（ACK）**：每个字节有序列号，接收方确认收到的序列号
- **超时重传**：发出去没收到 ACK 超时重发
- **滑动窗口/流量控制**：根据接收方缓冲区动态调整发送速率（防接收方处理不过来）
- **拥塞控制**：慢启动、拥塞避免、快重传快恢复，防网络拥塞
- **数据校验**：校验和检测错误
- **连接管理**：三次握手建立、四次挥手关闭

**知识点讲解：**
```text
主动方 -> FIN  -> 被动方
主动方 <- ACK  <- 被动方   （被动方进入 CLOSE_WAIT）
主动方 <- FIN  <- 被动方   （被动方发完剩余数据）
主动方 -> ACK  -> 被动方   （主动方进入 TIME_WAIT）
```
> [!Info] 可能的追问:
> - Q: 为什么主动关闭方要 TIME_WAIT 等 2MSL？
> - A: 1) 保证最后一个 ACK 能到达对方（丢失则对方重发 FIN，需再回 ACK）；2) 让旧连接的报文在网络中消失，防止干扰新连接（相同四元组）。TIME_WAIT 时长 2MSL（最大报文生存时间两倍）。
> - Q: 什么是半关闭、半连接状态？
> - A: 半关闭（half-close）：一方 FIN 后还能收数据（TCP 允许单向关闭）。半连接（SYN_RCVD）：服务端收到 SYN 发出 SYN+ACK 但未收到最终 ACK，处于半连接状态（防 SYN Flood 攻击的关键窗口）。

### HTTP 协议有使用过吗？Qt5 中使用的相关联的主要的几个类？
**回答话术：**
HTTP 协议使用过（客户端请求服务端）。Qt 网络访问核心三件套：
- `QNetworkAccessManager`：管理器，发请求、接收回复（singleton 风格）
- `QNetworkRequest`：封装请求（URL、头部、body）
- `QNetworkReply`：回复对象，异步，通过信号接收数据

流程：`manager->get(request)` 返回 reply，连接 reply 的 `readyRead`/`finished` 信号读取数据，完成后 `deleteLater`。

**知识点讲解：**
```cpp
QNetworkAccessManager manager;
QNetworkRequest req(QUrl("https://api.example.com/data"));
req.setHeader(QNetworkRequest::ContentTypeHeader, "application/json");
QNetworkReply* reply = manager.get(req);
connect(reply, &QNetworkReply::finished, [reply] {
    if (reply->error() == QNetworkReply::NoError) {
        QByteArray data = reply->readAll();
    }
    reply->deleteLater();
});
```
> [!Info] 可能的追问:
> - Q: 为什么 Qt 网络访问是异步的？
> - A: 网络请求耗时不确定，同步阻塞会卡死 UI 线程（事件循环无法处理事件）。异步：发出请求立即返回，数据到了通过信号（readyRead/finished）在事件循环回调，UI 不阻塞。这是 Qt 事件驱动 + 网络 IO 的典型配合。
> - Q: 如何设置超时/取消请求？
> - A: `QNetworkRequest::setTransferTimeout(ms)` 设超时；`reply->abort()` 取消。超时/取消都触发 `finished` 信号（error() 返回相应错误码）。跨线程可用 `QNetworkAccessManager` 在主线程，请求经队列连接。

### 什么是连接半打开、半关闭状态？
**回答话术：**
- **半打开（Half-Open）**：连接一方异常（崩溃/断电）未发 FIN，另一方不知道连接已断。TCP 靠**保活机制（KeepAlive）**探测，应用层靠心跳包检测。SYN_SENT 也是一种"半连接"（客户端已发 SYN 等服务端）
- **半关闭（Half-Close）**：TCP 支持单向关闭——一方 FIN 后仍可接收对方数据（`shutdown(SHUT_WR)` 或 close 发送方向）。应用层用半关闭实现"对方发完数据我还能继续收"

**知识点讲解：**
```text
半打开：A 崩溃，B 不知道，B 发数据无响应（需心跳/超时检测）
半关闭：A 调 shutdown(SHUT_WR) 不再发数据但仍可收，B 知道 A 发完了
```
> [!Info] 可能的追问:
> - Q: 如何检测半打开连接？
> - A: 1) 系统 KeepAlive（TCP 层周期探测，默认 2 小时太慢）；2) 应用层心跳包（定期互发，超时判定对端失效）——IM 系统/长连接常用；3) 写操作失败/超时检测（对端关闭后写会触发 RST）。生产系统用应用层心跳最可靠。
