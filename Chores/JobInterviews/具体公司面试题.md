### 一个 C 程序从源文件到可执行文件经历了哪几步？
关联笔记：[[Learn/Language/C C++/EmbedingDev#跟踪一次编译]]
**回答话术：**
四个阶段，每个阶段都是一个独立的程序，`gcc` 只是驱动：
1. **预处理**（`cc1 -E`）：展开 `#include`、宏、条件编译，去掉注释，产出 `.i`。
2. **编译**（`cc1 -S`）：词法→语法→语义分析，生成中间表示并优化，产出汇编 `.s`。
3. **汇编**（`as -c`）：把汇编翻成机器码，产出**可重定位目标文件** `.o`——此时地址还没定，符号表里留着"未定义符号"和"重定位项"。
4. **链接**（`ld`，gcc 通过 collect2 调用）：符号解析 + 重定位 + 段合并，补上 `crt*.o`、`-lc` 和动态链接器路径，产出可执行 ELF。
工具链岗位的额外关注点：入口不是 `main` 而是 `_start`（crt 里）→ `__libc_start_main` → `main`；交叉编译时这四步换成目标平台的版本，`--target`、`sysroot`、`-mcpu/-march` 决定用哪套工具和哪个 libc。
**知识点讲解：**
```sh
gcc -E main.c -o main.i   # 预处理
gcc -S main.i -o main.s   # 编译
gcc -c main.s -o main.o   # 汇编
gcc main.o -o main        # 链接
gcc -v main.c 2>&1 | grep -E 'cc1|as |collect2|ld'   # 看驱动实际调了谁
readelf -h main           # 入口地址、机器类型、是否 PIE
```
> [!Info] 可能的追问:
> - Q: `gcc` 和 `ld` 是什么关系？
> - A: `gcc` 是驱动程序，自己不做编译，按顺序调 `cc1`/`as`/`collect2`（再调 `ld`）；链接时自动补 `crt1.o`、`crti.o`、`-lc`、`-lgcc` 和动态链接器路径。所以要控制链接行为，用 `-Wl,` 把参数透传给 `ld`。
> - Q: 目标文件里的"重定位项"到底是什么？
> - A: 编译单个文件时不知道外部符号和最终段的地址，先写占位值，同时记一条"这里需要按符号 X 的地址改写"的记录（`R_X86_64_PC32`、`R_AARCH64_CALL26` 等）。链接器算出最终地址后逐条回填，这一步不可逆，所以链接后不能再随意改段布局。
> - Q: 为什么目标平台换了，程序就不能跑？
> - A: 三重不一致：指令编码（ISA）不同、ABI/调用约定不同（寄存器传参规则、栈对齐、结构体布局）、运行时不同（动态链接器路径、libc 版本、系统调用号）。`file` 和 `readelf -h` 能看出 `e_machine` 和解释器路径是否匹配。
### 汇编器和反汇编器是怎么实现出来的？
**回答话术：**
汇编器通常两遍扫描：
- **第一遍**：逐行解析标签、助记符和操作数，查指令编码表确认这条指令多长、需要什么编码格式，把标签记进符号表；遇到前向引用（先引用后定义）先留空。
- **第二遍**：生成机器码，把符号换成段内偏移；外部符号和最终地址未知的引用写占位值并追加一条重定位项。
关键数据结构就四样：指令表（助记符 → 编码格式 + 操作数约束）、操作数解析器（寄存器/立即数/寻址方式）、符号表、重定位表；再加段缓冲管理（`.text`/`.data`/`.bss`）。
反汇编是反向过程，难点不在"翻出来"，而在**边界**：x86 是变长指令，从错误起点开始解码会一路错下去；ARM/RISC-V 定长 4 字节，天然对齐。代码和数据混在一起时无法靠字节判断，要靠 ELF 符号表、DWARF 调试信息、函数边界，或者从入口/跳转目标递归（objdump 用的是线性扫描）。
工程坑：伪指令（`.text`/`.align`/`.word`）不产生机器码但影响布局；跳转目标超出立即数范围要换成长跳转；大小端决定多字节立即数和指令字的排布。
**知识点讲解：**
```text
汇编器两遍扫描
pass1：label → 段内偏移入符号表；确定每条指令长度（决定后续地址）
pass2：生成机器码；外部符号写 0 并记录重定位 (offset, symbol, type)

反汇编为什么可能错（x86）：定长不存在，起始点错 1 字节 → 后续全部错位
定长 ISA（ARM/RISC-V）：按 4 字节对齐切分，只需区分代码/数据
```
> [!Info] 可能的追问:
> - Q: 汇编器怎么处理"本地标签"和"全局符号"？
> - A: 本地标签（如 `.L1`）第一遍就能解析，直接替换成偏移，不进符号表；全局符号要留给链接器做符号解析，写进 `.symtab`，并限制可见性（`.globl`/`.local`）。
> - Q: 反汇编器怎么区分代码段里的常量池？
> - A: 做不到严格区分。靠段属性（只读数据不反汇编）、符号表、以及"控制流不会跳到这里"的启发式；所以反汇编输出里常出现把常量当指令的伪指令，工具会标注 `.byte` 或 `(bad)`。
> - Q: 为什么反汇编器要配合调试信息？
> - A: DWARF 提供源码行号、变量位置和函数边界，`objdump -S` 才能把机器码和源码行对齐；没有它只能给出裸汇编，无法确定内联和优化后的对应关系。
### 链接器怎么完成符号解析和重定位？
关联笔记：[[Learn/ToolChain/CppBuildAndLinking#符号表与重定位]]
**回答话术：**
链接器输入一组目标文件和库，做两件事：
- **符号解析**：把每个"未定义引用（U）"配到一个"定义（T/D/B）"。规则：强符号（函数、已初始化全局）不能重复定义，重复即报错；强 + 弱（`__attribute__((weak))`）取强；多个弱符号任选一个且不报错——这是 C 里最隐蔽的一类 bug。
- **重定位**：按最终地址改写引用处，包括段内相对跳转、绝对地址、GOT/PLT 表项。
静态库按需拉取：链接器按命令行顺序扫 `.a`，只把"能解决当前未定义符号"的成员拉进来；顺序错了就 `undefined reference`，循环依赖要用 `--start-group/--end-group` 或调整顺序。
段合并后按 linker script 映射到 VMA/LMA，写进 program header。动态链接把符号解析推迟到运行期，由 `ld.so` 完成，走 PLT/GOT 间接跳转。
**知识点讲解：**
```sh
nm -C a.o          # U 未定义 / T 代码 / D 已初始化 / B 未初始化 / W 弱符号
readelf -r a.o     # 重定位表：offset + R_TYPE + symbol
ld -T link.ld -o fw.elf a.o b.o   # 自定义段布局（裸机/DSP 必须）
objdump -d -j .text main
```
```text
linker script 管什么
MEMORY { FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 512K
         RAM  (rwx): ORIGIN = 0x20000000, LENGTH = 128K }
SECTIONS { .text : { *(.text*) } > FLASH
           .data : { *(.data*) } > RAM AT> FLASH   /* 初值放 flash，运行时拷到 RAM */
           .bss  : { *(.bss*)  } > RAM }
```
> [!Info] 可能的追问:
> - Q: `undefined reference` 的常见原因？
> - A: 根本没链接对应库、`.a` 顺序不对、C++ 名字修饰没对上（C 头文件缺 `extern "C"`）、模板或 inline 函数只声明未定义、符号被 `static` 限制成内部链接。
> - Q: 弱符号有什么用？
> - A: 允许"默认实现 + 可覆盖"：库里给弱定义，用户定义了强符号就自动替换（`-Wl,--wrap=` 也是类似思路的链接期打桩）。C++ 里常见的 `__attribute__((weak))` 用于可选功能，缺实现时退化为空实现。
> - Q: 静态链接的程序为什么还能用 `dlopen`？
> - A: 不能直接支持——静态链接没有动态链接器和导出符号表。要用需显式提供动态加载支持（`-Wl,-E`）并把符号导出，现实里通常改成动态链接或直接把插件静态链接进去。
### 把 libc（或 newlib）移植到一个新平台，需要实现哪些东西？
关联笔记：[[Learn/Language/C C++/EmbedingDev#工具链由哪些部分组成]]
**回答话术：**
libc 分两半：与架构无关的算法（`printf` 格式化、`malloc`、字符串函数）和必须针对平台实现的底层。
底层清单按"缺了就跑不起来"排序：
1. **启动代码 `crt0`**：设置栈指针、清 `.bss`、把 `.data` 从 flash 拷到 RAM、准备好参数（argc/argv，裸机上常造假）、调用 `main`，返回后走 `_exit`。
2. **系统调用桩**：`_write`/`_read`/`_close`/`_lseek`/`_fstat`/`_isatty`/`_sbrk`/`_exit`——裸机上映射到 UART、文件系统或调试通道；有 OS 的平台映射到真实 syscall 号。
3. **`malloc` 的内存来源**：`_sbrk` 从链接脚本给的堆起点分配；没有 MMU 的平台通常用 bump allocator 或固定池。
4. **体系结构相关汇编**：`setjmp/longjmp`（保存 callee-saved 寄存器和 SP）、`memcpy/memset` 的优化版本、原子操作、上下文切换。
5. **TLS 与 `errno`**：单线程可以给个全局变量；多线程要按 ABI 实现线程指针（如 RISC-V 的 `tp`、ARM 的 `TPIDR_EL0`）。
6. **stdio 重定向**：`printf` 默认走 `_write`，裸机上要保证 UART 初始化、并处理缓冲（行缓冲要 `\n` 或 `fflush`）。
newlib 的组织方式：`newlib/`（架构无关）+ `libgloss/`（各平台 syscall 桩与启动代码）；移植 = 新增一个 libgloss 目标 + 实现上面那批桩 + 跑通 newlib testsuite。
验证顺序：先在模拟器上跑 `hello world` → `printf` 的各类格式（`%d/%s/%f/%x`、宽度精度）→ 字符串/内存函数 → `malloc/free` 压力 → `setjmp/longjmp` 与 C++ 异常。
**知识点讲解：**
```c
/* 裸机上的最小 syscall 桩：printf 能不能出字，全看这里 */
int _write(int fd, char *buf, int len) {
    for (int i = 0; i < len; i++) uart_putc(buf[i]);
    return len;                     /* 返回值必须≥0，否则 stdio 认为失败 */
}
void *_sbrk(ptrdiff_t incr) {       /* malloc 向这里要内存 */
    extern char _end;               /* linker script 提供的堆起点 */
    static char *heap = &_end;
    char *old = heap;
    heap += incr;
    return old;
}
```
```text
移植顺序（缺一步就卡住）
crt0 → _sbrk → _write → printf 出字 → 字符串函数 → malloc 压力 → setjmp/longjmp → 异常/多线程
```
> [!Info] 可能的追问:
> - Q: 为什么 `setjmp/longjmp` 必须用汇编实现？
> - A: 它要在不依赖编译器生成的栈帧的情况下保存/恢复 callee-saved 寄存器、SP 和返回地址，还必须在函数返回后仍然有效的状态上工作；不同 ABI 保存的寄存器集合不同，只能用目标平台汇编逐条写。
> - Q: `printf` 在裸机上没输出，怎么定位？
> - A: 按链路查：`_write` 是否被调用（打桩计数/断点）→ 缓冲是否没刷（加 `\n` 或 `fflush`）→ UART 是否初始化、波特率与引脚是否正确 → 是否开了半主机（semihosting）导致卡在调试器上。
> - Q: 有 MMU 和没 MMU 的平台，移植差异最大在哪？
> - A: 内存分配与保护。没 MMU 只能用固定池/链接脚本划区，`_sbrk` 必须检查越界；有 MMU 要建页表、处理缺页，`malloc` 可以靠 `mmap` 向系统要页，栈溢出也会从"静默踩内存"变成可捕获的缺页异常。
### 什么是指令模拟器？解释执行、静态翻译、动态翻译有什么区别？
**回答话术：**
指令模拟器（ISS）用软件实现一颗 CPU：取指 → 译码 → 执行 → 写回寄存器/内存，循环到停机。真正的工作量在"模拟得不只是指令"：
- **内存模型**：地址空间映射、页权限、对齐检查、大小端、MMIO 区域（外设寄存器读写要有副作用）。
- **异常与中断**：指令边界才能精确处理，构造异常帧、跳向量表、保存/恢复状态。
- **特权级与 CSR**：系统寄存器、陷入与返回。
三种实现方式的取舍：

| 方式 | 做法 | 速度 | 适用 |
| --- | --- | --- | --- |
| 解释执行 | 每条指令循环里译码 + 执行 | 慢（相对硬件 10~100 倍） | 正确性优先、调试器、教学 |
| 静态翻译（AOT） | 整个 binary 先翻成本机代码再跑 | 快 | 代码固定、无自修改 |
| 动态翻译（JIT/TCG） | 以基本块为单位，首次执行时翻译并缓存 | 较快，兼顾动态性 | 通用模拟器（QEMU） |

动态翻译的关键：基本块（TB）以跳转结尾，翻译结果缓存在以 guest PC 为键的哈希表里；自修改代码必须让缓存失效（mprotect + 脏页跟踪），否则跑的是旧代码。寄存器映射是另一个核心：guest 寄存器放 host 寄存器还是内存槽，决定生成代码的质量。
**知识点讲解：**
```c
/* 解释执行的最小骨架 */
while (running) {
    uint32_t insn = fetch(pc);        /* 考虑端序与跨页 */
    decode(insn, &op);                /* opcode / rd / rs / imm */
    execute(&op, &regs, mem);         /* 算术、访存、跳转、异常 */
}
```
```text
动态翻译（QEMU TCG 思路）
  首次执行 TB → 翻译成 host 指令块 → 存 cache[guest_pc]
  下次直接跳进 cache 执行
  自修改代码：写 guest 代码页 → 标记脏 → invalidate 对应 TB
```
> [!Info] 可能的追问:
> - Q: 模拟器怎么保证"精确异常"？
> - A: 只在指令边界检查挂起事件，且单条指令的副作用要么全生效要么不生效——访存要延后提交或能回滚，否则异常发生时寄存器/内存状态已经不一致，恢复后行为就和真机不同。
> - Q: 怎么验证模拟器是对的？
> - A: 三层：架构一致性测试（如 riscv-tests、CPU 厂商的合规用例）、与参考实现逐指令对比（差分测试，随机指令序列）、跑真实软件栈（libc testsuite、CoreMark）看结果与硬件一致。
> - Q: 为什么 DSP 平台尤其需要模拟器？
> - A: 芯片流片前没有硬件可跑，软件（含工具链自测、libc 测试、算法验证）全靠模拟器；DSP 还常带特殊寻址/累加器行为，模拟器是唯一能逐周期对照规格的地方。
### 给一套 C 代码搭测试框架，你会怎么做？
**回答话术：**
分四层，先能用再完善：
1. **断言层**：一组宏，失败时打印文件、行号、表达式和期望/实际值，并累加失败计数（不要用 `assert`，它会 abort 掉整个进程，拿不到汇总）。
2. **用例注册与执行层**：每个用例是一个 `void(void)` 函数，注册进表，`main` 遍历执行、打印统计并返回非零码（CI 据此判定）。
3. **夹具与打桩层**：`setUp/tearDown` 建/拆环境；依赖用函数指针注入，或用链接期打桩（`-Wl,--wrap=foo`、`__attribute__((weak))` 提供默认可替换实现）。
4. **度量与集成层**：`--coverage` + gcov/lcov 出覆盖率，`ctest`/`make test` 进 CI，失败即阻断合并。
C 没有反射和全局构造，注册表常用两种写法：宏静态注册（手写数组）或**自定义链接节**（`__attribute__((section("tests")))` + `__start_tests/__stop_tests` 遍历），后者不用维护清单，加用例只写一个文件。
**知识点讲解：**
```c
#define TEST(name)                                        \
    static void name(void);                               \
    static const struct test_case tc_##name               \
        __attribute__((section("tests"))) = { #name, name }; \
    static void name(void)

#define ASSERT_EQ(a, b) do {                              \
    long long _a = (long long)(a), _b = (long long)(b);   \
    if (_a != _b) {                                       \
        fprintf(stderr, "%s:%d: %s(%lld) != %s(%lld)\n",  \
                __FILE__, __LINE__, #a, _a, #b, _b);      \
        g_failed++;                                       \
    }                                                     \
} while (0)
```
```sh
gcc -O0 -g --coverage tests/*.c src/*.c -o run_tests
./run_tests && gcov src/*.c && lcov --capture -d . -o cov.info
```
> [!Info] 可能的追问:
> - Q: 静态函数怎么测？
> - A: 三种：把逻辑抽到内部头文件暴露、测试文件直接 `#include "impl.c"`（简单但破坏隔离）、或编译时 `-Dstatic=` 去掉限制（hack，别进主干）。
> - Q: 覆盖率 100% 就说明测得好吗？
> - A: 不是。覆盖率只证明那行被执行过，不证明断言有效。要看边界值、错误分支、打桩的失败路径有没有断言；分支覆盖比行覆盖有意义。
> - Q: 嵌入式/裸机上能做单测吗？
> - A: 抽两层：算法与协议层在主机上编译测试（mock 硬件接口），硬件相关层用桩或用 QEMU/模拟器跑；这样绝大部分逻辑不依赖板子，回归速度也快。
### gdb 常用命令有哪些？程序崩溃或卡死怎么查？
**回答话术：**
- **断点**：`b func`、`b file:line`、`b *0x4005a0`（地址）、`tbreak`（一次性）、`condition`（条件断点）、`watch var`（值变化时停）。
- **执行**：`run`、`next`/`step`、`finish`、`until`、`continue`。
- **看状态**：`bt`、`frame n`、`info locals`/`info args`、`info registers`、`x/16gx $rsp`（看栈内存）、`disassemble`、`p var`、`ptype`。
- **崩溃**：开启 core（`ulimit -c unlimited` + `core_pattern`），`gdb ./app core`，`bt` 看栈顶几层；怀疑内存破坏直接上 ASan，比事后看 core 快得多。
- **卡死/卡慢**：`gdb -p <pid>` 后 `thread apply all bt`，看是否都停在 `futex`/`pthread_mutex_lock`；采样两三次对比，找出一直持有锁的线程。
- **坑**：`-O2` 下变量显示 `<optimized out>`、内联导致栈帧缺失、`static` 变量要写 `file::var`；看优化后的代码要结合 `disassemble`。
**知识点讲解：**
```sh
ulimit -c unlimited
echo '/tmp/core.%e.%p' | sudo tee /proc/sys/kernel/core_pattern
gdb ./app core.1234 -ex 'bt full' -ex 'info registers' -ex 'x/8gx $rsp' -ex quit
gdb -p $(pgrep app) -ex 'thread apply all bt' -ex 'detach'
gdb ./app -ex 'b main.cpp:42' -ex 'run' -ex 'p *obj' -ex 'bt'
```
> [!Info] 可能的追问:
> - Q: 段错误的常见原因？
> - A: 空/野指针解引用、数组越界踩到相邻对象、`use-after-free`、栈溢出覆盖返回地址、未对齐访问（SIMD 要求 16 字节对齐）、栈大小不足导致压栈踩到保护页。
> - Q: 线上没有 core 文件怎么查？
> - A: 先确认限制：`ulimit -c`、容器/`systemd` 的 core 限制、`core_pattern` 是否指向只读或不存在目录（否则静默失败）；有 `coredumpctl` 的系统直接 `coredumpctl gdb`。再不行用日志 + ASan 复现。
> - Q: 怎么调试一个多线程死锁？
> - A: `thread apply all bt` 看每个线程的阻塞点；如果都停在锁上，用 `pthread_mutex_t.__owner`（glibc）找持锁线程；再回到那个线程的栈看它在等什么资源。根治靠固定加锁顺序 + 超时/锁层级检测。
### ELF 文件里的段和节有什么区别？常见的有哪些？
关联笔记：[[Learn/Language/C C++/EmbedingDev#ELF 魔数、文件头与 `e_machine`]]
**回答话术：**
ELF 由三部分组成：**ELF 头**（类型、机器、入口地址）、**程序头表**（program header，给加载器看：哪些 segment 要映射、权限、虚拟地址）、**节头表**（section header，给链接器和调试器看：各节的类型、大小、偏移）。
- **节（section）** 是链接时的逻辑单位：`.text` 代码、`.rodata` 只读常量、`.data` 已初始化全局/静态、`.bss` 未初始化（不占文件空间只占内存）、`.symtab`/`.strtab` 符号与字符串、`.rela.*` 重定位、`.debug_info` 等调试信息。
- **段（segment）** 是加载时的映射单位，通常把若干节合并：`PT_LOAD` 只读段（`.text`+`.rodata`，R-X）、可读写段（`.data`+`.bss`，RW-）。按页设置权限，所以分段的目的是避免 W+X 和减少映射次数。
调试工具链时最常用的四条命令：`readelf -h/-l/-S`、`readelf -r`、`objdump -d/-t`、`size`。
**知识点讲解：**
```sh
readelf -h a.out   # 类型(EXEC/DYN/PIE)、e_machine、entry
readelf -l a.out   # 程序头：LOAD 段 vaddr/filesz/memsz/flags
readelf -S a.out   # 节头：.text .rodata .data .bss .symtab .strtab .rela.text
size a.out         # text/data/bss 三段，bss 不计入文件
```
```text
文件里     .text .rodata .data（.bss 只记大小）
加载后     只读段 R-X ← .text + .rodata
          读写段 RW- ← .data + .bss（清零 memsz - filesz 部分）
```
> [!Info] 可能的追问:
> - Q: `.bss` 为什么不占文件体积？
> - A: 内容全是零，没必要在文件里存一遍。ELF 只在节头/程序头记录大小（`memsz > filesz`），加载器分配内存后清零。对嵌入式尤其重要：固件体积不随大数组增长，但 RAM 占用照算。
> - Q: 为什么 PIE/PIC 需要 GOT？
> - A: 代码可能被加载到任意基址，指令里不能写死绝对地址。PIC 用 PC 相对寻址访问本模块数据，跨模块的全局符号/函数地址放在 GOT 里，由动态链接器在加载时填。详见[[Learn/ToolChain/CppBuildAndLinking#PLT、GOT 与动态符号插桩]]。
> - Q: `size` 报的 text 和我源文件大小对不上，正常吗？
> - A: 正常。`text` 含代码和只读常量，受优化、内联、模板实例化、调试信息（一般不算在 text 里但会进文件）影响；跨平台还受对齐填充影响。要比就比同配置下的相对变化。
### C 语言怎么实现"面向对象"（函数指针表 / 虚表）？
**回答话术：**
C 里用"结构体 + 函数指针"做多态，模式和 C++ 虚表一一对应：
- 数据结构和操作分离：结构体只存数据（或再放一个 `void *priv`），操作集中在一张 `const struct ops` 表里，构造时把表指针挂到对象上。
- 调用走间接：`obj->ops->read(obj->priv, ...)`，和 C++ 的 `vptr->read(this)` 是同一机制。
- 工具链和模拟器里大量这么写：后端抽象（`struct TargetOps` 放 emit/encode/relax 等函数指针，不同 ISA 各实现一份）、设备模型、驱动接口。
- 有意为之的取舍：C 没有自动析构和构造顺序，要显式 `init/destroy`；类型安全弱，参数靠 `void *`；好处是 ABI 稳定、能被汇编和其他语言直接调用。
**知识点讲解：**
```c
struct ops {
    int (*read)(void *ctx, void *buf, int n);
    int (*write)(void *ctx, const void *buf, int n);
};
struct uart { const struct ops *ops; void *ctx; };

static int uart_read(void *ctx, void *buf, int n)  { return hw_read((struct port *)ctx, buf, n); }
static int uart_write(void *ctx, const void *buf, int n) { return hw_write((struct port *)ctx, buf, n); }
static const struct ops uart_ops = { uart_read, uart_write };

struct uart u = { .ops = &uart_ops, .ctx = &port };
u.ops->read(u.ctx, buf, 16);        /* 多态调用 */
```
```text
C++ 虚表对照：对象首部隐含 vptr → 静态 vtable（每个类一份）→ 虚函数按声明顺序排
所以"函数指针表 + 对象里存表指针"就是手写虚表，多继承时相当于多张表 + this 调整偏移
```
> [!Info] 可能的追问:
> - Q: 函数指针和数据指针的大小一定相同吗？
> - A: 不保证。C 标准没有要求，某些平台（哈佛架构、部分嵌入式工具链）函数指针更宽或位于不同地址空间；把函数指针塞进 `void *` 是未定义行为。可移植写法是各自用正确的类型，或统一用 `union`。
> - Q: 为什么工具链/嵌入式代码偏爱这种 C 风格，而不是直接用 C++？
> - A: 编译器自举、C ABI 互通、没有运行时（不需要异常/RTTI/全局构造）、生成的代码可预测、跨编译器可移植；C++ 版本通常只用在工具链的高层（前端、优化器）。
> - Q: `extern "C"` 为什么关键？
> - A: C++ 会对函数名做名字修饰（mangling），C 不做。要给汇编、驱动、其他语言的接口必须 `extern "C"` 禁止修饰，否则链接器找不到符号；同时它也限制参数传递方式不能用 C++ 特有类型。详见[[Learn/ToolChain/CppBuildAndLinking#名称修饰与 ABI]]。
