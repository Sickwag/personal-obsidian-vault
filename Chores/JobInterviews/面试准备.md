#### 技术面
**一、把一个 `list<pair<int, int>>` 去重，输出到 `vector<pair<int, int>>`**
答题要点：
- 先问一句"要不要**保留每个值第一次出现的位置**"（也就是去重是否**稳定**），这一步决定用哪个容器，面试官要的就是这个判断。
- 保稳定：遍历 list，用哈希集合记录"见过的"，第一次出现才 push 进 vector，O(n)，输出顺序与输入中首次出现的顺序一致。
- 不要求稳定、只要求去重且有序：直接构造 `std::set<std::pair<int,int>>`，结果是按 `pair` 的字典序排好的，O(n log n)，`pair` 自带 `operator<`。
- 关键坑：`pair` **没有现成的 `std::hash` 特化**（C++20 也没有），要用 `unordered_set` 必须自己写 hash 函数。
代码：
```cpp
struct PairHash {
    std::size_t operator()(const std::pair<int, int>& p) const noexcept {
        std::size_t h1 = std::hash<int>{}(p.first);
        std::size_t h2 = std::hash<int>{}(p.second);
        // 黄金比例常数打散，避免 (1,2) 和 (2,1) 落到同一个桶
        return h1 ^ (h2 + 0x9e3779b97f4a7c15ULL + (h1 << 6) + (h1 >> 2));
    }
};
// 1) 保稳定去重：保留每个值第一次出现的位置
std::vector<std::pair<int, int>> dedupKeepOrder(const std::list<std::pair<int, int>>& l) {
    std::vector<std::pair<int, int>> out;
    std::unordered_set<std::pair<int, int>, PairHash> seen;
    out.reserve(l.size());
    for (const auto& p : l)
        if (seen.insert(p).second) out.push_back(p);   // insert 返回 {迭代器, 是否插入成功}
    return out;
}
// 2) 不保稳定、只要求有序
std::vector<std::pair<int, int>> dedupSorted(const std::list<std::pair<int, int>>& l) {
    std::set<std::pair<int, int>> s(l.begin(), l.end());
    return std::vector<std::pair<int, int>>(s.begin(), s.end());
}
// 3) 不用哈希表：先排序再 unique
std::vector<std::pair<int, int>> dedupSort(std::list<std::pair<int, int>> l) {
    std::vector<std::pair<int, int>> v(l.begin(), l.end());
    std::sort(v.begin(), v.end());
    v.erase(std::unique(v.begin(), v.end()), v.end());
    return v;
}
```
- 复杂度：哈希版 O(n) 期望、O(n log n) 最坏；set 版 O(n log n) 且额外内存；排序版不改输入时也要 O(n) 额外内存。
追问：
- Q: 为什么 `set` 那版不能保证稳定？
- A: `set` 是按 `operator<` 排好的红黑树，遍历顺序由 key 决定，与插入顺序无关；同样的元素换个输入顺序，输出完全一样。想"稳定 + 不用哈希表"，就得额外记一份"值 → 首次下标"，排完序再按下标还原，多花 O(n) 内存。
- Q: 为什么要自定义 hash？标准库不是有 `std::hash` 吗？
- A: 有 `std::hash<int>`，但**没有 `std::hash<std::pair<int,int>>`**——标准只给基础类型、`std::string` 等提供特化，`pair`/`tuple` 不提供（到 C++20 也没有）。`unordered_set<pair<...>>` 的 `Hasher` 模板参数必须能构造出对象，缺特化就编译不过。不想写 hash 就换 `std::set`（`pair` 自带 `operator<`），代价是 O(n) 变 O(n log n)。
- Q: 为什么写 `std::hash<int>{}(obj)` 这种别扭的形式？
- A: `std::hash<int>` 是**一个类型**（类模板的特化），不是函数。`std::hash<int>{}` 是值初始化一个临时对象，后面的 `(obj)` 才是调用它的 `operator()`；等价写法是 `std::hash<int>()(obj)` 或 `std::hash<int> h; h(obj);`。标准库把哈希设计成"可特化的函数对象类型"，容器才能在模板参数里换成自定义 hash。
- Q: `operator()` 为什么标 `const noexcept`？
- A: `const` 是**必需的**：标准要求 `Hash` 能在 **const 对象**上调用（表达式 `h(k)` 里 `h` 是 const），容器内部也是把哈希器当成员保存、以 const 引用调用；不标 const，主流实现（libstdc++/libc++）直接编译不过。`noexcept` 是**承诺**：哈希不分配、不抛异常（标准对 `std::hash` 的调用要求 Throws: nothing），标上它少一层异常处理表、容器的异常保证也更宽松。原则一句话：哈希只读、无副作用、同输入同输出。
- Q: 不想在面试里写 `0x9e3779b97f4a7c15ULL` 这种魔数，有没有更通用的写法？
- A: 有，按元素类型分三档，越靠前越干净：① **能拼进 64 位就直接拼**（`int` 场景零冲突、零魔数）；② **逐字段组合**（类型无关，要一个打散常数：`seed ^= h + k + (seed << 6) + (seed >> 2)`，`k` 就是黄金比例常数 `2^64/φ`，有出处、不是拍脑袋，32 位平台要换成 32 位常数）；③ **按字节哈希**（任意可平凡拷贝类型，把对象当 `const unsigned char*` 用 FNV-1a/xxh3 算，代价是 offset basis 这类"官方定义"的常数）。
- A: 第 ① 种写法（面试里推荐，不用魔数）：
```cpp
std::size_t operator()(const std::pair<int, int>& p) const noexcept {
    auto u = [](int v) { return static_cast<std::uint64_t>(static_cast<std::uint32_t>(v)); };
    return static_cast<std::size_t>((u(p.first) << 32) ^ u(p.second));
}
```
- 面试口径：先给拼接法，再说"通用组合需要一个有出处的打散常数，标准库不提供 `pair` 的组合器"；重点是**同输入恒定、分布均匀、无副作用**，常数本身不是知识点。
- Q: `std::unique` 返回什么？`erase` 的参数、返回值和工作原理？
- A:
    - `std::unique(first, last)` 返回**去重后新区间的尾后迭代器**（新的逻辑 end）。它不删元素，只把不重复的元素依次向前搬，区间长度不变；`[new_end, last)` 里是搬剩下的残留值（内容未规定）。
    - `vector::erase(first, last)` 接受要删的**迭代器范围**，返回**被删区间之后元素的迭代器**（即新的 end）；原理是把 `[last, end)` 逐个前移到 `first`，再把 size 减掉，元素移动 O(n)。
    - 所以惯用法是 `v.erase(std::unique(v.begin(), v.end()), v.end())`；注意 `unique` 只删**相邻**重复，必须先 `sort`。
    - 单参版本 `erase(it)` 删一个元素并返回下一个位置；`list::unique/remove` 是成员函数，直接摘节点、不搬元素。
- Q: 如果要保留第一次出现的位置，但又想省内存？
- A: 数据量小时排序去重更省（无哈希表），但要额外记原下标才能还原顺序；两头都要就只能上哈希集合。
**二、两数之和（返回下标）**
答题要点：
- 哈希表存"已经见过的值和下标"，遍历时查 `target - x`，命中就返回，O(n) 时间、O(n) 空间。
- **先查后插**：否则 `[3,3], target=6` 会把同一个元素用两次。

代码：
```cpp
std::vector<int> twoSum(const std::vector<int>& nums, int target) {
    std::unordered_map<int, int> seen;      // 值 -> 下标
    for (int i = 0; i < static_cast<int>(nums.size()); ++i) {
        auto it = seen.find(target - nums[i]);
        if (it != seen.end()) return {it->second, i};
        seen.emplace(nums[i], i);           // 先查后插
    }
    return {};
}
```
追问：
- Q: 数组有序怎么做？
- A: 双指针，`l + r < target` 就左移，反之右移，O(n) 时间 O(1) 空间；代价是丢了原下标（要下标就存 (值, 原下标) 再排序）。
- Q: 要返回所有不重复的解？
- A: 排序后固定第一个数，剩下双指针；跳过相邻重复值去重，注意"同一元素不能用两次"的判断。
**三、四、设计函数把 `map` 遍历一遍，把 key 和 value 一起取出来**
答题要点：
- 这两条面经是转写，题干不完整（"给定一个函数，返回 vector 里面两个 int，map 输入是两个 int"）。第一步一定是确认签名：输入是 `map<int,int>`，还是 `map<pair<int,int>, V>`？输出是 `vector<pair<...>>` 还是两个数组？
- 通用写法：一次遍历 + `reserve` + 结构化绑定，别用 `operator[]`。
代码：
```cpp
// 情况 A：输入 map<int,int>，输出 vector<pair<int,int>>
std::vector<std::pair<int, int>> flatten(const std::map<int, int>& m) {
    std::vector<std::pair<int, int>> out;
    out.reserve(m.size());                       // 一次分配，避免扩容
    for (const auto& [k, v] : m) out.emplace_back(k, v);
    return out;
}
// 情况 B：拆成两个数组
void split(const std::map<int, int>& m, std::vector<int>& keys, std::vector<int>& vals) {
    keys.reserve(m.size());
    vals.reserve(m.size());
    for (const auto& [k, v] : m) { keys.push_back(k); vals.push_back(v); }
}
// 情况 C：key 本身是两个 int
std::vector<std::pair<std::pair<int, int>, int>>
flattenPairKey(const std::map<std::pair<int, int>, int>& m) {
    std::vector<std::pair<std::pair<int, int>, int>> out;
    out.reserve(m.size());
    for (const auto& [k, v] : m) out.emplace_back(k, v);
    return out;
}
// 情况 D：函数返回 vector 里的两个 int 当 map 的 key
std::pair<int, int> makeKey(const std::vector<int>& v, std::size_t i) {
    return {v.at(i), v.at(i + 1)};               // at 会做边界检查
}
```
追问：
- Q: 遍历时为什么不能用 `m[k]`？
- A: `operator[]` 是非 const 成员，键不存在会插入默认值，遍历过程被改；读用 `find`/`at`，遍历用范围 for。
- Q: `map` 和 `unordered_map` 遍历顺序？
- A: `map` 按 key 升序（红黑树中序遍历），`unordered_map` 顺序取决于哈希和桶，不可预期；要稳定输出就排序或用 `std::map`。
- Q: 情况 A 能不能写成下面这样（预分配 + `for_each` + `emplace_back`）？
```cpp
std::vector<std::pair<int, int>> flatten(std::unordered_map<int, int>& input) {
    std::vector<std::pair<int, int>> result(input.size());
    std::for_each(input.begin(), input.end(),
                  [&result](const auto& pair) { result.emplace_back(pair); });
    return result;
}
```
- A: **不能**。能编译、`emplace_back` 的调用方式也没错，但结果错：`result(input.size())` 已经构造了 `size` 个**值初始化**的 `pair`（全是 `{0,0}`），随后的 `emplace_back` 是往尾部**追加**，容器最后变成 `2*size` 个元素，前一半全是 `{0,0}`。实测 `map{{1,10},{2,20},{3,30}}` 走这段得到 `size=6`、前三个是 `(0,0)`。
- A: `resize` 和 `reserve` 的区别就是这里的根因：`resize(n)` 改**元素个数**（构造 n 个元素），`reserve(n)` 只改**容量**（预留内存、不构造元素）。要"预分配 + 顺序写入"，用 `resize` 配下标；要用 `push_back`/`emplace_back`，就只能 `reserve`。
- A: 改法一（保留 `emplace_back`，只 `reserve`）：
```cpp
std::vector<std::pair<int, int>> flatten(const std::unordered_map<int, int>& m) {
    std::vector<std::pair<int, int>> out;
    out.reserve(m.size());              // 只预留容量，不构造元素
    for (const auto& kv : m) out.emplace_back(kv);
    return out;
}
```
- A: 改法二（保留预分配，改用下标写，不要 push）：
```cpp
std::vector<std::pair<int, int>> flatten2(const std::unordered_map<int, int>& m) {
    std::vector<std::pair<int, int>> out(m.size());
    std::size_t i = 0;
    for (const auto& kv : m) out[i++] = kv;
    return out;
}
```
- A: 改法三（最直接，迭代器区间构造；`pair<const int,int>` 能转换成 `pair<int,int>`）：
```cpp
std::vector<std::pair<int, int>> flatten3(const std::unordered_map<int, int>& m) {
    return {m.begin(), m.end()};
}
```
- A: 另外三个细节：① 参数该加 `const`，函数不改输入；② lambda 形参名 `pair` 遮蔽了类型名 `std::pair`，容易误用，改叫 `kv`；③ `std::for_each` 不如范围 for 直观，面试里写范围 for 更稳。
- Q: `emplace_back` 和 `push_back` 到底差在哪？谁需要 `std::move`？
- A: 机制差别：`push_back(T&&)` 接受一个**已经构造好的对象**再移动/拷贝进容器；`emplace_back(args...)` 把参数**直接转发给元素构造**（`allocator_traits::construct`），少一次临时对象。对 `pair<int,int>` 这种小对象，性能上几乎没有区别，区别在语义和重载解析：
    - 传**已存在的对象**（左值）时，两者都会**拷贝**，谁都不会自动 move。
    - 传**将亡值**（`std::move(x)`、临时对象、函数返回值）时，`push_back` 走移动构造，`emplace_back` 用参数原地构造，都不拷贝。而字符串字面量是一个坑，**它的真实类型是 `const char[6]`（退化为 `const char*`）**，如果 STL 容器元素类型为 `std::string`，编译器根据类型匹配到 string 的构造函数，导致一次构造的开销
    - 想避免"左值被拷贝"，必须显式 `std::move(x)`（之后 x 处于有效但未指定状态）；`emplace_back` 不会替你 move 一个左值参数，因为它的参数是 `T&&`/`const T&` 转发引用时照样绑定左值。
    - 坑：`emplace_back` 允许隐式转换，参数写错类型可能构造出别的元素（如 `vector<vector<int>>` 里 `emplace_back(3, 4)` 会构造"3 个 4"而不是你想的 `{3,4}`），`push_back` 的类型检查更严；另外 `emplace_back` 对聚合类型/带 `initializer_list` 构造的类型容易踩坑。
- Q: 这里传的是 `pair<const int, int>`（`unordered_map` 的 `value_type`），`push_back` 和 `emplace_back` 都能收吗？
- A: 都能，走的是 `pair<int,int>` 的转换构造函数（`pair<const int,int>` → `pair<int,int>`，`const int` 可拷成 `int`）。`emplace_back(kv)` 是"用 `kv` 构造元素"，`push_back(kv)` 是"先隐式转换成 `pair<int,int>` 再移动进去"，语义上多一步临时对象（编译器通常会优化掉）。
**五、六、读 LLVM `StringRef` 源码：它和 `std::string` 有什么区别？**
答题要点：
- `StringRef` 是**非拥有视图**，内部只有 `const char* Data` 和 `size_t Length` 两个成员：不分配、不拷贝、构造和拷贝都是 O(1)；不保证以 `\0` 结尾。这有引用悬垂问题，并且由于不保存数据，所以也不能够拼接字符串。
- `std::string` **拥有**内存（小字符串走 SSO 内联），可修改，生命周期自己管。
- 设计目的：函数入参用 `StringRef` 能同时接受 `const char*`、`std::string`、字面量、子串，且一律零拷贝；返回值/成员变量才用 `std::string`。
- 风险：视图悬垂。`StringRef s(std::string("tmp"));` 或对临时对象取 `.str()` 之外的引用，临时对象一析构，`s` 就是野指针。也不能把它直接传给 `printf("%s")`/`strlen`。
- 对标：它就是 C++17 的 `std::string_view` 的前身（LLVM 更早），多了 `startswith/endswith/trim/split/consume_front/consume_back` 这些便利方法。
- 源码证据：`begin()` 返回 `Data`、`end()` 返回 `Data + Length`；`bytes()` 也是用 `data()` 和 `size()` 造区间——全程不分配。
追问：
- Q: 为什么函数参数写 `StringRef` 而不是 `const std::string&`？
- A: 后者接受 `const char*` 时会先构造一个临时 `std::string`（可能分配），`StringRef` 直接就是指针 + 长度；而且能接受子串，不产生中间对象。
- Q: 那"可能分配内存"的"可能"指什么？
- A: 指 SSO（短字符串优化）：短字符串（libstdc++ ≤ 15 字符、libc++ ≤ 22、MSVC ≤ 15）直接存在 `std::string` 对象内部的缓冲里，**不 new**；超过阈值才堆分配。所以"每次传 `const char*` 都会分配"是错的，但"可能分配 + 一定 strlen + 一定拷贝"是对的。`StringRef` 把这三项砍到"只剩 strlen"，用 `StringRef(ptr, len)` 构造连 strlen 都省——它的准确说法是**零分配、零拷贝，可能有一次 strlen**。
- Q: `StringRef` 就没有任何风险吗？
- A: 有，而且是最常见的 bug：它不拥有内存。`StringRef s = makeTempString();`、`StringRef s(std::string("abc"));`、把 `StringRef` 存进成员变量而底层字符串已经析构——全部悬垂。规则是"只在参数位置用，不存起来"，非要存就存 `std::string` 或在文档里约定生命周期。
- Q: 为什么 `using iterator = const char *;`？解引用迭代器得到什么？
- A: 因为 StringRef 本身就是"一段连续内存的视图"，所以它把迭代器直接定义成裸指针——`*it` 得到 `char`（`const char*` 解引用是 `const char&`，赋给 `char` 时拷贝一份），`it[i]`、`it + n`、`end() - begin()` 全是指针算术，天然满足随机访问迭代器，无需任何代理类或包装，零开销。
    - `iterator` 和 `const_iterator` 都是 `const char*`：StringRef 从来不可写，没必要准备"可变/只读"两套迭代器。
    - 好处：`begin()/end()` 能直接喂给 `std::find`、`std::sort`、`std::string_view` 构造、`std::distance`，也能写 `for (char c : sref)`。
    - 代价：没有边界检查；`end()` 只是 `Data + Length`，**不保证 `*end() == '\0'`**，所以不能把它当 C 字符串传给 `printf("%s")`/`strlen`。`reverse_iterator` 也是拿它套 `std::reverse_iterator<iterator>` 得到的。
- Q: 那个 `operator=(T&&) = delete` 模板在防什么？`std::enable_if_t` 是什么？
```cpp
template <typename T>
std::enable_if_t<std::is_same<T, std::string>::value, StringRef> &
operator=(T &&Str) = delete;
```
- A: 防的是 `sref = std::string("tmp");` 这种**从临时 std::string 赋值**——临时对象在这条语句结束就析构，`sref` 立刻悬垂（源码注释原话：Disallow accidental assignment from a temporary std::string）。
    - `std::enable_if_t<cond, T>` 就是 `typename std::enable_if<cond, T>::type`：条件为真时它是 `T`（这里是 `StringRef&`），条件为假时这个 `type` 根本不存在，于是这条重载被 SFINAE 从候选集里摘掉。
    - 为什么不干脆写 `operator=(std::string&&) = delete;`：那样形参是 `std::string&&`，`sref = "abc"` 和 `sref = {}` 都会先隐式转换出一个临时 `std::string` 再去匹配这个被删的重载，**合法赋值也被一起毁掉**（实测这两种写法在 `= "abc"` / `= {}` 上直接报 ambiguous，因为被删的重载和"转换 + 拷贝赋值"两条路同时可行）。
    - 写成受约束的模板 + 转发引用：只有实参**本身就是 `std::string` 右值**（T 推导为 `std::string`）时才命中删除；`sref = "abc"` 会推导出 `T = const char (&)[4]`、`sref = {}` 根本无法推导，两者都从候选集里消失，于是回落到正常的拷贝/移动赋值——这就是源码注释说的"`stringRef = {}` 和 `stringRef = "abc"` 继续选中移动赋值"。加约束还有第二个作用：不约束的 `template<class T> operator=(T&&)` 对任何实参都是精确匹配，会把所有赋值都劫持走。
    - 具体推导：
        - `sref = std::string("x")`：T 推导为 `std::string`（右值 → `T&&` 是 `std::string&&`），条件成立 → 选中这个被 delete 的重载 → 编译报 "use of deleted function"，比让人写出悬垂代码好得多。
        - `std::string str = "x"; sref = str;`：T 推导为 `std::string&`，`is_same<std::string&, std::string>` 为**假** → 重载被摘掉 → 回落到拷贝赋值 + `StringRef(const std::string&)` 隐式转换，合法（左值活得比 sref 长是调用方责任）。
    - 同一片源码里还有两个配套设计：`StringRef(std::nullptr_t) = delete;` 禁止 `if (s == nullptr)` 这种糊里糊涂的比较；`StringRef(const char *Str LLVM_LIFETIME_BOUND)` 用 clang 的 lifetimebound 属性，让编译器对"把临时对象的内容交给 StringRef"发警告。
- Q: `find_if_not` 里为什么用 `[F]` 按值捕获？
```cpp
[[nodiscard]] size_t find_if_not(function_ref<bool(char)> F, size_t From = 0) const {
  return find_if([F](char c) { return !F(c); }, From);
}
```
- A: `F` 的类型是 `llvm::function_ref<bool(char)>`——**非拥有的函数视图**（内部就是一个对象指针 + 类型擦除的调用桩，拷贝只有两个指针级别，和 `std::function` 不同，它不做堆分配）。`[F]` 拷贝的是这个**视图对象本身**，不是被引用的那个函数对象，所以既便宜又语义不变。
    - 为什么不用 `[&F]`：`find_if` 是立即调用的，引用捕获其实也不会悬垂，但按值更稳——万一以后把 lambda 存起来或延后执行，引用捕获就成了生命周期炸弹；而且 `std::find_if` 的谓词参数本来就是按值传递，反正要拷一次。
    - 同文件的 `rfind_if_not` 用的是 `std::not_fn(F)`（C++17），`find_if_not` 用 lambda 是风格/历史差异，效果等价。
    - 追问"function_ref 和 std::function 的区别"：前者**引用**可调用对象（要求生命周期覆盖调用期、零分配），后者**拥有**它（可长期保存、可能堆分配）。LLVM 热路径一律用 `function_ref`。
- Q: `edit_distance` / `edit_distance_insensitive` 是干什么的？
- A: 就是**编辑距离（Levenshtein distance）**：把一个串变成另一个串所需的最少"插入/删除/替换"次数。
    - `Other`：另一个串；返回 0 表示完全相同。
    - `AllowReplacements = true`：一次字符替换算 1 步（经典 Levenshtein）；设成 `false` 时替换等价于"删一个 + 插一个"，算 2 步，也就是只允许插入/删除时的距离（等于 `|a| + |b| - 2*LCS`）。
    - `MaxEditDistance`：非 0 时是"上限"，一旦判断距离会超过它就提前返回 `MaxEditDistance + 1`。用于"是不是在 N 步之内"的快速判断——典型场景是报错时的 "did you mean 'xxx'?"（拼写相近的命令/选项提示）。
    - `_insensitive` 版本在比较前把每个字符过一遍 `toLower`（ASCII 意义），所以大小写不同不算差异；实现上就是同一套算法换了个 Map 函子。
    - 实现：`ComputeEditDistance` → `ComputeMappedEditDistance`，经典 DP，只保留**一行 + 一个左上角变量**，空间从 O(m*n) 降到 O(n)；上限剪枝有两处——① 长度差 > 上限直接返回；② 每算完一行，若该行最小值 > 上限就提前返回。
    - `LLVM_ABI`：跨动态库边界的导出/导入标记（Windows 上是 `__declspec(dllexport/dllimport)`），因为实现放在 `libLLVMSupport` 里、头文件只有声明；`[[nodiscard]]`：忽略返回值基本一定是 bug。
- Q: `consumeInteger` 里为什么要写 `static_cast<long long>(static_cast<T>(LLVal)) != LLVal` 这种套娃转换？
- A: 这是**值域检查（round-trip check）**。`consumeInteger<T>` 是模板，T 可能是 `short`/`int`/`char`，但内部统一先用最宽的 `long long`（或 `unsigned long long`）解析。解析出来的值可能超出 T 的范围（比如 `"70000"` 放进 `short`），直接赋值会截断回绕，用户拿到错的结果。
    - 做法：先把 `LLVal` 转成 T（可能截断），再转回 `long long` 和原值比；不相等 → T 装不下 → 返回 true 表示解析失败，`Result` 保持不动。
    - 无符号那条同理：`"-1"` 按无符号解析会变成巨大值，转进 `unsigned` 再转回来就对不上，直接判失败。
    - 为什么不跟 `numeric_limits<T>::max()` 比：一个 round-trip 就同时覆盖了有符号/无符号、各种宽度、以及"负数解析进无符号"的组合，代码短且不会漏分支。C++20 的 `std::in_range<T>(v)` 是标准写法，LLVM 要兼容老编译器才手写。
    - `if constexpr (std::numeric_limits<T>::is_signed)` 是编译期分支，避免给无符号类型实例化有符号那条路径。
- Q: `nonEmptyOr` 有什么用？它的 assert 为什么看着奇怪？
```cpp
[[nodiscard]] constexpr StringRef nonEmptyOr(llvm::StringRef Str) const {
  assert(!Str.empty() && "nonEmptyOr should not have an empty default!");
  return empty() ? Str : *this;
}
```
- A: 语义很直白：`s.nonEmptyOr(default)`——`s` 非空就返回 `s`，否则返回 `default`。典型用法是给"可能为空的配置项"兜底：`getOpt().nonEmptyOr("default")`。
    - assert 之所以看着奇怪，是因为它检查的不是 `*this`，而是**参数**：如果你传进来的默认值本身是空的，这个函数就没有意义（空进空出），几乎一定是调用方写错了，所以在 debug 构建里直接炸掉。LLVM 里这种"参数前置条件断言"很常见（对比 `operator[]` 里的 `assert(Index < size() && "Invalid index!")`）。
    - 注意 `assert` 在 `NDEBUG`（release）构建里被整个编译掉，所以它只防开发期误用，不能当运行期校验；`&& "消息"` 只是给崩溃日志看的一段字符串（`&&` 配合非零常量恒真，不改变逻辑）。
    - 返回值是 `StringRef`（值），不是引用：有可能返回的是参数，视图类型本来就该按值传。
- Q: `assert` 和 `std::assert` 有什么区别？它到底怎么工作？
- A: **没有 `std::assert`**——`assert` 是**宏**，定义在 `<cassert>`/`<assert.h>` 里，位于全局作用域，所以写 `std::assert` 编译不过，也不能取它的地址（它不是函数）。
    - 展开形式（glibc）：未定义 `NDEBUG` 时，`assert(expr)` 展开成 `((expr) ? (void)0 : __assert_fail(#expr, __FILE__, __LINE__, __func__))`；`__assert_fail` 打印 `prog: file:line: func: Assertion 'expr' failed.` 然后 `abort()`（SIGABRT，可产生 core）。
    - 定义 `NDEBUG`（编译时加 `-DNDEBUG`，Release 常用）后，宏展开成 `((void)0)`，**expr 根本不会被求值**——所以断言里绝不能写副作用，`assert(++i < n)` 在 release 里 i 不会自增。
    - 三个容易混的东西：`static_assert(cond, "msg")` 是**编译期**检查；`assert` 是运行期、debug 专用、失败即 abort；`llvm_unreachable("msg")` 是"声明这里不可能到达"（debug 等同 assert(false)，release 变成 `__builtin_unreachable()`）。
    - LLVM 的"assertions 构建"就是 `LLVM_ENABLE_ASSERTIONS=ON`（不定义 `NDEBUG`）；发行版常常关掉，所以这些断言的运行期成本是 0。
- Q: `slice(Start, End)` 到底在算什么？和 `substr` 有什么区别？
```cpp
[[nodiscard]] StringRef slice(size_t Start, size_t End) const {
  Start = std::min(Start, size());
  End = std::clamp(End, Start, size());
  return StringRef(data() + Start, End - Start);
}
```
- A: `slice` 取的是**下标区间 `[Start, End)`**：先把 Start 夹到不超过 size，再把 End 夹到 `[Start, size]` 之间，最后返回"起点 + 长度 End-Start"的视图。因为做了夹取，它**永远不越界、永远不抛异常**：Start 超尾得空串，End 超尾截到尾部，End < Start 得空串。
    - `substr(Start, N = npos)` 取的是"起点 + **长度** N"，同样做夹取（`min(Start, size())`、`min(N, size() - Start)`）。
    - 所以两者只是接口约定不同（区间 vs 起点+长度）：`StringRef("hello").slice(1, 3)` → `"el"`；`.substr(1, 3)` → `"ell"`。都是 O(1) 视图，不拷贝。
    - 为什么非要用 `clamp(End, Start, size())` 而不是 `min(End, size())`：必须保证 `End >= Start`，否则 `End - Start` 在 `size_t` 上会下溢成天文数字，构造出越界视图；而 `std::clamp` 要求 `lo <= hi`，所以前面才要先 `min` 把 Start 压进 size 里——这个顺序不能换。
- Q: `StringLiteral::withInnerNUL` 的参数为什么写成 `const char (&Str)[N]` 这么怪？
```cpp
template <size_t N>
static constexpr StringLiteral withInnerNUL(const char (&Str)[N]) {
  return StringLiteral(Str, N - 1);
}
```
- A: 因为**只有数组引用能把长度 N 带进模板参数**——`N` 是 `constexpr` 的，长度在**编译期**就算好了（`N - 1`，去掉结尾的 `'\0'`）。这正是 `StringLiteral` 存在的意义：编译期长度已知，可以放进全局 `constexpr` 表而不产生任何运行期构造/`strlen`。换写成 `const char *` 就只剩运行期 `strlen`，这个类的价值就没了。
    - 那为什么还需要 `withInnerNUL` 这个额外入口：`StringLiteral` 的常规构造函数带 clang 的 `enable_if` 属性，断言 `__builtin_strlen(Str) == N - 1`，也就是**不允许字面量里有内嵌 `\0`**（有的话 strlen 会短于 N-1，编译期直接报 "invalid string literal"）。而 `"foo\0bar"` 的 `sizeof` 是 8（7 个字符 + 结尾 NUL），strlen 只有 3，过不了检查；`withInnerNUL` 绕开检查、直接调私有构造 `StringLiteral(Str, N - 1)`，把中间的 `\0` 也当成内容保留下来。
    - 一句话对照：普通构造 = "以 NUL 结尾的 C 字符串"，`withInnerNUL` = "长度已知、允许中间有 NUL 的字节串"。
- Q: 文件末尾那个 `xxh3_64bits(StringRef)` 重载和 `DenseMapInfo<StringRef, void>` 特化在干什么？
- A: 两件事。
    - `xxh3_64bits(StringRef)` 是个**转发的 inline 重载**：真正干活的 `xxh3_64bits(const void*, size_t)` 声明在 `llvm/Support/xxhash.h`；StringRef 版本放在 `StringRef.h` 里，是为了让 `xxhash.h` 不必依赖 ADT（底层代码可以只 include xxhash.h）。源码注释原话就是 "They live here so xxhash.h can stay free of ADT dependencies"。调用 `xxh3_64bits("abc")` 时字面量先隐式转成 StringRef 命中这个重载，内部用 `reinterpret_cast<const uint8_t*>` + `size()` 调两参数版本。
    - `template <> struct DenseMapInfo<StringRef, void>` 是给 `llvm::DenseMap` / `DenseSet` 用的**键类型描述**：告诉哈希表"StringRef 怎么算哈希（`getHashValue`）、怎么判等（`isEqual`）"。`getHashValue` 只有声明 + `LLVM_ABI`，实现放在 Support 库里（避免每个 TU 都编一遍、也方便换实现）；`isEqual` 直接 `LHS == RHS`（先比长度再 `memcmp`），inline 展开。这样就能写 `DenseMap<StringRef, int>`。
    - 使用注意：key 只是视图，**map 里的 StringRef 必须指向生命周期更长的字符串**（字符串池、`StringSaver`），否则就是前面说的悬垂。
    - 面试延伸：`DenseMap` 是 LLVM 自研的开放寻址哈希表（比 `std::unordered_map` 快、内存紧凑），用之前必须给键类型提供 `DenseMapInfo`——这也是"LLVM 为什么到处能看到 `DenseMapInfo<...>` 特化"的原因。
**七、`static constexpr size_t npos = ~size_t(0);` 里三个关键字分别什么作用**
答题要点：
- `static`：类作用域静态成员，所有对象共享一份，不占对象空间；C++17 起 `constexpr` 静态数据成员**隐含 inline**，类内定义即可，不需要再在类外写一遍定义；访问写 `StringRef::npos`。
- `constexpr`：编译期常量，有三种使用方法:
	- 修饰对象表示，这个对象是 1 个常量表达式表示这个对象的值能够在编译期得到
	- 如果修饰函数的话，那么表示这个函数的得到返回值的求解过程可以在编译期完成，如果不能在编译器得到的话，它会退化为运行机计算写了等于没写。不是强制的，如果使用 consteval 修饰无法在编译期求职的话会报错
	- 它还可以在 17 以后修饰 if 条件语句，在编译期判断条件分支走向，最终不会出现在编译后的代码里。判断失败的分支的代码块中如果不依赖模板参数会进行一些语法检查，如果他依赖模板参数的话，那么连语法检查都不会做。
- `~size_t(0)`：
	- size t 是标准规定的无符号整数。
	- 它的内存大小占用是根据 cpu和机器平台决定的。一般来说将它定为 sizeof(void*)的大小，32->4/64->8
	- 先将它初始化为零，然后取反的意思是得到对应机器上 1 个指针长度内存大小的数据类型的无符号最大值
追问：
- Q: `~size_t(0)` 就是"本平台的最大值"吗？
- A: 是。`size_t(0)` 是全 0，按位取反得到全 1，即该宽度下的 `SIZE_MAX`（2^N - 1）。写 `~size_t(0)` 而不是写死数字，正是为了让它在 32/64 位上都自动对——这是一次编译期计算，零运行开销。
- Q: `size_t` 是无符号的，到最大值再自增会怎样？
- A: 回绕到 0。无符号整型运算按 2^N 取模，`SIZE_MAX + 1 == 0` 是**定义良好**的行为（有符号溢出才是 UB）。实测 `std::size_t z = SIZE_MAX; z + 1` 打印出来就是 0。由此有两个经典坑：① `for (std::size_t i = n - 1; i >= 0; --i)` 在 `i` 减到 0 后再减就变成 `SIZE_MAX`，`i >= 0` 永远为真 → 死循环，要写成 `for (std::size_t i = n; i-- > 0;)`；② 空容器 `size() - 1` 得到 `SIZE_MAX`，当数组下标用就越界崩。所以 `find` 的结果只能用 `== npos` 判断，不能 `< 0`。
**八、反向迭代器（`reverse_iterator`）是怎么工作的**
答题要点：
- `std::reverse_iterator<It>` 是适配器，内部保存一个 base 迭代器，解引用时"先减一再取值"，所以 `*r == *(it - 1)`。
- 因此 `rbegin() = reverse_iterator(end())`、`rend() = reverse_iterator(begin())`；`r.begin().base() == end()`。
- 这个"错位"是设计使然：让 `[rbegin(), rend())` 和正向区间一一对应，`rbegin()` 指向最后一个元素，`rend()` 是"第一个元素之前"。
- 用途：`std::sort(v.rbegin(), v.rend())` 降序；`rfind`、`rsplit`、`rtrim` 这类从尾部处理的实现。
- 坑：只对双向迭代器有效；`rbegin()` 不能直接和 `begin()` 比，要先 `.base()`；空容器里 `rbegin() == rend()` 成立，但解引用依然非法。
代码：
```cpp
template <class It>
class ReverseIt {
    It cur_;
public:
    explicit ReverseIt(It it) : cur_(it) {}
    auto operator*() const { It tmp = cur_; return *--tmp; }   // 先减一再取
    ReverseIt& operator++() { --cur_; return *this; }
    bool operator!=(const ReverseIt& o) const { return cur_ != o.cur_; }
};
std::vector<int> v{1, 2, 3};
ReverseIt<std::vector<int>::iterator> r(v.end()), re(v.begin());   // 3 2 1
```
追问：
- Q: 反向迭代器的 `base()` 指向哪？
- A: 指向"当前元素的下一个位置"：`(*r)` 实际是 `*(r.base() - 1)`，`r.base()` 本身指向前方一个元素。
- Q: 为什么 `erase`/`insert` 不能用反向迭代器？
- A: 容器接口只接受正向迭代器（`const_iterator`/`iterator`），反向迭代器是适配器，要先用 `.base()` 换回去，注意此时位置要再调整一位。
- Q: `base` 迭代器到底是什么？有什么作用？
- A: 就是 `reverse_iterator` 内部保存的那个**正向底层迭代器**（`std::reverse_iterator<It>` 的成员 `current`），`base()` 把它取出来。两个用途：① 把反向位置换回正向位置，好交给只认正向迭代器的接口（`erase`/`insert`）；② 两个反向迭代器相减、比较时，实现上都是拿 `base()` 算距离。关键点是**它和 `*r` 错一位**：`*r == *(r.base() - 1)`，所以 `r.base()` 指向的是"当前元素的下一个"。
- Q: 怎么让自定义容器支持 `for (auto x : c)`？
- A: 只要求提供 `begin()`/`end()`（成员函数，或者能被 ADL 找到的非成员版本），返回一对**输入迭代器**。迭代器最少实现四件事：`operator*`（取值）、`operator++`（前置自增）、`operator!=`（C++17 的 range-for 展开成 `it != end`，C++20 改看 `==`），以及一组类型别名（`value_type`/`difference_type`/`pointer`/`reference`/`iterator_category`），否则 STL 算法用不了：
```cpp
class IntRange {
    int b_, e_;
public:
    struct iterator {
        int cur;
        using value_type        = int;
        using difference_type   = std::ptrdiff_t;
        using pointer           = const int*;
        using reference         = int;
        using iterator_category = std::forward_iterator_tag;
        int operator*() const { return cur; }
        iterator& operator++() { ++cur; return *this; }
        bool operator!=(const iterator& o) const { return cur != o.cur; }
    };
    IntRange(int b, int e) : b_(b), e_(e) {}
    iterator begin() const { return {b_}; }
    iterator end() const { return {e_}; }
};
// for (int v : IntRange{1, 4}) ...   → 1+2+3 = 6
```
- Q: 为什么范围 for 只要求 `!=`，不要求 `<`？
- A: 因为它只是语法糖：`for (auto it = begin(c); it != end(c); ++it)`。`<` 只有随机访问迭代器才保证，输入/单链表迭代器都没有，所以标准只用 `!=`——这也是"自定义容器只要能前后走一遍就能用范围 for"的原因。
**九、读代码：`compareMemory`、`bytes()`、`xxh3_64bits(StringRef)` 分别在干什么**
答题要点：
- `compareMemory(Lhs, Rhs, Length)`：带 0 长度短路的 `memcmp` 包装。长度 0 直接返回 0——既省一次调用，也避开"把可能为空的指针传给 `memcmp`"这个标准上不干净的点；它被 `compare()` 用来做前缀比较。逐字节比较，不能用于比较带有 padding 的结构体/未经字节序转换的网络数据/指针/非平凡类型
- `bytes()`：把字符串内容按**无符号字节**暴露成迭代器区间 `iterator_range<const unsigned char*>`。为什么必须转 `unsigned char`：`char` 的符号性依平台而定（x86 有符号、ARM 常无符号），哈希/加密/序列化要按无符号字节算，否则同一份内容在不同平台算出不同结果。
- `xxh3_64bits(StringRef)`：给 `StringRef` 算 XXH3 64 位哈希的适配层，内部 `reinterpret_cast<const uint8_t*>(data.data())` + `data.size()` 调底层实现。它正好体现 `StringRef` 的设计意图：**只传指针 + 长度，不假设 `\0` 结尾，不拷贝**。
- XXH3 是非加密哈希，速度比 MD5/SHA 快一到两个数量级，适合哈希表、去重、快速校验；不能用于密码学场景。
追问：
- Q: 为什么哈希函数签名用 `StringRef` 而不是 `const std::string&`？
- A: 调用方不用为了传参构造 `std::string`（否则每次哈希都分配一次），也能直接哈希字面量和子串。
- Q: 如果字符串里含 `\0`，`StringRef` 还能正确表示吗？
- A: 能。`StringRef` 带长度，`(ptr, len)` 构造可表示任意字节序列；但用 `const char*` 隐式构造时会按 `strlen` 截断，这点要小心。
- Q: `iterator_range` 是什么类型？`make_range` 又在干什么？
- A: 都是 LLVM 的轻量工具（`llvm/ADT/iterator_range.h`）。`iterator_range<It>` 只干一件事：**保存一对 `[begin, end)` 迭代器**，并提供 `begin()/end()/empty()/size()/front()/back()`，把"一段序列"变成可以直接 `for` 的对象；它不拥有元素、不拷贝，返回它等于返回"两个迭代器"但用起来像容器。`make_range(b, e)` 是工厂函数：靠实参推导模板参数，省掉 `iterator_range<const unsigned char *>(...)` 这种啰嗦写法。标准库里的对应物是 C++20 的 `std::ranges::subrange`（任意迭代器）和 `std::span`（连续内存）。
- Q: 为什么 `char` 能被 `unsigned` 修饰？
- A: `char` 在标准里属于整型（字符类型是整型的一种），所以可以用 `signed`/`unsigned` 修饰，于是存在 `char`、`signed char`、`unsigned char` **三个不同类型**：`char` 的符号性由实现决定（x86 上通常有符号、部分 ARM 无符号），`signed char`/`unsigned char` 是明确的。`unsigned char` 的语义就是"0~255 的字节"，做哈希、编码、位运算时不会被符号扩展；`<cstdint>` 里的 `std::uint8_t` 通常就是 `unsigned char` 的别名（`uint8_t` 不是独立类型）。
- Q: `::memcmp` 和 C 的 `memcmp` 有什么区别？
- A: 是**同一个函数**，`::` 只是限定它在全局命名空间。为什么要加：如果当前作用域里有同名函数（类的成员、某个命名空间里的函数），裸写 `memcmp` 会先找到那个；`::memcmp` 明确指向 C 库的全局版本，避免被成员函数或 ADL 遮蔽——LLVM 这个 helper 就是起这个保险作用。
    - 工作原理：按字节（`unsigned char` 语义）逐字节比较，遇到不同就返回差值（正/负/0，**不保证是 ±1**）；不要求对齐，libc 内部通常用 SIMD 优化。
    - `n == 0` 时返回 0，但标准上指针仍需有效，所以有 `if (Length == 0) return 0;` 这个短路。
    - 和 `strcmp` 的区别：不看 `\0`、按长度比较，能比较任意二进制数据。
- Q: `xxh3_64bits` 为什么要把字符串转成 `const uint8_t*`？
- A: 三个原因：① 哈希的输入语义是"一段字节"，`uint8_t*`（即 `unsigned char*`）明确表达无符号字节视图，不受 `char` 符号性影响；② 底层 xxHash 的接口本来就是"指针 + 长度"，`reinterpret_cast` 只换类型视图、不拷贝、不改位模式；③ 用 `char`/`unsigned char`/`std::byte` 访问任意对象的字节表示，是标准明确允许的**严格别名例外**，所以这个 cast 合法、不是 UB。
    - 顺带一个易混点：`data.size()` 是字符串长度（字节数），`sizeof(StringRef)` 是对象本身大小（指针 + 长度，通常 16 字节），两者没关系。
**十、GDB：工作原理、常用命令，以及一次覆盖全部命令的实验（你没学过 gdb，这节当手册读）**
**1. gdb 是怎么工作的（为什么给一个可执行文件就能定位到源码）**
四层，从下往上看：
- **内核层**：gdb 是普通进程，靠 `ptrace` 系统调用控制被调试进程——读写它的寄存器和内存、单步、接收它收到的信号。所以"调试"本质是"另一个进程在操纵你的进程"。这也解释了为什么 `gdb -p` 需要权限（ptrace 有 `yama/ptrace_scope` 限制），以及容器里为什么经常 attach 失败。
- **编译层**：`-g` 让编译器把调试信息写进 ELF 的 `.debug_info`、`.debug_line`、`.debug_str`、`.debug_abbrev` 这些节。**没有 `-g`，gdb 只能看地址和汇编，看不到文件名、行号、变量名和类型。**
- **符号层**：`.symtab`（普通符号表）只有函数名和地址；`.debug_info` 是一棵树——编译单元（CU）→ 子程序 → 形参/局部变量，每个变量带 `DW_AT_location`（在栈帧里的偏移，如 `DW_OP_fbreg: -288`）、`DW_AT_decl_line`、`DW_AT_type`；`DW_AT_comp_dir` 记录编译时的**工作目录**，`DW_AT_stmt_list` 指向该 CU 的行号表。
- **行号层**：`.debug_line` 是一张"机器指令地址区间 → (源文件, 行号, 列号)"的映射表（line number program）。gdb 停下时用 `rip` 查表就能算出"现在停在哪个文件第几行"；`list` 反过来用行号查地址。**这张表只记录物理行号，和注释、空行无关**——注释删不删都不影响行号，唯一影响行号的是源码文件本身的行布局。
**2. 为什么 `gdb -q ./gdb_demo` 就能找到 `GdbDemo.cpp`**
- `-g` 编译时，编译器把 **CU 的源文件名（相对路径，如 `GdbDemo.cpp`）+ `DW_AT_comp_dir`（编译时的工作目录，如 `/tmp`）** 写进调试信息，并保留行号表。
- gdb 启动时读 ELF：先加载符号，再解析 `.debug_info` 建 CU 列表；此时它已经知道"这个 CU 叫 GdbDemo.cpp，编译目录是 /tmp，行号表在 .debug_line 的偏移 X"。
- 需要显示源码时（`list`、断点停下、`bt` 打印行），gdb 按这个顺序找文件：① 调试信息里的绝对路径 → ② `comp_dir` + 相对路径 → ③ `directory` 命令加的搜索目录 + 相对路径 → ④ 当前工作目录 + 相对路径。**这就是为什么要"在同一个目录下调试"或提前 `directory /path/to/src`。**
- 文件真的找不到时 gdb 会报 `No such file or directory`，但不影响打断点、看变量、看栈——它只是显示不了源码而已；用 `set substitute-path 编译时前缀 现在的前缀` 可以把路径整体重映射（换机器、换目录调试时最常用）。
- 相关命令：`info sources`（所有 CU 的文件列表）、`info source`（当前 CU：语言、编译目录、行号表地址）、`info line main`（函数/行号 ↔ 地址的换算）、`list`、`directory`、`show directories`、`set substitute-path`。
**3. 为什么我笔记里的地址和你的几乎一样（虚拟地址也会变，但 gdb 默认关掉 ASLR）**
- gdb 默认 `set disable-randomization on`，即通过 `personality(ADDR_NO_RANDOMIZE)` 让被调试进程关闭地址随机化。于是同一个二进制、同样的命令行和（大体相同的）环境变量，**每次运行地址都一样**。
- PIE 可执行文件的基址固定在 `0x555555554000` 附近，所以 `main` 的地址总是 `0x555555555xxx`；`b main` 打印的 `0x1664` 之类是**文件内偏移**，同一份二进制永远相同。
- 栈地址（`0x7fffffffe278` 这种）受环境变量长度、argv 长度影响，我的和你的会差几百字节——这就是笔记载图与实测数字不完全一致的原因。
- 想要"每次都不一样"：`set disable-randomization off` 后再运行，栈地址每次变化；想知道映射关系：`info proc mappings`。
- **gdb 里显示的所有地址都是进程的虚拟地址**（用户态视角），和物理地址无关；`p &x` 拿到的是虚拟地址，`info proc mappings` 能看它落在哪个段、什么权限。
**3.5 行号对不上怎么办？要不要用"预处理后的文件"来调试？**
- 先纠正一个猜测：**注释不会影响行号**。`.debug_line` 记录的是"物理行号"，编译器按每个 token 在源文件里的实际位置写表；删注释、加空行都不会让行号"被重新计算"，除非文件本身的行布局变了。
- 你调试时看到的 `55 / 64 / 66 / 68`，和我笔记里的 `74 / 89 / 91 / 93`，原因是**两边根本不是同一份源码**：你用的是最早那版 demo（`int main` 在第 55 行），后来我把文件重写成了综合实验版（带全局变量、list/map、递归、线程、异常），行号全变了。**同一个文件 + 同一份 `-g`，行号一定一致**——这也是我把实验里所有断点改成"函数名"的原因。
- "先预处理成干净文件再调试"技术上可行，但实测是**负收益**：
```sh
g++ -E GdbDemo.cpp -o GdbDemo.ii         # 保留 # 1 "GdbDemo.cpp" 行标记
g++ -E -P GdbDemo.cpp -o GdbDemo.P.ii    # -P 去掉所有行标记
g++ -g -O0 -pthread -std=c++17 GdbDemo.ii -o gd_keep
g++ -g -O0 -pthread -std=c++17 GdbDemo.P.ii -o gd_nop
```
    - 保留行标记（第一种）：`info line main` 仍然报 **`Line 89 of "GdbDemo.cpp"`** —— 行号映射由 `# 1 "GdbDemo.cpp"` 这些标记决定，预处理不改变任何行号，问题原封不动，反而多了一份 45583 行的中间文件。
    - 加了 `-P`（第二种）：`info line main` 变成 **`Line 30904 of "GdbDemo.P.ii"`** —— 行号是 `.ii` 自己的行号，但那个文件 30931 行、头文件全展开，`list` 出来完全没法读，断点位置还得重新查。
- 真正稳的做法：① **按函数名下断点**（`b sumVector`、`b factorial`），彻底绕开行号；② 需要具体某行时先 `info line 函数名` 或 `list 函数名` 现场查；③ 在源码里加标记注释（`// [断点]`），用 `grep -n '\[断点\]' GdbDemo.cpp` 一次拿到全部行号，再 `b 文件名:行号`。
**4. 编译选项逐个解释（`g++ -g -O0 -pthread -std=c++17 GdbDemo.cpp -o gdb_demo`）**
- `-g`：生成调试信息（DEBUG 信息节）。`-g3` 连宏定义也带上（可以 `p 宏名`），体积更大。
- `-O0`：关优化。优化会内联、重排、复用寄存器，后果是"变量 `<optimized out>`、单步跳行、栈帧缺失"。调试一律 `-O0`；只在 `-O2` 才复现的问题用 `-Og`。
- `-pthread`：启用 POSIX 线程（定义 `_REENTRANT`、链接 pthread）。不加它，多线程程序可能看不到完整线程信息。
- `-std=c++17`：语言标准（结构化绑定、`if constexpr`、`std::clamp` 需要）。
- `-Wall -Wextra`：打开常用警告。
- `-o gdb_demo`：输出文件名（不写默认 `a.out`）。
**5. gdb 启动参数**
- `gdb ./prog`：只加载不运行。`-q`：不打印版权横幅。
- `gdb --args ./prog a b`：后面全部当成被调试程序的参数（等价于进去后 `set args a b`）。
- `gdb ./prog core.1234`：加载 core 做"事后验尸"。
- `gdb -p 1234`：附加到运行中的进程（需要 ptrace 权限）；`detach` 脱离。
- `gdb -batch -ex '命令' -ex '命令' ./prog`：批处理，跑完退出（写脚本/CI 用；本节的输出就是这种方式抓的）。
- `gdb -nx`：不读 `~/.gdbinit`；`gdb -x cmds.txt`：从文件读命令；`gdb --tui`：带源码窗口的界面（`Ctrl-x a` 切换）。
- 进去先 `set pagination off` 关分页，否则长输出会停在 `---Type <return> to continue---`。
**6. 断点与监视点**
- `b main`、`b 类名::方法`：函数名断点（**推荐**，换编辑器、加注释都不会失效）。
- `b GdbDemo.cpp:40`、`b 40`：文件:行号 / 当前文件行号（行号会随源码版本变，先 `info line 函数名` 确认再下）。
- `b *0x4005a0`：绝对地址（没有符号或要停在指令中间时）。
- `b 函数 if 条件`：条件断点（第 8 轮演示）。
- `tbreak ...`：一次性断点，命中即删。`rbreak 正则`：批量给匹配的函数下断。
- `condition 2 条件`：给已有断点加/换条件；`ignore 2 100`：跳过前 100 次命中。
- `watch s` / `rwatch s` / `awatch s`：**写 / 读 / 读写**监视，靠 CPU 调试寄存器实现（x86 一般 4 个），只对内存位置有效。
- `i b`（`info breakpoints`）的列：`Num` 编号、`Type`（breakpoint / watchpoint / 类型）、`Disp`（命中后处置：`keep` 保留、`del` 删除、`dis` 禁用）、`Enb`（`y` 启用 / `n` 禁用）、`Address`（软件断点是它插入 `int3` 的**代码地址**；监视点这一列通常为空，因为它监视的是表达式/变量，地址在运行期才解析）、`What`（位置或表达式），以及 `breakpoint already hit N times`。
- `disable N` / `enable N` / `delete N` / `delete`（全删）/ `clear 函数名`（按位置删）。
- 编号为什么对不上：**编号按"你是本次会话创建的第几个断点/监视点"递增**。我笔记里 `watch s` 是 2 号，是因为会话里只有 1 号断点；你前面已经有 1、2、3 号，所以它是 4 号——`i b` 里的编号和你输入的顺序有关，和命令本身无关。
- `Hardware watchpoint N`：表示这个监视点用的是 CPU 硬件调试寄存器（比软件模拟快、数量有限）。写 `hw watchpoint` 是 `Type` 列的缩写形式。
**7. 运行与单步**
- `r`（run）/ `r 参数` / `set args 参数`；`c`（continue）；`n`（next，跨过函数调用）；`s`（step，进入函数）；`ni` / `si`（按汇编指令单步）；`finish`（跑完当前函数）；`until 行号`；`advance 行号`。
- `finish` 之后返回值在寄存器里：x86-64 整数看 `p $rax`，浮点看 `p $xmm0`。
**8. 看变量：p、printf、display，以及"为什么一次只能看一个"**
- `p 表达式` **只接受一个表达式**，所以 `p v.size() v.empty()` 会报 `A syntax error in expression`。一次看多个值有三条路：
    - `printf "sv=%d sl=%d\n", sv, sl` —— gdb 自己的 `printf` 命令，支持多参数和格式串，最灵活。
    - `display 表达式` 逐个添加，之后**每次停下自动打印**（`undisplay N` 取消，`undisplay` 不带参数会问是否全删）。
    - `info locals` / `info args` 一次列出当前帧全部局部变量 / 形参。
- `p/x`、`p/d`、`p/c`、`p/s`、`p/t`、`p/a`、`p/f`：格式修饰；`ptype 名字` 看类型定义；`set var x = 42` 直接改值。
- `p` 还可以调用函数：`p v.size()`。**但内联函数不一定能调用**（见下面"为什么 capacity 不行、empty 行"）。
**9. 看内存：x/nfu**
- 三个字母：**n** 数量、**f** 格式（`x` 十六进制、`d` 十进制、`c` 字符、`s` 字符串、`i` 指令、`a` 地址、`t` 二进制）、**u** 单位（`b` 1 字节、`h` 2、`w` 4、`g` 8）。
- `x/6dw arr` 看 6 个 4 字节整数；`x/8xb buf` 逐字节；`x/s buf` 当字符串；`x/2gx &b` 看一个 `Node` 的两个 8 字节字段（能直接看到 4 字节 `value` + 4 字节填充）；`x/4i $pc` 反汇编接下来 4 条指令。
**10. 栈与线程**
- `bt`（`#0` 当前函数，往下是调用者）、`bt 3`、`bt full`（每层带局部变量）；`frame N` / `up` / `down` 切换栈帧；`info frame` 看当前帧细节；`info args` / `info locals` 是**当前帧**的。
- 切换帧的用途：`p head` 报 `No symbol "head" in current context`，往往是因为你现在停在 `sumList` 里，而 `head` 是 `main` 的局部变量——`frame 1`（或 `up`）切过去就能看。
- `info threads`、`thread N`、`thread apply all bt`（死锁排查第一条命令）、`set scheduler-locking on`（单步时锁住只让当前线程跑）。
**11. 为什么 `p v.capacity()` 报 "may be inlined"，`p v.empty()` 却正常？**
- 这不是 `-O0` 没关内联的问题：`-O0` 只保证**用户代码**不被优化，标准库头文件里的成员函数天生是"类内定义 = 隐式 inline"，编译器在 `-O0` 下也**不生成它们的独立代码副本**（只有被真正调用且没被内联时才可能生成）。我用 `nm -C gdb_demo | grep 'vector<int.*>::'` 查过，这个二进制里只有 `begin()`/`end()` 有独立符号（range-for 用到了），`size()`/`empty()`/`capacity()` 都没有。
- 那 `size()`/`empty()` 为什么还能算？因为 **gdb 自带 xmethods**：`/usr/share/gcc/python/libstdcxx/v6/xmethods.py` 给 `std::vector` 注册了 `empty`、`size`、`front`、`back`、`at`、`operator[]` 这些"用内存布局直接算"的替身，不用真的调用 inferior 里的函数；**这份列表里恰好没有 `capacity`**，所以它只能退回"真调用"，而"真调用"需要函数有代码地址，于是报 `Cannot evaluate function -- may be inlined`。
- 结论：能不能 `p` 调用，取决于 ① 有没有真正生成的函数体 ② 有没有 xmethod 或内联实例可用；`-O0` 不改变这个规则。同理，`p v.capacity()` 失败时改看字段：`p v._M_impl._M_end_of_storage - v._M_impl._M_start`。

(gdb) while $n != &l._M_impl._M_node

 >set $n = $n->_M_next

  实测输出（地址每次不同）：

node @ 0x5555555732f0  value=20
node @ 0x555555573310  value=30
```
  原理：libstdc++ 的 `std::list` 是**带哨兵的循环双向链表**，节点类型 `std::_List_node<int>` 的布局是 `_List_node_base{ _M_next, _M_prev }`（16 字节）+ `int` 值（偏移 16），`sizeof(std::_List_node<int>) == 24`。`$n + 1` 之所以能取到值，是因为 `$n` 是 `_List_node_base*`，`+1` 正好跨过 16 字节的基类部分。
  VS Code 里能"清晰显示每个元素的值和地址"，靠的是同一套东西：它底层用 **gdb/mi**（`-enable-pretty-printing`）驱动 gdb，元素列表来自 libstdc++ 的 **Python pretty printer**（`/usr/share/gcc/python/libstdcxx/v6/printers.py`），它遍历节点、按 `[i]` 打印元素；要看每个节点地址，同样得用上面的循环或自己写 printer。**VS Code 能看到的，命令行 gdb 一定能看到**，反之亦然。

(gdb) set args throw
(gdb) catch throw              # 在任何 throw 处停下（Catchpoint 1）
(gdb) run
(gdb) bt                       # #0 __cxa_throw → #1 divide → #2 main
(gdb) frame 1                  # 切到 divide
(gdb) p a                      # 1
(gdb) p b                      # 0（就是它导致的除零异常）
```
  注意：在 `#0`（libstdc++ 内部）直接 `p a` 会解析成别的符号、打出乱值——**先切帧再取值**。
- **第 11 轮：多线程。**
```text
(gdb) set args threads
(gdb) b threadWorker
(gdb) run                      # 命中后会自动切到新线程
(gdb) info threads             # 列出全部线程，* 表示当前
(gdb) thread apply all bt 4    # 所有线程各打 4 层栈
(gdb) thread 2                 # 切到 2 号线程
(gdb) bt
(gdb) set scheduler-locking on # 单步时不让别的线程插进来
```
- **第 12 轮：崩溃与 core。**
```text
(gdb) set args crash
(gdb) b crashNull
(gdb) run
(gdb) n                        # 执行 Node* bad = nullptr;
(gdb) n                        # 执行 bad->value = 42  → Program received signal SIGSEGV
(gdb) bt                       # #0 crashNull → #1 main
(gdb) p bad                    # (Node *) 0x0
(gdb) x/i $pc                  # => movl $0x2a,(%rax)：往 rax(=0) 指向的地址写 42
(gdb) info registers rip       # 出错指令地址
(gdb) generate-core-file /tmp/gdb_demo.core   # 就地保存 core
(gdb) quit
```
```sh
gdb -q ./gdb_demo /tmp/gdb_demo.core -ex bt -ex 'p bad'
```
  另外两种拿 core 的方式：`gcore <pid>`（对运行中的进程在线抓）、内核自动生成（`ulimit -c unlimited` + `/proc/sys/kernel/core_pattern`）。
- **第 13 轮（可选）：死锁。**
```text
(gdb) set args deadlock
(gdb) run                      # 卡住不动，按 Ctrl-C 中断
(gdb) info threads
(gdb) thread apply all bt      # 两个线程分别停在 lock_guard 上，互相等对方的锁
```
  `Ctrl-C` 中断是"gdb 主动发 SIGINT 给被调试进程"，比 `gdb -p` 附加更适合本地排查。
**13. 常见报错与处理**

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `No symbol "head" in current context` | 当前栈帧里没有这个变量（它是别的函数的局部变量） | `bt` 看栈，`frame N` / `up` 切到定义它的帧 |
| `No source file named X.cpp` + `Make breakpoint pending…?` | 文件名/路径不对，或该文件还没被加载 | 名字写全（可用 Tab 补全）；想先挂着就答 `y`，或 `set breakpoint pending on`（`i b` 里显示 `<PENDING>`） |
| `Cannot access memory at address 0x…` | 断点停在变量初始化之前，指针是垃圾值 | 往后走一步（`n`）再 `p`；或改用函数内靠后的行 |
| `Cannot evaluate function -- may be inlined` | 该函数没有独立代码副本，也没有 xmethod | 改看字段（`p v._M_impl.…`），或换 `-O0` 下确实生成代码的函数 |
| `No such file or directory`（list 时） | 源码不在调试信息记录的路径上 | `directory /path/src`、`set substitute-path 旧前缀 新前缀` |
| `Could not attach to process` | `yama/ptrace_scope` 限制 | `sudo sysctl -w kernel.yama.ptrace_scope=0`，或改成在 gdb 里 `run` 然后 `Ctrl-C` |
| `<optimized out>` | 编译带了优化 | 用 `-O0`/`-Og` 重编；线上只能读寄存器或反汇编 |
| 地址每次不同 | 关了 gdb 的 ASLR 抑制，或换了二进制/环境 | `show disable-randomization`；同二进制同环境地址才稳定 |
**14. 追问**
- Q: gdb 为什么必须要有 `-g`？
- A: `-g` 才写出 `.debug_info`（变量名、类型、作用域、栈偏移）和 `.debug_line`（地址→行号）这些节；没有它，`bt` 只有裸地址，`p` 只认寄存器，断点只能按地址下。
- Q: 断点是怎么实现的？
- A: 软件断点把目标指令首字节换成 `int3`（x86 是 `0xCC`），执行到那里触发 `SIGTRAP`，gdb 捕获后写回原字节、停在被断点的那条指令上；继续时再换回去。所以软件断点要求代码段可写。硬件断点用调试寄存器（`DR0-DR3`），不改进程内存，可用于只读段和内存监视（`watch` 就是它），数量有限（x86 4 个）。
- Q: 为什么程序崩溃前打的日志没出来？
- A: 标准输出默认带缓冲：接终端行缓冲，重定向到管道/文件全缓冲；进程被信号杀掉时缓冲区不刷。演示程序开头 `setvbuf(stdout, nullptr, _IONBF, 0)` 就是关掉它；也可 `fflush(stdout)` 或把日志写 `stderr`。
- Q: 面试问"gdb 怎么用"，怎么答得像用过？
- A: 三句命令 + 一个实例：`b`（函数/行号/条件）、`i b`、`p`/`info locals`，再加 `bt` 和 `frame` 切帧；实例讲"协程挂死时 `bt` + `thread apply all bt` 区分挂起与死锁，core 看崩溃栈"。
- Q: 为什么说 gdb 里看到的是虚拟地址？
- A: 用户态进程只能看到自己的虚拟地址空间；`ptrace` 让 gdb 读写的也是这块空间。真正的物理页映射由内核管理（`/proc/self/pagemap` 才能问到）。
**十一、Linux 环境下怎么导入环境变量**
答题要点：
- 临时（当前 shell 和它启动的子进程）：`export NAME=value`；只对一条命令生效：`NAME=value cmd`。
- 永久：登录 shell 读 `/etc/profile`、`~/.profile`/`~/.bash_profile`；交互式 bash 读 `~/.bashrc`；zsh 读 `~/.zshrc`；系统级 `/etc/environment`（由 PAM 读取，只认 `KEY=value`，不支持变量展开）。
- 查看：`echo $NAME`、`printenv NAME`、`env | grep NAME`。
- 追加而不是覆盖：`export PATH="$PATH:/opt/toolchain/bin"`（写反了会顶掉系统命令）。
- 立即生效：`source ~/.bashrc`（`source` 等价于 `.`）。
- 子进程继承：`fork/exec` 时复制环境表，父导出子能见、子改了父看不见。
代码：
```sh
export CC=gcc CXX=g++
export PATH="/opt/toolchain/bin:$PATH"
export LD_LIBRARY_PATH="/opt/toolchain/lib:$LD_LIBRARY_PATH"
export C_INCLUDE_PATH=/opt/toolchain/include
source ~/.bashrc
printenv | grep -E '^(CC|CXX|PATH|LD_LIBRARY_PATH)='
```
追问：
- Q: 交叉编译时环境变量怎么起作用？
- A: `PATH` 决定用哪套 `gcc/as/ld`，`CC/CXX` 决定构建系统调用谁，`sysroot`/`--sysroot` 决定找目标平台的头文件和库；CMake 里对应 `CMAKE_C_COMPILER`、`CMAKE_SYSROOT`。
- Q: `LD_LIBRARY_PATH` 和链接时找库的路径是一回事吗？
- A: 不是。链接时用 `-L`（或 `LIBRARY_PATH`）找 `.so`，运行时用 `LD_LIBRARY_PATH`、`rpath`、`ld.so.cache` 找已经链接的库。
- Q: 为什么 `sudo` 之后环境变量没了？
- A: sudo 默认 `env_reset` 清空环境，`sudo -E` 或 `env_keep` 可保留；systemd 服务同理不读 `~/.bashrc`，要用 `Environment=`/`EnvironmentFile=`。
- Q: `PATH` 到底是什么？为什么能往里"追加"？它是什么数据结构？
- A: `PATH` 就是一个**以冒号分隔的目录字符串**，不是特殊结构；`export PATH="$PATH:/opt/toolchain/bin"` 就是普通的字符串拼接，没有数组也没有树。
    - 执行命令时，shell / `execvp` 把命令名依次拼到 PATH 的每个目录后面找可执行文件，**找到第一个就用**，所以顺序＝优先级；空的元素表示当前目录。
    - 能装很多目录，是因为它只是一条可以很长的字符串；上限来自内核的 `ARG_MAX`（环境变量 + 命令行参数总大小，常见 2MB），PATH 过长会出问题。
    - 常见坑：`PATH=/opt/bin` 覆盖掉原值 → 所有系统命令都找不到（`ls` 都没了）；正确写法永远是 `PATH="/新路径:$PATH"`。
- Q: 那"很多个不同的环境变量"是怎么存的？是哈希表吗？
- A: 不是。进程启动时内核给它一个 `char *envp[]`——**以 `\0` 分隔、以 `NULL` 结尾的字符串数组**，每项形如 `NAME=value`；`getenv/setenv/putenv` 操作的就是进程自己的 `environ` 这份数组副本。shell 内部为了 `$VAR` 查找快可能用哈希表，但传给子进程时又摊平成数组。这也解释了三个现象：① 环境变量值里的空格/特殊字符要加引号；② 子进程改了不影响父进程（各持一份）；③ `sudo`/systemd 会"丢环境"（它们重新构造一份干净的环境）。
- Q: 登录式 shell 和交互式 shell 有什么区别？
- A: 两个**独立维度**，组合起来决定读哪个配置文件。
    - **登录 shell**：由 `login`/`ssh` 启动的第一个 shell（`argv[0]` 前面带 `-`，`echo $0` 能看到 `-bash`），读 `/etc/profile` + `~/.bash_profile`/`~/.bash_login`/`~/.profile`，退出时读 `~/.bash_logout`。
    - **交互式 shell**：分配了终端、有提示符等你敲命令的 shell（`$-` 里含 `i`），读 `~/.bashrc`；非交互式（`bash script.sh`）不读。
    - 组合表：SSH 登录 = 登录 + 交互（先 profile，profile 里通常会再 `source ~/.bashrc`）；桌面终端新开窗口 = 非登录 + 交互（只读 bashrc）；`bash script.sh` = 非登录 + 非交互（两个都不读，只看 `BASH_ENV`）。
    - 实践含义：把 `export` 写进 `.bashrc`，对脚本和 systemd 服务不生效；写进 `.profile`，对图形终端新窗口不生效；systemd 谁都不读，得用 `Environment=`。

- Q: 什么是 DSP 芯片？为什么芯片能"被 C 语言编程"？
- A: DSP（Digital Signal Processor，数字信号处理器）是为数字信号处理优化的处理器：典型特征是硬件**乘加单元（MAC）**一个周期完成 `a*b+c`、**地址生成单元**支持循环缓冲和位反转寻址（FFT 用）、**饱和/舍入运算**、以及 SIMD/VLIW 让一条指令算多路数据；常见于音频/视频编解码、通信基带、工业控制、电机驱动。它和通用 CPU 的区别是"牺牲通用性换吞吐和确定性时延"。
    - "芯片能被 C 语言编程"准确说是**"指令集 + 工具链"让 C 代码变成它的机器码**：C 源文件 → 编译器前端（语法语义、IR）→ 后端（针对该 ISA 选指令、分配寄存器、调度）→ 汇编 → 汇编器 → 目标文件 → 链接器 → 可执行文件；运行时还要 libc 提供启动代码（`crt0`）、`memcpy`、`printf` 这些。**少任何一环，这颗芯片就只能用汇编甚至机器码写，C 代码根本落不了地**——这就是这家公司在做的事。
    - 现实约束：DSP 常常内存小、没有 MMU、没有操作系统（裸机或 RTOS），特殊指令（SIMD、饱和、循环寻址）C 编译器支持有限，有时要写 intrinsic 或内联汇编；不同 DSP 的 ABI（寄存器约定、栈对齐、数据类型宽度）不一样，所以 libc 必须逐个平台移植。
- Q: 什么是 ISA？为什么"ucontext 那套保存/恢复寄存器"能"在这上面做一遍"？
- A: ISA（Instruction Set Architecture，指令集架构）是**软件和硬件之间的契约**：指令的编码格式、寄存器集合与位宽、数据类型与寻址方式、内存模型（对齐、可见性）、异常/中断/特权级，以及通常配套的 ABI（调用约定）。同一份汇编只要 ISA 一致，换实现（不同微架构）也能跑。
    - `ucontext`（`getcontext`/`makecontext`/`swapcontext`）的本质是**保存和恢复 CPU 状态**：通用寄存器、栈指针、程序计数器、浮点/向量寄存器、信号掩码。这些状态正是一份 ISA 定义的东西，所以"保存现场 → 换栈 → 恢复现场"这个抽象动作在任何有寄存器、有栈的 ISA 上都成立。
    - 换到自研 DSP 上要重写的只是**具体动作**：哪些寄存器必须存（callee-saved + SP + PC）、栈往哪个方向长、对齐要求、保存指令怎么编码——这些由该 ISA/ABI 决定。libc 里的 `setjmp/longjmp` 就是这个道理，必须用目标平台的汇编写一份。
- Q: JD 里的 `asm/disasm/linker` 维护，具体是干什么活？
- A: 三个独立的程序，都是工具链的组成部分：
    - **asm（汇编器）**：把汇编文本翻成目标文件。日常维护 = 支持新指令的编码、伪指令与宏、表达式与重定位类型、放宽/收窄跳转（relaxation）、修 bug、提升大文件的汇编速度；配套要有测试（每条指令的编码/解码用例）。
    - **disasm（反汇编器）**：机器码 → 汇编文本。用途是调试、分析优化结果、crash 现场还原、以及**验证汇编器**（往返测试：汇编→反汇编→再汇编应得同样字节）。难点是变长指令的边界判断、代码与数据混排、伪指令与标签恢复。
    - **linker（链接器）**：符号解析 + 重定位 + 段布局。维护 = 支持新的重定位类型和段、linker script（内存区域、段地址、`AT>` 加载地址）、库的按需拉取顺序、错误诊断、增量/快速链接、和大工程的链接性能。
    - 共同特点：**"维护"占大头**——加一条新指令、修一个重定位 bug、跑一遍回归测试，都是日常工作；这和"从零写一个编译器"是两种活法。
- Q: 为什么必须有指令模拟器？
- A: 芯片流片（tape-out）之前没有硬件，但软件得先跑起来：工具链自测、libc 移植验证、算法/驱动开发、客户 demo 全靠模拟器；流片后它还能当"参考模型"用来对比真机行为、定位硬件 bug。DSP 常有特殊寻址和累加器行为，模拟器是唯一能逐条指令、逐周期对照规格书的地方。

- 别踩：不说"贵司做什么我都愿意"（显得没主见），也不要评价公司规模、融资、前景（信息不足容易说错）。

**三、大学期间哪个项目最有成就感？难点是什么？怎么解决的？**
答题要点：
- 用协程网络框架：从零搭到能跑（日志、配置、线程池、协程调度、epoll、HTTP/WebSocket），最难的是一次"协程挂死"——某条连接永远等不到事件，把同线程也拖住。
- 解决过程（按顺序说）：抓包排除网络 → 断点看协程状态停在 WAIT → 查 fd 有没有注册进 epoll → 定位到注册失败/事件丢失时协程仍在等 → 修：入口强校验（没注册就不走协程化）、所有等待加超时兜底、加状态监控。
- 收获一句话：让出 CPU 必须配一个"一定会到来的唤醒"（事件或超时），否则就是永久挂起。
- 备用故事（如果面试官追问业务类项目）：xTubeNest 的偏置补偿，闭合轮廓在尖角处自交，最后用尖角连接 + 圆角回退重建轨迹解决。
- 别踩：别说"跟着教程做的"；别只罗列技术栈不说问题。
