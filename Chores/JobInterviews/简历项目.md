# 简历项目（校招面试准备）

> [!note] 本文件定位
> 面向校招后端 / Qt / AI 方向。以「面试能答上」为导向：简历是包装过的，**回答比代码实现细节重要**。
> 所有回答遵循三原则：**先讲概念（解决什么问题）→ 再讲实现 → 再讲取舍/对比**。数字只说定性量级，不编造具体 QPS/并发数。

## 统一兜底框架

> [!warning] 这是全场最重要的策略。面试官深挖你没写/不熟的点时，按下面四步走，能保证高信息密度、简短、还显得你懂行。

### 核心策略（四步）
1. **先定生态位（分层认知）**——一句话说清「这个问题属于系统哪一层 / 解决什么问题」。这立刻展示你理解全貌，即使细节不熟也不露怯。
2. **落到通用原理**——把具体问题映射到你确定掌握的通用原理（顺序写 vs 随机写、一致性与可用性权衡、缓存三问题、WAL、幂等 + 至少一次、多数派共识等）。
3. **诚实边界 + 给技术方向**——明确「我在项目里做到哪层，其余是通用方案」，**不编造具体数字或细节**，但补一个你熟悉的切入点和合理技术方向。
4. **反拉回主场**——把话题接回你确定能展开证明的点（「这一点在 XX 里我是这样处理的……」）。

### 统一措辞模板（可背）
> **「这个问题本质上是在问（分类 / 想验证什么）。在（我的项目）里我主要保证的是（你能证明的点）；具体到（被问的细节），业界通用做法是（通用方案），我理解它的核心是（一句话原理）。落到实现上，我会从（你熟悉的切入点）入手。」**

完全不会时的兜底句：
> **「这块我在项目里只做了（程度），没有深挖到（细节），但我理解它要解决的是（原理）。如果要我实现，我的思路是（一个合理的技术方向）。」**

### 实例对照（背 3 个就够）
**例 A：被问 ZooKeeper 的 ZAB 协议**（简历只写了 ZooKeeper 集成）
> ZooKeeper 在项目里我主要用作**服务注册发现的协调者**（生态位）。ZAB 是它保证一致性的核心协议——leader 选举 + 半数以上确认的广播提交，和 Raft 的多数派思想一致，核心是**保证写操作全局有序**（通用原理）。我了解单 leader 写、多 follower 复制、崩溃重选主的基本流程，但没到能默写协议细节的程度（诚实边界）。深入的话我会从「多数派 + 日志复制 + 选举」这套共识框架入手（技术方向）。

**例 B：被问冷历史消息的对象存储怎么保证一致**（IM 简历一行带过）
> 这是分布式系统里「**日志是真相、索引是投影**」的经典问题（生态位 + 原理）。我的做法是固定写入顺序：先追加到日志并等确认，再提交索引；若中途崩溃，结果是「有日志、无索引」，不丢消息，可从日志重放重建索引（通用方案）。热→冷过渡要等冷日志确认 + 客户端游标 ack 才允许缓存过期（诚实边界 + 落点）。这正是 WAL / Kafka 的思路。

**例 C：被问分布式事务 / 两阶段提交**
> 我在项目里主要用的是**消息队列的事务消息 + 回查**来保证「单据入库」和「事件发送」的一致（能做证明的点）。更严格的跨服务分布式事务有 2PC / 3PC / TCC / 本地消息表这些方案（通用方案）。我理解它们的本质是在**一致性和可用性之间做权衡**：2PC 强一致但阻塞、协调者是单点；TCC 是把事务拆成 Try/Confirm/Cancel 由业务补偿（通用原理）。如果让我选，小流量强一致场景用 2PC，大流量高可用场景用本地消息表 + 幂等消费（技术方向）。

## 逐字逐项追问

> [!note] 每问格式：**Q → A（最佳回答）→ 追问×3（各带答）**。已有问答按项目保留，并补充了细节追问。回答已压缩为高信息密度口径。

### 专业能力·编程基础

**Q：你熟悉 C++11 到 C++20，具体用了哪些特性？**
A：核心几类：
1. RAII 与智能指针（`unique_ptr`/`shared_ptr`/`weak_ptr`）管资源，杜绝泄漏
2. 移动语义与右值引用，避免大对象拷贝
3. `constexpr` 与模板元编程，把计算提前到编译期
4. C++17 结构化绑定、`if constexpr`、折叠表达式
5. C++20 Concepts 约束模板参数、`std::variant` 承载多类型。项目里全程无裸指针。

**追问1：shared_ptr 和 unique_ptr 的区别，weak_ptr 解决什么问题？**
A：`unique_ptr` 独占所有权、零开销、不可拷贝只能移动；`shared_ptr` 用引用计数共享所有权，最后一个引用销毁时释放。`weak_ptr` 不增加引用计数，用来**打破循环引用**——两个对象互相持 shared_ptr 会形成环导致永远不释放，用 weak_ptr 观察但不持有，避免内存泄漏；用前需 `lock()` 提升为 shared_ptr 再访问，防止悬空。

**追问2：移动语义是什么，什么时候触发移动而不是拷贝？**
A：拷贝是深复制数据，移动是把资源（堆指针）的所有权"偷"过来，原对象置空，避免深拷贝开销。触发移动的关键是**右值**——函数返回局部对象（NRVO 之外）、`std::move` 显式转换、临时对象作为实参等。所以大对象传参用 `const&` 避免拷贝，需要转移所有权时用右值引用 + 移动构造。

**追问3：模板元编程和 constexpr 的区别？**
A：模板元编程是在编译期用模板递归/特化做计算或类型推导（如 Traits、`if constexpr` 分派）；`constexpr` 让普通函数在编译期求值。两者都"把工作挪到编译期"，但模板元编程更偏**类型层面**，`constexpr` 更偏**值计算**。C++20 里两者常结合，比如用 `constexpr` + Concepts 在编译期校验。

**Q：模板元编程是做什么的，concept 怎么用？**
A：模板元编程是在**编译期**利用模板实例化做类型计算与代码生成，典型如 `std::is_base_of`、`enable_if`、递归模板展开参数包。concept 是 C++20 对模板参数施加语义约束的机制，比如 `requires std::is_base_of_v<BaseDo, T>` 约束 T 必须继承某个基类，传错类型直接编译报错，比传统的 SFINAE 更清晰。

**追问1：`if constexpr` 和普通 if 的区别？**
A：普通 if 在运行期判断，两个分支都要能编译；`if constexpr` 在编译期判断，**不满足条件的分支直接不实例化**，可用于在编译期对不同类型分派不同实现（模板特化的一种替代）。

**追问2：折叠表达式（fold expression）做什么？**
A：C++17 用 `(... op pack)` 对参数包做折叠运算，把**变长的模板参数包压缩成一次表达式**，比如拼参数、求和、`&&` 串联所有参数的约束判断，避免递归展开。

**追问3：为什么说 concept 比 enable_if 好？**
A：enable_if 用 SFINAE 技巧，报错信息晦涩、写法繁琐；concept 语义直接（`requires` 一读就懂）、报错信息友好、能对模板做更细的约束与重载选择，是 C++20 的首选。

**Q：跳表是什么，为什么用、怎么实现？**
A：跳表是基于**有序链表 + 多层索引**的查找结构：底层全量有序链表，上层每若干节点抽一个做索引，查找时从顶层逐层向下，达到 O(log n) 的查找复杂度。实现要点：每个节点有随机高度的指针数组、插入时随机决定层高、查找时自上而下逼近。对比红黑树，跳表**实现简单、天然支持区间/范围查询（ZSET 的 score range）、无旋转操作**，Redis 的 ZSET 底层就用它。

**追问1：跳表和红黑树怎么选？**
A：都 O(log n)。红黑树是平衡二叉，内存紧凑、支持 O(1) 前驱后继；跳表**写起来简单、易于并发改造、支持按 score 范围遍历**。Redis 选跳表是因为 ZSET 要频繁做范围查询（ZRANGEBYSCORE），且跳表比平衡树更易实现和调试。

**追问2：跳表的层高怎么定？**
A：每个节点插入时随机决定高度，通常按几何分布（如 1/2 概率升层），期望层高 O(log n)。随机性保证整体平衡，无需像红黑树那样旋转调整。

**追问3：跳表查找过程？**
A：从最高层头节点开始，比较当前节点下一个节点的值：小于目标则向右移，大于则向下一层，重复直到最底层找到或确认不存在。每层前进、必要时下降，路径长度期望 O(log n)。

**Q：哈希表冲突怎么解决，负载因子是什么？**
A：常见两种：
1. **链地址法**（拉链），冲突元素挂成链表，jdk8 后树化
2. **开放寻址**（线性/二次探测），冲突往后找空位。负载因子 = 元素数 / 桶数，超过阈值（如 0.75）就扩容，保证平均查找接近 O(1)。C++ `unordered_map` 用拉链 + 桶数组，`std::hash` 计算桶下标。

**追问1：哈希表为什么扩容要 rehash？**
A：桶数变了，`hash(key) % size` 的下标全变，必须重新把所有元素放进新桶数组（rehash）。所以扩容是 O(n) 的一次性开销，通常按 2 倍扩容摊薄。

**追问2：为什么负载因子太高性能会退化？**
A：桶内链表/探测链变长，最坏退化为 O(n)。所以到阈值就扩容，维持摊还 O(1)。

**追问3：C++ 的 unordered_map 和 map 区别？**
A：`unordered_map` 是哈希表，无序、平均 O(1)；`map` 是红黑树，有序、O(log n)。需要有序遍历或范围操作用 map，否则用 unordered_map 更快。

**Q：TCP 三次握手、四次挥手？**
A：三次握手：SYN → SYN+ACK → ACK，双方确认收发能力，**同步初始序列号**，防止历史连接干扰。四次挥手：FIN → ACK → FIN → ACK，因为 TCP 全双工，双方各自独立关闭自己的发送方向，所以比握手多一次。为什么握手要三次：两次无法确认对方收到了自己的 SYN-ACK，无法可靠同步序列号；四次挥手需要两对 FIN/ACK 分别关闭两个方向。

**追问1：为什么握手 3 次而不是 2 次？**
A：2 次只能建立单工或无法确认「接收方也愿意收」，且无法处理**延迟的旧 SYN**——第 2 次握手无法区分「新连接」还是「旧 SYN 的重传」，可能建立错误连接。3 次靠确认号验证双方都正确同步了序列号。

**追问2：TIME_WAIT 是什么，为什么要有？**
A：主动关闭方收到对方 FIN 后进入 TIME_WAIT，等待 2MSL。作用：
1. 保证最后的 ACK 能到达（丢失则对方重发 FIN）
2. 让旧连接的报文在网络中自然消失，避免污染新连接。代价是端口/连接被占用 2MSL。

**追问3：大量 TIME_WAIT 怎么办？**
A：优化角度：
1. 提高可用端口/开启端口复用（`SO_REUSEADDR`）
2. 保证服务端是主动关闭方而非被动
3. 若短连接高并发，考虑连接复用/长连接。但 TIME_WAIT 是协议正确性需要，不能随便关闭。

**Q：滑动窗口和拥塞控制是做什么的？**
A：都是 TCP 流量/拥塞控制。滑动窗口解决**可靠传输与流量控制**——接收方通告窗口大小，发送方窗口内可连续发送、按 ACK 滑动，实现流水线提高吞吐；拥塞控制（慢启动、拥塞避免、快重传快恢复）解决**网络拥塞**——用 cwnd 探测网络容量，指数/线性增长，丢包时收缩。

**追问1：粘包/拆包怎么处理？**
A：TCP 是字节流，没有消息边界，需要应用层定界。常见方案：固定长度、**长度字段前缀**（本项目 2 字节长度 + JSON 载荷即这种）、分隔符。接收端维护缓冲，按长度字段循环解析出完整帧，半包留在缓冲等下一次。

**追问2：为什么不能靠 recv 返回次数判断一条消息？**
A：一次 recv 可能收到半条、一条、或多条。必须用**协议定的边界**（长度/分隔符）来切帧，而不是 recv 次数。这正是自定义帧协议存在的意义。

**追问3：粘包和拆包是 TCP 的问题吗？**
A：不是 TCP 的错，是**字节流没有消息边界**的必然结果，任何基于字节流的协议都需应用层解决。UDP 保消息边界但可能丢包乱序。

**Q：数据结构/算法你熟悉到什么程度，竞赛给你什么？**
A：熟悉链表、栈、队列、哈希表、跳表、堆、树、图及排序查找、DFS/BFS、贪心、DP、二分等。竞赛（ICPC 铜、CSP 前 2.56%）让我代码功底和**对复杂度的敏感度**扎实，能写清楚边界情况、快速实现正确的高效算法。

**追问1：排序算法对比，快排为什么快？**
A：快排平均 O(n log n)，利用分治 + 原地 partition，缓存友好、常数小，实际最快；归并稳定、O(n) 空间、适合外部/链表；堆排最坏 O(n log n) 但常数大、不稳定。快排最坏退化为 O(n²)（有序时），需随机化/三数取中避免。

**追问2：什么时候用 BFS 什么时候用 DFS？**
A：求**最短路径/层数**用 BFS（按层扩展，第一次到达即最短）；**遍历所有路径/连通分量、回溯**用 DFS。BFS 用队列、空间 O(层宽)；DFS 用栈/递归、空间 O(深度)。

**追问3：二分查找要注意什么？**
A：区间边界（左闭右开 vs 闭）、**终止条件避免死循环**、mid 防溢出用 `l + (r-l)/2`、查找上下界的区分。是高频且易错点。

### 专业能力·并发与架构

**Q：线程和进程的区别？为什么用多线程？**
A：进程是资源分配单位（独立地址空间、文件、信号），线程是**调度单位**（共享进程地址空间、栈和寄存器独立）。线程创建/切换开销远小于进程，且天然共享数据；多线程能利用多核、提高并发吞吐。代价是要处理同步与数据竞争。

**追问1：线程切换的开销在哪？**
A：上下文切换要保存/恢复寄存器、栈指针、程序计数器，还有**缓存/页表/TLB 失效**，陷入内核态。所以线程切换是微秒级，比用户态协程切换（纳秒级）贵一个数量级。

**追问2：什么时候用多进程而不是多线程？**
A：需要**强隔离**（一个崩了不影响其他）、安全关键场景、或利用多核但不想共享数据时用多进程；代价是 IPC 成本高。微服务本身就是进程级隔离的体现。

**追问3：线程池解决了什么问题？**
A：避免频繁创建/销毁线程的开销，复用空闲线程；用固定线程数限制系统负载，任务进入队列由池内线程消费。本项目协程框架的 N 线程池、连接池都是同一思想（池化复用）。

**Q：常用的锁有哪些，死锁怎么避免？**
A：同步原语：`mutex`（互斥锁）、`shared_mutex`（读写锁，读读共享）、`recursive_mutex`（可重入）、条件变量（配合锁做等待/唤醒）、信号量、自旋锁。死锁四条件：互斥、持有并等待、不可剥夺、循环等待。避免：**按固定顺序加锁、加锁超时、用 `std::lock` 一次性拿多把锁、避免嵌套锁、缩小临界区**。

**追问1：互斥锁和自旋锁区别？**
A：互斥锁拿不到就**让出 CPU 阻塞**，适合临界区长、竞争激烈的场景；自旋锁拿不到就**忙等**（循环检查），适合临界区极短（如改一个原子变量）的场景，避免线程切换开销，但会空耗 CPU。

**追问2：读写锁为什么快？**
A：读操作可**并发共享**，只有写需要独占。读多写少场景下，读写锁让多个读者并行，吞吐高于全互斥。代价是写者可能饥饿（需公平策略）。

**追问3：条件变量怎么用，配合锁是什么模式？**
A：`wait(lock, pred)` 在谓词不满足时**释放锁并阻塞**，被 `notify_one/all` 唤醒后重新加锁并检查谓词。必须配合 mutex 用，防止**丢失唤醒**（检查谓词和 wait 之间需原子）。标准模式是生产者/消费者。

**Q：CAS 是什么，怎么实现无锁？**
A：CAS（Compare-And-Swap）是一条原子指令：`if (*addr == expected) *addr = newval;`，比较并交换是原子的。用 CAS 循环（自旋）实现无锁更新：读取旧值 → 计算新值 → CAS，失败则重读重试（乐观并发）。C++ 里是 `std::atomic::compare_exchange_weak/strong`。

**追问1：CAS 的 ABA 问题是什么，怎么解决？**
A：读取旧值 A 后，其他线程把它改成 B 又改回 A，CAS 误以为没变。解决：加**版本号/戳**（比较 (地址,版本)），或 C++ 用带标记的指针。这是无锁编程经典陷阱。

**追问2：CAS 什么时候失败、性能如何？**
A：高竞争下 CAS 频繁失败重试，可能退化（活锁）。所以无锁适合**竞争不激烈**的场景；激烈时用锁或让重试有退避。本项目无锁队列用于单生产/消费者消息队列，竞争可控。

**追问3：`std::atomic` 和 `volatile` 区别？**
A：`volatile` 只是告诉编译器别优化掉访问，**不保证原子性和内存序**；`std::atomic` 才保证原子操作 + 内存序（memory_order），线程安全必须用 atomic。

**Q：内存池是什么，为什么用？**
A：频繁 `new/delete`（malloc/free）有系统调用和内存碎片开销，且慢。内存池**预分配一大块，内部切分复用**，分配/释放是 O(1) 的指针移动，显著降低开销和碎片。本项目对象池/内存池复用高频资源。

**追问1：内存碎片是什么，怎么产生？**
A：小块分配释放交错产生**外部碎片**（不连续空闲块无法满足大请求）和内部碎片（对齐浪费）。内存池固定块大小可缓解。

**追问2：为什么说内存池分配快？**
A：预分配后，分配就是从空闲链表取一块、释放就是放回链表，都 O(1)，不触发系统调用；而 malloc 通常要查空闲链表、可能扩展堆、加锁。

**追问3：对象池和内存池区别？**
A：对象池缓存**构造好的对象**避免反复构造/析构（如数据库连接、协程对象）；内存池只管原始内存块。对象池 = 内存复用 + 构造/析构复用。

**Q：异步日志怎么做到不阻塞主流程？**
A：双缓冲（Double Buffer）+ 后台写线程。业务线程只把日志写入**内存缓冲**（快、无 I/O），缓冲满或定时则**交换缓冲区**交给后台线程落盘，业务线程继续写另一块。这样主线程几乎不被磁盘 I/O 阻塞，日志写盘是异步的。

**追问1：为什么要双缓冲而不是直接一个缓冲？**
A：单缓冲要等写盘才能复用，会阻塞业务线程。双缓冲让业务线程写 A、后台线程写 B，满了**原子交换**，两边互不等待，接近零阻塞。

**追问2：日志会丢吗，怎么权衡？**
A：异步日志可能丢最近未落盘的数据（崩溃时内存缓冲丢失）。权衡：追求性能用异步+定期刷盘，追求不丢则同步/每条 fsync。一般用「定期 + 量触发」刷盘折中。

**追问3：日志级别怎么设计？**
A：TRACE/DEBUG/INFO/WARN/ERROR/FATAL，运行时按级别过滤，避免低级别日志刷屏拖垮性能；不同级别可路由到不同 appender/文件。

**Q：你怎么做性能分析（profiling）？**
A：先用**宏观定位**（压测、火焰图）找热点函数，再看是 CPU 密集（优化算法/数据结构）、I/O 密集（异步、批量、缓存）还是锁竞争（无锁/分区）。Linux 用 `perf`、火焰图，配合 gdb 定位。本项目优化过单接口 P95，靠测量而不是猜。

**追问1：发现瓶颈是锁竞争怎么办？**
A：
1. 缩小临界区
2. 读写锁/原子
3. **无锁数据结构**（本项目单线程消息队列即规避锁）
4. 分片/分区锁（把一把大锁拆成多把）
5. 最终多实例水平扩展摊薄。

**追问2：火焰图怎么看？**
A：火焰图横轴是 CPU 占比、纵轴是调用栈，**越宽的函数占用越高**，是瓶颈热点；看宽条顶端即耗时函数，顺调用栈往下找根因。

**追问3：压测怎么做，关注哪些指标？**
A：工具（wrk/ab/JMeter）打 QPS、并发数；看**P95/P99 延迟、吞吐、错误率、CPU/内存**。压测要控制变量、逐步加压，找到拐点和瓶颈。

### 专业能力·工具使用

**Q：Redis 你用了哪些数据结构，分别解决什么问题？**
A：String（缓存/计数）、Hash（对象/字段）、List（消息队列/最新列表）、Set（去重/标签）、**ZSet（有序集合，IM 里用 score=消息游标做增量拉取）**。Redis 单线程 + 内存，读写在微秒级；IM 里还用它维护「用户→所在实例」映射做路由。

**追问1：为什么 Redis 单线程还快？**
A：纯内存 + 单线程**免锁竞争** + I/O 多路复用（epoll）+ 高效数据结构。单线程避免了上下文切换和锁，瓶颈在内存/网络而非 CPU。

**追问2：ZSet 底层是什么，为什么支持范围查询？**
A：底层**跳表 + 哈希表**：哈希做 O(1) 精确查找，跳表做按 score 排序和**范围查询**（ZRANGEBYSCORE）。IM 里用 score 存消息序号/时间，客户端「给我 score 大于游标的消息」即增量拉取。

**追问3：Redis 持久化 RDB 和 AOF 区别？**
A：RDB 是定期**全量快照**（快、文件小、恢复快，但可能丢两次快照间的数据）；AOF 是**追加写命令日志**（更持久、可每秒 fsync，但文件大）。生产常用 AOF + 定期 RDB 备份。

**Q：MySQL 索引为什么用 B+ 树？**
A：B+ 树非叶子只存**键**、叶子存数据且**叶子间有链表**，一个节点能装更多键（扇出大、树矮、IO 次数少），且叶子链表天然支持**范围查询**。相比 B 树叶子存数据、无链表；相比哈希不支持范围；相比红黑树树太高。

**追问1：聚簇索引和非聚簇索引区别？**
A：聚簇索引（InnoDB 主键）**叶子直接存整行数据**，表数据按主键顺序组织；非聚簇（二级索引）叶子存**主键值**，查非主键列要回表（回主键索引取整行）。

**追问2：回表是什么，怎么避免？**
A：用二级索引查到主键后，再回主键索引取整行 = 回表。避免：**覆盖索引**（索引已包含所需列，不用回表）、合理选索引列。

**追问3：最左前缀原则？**
A：复合索引 (a,b,c) 能命中 a、a,b、a,b,c 的查询，从**最左列开始连续**才生效；跳过中间列（如只查 a,c）会失效。建索引要按查询列的顺序设计。

**Q：SQL 注入怎么防？**（简历强调）
A：核心是**参数化查询**：SQL 里用 `?` 占位符，参数通过 PreparedStatement 绑定，**用户输入只进参数集、不进 SQL 文本**，从根上杜绝拼字符串导致的结构注入。本项目 ORM 层全程走参数绑定，杜绝注入。

**追问1：为什么参数化能防注入？**
A：参数值被数据库驱动**按数据类型处理**，不作为 SQL 语法解析，所以 `' OR 1=1` 只是普通字符串值，不会改变查询结构。

**追问2：除了注入，SQL 还有哪些安全隐患？**
A：权限过宽、敏感数据明文、日志泄露、慢查询（无索引导致拖垮库）。防护：最小权限、参数化、加密、审计。

**追问3：PreparedStatement 比 Statement 好在哪？**
A：**预编译一次、复用执行计划**，性能更好；参数占位符绑定天然防注入。代价是第一次编译开销，长循环里优势明显。

**Q：Git 你怎么用，冲突怎么处理？**
A：日常用 add/commit/push/pull，用分支隔离功能（feature 分支合并到 main），用 `rebase` 保持线性或 `merge` 保留合并记录。冲突产生于多人改同一处，解决：`git status` 定位冲突文件，手动合并两方改动，保留正确的最终结果，再 add + commit。

**追问1：merge 和 rebase 区别？**
A：merge 产生一个**合并提交**、保留两条分支历史；rebase 把当前分支的提交**重放到目标分支顶端**、历史线性干净。rebase 会改写历史，公共分支慎用。

**追问2：如何撤销一个 commit？**
A：`git reset`（回退本地，可分 soft/mixed/hard）或 `git revert`（新增反向提交，**适合已推送的公共分支**，不改历史）。`git reset --hard` 会丢改动，慎用。

**追问3：怎么避免提交垃圾/泄露？**
A：提交前 review diff、`.gitignore` 排除敏感文件、不用 `git add -A` 盲目提交、用 pre-commit 钩子检查密钥。

**Q：CMake 你用来做什么，Presets 是什么？**
A：CMake 是**跨平台构建系统**，管理源文件、依赖、编译选项，生成 Makefile/Ninja 等构建文件。CMake Presets 是 CMakePresets.json 里**预定义好的构建/配置组合**（不同平台、Debug/Release、依赖开关），一行命令切换构建配置，避免手敲一长串参数。项目里还用 vcpkg 做 C++ 依赖管理 + Ragel/protoc 代码生成自动化。

**追问1：vcpkg 是什么，和 CMake 什么关系？**
A：vcpkg 是 **C++ 跨平台依赖包管理器**，一键安装第三方库（如 yaml-cpp、OpenSSL）并暴露给 CMake；通过 toolchain file 让 CMake 找到并链接这些库。

**追问2：条件编译/模块开关怎么在 CMake 实现？**
A：用 `option(USE_XXX ON/OFF)` 定义开关，`target_sources`/`target_link_libraries` 按开关添加，配合代码里 `#ifdef` 裁剪，实现按需构建（本项目 ERP 的模块热插拔即此思路）。

**追问3：Debug 和 Release 区别？**
A：Release 开优化（-O2/-O3）、去调试符号、可能无断言；Debug 有符号、可断点、无优化。性能问题必须在 Release 下测。

**Q：Agent 工作的基本原理是什么？**（简历「理解 Agent 原理」）
A：Agent 是一个**能自主完成多步任务**的 AI 程序，核心是「感知 → 推理 → 行动」循环：大模型接收任务，**拆解成子目标**，通过**工具调用**（查库、执行代码、读文件）获取反馈，再基于反馈规划下一步，直到完成任务。关键机制：上下文管理、工具定义与调用、记忆/反思、任务规划（ReAct：Reason + Act）。

**追问1：Agent 和普通大模型对话的区别？**
A：普通对话是「一问一答」；Agent 有**循环执行 + 工具 + 目标导向**，能主动多次操作外部世界、根据结果调整，而不仅是生成文本。

**追问2：工具调用（Function Calling）是什么？**
A：模型输出一个**结构化的工具调用请求**（函数名 + 参数），由宿主程序执行真实操作，把结果返回给模型继续推理。这让模型能访问实时数据、执行代码、操作文件，突破纯文本生成。

**追问3：你觉得 Agent 应用的难点/瓶颈？**
A：
1. **上下文长度**限制（长任务信息过载）
2. **错误累积**（一步错后面全错，需校验/回滚）
3. 工具可靠性与安全（自主执行有风险）
4. 规划能力（复杂任务拆解质量）。所以工程上要设计好工具边界、加护栏、分阶段校验。

**Q：你怎么用 AI 工具加速开发？**（简历「AI 方法论」）
A：我的方法论分几类场景：
1. **逻辑审查**——让 AI 审查我的代码找 bug、边界、内存/并发问题
2. **检索**——把框架报错/API 问题丢给 AI 快速定位，替代低效搜索
3. **生成**——写测试、样板、重复性代码，我 review 后合入
4. **方法论沉淀**——我维护自己的 workflow 和 prompt 模板，让 AI 产出更稳定。

**追问1：AI 生成的代码你敢直接上生产吗？**
A：不敢直接上。**AI 是加速器不是正确性保证**：生成代码我会逐行 review、写测试覆盖、在真实场景验证，尤其对**并发、内存、安全**相关的代码绝不全信。它省的是「从零写样板」的时间，不是「理解并验证」的时间。

**追问2：什么场景 AI 帮不上忙？**
A：需要**深度系统理解**的调试、跨模块的架构权衡、涉及公司特定业务/历史包袱的逻辑，AI 常因缺乏上下文而给出表面/错误答案。这时候人要先理解系统，AI 只能当辅助。

**追问3：你用 AI 有没有翻车/踩坑经历？**
A：有——AI 会**自信地给出看似合理但错误**的实现（编造不存在的 API、忽略边界、用错并发语义）。所以我养成了**先验证再采用**的习惯：编译、测试、跑通才算数。这正好反映我了解它的局限，不是无脑依赖。

### 高性能协程网络服务框架

> [!note] 简历要点：ucontext 协程、N-M 调度、epoll+定时器、Hook、Ragel、HTTP/WebSocket、Servlet 路由、ConfigVar、日志、Singleton、池化、数据访问层、ORM 代码生成、ZooKeeper、so 热加载、Daemon、vcpkg/CMake Presets。

**Q：协程和线程的区别？为什么用协程？**
A：线程是内核调度的执行单元，切换要陷入内核、上下文切换开销大（微秒级，涉及寄存器/栈/页表/缓存）；协程是用户态调度，切换只保存/恢复少量寄存器和栈指针（纳秒级），由程序控制。高并发网络场景线程数受限，用少量线程承载海量协程，提升吞吐。

**追问1：协程和线程的数量级差距？**
A：线程默认栈约 8MB，内存受限，几万线程就扛不住；协程栈可指定小栈（几 KB 到几十 KB），几十万没问题。且协程切换不陷内核，吞吐更高。

**追问2：协程能利用多核吗？**
A：单线程跑协程只用一个核，所以用 **N-M 模型**（N 线程 M 协程），把协程分发到多线程上，既享协程轻量又用满多核。

**追问3：什么时候协程不如线程？**
A：协程适合 **I/O 密集**（大量等 I/O）；**CPU 密集**或需要**强实时抢占**、依赖系统调度优先级时，线程/进程更合适。且协程若有阻塞调用会卡住整条线程（靠 Hook 解决）。

**Q：协程怎么实现的？基于 ucontext 的原理？**
A：每个协程有独立栈和上下文。ucontext 提供 `getcontext`/`makecontext`/`swapcontext`：切换时把当前 CPU 上下文（寄存器、栈指针、指令指针）存入 `ucontext_t`，再恢复目标协程的上下文，实现用户态跳转。封装成 Fiber：管理主协程/工作协程切换、栈分配（可指定大小）、状态机（READY/RUNNING/TERM）。

**追问1：为什么协程不用线程做，栈怎么来的？**
A：协程是**用户态**的，不经过内核调度器，所以不用线程。栈用 `malloc`/`mmap` 分配（可指定大小），ucontext 的 `uc_stack` 指定栈基址与大小，栈用完可检测溢出。

**追问2：协程栈小，递归/大局部变量栈溢出怎么办？**
A：可检测栈溢出（栈底放哨兵值检查），或**动态栈/分段栈**（溢出时扩展）。本项目用固定栈 + 约定协程内避免深递归和大栈对象，是常见取舍。

**追问3：协程状态机有哪几态？**
A：READY（就绪等待调度）、RUNNING（运行中）、TERM（已结束）、可能还有 WAIT/SUSPEND（让出等待事件）。调度器维护就绪队列，取 READY 协程运行。

**Q：N-M 协程调度模型是什么？**
A：N 个系统线程组成线程池，M 个协程作为用户态任务，N-M 即多线程多协程。调度器维护**任务队列**，空闲线程从队列取协程执行，协程让出/阻塞回到队列。相比 1:1 省线程开销，相比 M:1 能利用多核。还支持协程绑定固定线程（亲和）和跨线程迁移。

**追问1：协程在线程间迁移怎么保证安全？**
A：协程被让出后其上下文是**完整的快照**，放到共享就绪队列后，任何空闲线程都能取走恢复执行；只要协程不依赖「当前运行线程」的线程局部状态，迁移就安全。这正是把 Hook 开关做成**线程粒度**的原因——避免协程迁移后线程局部状态错乱。

**追问2：亲和绑定是为什么？**
A：让某协程**固定跑在指定线程**，可利用该线程的缓存/线程局部资源，避免迁移抖动；代价是牺牲负载均衡。适合有亲和需求的场景。

**追问3：调度器本身是线程安全的吗？**
A：任务队列需要加锁或原子操作（多线程同时取/放）。本项目用线程安全的任务队列 + 信号量/条件变量唤醒空闲线程，属于多生产者多消费者模型。

**Q：协程会不会阻塞整个线程？普通阻塞调用怎么办？**
A：会——协程在用户态运行，普通阻塞调用（sleep、阻塞 socket）会阻塞**整条线程**，饿死同线程其他协程。这正是 **Hook 系统**的意义：把阻塞调用替换为异步 + 让出，协程等待事件时把 CPU 让给别的协程。

**追问1：Hook 怎么拦截系统调用？**
A：本质是**符号替换**（dlsym + 函数指针或链接期拦截）。把 `socket`/`connect`/`read`/`write`/`sleep` 替换为自定义实现：调用真实函数前先查 fd_manager 看该 fd 是否注册到 IOManager，是则把协程挂到对应读写事件上并**让出**；事件就绪后由 IOManager 唤醒协程继续，实现「阻塞即让出」。

**追问2：如何只对指定线程生效？**
A：用一个**线程局部变量**标记当前线程是否启用 hook。hook 函数入口先检查该标志，开启则走协程化异步路径，否则直接调真实 syscall。这样可自由选择哪些线程走 hook，避免影响非协程场景。

**追问3：Hook 了 read/write，业务代码怎么写？**
A：业务代码**完全看不出差别**——还是写同步的 recv/send，但底层变成了「让出→等事件→唤醒」。这就是「同步语义、异步性能」：开发者按同步风格写，却获得高并发吞吐，降低异步回调的心智负担。

**Q：定时器怎么实现的？**
A：用 **epoll 超时机制 + 内部最小堆**（或红黑树）管理定时器。所有定时器按到期时间组织，每次 epoll_wait 取**最近到期时间**作超时值；epoll 返回后检查堆顶是否到期，触发到期定时器回调。比每定时器一个 timerfd 统一、高效。

**追问1：为什么用最小堆而不用 timerfd 每个定时器？**
A：每个定时器一个 timerfd 会**消耗大量 fd、系统调用多**；统一一个最小堆 + 一次 epoll_wait 就能管理所有定时器，堆顶即最近到期，效率 O(log n)。

**追问2：定时器和 I/O 事件怎么统一调度？**
A：IOManager 里 epoll_wait 的**超时参数 = 最近定时器到期时间**。epoll 返回后先处理就绪 I/O，再检查堆顶定时器，两者在同一次调度循环里统一触发，避免两套调度。

**追问3：红黑树 vs 最小堆做定时器？**
A：最小堆更适合**取最近到期**（O(1) 取最小、O(log n) 插入/删除），且有**取消定时器**能力；红黑树支持有序遍历但取最小也 O(log n)。取最小堆更自然。

**Q：epoll 的 ET 和 LT 区别？为什么用 ET？**
A：LT 只要缓冲区有数据就持续通知（没读完会反复触发）；ET 仅状态**变化时通知一次**，必须一次读完。ET 减少系统调用与重复唤醒，配合非阻塞 I/O + 循环读写更高效，但要求读全、容易漏读，需在框架层保证一次读完。

**追问1：为什么用 ET 不用 LT？**
A：高并发下 LT 每次有数据都唤醒，**重复系统调用和唤醒开销**大；ET 只在可读/可写状态变化时触发一次，配合循环读直到 EAGAIN，减少无谓唤醒，吞吐更高。

**追问2：ET 容易踩什么坑？**
A：
1. 必须用**非阻塞** fd，否则读不全会阻塞
2. 必须**循环读到 EAGAIN**，否则漏数据（一次读不完整条消息）
3. 边沿触发要小心处理半包。框架层统一处理这些。

**追问3：epoll 和 select/poll 区别？**
A：select/poll 每次要**拷贝全部 fd 集合、线性扫描**，O(n)；epoll 用**红黑树 + 就绪链表**，只返回就绪的 fd，O(1) 处理，且无需反复拷贝，适合大量连接。epoll 还支持 ET 和水平两种模式。

**Q：HTTP 解析为什么用 Ragel？**
A：HTTP 报文是典型的**有限状态机解析**场景（请求行/头/体、字段状态迁移）。Ragel 是**状态机编译器**，把正则/状态图编译成 C 代码的 DFA（确定性有限自动机），无回溯、无递归、解析性能接近手写汇编；比逐字符手写解析状态迁移清晰、易维护、可组合生成。

**追问1：DFA 为什么解析快？**
A：DFA 每个状态 + 输入字符 → **唯一确定的下一个状态**，无回溯（NFA 才有回溯），扫描一遍 O(n) 完成，且生成的是紧凑的表驱动/跳转代码，缓存友好。

**追问2：手写状态机 vs 生成器怎么选？**
A：简单协议手写可控；HTTP 这种**状态多、易漏**的用生成器（Ragel/ragel 语法描述状态迁移）保证正确性和可维护性。这是「正确性优先 + 生成自动化」的工程选择。

**追问3：解析器性能接近汇编是什么概念？**
A：因为生成的是**无回溯 DFA**，每字符 O(1) 的查表/跳转，常数极低，接近手写底层代码。但一般不需要追求极致，重点是状态迁移清晰、正确。

**Q：Servlet 路由怎么匹配的？**
A：仿 Java Servlet 实现 ServletDispatch，维护**精确匹配（哈希表）+ 模糊匹配（前缀树/通配符）**两级路由，注册时绑定 path 与处理函数，请求按 URI 查表分发，未命中走 NotFoundServlet 兜底，精确优先于模糊。

**追问1：为什么精确用哈希、模糊用前缀树？**
A：精确匹配是**等值查找**，哈希 O(1)；模糊/通配符匹配（如 `/user/*`、带参数的路径）需**最长前缀匹配**，前缀树（Trie）适合，逐段匹配、回退找最近的通配祖先。

**追问2：路由冲突/优先级怎么定？**
A：精确路由 > 前缀/通配路由 > 兜底（404）。同一层级多匹配取**最长前缀 / 注册顺序**，需约定一致规则，避免歧义。

**追问3：新增一个接口要改网络层吗？**
A：不用——注册 handler 到路由表即可，**协议层与业务层解耦**。这也是自研框架「业务扩展不碰框架」的体现。

**Q：ConfigVar 配置中心怎么做到「定义即配置、变更即通知」？**
A：用模板类 `ConfigVar<T>` 承载配置项，静态注册到全局 Config。`Config::Lookup("a.b.c", default, "desc")` 时若已存在同名项则复用，否则新建注册。加载 YAML 时按 key 反序列化（支持 STL 容器与自定义类型），变更时**回调注册的监听函数**，业务配置随配置重载自动更新。

**追问1：怎么支持自定义类型序列化？**
A：通过**模板特化/偏特化**为类型提供序列化/反序列化函数（lexical_cast 到 YAML Node），注册到配置系统；内置类型和 STL 容器提供默认实现。这是模板元编程的实际应用。

**追问2：变更即回调怎么实现的？**
A：ConfigVar 维护一个监听函数列表（`std::function`），加载/修改配置后遍历调用监听器，业务注册 `addListener` 即可感知变更，无需轮询。

**追问3：配置加载失败/缺 key 怎么办？**
A：有默认值兜底（Lookup 传 default），缺 key 用默认；类型不匹配则报错或跳过并记日志，避免崩。

**Q：双风格日志怎么实现的？**
A：Logger 聚合多个 Appender，Appender 决定输出目标（文件/终端）与格式（Formatter）。**流式风格**用宏展开 `<<` 拼装日志流；**格式化风格**走 `vsnprintf`。多 logger 按名称隔离，级别从 TRACE 到 FATAL 过滤。

**追问1：流式和格式化为什么两种都要？**
A：流式 `LOG_INFO << x << y` 类型安全、惰性求值（级别不满足时连字符串都不拼）、写起来自然；格式化 `LOG_FMT("%d %s", ...)` 灵活控制格式但类型不安全。两种满足不同场景。

**追问2：日志级别过滤怎么做到不浪费？**
A：宏里先判断当前 logger 级别，**不满足就不执行拼接**（惰性），避免低级别日志在拼接和格式化上白白消耗 CPU。

**追问3：多 logger/appender 隔离的价值？**
A：不同模块可配不同输出目标/级别/格式（如业务日志、错误日志分文件），互不干扰，便于运维排查。

**Q：为什么用 Singleton？**
A：保证全局唯一实例 + **首次使用时才构造（延迟初始化）+ 线程安全**（C++11 局部静态变量保证），统一各模块（Logger、Config、IOManager）的全局访问点，避免散落全局对象与初始化顺序问题。

**追问1：C++11 局部静态变量为什么线程安全？**
A：局部 static 的初始化由编译器加**双重检查 + 同步**保证，多线程首次访问时只初始化一次，标准保证其线程安全（magic static）。

**追问2：Singleton 的缺点/什么时候不该用？**
A：隐藏依赖、难测试、难并发控制（若带可变状态要加锁）。跨模块共享的**无状态/单例资源**（配置、日志）适合；有状态或需要多实例的场景不该硬套。

**追问3：线程池/内存池/对象池为什么能提升性能？**
A：**池化复用**避免频繁创建/销毁（线程、连接、对象）的高开销，分配即取、用毕归还，配合缓存降低分配和上下文切换。

**Q：ZooKeeper 在项目里做什么？**
A：用作**服务注册与发现 + 分布式协调**：服务启动时在 ZK 创建临时节点注册，下线/宕机临时节点自动消失；调用方 watch 节点获取可用服务列表。ZK 还常用于分布式锁（临时顺序节点）。

**追问1：ZK 临时节点和持久节点区别？**
A：**临时节点**随会话结束自动删除（用于服务注册，宕机即摘除）；**持久节点**不随会话消失（存配置等）。正是临时节点特性实现了「服务下线自摘除」。

**追问2：ZK 和 Nacos 的区别？（若被对比）**
A：都做注册中心/配置中心。ZK 更底层、强一致（ZAB）、基于临时节点；Nacos 原生支持**动态配置下发 + 权重负载均衡 + 健康检查**，更贴合微服务。项目里协程框架用 ZK，ERP 用 Nacos，都实现自注册。

**追问3：服务发现和负载均衡的关系？**
A：注册中心提供**可用实例列表**（服务发现）；调用方在此基础上做**负载均衡**（随机/权重/最小连接）选一个实例。发现解决「有哪些」，均衡解决「选哪个」。

**Q：so 动态模块热加载怎么做？**
A：用 `dlopen`/`dlsym`/`dlclose` 动态加载 `.so`，通过统一接口（如导出的注册函数）把模块的 handler/服务注册进框架，运行时加载/卸载，实现**不停机扩展**（模块热插拔）。

**追问1：热加载要注意什么？**
A：符号冲突、**导出接口约定**（要有一个稳定的注册入口）、资源/线程的优雅卸载（避免正在用的模块被卸载）、版本管理。热更新常用于插件系统。

**追问2：Daemon 守护进程化是什么？**
A：把进程**脱离终端后台运行**（fork + setsid + 重定向标准流），作为常驻服务，配合日志落盘、崩溃重启（supervisor/systemd），是生产服务部署形态。

**追问3：CMake Presets + vcpkg 的价值？**
A：Presets 预定义构建配置一键切换；vcpkg 管第三方依赖；Ragel/protoc 代码生成进构建流程——**可复现、可移植、自动化**的工程化，面试官想听的是「不只会写代码，还懂工程化」。

### 谈谈你对 Ragel 的理解
**回答话术：**
Ragel 是一个**状态机编译器**：把用正则/状态图描述的状态机编译成 C/C++ 代码，生成的是**确定性有限自动机（DFA）**。核心价值是把「协议解析」这类繁琐易错的手写工作交给「描述 + 生成」：生成的代码**无回溯、无递归、每字符 O(1)**，性能接近手写汇编；状态迁移清晰、易维护、可组合。
它与手写解析的区别在于**正确性来源**：手写是「人保证状态迁移正确」，Ragel 是「生成器保证 DFA 正确」，人只需要写对描述，特别适合 HTTP 这类状态多、边界多的协议。
***引申知识: DFA 为什么快——每个「状态 × 输入字符」唯一确定下一个状态，无回溯（NFA 才有），单遍 O(n) 扫描；理解「状态机 vs 逐字符手写」是协议解析的核心；Ragel 还能生成可视化状态图用于调试。***
> [!Info] 可能的追问:
> - Q: Ragel 和手写解析器比有什么缺点？
> - A: 引入生成步骤（构建依赖）、生成代码可读性差、调试要理解状态机的生成逻辑。所以复杂/易错协议用生成器，简单协议手写更直接。
> - Q: 除了 HTTP 还能解析什么？
> - A: 任何**有状态迁移的字节流**：URI、JSON 字段、二进制协议帧、正则匹配本身。Ragel 的通用模型就是「状态 × 输入 → 动作」。

### 什么叫做 Ragel 有限状态机生成 HTTP/1.1？
**回答话术：**
HTTP/1.1 报文结构本质是一个**有限状态机**：请求行（方法 空格 URI 空格 版本 CRLF）→ 头部若干行（key: value CRLF）→ 空行 → 消息体，每条规则对应一个**状态迁移**。我用 Ragel 把这些规则**描述成状态图/正则**，由它**生成对应的解析 C++ 代码**：运行时按字节逐个驱动状态迁移，解析出请求行字段和头部，完成一次 HTTP 报文解析。
关键点是**支持跨包（半包）状态挂起恢复**——数据不足时解析器保存状态、返回「待更多数据」，下次读满再继续，这正是配合 epoll/协程（读一次可能只有半包）的必需能力。
***引申知识: 生成的解析器 + 半包缓冲 = 一个「解析器实例」，在协程/异步场景下每次读到新字节片段喂给它即可，状态自动续接；这就是「状态机天然支持流式解析」的价值。***
> [!Info] 可能的追问:
> - Q: HTTP 解析为什么难？
> - A: 边界多：请求行/头部/空行/体的分界、CRLF 处理、头部大小上限、跨包（TCP 半包）时状态要能挂起恢复。手写容易漏边界、出 bug。
> - Q: 生成的解析器怎么和 epoll/协程配合？
> - A: 数据不足时返回「待更多数据」，协程让出；下次读满再喂给同一解析器实例，状态不丢失。

### N-M 线程调度模型是怎么实现的？
**回答话术：**
N 个系统线程构成线程池、M 个协程作为用户态任务，调度器在中间做匹配。实现分三层：
1. **任务队列**——线程安全 FIFO 存 READY 协程（互斥锁或原子 CAS）
2. **线程池**——每线程一个调度循环，从队列取协程执行，无活时用条件变量/信号量阻塞等待
3. **调度逻辑**——协程让出（yield）或结束（TERM）后回到队列或回收，`swapcontext` 在协程间切换。
**亲和 vs 迁移**：默认协程进**共享队列**，任意空闲线程可取走执行（跨线程迁移）；也可绑定固定线程（亲和）利用缓存/线程局部资源。线程用 `std::thread` 创建，启动时各自跑调度循环。
***引申知识: 与「1 线程 1 协程」相比省线程开销、与「单线程多协程」相比能用满多核；调度循环本质是「取任务 → 执行到让出 → 再取」的循环，所以叫「事件循环 + 任务队列」的调度器。***
> [!Info] 可能的追问:
> - Q: 多个线程同时取任务怎么保证安全？
> - A: 任务队列用互斥锁或原子 CAS（无锁队列）保护，取/放都是原子操作；用条件变量/信号量做「队列有货」的通知，避免忙等。
> - Q: 为什么不是 1 协程绑 1 线程？
> - A: 线程数受内存/调度开销限制，几万协程无法开几万线程；N-M 让少量线程承载海量协程，还利用多核。

### 你的 Hook 系统是怎么实现的？它主要解决了什么问题？
**回答话术：**
**解决的问题**：协程一遇到阻塞系统调用（`socket`/`read`/`write`/`connect`/`sleep`）就会卡死整条线程，同线程其他协程饿死——这是协程用于网络服务最大的坑。
**实现**：**符号替换**（拦截层 + `dlsym` 拿到真实函数指针）。进入 hook 函数先查**线程局部开关**（该线程是否启用 hook）和 **fd_manager**（该 fd 是否注册到 IOManager）：是则注册读写事件并**让出协程**，事件就绪后 IOManager 唤醒协程继续；否则直接调真实 syscall。于是「阻塞即让出、就绪即唤醒」，业务代码写同步风格、底层是异步性能。
***引申知识: hook 的语义兼容很关键——返回码、errno 必须和真实 syscall 一致，否则上层判断出错；「线程粒度开关」用线程局部变量实现，是 hook 系统能选择性生效的基础。***
> [!Info] 可能的追问:
> - Q: 如何做到只对指定线程生效（线程粒度）？
> - A: 一个**线程局部变量**标记当前线程是否启用 hook；入口先检查标志，开启走协程化异步路径，否则调真实 syscall，可自由选择哪些线程走 hook。
> - Q: hook 了 sleep，协程怎么不阻塞？
> - A: `sleep` 被替换为「注册到期定时器 + 让出协程」，到期由定时器唤醒恢复，线程本身不睡。
> - Q: hook 会不会有坑？
> - A: 1. 必须处理**非阻塞 fd**（阻塞 fd 的 read 会真的阻塞线程）
>   2. 事件注册失败/漏注册会导致协程永久挂起（经典 bug，见通用题）
>   3. 语义要与真实 syscall 完全兼容

### 模仿 Java Servlet 的路由分发（哈希 + 前缀树支撑精确/模糊匹配）是如何做到的？
**回答话术：**
实现一个 ServletDispatch 分发器，注册时把 path 和处理函数绑定。**精确匹配**用哈希表（`unordered_map<path, handler>`）O(1) 命中；**模糊匹配**用前缀树（Trie）支持通配符（如 `/user/*/info`、`/*.do`）。请求到来：先查哈希表，未命中进前缀树做**最长前缀匹配**，仍未命中走 NotFoundServlet 兜底，**精确优先于模糊**。
***引申知识: 等值查找哈希 O(1)、通配查找需「最长前缀 + 回退到最近通配祖先」只有 Trie 适合；两层结构是「查得快的用哈希、查得准的用前缀树」的典型组合。***
> [!Info] 可能的追问:
> - Q: 路由冲突/优先级怎么定？
> - A: 精确 > 前缀/通配 > 兜底；同一层级多匹配取**最长前缀 / 注册顺序**，需统一规则避免歧义。
> - Q: 新增一个接口要改网络层吗？
> - A: 不用——注册 handler 到路由表即可，**协议层与业务层解耦**，业务扩展不碰框架。

### 你用 ZooKeeper 在网络框架中做了什么？
**回答话术：**
用作**服务注册与发现 + 分布式协调**：服务启动时在 ZK 创建**临时节点**注册自己（IP:port 写进节点），下线/宕机会话断开节点自动消失；其他服务 **watch** 该节点感知服务上下线，动态获取可用实例列表做寻址。利用的正是 ZK **临时节点 + watch 机制**实现「服务自注册、下线自摘除」。
***引申知识: 临时节点随会话结束自动删除（注册服务、宕机即摘除）vs 持久节点不随会话消失（存配置）；「服务发现提供有哪些实例、负载均衡决定选哪个」是两件事。***
> [!Info] 可能的追问:
> - Q: ZK 和 Nacos 的区别？
> - A: 都做注册/配置中心。ZK 更底层、强一致（ZAB）、基于临时节点；Nacos 原生支持动态配置下发 + 权重负载均衡 + 健康检查，更贴合微服务。协程框架用 ZK，ERP 用 Nacos。
> - Q: 服务发现和负载均衡的关系？
> - A: 注册中心提供**可用实例列表**（发现：有哪些）；调用方在此基础上做**负载均衡**（均衡：选哪个）。

### 如何让一个网络框架在 Linux 中有 daemon 守护进程？
**回答话术：**
标准 Daemon 化流程：
1. `fork()` 一次并让父进程退出，子进程成为孤儿由 init 收养
2. `setsid()` 创建新会话**脱离控制终端**
3. 可选再 `fork()` 一次防止重新获取终端
4. `chdir("/")` 避免占用挂载点
5. 重定向标准输入/输出/错误到 `/dev/null` 或日志文件
6. 设置 umask。再配合**守护管理**：pid 文件、崩溃自动拉起（systemd/supervisor 守护）。
***引申知识: daemon 与后台运行 `&` 的区别——`&` 仍属当前会话/终端组，终端关闭收到 SIGHUP 被杀；daemon 完全脱离会话/终端/工作目录，生命周期由系统管理。***
> [!Info] 可能的追问:
> - Q: 为什么 fork 后要 setsid？
> - A: 脱离**控制终端**——若仍挂终端，终端关闭会收到 SIGHUP 被杀死；`setsid` 让进程成为新会话首进程、脱离控制终端。
> - Q: 为什么有时 fork 两次？
> - A: 第一次 fork 让父进程退出、避免成为会话首进程后重新获取控制终端；第二次 fork 防止进程再次获得终端。双重 fork 更稳妥。

### per-module 的单测二进制是什么？你是怎么做的测试？
**回答话术：**
per-module 指**每个功能模块一个独立的测试二进制**（如 `test_fiber`、`test_iomanager`、`test_http_server`、`test_bytearray`、`test_mysql`），由 CMake 为每个 `tests/test_*.cc` 生成一个可执行，各自链接被测模块。好处：**模块独立验证、失败定位精确、可单独跑不互相污染**。
做法：
1. 为每个核心模块写针对性用例（协程状态机、调度器调度顺序、定时器到期、HTTP 解析合法/非法报文、ByteArray 序列化往返）
2. 断言用 ASSERT/EXPECT，失败即退出码非 0
3. CMake 的 `add_test` 注册进 CTest，`ctest` 一键全跑，也能单独跑某个二进制。
***引申知识: 单测的价值不是「跑通」而是「有判定」——每个用例必须断言结果（解析出的头字段值、序列化还原、回调被调用），失败有明确报错；边界/非法输入用例比正常路径更能暴露 bug。***
> [!Info] 可能的追问:
> - Q: 怎么保证测试真的验证了逻辑？
> - A: 写**有判定性的用例**：不只跑通，还要断言结果（HTTP 头字段值、ByteArray 序列化后还原、定时器回调被调用），失败有明确报错。
> - Q: 边界/异常情况怎么测？
> - A: 专门测**边界和非法输入**：半包 HTTP（分两次喂数据）、超长头、空 Body、非法字节、定时器取消，比只测正常路径更能暴露 bug。
> - Q: 测试覆盖率怎么保证？
> - A: 用 gcov/lcov 看模块覆盖率，核心模块（协议解析、调度）优先覆盖；配合 gdb 对可疑路径单步验证。

### gdb 验证测试是怎么做的？
**回答话术：**
gdb 用于**跑不出来的逻辑/崩溃/段错误/死锁**的定位：
1. 编译加 `-g -O0` 保留符号
2. 崩溃时 `backtrace` 看调用栈定位到哪行
3. `print` 查看变量/内存值
4. 断点（break 行号/函数）、条件断点（`break xx if n==5`）、watch 变量
5. 协程/线程相关：`info threads` 切线程、`thread apply all bt` 看全部线程栈，确认是不是死锁/挂起。
***引申知识: 段错误定位看「崩溃栈顶的调用点 + 指针合法性」；死锁用「所有线程栈是否都卡在锁上」判断；gdb 是确认手段，配合日志 + ASan/TSan + 状态统计（协程 READY/RUNNING 计数）更快缩小范围。***
> [!Info] 可能的追问:
> - Q: 段错误一般是什么原因，gdb 怎么定位？
> - A: 野指针/悬空/越界/栈溢出/use-after-free。`bt` 看崩溃栈顶调用点，`print` 看指针是否合法；配合 ASan 能直接报「哪行越界/哪块内存被释放后访问」。
> - Q: 死锁怎么用 gdb 查？
> - A: `info threads` 列全部线程，逐个 `bt` 看是否卡在锁上；`thread apply all bt` 一次看全部，找出「互相等对方」的循环等待。
> - Q: 多线程/协程问题 gdb 够吗？
> - A: gdb 能看到线程/协程栈与状态，是基础手段；结合日志 + ASan/TSan + 状态统计更快缩小范围，gdb 负责最终确认。

### 实习经历

**Q：AUTOSAR 是什么，分哪些层？**
A：AUTOSAR 是汽车电子软件的**标准化软件架构**（CP 经典平台），分层解耦：**应用层（SWC）** 用 RTE 通信，**RTE（运行时环境）** 提供应用与基础软件通信的抽象，**BSW（基础软件）** 分服务层、ECU 抽象层、MCAL（微控制器抽象层），再往下是复杂驱动。目标是**硬件无关、软件可复用、功能安全**。

**追问1：你做的 IEEE1722Tp 和 LsduR 是什么模块？**
A：都属于**通信栈/传输层**模块：IEEE1722Tp 是基于 IEEE 1722（AVB 音视频传输协议）的**传输协议模块**，负责把数据封装进 1722 包并完成收发传输；LsduR 是 **LSDU（链路服务数据单元）路由模块**，在通信栈里做消息的路由分发（按 ID/通道把收到的数据路由到对应上层处理）。

**追问2：CP 协议栈通讯软件是什么？**
A：AUTOSAR CP 的**通信栈**（COM 栈）：从应用/ RTE 到 CAN/Ethernet 底层的一组模块（COM、PDUR、CANIF、CANSM、Can 驱动等），负责**信号/PDU 的组包、路由、传输**。我做的模块是其中一部分，按广汽技术需求实现并重构为符合 AUTOSAR 标准。

**追问3：NeuSAR 校验是什么？**
A：NeuSAR 是**国内主流的 AUTOSAR 平台/工具链**（东软睿驰），用于开发、配置、**校验 AUTOSAR 代码是否符合规范和接口**。我写的模块通过它的校验，说明符合 AUTOSAR 标准接口。

**Q：QAC 和 Polyspace 是什么？**
A：都是**静态代码分析工具**。QAC（QAC/QAC++）检查**代码规范（MISRA C 等）和常见缺陷**——未初始化变量、死代码、越界、资源泄漏、不规范写法；Polyspace 做**更严格的形式化/运行时错误分析**，用数学方法证明无越界、除零、指针空悬等**运行时错误**。用于功能安全认证（ISO 26262）场景。

**追问1：静态分析能发现什么，有什么局限？**
A：能发现**无需运行就能判定**的问题（变量未初始化、类型/转换错误、违背 MISRA、部分越界/死代码）。局限：**无法发现逻辑错误、并发时序问题、需要运行数据才能暴露的行为**，所以静态分析是**编译之外的补充**，配合动态测试/代码评审。

**追问2：MISRA C 是什么？**
A：MISRA C 是**汽车/嵌入式 C 语言编码规范**，限制易出错的语言用法（如禁动态内存分配、限制指针/整数转换、要求明确类型），提高安全性与可移植性，是 QAC 检查的主要标准之一。

A：嵌入式让我**更看重内存管理、资源受限、代码规范与确定性**（没有无限内存、不能随便 new、要求行为可预测），也接触了**工具链、静态分析、功能安全**流程。这些规范性和「在约束下写正确代码」的素养能迁移到 C++/后端开发。

### 高性能 ERP 进销存系统

> [!note] 简历要点：ORM 反射层、动态 SQL、类型安全/Concepts、防注入、连接池、事务、JWT RSA/HMAC、CORS、WebSocket 鉴权、JsonVO、RocketMQ 事务消息、削峰、MongoDB、缓存三问题、Nacos、模块热插拔。

**Q：ORM 反射是怎么实现的？**
A：每个 DO（数据对象）继承 BaseDo，构造函数里用 `std::function` getter 把字段注册成**「字段域」**，记录列名 + 类型占位符（s/i/d/dt 等）+ 取值函数。BaseDao 遍历这些字段域，按列名拼装 INSERT/UPDATE/DELETE/SELECT **动态 SQL**，字段值通过 getter 取出放入参数集，交给 PreparedStatement 绑定执行。增删改查、批量、分页都由这套元数据驱动，业务 DAO 不手写 SQL。

**追问1：为什么不用现成 ORM 框架？**
A：
1. 为学习与掌控底层，理解 JDBC/连接本质
2. 自研能定制**动态 SQL 和事务内分批批量写入**等特定需求
3. 基于运行期元数据（字段域）的方案天然支持动态 where 和批量参数化，比通用框架更贴合本项目。

**追问2：动态 SQL 里的 where 条件怎么拼？**
A：根据传入的查询条件**有选择地拼接**字段段（有值才加该条件），全部走参数占位符；字段名来自注册的列名（可信），值来自参数集（防注入），所以「动态」也不牺牲安全。

**追问3：增删改查之外，批量/分页怎么用同一套元数据？**
A：批量就是遍历对象集生成带**多组占位符**的批量 INSERT（事务内分批），分页就是在 SELECT 尾部拼 LIMIT/OFFSET。都从字段域元数据驱动，无需每表手写。

**Q：怎么做到编译期校验类型安全？**
A：泛型 DAO 方法（如 `insertBatch<T>`）用 `static_assert(std::is_base_of_v<BaseDo, T>)` 在编译期约束 T 必须继承 BaseDo，传错类型直接编译报错；SQL 参数绑定用 **Concepts（`requires`）+ 折叠表达式**约束每个参数必须是可绑定类型，杜绝 C 风格 varargs 类型错配。

**追问1：运行时反射和编译期约束的关系？**
A：字段注册是**运行时元数据**（用 `std::function` 收集），但 DAO 的泛型参数、参数类型用**编译期**约束（static_assert/Concepts）保证类型安全——两者结合：运行期驱动 SQL 生成，编译期堵类型错误。

**追问2：参数集为什么用 `std::variant`？**
A：因为参数类型不固定（int/string/double/date 等），`std::variant` 能**类型安全地承载多类型参数**，配合 `visit` 分发到 PreparedStatement 的 setXxx，比 `void*`/varargs 安全。

**追问3：为什么强调无宏/无裸指针？**
A：宏和裸指针是出错根源（类型不安全、资源泄漏风险）。项目遵循 RAII + 智能指针 + 类型安全模板，体现现代 C++ 工程实践。

**Q：全程防注入是怎么实现的？**
A：所有 SQL 一律走 **PreparedStatement 参数占位符（`?`）绑定**，不用字符串拼接；用户输入只进参数集、不进 SQL 文本，从根上杜绝 SQL 注入。

**追问1：为什么参数化能防注入？**
A：参数值由驱动**按数据类型处理**、不作为 SQL 语法解析，`' OR 1=1` 只是普通值，不改变查询结构。

**追问2：除了防注入，PreparedStatement 还有啥好处？**
A：**预编译、复用执行计划**，性能更好；长循环/批量场景优势明显。

**追问3：还有哪些 SQL 安全要注意？**
A：最小权限、敏感数据不落明文日志、慢查询治理、备份。防注入是其中一环。

**Q：为什么要用连接池？**
A：建 MySQL 连接开销大（TCP 握手 + 认证 + 内存分配），高并发下每次建连拖垮性能。连接池**预建、借还复用、控制上限**，析构自动归还，显著降开销、限并发。

**追问1：连接池怎么保证不泄漏？**
A：连接、PreparedStatement、ResultSet 全用 `std::unique_ptr`（RAII）持有，SqlSession 析构自动归还连接池，**异常路径也能正确回收**。

**追问2：连接池满了怎么办？**
A：等待（队列阻塞）或超时抛错；可配**最大连接数、等待超时**，防止请求无限堆积拖垮数据库。

**追问3：连接池和线程池异同？**
A：思想相同（**池化复用**避免频繁创建），但管的对象不同（数据库连接 vs 线程），连接还涉及归还、校验、超时释放。都是「分配-复用-归还」模式。

**Q：事务怎么保证一致性？**
A：`beginTransaction` / `commit` / `rollback` 三个方法。批量写入先开事务，循环逐批执行，**任一批抛异常就 catch 并整体 rollback 再上抛**；全部成功且影响行数对得上才 commit，保证要么全成要么全失败（原子性）。

**追问1：事务 ACID 分别是什么？**
A：原子性（Atomicity，全成或全无，靠 undo 日志）、一致性（Consistency，约束满足）、隔离性（Isolation，并发不互相干扰）、持久性（Durability，提交后不丢，靠 redo/落盘）。

**追问2：隔离级别有哪些，怎么选？**
A：读未提交、读已提交（多数默认）、可重复读（MySQL 默认）、串行化。级别越高越安全但并发越低。MySQL 可重复读靠 **MVCC** 实现一致性读。

**追问3：并发下事务的脏读/幻读？**
A：脏读=读到未提交数据；幻读=同一查询两次结果不同（插入）。隔离级别越高越能避免；MySQL InnoDB 可重复读 + 间隙锁可防幻读。

**Q：JWT 两种算法（RSA / HMAC）区别？为什么用两种？**
A：RSA 是**非对称**，私钥签发、公钥验签，私钥只在签发端，多服务可共享公钥验签，适合跨服务/多方校验；HMAC 是**对称**，签名和验签同一把密钥，快、实现简单。两者都封装，按场景选用——**分布式验签用 RSA，单服务内部用 HMAC**。

**追问1：JWT 由哪三部分组成？**
A：Header（算法、类型）+ Payload（claims，如用户、过期时间）+ Signature（签名）。三部分 Base64Url 编码，用 `.` 连接。签名部分防篡改。

**追问2：JWT 和 Session 区别？**
A：Session 是**服务端存储状态 + 客户端存 sessionId**，需要服务端共享/持久化；JWT 是**无状态**的，签名自包含在 token 里，服务端验签即可，天然适合分布式/多服务（无需查共享 session）。代价是 JWT 无法主动吊销（需黑名单）。

**追问3：JWT 泄露/过期怎么处理？**
A：设置**过期时间（exp）**、可加 refresh token 刷新；服务端可维护**黑名单**吊销；敏感信息不放进 payload（只是签名不加密）。

**Q：鉴权怎么做到统一拦截？**
A：所有 Controller 统一挂 `CustomerAuthorizeHandler` 授权处理器，在请求进入业务方法前校验 JWT；用拦截器做 **CORS 与凭证校验**，公开接口（/swagger/、/file/ 等）走**白名单放行**，其余必须带有效 Token。

**追问1：WebSocket 的 AI 客服怎么鉴权？**
A：用 oatpp-websocket 连接处理器；因为 /chat 在白名单放行，**Token 通过 WebSocket 子协议（Sec-WebSocket-Protocol）传递**，握手时读取校验，连接建立后注入用户参数，实现带身份的双向实时消息。

**追问2：CORS 是什么，凭证拦截做什么？**
A：CORS（跨域资源共享）控制**浏览器跨域请求**能否访问，通过响应头（Access-Control-Allow-Origin 等）；凭证模式（credentials）允许携带 cookie/授权头。预检（OPTIONS）请求需放行。

**追问3：Token 校验失败/过期返回什么？**
A：统一返回 401 + JsonVO 错误体，前端收到后引导重新登录；这是**统一返回格式**的好处——契约一致。

**Q：统一返回 JsonVO 有什么好处？**
A：所有接口返回**固定三段式 code/message/data**，前端与错误处理契约一致，成功/失败/分页结构统一，无需每接口自定义格式，通信与解析更规范、高效。

**追问1：错误码怎么设计？**
A：按模块/错误类型分层编码（业务码 + 细分），配合 message 给前端可读提示，便于排查和前端分支处理。

**追问2：分页返回结构？**
A：data 里含 list + total + page + size，统一结构让前端表格/分页组件直接消费。

**追问3：成功和失败为什么不搞两套结构？**
A：一套结构让前端**统一解析**，避免成功/失败字段不一致导致前端到处判空/分支，降低耦合。

**Q：为什么用 RocketMQ / 消息队列解决了什么问题？**
A：单据创建与审批是最重路径，若报表生成、库存扣减、日志都同步在请求线程跑，主接口被下游拖慢、任一下游抖动都整单失败。改成**异步发布事件消息**后：主流程只落库 + 发消息，下游异步消费，实现解耦、削峰、可重试。主接口 P95 从 ~300ms 降到 ~60ms。

**追问1：为什么能降到 60ms？**
A：把同步等待下游（报表、库存、日志）的时间**移出请求线程**——主线程只做「落库 + 发消息」两步立刻返回，下游异步消化，请求耗时大幅下降。这是**异步化 + 削峰**的直接收益。

**追问2：下游失败怎么办？**
A：**可重试**——消费失败按策略重试（重试 3 次），仍失败进死信/人工处理；上游不因下游失败而失败，只保证「消息至少被处理一次」。

**追问3：削峰填谷怎么理解？**
A：月末集中开单/大促瞬时写入量大，消息先**积压在 Broker 缓冲**，数据库按稳定速率消费，避免瞬时打爆数据库，用时间换峰值稳定性。

**Q：事务消息怎么保证「单据入库」和「消息发送」一致？**
A：先发**半消息（Half Message）**给 Broker，本地单据事务提交成功后再 **commit**，事务失败则 **rollback**；若本地事务迟迟不确认，**Broker 会回查（check）本地事务状态**兜底。避免「单据没存上却发了消息」或「单据存上却丢了消息」。

**追问1：本地事务状态在哪里回查？**
A：实现一个**本地事务检查实现类**（查询数据库里单据是否存在/是否已提交），Broker 在超时后调用它确认最终状态，据此决定提交/回滚半消息。这是 RocketMQ 的回查机制。

**追问2：如果回查时数据库也挂了/网络分区？**
A：回查会失败，Broker **定时重试回查**，直到拿到明确结果或人工介入；配合「至少一次 + 幂等消费」兜底，不会造成数据丢失。

**追问3：事务消息和本地消息表方案的区别？**
A：都是**最终一致性**思路。本地消息表：业务和消息同库事务提交，后台扫表发消息；事务消息：由 Broker 协调半消息 + 回查，**省掉本地消息表和轮询**，由 MQ 保证。核心都是「业务操作和消息发送要么都成、要么都不成」并最终补偿。

**Q：怎么保证消息不丢失、不重复？**
A：不丢靠 **Producer 同步发送 + Broker 持久化 + 消费失败重试**（重试 3 次）；不重复靠消费者**幂等**（按业务主键去重）。核心是「**至少一次 + 幂等消费**」。

**追问1：为什么是「至少一次」而不是「恰好一次」？**
A：分布式下网络可能超时/重发，Broker 无法绝对保证不重复投递。工程上用**至少一次（保证不丢）+ 消费端幂等（去重）**来达到「逻辑上的恰好一次」，比追求传输层恰好一次简单可靠。

**追问2：消费端幂等怎么实现？**
A：按业务唯一键（如单据号）查重/建唯一索引，重复消息直接跳过；或把消费写成**幂等操作**（更新类天然幂等）。

**追问3：消息积压怎么处理？**
A：加消费者实例/并发、批量消费、排查慢消费；配合削峰，让消费速率匹配生产速率。

**Q：什么时候用 MongoDB 而不是 MySQL？**
A：数据**文档型/非结构化、字段常变（schema-less 免改表）、写入量大、需水平扩展（分片）**用 Mongo；强一致、需事务和 JOIN 的关系型用 MySQL。本项目把**操作审计日志、运行日志**这类写多读少、结构易变的数据放 Mongo，避免高频日志写入膨胀 MySQL 核心表、拖垮主业务。

**追问1：Mongo 的文档模型和 MySQL 行模型区别？**
A：Mongo 存 **BSON 文档**，一个文档可嵌套子文档/数组，字段可变、免 ALTER；MySQL 是**扁平行 + 固定 schema**，靠外键/JOIN 关联。Mongo 适合聚合形态数据，MySQL 适合强关系。

**追问2：为什么日志适合 Mongo？**
A：日志**写多读少、结构易变、无需事务/JOIN**，正是文档型 + 可水平扩展（分片按时间/节点）的适用场景；放 MySQL 会因高频写入膨胀核心表、竞争资源。

**追问3：Mongo 能保证强一致/事务吗？**
A：Mongo 也支持事务和副本集，但为水平扩展和写性能，**一致性模型与事务能力弱于关系库**（非主从强一致场景）；强一致、需复杂事务的业务仍用 MySQL。

**Q：Redis 缓存策略？缓存穿透/击穿/雪崩怎么办？**
A：缓存 JWT 会话和字典/菜单等**热点数据**，降低 DB 压力。**穿透**（查不存在的数据）：缓存空值或布隆过滤器；**击穿**（热点 key 过期瞬间大量请求打 DB）：互斥锁/逻辑过期重建；**雪崩**（大量 key 同时过期）：过期时间加**随机抖动**、多级缓存。

**追问1：穿透和击穿区别？**
A：穿透是**缓存和 DB 都没有**（恶意/不存在 key 绕过缓存直打 DB）；击穿是**单个热点 key 过期**瞬间集中请求打 DB。雪崩是**大量 key 同时过期**。

**追问2：布隆过滤器是什么，怎么用？**
A：用位数组 + 多个哈希函数判断**元素是否可能存在**（可能误报、绝不漏报）。用于穿透防护：先过滤不存在 key，命中才查缓存/DB，减少无效 DB 查询。

**追问3：互斥锁重建缓存怎么实现？**
A：热点 key 过期后，只让**一个线程去 DB 重建并回填**，其他线程等待/拿旧值，避免同时打 DB；配合逻辑过期（不真删、后台异步更新）可进一步平滑。

**Q：Nacos 解决什么问题？**
A：多实例部署后实例 IP 动态变化，不能硬编码。Nacos 让服务**启动自注册、下线自摘除**，调用方按**服务名**寻址而非 IP；还作为**配置中心**统一管理数据源/中间件配置，支持动态下发。

**追问1：故障剔除与负载均衡怎么做的？**
A：实例心跳 5s/次，异常实例 15s 判定不健康、30s 自动剔除，新请求不再路由到故障节点；调用方**本地维护实例列表做负载均衡**（权重分发），多实例流量自动分摊、可弹性扩缩容。

**追问2：配置中心为什么能做到秒级生效、无需重启？**
A：配置集中存储，变更时服务端**推送/客户端长轮询**拉到最新值并触发本地回调更新，业务无需重启；客户端还有**本地缓存 + 容灾降级**，注册中心短暂不可用也能继续服务。

**追问3：注册中心挂了会怎样？**
A：因为有**本地缓存实例列表 + 容灾降级**，已建立的调用不受影响；新实例注册/变更暂时失效，恢复后重连同步。这体现「注册中心是辅助不是主链路」的容灾设计。

**Q：模块热插拔 / 条件编译怎么实现的？**
A：顶层用 **BUILD_\*（业务模块）与 USE_\*（中间件）CMake option** 控制条件编译，`app/CMakeLists.txt` 按开关加入 `target_sources`，Router 用 `#ifdef` 决定是否 bind 对应 Controller，**按需裁剪、轻量部署**。

**追问1：为什么要有编译开关而不是全编译？**
A：不同部署环境（是否启用 Mongo/RocketMQ/Redis）需求不同，编译开关**按需裁剪**，减少体积、避免引入未使用依赖和部署复杂度，还方便模块隔离测试。

**追问2：RocketMQ/Mongo/Redis 是默认启用吗？**
A：做了完整封装和集成测试，底层链路是通的；但**进销存主业务为保证核心链路稳定、避免外部依赖的部署复杂度，线上默认走 MySQL + 本地日志**，消息队列和文档库作为**可插拔扩展**保留，编译开关（USE_ROCKETMQ/USE_MONGO）即启即用。
（面试官追问「Mongo/RocketMQ 具体哪用到」就用这句——诚实、有落点、显工程判断。）

**追问3：为什么不默认全开外部依赖？**
A：核心链路优先稳定、部署简单是**工程取舍**；封装 + 集成测试 + 开关保证「想用随时能用」，而不是「不用的东西默认拖累主链路」。

### 你的 ORM 是怎么实现的？
**回答话术：**
每个 DO（数据对象）继承 BaseDo，构造函数里用 `std::function` getter 把字段注册成**「字段域」**，记录列名 + 类型占位符（s/i/d/dt 等）+ 取值函数。BaseDao 遍历字段域，按列名拼装 INSERT/UPDATE/DELETE/SELECT **动态 SQL**，字段值经 getter 取出放入参数集，交给 PreparedStatement 绑定执行。增删改查、批量、分页都由这套元数据驱动，业务 DAO 不手写 SQL。
***引申知识: 这是「运行期元数据反射」——C++ 没有语言级反射，用 `std::function` 收集字段访问器实现轻量反射；编译期用 Concepts/static_assert 约束类型，运行期反射 + 编译期类型安全两条线结合。***
> [!Info] 可能的追问:
> - Q: 为什么不用现成 ORM 框架？
> - A: 1. 为学习与掌控底层
>   2. 自研能定制**动态 SQL 和事务内分批批量写入**等特定需求
>   3. 基于运行期元数据天然支持动态 where 和批量参数化
> - Q: 动态 SQL 里的 where 条件怎么拼？
> - A: 根据传入条件**有选择地拼接**字段段（有值才加），全部走参数占位符；字段名来自注册列名（可信）、值来自参数集（防注入），「动态」不牺牲安全。
> - Q: 参数集为什么用 `std::variant`？
> - A: 参数类型不固定，`variant` **类型安全承载多类型**，配合 `visit` 分发到 PreparedStatement 的 setXxx，比 `void*`/varargs 安全。

### JWT 鉴权是怎么做的？JWT 鉴权是为了什么？
**回答话术：**
**为什么**：HTTP 是无状态的，JWT 让服务端**无需保存会话**即可校验请求身份，token 自包含用户信息与过期时间，天然适合**分布式多服务**（每个服务都能验签，不必查共享 session）。
**怎么做**：登录成功用密钥/私钥签发 JWT（Header + Payload + Signature 三部分 Base64Url 拼接）；客户端请求带 `Authorization: Bearer <token>`；所有 Controller 统一挂 `CustomerAuthorizeHandler` 授权处理器，进入业务方法前**校验签名 + 过期时间**，通过才放行，失败返回 401；公开接口走白名单。
***引申知识: Signature 是「对 Header+Payload 用密钥签名」，payload 可被 Base64 解码（不加密）、但改任何字段签名即失效（不可篡改）；RSA 非对称适合多服务共享公钥验签，HMAC 对称适合单服务快。***
> [!Info] 可能的追问:
> - Q: JWT 和 Session 区别？
> - A: Session 是**服务端存储状态 + 客户端存 sessionId**，需共享/持久化；JWT **无状态**自包含签名，天然适合分布式。代价是 JWT 无法主动吊销（需黑名单）。
> - Q: JWT 泄露/过期怎么处理？
> - A: 设**过期时间（exp）**、refresh token 刷新；服务端维护**黑名单**吊销；敏感信息不放进 payload（签名不加密）。
> - Q: WebSocket 的 AI 客服怎么鉴权？
> - A: 用 oatpp-websocket 连接处理器；/chat 在白名单放行，**Token 通过 WebSocket 子协议（Sec-WebSocket-Protocol）传递**，握手时读取校验，连接建立后注入用户参数。

### 你如何通过 RocketMQ 做各种服务的解耦？
**回答话术：**
把**强同步耦合**改成**异步事件流**：单据创建/审批等核心动作完成后，Producer 只发一条**事件消息**（单据已创建/已审批），下游报表生成、库存变动、日志记录作为**独立 Consumer** 各自订阅、各自消费。收益：
1. **上游不依赖下游**——下游挂掉/变慢不影响主流程
2. **下游独立扩展**——报表慢就多起消费实例
3. **新增下游只需新加 Consumer**，不动上游。
配合**事务消息**（半消息 + 本地事务确认 + Broker 回查）保证「单据入库」和「事件发布」一致；**幂等消费 + 重试**保证不丢不重。
***引申知识: 解耦的本质是发布/订阅（上游只发事件、下游自己消费）；「至少一次 + 幂等」是 MQ 可靠性的黄金组合；事务消息的最终一致性靠「先发半消息 → 本地事务成功再确认 → 超时回查」闭环。***
> [!Info] 可能的追问:
> - Q: 为什么能实现削峰填谷？
> - A: 大促/月末瞬时写入量大，消息先**积压在 Broker 缓冲**，数据库按稳定速率消费，避免瞬时打爆数据库，用时间换峰值稳定性。
> - Q: 下游消费失败怎么办？
> - A: **可重试**（重试 3 次），仍失败进死信/人工处理；上游不因下游失败而失败，只保证「消息至少被处理一次」。
> - Q: 怎么保证事件不丢、不重复？
> - A: 不丢靠 Producer 同步发送 + Broker 持久化 + 消费重试；不重复靠消费者**幂等**（按业务主键去重）。核心是「至少一次 + 幂等消费」。

### 「单据提交接口 P95 由 ~300ms 降至 ~60ms，P99<120ms」是什么意思？你如何测出来的？
**回答话术：**
**含义**：P95 指 95% 的请求耗时在 60ms 内（优化后）、P99 指 99% 在 120ms 内；优化前 P95≈300ms。优化手段是把同步等待下游（报表生成、库存扣减、日志）改成**异步发消息**，主线程只做「落库 + 发消息」立刻返回。
**怎么测出来的**：
1. **接口耗时埋点**——接口入口/出口记时间，采集每次请求耗时
2. **压测**——wrk/自定义压测打一定并发与请求量
3. **分位计算**——耗时排序取 95%、99% 分位点
4. **前后对比**——同环境、同参数下异步化前后各测一轮，去掉冷启动/缓存预热影响，多次取稳定值。
***引申知识: 为什么用 P95/P99 而不用平均值——平均值被少量极慢请求拉高、也掩盖大量慢请求；分位数反映**尾部延迟**，在线服务用户感知的正是尾部。***
> [!Info] 可能的追问:
> - Q: 异步化为什么能降 P95 这么明显？
> - A: 把同步等待下游的 200-300ms 移出请求线程，主流程只剩落库 + 发消息的毫秒级操作，返回快，请求耗时的**尾部**显著下降。
> - Q: 压测结果可信吗？误差来源？
> - A: 学习/联调环境的**相对优化**结论可信，绝对值受环境影响（机器、网络、并发参数、数据量）。误差来源：冷启动、缓存预热、并发不均、其他进程干扰。控制变量 + 多次取稳定值可减小误差。

### 你的 MongoDB 只用来增量记录日志吗？记录的日志用来做什么？
**回答话术：**
不止。我把它作为**文档型存储**用于两类数据：
1. **运行/操作审计日志**——写多读少、结构易变，用 Mongo 避免高频日志写入膨胀 MySQL 核心表
2. 日志的用途：**故障排查**（回溯某次操作/异常的完整上下文）、**行为审计**（谁在何时做了什么）、**业务追溯**（对应 ERP 的「追溯」能力，追单据流转历史）。
***引申知识: 文档型 vs 关系型——日志「写多读少、结构易变、无需事务/JOIN」正是 schema-less + 可水平扩展（分片）的适用场景；放 MySQL 会高频写入膨胀核心表、竞争资源、拖慢主业务。***
> [!Info] 可能的追问:
> - Q: 审计日志怎么保证不丢？
> - A: 写日志走**独立队列异步落库**（批量 + 定期刷），关键操作同步确认；配合 WiredTiger 持久化 + 副本集，掉电不丢已确认数据。
> - Q: 日志量大怎么办？
> - A: 按时间**分片/分库**、定期归档冷数据、设置 TTL 过期；只保留最近窗口热数据，长期历史归档到对象存储/冷库。

### Nacos 在项目中到底做了什么？你是如何使用的？
**回答话术：**
做两件事：**注册中心**和**配置中心**。
**注册中心**：服务启动时向 Nacos **注册自身**（IP:port + 元数据），启动 <1s 自注册；每 5s 发心跳，异常实例 15s 判不健康、30s **自动剔除**；调用方从 Nacos 拉取实例列表做**负载均衡**（权重分发），实现多实例流量分摊与故障自愈。
**配置中心**：把数据源/中间件配置集中管理，变更时服务端推送/客户端长轮询拉到新值，**秒级生效、无需重启**。
**我的使用**：多实例服务都接 Nacos 注册发现 + 配置下发；客户端本地缓存实例列表 + 配置，注册中心短暂不可用也能**容灾降级**继续服务。
***引申知识: 注册中心是「辅助不是主链路」——客户端有本地缓存实例列表，注册中心挂了已建立的调用不受影响；这体现「注册发现要能降级」的容灾设计。***
> [!Info] 可能的追问:
> - Q: 故障剔除与负载均衡怎么做的？
> - A: 实例心跳 5s/次，异常实例 15s 判定不健康、30s 自动剔除，新请求不再路由到故障节点；调用方本地维护实例列表做负载均衡（权重分发）。
> - Q: 注册中心挂了会怎样？
> - A: 因有**本地缓存实例列表 + 容灾降级**，已建立的调用不受影响；新实例注册/变更暂时失效，恢复后重连同步。

### 你如何做到配置更改之后不用重新编译或重启服务就能让服务器使用新的数据的？
**回答话术：**
核心是**配置与代码分离 + 动态加载**：
1. 配置从代码里抽出来放到**配置文件/配置中心**（数据源、中间件、业务开关都不硬编码）
2. 程序启动读取、运行时**监听配置变化**——本地文件监听变更 + 重载回调，配置中心用「推送/长轮询拉取」
3. 业务侧对配置项注册**变更回调**（如数据源地址变化重建连接池、业务开关变化即时生效）。链路：配置变更 → 通知 → 回调更新 → 生效，全程**不重编译不重启**。
***引申知识: 与本地配置文件比，配置中心**集中管理 + 广播/长轮询**，改一处全部实例同步，还有版本管理和回滚；这是「控制面与数据面分离」思想的落地。***
> [!Info] 可能的追问:
> - Q: 配置变更时正在进行的请求怎么办？
> - A: **灰度 + 优雅过渡**：新配置只影响之后的新请求/新连接，存量请求继续用旧值（如连接池重建不影响在用的连接，等归还后按新配置重建）。
> - Q: 配置格式错误/加载失败怎么兜底？
> - A: **本地缓存 + 旧值回退**：拉取/解析失败时用上一次成功的配置继续服务，不因配置错误崩服务；校验不通过则报警并保持旧配置。

### 跨平台分布式即时通讯系统

> [!note] 简历要点：自研二进制帧、协议/业务解耦、单线程消息队列、连接池、微服务拆分、gRPC、负载均衡、跨实例路由、踢下线、离线消息、Redis ZSET 游标、消息存储分层/LSM、冷历史 ranged GET、文件上传/fileId/一致性/分片、Qt6 客户端。

**Q：为什么用自研二进制 TCP 帧协议，而不是 HTTP / WebSocket？**
A：头部开销小、可长连接复用、实时性好、便于心跳保活；相比 HTTP 每次请求带大量头部、WebSocket 帧也偏重，自定义帧（2 字节消息 ID + 2 字节长度 + JSON 载荷）更轻量，且能按业务定制消息 ID 与长度校验，**协议层与业务层彻底解耦**。

**追问1：协议层与业务层解耦体现在哪？**
A：消息 ID 枚举（服务端 `ChatMessageId` 与客户端 `RequestId`）一一对应，解析出消息 ID 后**分发到对应业务 handler**，新增消息类型只需加枚举 + 注册 handler，不改网络层。

**追问2：为什么用 JSON 做载荷而不是纯 Protobuf？**
A：本项目消息体用 JSON 便于跨端（C++/Web/可能前端）调试、可读性好；Protobuf 用于**服务端间 RPC**（更紧凑高效）。业务帧保可读、内部 RPC 保性能，是分工。

**追问3：为什么长度是 2 字节，能覆盖多大？**
A：2 字节最多 65535 字节，用于**普通消息**足够（大文件走独立通道不占消息帧）；这也是协议按业务定界的取舍——消息通道保持轻量。

**Q：并发模型怎么设计的？为什么用单线程消息队列？**
A：I/O 线程池负责收发、业务逻辑进**一个 worker 线程串行处理**，即生产者（I/O 线程）入队、消费者（worker）出队的**生产者/消费者模型**。好处：所有业务逻辑**串行化，规避多线程加锁竞争**，同一连接消息天然有序。代价是单线程瓶颈，配合多实例水平扩展摊薄。

**追问1：为什么串行化就没锁竞争？**
A：单消费者**同一时刻只处理一个任务**，任务间天然互斥，无需加锁；生产者入队用**无锁/轻量队列**（单写多读或原子 CAS）规避锁。这是「以确定性的单线程顺序换取无竞争」的经典取舍。

**追问2：单线程业务会不会是瓶颈？**
A：会是——所以用**多实例水平扩展**分摊：聊天服务可多实例，Redis 路由把不同用户分到不同实例，每实例内单线程串行，整体吞吐靠实例数扩展。

**追问3：消息有序性怎么保证？**
A：同一连接/会话的消息都进同一 worker 串行处理，天然保序；跨实例用 Redis 游标机制在同步层保证顺序。

**Q：连接池解决了什么问题？**
A：建连开销大（TCP 握手 + 认证 + 内存分配），高并发下每次建连拖垮性能。MySQL/Redis/gRPC 三层都用连接池**预建、借还复用、控制上限**，RPC 延迟能做到毫秒级。

**追问1：为什么 RPC 能做到毫秒级？**
A：连接复用避免每次握手开销 + 内网低延迟 + 消息体小，端到端链路短。毫秒级是定性描述，不追求绝对精确。

**追问2：连接池的借还与超时？**
A：借出标记在用、归还复位，超时/失效连接自动剔除重建，防止「连接已被服务端关闭但仍被复用」导致卡死。

**追问3：为什么分三层都用连接池？**
A：MySQL/Redis/gRPC 都是**外部资源**，建连成本高，统一池化是通用优化；这也体现「池化复用」这一核心思想贯穿全项目。

**Q：为什么拆成网关 / 鉴权调度 / 聊天 / 验证四个服务？**
A：各司其职、**故障隔离、可独立扩展**。网关做无状态 HTTP 接入可水平扩容；鉴权调度与聊天逻辑解耦，聊天引擎可多实例部署；验证服务独立降低主链路耦合。服务间统一 **gRPC + Protobuf** 通信。

**追问1：网关为什么无状态可水平扩容？**
A：网关不保存业务状态（会话/连接数据都在 Redis/聊天服务），所以可随意加实例做**接入层负载均衡**，是最容易扩展的一层。

**追问2：为什么服务间用 gRPC 而不是自研协议？**
A：内部服务间**高吞吐、强类型、跨语言**，gRPC（Protobuf + HTTP/2）提供类型安全、流式、多语言支持，比自研协议开发成本低、可靠性高。外部客户端才用轻量自研帧。

**追问3：一个用户请求怎么走完整个链路？**
A：客户端 → 网关（HTTP）→ 鉴权调度（校验/发 token）→ 聊天服务（gRPC）→ Redis 路由 → 目标实例推送客户端。各服务职责单一，链路清晰。

**Q：负载均衡是怎么做的？**
A：ChatServer 启动向 StatusServer 注册自身，通过 Redis 维护**在线实例与连接数**；客户端登录时 StatusServer **按连接数把请求分配到负载最低的实例**并签发 token，实现负载均衡。

**追问1：为什么按连接数而不是随机？**
A：连接数近似反映实例负载，**最不繁忙优先**比随机更均衡，避免热点实例被压垮；Redis 维护全局连接数提供跨实例视野。

**追问2：token 里带了什么？**
A：用户身份 + **分配到的目标实例信息**，客户端后续用它定位、服务端据此路由，避免每次重新调度。

**追问3：如果实例挂了，已分发的用户怎么办？**
A：实例心跳剔除 + 客户端重连时**重新调度**到健康实例；在线状态/会话数据在 Redis/存储层，可迁移恢复，实现故障自愈。

**Q：跨实例消息路由怎么保证可达？**
A：Redis 维护**用户 ID → 所在实例**的映射。发送方 ChatServer 若发现目标用户不在本实例，通过 gRPC **把消息转发到目标实例**，由目标实例推送给客户端，实现多实例下消息可达。

**追问1：为什么用户和实例映射放 Redis？**
A：需要**全局、低延迟、可查**的映射，Redis 内存读写快、天然适合；所有实例都能访问，作为消息路由的「全局表」。

**追问2：实例挂了映射怎么更新？**
A：临时会话数据 + 心跳检测，实例下线时更新/清理其用户映射，客户端重连后重新绑定新实例。

**追问3：同一用户多端在哪几个实例？**
A：每端一个连接可能落在不同实例，映射可维护**用户 → 多实例集合**，消息向所有实例广播推送，实现多端同时收。

**Q：多端登录踢下线怎么做的？**
A：同账号再次登录时，服务端通过 gRPC **通知旧连接所在实例**，把旧会话关闭踢下线，防止同账号多端同时在线造成消息错乱。

**追问1：为什么同一账号只允许一端在线？**
A：避免同一账号多端同时消费/修改状态造成**消息错乱**（如已读、消息归属冲突），新登录踢旧会话保证状态唯一。

**追问2：新旧连接并发登录怎么避免竞态？**
A：登录校验串行化（Redis 锁/原子操作），后登录者原子地「取代」旧会话注册，旧实例收到通知后关闭连接；保证最终一端在线。

**追问3：怎么知道旧连接在哪个实例？**
A：Redis 用户→实例映射，踢下线时查映射定位旧实例再通知。

**Q：离线消息怎么处理，为什么用 Redis？**
A：在线用户实时推送；**离线用户消息暂存 Redis**，登录后服务端批量补发，保证不丢失。用 Redis 因为内存读写快、支持 **TTL 自动过期**，适合短期高频读写；MySQL 用于持久化强关系数据。

**追问1：离线消息存 Redis 会不会丢？**
A：Redis 是**短期缓存**，有 TTL 和持久化策略；长期/权威历史另有存储层，离线窗口较短可接受缓存丢失风险，或开启 AOF 提高持久性。

**追问2：登录后怎么补发？**
A：登录时查该用户离线队列，**按序批量补发**，补发后清理/更新游标，客户端一次拉全后进入增量同步。

**追问3：离线消息和在线推送边界？**
A：连接在=在线实时推；连接断/不在=入离线队列。靠**连接状态 + Redis 队列**判断，消息不因接收方离线而丢弃。

**Q：多端消息同步 / 增量拉取怎么做？**
A：用 **Redis 有序集合（ZSET）+ 消息游标**维护每端已读位点。客户端带游标请求「游标之后的消息」，服务端按序返回 ZSET 中 **score 大于游标**的成员，消费后更新游标，避免全量重传、不重不漏。配合客户端 SQLite 本地缓存 + Qt 信号槽异步分发，界面不阻塞。

**追问1：为什么用 ZSET 而不是 List？**
A：ZSET 按 **score（消息序号/时间）排序**且天然支持「取大于某 score」的范围查询（增量），List 只能按索引/从头 pop，难做任意游标增量。ZSET 正是为「按序 + 范围」设计的。

**追问2：游标是什么，存在哪？**
A：游标是**每端的已读位点**（最大已消费消息序号），存在服务端（Redis/DB）记录各端进度；客户端拉取后更新，实现**每端独立进度**、互不干扰。

**追问3：客户端本地 SQLite + 服务端权威怎么分工？**
A：**本地 SQLite 是缓存**（离线可看、浏览/搜索快、本地优先读取），**服务端是权威真相**（多端同步、换设备、备份靠它）。客户端带游标向服务端增量同步（「给我 seq N 之后的」），本地缓存和服务端权威互补两层。

**Q：MySQL 在 IM 里存什么？**
A：存**强关系、强事务的结构化数据**：用户账号、好友关系、会话/群组、群成员、好友申请等。它管「人和关系」，不管「消息流水」。

**追问1：用 MySQL 存聊天消息是不是不规范？**
A：是反模式，正规 IM 不用 MySQL 做海量消息的最终存储。因为 MySQL 是**行式 + B+Tree**，擅长随机更新、事务、关联查询；消息是 **append-heavy 追加写流水**、只需按「会话 + 时间序」范围扫描，且海量消息单表膨胀、分库分表成本高。学习项目用它验证全链路合理，关键要知道「该不该、理想怎么做」。

**追问2：IM 聊天消息一般怎么存储？**
A：按**热/温/冷分层**。在线消息直接推送、服务器不落库或仅异步记录；离线消息存 Redis（TTL）登录补发；长期历史放**对象存储 + 索引**（或 LSM 存储如 HBase/Cassandra/TiDB）。腾讯等做法是 SeqSvr 分配全局有序序号 + 内容落对象存储 + 索引库，客户端按序号增量拉取。

**追问3：什么是 LSM？为什么适合消息存储？**
A：LSM-Tree 把**随机写转成顺序写 + 批量落盘**，顺序写、写放大低，适合高吞吐追加写和范围扫描，对应 HBase/Cassandra/TiDB。能讲出「**顺序写 vs 随机写**」的区别就够。

**Q：冷历史存对象存储，查询时不是要下载所有文件再解析吗？**（关键深度追问）
A：不会。历史消息按序追加写成对象存储的**追加日志文件（append-only log）**，同时维护**元数据索引** `(会话, 消息序号) → (对象 key, 字节偏移, 长度)`。用户拉某段历史先查索引定位文件 + 具体字节区间，再用对象存储的 **ranged GET** 只下载需要的字节，绝不全量下载。

**追问1：为什么用追加日志文件而不是每条消息一个对象？**
A：写是**顺序追加**到文件尾部，成本低、吞吐高；文件不可变、只追加，契合对象存储（对象不可变、多副本由存储层保证）；**文件数少**，索引小、列举请求少。

**追问2：冷历史的一致性怎么保证？**
A：**日志当真相源、索引当可重建的投影**。固定顺序：先追加日志并等确认，再提交索引。若中间崩溃，结果是「有日志、无索引」，不丢消息，可从日志重放重建索引。热→冷过渡要等冷日志确认 + 客户端游标 ack 才允许缓存过期。这正是 **WAL / Kafka** 的思路。

**追问3：这套机制和 LSM 的关系？**
A：Redis 热层 ≈ **memtable**、对象存储追加日志 ≈ **不可变 SSTable**、元数据索引 ≈ **稀疏索引**、日志合并清理 ≈ **compaction**。本质上就是 **LSM 在系统层的实现**。

**Q：文件上传是怎么做的？**
A：客户端把文件通过 HTTP 上传到网关，网关用**全局唯一 UUID 作为 fileId** 命名落盘，写一个 **.meta 侧车文件**记录原始文件名和大小；返回 fileId 给客户端，**聊天消息里只传 fileId 不传二进制**，下载时用 fileId 反查。文件大小在网关做上限校验。行业大文件另有两种方案：**预签名 URL 直传**（客户端直传对象存储，绕过应用服务器）、**分片上传**（断点续传、秒传）。

**追问1：为什么消息里只传 fileId 不传二进制？**
A：消息通道保持轻量、不阻塞实时性；**文件走独立通道，收发解耦**。

**追问2：上传如何保证分布式一致性？**
A：多实例部署时文件若只落某实例本地盘，其他实例读不到，所以要把文件放**统一对象存储层**（MinIO/S3），所有实例读写同一存储，一致性由存储层兜底。应用层上传本质是「写文件 + 写元数据」两步，靠**顺序（先写对象存储确认，再写元数据）+ 幂等 fileId** 避免孤儿数据；元数据写失败则标记未完成由后台回收，避免「有文件无记录」。

**追问3：大文件怎么保证可靠传输？**
A：**TCP 已保证字节级可靠**（重传、去重、保序）——先说这句体现分层认知。应用层再补三件：
1. **分片断点续传**（网络中断不用整文件重传，每片带偏移量）
2. **完整性校验**（每片/整体 MD5/CRC32，服务端重算比对）
3. **hash 秒传 + 并发分片**提升带宽利用。

**Q：Qt6 客户端你做了哪些，涉及哪些机制？**（投 Qt 岗必问）
A：IM 客户端用 Qt6 实现，涉及：**信号槽机制**做界面线程与业务线程的解耦（消息在工作线程入队、界面线程通过信号槽消费，界面不卡顿）；**SQLite**（Qt SQL）做本地文本消息缓存（离线可看、浏览快）；**跨平台编译**（CMake + Qt 支持多平台）；异步分发保证 UI 响应。理解 Qt 的信号槽、事件循环、Model/View。

**追问1：信号槽机制的原理？**
A：Qt 的**信号槽**是对象间解耦的通信机制：信号是「发生了某事件」的通知，槽是处理函数；通过 `connect` 把信号连到槽。关键特性：**跨线程安全**（队列连接把槽投递到目标线程事件循环，而非直接调用）、**类型安全**、一对一/一对多。内部用元对象系统（MOC 生成代码）实现连接与调用。

**追问2：信号槽的连接方式（直连 vs 队列）怎么选？**
A：**直连**（Direct）同线程直接调用；**队列**（Queued）跨线程通过**事件循环**投递。跨线程默认队列连接——这正是消息「在工作线程 emit 信号、界面线程收到槽」的实现，保证界面线程不被占用。还有阻塞队列连接（跨线程同步等待）。

**追问3：为什么界面操作必须放界面线程？**
A：Qt UI 不是线程安全的，**所有控件操作必须在 GUI 线程**（主线程事件循环）。业务/网络线程只做数据处理，通过信号槽把结果**投递回界面线程**再更新控件，否则界面卡顿/崩溃。这就是「消息在工作线程入队、界面线程消费」的架构保证。

**Q：Qt 的 Model/View 是什么，你用在哪？**
A：Model/View 是 Qt 把**数据与显示分离**的架构：Model 提供数据（QAbstractListModel 等），View 负责显示（QListView/TableView），通过**索引**访问数据。数据变化用信号通知视图刷新，**增删改只更新局部**不用整表重绘。适合消息列表、会话列表这类数据驱动的界面。

**追问1：为什么用 Model/View 而不是直接操作控件？**
A：数据与显示解耦，**数据变化自动反映到视图**、局部刷新性能好、一套 Model 可对接多个 View，代码更清晰。直接拼控件在大数据量下性能差、难维护。

**追问2：自定义 Model 要重写哪些方法？**
A：继承 `QAbstractListModel` 要重写 `rowCount()`、`data()`（返回指定索引的数据角色如 DisplayRole），加数据时 `beginInsertRows/endInsertRows` 通知视图，实现动态列表。

**追问3：信号槽和事件循环的关系？**
A：Qt 应用跑在一个**事件循环**里（`QCoreApplication::exec`），事件（用户输入、定时器、队列信号）进入队列被逐个处理；跨线程信号槽就是**投递一个事件**到目标线程的队列，由该线程事件循环处理。理解事件循环是理解 Qt 异步的关键。

**Q：跨平台是怎么做到的？**
A：Qt 是**跨平台框架**，封装了各平台底层（窗口、事件、I/O），同一份 C++ 代码 + Qt API 可用 CMake 在 Windows/Linux/macOS 编译运行；项目服务端用 C++（Asio/协程）也是跨平台的。部署做到「写一份、处处编译」。

**追问1：跨平台有哪些坑？**
A：**路径分隔符**、**平台特有 API**、字节序/编码、文件系统差异、不同编译器的 C++ 支持差异。要靠**抽象层 + 条件编译 + CI 多平台验证**处理，CMake Presets 按平台配置。

**追问2：Qt Widgets 和 QML 区别？**
A：Widgets 用 C++ 代码/布局，适合**桌面工具、性能、复杂控件**；QML 用声明式语言，适合**现代动画 UI、快速开发、移动/触控**。本项目客户端用 Widgets 路线（C++ 为主）。

**追问3：Qt 和原生开发的取舍？**
A：Qt 一次开发多平台部署，省成本但体积/性能略逊原生、非官方原生观感；原生性能/观感最优但平台重复开发。桌面跨平台场景 Qt 是成熟选择。

### 你如何在客户端和服务端中使用自定义的 TCP 帧协议？它们二者如何借助自定义的协议通信？
**回答话术：**
**协议定义**：固定帧头 `2 字节消息 ID + 2 字节长度 + JSON 载荷`。消息 ID 是**协议语义**（对应某个业务操作，客户端 `RequestId` 与服务端 `ChatMessageId` 一一对应）；长度字段标记载荷字节数；载荷是 JSON 承载业务数据。
**客户端**：业务层把操作封装成「消息 ID + JSON」，序列化成帧字节流经 socket 发出；收包按帧头长度字段**循环切帧**，解析出消息 ID 分发给对应 handler。
**服务端**：同样按帧定界解析，把消息 ID 路由到对应业务处理；响应也组装成同样格式的帧回给客户端。
**二者如何通信**：都遵守同一份「帧格式 + 消息 ID 映射表」协议约定，客户端发什么格式、服务端按什么格式解析，天然对称；半包靠长度字段 + 缓冲解决。
***引申知识: TCP 是字节流无消息边界，必须应用层定界——长度前缀比固定长度（浪费空间）和分隔符（载荷含分隔符会破坏边界）更可靠；客户端与服务端共用同一份协议定义，是「协议先行」的体现。***
> [!Info] 可能的追问:
> - Q: 为什么用长度字段而不是固定长度或分隔符？
> - A: 固定长度浪费空间、不适配变长 JSON；分隔符若载荷里含该字符会破坏边界；**长度前缀**精确知道载荷字节数，最可靠，还能提前分配缓冲。
> - Q: 为什么用 JSON 做载荷而不是纯 Protobuf？
> - A: 本项目消息体用 JSON 便于**跨端调试、可读性好**；Protobuf 用于**服务端间 RPC**（更紧凑高效）。业务帧保可读、内部 RPC 保性能。
> - Q: 粘包/拆包怎么处理？
> - A: 接收端维护**接收缓冲**，先读 2 字节长度，再按长度读完整载荷；不够就是半包，留缓冲等下次 recv 继续拼；一次可能多帧则循环处理。

### 你为什么要采用微服务架构？这样一个应用程序多个进程是否在浪费资源？
**回答话术：**
**为什么用**：
1. **故障隔离**——聊天、鉴权、验证任一服务崩了不影响其他
2. **独立扩展**——聊天服务是高负载热点可单独多实例水平扩展，网关无状态可随意扩容
3. **职责清晰**——每服务单一职责、独立部署发布
4. **团队协作**——不同服务可并行开发。
**多进程是否浪费资源**：有一定开销（进程内存、IPC），但**可接受且值得**：
1. 每个服务实例资源占用可控（热点按需扩展、轻量服务保持少量实例）
2. 相比资源开销，**故障隔离和扩展性收益远大于成本**
3. 同机可共存多个轻量实例，且按负载动态扩缩容，不算浪费。学习项目规模小，微服务的价值更多在于**验证架构能力和工程思维**。
***引申知识: 微服务的成本本质是「把单体的复杂度转移为分布式的复杂度」——网络故障、数据一致性、链路追踪、运维；规模小时单体更快，业务复杂/需独立扩展时才值得拆分。***
> [!Info] 可能的追问:
> - Q: 什么规模适合微服务？
> - A: 业务复杂、团队大、需要独立扩展/发布时；单体够用时用微服务是过度设计。本项目用它验证架构能力。
> - Q: 微服务的缺点？
> - A: 分布式复杂度（网络故障、数据一致性、链路追踪）、运维成本、服务间调用延迟。需要网关、注册中心、监控配套。
> - Q: 怎么拆分服务是合理的？
> - A: 按**业务边界/变更频率/资源特征**拆：独立部署、独立扩展、故障域隔离。本项目按职责（网关/鉴权/聊天/验证）拆分，聊天是扩展热点。

### 鉴权防伪造会话是如何做到的？
**回答话术：**
**核心是让会话不可伪造**：
1. 登录成功后服务端签发**签名 token**（JWT：Header+Payload+Signature，签名用密钥/私钥），token 内含用户 ID、过期时间
2. token 的签名**防篡改**——客户端改 payload 任何字段，验签即失败
3. 客户端后续请求带 token，服务端**校验签名 + 过期时间 + 权限**，通过才建立/放行会话
4. 配合**防重放**（token 有效期 + 关键操作绑定随机数/时间戳）与**用户态校验**（每请求查用户是否合法）。
***引申知识: 鉴权防伪造的本质是「签名保证完整性、过期保证时效、权限保证范围」；JWT 的 Signature 让 token 不可篡改（但 payload 可读），所以敏感信息不能进 payload。***
> [!Info] 可能的追问:
> - Q: 为什么改了 payload 就失效？
> - A: Signature = 对 (Header+Payload) 用密钥签名；任何改动都导致重算的签名与 token 里的签名不一致，验签失败。token **不可篡改**（不是不可读，payload 是 Base64 可解码）。
> - Q: token 被窃取/重放怎么办？
> - A: 设**短有效期**（过期作废）+ **refresh token** 刷新；高风险操作绑定设备/IP/随机 nonce 校验；必要时服务端维护**黑名单**吊销。
> - Q: 鉴权服务挂了会影响主链路吗？
> - A: 会——所以鉴权独立成服务 + 可扩展，且 token 验签是**无状态计算**（不查库）吞吐高；必要时可本地缓存公钥/验签结果降级。

### 离线消息落登录后批量补发是如何做到的？
**回答话术：**
**在线**用户消息实时推送；**离线**（连接断开）时，发送方把消息写入 Redis **离线队列**（按用户）暂存。用户登录时：
1. 服务端检测该用户有未消费的离线消息
2. **按序批量补发**（按消息序号从小到大一次或分批发）
3. 补发完成后**更新游标/清理离线队列**，此后进入增量同步。Redis 内存读写快 + TTL 自动过期，适合短期暂存。
***引申知识: 离线补发的关键是有序 + 可重入——队列按消息序号有序存储（Redis ZSET 或有序 List），补发按序取；客户端本地 SQLite 缓存已收消息，游标保证「不重不漏」。***
> [!Info] 可能的追问:
> - Q: 为什么离线消息存 Redis 而不存 MySQL？
> - A: 离线消息是**短期高频读写 + TTL 过期**场景，Redis 内存读写微秒级、天然支持过期；MySQL 用于持久化强关系数据。
> - Q: 补发时顺序怎么保证？
> - A: 离线队列按**消息序号**有序存储（Redis ZSET 或有序 List），补发按序号从小到大取，和在线时的消息顺序一致。
> - Q: 补发中途连接断了怎么办？
> - A: 游标机制保证**可重入**——下次登录从上次补发到的游标继续，不重不漏；已补发消息写入客户端本地 SQLite，避免重复消费。

### 多端登录自动踢下线是如何做到的？
**回答话术：**
**同一账号只允许一端在线**：
1. 登录时服务端检查该用户是否已有在线会话
2. 若有，通过**用户→实例映射**（Redis）定位旧连接所在实例，gRPC 通知该实例**关闭旧会话**
3. 旧连接被关闭，同时新登录注册成功，**确保最终只有新会话在线**。踢下线动作要**串行化**（Redis 锁/原子操作），避免新旧并发登录竞态。
***引申知识: 竞态窗口在于「更新映射」和「关闭旧连接」不是原子操作——用 Redis 原子操作把「检查在线 → 标记新会话 → 通知旧会话」做成原子的，配合会话版本号防误杀旧通知。***
> [!Info] 可能的追问:
> - Q: 为什么同一账号只允许一端在线？
> - A: 避免同一账号多端同时消费/修改状态造成**消息错乱**（已读、消息归属冲突），新登录踢旧会话保证状态唯一。
> - Q: 并发登录怎么避免竞态？
> - A: 登录校验**串行化**（Redis 原子操作/锁），后登录者原子地「取代」旧会话注册，旧实例收到通知关闭连接；保证最终一端在线。
> - Q: 怎么知道旧连接在哪个实例？
> - A: Redis **用户→实例映射**，踢下线时查映射定位旧实例再通知。

### 热文件从服务器缓存下载，冷文件收发采用网关转发落盘 + 对象存储混合模式是如何做到的？
**回答话术：**
这是**按访问频率分层的文件存储**策略：
**热文件（近期高频访问）**：从**服务器缓存**（本地磁盘/内存缓存区）直接下载——近期上传/频繁访问的文件留在近端，路径短、响应快。
**冷文件（长期/低频）**：**网关转发落盘 + 对象存储混合**——上传时客户端发给网关，网关按文件落盘并转存**对象存储**（统一存储层）；下载时网关先查本地，未命中从对象存储取。混合模式平衡了「近端快」和「存储层统一、可水平扩展」。
***引申知识: 冷文件放对象存储的核心原因是**多实例共享**——文件只落某实例本地盘其他实例读不到；对象存储（MinIO/S3）所有实例读写同一存储，一致性由存储层兜底，还提供副本与扩展性。***
> [!Info] 可能的追问:
> - Q: 怎么判定热还是冷？
> - A: 按**访问频率/最近访问时间**（LRU 思想）：近期访问的留在缓存/近端，长期未访问的迁移到冷层；可配阈值（如 30 天未访问转冷）。
> - Q: 热层缓存命不中怎么办？
> - A: 回源——从冷层/对象存储取，取回后按需提升为热层缓存，同时更新索引；本质是「缓存未命中回源」的标准模式。

### 所有文件收发记录日志确保索引可重建是如何做到的？
**回答话术：**
**文件与元数据分离 + 全量记录**：每次文件收发（上传/下载/转发）都**记录完整日志**——fileId、文件名、大小、对象 key、字节偏移、时间、操作类型。这些日志本身就是**可重建的索引数据**：如果主索引（数据库/内存映射）丢失或损坏，**从日志重放**即可重建「fileId → 存储位置」的完整索引。
***引申知识: 这是「**日志是真相源、索引是投影**」思想的落地——日志是权威、索引可丢弃重建；先写文件确认成功再写日志/索引，保证索引可恢复、文件不成为孤儿。***
> [!Info] 可能的追问:
> - Q: 为什么要设计「索引可重建」？
> - A: 索引可能因故障/误删/迁移丢失，若不可重建，文件就成了孤儿——有数据找不到、浪费存储。日志重放让索引**可恢复**。
> - Q: 日志重放怎么保证不漏？
> - A: 日志**追加写、顺序持久化**（类似 WAL），重放时按 fileId 收敛到最新状态；配合幂等（同一 fileId 记录覆盖不重复建），保证重建结果正确。

### 落盘数据借助 flusher 批量迁移是如何做到的？
**回答话术：**
flusher 是一个**批量刷盘/迁移组件**，核心思想：**把零散的落盘操作合并成批量、有序、异步**。机制：
1. 数据先进**内存缓冲**（待落盘队列）
2. flusher 按**批量阈值 + 定时**触发（如攒够 N 条或每 M 毫秒），把一批数据**顺序写盘**
3. 批量迁移到目标存储时，按批次**原子推进游标/水位**，记录「已迁移到哪个位置」
4. 迁移完成后更新索引，崩溃可从水位**断点续迁**。
***引申知识: 批量 vs 逐条的核心收益是「**顺序写 + 减少 IO 次数**」——逐条落盘系统调用/磁盘 IO 次数多、吞吐低；批量合并成顺序大块写，吞吐提升一个量级。***
> [!Info] 可能的追问:
> - Q: 批量迁移怎么保证不丢数据？
> - A: **先落盘/写源、再推进水位**：数据先持久化成功才移动水位；崩溃后从水位恢复继续迁，已迁的不重迁（幂等）。本质是「水位是进度真相」。
> - Q: 批量失败/部分成功怎么办？
> - A: 按批重试（批内数据按序重写），记录失败批次待重放；水位只在实际成功后推进，保证「要么整批成功、要么整批重来」，不产生中间状态。

### 如何使用 flusher 做数据迁移？
**回答话术：**
具体使用流程分四步：
1. **注册数据源与目标**：告诉 flusher「从哪个缓冲区/文件迁到哪个存储（如本地盘 → 对象存储）」，并约定**批次大小与触发间隔**
2. **投递数据**：业务侧把待迁移数据写入 flusher 的内存缓冲（它内部按「批量阈值 + 定时」攒批）
3. **触发批量迁移**：缓冲攒够一批或到定时点，flusher 把这批**顺序写**到目标，写成功后**推进迁移水位**（记录已迁到哪条）
4. **断点续迁与重试**：迁移中途崩溃，重启后从**水位**继续；失败批次按序重试；迁移完成后**更新索引/清理源数据**。
***引申知识: flusher 的本质是「批量、有序、可断点续传的迁移执行器」——使用方只需要投递数据 + 注册目标，批量节奏、水位、重试都由组件负责；水位设计类似 Kafka 的 offset / 数据库的 WAL LSN。***
> [!Info] 可能的追问:
> - Q: flusher 和直接写存储有什么区别？
> - A: 直接写是「逐条、实时、随机」，每次都要 IO；flusher 是「攒批、定时、顺序」，把多次小 IO 合并成一次大 IO，吞吐高、对存储压力小，且水位机制保证可恢复。
> - Q: 迁移延迟能接受吗？
> - A: 能——这类数据是「落盘/归档类」不要求实时可见，攒批引入的秒级延迟可接受；实时性要求高的数据不走 flusher，走直接写。

# 通用项目面试题
> [!note] 这两题是跨项目的高频深挖题，每题准备**三个项目各自的版本**。回答要领：**不编造**，但说出「这个位置很可能泄漏 / 这个 bug 很可能长什么样」是允许且有价值的——面试官想看的是你对风险点的敏感度和排查方法论。

### 项目中有没有碰到过内存泄漏，你是怎么解决的？
#### 高性能协程网络服务框架
**回答话术：**
本项目内存泄漏风险最高的是**协程栈**。协程用 `malloc` 分配独立栈（默认 128KB），由 Fiber 对象析构负责 `free`。**最容易泄漏的写法**：协程的回调 lambda 里捕获了持有该协程的 `shared_ptr`（`Fiber::ptr`），形成**循环引用**——协程对象引用栈内存、lambda 引用协程对象，双方互相持有，引用计数永远到不了 0，析构不执行，**128KB 栈内存永久泄漏**；协程创建多、泄漏就线性增长。
**排查方法**：
1. **ASan/valgrind**——报告大量未释放的 128KB 块、指向 fiber.cc 分配点
2. **监控协程存活数**——调度器记录 `new Fiber` 与析构计数，长期运行数字只涨不跌就是泄漏
3. `gdb` 看存活 Fiber 的引用计数/持有链。
**解决**：
1. 回调里捕获**裸指针/weak_ptr**，或确保协程结束（TERM）后**主动 reset 自身引用**
2. 约定协程内不捕获持有自身 `shared_ptr` 的长生命周期对象
3. 诊断期做**循环引用检测**（把引用计数打日志）。
另外 `iomanager` 的 `FdContext` 是裸 `new/delete`，**事件注册后未注销**会导致 fd 上下文泄漏——排查用 `ls /proc/PID/fd` 看 fd 数只涨不跌；解决是注册/注销成对 + 析构清理。
***引申知识: shared_ptr 循环引用是最典型的 C++ 内存泄漏——A 持 B、B 持 A 时计数互不为 0、析构永不触发，`weak_ptr` 不增加计数可破环；排查工具链是「ASan 报点 → valgrind 复核 → 对象计数/资源计数找趋势」。***
> [!Info] 可能的追问:
> - Q: 为什么循环引用会泄漏内存？
> - A: shared_ptr 靠引用计数决定释放，A 持 B、B 持 A 时计数互不为 0，析构永不触发；weak_ptr 不增加计数可打破环。协程栈是 128KB 堆内存，环不破则永不 free。
> - Q: valgrind 和 ASan 的区别？
> - A: valgrind 动态二进制插桩，慢（10-20 倍）但无需重编译；ASan 编译期插桩，快、报错精确（越界/泄漏/use-after-free），需 `-fsanitize=address` 重编。项目用 ASan 定位 + valgrind 复核。
> - Q: 怎么在不停服的情况下发现泄漏？
> - A: 监控**内存 RSS 与对象计数**（协程数、连接数、fd 数），趋势性上涨即泄漏信号；配合定期 dump 堆、按分配点聚合（`mtrace`/`heaptrack`）定位来源。

#### 跨平台分布式即时通讯系统
**回答话术：**
本项目泄漏风险最高的是**连接会话（ChatSession）的循环引用**。会话类继承 `enable_shared_from_this`，内部把 `shared_from_this()` 捕获进 **Asio 异步回调**（读写完成回调），同时会话又持有 socket——形成「会话持 socket、socket 回调持会话」的环；连接断开后回调不主动解除，**引用计数不为 0，会话对象不销毁**，每次连接都泄漏一个会话 + socket。
**排查方法**：
1. **监控在线连接数 vs 会话对象数**——连接断开后对象数不回落即泄漏
2. ASan/valgrind 报未释放的 ChatSession 块
3. `gdb` 看断连后会话引用计数/回调持有链。
**解决**：
1. 连接关闭时**主动解环**——`socket.shutdown/close` 后**清空所有挂着的回调**（回调捕获的 `self.reset()`），断开循环
2. 用 **weak_ptr** 捕获会话，回调里 `lock()` 成功才处理（对象已销毁则跳过）
3. 设计显式的 `close()` 流程，析构前把持有的回调/队列清空。
**次高风险**：Qt 客户端 **QObject 未设 parent**——`new` 出来的控件/对象没指定父对象，Qt 父子树不管理它，忘了 `delete` 就泄漏；排查用 Qt 自带的 `QObject` 计数/Valgrind；解决是**统一设 parent + RAII 包装 + `deleteLater` 跨线程释放**。
***引申知识: Asio 的异步模型要求「handler 在操作完成前持有对象」，所以 handler 捕获 `shared_from_this` 是惯例——但「socket 持 handler、handler 持 socket」就成环，必须在 close 时显式断开；这是「异步框架 + shared_ptr」组合的经典陷阱。***
> [!Info] 可能的追问:
> - Q: 为什么 Asio + shared_from_this 容易泄漏？
> - A: 异步操作要求 handler 在操作完成前持有对象（否则回调时对象已析构），所以 handler 捕获 `shared_from_this`；若 socket 对象被 handler 捕获、handler 又挂在 socket 上就形成环，操作完成后环不自动断就泄漏。
> - Q: 怎么判断是泄漏还是长生命周期对象？
> - A: 看对象是否随**连接断开/任务结束**应被回收——应回收却回收不了就是泄漏；长生命周期对象是「设计上存活」的，数量稳定不涨。
> - Q: Qt 里跨线程 delete 会怎样？
> - A: 直接 delete 非 GUI 线程的 QObject 有风险（事件队列里可能还挂着它的信号）。规范做法是 `deleteLater()`——投递一个删除事件，回到对象所属线程的事件循环再销毁，安全。

#### 高性能 ERP 进销存系统
**回答话术：**
本项目泄漏风险最高的是**连接池的裸指针连接**。连接池借出 `sql::Connection*`（裸指针），要求业务用完**手动归还** `releaseConnection`——**任何异常路径/忘记归还**都会让连接「借出后不回来」，连接池里的可用连接越来越少，最终**池被耗尽**，新请求拿不到连接、系统不可用；归还逻辑出错还会**重复归还**同一连接导致并发安全问题。
**排查方法**：
1. **监控池容量/借用计数**——长期运行可用连接数只降不升即泄漏
2. ASan/valgrind 报未释放的 MySQL 连接句柄
3. 打开**借用/归还日志**看哪些路径借了没还。
**解决**：
1. **RAII 包装**——用 `SqlSession`（RAII 对象）持有连接，**析构时自动归还**，业务不再手动管理归还，异常路径也安全
2. **借用超时/回收**——超时未归还的连接强制回收重建
3. 池内连接**失效剔除**——MySQL `wait_timeout` 断连后，借出校验（SELECT 1）失败就重建，避免「借到已死连接」。
***引申知识: 裸指针 + 手动归还 = 泄漏温床；RAII 的核心是「资源获取即初始化、析构即释放」，作用域结束（含异常栈展开）析构必然执行，异常安全；这是 C++ 资源管理的第一原则。***
> [!Info] 可能的追问:
> - Q: RAII 怎么保证异常安全？
> - A: RAII 对象析构在作用域结束（含异常栈展开）时必然执行，连接在析构里归还，所以**无论正常返回还是抛异常都能归还**。
> - Q: 连接池耗尽的表现和危害？
> - A: 新请求获取连接阻塞/超时失败，接口大面积报「连接池已满」，DB 可能没被打爆但应用层先不可用——池耗尽比连接泄漏更难排查，因为报错在远端。
> - Q: MySQL 连接为什么会被 wait_timeout 断掉？
> - A: MySQL 服务端对空闲超过 `wait_timeout`（默认 8 小时）的连接主动关闭，池里借出的连接可能已被服务端断开，复用会报「connection lost」；解决是借出时校验 + 保活 ping。

### 项目中遇到过最难解决的 Bug 是什么？如何排查和解决的？
#### 高性能协程网络服务框架
**回答话术：**
最难的是**协程挂死：某条连接彻底无响应，同线程其他协程也被拖住**。
**现象**：压测时部分连接超时，日志显示这些协程永远停在「等待事件」状态，调度器不再调度它们。
**排查过程**：
1. 先怀疑网络——抓包发现请求已到但无响应，排除
2. 在挂死协程处 `gdb` 断点看状态——协程处于 WAIT，等待的 fd 事件一直没来
3. 查 `fd_manager`——发现该 fd **没注册到 IOManager**（或注册了但 epoll 事件被覆盖丢失）
4. 定位根因：**hook 后的 `read` 在 fd 注册失败/事件竞争丢失时，协程挂起等事件、事件永不触发**，形成永久等待。
**解决**：
1. hook 入口**强校验**——fd 未成功注册到 IOManager 时**不走协程化**，直接调真实 syscall，杜绝「挂起等一个不会来的事件」
2. 所有等待加**超时兜底**——事件超时强制唤醒协程返回错误
3. 调度器加**协程状态监控**（WAIT 超时告警）。
**收获**：这是「阻塞即让出」模型的核心边界问题，让我深刻理解了**让出必须配对「一定会到来的唤醒」**（要么事件、要么超时），否则就是永久挂起。
***引申知识: 异步编程的正确性边界是「每个等待都必须有明确的唤醒来源」——事件 OR 超时；排查这类问题的路径是「现象（无响应）→ 排除网络 → 看等待状态 → 查等待的事件为何不来 → 定位注册/竞争丢失」。***
> [!Info] 可能的追问:
> - Q: 为什么协程挂死会连累同线程其他协程？
> - A: 协程本身挂起不影响别的协程，但如果挂死占着**调度循环的关键路径**（如等待队列操作/锁），或协程占着资源不归还，调度循环被卡住就会波及同线程其他协程。
> - Q: 怎么用 gdb 确认是死锁还是挂起？
> - A: `thread apply all bt` 看所有线程栈：都卡在锁上 = 死锁；协程停在用户态事件等待点、线程本身空闲 = 协程挂起。再看挂起协程等的事件是否可能触发。
> - Q: 超时兜底怎么选时间？
> - A: 覆盖业务正常耗时上限（如连接超时 30s、读写 5s），太短误杀正常请求、太长拖慢故障恢复；可配置化，线上按场景调。

#### 跨平台分布式即时通讯系统
**回答话术：**
最难的是**多端登录踢下线的竞态导致消息错发/会话泄漏**。
**现象**：同一账号快速在 A 端登录、B 端登录时，偶尔出现：A 端没被踢但消息只发到 B；或踢下线的通知丢失，A/B 都显示在线，消息错乱。
**排查过程**：
1. 复现——固定「A 登录 → 立即 B 登录」的时序能稳定触发，确认是**竞态**而非逻辑错误
2. 看日志——发现「踢下线 gRPC 通知」和「新登录注册」**没有顺序保证**：B 注册成功时，A 的踢下线通知还没到 A 实例，或到了但 A 会话已因别的原因断开
3. 定位根因：**用户→实例映射的更新和旧会话关闭不是原子操作**，两个动作之间有窗口，期间的请求路由到错误实例。
**解决**：
1. 登录流程**串行化**——用 Redis 原子操作（`SET NX` 或 Lua 脚本）保证「检查在线 → 标记新会话 → 通知旧会话」是原子的，后登录者必然取代旧会话
2. 踢下线通知带**会话版本号**，旧会话收到比自己新的版本就自我关闭，避免误杀
3. 消息路由加**双查**——路由前确认目标会话仍有效，避免发到已关闭会话。
**收获**：这类 bug 让我明白分布式下**「先读后写非原子」是最普遍的竞态来源**，解法要么原子化（锁/版本号），要么接受最终一致并用补偿。
***引申知识: 竞态类 bug 的排查方法论——先固定时序复现、再对关键动作加时间戳日志、必要时用分布式追踪/TSan 定位先后关系；解决靠「原子化操作」或「版本号 + 最终一致」两条路。***
> [!Info] 可能的追问:
> - Q: 为什么不是「新登录把旧的 Redis 映射覆盖掉」就完事了？
> - A: 覆盖映射只改了「路由表」，但**旧会话的 socket 还活着**——客户端可能还在用旧连接收发，必须通知旧实例**主动关闭连接**；映射更新和连接关闭两件事之间就有竞态窗口。
> - Q: 版本号怎么防误杀？
> - A: 每次登录生成递增会话版本；旧会话收到踢下线通知时比较版本，发现「通知的版本 ≥ 自己」才关闭，「版本比自己旧」说明是过期的踢下线通知，忽略——避免旧通知误杀新会话。
> - Q: 竞态问题一般怎么定位？
> - A: 不能只靠看代码，要**固定时序复现**（脚本控制操作顺序）、加**时序日志**（每个关键动作记时间戳）、必要时用 **TSan（线程）或分布式追踪**定位跨节点的先后关系。

#### 高性能 ERP 进销存系统
**回答话术：**
最难的是**批量写入事务在高峰时偶发整体回滚，且查不出直接原因**。
**现象**：月末集中开单时，批量导入偶尔整个事务回滚，报「connection lost」或「锁等待超时」，但复现困难。
**排查过程**：
1. 先看业务日志——事务里的 SQL 都正常，异常发生在**中途某条**
2. 看 MySQL 错误日志 + 慢查询——发现偶发**锁等待超时（lock wait timeout）**和**连接被断**
3. 深挖根因：一是连接池里借出的连接**被 MySQL `wait_timeout` 或主从切换断掉**，批量中途连接失效、整批回滚；二是批量事务**持锁时间过长**，与并发的其他事务互相等待。
**解决**：
1. **借出连接先校验**（SELECT 1/ping），失效连接不借出、直接重建
2. 批量事务**控制单批大小 + 分批提交**，缩短持锁时间、降低锁冲突
3. 事务内**检查连接有效性**，中途失效则**重试整批**（幂等）
4. 批量导入错峰执行，避开高峰。
**收获**：这个 bug 让我意识到「**事务的原子性既是保证也是风险**」——一旦中途任何一环失败，整批回滚；所以批量操作要控制粒度、保证连接可靠、设计重试，而不是盲目把超大批塞进一个事务。
***引申知识: 事务原子性的代价——事务越大持锁越久、锁冲突和回滚成本越高；「分批事务 + 幂等重试」把风险摊薄；连接池管理的两大坑是「忘记归还（泄漏）」和「借到已死连接（wait_timeout）」。***
> [!Info] 可能的追问:
> - Q: 为什么不把整个批量放一个事务？
> - A: 事务越大持锁越久、锁冲突和回滚成本越高、失败全盘回滚；**分批事务**把风险摊薄——一批失败只回滚该批，且可断点重续。但要配幂等（主键去重）防重复。
> - Q: 「connection lost」一般是什么原因？
> - A: MySQL 服务端主动断开（wait_timeout 空闲超时）、网络闪断、主从切换/重启、连接被 kill。排查：看 MySQL 错误日志、检查连接建立时间，借出前校验可避免复用已死连接。
> - Q: 锁等待超时怎么优化？
> - A: 缩短持锁时间（分批、少做慢查询）、**按固定顺序加锁**避免死锁、控制事务内不要有网络/外部调用、必要时读已提交隔离级别减少间隙锁。
