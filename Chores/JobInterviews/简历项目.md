# 通用项目面试题
### 项目中有没有碰到过内存泄漏，你是怎么解决的？
#### 网络服务框架
**回答话术：**
本项目内存泄漏风险最高的是**协程栈**。协程用 `malloc` 分配独立栈（默认 128KB），由 Fiber 对象析构负责 `free`。**最容易泄漏的写法**：协程的回调 lambda 里捕获了持有该协程的 `shared_ptr`（`Fiber::ptr`），形成**循环引用**——协程对象引用栈内存、lambda 引用协程对象，双方互相持有，引用计数永远到不了 0，析构不执行，**128KB 栈内存永久泄漏**；协程创建多、泄漏就线性增长。
**排查方法**：
1. **ASan/valgrind**——报告大量未释放的 128KB 块、指向 fiber.cc 分配点
2. **监控协程存活数**——调度器记录 `new Fiber` 与析构计数，长期运行数字只涨不跌就是泄漏
3. `gdb` 看存活 Fiber 的引用计数/持有链。
**解决**：
1. 回调里捕获**裸指针/weak_ptr**，或确保协程结束（TERM）后**主动 reset 自身引用**
2. 约定协程内不捕获持有自身 `shared_ptr` 的长生命周期对象
3. 诊断期做**循环引用检测**（把引用计数打日志）。
另外 `iomanager` 的 `FdContext` 是裸 `new/delete`，**事件注册后未注销**会导致 fd 上下文泄漏——排查用 `ls /proc/PID/fd` 看 fd 数只涨不跌；解决是注册/注销成对 + 析构清理。
***引申知识: shared_ptr 循环引用是最典型的 C++ 内存泄漏——A 持 B、B 持 A 时计数互不为 0、析构永不触发，`weak_ptr` 不增加计数可破环；排查工具链是「ASan 报点 → valgrind 复核 → 对象计数/资源计数找趋势」。***
> [!Info] 可能的追问:
> - Q: 为什么循环引用会泄漏内存？
> - A: shared_ptr 靠引用计数决定释放，A 持 B、B 持 A 时计数互不为 0，析构永不触发；weak_ptr 不增加计数可打破环。协程栈是 128KB 堆内存，环不破则永不 free。
> - Q: valgrind 和 ASan 的区别？
> - A: valgrind 动态二进制插桩，慢（10-20 倍）但无需重编译；ASan 编译期插桩，快、报错精确（越界/泄漏/use-after-free），需 `-fsanitize=address` 重编。项目用 ASan 定位 + valgrind 复核。
> - Q: 怎么在不停服的情况下发现泄漏？
> - A: 监控**内存 RSS 与对象计数**（协程数、连接数、fd 数），趋势性上涨即泄漏信号；配合定期 dump 堆、按分配点聚合（`mtrace`/`heaptrack`）定位来源。

#### 通讯系统
**回答话术：**
本项目泄漏风险最高的是**连接会话（ChatSession）的循环引用**。会话类继承 `enable_shared_from_this`，内部把 `shared_from_this()` 捕获进 **Asio 异步回调**（读写完成回调），同时会话又持有 socket——形成「会话持 socket、socket 回调持会话」的环；连接断开后回调不主动解除，**引用计数不为 0，会话对象不销毁**，每次连接都泄漏一个会话 + socket。
**排查方法**：
1. **监控在线连接数 vs 会话对象数**——连接断开后对象数不回落即泄漏
2. ASan/valgrind 报未释放的 ChatSession 块
3. `gdb` 看断连后会话引用计数/回调持有链。
**解决**：
1. 连接关闭时**主动解环**——`socket.shutdown/close` 后**清空所有挂着的回调**（回调捕获的 `self.reset()`），断开循环
2. 用 **weak_ptr** 捕获会话，回调里 `lock()` 成功才处理（对象已销毁则跳过）
3. 设计显式的 `close()` 流程，析构前把持有的回调/队列清空。
**次高风险**：Qt 客户端 **QObject 未设 parent**——`new` 出来的控件/对象没指定父对象，Qt 父子树不管理它，忘了 `delete` 就泄漏；排查用 Qt 自带的 `QObject` 计数/Valgrind；解决是**统一设 parent + RAII 包装 + `deleteLater` 跨线程释放**。
***引申知识: Asio 的异步模型要求「handler 在操作完成前持有对象」，所以 handler 捕获 `shared_from_this` 是惯例——但「socket 持 handler、handler 持 socket」就成环，必须在 close 时显式断开；这是「异步框架 + shared_ptr」组合的经典陷阱。***
> [!Info] 可能的追问:
> - Q: 为什么 Asio + shared_from_this 容易泄漏？
> - A: 异步操作要求 handler 在操作完成前持有对象（否则回调时对象已析构），所以 handler 捕获 `shared_from_this`；若 socket 对象被 handler 捕获、handler 又挂在 socket 上就形成环，操作完成后环不自动断就泄漏。
> - Q: 怎么判断是泄漏还是长生命周期对象？
> - A: 看对象是否随**连接断开/任务结束**应被回收——应回收却回收不了就是泄漏；长生命周期对象是「设计上存活」的，数量稳定不涨。
> - Q: Qt 里跨线程 delete 会怎样？
> - A: 直接 delete 非 GUI 线程的 QObject 有风险（事件队列里可能还挂着它的信号）。规范做法是 `deleteLater()`——投递一个删除事件，回到对象所属线程的事件循环再销毁，安全。

#### 进销存系统
**回答话术：**
本项目泄漏风险最高的是**连接池的裸指针连接**。连接池借出 `sql::Connection*`（裸指针），要求业务用完**手动归还** `releaseConnection`——**任何异常路径/忘记归还**都会让连接「借出后不回来」，连接池里的可用连接越来越少，最终**池被耗尽**，新请求拿不到连接、系统不可用；归还逻辑出错还会**重复归还**同一连接导致并发安全问题。
**排查方法**：
1. **监控池容量/借用计数**——长期运行可用连接数只降不升即泄漏
2. ASan/valgrind 报未释放的 MySQL 连接句柄
3. 打开**借用/归还日志**看哪些路径借了没还。
**解决**：
1. **RAII 包装**——用 `SqlSession`（RAII 对象）持有连接，**析构时自动归还**，业务不再手动管理归还，异常路径也安全
2. **借用超时/回收**——超时未归还的连接强制回收重建
3. 池内连接**失效剔除**——MySQL `wait_timeout` 断连后，借出校验（SELECT 1）失败就重建，避免「借到已死连接」。
***引申知识: 裸指针 + 手动归还 = 泄漏温床；RAII 的核心是「资源获取即初始化、析构即释放」，作用域结束（含异常栈展开）析构必然执行，异常安全；这是 C++ 资源管理的第一原则。***
> [!Info] 可能的追问:
> - Q: RAII 怎么保证异常安全？
> - A: RAII 对象析构在作用域结束（含异常栈展开）时必然执行，连接在析构里归还，所以**无论正常返回还是抛异常都能归还**。
> - Q: 连接池耗尽的表现和危害？
> - A: 新请求获取连接阻塞/超时失败，接口大面积报「连接池已满」，DB 可能没被打爆但应用层先不可用——池耗尽比连接泄漏更难排查，因为报错在远端。
> - Q: MySQL 连接为什么会被 wait_timeout 断掉？
> - A: MySQL 服务端对空闲超过 `wait_timeout`（默认 8 小时）的连接主动关闭，池里借出的连接可能已被服务端断开，复用会报「connection lost」；解决是借出时校验 + 保活 ping。

**回答话术：**
最难的是**协程挂死：某条连接彻底无响应，同线程其他协程也被拖住**。
**现象**：压测时部分连接超时，日志显示这些协程永远停在「等待事件」状态，调度器不再调度它们。
**排查过程**：
1. 先怀疑网络——抓包发现请求已到但无响应，排除
2. 在挂死协程处 `gdb` 断点看状态——协程处于 WAIT，等待的 fd 事件一直没来
3. 查 `fd_manager`——发现该 fd **没注册到 IOManager**（或注册了但 epoll 事件被覆盖丢失）
4. 定位根因：**hook 后的 `read` 在 fd 注册失败/事件竞争丢失时，协程挂起等事件、事件永不触发**，形成永久等待。
**解决**：
1. hook 入口**强校验**——fd 未成功注册到 IOManager 时**不走协程化**，直接调真实 syscall，杜绝「挂起等一个不会来的事件」
2. 所有等待加**超时兜底**——事件超时强制唤醒协程返回错误
3. 调度器加**协程状态监控**（WAIT 超时告警）。
**收获**：这是「阻塞即让出」模型的核心边界问题，让我深刻理解了**让出必须配对「一定会到来的唤醒」**（要么事件、要么超时），否则就是永久挂起。
***引申知识: 异步编程的正确性边界是「每个等待都必须有明确的唤醒来源」——事件 OR 超时；排查这类问题的路径是「现象（无响应）→ 排除网络 → 看等待状态 → 查等待的事件为何不来 → 定位注册/竞争丢失」。***
> [!Info] 可能的追问:
> - Q: 为什么协程挂死会连累同线程其他协程？
> - A: 协程本身挂起不影响别的协程，但如果挂死占着**调度循环的关键路径**（如等待队列操作/锁），或协程占着资源不归还，调度循环被卡住就会波及同线程其他协程。
> - Q: 怎么用 gdb 确认是死锁还是挂起？
> - A: `thread apply all bt` 看所有线程栈：都卡在锁上 = 死锁；协程停在用户态事件等待点、线程本身空闲 = 协程挂起。再看挂起协程等的事件是否可能触发。
> - Q: 超时兜底怎么选时间？
> - A: 覆盖业务正常耗时上限（如连接超时 30s、读写 5s），太短误杀正常请求、太长拖慢故障恢复；可配置化，线上按场景调。

#### 通讯系统
**回答话术：**
最难的是**多端登录踢下线的竞态导致消息错发/会话泄漏**。
**现象**：同一账号快速在 A 端登录、B 端登录时，偶尔出现：A 端没被踢但消息只发到 B；或踢下线的通知丢失，A/B 都显示在线，消息错乱。
**排查过程**：
1. 复现——固定「A 登录 → 立即 B 登录」的时序能稳定触发，确认是**竞态**而非逻辑错误
2. 看日志——发现「踢下线 gRPC 通知」和「新登录注册」**没有顺序保证**：B 注册成功时，A 的踢下线通知还没到 A 实例，或到了但 A 会话已因别的原因断开
3. 定位根因：**用户→实例映射的更新和旧会话关闭不是原子操作**，两个动作之间有窗口，期间的请求路由到错误实例。
**解决**：
1. 登录流程**串行化**——用 Redis 原子操作（`SET NX` 或 Lua 脚本）保证「检查在线 → 标记新会话 → 通知旧会话」是原子的，后登录者必然取代旧会话
2. 踢下线通知带**会话版本号**，旧会话收到比自己新的版本就自我关闭，避免误杀
3. 消息路由加**双查**——路由前确认目标会话仍有效，避免发到已关闭会话。
**收获**：这类 bug 让我明白分布式下**「先读后写非原子」是最普遍的竞态来源**，解法要么原子化（锁/版本号），要么接受最终一致并用补偿。
***引申知识: 竞态类 bug 的排查方法论——先固定时序复现、再对关键动作加时间戳日志、必要时用分布式追踪/TSan 定位先后关系；解决靠「原子化操作」或「版本号 + 最终一致」两条路。***
> [!Info] 可能的追问:
> - Q: 为什么不是「新登录把旧的 Redis 映射覆盖掉」就完事了？
> - A: 覆盖映射只改了「路由表」，但**旧会话的 socket 还活着**——客户端可能还在用旧连接收发，必须通知旧实例**主动关闭连接**；映射更新和连接关闭两件事之间就有竞态窗口。
> - Q: 版本号怎么防误杀？
> - A: 每次登录生成递增会话版本；旧会话收到踢下线通知时比较版本，发现「通知的版本 ≥ 自己」才关闭，「版本比自己旧」说明是过期的踢下线通知，忽略——避免旧通知误杀新会话。
> - Q: 竞态问题一般怎么定位？
> - A: 不能只靠看代码，要**固定时序复现**（脚本控制操作顺序）、加**时序日志**（每个关键动作记时间戳）、必要时用 **TSan（线程）或分布式追踪**定位跨节点的先后关系。

#### 进销存系统
**回答话术：**
最难的是**批量写入事务在高峰时偶发整体回滚，且查不出直接原因**。
**现象**：月末集中开单时，批量导入偶尔整个事务回滚，报「connection lost」或「锁等待超时」，但复现困难。
**排查过程**：
1. 先看业务日志——事务里的 SQL 都正常，异常发生在**中途某条**
2. 看 MySQL 错误日志 + 慢查询——发现偶发**锁等待超时（lock wait timeout）**和**连接被断**
3. 深挖根因：一是连接池里借出的连接**被 MySQL `wait_timeout` 或主从切换断掉**，批量中途连接失效、整批回滚；二是批量事务**持锁时间过长**，与并发的其他事务互相等待。
**解决**：
1. **借出连接先校验**（SELECT 1/ping），失效连接不借出、直接重建
2. 批量事务**控制单批大小 + 分批提交**，缩短持锁时间、降低锁冲突
3. 事务内**检查连接有效性**，中途失效则**重试整批**（幂等）
4. 批量导入错峰执行，避开高峰。
**收获**：这个 bug 让我意识到「**事务的原子性既是保证也是风险**」——一旦中途任何一环失败，整批回滚；所以批量操作要控制粒度、保证连接可靠、设计重试，而不是盲目把超大批塞进一个事务。
***引申知识: 事务原子性的代价——事务越大持锁越久、锁冲突和回滚成本越高；「分批事务 + 幂等重试」把风险摊薄；连接池管理的两大坑是「忘记归还（泄漏）」和「借到已死连接（wait_timeout）」。***
> [!Info] 可能的追问:
> - Q: 为什么不把整个批量放一个事务？
> - A: 事务越大持锁越久、锁冲突和回滚成本越高、失败全盘回滚；**分批事务**把风险摊薄——一批失败只回滚该批，且可断点重续。但要配幂等（主键去重）防重复。
> - Q: 「connection lost」一般是什么原因？
> - A: MySQL 服务端主动断开（wait_timeout 空闲超时）、网络闪断、主从切换/重启、连接被 kill。排查：看 MySQL 错误日志、检查连接建立时间，借出前校验可避免复用已死连接。
> - Q: 锁等待超时怎么优化？
> - A: 缩短持锁时间（分批、少做慢查询）、**按固定顺序加锁**避免死锁、控制事务内不要有网络/外部调用、必要时读已提交隔离级别减少间隙锁。

### 谈谈你对 Qt 信号槽机制的理解？（底层原理）
**回答话术：**
信号槽是 Qt 的核心通信机制，解耦「谁触发」和「谁处理」——一个对象发出信号，不关心谁接收；接收者的槽函数在被通知时执行，连接通过 `connect(sender, &Sender::sig, receiver, &Receiver::slot)` 建立。
底层是**元对象系统**（MOC）：带 `Q_OBJECT` 的类经 moc 预处理生成元信息，信号被翻译成保护级成员函数，执行时调用 `QMetaObject::activate` 按连接的接收者 + 槽索引查元对象表分发。连接类型决定调用方式：
- DirectConnection——同线程直接调用槽（像普通函数调用）
- QueuedConnection——跨线程时把调用**打包成事件投递到接收者所属线程的事件队列**，由该线程事件循环取出执行（异步、线程安全）
- AutoConnection（默认）——按发送/接收者是否同线程自动选 Direct 或 Queued
跨线程用 QueuedConnection 就保证「槽函数代码一定跑在接收者线程」，界面更新因此安全。
***引申知识: MOC 是「编译期代码生成」式的反射——C++ 无原生运行时反射，靠 moc 生成元信息表（方法索引、参数类型）支撑信号槽；QueuedConnection 本质是「把一次函数调用序列化成事件跨线程排队」，这也是 Qt 跨线程通信不用加锁的原因。***
> [!Info] 可能的追问:
> - Q: 为什么需要 MOC 而不是纯 C++ 实现？
> - A: C++ 没有运行时反射，信号槽需要「按名字/索引查方法、动态调用」的能力，MOC 编译期扫描 `Q_OBJECT` 生成元信息表提供之；纯 C++ 用模板 + 函数指针可做简单回调，但做不到信号到多槽、类型擦除、跨线程投递。
> - Q: 信号可以连接信号吗？
> - A: 可以——信号连接信号实现链式转发；Qt5+ 信号也可直接连接 lambda。
> - Q: 一个信号连多个槽，执行顺序？
> - A: 按 connect 建立顺序执行；同线程 Direct 下同步顺序调用，跨线程 Queued 下按事件入队顺序执行。

### Qt 的事件循环（exec / 事件队列）是怎么工作的？
**回答话术：**
Qt 程序跑在**事件循环**上：`QApplication::exec()` 进入主事件循环，不断从**事件队列**取事件分发给目标对象的 `event()`。事件源包括输入设备、窗口系统、定时器，以及**跨线程投递的信号槽**（QueuedConnection 就是投递一个事件）。
分发路径：`事件队列 → QCoreApplication::notify → 目标 event() → 按类型调对应事件处理器`（mousePressEvent、paintEvent 等）。每处理完一个事件才取下一个，所以**单个事件处理耗时过长就卡界面**——长任务应放工作线程或异步。`QTimer`、动画、重绘都靠事件循环驱动，循环一旦被阻塞它们全部停摆。
事件过滤：`installEventFilter` 可在事件到达目标前先经过滤器，常用于全局拦截（滚动、热键）。
***引申知识: 「事件循环 + 事件队列」是所有 GUI 框架的骨架（Win32 消息泵同理）；嵌套 `QEventLoop`/对话框 `exec()` 开启局部事件循环，实现模态等待但不冻结界面。***
> [!Info] 可能的追问:
> - Q: 界面卡顿的根因和排查？
> - A: 根因是某个事件处理器耗时过长阻塞循环（同步网络、大循环、IO）。排查用 profiler；解决是把长任务异步化（线程 + 信号槽）、用 `QTimer::singleShot` 分批处理。
> - Q: QTimer 依赖事件循环吗？
> - A: 依赖——定时器由事件循环轮询到期时间，循环被阻塞定时器不触发；所以定时器回调里也不能做耗时操作。
> - Q: 阻塞对话框的 exec() 是死循环吗？
> - A: 不是死循环，而是进入**嵌套事件循环**——仍不断处理事件（窗口还能响应、重绘），直到对话框关闭返回。

### 谈谈你对 Ragel 的理解
@sylar coroutine web framework/src/http/http11_parser.rl L49-L257 — Ragel 文法：`machine http_parser`、Request_Line/message_header、`main := (Request|SocketRequest) @done`
@sylar coroutine web framework/src/http/http_parser.cc L123-L147 — HttpRequestParser 构造（注册 8 个回调）+ execute 调 `http_parser_execute`
@sylar coroutine web framework/cmake/utils.cmake L19-L30 — ragel `-l -C -G2` 构建期生成 .rl.cc 的规则
**回答话术：**
Ragel 是一个**状态机编译器**：把用正则/状态图描述的状态机编译成 C/C++ 代码，生成的是**确定性有限自动机（DFA）**。最常用的场景是把「协议解析」这类繁琐易错的手写工作交给「描述 + 生成」：生成的代码**无回溯、无递归、每字符 O(1)**，性能接近手写汇编同时易维护、可组合。
它与手写解析的区别在于**正确性来源**：手写是「人保证状态迁移正确」，Ragel 是「生成器保证 DFA 正确」，人只需要写对描述，特别适合 HTTP 这类状态多、边界多的协议。
***引申知识: DFA 为什么快——把正则/解析和 if-else 跳转抽象为状态机跳转表，状态转移用 CPU 跳转指令查表跳转，每个「状态 × 输入字符」唯一确定下一个状态，无回溯（NFA 才有），单遍 O(n) 扫描；所有状态在编译期确定，并且无对内存分配***
> [!Info] 可能的追问:
> - Q: Ragel 和手写解析器比有什么缺点？
> - A: 引入生成步骤（构建依赖）、生成代码可读性差、调试要理解状态机的生成逻辑。所以复杂/易错协议用生成器，简单协议手写更直接。
> - Q: 除了 HTTP 还能解析什么？
> - A: 任何**有状态迁移的字节流**：URI、JSON 字段、二进制协议帧、正则匹配本身。Ragel 的通用模型就是「状态 × 输入 → 动作」。

### 什么叫做 Ragel 有限状态机生成 HTTP/1.1？
@sylar coroutine web framework/src/http/http11_parser.rl L49-L257 — HTTP 报文的状态机文法（请求行/头部/空行/体）
@sylar coroutine web framework/src/http/http_parser.cc L143-L147 — execute 驱动生成的状态机解析
@sylar coroutine web framework/src/http/http_session.cc L10-L37 — 服务端 recvRequest 循环调用 parser->execute，支持半包续接
**回答话术：**
HTTP/1.1 报文结构本质是一个**有限状态机**：请求行（方法空格 URI 空格版本 CRLF）→ 头部若干行（key: value CRLF）→ 空行 → 消息体，每条规则对应一个**状态迁移**。我用 Ragel 把这些规则**描述成状态图/正则**，由它**生成对应的解析 C++ 代码**：运行时按字节逐个驱动状态迁移，解析出请求行字段和头部，完成一次 HTTP 报文解析。
关键点是**支持跨包（半包）状态挂起恢复**——数据不足时解析器保存状态、返回「待更多数据」，下次读满再继续，这正是配合 epoll/协程（读一次可能只有半包）的必需能力。
***引申知识: 生成的解析器 + 半包缓冲 = 一个「解析器实例」，在协程/异步场景下每次读到新字节片段喂给它即可，状态自动续接；这就是「状态机天然支持流式解析」的价值。***
> [!Info] 可能的追问:
> - Q: HTTP 解析为什么难？
> - A: 边界多：请求行/头部/空行/体的分界、CRLF 处理、头部大小上限、跨包（TCP 半包）时状态要能挂起恢复。手写容易漏边界、出 bug。
> - Q: 生成的解析器怎么和 epoll/协程配合？
> - A: 数据不足时返回「待更多数据」，协程让出；下次读满再喂给同一解析器实例，状态不丢失。

### N-M 线程调度模型是怎么实现的？
@sylar coroutine web framework/include/sylar/scheduler.h L21-L26 — 类注释：封装 N-M 协程调度器 + 线程池
@sylar coroutine web framework/src/scheduler.cc L47-L67 — start() 按 m_threadCount 建线程池，每线程跑 run()
@sylar coroutine web framework/src/scheduler.cc L127-L218 — Scheduler::run() 调度主循环（取任务 → swapIn → 按状态回队列）
@sylar coroutine web framework/include/sylar/scheduler.h L74-L105 — schedule() 模板（入队 + tickle 唤醒）
**回答话术：**
N 个系统线程构成线程池、M 个协程作为用户态任务，调度器在中间做匹配。实现分三层：
1. **任务队列**——线程安全 FIFO 存 READY 协程（互斥锁或原子 CAS）
2. **线程池**——每线程一个调度循环，从队列取协程执行，无活时用条件变量/信号量阻塞等待
3. **调度逻辑**——协程让出（yield）或结束（TERM）后回到队列或回收，`swapcontext` 在协程间切换。
**亲和 vs 迁移**：默认协程进**共享队列**，任意空闲线程可取走执行（跨线程迁移）；也可绑定固定线程（亲和）利用缓存/线程局部资源。线程用 `std::thread` 创建，启动时各自跑调度循环。
***引申知识: 与「1 线程 1 协程」相比省线程开销、与「单线程多协程」相比能用满多核；调度循环本质是「取任务 → 执行到让出 → 再取」的循环，所以叫「事件循环 + 任务队列」的调度器。***
> [!Info] 可能的追问:
> - Q: 多个线程同时取任务怎么保证安全？
> - A: 任务队列用互斥锁或原子 CAS（无锁队列）保护，取/放都是原子操作；用条件变量/信号量做「队列有货」的通知，避免忙等。
> - Q: 为什么不是 1 协程绑 1 线程？
> - A: 线程数受内存/调度开销限制，几万协程无法开几万线程；N-M 让少量线程承载海量协程，还利用多核。

### 你的 Hook 系统是怎么实现的？它主要解决了什么问题？

**回答话术：**
**解决的问题**：协程一遇到阻塞系统调用（`socket` / `read` / `write` / `connect` / `sleep`）就会卡死整条线程，同线程其他协程饿死——这是协程用于网络服务最大的坑。
**实现**：**符号替换**（拦截层 + `dlsym` 拿到真实函数指针）。进入 hook 函数先查**线程局部开关**（该线程是否启用 hook）和 **fd_manager**（该 fd 是否注册到 IOManager）：是则注册读写事件并**让出协程**，事件就绪后 IOManager 唤醒协程继续；否则直接调真实 syscall。于是「阻塞即让出、就绪即唤醒」，业务代码写同步风格、底层是异步性能。
***引申知识: hook 的语义兼容很关键——返回码、errno 必须和真实 syscall 一致，否则上层判断出错；「线程粒度开关」用线程局部变量实现，是 hook 系统能选择性生效的基础。***
> [!Info] 可能的追问:
> - Q: 如何做到只对指定线程生效（线程粒度）？
> - A: 一个**线程局部变量**标记当前线程是否启用 hook；入口先检查标志，开启走协程化异步路径，否则调真实 syscall，可自由选择哪些线程走 hook。
> - Q: hook 了 sleep，协程怎么不阻塞？
> - A: `sleep` 被替换为「注册到期定时器 + 让出协程」，到期由定时器唤醒恢复，线程本身不睡。
> - Q: hook 会不会有坑？
> - A: 1. 必须处理**非阻塞 fd**（阻塞 fd 的 read 会真的阻塞线程）
>   2. 事件注册失败/漏注册会导致协程永久挂起（经典 bug，见通用题）
>   3. 语义要与真实 syscall 完全兼容

### 如何让一个网络框架在 Linux 中有 daemon 守护进程？
@sylar coroutine web framework/src/daemon.cc L31-L67 — real_daemon：daemon(1,0) + fork 循环 waitpid 监控子进程，崩溃自动重启
@sylar coroutine web framework/src/daemon.cc L13-L14 — Config::Lookup("daemon.restart_interval", 5) 重启间隔可配置
**回答话术：**
标准 Daemon 化流程：
1. `fork()` 一次并让父进程退出，子进程成为孤儿由 init 收养
2. `setsid()` 创建新会话**脱离控制终端**
3. 可选再 `fork()` 一次防止重新获取终端
4. `chdir("/")` 避免占用挂载点
5. 重定向标准输入/输出/错误到 `/dev/null` 或日志文件
6. 设置 umask。再配合**守护管理**：pid 文件、崩溃自动拉起（systemd/supervisor 守护）。
***引申知识: daemon 与后台运行 `&` 的区别—— `&` 仍属当前会话/终端组，终端关闭收到 SIGHUP 被杀；daemon 完全脱离会话/终端/工作目录，生命周期由系统管理。***
> [!Info] 可能的追问:
> - Q: 为什么 fork 后要 setsid？
> - A: 脱离**控制终端**——若仍挂终端，终端关闭会收到 SIGHUP 被杀死；`setsid` 让进程成为新会话首进程、脱离控制终端。
> - Q: 为什么有时 fork 两次？
> - A: 第一次 fork 让父进程退出、避免成为会话首进程后重新获取控制终端；第二次 fork 防止进程再次获得终端。双重 fork 更稳妥。

### 谈谈你对协程的理解？ucontext 是什么类型的协程实现？它的原理是什么？
**回答话术：**
协程是**用户态的可挂起/恢复的函数执行单元**，本质是一个「可以暂停、之后能从暂停点继续」的函数，暂停时保存现场（寄存器、栈指针、指令指针），恢复时还原。与线程的区别：线程由**内核**调度、切换要陷内核开销大（微秒级，涉及寄存器/栈/页表/缓存）；协程由**程序自身**调度、切换只在用户态保存/恢复少量寄存器（纳秒级）。
ucontext 是**有栈协程**的实现基础——它为每个协程分配**独立调用栈**和上下文结构 `ucontext_t`，提供 `getcontext`（保存当前上下文）、`makecontext`（设置新协程入口与栈）、`swapcontext`（原子地保存当前并切换到目标）。切换时把 CPU 寄存器/栈指针/指令指针存进当前 `ucontext_t`，再从目标 `ucontext_t` 恢复，实现用户态跳转。「有独立调用栈」决定它是**有栈协程**：协程体内可以正常递归、调用任意嵌套函数，语义接近线程。
***引申知识: 有栈 vs 无栈的分水岭就是「有没有独立调用栈」——有栈能嵌套调用任意函数、易上手但每协程占一块栈内存；ucontext 属于最原始的有栈方案，现代高性能方案多用**汇编手写切换**（Boost.Context）或**无栈状态机**。***
> [!Info] 可能的追问:
> - Q: 为什么协程切换比线程快？
> - A: 线程切换要陷入内核 + 保存/恢复寄存器 + 缓存/页表失效（微秒级）；协程只在用户态保存/恢复少量寄存器和栈指针，不陷内核、不动页表，纳秒级。
> - Q: 有栈协程的栈哪来的？多大？
> - A: 用 malloc/栈池分配，大小可指定（几 KB 到几十 KB）。太小递归/大局部变量会溢出（可加哨兵检测），太大浪费内存。本框架协程栈默认约 128KB。
> - Q: 协程和线程的数量级差距？
> - A: 线程默认栈约 8MB、受内存和调度限制，几万线程就扛不住；协程栈可指定小栈，几十万没问题，且切换不陷内核。

### 什么是无栈协程？和有栈协程有什么区别？
**回答话术：**
无栈协程**没有独立调用栈**，它的「挂起」不是保存整块栈，而是把函数状态编译成**显式状态机**（如 C++20 的 `co_await` 把函数拆成多个片段，挂起点之间用堆上的帧保存局部变量）。挂起/恢复只是**状态 + 数据的装载**，没有完整调用栈可递归。
对比：
- **有栈协程**（ucontext / Boost.Context / Go goroutine）：有独立栈，**可嵌套调用任意函数**、语义接近线程、易上手；代价是每协程占一块栈内存。
- **无栈协程**（C++20 coroutine / Rust async / JS Promise）：内存开销极小（只保存局部变量帧）、切换快；但**不能在协程内做任意深度递归**，挂起点必须是协程函数自身，库函数里不能随便 await。
***引申知识: C++20 协程就是无栈模型——`co_await`/`co_yield` 由编译器把函数改造成状态机，挂起时局部变量存进 `coroutine frame`（堆上）。所以 C++20 原生协程与 ucontext 有栈协程是两条技术路线，本框架用的是 ucontext 有栈路线。***
> [!Info] 可能的追问:
> - Q: 你们为什么选有栈（ucontext）而不是 C++20 无栈协程？
> - A: 有栈能把**阻塞式库调用**（socket/read）天然包进协程（同步语义），业务代码零侵入；无栈每个挂起点要显式 await、侵入性强。当时环境 ucontext 更成熟直接。
> - Q: 有栈协程的缺点？
> - A: 栈内存占用、栈溢出风险、切换要保存整个上下文。用栈池复用 + 大小可配缓解。

### pthread 有哪些常用 API？pthread 和 std::thread / std::jthread 的关系？
**回答话术：**
pthread（POSIX Threads）是 Linux 的 C 线程库，常用 API：
- 线程：`pthread_create`（创建）、`pthread_join`（等待回收）、`pthread_detach`（分离、自动回收）
- 互斥锁：`pthread_mutex_lock/unlock`、`pthread_mutex_init/destroy`
- 条件变量：`pthread_cond_wait`（等待 + 释放锁）、`pthread_cond_signal/broadcast`（唤醒）、必须配合 mutex
- 其他：`pthread_self`、`pthread_exit`、`pthread_rwlock`（读写锁）、`pthread_key`（线程局部）、`pthread_barrier`（屏障）、信号量 `sem_wait/post`。
**关系**：`std::thread` 是 C++11 对 pthread 的**跨平台封装**——Linux 上底层就调 pthread_create 等，但提供 RAII、`join`/`detach`、异常安全、可传任意可调用对象；`std::jthread`（C++20）在 thread 基础上增加**可请求停止（stop_token）** 和**析构自动 join**，避免忘记 join 导致 `std::terminate`。
***引申知识: 本质是「C 库 vs C++ 标准库」的封装关系——pthread 是底层实现，std::thread 是类型安全封装（Linux 底层即 pthread）；现代 C++ 优先 std::thread/jthread，pthread 多用于需要精细控制（线程属性、信号、亲和）或 C 接口的场合。***
> [!Info] 可能的追问:
> - Q: 项目里用的是 pthread 还是 std::thread？
> - A: 调度器线程用 pthread 创建（便于精细控制线程属性/亲和），简历技术选型也列了 pthread；C++ 侧用 std::thread 也行，本质都是系统线程。
> - Q: std::thread 和 pthread 的区别？
> - A: std::thread 跨平台、RAII、类型安全、传可调用对象；pthread 是 C 接口、POSIX 特定、需手动管理。Linux 上 std::thread 底层就是 pthread。
> - Q: std::jthread 比 std::thread 好在哪？
> - A: jthread 析构自动 join（thread 不 join 会 terminate）、支持协作式取消（get_stop_token），更安全省心。

### 基于 ucontext 自研用户态协程具体是怎么做的？
**回答话术：**
核心是封装 **Fiber 类 + ucontext 切换**：
1. **上下文**：每个 Fiber 持有一个 `ucontext_t`，用 `getcontext` 初始化保存当前状态
2. **栈分配**：为协程分配独立栈（`malloc`/栈池，指定大小），用 `makecontext(&uctx, func, ...)` 把入口函数和栈绑定到该上下文
3. **主/从切换**：调度线程持有一个「主协程」上下文；运行某协程用 `swapcontext(&main_ctx, &fiber_ctx)` 切入，协程让出/结束时 `swapcontext(&fiber_ctx, &main_ctx)` 切回
4. **状态机**：Fiber 维护 READY/RUNNING/TERM 状态，配合调度器队列——让出进队列、结束回收栈。
关键：`swapcontext` 是**原子切换**——把当前寄存器/栈指针/指令指针存入源 `ucontext_t`，同时加载目标上下文，CPU 跳到目标协程继续执行。
***引申知识: 手写协程三要素——**上下文（ucontext_t 或寄存器集）**、**独立栈**、**状态机**；ucontext 提供「切换原语」，在其上封装出可复用的 Fiber 抽象，再被调度器驱动，就是用户态协程的完整实现。***
> [!Info] 可能的追问:
> - Q: 为什么 getcontext/makecontext/swapcontext 三个都要？
> - A: getcontext 保存当前、makecontext 配置新协程入口 + 栈、swapcontext 执行「保存当前 + 加载目标」的切换。三者配合完成「创建可切换的协程」。
> - Q: 协程结束后栈怎么回收？
> - A: 状态到 TERM 后由 Fiber 析构（RAII）释放栈内存，或放入栈池复用（避免反复 malloc），降低分配开销。
> - Q: 和 Boost.Context / 汇编切换比，ucontext 有什么缺点？
> - A: ucontext 是较老的 glibc 接口、部分平台 deprecated、切换开销略高于手写汇编；但跨平台、实现简单，学习/教学场景足够。

### 协程在线程间迁移与亲和绑定是怎么做到的？
**回答话术：**
前提：协程被让出后，其上下文是**完整快照**，放回**共享就绪队列**，任何空闲线程都能取出恢复执行。
- **跨线程迁移**：默认调度器的 READY 队列是**线程共享的**（加锁/无锁保护），协程让出后入共享队列，N 个调度线程任意一个空闲时取走执行——协程天然可在线程间迁移，实现负载均衡。
- **亲和绑定**：若某协程需固定到指定线程（利用该线程缓存/线程局部资源、避免迁移抖动），给它打「目标线程 id」，调度器只把它投给该线程的队列，实现绑定。
**安全关键**：迁移的协程**不能依赖「当前运行线程」的线程局部状态**——所以 Hook 开关做成线程局部变量时，要走 hook 的协程需保证迁移后语义一致，这是设计时要规避的坑。
***引申知识: 迁移 = 共享队列（自由派发、负载均衡），亲和 = 绑定线程（稳定、利用线程局部资源）；两者是对「协程跑到哪个线程」的策略选择，本质是**负载均衡 vs 局部性**的权衡。***
> [!Info] 可能的追问:
> - Q: 迁移会不会有数据竞争？
> - A: 协程自身的局部数据在栈上、迁移跟着走；但协程访问的**共享数据**仍需线程安全（锁/原子）。迁移只改变「谁在跑这个协程」，不改变共享数据语义。
> - Q: 为什么有时要亲和绑定？
> - A: 绑定线程可利用该线程的**缓存亲和性**、避免频繁迁移的调度开销；若协程反复用到线程局部缓存资源，绑定能显著提升局部性。

### Hook 怎么拦截系统调用？用了什么技术？（如何做到同步语义、异步性能）
**回答话术：**
技术本质是**符号拦截/替换**：用 `dlsym(RTLD_NEXT, "read")` 拿到**真实函数指针**，把自定义同名函数替换对 `read/write/socket/connect/sleep` 等的调用。
拦截后的逻辑：
1. 入口先查**线程局部开关**（本线程是否启用 hook）
2. 再查 **fd_manager**：该 fd 是否已注册到 IOManager
3. 是 → 把当前协程挂到该 fd 的**读写事件**上并**让出**（yield），事件就绪由 IOManager 唤醒继续
4. 否 → 直接调用真实 syscall。
于是业务代码写 `read` 是**同步语义**（像普通函数一样用），但底层变成「让出 → 等事件 → 唤醒」，获得**异步 I/O** 的并发能力——这就是「同步语义、异步性能」，开发者零心智负担。
***引申知识: hook 的本质是「在系统调用边界插入自己的调度逻辑」；关键坑：返回码/errno 要与真实 syscall 一致（否则上层判断错）、事件未注册会永久挂起（见通用题）、非阻塞 fd 必须配合循环读。***
> [!Info] 可能的追问:
> - Q: dlsym 和链接期符号覆盖有什么区别？
> - A: 链接期符号覆盖（同符号名）简单但影响全局；`dlsym(RTLD_NEXT,...)` 运行时查下一个符号，能拿到真实函数指针、更可控，适合按需 hook。两者都是「符号替换」。
> - Q: hook 后怎么保证业务写同步代码不阻塞线程？
> - A: 同步是**语义上**的——业务以为阻塞，实际 read 被替换为「注册事件 + 让出」，线程去跑别的协程，等可读事件回来再唤醒该协程「假装阻塞完成」。线程一直忙，不空等。
> - Q: 为什么要线程局部开关？
> - A: 让**非协程线程/场景**不被打扰走真实 syscall，只有协程调度线程启用 hook；用线程局部变量标记，是 hook 可选择性生效的基础。

### 仿 Java Servlet 路由分发是怎么做到的？Servlet 是什么？
**回答话术：**
**Servlet 是什么**：Java 里「一个 URL 对应一个处理类」的 Web 组件模型——每个 Servlet 处理特定路径的请求，Web 容器（如 Tomcat）把 HTTP 请求分发到对应 Servlet。核心是「**路径 → 处理器**」的映射 + 容器管理的生命周期。
**仿 Servlet 的路由分发**：实现一个 `ServletDispatch` 分发器：
1. 注册时把 path 与处理函数（handler）绑定
2. **精确匹配**用哈希表（`unordered_map<path, handler>`）O(1) 命中
3. **模糊匹配**用前缀树（Trie）支持通配符（如 `/user/*/info`、`/*.do`），做**最长前缀匹配**
4. 请求到来：先查哈希，未命中进前缀树，仍未命中走 NotFoundServlet 兜底，**精确优先于模糊**。
***引申知识: 这套「路径 → 处理器」映射 + 兜底 + 精确优先于模糊，是几乎所有 Web 框架（Spring MVC、Node 路由、本项目仿 Servlet）的通用模型；等值查找用哈希、通配查找用前缀树是最优组合。***
> [!Info] 可能的追问:
> - Q: 为什么不直接用 if-else 判断路径？
> - A: 路径多、有通配时 if-else 不可维护、性能差；哈希 + 前缀树做到「查得快、匹配得准」，扩展新接口只需注册，不改分发逻辑。
> - Q: Servlet 的生命周期概念？
> - A: 容器管理 Servlet 的**加载/初始化（init）→ 服务（service）→ 销毁（destroy）**生命周期，单实例多线程处理请求。仿 Servlet 主要借鉴「路径→处理器」映射这一层。

### 单线程支撑数万并发连接是怎么测出来的？（用什么软件、怎么测）
**回答话术：**
不是「架构上声称」，是**实际压测验证**的：
1. **压测工具**：服务端用框架起 HTTP echo / 长连接服务；客户端用 **wrk**（HTTP 场景）做高并发压测，或**自写压测客户端**（epoll + 多线程模拟大量并发连接）压长连接场景
2. **做法**：单线程调度器起服务，客户端逐步加压（几千 → 数万并发连接），观测是否保持低延迟、零丢包、CPU/内存稳定
3. **验证点**：同时建立数万条 TCP 连接、连接保持并周期性收发 echo，确认连接数、吞吐、延迟达标且稳定，证明单线程 + epoll + 协程能承载数万连接。
4. 观测用 `ss`/`netstat` 看连接数、`top`/`perf` 看 CPU 与热点。
***引申知识: 数万并发连接的可行性来自 **epoll 的 O(1) 就绪通知 + 非阻塞 IO + 协程把「每连接一线程」变成「每连接一协程」**——连接多但活跃度低，epoll 只在就绪时唤醒，单线程足以轮转。压测要看「连接数 + 活跃度 + 延迟」三个维度，光连接多不活跃说明不了问题。***
> [!Info] 可能的追问:
> - Q: 几万连接是真的同时活跃还是挂着？
> - A: 测试分两种：**长连接保活**（连接挂着、低频心跳，验证连接承载上限）和**高活跃**（持续收发，验证吞吐/延迟）。数万并发主要指**承载的连接规模**，高活跃并发会低一些。
> - Q: wrk 和自写压测的区别？
> - A: wrk 适合 HTTP 短请求压测（QPS/延迟）；长连接、自定义协议、需精确控制连接数时用**自写压测客户端**（epoll 模拟海量连接）更灵活。
> - Q: 压测结果怎么保证可信？
> - A: 控制变量（同环境多次）、逐步加压找拐点、用 perf/top 确认瓶颈在客户端还是服务端、多轮取稳定值；报告时说明「开发机/联调环境下的相对结论」。

### 调度器与任务队列的工作逻辑（深剖）
@sylar coroutine web framework/include/sylar/scheduler.h L225-L231 — m_mutex + m_threads(线程池) + m_fibers(就绪队列) + m_rootFiber
@sylar coroutine web framework/include/sylar/scheduler.h L74-L105 — schedule()：加锁入队 + tickle 唤醒
@sylar coroutine web framework/src/scheduler.cc L127-L218 — run() 调度主循环
**调度器是什么**：Scheduler 是「线程池 + 就绪队列 + 调度循环」三者合一的类。持有 N 个系统线程（m_threads，每线程跑一个 run() 循环）；M 个协程任务放进共享就绪队列 m_fibers（`std::list<FiberAndThread>`，m_mutex 保护）；循环从队列取任务 → 协程切换过去执行 → 协程让出/结束 → 取下一个。这就是 N-M 中间的「调度器」。
**怎么调度**：schedule() 加锁把任务 push_back 入队 + tickle() 唤醒一个空闲线程；空闲线程的 run()：加锁取队头 → 亲和检查（FiberAndThread.thread 指定则只能该线程跑）→ swapIn 切入协程 → 执行到让出（YieldToHold 切回）或结束 → 继续取下一个；队列空则进 idle（IOManager 里是 epoll_wait 等事件/超时）。
**任务队列是什么**：就是 m_fibers。FiberAndThread 是任务载体——要么存 Fiber::ptr（复用协程），要么存 std::function 回调（首次运行包成 Fiber）。队列回答「哪些协程等着被执行」，由 m_mutex 保证多线程取放安全。
**yield/TERM 后**：让出 YieldToHold → 状态置 HOLD、上下文切回调度线程 rootFiber，控制权回 run() 循环（协程留在队列外等事件重新调度）；协程函数返回 → MainFunc 置 TERM → 切回 rootFiber → Fiber 析构 RAII 释放协程栈（或栈池复用）。YieldToReady 则状态置 READY 重新入队。
**N-M 完整流程（纠正：线程是主动方，协程是被调度对象）**：
1. 创建线程池：N 个系统线程，每个线程跑一个 run() 调度循环
2. 业务投任务：schedule(cb) 加锁把任务（包装成 FiberAndThread）push 进就绪队列 m_fibers + tickle 唤醒
3. 线程从队列**取任务**：run() 里加锁取队头（含亲和检查）
4. 线程用 **swapcontext 切入协程**：swapIn(rootFiber → fiber)，协程开始跑
5. 协程让出：YieldToHold() → swapcontext(fiber → rootFiber)，控制权回 run() 循环，线程继续取下一个任务
6. 协程结束：函数返回 → TERM → Fiber 析构回收栈
关键：**线程是主动取任务的执行者，协程是被调度/被切换的对象**。线程池里的线程不「管理」某个固定协程——协程放共享队列，谁取谁跑；线程也从不在「空闲列表」里待着，而是持续跑 run() 循环，队列空才进 idle 挂起。
**为什么设计 N-M**：
- 单线程多协程：只用一个核，扛不住多核机器/高并发计算
- 每协程一线程：数万协程要数万线程，线程栈 8MB、切换陷内核，资源爆炸
- N-M：N 个线程（≈核数）承载 M 个协程（数万），用满多核 + 海量并发 + 用户态快速切换——是「并发规模 × 多核利用 × 切换开销」的最优折中
> [!Info] 可能的追问:
> - Q: 队列空了线程在干嘛？
> - A: 进 idle 挂起：IOManager 里是 epoll_wait 阻塞等事件/超时，有活才醒；普通 Scheduler 让出 rootFiber 等下次 tickle。
> - Q: 入队取队为什么都要加锁？
> - A: N 个线程可能同时入队（schedule 可从任意线程调用）和取队，m_fibers 是共享结构，不加锁数据竞争。

### 线程亲和性 vs 协程亲和性（深剖）
@sylar coroutine web framework/src/scheduler.cc L146-L151 — run() 里亲和检查（thread != -1 且非当前线程则跳过）
@sylar coroutine web framework/include/sylar/scheduler.h L159-L221 — FiberAndThread.thread 字段
**先回答哲学质疑（协程恢复后任何 CPU 都一样？）**：在**逻辑正确性**上你说得对——协程上下文（寄存器+栈）是自包含快照，切到任何线程/CPU 都能接着跑。但**性能**上不一样，这正是亲和绑定的意义：
1. **线程局部资源**：协程代码可能访问 thread_local 变量、线程绑定的资源（某 IOManager 的 epoll fd、连接、buffer），迁到别的线程去读就错或变慢——绑线程保证「访问的线程局部数据是对的、热的」
2. **CPU 缓存局部性**：L1/L2 cache 是 per-core 的。协程在核 A 跑过，栈、堆对象在核 A 的 cache/TLB 里是热的；迁到核 B 全冷、TLB 全 miss，首次访问性能骤降（缓存亲和）
3. **迁移本身有开销**：入队 + 加锁 + 唤醒另一线程，频繁迁移的调度开销可能超过收益（迁移抖动）
**所以**：共享队列（可迁移）= 用局部性换负载均衡（谁闲谁干）；亲和绑定 = 用均衡换稳定 + 局部性。默认共享队列，需要时对某协程指定 thread。
**线程挂起恢复是否同核**：线程被**内核**调度，恢复时通常优先同核（内核有缓存亲和偏好、尽量不迁移），但**不保证**，负载高时可能迁移。协程被**用户态调度器**调度：共享队列可落任意空闲线程，绑定则固定线程。
**能否指定 CPU**：线程可以——sched_setaffinity / pthread_setaffinity_np 固定到某核；协程不能直接绑核，只能绑线程（线程再被内核调度到某核）。
> [!Info] 可能的追问:
> - Q: 那协程到底要不要绑线程？
> - A: 默认不绑（共享队列负载均衡）；对依赖线程局部资源、要复用连接/缓存的协程绑线程划算。是局部性/均衡的权衡，不是正确性问题。

### 协程上下文/寄存器存在哪？为什么切换比线程快？（深剖）
@sylar coroutine web framework/include/sylar/fiber.h L156-L169 — m_ctx(ucontext_t) + m_stack + m_stacksize
@sylar coroutine web framework/src/fiber.cc L50-L71 — makecontext 绑定独立栈
@sylar coroutine web framework/src/fiber.cc L125-L148 — swapIn/swapOut：swapcontext 切换
**线程上下文存哪**：线程被内核调度，上下文（CPU 寄存器、内核栈指针、指令指针、信号掩码）由**内核**保存在该线程自己的**内核栈**里；切换要「用户态→内核态→换内核栈→调度器选下一个→回用户态」，涉及系统调用、页表/TLB、cache 全部受影响，微秒级。
**协程上下文存哪**：存在协程对象的内存里——Fiber::m_ctx 是 ucontext_t 结构（保存寄存器值），用户栈是 malloc 的独立栈（栈指针在 m_ctx.uc_stack）。swapcontext 是纯用户态库函数：存当前寄存器进源 m_ctx、从目标 m_ctx 加载，不陷内核、不动页表，纳秒级。
**为什么协程快**：① 不陷入内核（无系统调用）；② 不经内核调度器；③ 不换内核栈、不刷新 TLB/cache（地址空间没变）；④ 保存/恢复的寄存器更少。线程切换的「慢」主要在内核态往返 + TLB/cache 失效，协程全免。

### 为什么用有栈协程（ucontext）而不用无栈 / C++20 co_await？（深剖）
**先回答「侵入性」是什么意思**：无栈协程（C++20 co_await）要求「协程函数本身」是挂起点——你用 co_await 挂起的是**当前这个函数**。如果你调了一个普通库函数（比如 libc 的 read），它内部没有 co_await，你在里面挂不起来，想让这个库函数可挂起就必须重写它。这就叫侵入：**挂起点必须显式写在你的代码里，且穿透不进第三方函数**。
**有栈协程为什么没这个限制**：它有自己的完整调用栈，`swapcontext` 在**任何嵌套深度**都能挂起——包括 read() 这种第三方库函数深处（配合 hook，read 内部也会让出）。所以业务代码可以无脑写同步风格：`int n = read(fd, buf, len);` 一行，底层该让出让出，业务零改造 = 零侵入。
**对比**：

| | 有栈（ucontext/Boost.Context） | 无栈（co_await） |
|---|---|---|
| 独立栈 | 有，可嵌套任意深度 | 无，挂起点是协程函数自身 |
| 第三方阻塞函数 | hook 一下就能挂起 | 必须重写成协程版 |
| 业务代码 | 同步风格零改造 | 每个挂起点显式 await |
| 内存 | 每协程一块栈（默认 128KB） | 只需堆上小帧 |
| 切换 | 保存/恢复整块上下文 | 恢复帧 |
**为什么不用 C++20 co_await**：
- 当时 ucontext 方案更成熟、生态验证充分；
- 无栈侵入性强，socket/read 这类 libc 阻塞调用要每个都包装成协程版，工作量巨大；
- co_await 的挂起恢复局限在函数体内，无法天然把「阻塞 I/O」整体移出线程，达不到 hook 那种「同步语义异步性能」。所以有栈 + hook 是成本/收益最优解。
> [!Info] 可能的追问:
> - Q: 有栈协程的缺点？
> - A: 每协程占一块栈（内存开销、栈溢出风险、切换保存量大）。用栈池复用 + 大小可配缓解。

### Hook 系统全流程深剖（dlsym 是两种不同用途！）
@sylar coroutine web framework/src/hook.cc L42-L50 — dlsym(RTLD_NEXT) 取真实函数
@sylar coroutine web framework/src/hook.cc L53-L66 — \_HookIniter 静态初始化器
@sylar coroutine web framework/src/hook.cc L78-L147 — do_io 核心
@sylar coroutine web framework/src/hook.cc L17/L68-L70 — t_hook_enable 线程局部开关
**先纠正一个混淆**：代码里两处 dlsym 是**两种完全不同的东西**：
- `src/hook.cc` 的 `dlsym(RTLD_NEXT, "sleep")` —— **符号拦截**：从 libc 下一个符号表拿真实 sleep 地址，这是 hook 系统的核心。
- `src/library.cc` 的 `dlsym(handle, "CreateModule")` —— **插件加载**：从已 dlopen 的动态库句柄拿导出函数，属于 module 插件系统，跟协程 hook 无关。
所以「为什么是 CreateModule/DestoryModule」——那是插件库规定的导出接口名，不是 hook 的目标。hook 的目标是 sleep/socket/read/write/connect 等 21 个系统调用。
**Hook 为什么需要 dlsym**：我们要「覆盖」系统符号（让业务调 sleep 走我们的版本），又要在内部「还原」真实行为（真正去睡）。`dlsym(RTLD_NEXT, "sleep")` 返回 libc 里真实 sleep 地址存进 sleep_f，我们的 sleep 包装里调 sleep_f(...) 就是真调用。没有 dlsym 就拿不到真实函数指针，只能无限递归。
**整个工作流程**：
1. 进程启动，`_HookIniter` 静态初始化器执行 hook_init()：对 21 个符号逐个 dlsym(RTLD_NEXT) 拿真实指针存 `name_f`
2. 同名函数（sleep/socket/read...）定义在 hook.cc，靠链接（-rdynamic 导出符号）覆盖 libc 同名符号——业务调 read() 实际进 hook.cc 的 read
3. hook 函数入口查线程局部开关 t_hook_enable：关闭 → 直接调真实 read_f；开启 → 走 do_io
4. do_io 把阻塞调用协程化（见下）
**线程局部开关怎么做到只对指定线程生效**：`static thread_local bool t_hook_enable`（hook.cc L17）——每线程一份独立变量。调度线程启动时 set_hook_enable(true)（scheduler.cc L129），普通线程默认 false。于是只有调度线程的阻塞调用被拦截转协程，其他线程走真实 syscall，互不干扰。
**do_io 在做什么**（hook.cc L78-L147）：
1. 非 hook 线程/非 socket/用户显式非阻塞 → 直接真调用（保持语义）
2. 调真实函数 fun(fd,...)：若 EAGAIN（数据没准备好/缓冲满）：
   - 注册超时定时器（addConditionTimer，超时则 cancelEvent 唤醒协程并置 ETIMEDOUT）
   - `iom->addEvent(fd, event)`：把当前协程挂到这个 fd 的可读/可写事件上
   - `Fiber::YieldToHold()`：协程让出，线程去跑别的协程
   - 事件就绪（或超时）被 IOManager 唤醒 → goto retry 重新调真实函数
3. `retry:` 是什么语法：C 的 **goto 标签**。EAGAIN 让出再唤醒后要重新尝试系统调用，用 `goto retry` 回到重试（含 EINTR 中断循环）。这是 C/C++ 合法的标签跳转，hook 里用于「重试循环」。
**为什么协程遇阻塞系统调用会卡死线程**：一个线程同一时刻只能跑一个协程。协程 A 里调真 read（阻塞），线程卡在 read 等数据，同线程其他协程全没机会跑。所以必须把阻塞调用变成「注册事件 + 让出」，线程腾出来跑别的协程。
> [!Info] 可能的追问:
> - Q: hook 为什么必须线程局部开关？
> - A: 协程调度线程要 hook（阻塞转异步），普通业务线程不该被劫持；且 hook 会把 fd 改 O_NONBLOCK，非协程线程改了会破坏语义。
> - Q: 返回值和 errno 要跟真实 syscall 一致吗？
> - A: 必须一致，否则上层业务判断（EAGAIN/EINTR）全错。hook 代码里每个分支都维护 errno。
> - Q: dlsym 为什么是 RTLD_NEXT 不是 RTLD_DEFAULT？
> - A: RTLD_NEXT 从「当前对象之后的下一个」符号表找真实实现，避免拿到我们自己覆盖的符号造成死循环；RTLD_DEFAULT 全局找，可能拿回自己。

### ZooKeeper 服务注册发现的工作逻辑
@sylar coroutine web framework/src/zk_client.cc L55-L66 — 建会话 + watcher 注册
**ZK 是什么**：分布式协调服务——一棵「树形目录（znode）+ 一致性协议（ZAB）」。所有节点共享同一棵树，读写强一致。znode 分**持久节点**（显式删除才消失）和**临时节点**（创建它的会话断开自动消失）。
**服务注册发现怎么做**：
1. 服务启动，在约定目录创建**临时节点**注册自己：`/services/chat/192.168.1.10:9000`，节点数据写 IP:port/元数据。会话在，节点就在
2. 服务宕机/网络断开 → ZK 会话过期 → **临时节点自动删除** → 服务从注册表消失（宕机自摘除，无需手动删）
3. 消费方对目录 watch：子节点变化（增/删）推通知给 watcher，消费方重拉子节点列表，维护可用实例集合
4. 再配合负载均衡（轮询/哈希）在可用实例里选一个调用
**临时节点 + watch 是核心**：临时节点解决「服务挂了怎么知道」，watch 解决「变化怎么通知消费者」。这就是 ZK 注册发现的标准用法。
**本框架情况**：zk_client.cc 是对官方 C API 的封装；真正把注册发现做成业务的在 src/ns（nameserver）、src/rock（service_discovery、load_balance）。面试讲 ZK 原理即可。

### daemon 化细节：umask / fd 关闭 / IO 重定向 / pid 文件 / systemd
@sylar coroutine web framework/src/daemon.cc L31-L67 — real_daemon（daemon(1,0) + fork 循环）
**umask 是什么**：**文件创建权限掩码**。Linux 新建文件默认权限 0666（rw-rw-rw-）再**去掉 umask 中为 1 的位**。`umask(0022)` → 0666 & ~0022 = 0644（rw-r--r--），即「不让组/其他用户写」。daemon 设 umask 是安全惯例：保证新建文件权限可控，不因提权/目录可写而开放多余权限。
**为什么关闭不需要的 fd、怎么知道哪些没用**：daemon 可能继承父进程（shell/终端）一堆 fd——终端、socket、文件。不关的后果：占用资源、意外保持连接、重定向冲突。怎么判断：**没法逐个判断，干脆全关**——把 0/1/2 重定向到 /dev/null 后，从 3 到系统 fd 上限（ulimit -n）全部 close（Linux 5.9+ 用 close_range(3, ~0U, 0) 批量关）。不确定的 fd 一律关掉最安全。
**为什么重定向 0/1/2 到 /dev/null**：daemon 脱离终端（setsid）后，stdin/stdout/stderr 可能指向已关闭/无主的终端，一读写就出错（SIGPIPE 甚至崩）。重定向到 /dev/null 保证「读写无害」；生产上常把 stdout/stderr 重定向到日志文件保留输出。
**pid 文件 + systemd/supervisor**：
- **pid 文件**（/var/run/xxx.pid）：记录进程 PID。用途：判断服务是否在跑（文件存在且 PID 活着）、精确发信号 `kill $(cat xxx.pid)`、方便管理工具接管
- **systemd/supervisor 守护**：把「崩溃自动拉起」交给专门进程管理器，比自己 fork+waitpid 循环更规范。systemd 服务文件 `Restart=always`，进程退出 systemd 自动重启，还能管日志/依赖/启动顺序；supervisor 同理（`autorestart=true`）。项目 daemon.cc 是**手写 fork+waitpid 自守护**（老派做法），面试可对比讲「生产一般用 systemd/supervisor」。

### 协作式取消（jthread stop_token）
**是什么**：std::jthread 提供的协作式线程取消机制。jthread 持有一个 stop_token，外部调 `request_stop()` 只是把「停止请求」标志置位，**不强制杀线程**；线程内代码自己检查 `stop_token.stop_requested()`，在安全点主动退出。所以是**协作式**：目标线程配合才生效。

### IOManager：epoll + 定时器统一调度（事件驱动 I/O）（深剖）
@sylar coroutine web framework/src/iomanager.cc L319-L353 — idle()：epoll_wait 超时=最近定时器 + listExpiredCb
@sylar coroutine web framework/src/iomanager.cc L146-L192 — addEvent：fd 注册 epoll（ET 模式）
@sylar coroutine web framework/include/sylar/timer.h L78/L165 — Timer::Comparator + std::set m_timers（红黑树）
**「事件驱动 I/O」是什么**：传统做法是「每连接一个线程，线程阻塞在 read 等数据」——连接多线程就多，资源撑不住。事件驱动：所有连接的非阻塞 fd 注册到 epoll，一次 `epoll_wait` 返回「哪些 fd 就绪了」，应用只对就绪 fd 做 IO。连接多但就绪的少，单线程就能管理数万连接。
**「调度器之上封装 epoll 与定时器」在做什么**：IOManager 继承 Scheduler，覆写了 Scheduler 的 idle()（原本空闲时忙等/空转）。新 idle() 把「等 IO 事件」和「等定时器到期」合成一次 epoll_wait：
1. epoll_wait 的超时参数设为「最近一个定时器的到期时间」（无定时器则 3s 上限）
2. fd 就绪 → 取出事件，唤醒对应协程/执行回调
3. listExpiredCb() 从定时器红黑树取所有到期项，schedule 进调度器执行
**为什么这样设计**：线程空闲时不再忙等，阻塞在 epoll_wait 睡到「最近事件或最近定时器」；IO 事件和超时事件共用一个循环，一次等待服务两类需求，毫秒级定时精度。
**为什么用红黑树（std::set）**：定时器容器 `std::set<Timer::ptr, Comparator>` 按到期时间排序。红黑树 vs 最小堆：取最小 O(1)、插入删除 O(logn) 都满足；红黑树在 C++ 里 std::set 现成、**任意删除（取消定时器）方便**（最小堆任意删除要维护位置或标记失效）。sylar 实际用红黑树；简历写「红黑树/最小堆」是两种可选实现。
**IO 事件和定时事件是两个独立的数据结构，没有共用一个**：
- **epoll**（内核数据结构：内核红黑树 + 就绪队列）——管「哪些 fd 的 IO 事件就绪了」
- **定时器**（用户态 `std::set` 红黑树）——管「哪些超时到期了」
它们「共用」的只有**一次 epoll_wait 调用**：epoll_wait 的 timeout 参数取「最近一个定时器的到期时间」，线程睡到「最近事件或最近定时器」，一次唤醒两个都检查——fd 就绪处理 IO，定时器到期 listExpiredCb 处理超时。所以是「两个独立数据结构 + 一个统一等待点」。
**完整数据流**：
1. 业务协程读 fd（hook 后 read）→ EAGAIN → do_io 里 `iom->addEvent(fd, READ)` 把「协程 + fd 可读事件」注册进 epoll → 可选 `addConditionTimer(超时, 回调)` 把「超时」加进定时器红黑树 → 协程让出
2. 线程空闲 → 跑 idle() → epoll_wait（timeout = 最近定时器到期时间）
3. a) fd 就绪 → 内核放入就绪队列，epoll_wait 返回 → IOManager 触发该 fd 回调 → 唤醒挂起的协程 → goto retry 继续读
   b) 定时器先到期 → epoll_wait 因 timeout 返回 → listExpiredCb 取到期项 → cancelEvent 唤醒协程并置 ETIMEDOUT
4. 协程被唤醒回 do_io 重试系统调用
所以：**epoll 管「IO 就绪」，红黑树管「超时到期」，两者由 idle() 里一次 epoll_wait 统一点火**。
**如何真正做到文件监听热重载（inotify）**：项目当前 LoadFromConfDir 用 **mtime 轮询**（主动重载时 stat 比较修改时间）。要「文件一改立刻感知」用内核 **inotify**：`inotify_init()` 建实例 → `inotify_add_watch(fd, 配置目录, IN_MODIFY|IN_CLOSE_WRITE)` 注册监听 → `read(fd)` 阻塞等文件事件 → 收到后重新 LoadFromYaml。比轮询更实时、省 CPU；注意防抖（保存可能多次触发）和重载串行化。
> [!Info] 可能的追问:
> - Q: 为什么用 epoll 而不是 select/poll？
> - A: select 有 fd 上限（1024）且每次全量扫描 O(n)；poll 无上限但也是全量扫描；epoll 就绪通知 O(1)、支持大量 fd、事件驱动。高并发连接场景 epoll 是现实选择。
> - Q: ET 和 LT 区别？
> - A: LT 有数据就持续通知（可能反复唤醒），ET 只在状态变化时通知一次（必须一次读完）。sylar 用 ET 减少重复唤醒，配合循环读避免数据残留在缓冲区，同时用内核标志（`SO_REUSEPORT/EPOLLEXCLUSIVE`）避免惊群效应

### ZooKeeper 节点与 1MB 限制（深剖）
**每个节点是什么**：znode 是 ZK 树上的一个节点，路径类似文件系统 `/services/chat/192.168.1.10:9000`。每个节点能存一小段数据（字节数组）+ 属性（ACL、版本号、时间戳）。它是「目录 + 小文件」的结合体。
**临时节点 vs 持久节点**：临时节点（ephemeral）绑定创建它的会话，会话断开自动删除——用于「注册服务，宕机自摘除」；持久节点要显式删除——用于存配置等长期数据。
**为什么每个节点只能存 1MB**：ZK 定位是**协调元数据**（注册信息、配置、锁、选主状态），不是业务数据存储。数据小保证：
- 所有节点数据常驻内存、读写快；
- ZAB 协议要把数据同步复制到所有 follower，数据越小复制越快、集群吞吐越高；
- 防止内存膨胀拖垮集群。大业务数据存外部存储（DB/对象存储），ZK 只存引用。

**「统一二进制序列化」是什么**：把 C++ 的结构化数据（int、string、对象字段）按统一二进制格式转成字节流，便于网络传输/存储；对端用对称接口读回。ByteArray 封装一块动态字节缓冲，提供：

### ORM 两种实现：代码生成 vs 运行时反射（深剖）
@sylar coroutine web framework/src/orm/orm.cc L22-L66 — 生成器入口：扫 XML → Table::gen → gen_cmake

**「orm 文件夹」是代码生成器，不是反射**：`src/orm/` 干的是「读数据库表结构，生成 C++ 数据访问代码」：
1. orm.cc 入口：扫描 `bin/orm_conf` 下的 **.xml 表定义文件**（tinyxml2 解析）
2. 每个 xml → Table 对象（init 解析字段/主键/索引）
3. `Table::gen(out_path)`：用 ofstream **写出 .h/.cc 源码文件**——该表的 DO 类（字段成员 + getter/setter）+ DAO 类（增删改查）
4. gen_cmake：同时生成 CMakeLists.txt 把产出编进库

**和 ERP 的 ORM 反射是两条路线**：
- **代码生成**（sylar src/orm）：表结构 → 生成 C++ 源码 → 编译。运行时就是普通函数调用
- **运行时反射**（ERP BaseDo/BaseDao）：运行时遍历字段注册表 → 拼动态 SQL → PreparedStatement 执行。没有生成源码，靠运行时元数据驱动

> [!Info] 可能的追问:
> - Q: 简历里 ERP 的 ORM 是哪种？
> - A: ERP 是**运行时反射**（BaseDo 字段注册 + SqlValue variant + BaseDao 模板动态 SQL）；sylar 的 src/orm 是**代码生成器**。讲项目按对应实现说，别混。
> - Q: 生成器 vs 反射优缺点？
> - A: 生成器编译期定型、运行快、可读性好，但改表结构要重新生成编译；反射运行时灵活、无重编译，但动态 SQL 拼接有运行时开销和复杂度。

### CMake 代码生成（ragel/protoc）（深剖）

**怎么做**：utils.cmake 定义两个函数，核心是 `add_custom_command`：

### 你如何在客户端和服务端中使用自定义的 TCP 帧协议？它们二者如何借助自定义的协议通信？
**回答话术：**
**协议定义**：固定帧头 `2 字节消息 ID + 2 字节长度 + JSON 载荷`。消息 ID 是**协议语义**（对应某个业务操作，客户端 `RequestId` 与服务端 `ChatMessageId` 一一对应）；长度字段标记载荷字节数；载荷是 JSON 承载业务数据。
**客户端**：业务层把操作封装成「消息 ID + JSON」，序列化成帧字节流经 socket 发出；收包按帧头长度字段**循环切帧**，解析出消息 ID 分发给对应 handler。
**服务端**：同样按帧定界解析，把消息 ID 路由到对应业务处理；响应也组装成同样格式的帧回给客户端。
**二者如何通信**：都遵守同一份「帧格式 + 消息 ID 映射表」协议约定，客户端发什么格式、服务端按什么格式解析，天然对称；半包靠长度字段 + 缓冲解决。
***引申知识: TCP 是字节流无消息边界，必须应用层定界——长度前缀比固定长度（浪费空间）和分隔符（载荷含分隔符会破坏边界）更可靠；客户端与服务端共用同一份协议定义，是「协议先行」的体现。***
> [!Info] 可能的追问:
> - Q: 为什么用长度字段而不是固定长度或分隔符？
> - A: 固定长度浪费空间、不适配变长 JSON；分隔符若载荷里含该字符会破坏边界；**长度前缀**精确知道载荷字节数，最可靠，还能提前分配缓冲。
> - Q: 为什么用 JSON 做载荷而不是纯 Protobuf？
> - A: 本项目消息体用 JSON 便于**跨端调试、可读性好**；Protobuf 用于**服务端间 RPC**（更紧凑高效）。业务帧保可读、内部 RPC 保性能。
> - Q: 粘包/拆包怎么处理？
> - A: 接收端维护**接收缓冲**，先读 2 字节长度，再按长度读完整载荷；不够就是半包，留缓冲等下次 recv 继续拼；一次可能多帧则循环处理。

### 你为什么要采用微服务架构？这样一个应用程序多个进程是否在浪费资源？
**回答话术：**
**为什么用**：
1. **故障隔离**——聊天、鉴权、验证任一服务崩了不影响其他
2. **独立扩展**——聊天服务是高负载热点可单独多实例水平扩展，网关无状态可随意扩容
3. **职责清晰**——每服务单一职责、独立部署发布
4. **团队协作**——不同服务可并行开发。
**多进程是否浪费资源**：有一定开销（进程内存、IPC），但**可接受且值得**：
5. 每个服务实例资源占用可控（热点按需扩展、轻量服务保持少量实例）
6. 相比资源开销，**故障隔离和扩展性收益远大于成本**
7. 同机可共存多个轻量实例，且按负载动态扩缩容，不算浪费。学习项目规模小，微服务的价值更多在于**验证架构能力和工程思维**。
***引申知识: 微服务的成本本质是「把单体的复杂度转移为分布式的复杂度」——网络故障、数据一致性、链路追踪、运维；规模小时单体更快，业务复杂/需独立扩展时才值得拆分。***
> [!Info] 可能的追问:
> - Q: 什么规模适合微服务？
> - A: 业务复杂、团队大、需要独立扩展/发布时；单体够用时用微服务是过度设计。本项目用它验证架构能力。
> - Q: 微服务的缺点？
> - A: 分布式复杂度（网络故障、数据一致性、链路追踪）、运维成本、服务间调用延迟。需要网关、注册中心、监控配套。
> - Q: 怎么拆分服务是合理的？
> - A: 按**业务边界/变更频率/资源特征**拆：独立部署、独立扩展、故障域隔离。本项目按职责（网关/鉴权/聊天/验证）拆分，聊天是扩展热点。

### 鉴权防伪造会话是如何做到的？
**回答话术：**
**核心是让会话不可伪造**：
1. 登录成功后服务端签发**签名 token**（JWT：Header+Payload+Signature，签名用密钥/私钥），token 内含用户 ID、过期时间
2. token 的签名**防篡改**——客户端改 payload 任何字段，验签即失败
3. 客户端后续请求带 token，服务端**校验签名 + 过期时间 + 权限**，通过才建立/放行会话
4. 配合**防重放**（token 有效期 + 关键操作绑定随机数/时间戳）与**用户态校验**（每请求查用户是否合法）。
***引申知识: 鉴权防伪造的本质是「签名保证完整性、过期保证时效、权限保证范围」；JWT 的 Signature 让 token 不可篡改（但 payload 可读），所以敏感信息不能进 payload。***
> [!Info] 可能的追问:
> - Q: 为什么改了 payload 就失效？
> - A: Signature = 对 (Header+Payload) 用密钥签名；任何改动都导致重算的签名与 token 里的签名不一致，验签失败。token **不可篡改**（不是不可读，payload 是 Base64 可解码）。
> - Q: token 被窃取/重放怎么办？
> - A: 设**短有效期**（过期作废）+ **refresh token** 刷新；高风险操作绑定设备/IP/随机 nonce 校验；必要时服务端维护**黑名单**吊销。
> - Q: 鉴权服务挂了会影响主链路吗？
> - A: 会——所以鉴权独立成服务 + 可扩展，且 token 验签是**无状态计算**（不查库）吞吐高；必要时可本地缓存公钥/验签结果降级。

### 离线消息落登录后批量补发是如何做到的？
**回答话术：**
**在线**用户消息实时推送；**离线**（连接断开）时，发送方把消息写入 Redis **离线队列**（按用户）暂存。用户登录时：
1. 服务端检测该用户有未消费的离线消息
2. **按序批量补发**（按消息序号从小到大一次或分批发）
3. 补发完成后**更新游标/清理离线队列**，此后进入增量同步。Redis 内存读写快 + TTL 自动过期，适合短期暂存。
***引申知识: 离线补发的关键是有序 + 可重入——队列按消息序号有序存储（Redis ZSET 或有序 List），补发按序取；客户端本地 SQLite 缓存已收消息，游标保证「不重不漏」。***
> [!Info] 可能的追问:
> - Q: 为什么离线消息存 Redis 而不存 MySQL？
> - A: 离线消息是**短期高频读写 + TTL 过期**场景，Redis 内存读写微秒级、天然支持过期；MySQL 用于持久化强关系数据。
> - Q: 补发时顺序怎么保证？
> - A: 离线队列按**消息序号**有序存储（Redis ZSET 或有序 List），补发按序号从小到大取，和在线时的消息顺序一致。
> - Q: 补发中途连接断了怎么办？
> - A: 游标机制保证**可重入**——下次登录从上次补发到的游标继续，不重不漏；已补发消息写入客户端本地 SQLite，避免重复消费。

### 多端登录自动踢下线是如何做到的？
**回答话术：**
**同一账号只允许一端在线**：
1. 登录时服务端检查该用户是否已有在线会话
2. 若有，通过**用户→实例映射**（Redis）定位旧连接所在实例，gRPC 通知该实例**关闭旧会话**
3. 旧连接被关闭，同时新登录注册成功，**确保最终只有新会话在线**。踢下线动作要**串行化**（Redis 锁/原子操作），避免新旧并发登录竞态。
***引申知识: 竞态窗口在于「更新映射」和「关闭旧连接」不是原子操作——用 Redis 原子操作把「检查在线 → 标记新会话 → 通知旧会话」做成原子的，配合会话版本号防误杀旧通知。***
> [!Info] 可能的追问:
> - Q: 为什么同一账号只允许一端在线？
> - A: 避免同一账号多端同时消费/修改状态造成**消息错乱**（已读、消息归属冲突），新登录踢旧会话保证状态唯一。
> - Q: 并发登录怎么避免竞态？
> - A: 登录校验**串行化**（Redis 原子操作/锁），后登录者原子地「取代」旧会话注册，旧实例收到通知关闭连接；保证最终一端在线。
> - Q: 怎么知道旧连接在哪个实例？
> - A: Redis **用户→实例映射**，踢下线时查映射定位旧实例再通知。

### 热文件从服务器缓存下载，冷文件收发采用网关转发落盘 + 对象存储混合模式是如何做到的？
**回答话术：**
这是**按访问频率分层的文件存储**策略：
**热文件（近期高频访问）**：从**服务器缓存**（本地磁盘/内存缓存区）直接下载——近期上传/频繁访问的文件留在近端，路径短、响应快。
**冷文件（长期/低频）**：**网关转发落盘 + 对象存储混合**——上传时客户端发给网关，网关按文件落盘并转存**对象存储**（统一存储层）；下载时网关先查本地，未命中从对象存储取。混合模式平衡了「近端快」和「存储层统一、可水平扩展」。
***引申知识: 冷文件放对象存储的核心原因是**多实例共享**——文件只落某实例本地盘其他实例读不到；对象存储（MinIO/S3）所有实例读写同一存储，一致性由存储层兜底，还提供副本与扩展性。***
> [!Info] 可能的追问:
> - Q: 怎么判定热还是冷？
> - A: 按**访问频率/最近访问时间**（LRU 思想）：近期访问的留在缓存/近端，长期未访问的迁移到冷层；可配阈值（如 30 天未访问转冷）。
> - Q: 热层缓存命不中怎么办？
> - A: 回源——从冷层/对象存储取，取回后按需提升为热层缓存，同时更新索引；本质是「缓存未命中回源」的标准模式。

### 为什么为了性能自定义了协议编码，还用 JSON 做载荷而不是纯 Protobuf？
**回答话术：**
这是**协议分层**的考量——「帧格式」和「载荷编码」是两件事，各自优化：
1. **帧格式轻量化**（2 字节消息 ID + 2 字节长度）：解决的是**定界和路由**，让消息头最小、长连接复用、实时性好——这是自定义帧带来的实时性/效率收益
2. **载荷用 JSON**：面向**跨端调试、可读性好、开发快**——客户端（C++/Qt）等多端都能方便序列化/反序列化，出问题能直接读报文
3. **纯 Protobuf 的优势**：二进制紧凑、序列化快、类型强；但**不直观、调试难、跨端要维护 .proto 契约**。
选型：**业务帧（客户端 ↔ 服务端）用 JSON 保可读易调试**；**服务端内部 RPC（gRPC）用 Protobuf 保性能**，两头各取所长。
***引申知识: 性能瓶颈往往不在「载荷是 JSON 还是 Protobuf」（JSON 解析也很快），而在**连接复用、IO 模型、协议定界**；JSON 对可维护性的收益远大于它的序列化开销，所以「轻量帧 + JSON 载荷」是很多自研协议的真实选择。***
> [!Info] 可能的追问:
> - Q: JSON 解析比 Protobuf 慢多少？值得吗？
> - A: 慢一些，但消息量级下差异可接受；换来的是**可读、易调试、跨端方便**。性能敏感、量大、强类型的内网 RPC 才值得上 Protobuf。
> - Q: 什么场景必须上 Protobuf？
> - A: 服务端间高吞吐 RPC（gRPC）、跨语言强类型契约、海量消息、需要极致紧凑与序列化性能的场景。
> - Q: 那自定义协议的意义在哪？
> - A: 意义在**帧结构**——轻量头 + 长度定界 + 长连接复用 + 心跳，这是 HTTP 头部冗余、WebSocket 帧偏重替代不了的实时性/效率优化。

### 并发模型是怎么设计的？为什么用单线程消息队列？性能瓶颈在哪？
**回答话术：**
设计是**I/O 多路复用 + 单线程业务队列（生产者/消费者）**：
1. **I/O 层**：Asio/epoll 异步非阻塞收发包，I/O 线程只做收发和切帧
2. **业务层**：解析出的完整消息**入一个消息队列**，一个 worker 线程串行消费、处理业务
3. 即生产者（I/O 线程）入队、消费者（worker）出队。
**为什么单线程**：**所有业务逻辑串行化，天然规避多线程加锁竞争**——不用锁就能保证数据一致，同一连接消息天然有序；编程简单、无死锁/竞态。
**性能瓶颈**：单线程 worker 是**CPU 串行瓶颈**——业务处理吞吐受单核限制，消息量大时 worker 成为队列堵点。
**解法**：① 业务只做轻量逻辑，重活异步化；② **多实例水平扩展**——聊天服务可多实例，Redis 路由把不同用户分到不同实例，每实例内单线程串行，整体吞吐靠实例数摊薄。
***引申知识: 「单线程事件循环 + 串行业务」是分布式里「用确定性换取免锁」的经典取舍（类似 Node/Redis 单线程模型）——单线程免锁、有序、好推理，用「多实例分片」绕开单核瓶颈；这是**垂直（单核）与水平（多实例）**两种扩展方式的权衡。***
> [!Info] 可能的追问:
> - Q: 单线程业务会不会浪费多核？
> - A: 单实例单 worker 只用单核，但通过**多实例**（每实例各一个 worker）并行利用多核且天然隔离；比「单实例多线程抢锁」更简单可靠。
> - Q: 消息顺序怎么保证？
> - A: 同一会话/连接的消息都进同一 worker 串行消费，天然保序；跨实例同步层用 Redis 游标保证顺序。
> - Q: I/O 线程和 worker 之间怎么传数据不阻塞？
> - A: 无锁/轻量消息队列（生产者入队、消费者出队），入队快、不阻塞 I/O 线程；必要时用原子/单写单读优化。

### 为什么用游标来维护已读消息的状态？
**回答话术：**
**游标（cursor）= 每端/每会话的已读位点**，记录「我已经消费到哪条消息」。用它维护已读的原因：
1. **增量同步的基础**：客户端带游标请求「游标之后的消息」，服务端返回 `seq > cursor` 的消息，**只传新增、不重不漏**，避免每次全量拉取
2. **每端独立进度**：多端登录时各端有各自的游标，A 端读到的、B 端可以独立追，互不干扰
3. **离线/断线续传**：断线后重连，从上次游标继续，**天然支持断点续传**
4. **已读回执的表示**：已读状态 = 游标推进到某位置，比逐条打标更**紧凑高效**。
用 Redis **ZSET + score=消息序号**存消息，游标就是 score 值，`ZRANGEBYSCORE (cursor, +inf)` 一次取增量，天然契合。
***引申知识: 游标是「**增量拉取 + 每端进度 + 断点续传**」的统一抽象；与「逐条已读标记」比，游标是「一个数字描述已读边界」，O(1) 存储、支持批量增量，是消息系统的标准做法（类似 Kafka 的 offset）。***
> [!Info] 可能的追问:
> - Q: 游标和已读回执的关系？
> - A: 「已读」就是「游标推进到某条消息之后」，不需逐条记录；展示未读数 = 消息总数 − 游标位置。
> - Q: 多端各自游标，会不会乱？
> - A: 不会——游标按「端/设备」独立存，各端互不影响；同一端内严格单调推进，避免回退。
> - Q: 游标存哪？
> - A: Redis（每端一个 key 存游标值），读快、跨实例共享；配合服务端权威消息序号，保证「游标之后」语义一致。

### IM 聊天消息按温度分层是怎么做到的？和客户端本地 SQLite 怎么配合？
**回答话术：**
**分层**是按「访问频率 + 时间」把消息分到不同存储，各层各司其职：
- **热层（近期）**：Redis——在线/近期消息，读写快、TTL 过期，提供实时拉取与离线短期暂存
- **温层（权威文本）**：可扩展的追加式 / LSM / KV 消息库——所有文本消息的权威存储，按时间序
- **冷层（历史/富媒体）**：对象存储 + 索引——长期历史与图片/视频/文件，用「追加日志 + 元数据索引 + ranged GET」按需取。
**迁移**：热 → 温 → 冷按时间/访问频率自动流转（近期留热层，超过阈值转冷），冷层索引可重建。
**与客户端 SQLite 的配合**：**SQLite 是客户端本地缓存，不是真相源**：
- 客户端本地 SQLite 存已拉取的历史，**本地优先读取**——离线可看、浏览/搜索快、不每次打服务端
- 服务端（Redis + 消息库 + 对象存储）是**权威**——多端同步、换设备、备份靠它
- 客户端带**游标**向服务端**增量同步**（「给我 seq N 之后的」），拉到后写本地 SQLite；本地缓存和服务端权威互补两层，不是二选一。
***引申知识: 完整四层模型——客户端 SQLite（本地缓存）→ 热层 Redis（近期）→ 温层文本消息库（权威）→ 冷层对象存储（富媒体/历史）；「本地缓存 + 服务端权威」是移动端同步的标准范式，靠游标对齐，本地缓存丢了也能从服务端重建。***
> [!Info] 可能的追问:
> - Q: 本地 SQLite 会不会和服务端不一致？
> - A: 会短暂不一致（本地是快照）——但**服务端权威 + 游标增量同步**保证最终一致；本地缓存可随时清掉从服务端重建，不作为真相源。
> - Q: 冷层消息查询不是要下载所有文件吗？
> - A: 不会——冷层用「追加日志 + 元数据索引 + ranged GET」，先查索引定位到具体文件的字节区间，再按需下载，绝不全量拉取。
> - Q: 热→冷迁移怎么保证不丢？
> - A: 先写冷层确认、再更新索引、等客户端游标 ack 才允许热层过期，转移窗口不丢消息（同「日志是真相、索引是投影」思路）。

### 在这个通讯系统中，你是如何用多线程提升性能的？
**回答话术：**
多线程的收益在**并行利用多核 + 隔离不同职责**，本项目体现在：
1. **I/O 线程池**：多个 I/O 线程并行处理收发与切帧，突破单线程 I/O 吞吐
2. **业务 worker 与 I/O 解耦**：I/O 线程只收发，业务逻辑进 worker 处理，两者并行不互相拖慢
3. **不同职责分线程/分服务**：网络收发、业务处理、消息持久化、文件传输各自独立，一个环节慢不阻塞其他
4. **池化复用**：连接池、线程池避免频繁创建销毁开销
5. **水平扩展**：聊天服务多实例，每实例多线程，整体吞吐靠「多核 × 多实例」摊薄。
关键：多线程必须配合**正确的并发模型**（本项目的单线程业务队列避免锁竞争 + I/O 线程池并行收发），否则多线程引入锁竞争反而更慢。
***引申知识: 多线程提效的前提是「**把可并行的部分分开、把必须串行的部分保护起来**」——I/O 天然可并行（多路复用 + 线程池），业务若可分区（按用户分片）则并行，需共享的部分才加锁；盲加线程 + 抢锁是负优化。***
> [!Info] 可能的追问:
> - Q: I/O 线程池和业务 worker 为什么分开？
> - A: 收发是 I/O 密集、业务是 CPU 密集，分开可分别优化（I/O 线程多路复用、worker 专注计算），互不阻塞；且业务串行免锁。
> - Q: 多线程会不会有锁竞争？
> - A: 核心设计规避了——业务用**单线程队列串行**免锁；I/O 线程间共享数据少、用轻量无锁/原子；需共享的部分才加锁并缩到最小临界区。
> - Q: 什么时候多线程反而慢？
> - A: 任务本身极轻、线程切换/锁竞争开销大于并行收益时；或共享数据竞争激烈时。所以「单线程免锁 + 多实例并行」常常比「单实例多线程抢锁」更优。
### IM 客户端如何做到网络收发不阻塞界面？跨线程信号槽如何保证安全？
**回答话术：**
线程模型设计是**三层分离**：网络层（收发与协议解析）、业务层（消息处理）、UI 层（界面渲染）分属不同线程，层间用**队列 + 信号槽**衔接。
- 网络线程收到完整消息帧 → 解析后**入业务队列**（生产者）；业务线程消费处理（落 SQLite、更新会话状态）→ 处理结果通过**跨线程信号**（QueuedConnection）投递到 UI 线程
- 信号跨线程发送时，Qt 自动把调用打包成**事件**投递到接收者（UI 线程）的事件队列，由界面线程事件循环取出执行——**调用槽函数的代码一定在 UI 线程**，更新控件天然线程安全，不需要手动加锁
- 界面线程只消费处理结果、刷新界面，不做网络 IO、不碰 SQLite 写，保证主线程不被阻塞、滚动不卡
这样实现「网络线程收、业务线程处理、界面线程渲染」各司其职，配合异步非阻塞 IO + 半包缓冲，收发不卡界面。
***引申知识: Qt 跨线程通信的哲学是「事件投递代替锁」——QueuedConnection 把一个函数调用变成事件跨线程排队，接收方线程串行执行，消除跨线程数据竞争的加锁需求；界面更新必须发生在 GUI 线程是 Qt 的铁律（QObject 线程亲和性）。***
> [!Info] 可能的追问:
> - Q: 为什么 UI 只能在主线程更新？
> - A: Qt 控件非线程安全且与线程绑定（QObject 线程亲和性），跨线程直接改控件就是数据竞争；通过信号槽 Queued 投递到主线程执行则天然串行安全。
> - Q: 业务线程的处理结果怎么回 UI？
> - A: 处理完成 emit 信号，连接 UI 线程对象的槽（跨线程自动 Queued），信号参数按值拷贝打包进事件，UI 线程取出执行。
> - Q: 大量消息时 UI 还会卡吗？
> - A: 会——最终仍由 UI 线程逐条渲染，消息过多时渲染本身成瓶颈；所以界面做**惰性渲染**（可见区才构建气泡）、批量插入、滚动时暂停加载。

## 进销存系统
### 你的 ORM 是怎么实现的？
**回答话术：**
每个 DO（数据对象）继承 BaseDo，构造函数里用 `std::function` getter 把字段注册成**「字段域」**，记录列名 + 类型占位符（s/i/d/dt 等）+ 取值函数。BaseDao 遍历字段域，按列名拼装 INSERT/UPDATE/DELETE/SELECT **动态 SQL**，字段值经 getter 取出放入参数集，交给 PreparedStatement 绑定执行。增删改查、批量、分页都由这套元数据驱动，业务 DAO 不手写 SQL。
***引申知识: 这是「运行期元数据反射」——C++ 没有语言级反射，用 `std::function` 收集字段访问器实现轻量反射；编译期用 Concepts/static_assert 约束类型，运行期反射 + 编译期类型安全两条线结合。***
> [!Info] 可能的追问:
> - Q: 为什么不用现成 ORM 框架？
> - A: 1. 为学习与掌控底层
>   2. 自研能定制**动态 SQL 和事务内分批批量写入**等特定需求
>   3. 基于运行期元数据天然支持动态 where 和批量参数化
> - Q: 动态 SQL 里的 where 条件怎么拼？
> - A: 根据传入条件**有选择地拼接**字段段（有值才加），全部走参数占位符；字段名来自注册列名（可信）、值来自参数集（防注入），「动态」不牺牲安全。
> - Q: 参数集为什么用 `std::variant`？
> - A: 参数类型不固定，`variant` **类型安全承载多类型**，配合 `visit` 分发到 PreparedStatement 的 setXxx，比 `void*` /varargs 安全。

### JWT 鉴权是怎么做的？JWT 鉴权是为了什么？
**回答话术：**
**为什么**：HTTP 是无状态的，JWT 让服务端**无需保存会话**即可校验请求身份，token 自包含用户信息与过期时间，天然适合**分布式多服务**（每个服务都能验签，不必查共享 session）。
**怎么做**：登录成功用密钥/私钥签发 JWT（Header + Payload + Signature 三部分 Base64Url 拼接）；客户端请求带 `Authorization: Bearer <token>`；所有 Controller 统一挂 `CustomerAuthorizeHandler` 授权处理器，进入业务方法前**校验签名 + 过期时间**，通过才放行，失败返回 401；公开接口走白名单。
***引申知识: Signature 是「对 Header+Payload 用密钥签名」，payload 可被 Base64 解码（不加密）、但改任何字段签名即失效（不可篡改）；RSA 非对称适合多服务共享公钥验签，HMAC 对称适合单服务快。***
> [!Info] 可能的追问:
> - Q: JWT 和 Session 区别？
> - A: Session 是**服务端存储状态 + 客户端存 sessionId**，需共享/持久化；JWT **无状态**自包含签名，天然适合分布式。代价是 JWT 无法主动吊销（需黑名单）。
> - Q: JWT 泄露/过期怎么处理？
> - A: 设**过期时间（exp）**、refresh token 刷新；服务端维护**黑名单**吊销；敏感信息不放进 payload（签名不加密）。
> - Q: WebSocket 的 AI 客服怎么鉴权？
> - A: 用 oatpp-websocket 连接处理器；/chat 在白名单放行，**Token 通过 WebSocket 子协议（Sec-WebSocket-Protocol）传递**，握手时读取校验，连接建立后注入用户参数。

### 你如何通过 RocketMQ 做各种服务的解耦？
**回答话术：**
把**强同步耦合**改成**异步事件流**：单据创建/审批等核心动作完成后，Producer 只发一条**事件消息**（单据已创建/已审批），下游报表生成、库存变动、日志记录作为**独立 Consumer** 各自订阅、各自消费。收益：
1. **上游不依赖下游**——下游挂掉/变慢不影响主流程
2. **下游独立扩展**——报表慢就多起消费实例
3. **新增下游只需新加 Consumer**，不动上游。
配合**事务消息**（半消息 + 本地事务确认 + Broker 回查）保证「单据入库」和「事件发布」一致；**幂等消费 + 重试**保证不丢不重。
***引申知识: 解耦的本质是发布/订阅（上游只发事件、下游自己消费）；「至少一次 + 幂等」是 MQ 可靠性的黄金组合；事务消息的最终一致性靠「先发半消息 → 本地事务成功再确认 → 超时回查」闭环。***
> [!Info] 可能的追问:
> - Q: 为什么能实现削峰填谷？
> - A: 大促/月末瞬时写入量大，消息先**积压在 Broker 缓冲**，数据库按稳定速率消费，避免瞬时打爆数据库，用时间换峰值稳定性。
> - Q: 下游消费失败怎么办？
> - A: **可重试**（重试 3 次），仍失败进死信/人工处理；上游不因下游失败而失败，只保证「消息至少被处理一次」。
> - Q: 怎么保证事件不丢、不重复？
> - A: 不丢靠 Producer 同步发送 + Broker 持久化 + 消费重试；不重复靠消费者**幂等**（按业务主键去重）。核心是「至少一次 + 幂等消费」。

### 「单据提交接口 P95 由 ~300ms 降至 ~60ms，P99<120ms」是什么意思？你如何测出来的？
**回答话术：**
**含义**：P95 指 95% 的请求耗时在 60ms 内（优化后）、P99 指 99% 在 120ms 内；优化前 P95≈300ms。优化手段是把同步等待下游（报表生成、库存扣减、日志）改成**异步发消息**，主线程只做「落库 + 发消息」立刻返回。
**怎么测出来的**：
1. **接口耗时埋点**——接口入口/出口记时间，采集每次请求耗时
2. **压测**——wrk/自定义压测打一定并发与请求量
3. **分位计算**——耗时排序取 95%、99% 分位点
4. **前后对比**——同环境、同参数下异步化前后各测一轮，去掉冷启动/缓存预热影响，多次取稳定值。
***引申知识: 为什么用 P95/P99 而不用平均值——平均值被少量极慢请求拉高、也掩盖大量慢请求；分位数反映**尾部延迟**，在线服务用户感知的正是尾部。***
> [!Info] 可能的追问:
> - Q: 异步化为什么能降 P95 这么明显？
> - A: 把同步等待下游的 200-300ms 移出请求线程，主流程只剩落库 + 发消息的毫秒级操作，返回快，请求耗时的**尾部**显著下降。
> - Q: 压测结果可信吗？误差来源？
> - A: 学习/联调环境的**相对优化**结论可信，绝对值受环境影响（机器、网络、并发参数、数据量）。误差来源：冷启动、缓存预热、并发不均、其他进程干扰。控制变量 + 多次取稳定值可减小误差。

### 你的 MongoDB 只用来增量记录日志吗？记录的日志用来做什么？
**回答话术：**
不止。我把它作为**文档型存储**用于两类数据：
1. **运行/操作审计日志**——写多读少、结构易变，用 Mongo 避免高频日志写入膨胀 MySQL 核心表
2. 日志的用途：**故障排查**（回溯某次操作/异常的完整上下文）、**行为审计**（谁在何时做了什么）、**业务追溯**（对应 ERP 的「追溯」能力，追单据流转历史）。
***引申知识: 文档型 vs 关系型——日志「写多读少、结构易变、无需事务/JOIN」正是 schema-less + 可水平扩展（分片）的适用场景；放 MySQL 会高频写入膨胀核心表、竞争资源、拖慢主业务。***
> [!Info] 可能的追问:
> - Q: 审计日志怎么保证不丢？
> - A: 写日志走**独立队列异步落库**（批量 + 定期刷），关键操作同步确认；配合 WiredTiger 持久化 + 副本集，掉电不丢已确认数据。
> - Q: 日志量大怎么办？
> - A: 按时间**分片/分库**、定期归档冷数据、设置 TTL 过期；只保留最近窗口热数据，长期历史归档到对象存储/冷库。

### Nacos 在项目中到底做了什么？你是如何使用的？
**回答话术：**
做两件事：**注册中心**和**配置中心**。
**注册中心**：服务启动时向 Nacos **注册自身**（IP:port + 元数据），启动 <1s 自注册；每 5s 发心跳，异常实例 15s 判不健康、30s **自动剔除**；调用方从 Nacos 拉取实例列表做**负载均衡**（权重分发），实现多实例流量分摊与故障自愈。
**配置中心**：把数据源/中间件配置集中管理，变更时服务端推送/客户端长轮询拉到新值，**秒级生效、无需重启**。
**我的使用**：多实例服务都接 Nacos 注册发现 + 配置下发；客户端本地缓存实例列表 + 配置，注册中心短暂不可用也能**容灾降级**继续服务。
***引申知识: 注册中心是「辅助不是主链路」——客户端有本地缓存实例列表，注册中心挂了已建立的调用不受影响；这体现「注册发现要能降级」的容灾设计。***
> [!Info] 可能的追问:
> - Q: 故障剔除与负载均衡怎么做的？
> - A: 实例心跳 5s/次，异常实例 15s 判定不健康、30s 自动剔除，新请求不再路由到故障节点；调用方本地维护实例列表做负载均衡（权重分发）。
> - Q: 注册中心挂了会怎样？
> - A: 因有**本地缓存实例列表 + 容灾降级**，已建立的调用不受影响；新实例注册/变更暂时失效，恢复后重连同步。

### 你如何做到配置更改之后不用重新编译或重启服务就能让服务器使用新的数据的？
**回答话术：**
核心是**配置与代码分离 + 动态加载**：
1. 配置从代码里抽出来放到**配置文件/配置中心**（数据源、中间件、业务开关都不硬编码）
2. 程序启动读取、运行时**监听配置变化**——本地文件监听变更 + 重载回调，配置中心用「推送/长轮询拉取」
3. 业务侧对配置项注册**变更回调**（如数据源地址变化重建连接池、业务开关变化即时生效）。链路：配置变更 → 通知 → 回调更新 → 生效，全程**不重编译不重启**。
***引申知识: 与本地配置文件比，配置中心**集中管理 + 广播/长轮询**，改一处全部实例同步，还有版本管理和回滚；这是「控制面与数据面分离」思想的落地。***
> [!Info] 可能的追问:
> - Q: 配置变更时正在进行的请求怎么办？
> - A: **灰度 + 优雅过渡**：新配置只影响之后的新请求/新连接，存量请求继续用旧值（如连接池重建不影响在用的连接，等归还后按新配置重建）。
> - Q: 配置格式错误/加载失败怎么兜底？
> - A: **本地缓存 + 旧值回退**：拉取/解析失败时用上一次成功的配置继续服务，不因配置错误崩服务；校验不通过则报警并保持旧配置。

### 为什么 JWT 你用了两种算法（RSA 和 HMAC）？
**回答话术：**
两种算法解决**不同场景的验签需求**：
- **HMAC（对称）**：签名和验签用**同一把密钥**。优点：实现简单、快；缺点：**签发端和所有验签端共享密钥**，任何一方泄露都能伪造 token，只适合**单服务 / 信任域内**使用。
- **RSA（非对称）**：**私钥签发、公钥验签**，私钥只在签发端，其他服务只需持有**公钥**即可验签、但无法伪造。适合**分布式多服务**——多个后端服务共享公钥验签，安全隔离签发权。
**为什么两种都要**：项目里**内部单服务**（或性能敏感、信任环境）用 HMAC（快）；**需要跨服务验签 / 更安全**的场景用 RSA（私钥隔离）。两种都封装，按场景选用，体现对不同鉴权形态的覆盖。
***引申知识: 选型本质是「**对称（快、共享密钥）vs 非对称（安全、私钥隔离）**」的权衡；微服务 / 多服务验签几乎必选非对称（共享公钥、私钥只在认证中心），单机内部可用对称省开销。***
> [!Info] 可能的追问:
> - Q: RSA 和 HMAC 哪个快？
> - A: HMAC 快（对称哈希运算）；RSA 验签也较快但签发慢、密钥管理复杂。性能敏感 + 单信任域用 HMAC，多服务 / 安全敏感用 RSA。
> - Q: 两种能混用吗？
> - A: 可以——按接口/服务选择：对外 / 跨服务用 RSA，内部高频低敏感用 HMAC；关键是密钥管理和「哪些服务能验签 / 签发」要清晰。
> - Q: RSA 私钥泄露了怎么办？
> - A: 轮换密钥 + 设置 token 短有效期 + refresh token；私钥放安全设施（密钥管理服务、环境变量、硬件），不落代码 / 日志。

### 你在进销存系统中用 RocketMQ 在什么场景解决了什么问题？
**回答话术：**
**场景**：单据（采购 / 销售 / 退货）的**创建与审批**这类核心动作完成后，需要触发一系列下游任务——**报表生成、库存变动、记录日志**。
**没解耦的问题**：这些下游任务如果都**同步**在创建单据的请求线程里执行，主接口被下游拖慢（报表慢则整单慢）、任一下游抖动都导致整单失败、上下游强耦合。
**MQ 解决**：创建 / 审批完成后只发一条**事件消息**，下游作为**独立 Consumer 异步消费**，获得：
1. **解耦**——上游不依赖下游，下游挂了 / 慢不影响主流程
2. **削峰填谷**——瞬时大量单据，消息先积压 Broker，DB 按稳定速率消费，避免打爆
3. **可重试**——下游消费失败重试，不因一次失败丢数据
4. **事务一致性**——事务消息（半消息 + 本地确认 + Broker 回查）保证「单据入库」与「事件发布」一致。
**效果**：主接口 P95 由 ~300ms 降至 ~60ms。
***引申知识: MQ 的价值本质是「**把强同步耦合改为异步事件流**」——上游只发布事件、下游自主订阅消费；配合「至少一次 + 幂等」保证可靠，「事务消息」解决异步化后的一致性。***
> [!Info] 可能的追问:
> - Q: 哪些场景不值得用 MQ？
> - A: 要求实时同步返回、事务强一致（必须即时看到结果）、下游必须同步执行完成的场景不适合；MQ 适合「可异步、可容忍短暂延迟」的下游任务。
> - Q: 报表生成怎么保证数据最终正确？
> - A: 消费端**幂等 + 重试**，报表按单据号去重累加；配合事务消息保证事件不丢，最终一致性由「至少一次消费 + 幂等」保证。
> - Q: 消息积压怎么处理？
> - A: 增加消费实例 / 并发、批量消费、排查慢消费；削峰设计让消费速率匹配生产速率。

### 使用消息队列之前，单据提交接口是怎么做的？（P95 如何从 300ms 到 60ms）
**回答话术：**
**MQ 之前**：单据创建请求到达后，**在同一请求线程里同步串行执行**：
1. 落库单据 → 2. **同步生成报表** → 3. **同步扣减库存** → 4. **同步写操作日志** → 5. 返回。
每个下游都是同步阻塞调用，耗时叠加；报表 / 库存这类重活若慢（几百 ms），整个请求跟着慢，**P95 ≈ 300ms**；且任一下游报错，整单失败回滚。
**MQ 之后**：请求线程只做「**落库 + 发一条事件消息**」两步立刻返回（毫秒级），报表 / 库存 / 日志由**消费者异步**去处理：
- 主线程耗时从「落库 + 全部下游」变成「落库 + 发消息」，尾部延迟骤降
- P95 从 ~300ms 降至 ~60ms，P99 < 120ms。
**本质**：把**同步等待下游的时间移出请求线程**，用异步 + 削峰换取低延迟，代价是报表 / 库存等**短暂延迟可见**（最终一致）。
***引申知识: 这是「**同步调用 → 异步消息**」改造的典型收益——主路径只保留必要同步操作（落库 + 发消息），把可延后的重活移出请求链路；延迟降低的本质是「不在请求线程里等下游」，而非某个操作变快了。***
> [!Info] 可能的追问:
> - Q: 异步后用户马上看不到报表 / 库存更新，能接受吗？
> - A: 能——这类操作**不要求同步实时可见**，秒级最终一致可接受；且换来主接口更快的响应和更高吞吐。要求实时同步的字段仍走同步。
> - Q: 怎么保证异步后数据不丢？
> - A: 事务消息 + 消费重试 + 幂等，保证「单据已入库 → 事件必发 → 下游必消费」，最终一致不丢。
> - Q: P95 测出来真实可靠吗？
> - A: 是**同环境、同参数下异步化前后对比**的相对结论（见 P95 那题），绝对值受环境影响，机制收益是真实的。

### 将消息体包装成 DAO 提高通讯效率是什么意思？谈谈你对 DAO 的理解？
**回答话术：**
**DAO（Data Access Object，数据访问对象）**是分层架构里的**数据访问层抽象**——把「业务逻辑」和「数据操作」分离：DAO 封装对数据源的增删改查，业务层只调用 DAO 接口，不直接碰 SQL / 连接。好处：**职责清晰、可复用、可替换数据源、便于测试（可 mock）**。
**「包装成 DAO 提高通讯效率」**是指：HTTP 接口的消息体（请求 / 响应）统一由 **DAO 封装的数据结构**承载，而不是每个接口各自拼结构。收益：
1. **统一序列化**——消息体结构统一，序列化 / 反序列化一次设计、处处复用，避免每接口重复编码
2. **契约一致**——前端 / 客户端面对统一结构，解析逻辑一致，减少适配
3. **连接 / 参数复用**——DAO 层集中管理连接与参数绑定（结合 PreparedStatement），减少重复建连与拼接
4. **类型安全**——DAO 用类型化对象而非散乱的 Map / 字符串传数据，减少解析错误与转换开销。
***引申知识: 要区分两个「DAO」——**架构层的 DAO（数据访问对象，本意）** 与 **业务里把消息体 / 实体封装成可复用的访问对象**；面试官若问「DAO 为什么提升效率」，核心是「**统一封装 → 复用序列化与连接 → 类型安全 → 契约一致**」，而不是 DAO 本身更快，是「减少重复、统一处理」带来的效率。***
> [!Info] 可能的追问:
> - Q: DAO 和 Repository 的区别？
> - A: 两者都隔离数据访问；DAO 偏底层（CRUD、贴近数据源），Repository 偏领域（以聚合 / 领域对象为中心、更接近业务语义）。本项目用的是 DAO 风格。
> - Q: DAO 层会不会是性能瓶颈？
> - A: 不会——DAO 层本身是薄封装，性能取决于连接池、SQL、序列化；DAO 反而通过连接复用、参数绑定、统一序列化**减少重复开销**。
> - Q: 为什么说 DAO 便于测试？
> - A: 业务依赖 DAO **接口**而非具体实现，测试时可用 mock / fake DAO 替换真实数据源，隔离测试业务逻辑，不碰数据库。
