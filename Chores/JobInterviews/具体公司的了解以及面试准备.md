## 一个具体的项目场景（看清每天做什么）
> 用「给某药企上线 QMS 的偏差 + CAPA 模块」举例，把抽象职责还原成一周的日常。eGxP 是整套软件；QMS 是其中一个模块；偏差处理、CAPA 是 QMS 里的功能。

背景：客户（比如齐鲁制药）要上 QMS，先做「偏差处理 + CAPA」两个模块。

- 周一：到客户现场，和客户质量部 QA 开会。他们现在用纸质表格 + Excel 管偏差：有人发现生产偏差，填纸质表，到处找人审批，CAPA 用 Excel 记。你说：好，我先看看你们现在的流程。→ 拿到他们的偏差表模板和审批链（谁发起、谁调查、谁批准）。
- 周二：在 QMS 产品里配置「偏差流程」：把表单字段配出来（标题/严重度/涉及部门/根本原因/处理措施），把审批流配出来（发起 → QA 调查 → 质量负责人批准 → 关闭），配通知（每步提醒谁），开审计追踪。
- 周三：客户要一个产品里没有的字段/报表 → 你用配置加，或评估后把需求反馈给开发部；同时写《偏差模块配置说明》。
- 周四：自己把配置跑一遍测试：模拟一条偏差走完流程，确认每步审批、通知、留痕都对；测试偏差关闭后自动生成 CAPA 行动项（偏差和 CAPA 联动）。
- 周五：给客户的 QA/操作员做培训，带他们实操、解答问题；收集他们觉得别扭的地方，回去优化配置。

关键理解：
- **eGxP 平台** = 这套质量管理软件的总称，QMS/DMS/TMS 等都是它的模块。
- **CAPA** = 纠正与预防措施，质量问题处理完要「改正 + 防止再犯」，CAPA 就是把「怎么改、怎么防」也流程化、留痕。
- 你的日常 = 理解客户流程 → 在系统里配置 → 测试 → 培训 → 支持，全程基本不写代码，写的是配置和文档。

## 出差到底在做什么
> 你没出过差，先消除陌生感。实施岗的出差不是"旅游式出差"，是**去客户公司驻场干活**，本质就是把上面那个场景搬到客户现场。
- 到客户现场（通常是药企的工厂/总部/生产基地），每天和客户的 QA、IT、操作员一起工作。
- 住酒店/客户安排住宿，工作日正常上班（朝九晚五左右），周末一般休息或返程。
- 出差核心内容：开需求会、配置系统、测试、培训、陪客户跑流程、写文档——和在公司做的没本质区别，只是换了地方、面对面。
- 为什么必须去现场：需求在客户脑子里、流程在他们日常里，很多问题只有面对面才能说清；培训也要当面带。
- 阶段式：一个阶段干完**回公司休整**，客户准备好了再过去。所以「一次几个月」指整个项目周期，不是连续几个月呆在外地。
- 补贴：一般有差旅补贴 + 住宿交通报销。

## 行业术语
- **GMP**：药品生产质量管理规范（药品生产的最低质量标准体系）
- **GxP**：Good x Practice，GMP/GLP/GCP 等的统称，覆盖药品全生命周期质量规范
- **21 CFR Part 11**：美国 FDA 关于电子记录、电子签名的法规——核心是电子记录要可靠、可追溯、防篡改，是 QMS/DMS/ERS 合规的底层要求
- **ALCOA+**：数据完整性国际原则——Attributable（可归因）Legible（清晰）Contemporaneous（同步/及时）Original（原始）Accurate（准确）+ 完整/一致/持久/可用
- **CAPA**：纠正与预防措施（Corrective And Preventive Action），质量问题闭环管理
- **偏差 / 变更 / 审计**：制药质量管理核心流程，正是 QMS 系统内的模块

能说出「ALCOA 是数据完整性的原则」「21 CFR Part 11 管电子记录和电子签名」这两点，足以显专业。

- 坑点：若避重就轻只说「看个人」，说明不够坦诚，要多留个心眼。

- 目的：提前知道真实辛苦点，判断能否接受。

### 成长与晋升
**Q：成长路径和晋升节奏？大概几年能带项目 / 做解决方案？**
- 可能/坑回答：实施顾问 → 高级 → 项目经理/解决方案，通常 2-4 年，看项目积累。
- 坑点：晋升常是「看项目机会」，不给明确承诺；警惕只画饼不给路径。
- 我的追问：「往项目经理或解决方案走，具体看什么能力/成果？公司有明确的晋升标准和周期吗？」
- 目的：判断天花板与晋升是否透明，是否匹配节奏。

**Q：公司对新人有没有带教/导师制和培训规划？**
- 可能/坑回答：有导师、前期集中培训产品和业务。
- 坑点：培训常是「入职自学 + 老带新」，深浅不定，别只听一句「有培训」。
- 我的追问：「新人一般多久能独立跟项目？前期培训主要在公司内部，还是会直接上客户现场实战？」
- 目的：判断能否快速上手、降低学习成本（尤其不是制药背景）。

### 转行 / 灵活性（核心顾虑）
**Q：实施工程师内部有机会转开发、产品、售前或解决方案吗？有过这样的内部转岗吗？**
- 可能/坑回答：有，但要先做 2-3 年成为资深实施/顾问，转岗看机会和个人意愿。
- 坑点：这句可接受，但若态度迟疑或说「不太常见」，说明内部转岗通道窄。
- 我的追问：「有没有具体的同事是从实施转过去的？公司支持这种内部流动吗？」
- 目的：直接回应「以后能否转」的顾虑，判断内部空间、降低「锁死」风险。

**Q：做几年实施后想往产品经理或解决方案顾问发展，公司会支持吗？需要什么条件？**
- 可能/坑回答：支持，产品/方案岗优先从一线实施里选，因为最懂客户需求。
- 坑点：这是行业通说，别当承诺；追问「具体条件」看他给不给得出。
- 我的追问：「转产品/方案一般需要几年、什么成绩？有没有现成的例子？」
- 目的：为「开发 → 实施 → 产品/方案」路线铺路。

**Q：有没有从实施岗转去售前、客户成功、海外项目的例子？**
- 可能/坑回答：有；海外项目正拓展，优先派英语好的。
- 坑点：若海外只是「未来计划」，要判断兑现概率。
- 我的追问：「海外项目现在是已经在做，还是规划中？做海外主要需要哪些能力？」
- 目的：判断海外 = 更高收入机会是否真实可达。

### 出差与生活

**Q：出差期间工作/生活怎么平衡？**

- 坑点：实施出差强度通常不低，别期望朝九晚五。
- 我的追问：「高峰期大概连续在外多少天？团队是几个人一起驻场还是一个人？」
- 目的：判断强度可承受度。

## 岗位前景分析
> [!warning] 结论
> 网上说的基本属实：这是**实施岗**，出差多、偏累、带一定咨询/服务性质，和**深度开发经验关联不大**。但它是否有前景，取决于你的**职业目标**，而不是岗位本身。

事实核查：
- 是实施岗，靠配置 + 轻二次开发交付产品，**不写核心代码**（HR 明说「不要求开发精深，搞不定的反馈开发部门」）。
- 出差多、客户现场压力大，属实。
- 有一定「服务/客户成功/咨询」性质，偏售后的多，**不是**典型销售。
- 技术背景在这里是**加分**（快速上手产品、能做二次开发、更懂数据完整性），但不会让你一直写代码。

两种可能的走向：
- 若你**想长期做开发**（后端/Qt，正是简历和之前准备的方向）→ 这个岗是**偏离**，做几年实施后再转回深度开发会变难，等于用第一份工作押注了一条你不想要的路，**不建议**。
- 若你**愿意走咨询/解决方案/项目管理**方向 → 实施是**正经的起点**，可成长为实施顾问、项目经理、解决方案专家、客户成功，技术 + 英语是你的差异化优势，且这家公司在做海外 = 有机会走国际咨询（收入更高）。

决策框架（问自己三问）：
1. 你真正想长期做的是不是写代码？如果是，别为「有个 offer」而转，你的开发底子够拿开发 offer。
2. 你是不是对和人打交道、理解业务、项目管理有兴趣？有兴趣则实施是加分项。
3. 你是把它当「第一志愿」还是「保底」？保底心态最危险——第一份工作决定初始赛道。

> [!warning] 对明天的建议
> 面试前先对自己诚实：想清楚到底要不要走实施/咨询。若内心仍想开发，就别在面试里假装向往实施（双向都亏）；若决定试，就坚定表现「既懂技术又愿面向客户」。

## 开发 vs 实施对比
> 数字是量级参考，别当精确值。

| 维度 | 开发岗（后端/C++） | 实施 / 咨询岗 |
|------|-------------------|--------------|
| 校招入口 | 一线 20-35w / 二线 12-20w 总包 | 厂商实施 8-15w + 出差补贴，通常低于开发 |
| 核心能力 | 技术深度：系统设计、性能、架构、底层 | 业务理解 + 沟通 + 项目管理 + 行业知识 |
| 发展路线 | 初级 → 中高级 → 架构师 / 技术专家 / 技术管理 | 实施顾问 → 高级顾问 → 项目经理 → 解决方案 / 售前 / 客户成功 |
| 顶点 | 高：大厂架构师 / 技术总监，50-100w+ | 中高：厂商内项目经理 / 解决方案 25-50w；顶级咨询更高（需走咨询赛道） |
| 晋升难度 | 竞争激烈，越往上越靠真本事 + 持续学习 | 靠项目经验 + 行业年限 + 软技能，相对线性 |
| 技术贬值风险 | 低端 CRUD 被 AI 压缩明显，中高端仍稀缺 | 更抗 AI（靠人、上下文、信任），但入门段也偏执行 |
| 中年危机 | 明显（35 岁未到管理/架构，易被更年轻更便宜替代） | 较轻（行业经验 + 客户关系 + 管理能力随年龄增值），但体力/出差耐受力下降 |
| 退出 / 转型 | 技术管理、架构、创业、转产品/咨询 | 项目管理、售前、产品、咨询、独立顾问 |

关键判断：AI 让「照明确需求写样板代码」贬值，但不让「理解需求、设计系统、验证 AI 输出、为结果负责、和人类打交道」贬值。所以核心不是「技术贬值」，而是「只写代码的人贬值」。真正的护城河是更快到达高判断、不可替代的层级，两条路都有这一层。

## 第一份工作选择
> [!warning] 结论
> 若目标是保留「跳槽/转行」弹性（开发跳实施/产品，或实施跳回开发），第一份选**开发**。原因在可逆性不对称：
- 开发 → 实施/产品/PM：容易。技术背景是加分，toB 公司抢着要懂技术的做实施/解决方案/产品，方向向下/横向，随时能转。
- 实施 → 开发：极难。做几年配置/交付/支持，编码能力退化、简历是「实施经验」；回开发要重新过技术面试，且年龄越大越吃亏（35 危机）。

一句话：开发是「枢纽」可朝任何方向转，实施是「辐条」转出去基本回不到开发。第一份放开发 = 把「随时能转」的选项握在手里。

结合目标（攒钱开小店躺平）：
- 攒钱：开发（能到中高级）前期薪资明显高于厂商实施，攒启动金更快。
- 选项：开发身份能随时跳实施/产品/PM，进可攻退可守。

诚实前提：前提是能真实拿到并胜任一份初级开发工作（简历有包装，需把「核心」补成真的）：
- 初级后端/C++ 核心：C++ 语法与内存、数据结构、能写业务代码、会用 Git/调试。
- 高深包装点（协程/中间件细节）面试答得出即可，工作不需要全懂。
- 若不真补核心，进去露馅/试用期不过，反而断送起点。

兜底逻辑：若确实拿不到开发 offer，才选实施，但要接受两个条件：
1. 放弃「回开发」计划，全力走 实施/咨询/项目管理 路线（资深也够攒开小店的钱）。
2. 别用「害怕技术贬值」当转实施的理由，要用「我愿意走业务/管理线」来定。
