### 3. 在项目中用到了什么优化的点？
**回答要点：**
- 内存池：三层缓存架构，自旋锁减小锁粒度，固定大小分配 O(1)
- 异步日志：多缓冲区 + 环形队列 + 编译期求值，避免直接磁盘 I/O
- HTTP 服务器：epoll ET 模式 + 线程池，动静路由分离（前缀树 + 哈希表）
- 数据库连接池：连接复用减少三次握手，心跳检测无效连接
- 回答时挑 1~2 个深入展开，体现"遇到了什么问题 → 怎么分析 → 怎么解决 → 效果如何"的完整思路

### 4. 项目中遇到的难点是什么？如何解决的？
**回答要点（推荐日志库性能优化）：**
- 问题：初始 mutex 锁写操作，性能仅 30 万行/秒
- 分析：瓶颈在锁竞争和磁盘 I/O 等待
- 方案：多缓冲区异步写入——前端写环形缓冲区，后端线程批量刷盘
- 微优化：自旋锁代替互斥锁（锁持有极短）、编译期计算日志等级和格式化、对齐内存避免伪共享
- 结果：提升到 220 万行/秒

### 6. 实习中如何定位排查困难的 Bug？
**回答要点：**
- 先复现，确定稳定/偶现，缩小触发条件范围
- 用工具：gdb（断点 + backtrace）、strace（系统调用跟踪）、AddressSanitizer（内存问题）、Valgrind
- 二分法注释/隔离代码段，定位到具体模块和函数
- 举例：遇到过一个偶发的 use-after-free，通过 AddressSanitizer + 日志定位到某处 delete 后未置空指针
- 修复后补充单元测试防止回归

### 7. 怎么定位排查程序接口调用变慢的情况？
**回答要点：**
- 先用 top/htop 看 CPU 和内存，判断是否资源瓶颈
- 用 perf 采样热点函数，定位 CPU 消耗在哪
- 用 strace -c 统计系统调用次数和耗时（看是否有过多系统调用）
- 用 iostat/vmstat 看磁盘 I/O 和上下文切换频率
- 检查是否锁竞争导致线程阻塞（gdb thread apply all bt 看等待在哪）
- 应用层：打日志记录接口耗时分布，找到最慢的环节
- 结合具体场景举例（如 HTTP 请求变慢，发现是数据库连接池满导致等待）
