## 第1章：C/C++ 语言基础

---

### 1.1 C 和 C++ 有什么区别？

**回答话术：**
C++ 是 C 的超集，主要区别在于：C++ 支持面向对象（封装、继承、多态）、泛型编程（模板）、异常处理、函数重载和运算符重载。C++ 通过 RAII 和智能指针提供更安全的内存管理，还有 STL 标准库。C 是面向过程的语言，更贴近硬件，执行效率在某些场景略高，但大型项目开发效率较低。

**知识点讲解：**
- C++ 在 C 基础上增加了：class、虚函数、模板、异常、namespace、引用、new/delete、STL 容器和算法
- C 的 struct 只有数据成员；C++ 的 struct/class 可以有成员函数、继承、访问控制
- C 的强制类型转换；C++ 提供 static_cast/dynamic_cast/reinterpret_cast/const_cast
- C++ 的函数重载靠名字修饰（name mangling）实现，C 不支持

**可能的追问：**
- Q: 为什么 C++ 需要 `extern "C"`？ → A: 因为 C++ 编译时函数名会被 mangling（加入参数类型信息），而 C 不会。加上 `extern "C"` 告诉链接器按 C 的方式查找函数符号，用于 C/C++ 混合编程或调用 C 库。
- Q: C 和 C++ 的 struct 在内存布局上是否有差异？ → A: 基本一致，都遵循对齐规则。但 C++ struct 如果有虚函数则包含虚函数表指针，头部多 8 字节（64位）。

### 1.2 static 关键字的作用

**回答话术：**
static 在不同语境有不同含义：
1. **局部静态变量**：保持变量值在函数调用间持续存在，只初始化一次，生命周期为整个程序
2. **全局静态变量/函数**：限制作用域在当前文件（内部链接），其他文件不可见
3. **类静态成员变量**：所有对象共享同一份，需要在类外单独定义
4. **类静态成员函数**：属于类而非对象，没有 this 指针，只能访问静态成员

**知识点讲解：**
```cpp
void func() {
    static int count = 0;  // 只初始化一次，多次调用累加
    count++;
}
class MyClass {
    static int s_val;       // 声明
    static void s_func() {} // 没有 this 指针
};
int MyClass::s_val = 0;     // 定义
```

**可能的追问：**
- Q: static 局部变量是线程安全的吗？ → A: C++11 起，static 局部变量的初始化是线程安全的（编译器会加锁保证只初始化一次），但后续修改仍需同步。
- Q: static 成员函数为什么不能是 const 或 virtual？ → A: const 限制修改 this 所指对象，但 static 函数没有 this；virtual 依赖对象的虚函数表，static 属于类不参与多态。

### 1.3 const 和 volatile 关键字的区别

**回答话术：**
- **const**：声明变量不可修改，编译期约束。指针场景有 const int*（指向内容不可改）和 int* const（指针本身不可改）
- **volatile**：告诉编译器该变量可能被意外修改（如硬件寄存器、多线程共享变量），禁止编译器对其读取做优化（每次从内存读，不从寄存器缓存读）

**知识点讲解：**
```cpp
const int a = 10;     // a 不可修改
const int* p = &a;    // *p 不可改，p 可改
int* const q = &a;    // q 不可改，*q 可改（但 a 本身是 const 会有 warning）

volatile int flag;    // 每次从内存读，多用于中断或信号处理
while (flag);         // 如果 flag 不是 volatile，编译器可能优化成死循环
```

**可能的追问：**
- Q: const_cast 的作用和风险？ → A: 去掉 const 属性。如果原对象本身就是 const，修改它是未定义行为。
- Q: volatile 能保证多线程安全吗？ → A: 不能。volatile 只防止编译器优化，不保证内存可见性（不插入内存屏障）。多线程同步应使用 mutex 或 atomic。

### 1.4 struct 和 class 的区别

**回答话术：**
C++ 中 struct 和 class 在功能上完全等价，唯一区别是默认访问权限：struct 默认 public，class 默认 private。继承时同理，struct 默认 public 继承，class 默认 private 继承。

**知识点讲解：**
```cpp
struct A { int x; };          // x 默认 public
class B { int x; };           // x 默认 private
struct C : A {};              // public 继承
class D : B {};               // private 继承
// 实践中 struct 多用于 POD 类型的数据聚合，class 用于封装行为的对象
```

**可能的追问：**
- Q: C 语言的 struct 和 C++ 的 struct 有什么区别？ → A: C 的 struct 不能有成员函数、继承、访问控制；C 中定义结构体变量必须加 struct 关键字（除非 typedef）。
- Q: POD 类型是什么？ → A: Plain Old Data，与 C 兼容的简单数据结构，没有虚函数、自定义构造/析构、非静态成员的 private/protected 访问等。

### 1.5 new 和 malloc 的区别

**回答话术：**
1. new 是 C++ 运算符，malloc 是 C 标准库函数
2. new 自动计算大小并返回正确类型指针，malloc 需手动指定字节数，返回 void*
3. new 分配内存后**调用构造函数**，malloc 只分配原始内存
4. new 失败抛出 bad_alloc 异常，malloc 失败返回 NULL
5. new 可被 operator new 重载，支持 placement new
6. 对应释放：delete（调用析构函数）和 free（不调用）

**知识点讲解：**
```cpp
int* p1 = new int(42);         // 分配 + 构造
int* p2 = (int*)malloc(sizeof(int)); // 仅分配
free(p1);                      // 错误！new/delete 和 malloc/free 必须配对
// placement new: 在已有内存上构造
void* buf = malloc(sizeof(string));
string* s = new (buf) string("hello");
s->~string(); // 手动调用析构
free(buf);
```

**可能的追问：**
- Q: new[] 和 delete[] 不匹配会导致什么？ → A: new[] 会在头部记录数组长度（实现相关），delete[] 根据这个长度逐个调用析构函数。用 delete 代替 delete[] 可能只析构第一个对象或内存泄漏。反过来也是未定义行为。
- Q: operator new 可以重载吗？应用场景？ → A: 可以。用于内存池、对象池等场景，提前分配大块内存减少系统调用。

### 1.6 内联函数（inline）的优缺点

**回答话术：**
**优点：** 消除函数调用开销（压栈、跳转、返回），编译器可能基于更大上下文做进一步优化（如常量传播）。
**缺点：** 增加代码体积（代码膨胀），可能降低指令缓存命中率；修改 inline 函数需要重新编译所有调用方；无法递归（理论上可以，但只能展开一层）；调试不便（无法在调用处设断点）。

**知识点讲解：**
- inline 只是对编译器的**建议**（C++98/03），编译器可选择忽略
- C++17 起 inline 变量可用于头文件中定义全局变量，解决 ODR 违反
- 放在类定义体内的函数默认是 inline 的
- 现代编译器对 inline 的优化非常智能，通常由编译器决定是否内联

**可能的追问：**
- Q: inline 函数和宏的区别？ → A: 宏只是文本替换，没有类型检查、作用域；inline 是真正的函数，有类型检查、作用域、调试信息。宏可能多次计算参数（MAX(a++, b) 这样的陷阱）。
- Q: C++17 inline 变量解决了什么问题？ → A: 头文件中定义全局常量/变量时，如果被多个 .cpp include 会导致多重定义链接错误。C++17 前需要用`constexpr` 或 `inline` 函数返回引用来绕开。inline 变量允许在头文件中直接定义。

### 1.7 explicit 关键字的作用

**回答话术：**
explicit 用于修饰单参数的构造函数（或 C++11 起多参构造函数），防止编译器进行隐式类型转换。避免预期之外的对象构造。

**知识点讲解：**
```cpp
class String {
public:
    explicit String(int n) {}   // 禁止隐式转换
    String(const char* s) {}    // 允许隐式转换
};
String s1 = 'a';   // 错误！explicit 构造函数不能隐式调用
String s2 = "abc"; // 允许，const char* 隐式转换
void func(String s);
func('x');         // 错误！String(int) 被 explicit 阻止
```

**可能的追问：**
- Q: C++11 起 explicit 还能用于转换运算符？ → A: 是的，`explicit operator bool()` 可以防止对象被隐式转换为 bool，如在 if 条件中需要显式转换。
- Q: 为什么建议单参构造函数都加 explicit？ → A: 防止意料之外的隐式转换导致的 bug。如果确实需要隐式转换再不加。

### 1.8 重载（overload）和重写（override）的区别

**回答话术：**
- **重载**：同一作用域内，函数名相同但参数列表不同（个数/类型/顺序）。编译期多态，由编译器根据参数类型确定调用哪个版本
- **重写**：子类重写父类的虚函数，函数签名必须相同。运行期多态，通过虚函数表在运行时确定调用哪个版本

**知识点讲解：**
```cpp
// 重载（overload）—— 编译期
void print(int);
void print(string);
void print(int, string);

// 重写（override）—— 运行期，需 virtual 关键字
class Base {
    virtual void show() { cout << "Base"; }
};
class Derived : public Base {
    void show() override { cout << "Derived"; }
};
```

**可能的追问：**
- Q: override 关键字的作用（C++11）？ → A: 显式标记子类重写的函数，编译器会检查基类是否有对应的虚函数，避免拼写错误或签名不匹配导致的"本以为重写实则新建"的 bug。
- Q: 函数隐藏（hiding）是什么？ → A: 子类定义同名函数（不管参数），父类的所有同名函数都被隐藏。即使参数不同也不会构成重载。不同于重写（需要 virtual）。

### 1.9 面向对象的三大特性

**回答话术：**
1. **封装**：将数据和操作数据的函数绑定在一起，对外隐藏内部实现，通过 public/protected/private 控制访问权限
2. **继承**：子类复用父类的成员和方法，可扩展新功能，形成类层次结构
3. **多态**：同一接口在不同对象上有不同实现。C++ 通过虚函数实现动态多态（运行期），通过模板/重载实现静态多态（编译期）

**知识点讲解：**
- 封装降低了耦合，便于维护
- 继承可用 public（接口继承）、protected/private（实现继承）
- 多态依赖于虚函数表和虚函数表指针（vtbl/vptr）

**可能的追问：**
- Q: 继承和组合如何选择？ → A: 组合优先于继承。"is-a"关系用继承，"has-a"关系用组合。组合耦合度更低，更灵活。
- Q: 多态的实现原理？ → A: 每个有虚函数的类有一个虚函数表（vtbl），对象内存头部有一个虚函数表指针（vptr）指向它。调用虚函数时，通过 vptr → vtbl → 函数指针，间接调用，实现动态绑定。

### 1.10 C++ 多态的实现原理（虚函数表）

**回答话术：**
C++ 多态通过**虚函数表（vtbl）** 实现。每个包含虚函数的类有一个 vtbl，存储函数指针。每个对象有一个隐藏的 vptr 指针指向类的 vtbl。调用虚函数时，通过 vptr → vtbl → 函数指针间接调用，实现运行期动态绑定。

单继承下，一个对象只有一个 vptr；多继承下，每个基类对应一个 vptr。构造过程中，vptr 在基类构造阶段指向基类 vtbl，进入派生类构造阶段后指向派生类 vtbl，这正是构造期间调用虚函数不会多态的原因。

**知识点讲解：**
```cpp
class Base {
public:
    virtual void foo() { cout << "Base"; }
    virtual ~Base() = default;
};
class Derived : public Base {
    void foo() override { cout << "Derived"; }
};
Base* p = new Derived();
p->foo(); // 输出 Derived，通过 vptr 动态分发
// 对象内存布局：[vptr | Base members | Derived members]
```

**可能的追问：**
- Q: 构造函数和析构函数中调用虚函数会发生什么？ → A: 调用的是当前正在构造/析构的类的版本，不是多态调用。因为构造时 vptr 指当前类的 vtbl。
- Q: 虚函数表存放在哪里？ → A: 通常只读数据段（.rodata），是编译期确定的静态数据。
- Q: 虚函数表什么时候初始化？ → A: 编译期由编译器生成，运行期在构造函数的初始化列表阶段设置 vptr。

### 1.11 模板算不算多态？

**回答话术：**
模板属于**静态多态（编译期多态）**，也称泛型多态。模板在编译期根据实参类型实例化生成具体代码，没有运行时查找开销。而虚函数多态是动态多态（运行期多态）。从"同一接口不同实现"的意义上说模板算多态，C++ 标准中确实将模板视为一种多态机制（编译期多态）。

**知识点讲解：**
```cpp
// 静态多态 —— 模板
template<typename T>
T max(T a, T b) { return a > b ? a : b; }
// 实例化出 max<int>, max<double> 等，编译期决定

// 动态多态 —— 虚函数
class Animal { virtual void speak() = 0; };
```

**可能的追问：**
- Q: 静态多态和动态多态各自的优缺点？ → A: 静态多态零运行时开销，编译器可充分优化；但生成的二进制体积增大（代码膨胀），且函数签名必须完全匹配。动态多态运行时灵活（可在运行时决定类型），但有虚函数调用开销（一次间接跳转），且不易被编译器内联优化。

### 1.12 构造函数和析构函数能否为虚函数

**回答话术：**
- **构造函数不能是虚函数**：虚函数调用依赖于 vptr，而 vptr 在构造函数体内才设置好，构造时对象还未完全创建，无法通过 vtbl 调用。从语义上，构造是确定对象类型的过程，"多态构造"无意义。
- **析构函数可以且通常应该为虚函数**：当通过基类指针删除派生类对象时，如果析构函数不是虚函数，则只调用基类析构函数，派生类资源无法释放。注意：如果类不被用作基类，则不必虚析构（增加 vptr 开销）。

**知识点讲解：**
```cpp
class Base {
public:
    virtual ~Base() {}  // 虚析构，保证派生类资源释放
};
class Derived : public Base {
    int* data = new int[100];
    ~Derived() { delete[] data; }
};
Base* p = new Derived();
delete p;  // 想调用 ~Derived()，靠虚析构实现
```

**可能的追问：**
- Q: 如果不需要多态删除，是否还需要虚析构？ → A: 不需要。虚析构会引入 vptr，增加对象体积（8字节）。如果类不被作为基类使用，可以不声明虚析构。
- Q: 纯虚析构函数可以吗？ → A: 可以，但**必须给出实现**（因为析构函数总是在继承链上被调用的）。`virtual ~Base() = 0;` + 类外 `Base::~Base() {}`。

### 1.13 空类生成哪些函数？

**回答话术：**
C++ 编译器会为一个空类自动生成六个默认成员函数（如果被使用的话）：
1. 默认构造函数
2. 默认析构函数
3. 拷贝构造函数
4. 拷贝赋值运算符
5. 移动构造函数（C++11）
6. 移动赋值运算符（C++11）

**知识点讲解：**
```cpp
class Empty {};
// 等价于：
class Empty {
public:
    Empty() = default;
    ~Empty() = default;
    Empty(const Empty&) = default;
    Empty& operator=(const Empty&) = default;
    Empty(Empty&&) = default;      // C++11
    Empty& operator=(Empty&&) = default; // C++11
};
// sizeof(Empty) 通常为 1，因为 C++ 标准要求每个对象必须有唯一地址
```

**可能的追问：**
- Q: 什么情况下编译器会拒绝生成默认函数？ → A: 如果类有 const 或引用成员，默认拷贝赋值运算符不会被生成（无法修改 const 成员或重置引用）。如果类有 move-only 成员（如 unique_ptr），拷贝构造和拷贝赋值会被删除（=delete）。
- Q: 自动生成的析构函数可以析构其他类的指针成员吗？ → A: 对于 raw 指针，自动生成的析构函数**不会**自动 delete 它们（导致内存泄漏）。对于智能指针成员（unique_ptr/shared_ptr），它们的析构函数会自动调用，所以不需要手动 delete。

### 1.14 右值引用、移动语义和完美转发

**回答话术：**
- **右值引用（&&）**：绑定到"将亡值"（即将销毁的临时对象），允许我们"偷"走它的资源而不是拷贝
- **移动语义**：通过移动构造函数和移动赋值运算符，将源对象的资源（如堆内存）转移给目标对象，避免深拷贝。源对象被置为有效但未定义的状态
- **完美转发**：利用模板 + 引用折叠规则，保持参数在传递过程中左值/右值属性不变。通过 std::forward 实现

```cpp
// 移动构造 —— 避免深拷贝
vector<string> v1(1000000);
auto v2 = std::move(v1);  // v1 的资源被转移到 v2，O(1) 操作

// 完美转发
template<typename T>
void wrapper(T&& arg) {
    func(std::forward<T>(arg));  // 保持 arg 的左右值属性
}
```

**知识点讲解：**
- 引用折叠规则：`T& &` → `T&`, `T& &&` → `T&`, `T&& &` → `T&`, `T&& &&` → `T&&`
- std::move 不做任何实际移动，只是把参数转化成右值引用（static_cast<T&&>）
- std::forward 根据模板参数决定转换：T 是左值引用就转为左值，否则转为右值
- 移动后的源对象应该处于可析构的安全状态，一般置为 null

**可能的追问：**
- Q: move 之后源对象还能用吗？ → A: 标准库容器被 move 后处于有效但未指定的状态，通常 size() 为 0。最佳实践是不要继续使用源对象（除非重新赋值）。用户自定义类型应保证 move 后的对象可析构、可赋值。
- Q: 如果没有移动构造函数，传右值会怎样？ → A: 如果只有拷贝构造（const T&），右值会匹配到拷贝构造函数，退化为拷贝。这是安全的但失去了移动优化的机会。
- Q: push_back 和 emplace_back 的区别？ → A: emplace_back 直接在容器内构造对象，完美转发参数，避免临时对象的构造和移动。push_back 需要先构造临时对象然后移动/拷贝到容器中。

### 1.15 智能指针（shared_ptr、unique_ptr、weak_ptr）

**回答话术：**
C++11 引入的三类智能指针：
- **unique_ptr**：独占所有权，不可拷贝只可移动。零开销，大小等于裸指针。通过 `std::make_unique` 创建
- **shared_ptr**：共享所有权，引用计数。拷贝时引用计数 +1，析构时 -1，归零时删除对象。大小是裸指针的两倍（一个指向对象，一个指向控制块）。通过 `std::make_shared` 创建
- **weak_ptr**：弱引用，不增加引用计数。解决 shared_ptr 循环引用问题。通过 lock() 获取 shared_ptr 检查对象是否存活

```cpp
auto u = std::make_unique<int>(42);     // unique_ptr，不可拷贝
auto s = std::make_shared<int>(42);      // shared_ptr，引用计数
std::weak_ptr<int> w = s;               // weak_ptr，不增加计数
if (auto locked = w.lock()) {           // 检查对象是否存活
    // 使用 locked
}
```

**知识点讲解：**
- 使用 make_shared 比 new shared_ptr 更高效（一次分配 + 控制块与对象合并分配）
- shared_ptr 的线程安全性：控制块（引用计数）的加减是原子操作，线程安全；但所指对象的线程安全性需要额外同步
- enable_shared_from_this：类继承它后可通过 shared_from_this() 安全地获取自身的 shared_ptr，避免 this 裸指针造成多个控制块

**可能的追问：**
- Q: 智能指针管理一定不会有内存泄漏吗？ → A: 不一定。最常见场景是 shared_ptr 循环引用（A 持有 B 的 shared_ptr，B 持有 A 的 shared_ptr），引用计数永远不会降为零，导致内存泄漏。解决：用 weak_ptr 打破循环。另外，`new` 表达式抛出异常也会导致泄漏。
- Q: shared_ptr 的线程安全性具体如何？ → A: 引用计数的增减是原子操作，多个线程同时拷贝或销毁 shared_ptr 是安全的。但同一个 shared_ptr 在多线程中同时修改（如同时 reset）会 data race。**所指对象的线程安全需要加锁**。
- Q: make_shared 的缺点？ → A: 控制块和对象在同一块内存上分配，如果 weak_ptr 还存在，即使 shared_ptr 都析构了，对象内存不能释放（因为控制块和对象在同一块分配中）。另外 make_shared 不支持自定义 deleter。

### 1.16 内存泄漏（原因、后果、预防、排查）

**回答话术：**
**原因**：new 出来的堆内存没有 delete；new[] 没有 delete[]；malloc/free 不配对；基类析构函数非虚导致派生类资源未释放；容器中存储的指针未释放；循环引用（shared_ptr）；资源句柄（文件描述符、socket、数据库连接）忘记关闭。

**后果**：程序占用的内存持续增长，最终 OOM（Out Of Memory）导致进程被系统杀死或系统卡顿。

**预防**：优先使用 RAII（智能指针、容器）；遵循所有权语义（unique_ptr 表示独占，shared_ptr 表示共享）；基类析构设为虚函数；new/delete 配对；使用 `= default` 或 `= delete` 规则。

**排查**：Linux 下使用 Valgrind（`valgrind --leak-check=full ./program`）、AddressSanitizer（编译加 `-fsanitize=address`）、或者用 mtrace。

**知识点讲解：**
- 内存泄漏分类：堆泄漏（最典型）、系统资源泄漏（句柄未释放）、对象泄漏（未 delete）

**可能的追问：**
- Q: 有没有遇到过 OOM？场景是什么？ → A: 常见场景：一次性读入超大文件到内存、创建过多线程（每个线程有自己的栈空间）、缓存未限制大小。在实际项目中遇到过因为日志缓存未及时刷盘导致的 OOM。

---

### 1.17 野指针（怎么来的、危害、如何避免）

**回答话术：**
野指针是指向"已释放内存"或"无效地址"的指针。
**来源**：
1. 指针 delete/free 后未置为 nullptr（悬空指针 dangling pointer）
2. 返回栈对象的地址（函数返回时局部变量销毁）
3. 指针未初始化

**危害**：解引用野指针导致未定义行为——可能崩溃（段错误）、数据损坏、安全漏洞（use-after-free）。

**预防**：
1. delete 后立即置为 nullptr
2. 优先使用智能指针（shared_ptr/weak_ptr 自动管理生命周期）
3. 不返回局部变量的地址或引用
4. 指针定义时立即初始化（int* p = nullptr;）

**知识点讲解：**
```cpp
int* p = new int(42);
delete p;
// p 变成悬空指针（dangling pointer）
// p 仍然指向之前的内存地址，但该内存已被释放
*p = 10; // 未定义行为！use-after-free
p = nullptr; // 好习惯

int* bad() {
    int x = 42;
    return &x; // 错误！返回栈地址
}
```

**可能的追问：**
- Q: 野指针和空指针的区别？ → A: 空指针（nullptr）指向安全的已知地址（0），解引用会明确崩溃（容易排查）。野指针指向随机地址，解引用结果是未定义行为，可能不马上崩溃，debug 困难。
- Q: shared_ptr 有悬空问题吗？ → A: shared_ptr 本身不会悬空（引用计数归零才释放），但 weak_ptr lock() 可检测对象是否存活，返回空表示对象已释放。

### 1.18 结构体中定义了 string 类型，如何 delete？

**回答话术：**
这里的核心问题是：struct 中含有 string 这种有自定义析构函数的非 POD 成员，如何正确释放。

关键在于 struct 的分配方式决定释放方式：
- 如果 struct 是通过 `new` 在堆上分配的（`struct A* p = new A;`），用 `delete p;` 自动调用 string 的析构函数释放其内部堆内存
- 如果 struct 是栈上分配的（`A obj;`），作用域结束自动调用析构函数
- 如果 struct 是用 malloc 分配的（`A* p = (A*)malloc(sizeof(A));`），必须先用 placement new 构造，然后手动调用析构 `p->~A();` 再 free(p)

**知识点讲解：**
```cpp
struct Person {
    string name;  // 有析构函数，需要被正确调用
    int age;
};
// 正确：new/delete 自动处理
Person* p = new Person{"Alice", 20};
delete p;  // 自动调用 ~string()

// 错误：malloc/free 不会调用构造/析构
Person* p2 = (Person*)malloc(sizeof(Person));  // 未构造
free(p2);  // 未析构，string 内部内存泄漏
```

**可能的追问：**
- Q: malloc 和 new 混用的后果？ → A: 如果在 malloc 分配的内存上调用了 string 成员，string 的构造函数未执行，内部指针未初始化，使用会崩溃。同样，free 不调用析构函数，string 内部堆内存泄漏。

### 1.19 什么是完美转发？

**回答话术：**
完美转发指在函数模板中，将参数**原样**传递给另一个函数——保持其左值/右值属性、const 限定等不变。通过引用折叠（`T&&` 作为万能引用）和 `std::forward` 实现。

**知识点讲解：**
```cpp
template<typename T>
void wrapper(T&& arg) {           // T&& 不是右值引用，是万能引用
    target(std::forward<T>(arg)); // 按 T 推导结果转发
}

int x = 42;
wrapper(x);     // T = int&,  arg = int&,  forward 为左值
wrapper(42);    // T = int,   arg = int&&, forward 为右值
```

**可能的追问：**
- Q: std::move 和 std::forward 的区别？ → A: move 无条件转为右值引用；forward 有条件地转发（当参数是右值时转右值，左值时转左值）。move 用于明确表示"不再需要这个值"，forward 用于泛型代码中的完美转发。
- Q: 万能引用和右值引用的语法一样，如何区分？ → A: `T&&` 出现在模板参数中（带类型推导）是万能引用；`int&&` 或 `vector<int>&&`（具体类型）是右值引用。`auto&&` 也是万能引用。

### 1.20 pthread_create 传入的函数指针可以是类的成员函数吗？

**回答话术：**
不能直接传入非静态成员函数。因为成员函数有隐式的 this 指针参数，函数签名不匹配 `void* (*)(void*)`。

**解决方案：**
1. 将成员函数声明为 **static**（没有 this 指针），然后通过 void* 参数传入对象指针
2. 使用 **lambda 表达式**（C++11），用捕获列表捕获 this，配合 `pthread_create` 需要 lambda 转换成函数指针（无捕获 lambda 可转函数指针）
3. 或者包装一个外部 C 函数，将对象指针通过 arg 参数传入，调用对象的成员函数

```cpp
class Task {
public:
    void run() { /* ... */ }
    static void* run_helper(void* arg) {
        static_cast<Task*>(arg)->run();
        return nullptr;
    }
};
Task t;
pthread_t tid;
pthread_create(&tid, nullptr, &Task::run_helper, &t);
```

**可能的追问：**
- Q: C++11 的 std::thread 可以吗？ → A: 可以，std::thread 能接受任何可调用对象（包括成员函数 + 对象指针的 bind 或 lambda），如 `std::thread(&Task::run, &t)`。
- Q: 为什么 C++ 成员函数不能直接作为线程函数？ → A: 成员函数隐含 this 参数，调用约定（thiscall vs cdecl）不同，函数指针类型不兼容。

## 第2章：STL 标准模板库

---

### 2.1 STL 有哪些容器？分类介绍一下

**回答话术：**
STL 容器分为三大类：
1. **序列式容器**（Sequential）：vector（动态数组，随机访问快，尾部插入快）、deque（双端队列，头尾插入都快）、list（双向链表，任意位置插入快）、forward_list（单向链表）
2. **关联式容器**（Associative）：set/multiset、map/multimap，底层红黑树，有序，O(log n) 查找
3. **无序关联容器**（Unordered）：unordered_set/map（C++11），底层哈希表，平均 O(1) 查找
4. **容器适配器**：stack、queue、priority_queue，基于底层容器实现

**知识点讲解：**
- 关联容器是有序的（自动排序），无序容器是无序的
- 选择原则：需要随机访问用 vector，需要频繁头尾插入用 deque，频繁任意位置插入用 list，查找为主用 unordered_map/set

**可能的追问：**
- Q: map 和 unordered_map 如何选择？ → A: 需要有序遍历或用范围查询用 map；只需单点查找且对性能敏感用 unordered_map（O(1) vs O(log n)）。
- Q: 什么时候用 list？ → A: 需要大量在任意位置插入/删除操作（尤其是中间）。但通常是 write-heavy 场景较少，多数场景 vector + 适当 reserve 表现更好。

---

### 2.2 vector 和 list 的区别与线程安全性

**回答话术：**
| 特性 | vector | list |
|------|--------|------|
| 底层 | 动态数组（连续内存） | 双向链表（非连续） |
| 随机访问 | O(1) | O(n) |
| 尾部插入/删除 | O(1) 均摊 | O(1) |
| 中间插入/删除 | O(n)（需移动元素） | O(1)（找到位置后） |
| 内存 | 连续，缓存友好 | 节点分散，缓存不友好 |
| 额外开销 | 无 | 每个节点两个指针（前后） |

**线程安全性**：STL 容器**都不是线程安全的**。多个线程：
- 同时读：没有写是安全的
- 一读一写同一容器 → data race，未定义行为
- 需要加外部锁（mutex）或使用线程安全的替代方案

**知识点讲解：**
- vector 的扩容机制：capacity 不够时，重新分配 1.5~2 倍新空间，将旧元素 move 或 copy 过去
- list 每次插入都分配新节点，每次删除释放节点

**可能的追问：**
- Q: vector 扩容为什么通常是 1.5 或 2 倍？ → A: 2 倍是时间最优（分摊 O(1)），但内存浪费多。1.5 倍可复用之前释放的内存块（内存分配更友好）。不同实现选择不同，gcc 是 2 倍，clang 是 2 倍。
- Q: vector 的 reserve 和 resize 区别？ → A: reserve 只分配 capacity，不构造元素；resize 改变 size，构造新元素（值初始化）。

---

### 2.3 vector 和 deque 的区别

**回答话术：**
- **底层结构**：vector 连续内存；deque 由多个固定大小的缓冲区（buffer）组成，通过中控器（map）管理
- **随机访问**：vector O(1)；deque O(1) 但略慢（需要一次间接索引）
- **头插/头删**：vector O(n)；deque O(1)
- **内存分配**：vector 扩容时需要移动所有元素；deque 只在头部或尾部不足时分配新 buffer，已有元素不动
- **缓存局部性**：vector 最好；deque 中等（每个 buffer 内连续）

**知识点讲解：**
```cpp
// deque 的双端操作
deque<int> dq;
dq.push_front(1);  // O(1)
dq.push_back(2);   // O(1)
dq[1];             // O(1)，但比 vector 多一次寻址
```

**可能的追问：**
- Q: 什么场景应该用 deque 而不是 vector？ → A: 需要频繁在头部插入/删除时（如双端队列、滑动窗口算法）。另外 queue 的默认底层容器是 deque。
- Q: deque 的中控器（map）是什么？ → A: deque 维护一个指针数组（map），每个元素指向一个固定大小的 buffer（通常 512 字节）。访问时先定位到哪个 buffer，再在 buffer 内偏移。

---

### 2.4 map 与 unordered_map 的区别与底层实现

**回答话术：**
| 特性 | map | unordered_map |
|------|-----|---------------|
| 底层 | 红黑树（自平衡二叉搜索树） | 哈希表 |
| 元素顺序 | 按键升序 | 无序 |
| 查找复杂度 | O(log n) | 平均 O(1)，最坏 O(n) |
| 插入复杂度 | O(log n) | 平均 O(1) |
| 内存 | 节点存储（含左右指针、颜色标记） | 桶数组 + 链表/红黑树 |
| 迭代器稳定性 | 插入不失效，删除被删元素失效 | 重哈希时全部失效 |
| 需要头文件 | `<map>` | `<unordered_map>` |

**选择**：需要有序遍历 → map；追求查找性能 → unordered_map。

**知识点讲解：**
- unordered_map 的哈希冲突解决：**链地址法**（数组 + 链表），C++11 起当链表超过一定长度转为红黑树（类似 Java 8+）
- map 的红黑树保证插入/删除/查找都是 O(log n)，不会退化

**可能的追问：**
- Q: unordered_map 的自定义哈希函数怎么写？ → A: 提供自定义的 hash 模板特化或传函数对象。需保证相同对象产生相同哈希值，不同对象尽量分散。
- Q: map 基于什么比较规则？ → A: 默认 `std::less<Key>`，使用 `operator<`。可自定义比较器。

---

### 2.5 map 和 multimap 的区别

**回答话术：**
- **map**：键唯一。插入已存在的 key 时，`operator[]` 会覆盖，`insert` 会失败（返回 pair<iterator, bool>，bool 表示是否成功）
- **multimap**：允许相同 key 存在多个元素。不提供 `operator[]`（因为 key 不唯一）

```cpp
map<int, string> m;
m.insert({1, "a"});
m.insert({1, "b"}); // 失败，key 1 已存在
m[1] = "b";          // 覆盖

multimap<int, string> mm;
mm.insert({1, "a"});
mm.insert({1, "b"});  // 成功，允许重复
auto range = mm.equal_range(1); // 获取所有 key=1 的元素范围
```

**可能的追问：**
- Q: multimap 如何遍历相同 key 的所有元素？ → A: 用 `lower_bound(key)` 和 `upper_bound(key)` 得到区间，或用 `equal_range(key)` 一次性获取区间。
- Q: 什么时候用 multimap？ → A: 需要一对多的映射关系，如"一个客户多个订单号"。

---

### 2.6 哈希冲突的解决方法（链地址法和线性探测）

**回答话术：**
**链地址法（Separate Chaining）**：每个哈希桶维护一个链表（或红黑树），冲突元素挂在链表上。unordered_map 使用此方式。优点是删除简单，元素数量不受表大小限制。缺点是额外指针存储。

**线性探测（Linear Probing）**：发生冲突时，顺序查找下一个空闲桶。优点是数据连续、缓存友好。缺点是容易产生"一次聚集"现象，删除需要惰性标记。

**其他方法**：二次探测（平方探测）、双重哈希。

**知识点讲解：**
```
链地址法：  0 → [a] → [b]
            1 → [c]
            2 → [d] → [e] → [f]

线性探测： 插入 key=5 时 hash=2 但 2 已被占 → 尝试 3 → 3 也被占 → 尝试 4 → 成功
```

**可能的追问：**
- Q: 链地址法和线性探测各有什么优劣势？ → A: 链地址法删除容易、负载因子可大于 1；线性探测缓存友好、但删除复杂（需惰性删除标记），负载因子不宜超 0.7 否则性能急剧下降。unordered_map 用链地址法使它能在高负载因子下保持性能。
- Q: 加载因子 0.75 的意义？ → A: 空间和时间折中。低于 0.75 浪费空间（桶太稀疏），高于 0.75 冲突概率增加，性能下降。当元素数超过 容量×加载因子 时触发 rehash。

---

### 2.7 priority_queue 的底层实现

**回答话术：**
priority_queue 是容器适配器，默认底层容器是 vector，使用 **二叉堆（binary heap）** 实现，默认是大顶堆（最大元素在堆顶）。插入（push）是 O(log n)，删除堆顶（pop）是 O(log n)，取堆顶（top）是 O(1)。

**知识点讲解：**
```cpp
// 默认是大顶堆
priority_queue<int> pq;       // 等同于 priority_queue<int, vector<int>, less<int>>
pq.push(3); pq.push(1); pq.push(4);
pq.top(); // 4

// 小顶堆
priority_queue<int, vector<int>, greater<int>> min_pq;

// 自定义比较
auto cmp = [](int a, int b) { return a > b; };
priority_queue<int, vector<int>, decltype(cmp)> custom_pq(cmp);
```

二叉堆用数组存储：节点 i 的左子 2i+1，右子 2i+2，父节点 (i-1)/2。push 时元素先放到尾部，然后上浮（percolate up）；pop 时将堆顶与最后一个交换，然后下沉（percolate down）。

**可能的追问：**
- Q: priority_queue 的迭代器在哪里？ → A: priority_queue 不提供迭代器，不支持遍历。如果需要遍历或修改堆中元素，直接用 `make_heap` / `push_heap` / `pop_heap` 算法函数族，它们在 vector 上操作，可遍历。
- Q: 堆排序和 priority_queue 有什么关系？ → A: 堆排序就是利用堆结构进行排序——建堆 O(n)，每次取堆顶 O(log n)，整体 O(n log n)。priority_queue 本质就是堆的封装。

---

### 2.8 std::sort 的底层实现

**回答话术：**
std::sort 是**内省排序（IntroSort）**，混合了三种算法：
1. 数据量大时用**快速排序**（三数取中法选 pivot）
2. 递归深度超过 2×log₂(n) 时切换为**堆排序**（防止快排退化到 O(n²)）
3. 分区小到一定程度（通常 16）时用**插入排序**（小规模数据插入排序比快排快，因为缓存友好）

整体时间复杂度 O(n log n)，最坏情况也是 O(n log n)。

**知识点讲解：**
```cpp
vector<int> v = {4, 2, 5, 1, 3};
sort(v.begin(), v.end());          // 升序
sort(v.begin(), v.end(), greater<>()); // 降序
// sort 要求随机访问迭代器，所以 vector/deque 可用，list 不行
// list 用 list::sort（归并排序）
```

**可能的追问：**
- Q: 为什么小数据用插入排序？ → A: 插入排序虽然 O(n²)，但常数极小，对小数组缓存友好。快排等需要递归或交换，开销更重。在 n < 16 时插入排序实测更快。
- Q: std::stable_sort 的实现？ → A: stable_sort 保证相等元素的原始顺序不变，底层使用归并排序。当内存够用时 O(n log n)，不够用则退化为 O(n log² n)。

### 2.9 哪些操作会导致 vector 迭代器失效？

**回答话术：**
1. **插入/扩容**：扩容时所有迭代器失效（内存重新分配）；插入在中间位置使插入点之后的迭代器失效
2. **删除**：`erase(pos)` 使 pos 及之后的迭代器失效；`erase(begin, end)` 使区间内及之后的所有迭代器失效
3. **赋值/交换**：赋值（`operator=`）和 clear 导致全部失效；`swap` 不失效

**map/unordered_map 的情况：**
- map：插入不失效；删除只失效指向被删元素的迭代器（红黑树节点地址不变）
- unordered_map：插入不失效（除非触发 rehash）；删除只失效被删元素；rehash 时全部失效

**知识点讲解：**
```cpp
// vector 删除的正确写法 —— erase 返回下一个有效迭代器
vector<int> v = {1, 2, 3, 4, 5};
for (auto it = v.begin(); it != v.end();) {
    if (*it % 2 == 0)
        it = v.erase(it);  // 返回被删元素的下一个
    else
        ++it;
}
```

**可能的追问：**
- Q: deque 的迭代器失效情况？ → A: 在中间 insert/erase 使所有迭代器失效；两端操作（push_front/push_back/pop_front/pop_back）只影响被操作端的迭代器。

### 2.10 erase 和 remove 删除元素

**回答话术：**
`std::remove` 并不真正删除元素，而是将"要删除的元素"移到容器末尾，并返回新逻辑结尾的迭代器。真正的删除需要配合 erase，即 **erase-remove 惯用法**。

```cpp
vector<int> v = {1, 2, 3, 2, 4, 2};
// remove 将 2 移到末尾，返回新结尾
auto new_end = std::remove(v.begin(), v.end(), 2);
// v 变成 [1, 3, 4, ?, ?, ?]，new_end 指向第一个 ?
v.erase(new_end, v.end());  // 真正删除
// 或者一行 v.erase(std::remove(v.begin(), v.end(), 2), v.end());
```

**知识点讲解：**
- remove 不改变 size，只是覆盖：用后面的元素前移覆盖要删除的元素
- remove_if 可配合谓词：`remove_if(v.begin(), v.end(), [](int x){ return x > 2; });`
- list 有独立成员函数 `list::remove`，直接删除

**可能的追问：**
- Q: 为什么 remove 不直接删除？ → A: remove 是算法，只操作迭代器范围，不知道底层容器类型。它只做"移动"工作，释放内存由容器自己负责。这样同一算法可用于 vector、deque 等容器。
- Q: list 有自己的 remove 为什么还要 erase-remove？ → A: list::remove 是专门优化的（直接遍历链表节点删除），O(n) 且效率更高。对 list 用 erase-remove 会导致元素反复移动，效率低。

## 第3章：操作系统

### 3.1 进程和线程的区别

**回答话术：**
**进程**是资源分配的基本单位，有独立的地址空间（代码段、数据段、堆栈），进程间相互隔离。**线程**是 CPU 调度的基本单位，同一进程内的线程共享地址空间和资源，每个线程有独立的栈和寄存器上下文。

| 对比 | 进程 | 线程 |
|------|------|------|
| 地址空间 | 独立 | 共享 |
| 资源开销 | 大（创建需分配独立空间） | 小（共享进程资源） |
| 切换代价 | 大（TLB 刷新等） | 小 |
| 通信 | 需要 IPC（pipe/shared memory/socket） | 直接读写共享变量 |
| 健壮性 | 一个进程崩溃不影响其他 | 一个线程崩溃可能导致整个进程退出 |

**知识点讲解：**
- Linux 里线程是一类特殊的进程（轻量级进程 LWP），通过 clone() 系统调用创建，共享地址空间
- 线程私有：线程栈、寄存器、errno、信号屏蔽字；线程共享：堆、全局变量、文件描述符

**可能的追问：**
- Q: 协程和线程的区别？ → A: 协程是用户态调度，切换不涉及系统调用，成本极低（纳秒级）。协程是协作式调度，线程是抢占式调度。一个线程内可运行多个协程。

---

### 3.2 线程间同步方式有哪些？

**回答话术：**
1. **互斥锁（Mutex）**：保护临界区，一次只有一个线程访问共享资源
2. **读写锁（RWLock）**：读读不互斥，读写/写写互斥，适合读多写少场景
3. **条件变量（Condition Variable）**：与 mutex 配合，线程等待某个条件满足才继续执行，避免忙等
4. **信号量（Semaphore）**：控制对资源的访问数量（计数），可用于生产者-消费者模型
5. **自旋锁（SpinLock）**：忙等（不阻塞，循环检查），适合锁持有时间极短的场景
6. **屏障（Barrier）**：等待所有线程到达某点后继续
7. **原子操作（Atomic）**：无需锁的线程安全操作，通过 CPU 指令保证

```cpp
// C++11 标准
std::mutex mtx;
std::lock_guard<std::mutex> lock(mtx); // RAII 加锁

std::condition_variable cv;
cv.wait(lock, []{return ready;});  // 等待条件

std::atomic<int> counter{0};
counter.fetch_add(1);  // 原子自增
```

**可能的追问：**
- Q: 互斥锁和信号量的区别？ → A: 互斥锁是"锁"语义（谁拥有谁释放，同一时刻一个线程持有），信号量是"计数"语义（允许多个线程同时访问最多 N 个资源）。互斥锁通常由持锁线程释放，信号量可由不同线程释放。
- Q: 自旋锁和互斥锁如何选择？ → A: 锁持有时间短（几微秒内）且不阻塞→自旋锁；锁持有时间长或可能被阻塞→互斥锁。自旋锁浪费 CPU，但避免了上下文切换开销。

---

### 3.3 多线程间哪些资源是共享的，哪些是私有的？

**回答话术：**
**共享**（同一进程下的线程间）：
- 堆内存（new/malloc 分配的空间）
- 全局变量和静态变量
- 文件描述符、信号处理函数
- 进程的当前工作目录等

**私有**：
- 线程栈（局部变量、函数调用链）
- 寄存器值（包括程序计数器 PC、栈指针 SP）
- 线程 ID（tid）
- errno（每个线程独立）
- 信号屏蔽字

**知识点讲解：**
- C++ thread_local 关键字可声明线程局部存储变量

**可能的追问：**
- Q: 栈上变量能否被其他线程访问？ → A: 一般不能，因为其他线程不知道栈地址。但如果将栈上变量的地址传递给其他线程（通过指针），则理论上可以访问——这是危险的做法，可能导致栈上的变量被访问时已经失效。

### 3.4 死锁的四个必要条件

**回答话术：**
死锁产生的四个必要条件（缺一不可）：
1. **互斥**：资源一次只能被一个线程占用
2. **请求与保持**：线程持有至少一个资源的同时，请求其他被占用的资源
3. **不可剥夺**：已分配的资源不能被强制剥夺，只能由持有者主动释放
4. **循环等待**：多个线程形成环形链，每个持有一个资源并等待下一个的资源

```cpp
// 死锁经典场景 A 等 B，B 等 A
std::mutex m1, m2;
// Thread 1               // Thread 2
lock(m1);                  lock(m2);
lock(m2); // 等待 m2      lock(m1); // 等待 m1 → 死锁！
```

**可能的追问：**
- Q: 如何预防死锁？ → A: 破坏四个条件之一即可。常用：资源按固定顺序获取（破坏循环等待）、一次性申请所有资源（破坏请求与保持）、使用 try_lock 超时回退。
- Q: 锁顺序死锁和资源死锁的区别？ → A: 锁顺序死锁是两线程以不同顺序申请相同锁；资源死锁是两个线程各自持有对方需要的资源。

---

### 3.5 如何避免死锁？开发中的原则和规范

**回答话术：**
**预防方法：**
1. **固定锁顺序**：所有线程按相同顺序获取锁（如总是先锁 m1 再锁 m2）
2. **使用 std::lock 一次性锁多个**：C++11 std::lock 可对多个 mutex 原子性加锁，避免中间状态
3. **分层锁**：对锁编号，只允许按编号递增顺序获取
4. **超时回退**：使用 try_lock 加超时，获取失败时释放已有锁并重试

**开发规范：**
1. 尽量减少锁的范围和持有时间
2. 避免在持锁时调用用户代码（回调、虚函数），不知道对方会不会拿别的锁
3. 使用 RAII 包装（lock_guard/unique_lock）避免异常安全下的死锁
4. 使用线程安全分析工具：helgrind/ThreadSanitizer

```cpp
// 好的做法：std::lock 避免死锁
std::lock(m1, m2);
std::lock_guard<std::mutex> lock1(m1, std::adopt_lock);
std::lock_guard<std::mutex> lock2(m2, std::adopt_lock);
```

**可能的追问：**
- Q: 银行家算法是什么？ → A: 死锁避免算法。每个新请求到达时检查分配后系统是否处于安全状态（是否存在安全序列）。如果是才分配，否则等待。但实际系统中很少用，因为需要知道最大需求量等信息。
- Q: 如何排查死锁？ → A: Linux 下 gdb attach 到进程，`thread apply all bt` 查看各线程栈，看卡在哪个锁上。或用 helgrind（Valgrind 工具）、ThreadSanitizer（gcc -fsanitize=thread）。

### 3.6 进程切换和 CPU 调度

**回答话术：**
**进程切换（上下文切换）**：CPU 从一个进程切换到另一个进程的过程——保存当前进程的寄存器、PC、栈指针等上下文，恢复目标进程的上下文。成本较高（微秒级），因为需要清空 TLB、切换页表等。

**CPU 调度算法**：
- **FCFS**（先来先服务）：简单，但平均等待时间长
- **SJF**（短作业优先）：最短完成时间优先，理论上最优但无法预知执行时间
- **时间片轮转（RR）**：每个进程分到固定时间片，适合交互式系统
- **多级反馈队列**：Linux 实际使用的调度算法，进程在不同优先级队列间升级/降级，兼顾交互性和吞吐量
- **完全公平调度（CFS）**：Linux 默认调度器，基于 vruntime（虚拟运行时间）选择运行最少的进程

**可能的追问：**
- Q: 上下文切换的成本具体来自哪里？ → A: 主要是 TLB 刷新（编译器 10~100μs）、缓存污染、页表切换、内核态切换开销。
- Q: Linux 下如何查看上下文切换频率？ → A: `vmstat 1` 看 cs（context switch）列，或 `pidstat -w` 查看每个进程。

### 3.7 虚拟内存解决了什么问题？

**回答话术：**
虚拟内存是操作系统提供的一种内存管理机制，为每个进程提供独立的虚拟地址空间，通过 MMU（内存管理单元）映射到物理内存。解决的核心问题：

1. **隔离保护**：进程间地址空间互不干扰，恶意或错误的进程不能访问其他进程的内存
2. **地址空间连续**：即使物理内存碎片化，虚拟地址空间对进程也是连续的
3. **超越物理内存**：通过页面置换，可以运行比物理内存更大的程序
4. **简化内存管理**：每个进程"认为"自己独占完整地址空间（32 位 4GB，64 位极大），加载地址可固定

**知识点讲解：**
- 页表将虚拟页映射到物理页帧
- MMU 在每次内存访问时做虚拟地址到物理地址的转换
- 缺页中断：访问的页不在物理内存中时触发，OS 从磁盘换入

**可能的追问：**
- Q: 栈和堆在虚拟内存中的位置？ → A: 栈在高地址向下增长，堆在低地址向上增长，中间是空闲区（可 mmap 映射）。从低到高：代码段 → 数据段 → BSS → 堆 → 内存映射区 ↓ → 栈 → 内核空间。栈大小通常有限（Linux 默认 8MB），堆可动态扩展。
- Q: 页表太大怎么办？ → A: 使用多级页表（x86-64 使用 4 级页表），只映射实际使用的虚拟地址段，节省内存。在有虚拟内存的操作系统中，页表是分段管理的，未使用的段不需要分配页表项。

### 3.8 局部性原理

**回答话术：**
局部性原理包含两种：
- **时间局部性**：刚访问过的数据很可能很快再次被访问（如循环中的变量、计数器）。CPU 利用缓存（L1/L2/L3 cache）利用这一特性
- **空间局部性**：访问某个地址后，其附近的地址很可能也会被访问（如数组遍历）。CPU 通过缓存行（cache line，通常 64 字节）预取相邻数据

**在编程中的体现：**
- 数组按行遍历比按列遍历快（空间局部性好）
- 结构体包含经常一起访问的字段
- 循环体尽可能小（代码的局部性）

**可能的追问：**
- Q: 如何写缓存友好的代码？ → A: 1) 连续内存遍历（vector 比 list 好） 2) 按内存顺序访问（行优先 vs 列优先） 3) 结构体对齐避免 padding 浪费 4) 减少间接跳转（虚函数、函数指针）
- Q: cache line 失效的后果？ → A: 如果数据结构是链表（节点分散），遍历时每次访问都可能是 cache miss，延迟从~1ns（L1）变为~60ns（内存），差两个数量级。

---

### 3.9 共享内存的原理及同步机制

**回答话术：**
共享内存是最高效的 IPC 方式——两个或多个进程共享同一块物理内存，数据写入立即被其他进程看到，不需要内核拷贝。

**实现方式**：
- POSIX 共享内存（shm_open + mmap）
- System V 共享内存（shmget + shmat）

**同步机制**：共享内存本身不提供同步，需要配合：
- **信号量**（POSIX/SysV 信号量）：最常用，用于互斥访问共享内存
- **互斥锁**：但进程间互斥锁需要进程共享属性（pthread_mutexattr_setpshared）
- **文件锁**：简单但低效

```cpp
// POSIX 共享内存
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 4096);
void* ptr = mmap(nullptr, 4096, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
// 多个进程可通过 ptr 访问同一块物理内存
```

**可能的追问：**
- Q: 共享内存和 mmap 的关系？ → A: mmap 可以将文件或匿名区域映射到进程地址空间。共享内存本质上是 mmap 的 MAP_SHARED + /dev/shm 下的临时文件。二者底层都是通过页表映射到同一物理页。
- Q: 共享内存适合什么场景？ → A: 大数据量传输、高频读写场景（如数据库缓存、消息中间件）。不适合小数据或低频通信（同步开销占比高）。

---

### 3.10 池化技术了解吗？（线程池、内存池、数据库连接池）

**回答话术：**
池化技术的核心思想是**复用**——提前创建一批资源放在池中，需要时从池中取，用完归还，避免频繁创建/销毁的开销。

**线程池**：
- 提前创建 N 个线程，任务队列存放待执行任务
- 避免了线程频繁创建/销毁（系统调用成本高）
- 控制并发数，避免过多线程导致资源耗尽
- 核心参数：核心线程数、最大线程数、任务队列容量、拒绝策略

**内存池**：
- 预分配大块内存，切分成固定大小块管理
- 避免频繁 malloc/free（系统调用 + 内存碎片）
- 提高分配速度和内存利用率

**数据库连接池**：
- 维护多个数据库连接，业务代码从池中获取连接而不是新建
- 避免 TCP 三次握手、MySQL 鉴权的开销
- 控制连接数避免数据库过载

**知识点讲解：**
```cpp
// 线程池核心思路
class ThreadPool {
    vector<thread> workers;
    queue<function<void()>> tasks;
    mutex queue_mutex;
    condition_variable cv;
    bool stop;
public:
    template<typename F>
    void enqueue(F&& f) {
        // 将任务放入队列，通知一个工作线程
    }
};
```

**可能的追问：**
- Q: 线程池的核心线程数和最大线程数怎么设？ → A: CPU 密集型：核心线程数 = CPU 核数 + 1 或直接等于核数；IO 密集型：可更大（核数 × [1 + IO_time/CPU_time]）。最大线程数考虑系统上限（一般在几百到几千）。
- Q: 线程池中任务队列满了怎么办（拒绝策略）？ → A: 常见的：1) 抛异常 2) 由提交线程自己执行 3) 丢弃最老的任务 4) 直接丢弃新任务。Java 的 ThreadPoolExecutor 内置了这些策略。

### 3.11 进程同步的方式有哪些？

**回答话术：**
进程间同步与线程间同步类似，但需要多进程间共享的机制：
1. **信号量（Semaphore）**：最常用，可以用于互斥和同步
2. **文件锁（flock/fcntl）**：通过加锁文件实现互斥
3. **互斥锁（进程共享属性）**：设置 PTHREAD_PROCESS_SHARED 属性
4. **条件变量（进程共享属性）**：配合互斥锁
5. **信号（Signal）**：用于异步通知
6. **管程/消息队列**：同步通信机制

**知识点讲解：**
```cpp
// 进程共享互斥锁
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
pthread_mutex_t* mtx = (pthread_mutex_t*)shm_ptr;
pthread_mutex_init(mtx, &attr);
```

**可能的追问：**
- Q: 进程信号量和线程信号量有什么区别？ → A: 进程信号量在共享内存中创建，对所有进程可见。线程信号量在线程间共享。用法上，进程信号量初始化时需要指定 pshared 为非 0。

### 4.1 计算机网络五层模型及对应协议

**回答话术：**
| 层次 | 功能 | 典型协议 |
|------|------|----------|
| **应用层** | 为用户应用提供网络服务 | HTTP、HTTPS、FTP、SMTP、DNS、WebSocket |
| **传输层** | 端到端通信、可靠传输 | TCP、UDP |
| **网络层** | 路由选择、分组转发、IP 寻址 | IP、ICMP、ARP、RIP、OSPF |
| **数据链路层** | 帧封装、介质访问控制（MAC） | Ethernet、PPP、VLAN |
| **物理层** | 比特流传输（电压、光信号） | 双绞线、光纤、无线电 |

数据封装过程：应用数据 → 传输层加 TCP/UDP 头部 → 网络层加 IP 头部 → 链路层加 MAC 头部 → 物理层发送

**可能的追问：**
- Q: ARP 协议在哪一层？ → A: 工作在**网络层**和**链路层之间**，用于将 IP 地址解析为 MAC 地址。通常归为链路层协议，但使用 IP 地址所以也被视为网络层的一部分。
- Q: ICMP 协议的作用？ → A: 用于传递网络层控制信息和差错报告（如 ping 命令用的就是 ICMP echo request/reply）。

### 4.2 TCP 和 UDP 的区别

**回答话术：**
| 特性 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠传输（确认重传、序号） | 不可靠，尽力而为 |
| 有序 | 保证数据按序到达 | 不保证 |
| 速度 | 较慢（有拥塞控制、流量控制） | 快（无控制机制） |
| 头部开销 | 20~60 字节 | 8 字节 |
| 应用场景 | HTTP、FTP、SMTP | DNS、视频流、在线游戏、VoIP |

**知识点讲解：**
- TCP 适合需要可靠有序传输的场景
- UDP 适合对实时性要求高、可容忍丢包的场景

**可能的追问：**
- Q: UDP 能否实现可靠性？ → A: 可以。在应用层实现确认重传、序号、流量控制等机制（如 QUIC 协议基于 UDP 实现了类似 TCP 的可靠传输，且解决了 TCP 队头阻塞问题）。但比 TCP 灵活，可以自定义重传策略。

---

### 4.3 TCP 如何保证可靠性？

**回答话术：**
TCP 通过以下机制保证可靠性：
1. **确认应答（ACK）**：接收方收到数据后回复 ACK，发送方收到 ACK 才知道数据已到达
2. **超时重传**：发送方启动定时器，超时未收到 ACK 则重传
3. **序列号**：每个字节有序列号，接收方按序列号重组数据，去重
4. **流量控制**：通过滑动窗口机制，接收方告知发送方自己的接受能力（窗口大小），防止发送过快
5. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复，控制网络中的总数据量
6. **校验和**：检测数据损坏，损坏则丢弃（不回复 ACK 触发重传）

**可能的追问：**
- Q: 超时重传的 RTO 是怎么计算的？ → A: 根据 RTT（往返时间）动态计算。RFC 推荐 RTO = SRTT + 4×RTTVAR，其中 SRTT 是平滑 RTT，RTTVAR 是 RTT 的偏差。RTO 通常不小于 1 秒（新实现有更精细的算法）。
- Q: 快重传和超时重传的区别？ → A: 快重传是收到三个冗余 ACK 后立即重传，不等超时。超时重传说明丢包严重，还会降低发送速度（进入慢启动）。

---

### 4.4 TCP 三次握手

**回答话术：**
建立 TCP 连接需要三次握手（客户端 → 服务端）：
```
1. 客户端 → SYN=1, seq=x              // 客户端进入 SYN_SENT
2. 服务端 → SYN=1, ACK=1, seq=y, ack=x+1  // 服务端进入 SYN_RCVD
3. 客户端 → ACK=1, seq=x+1, ack=y+1        // 客户端进入 ESTABLISHED，服务端收到后也进入
```
为什么不是两次：防止已失效的连接请求到达服务器。两次握手时，客户端第一次 SYN 滞留后到达，服务器以为有新连接而建立连接并等待数据，浪费资源。三次握手让服务器确认客户端确实在"活跃"状态。

**可能的追问：**
- Q: 为什么不是四次？ → A: 三次够了。第二次握手同时发送 SYN 和 ACK，合并在同一报文。四次没有额外收益。
- Q: SYN Flood 攻击是什么？ → A: 恶意客户端只发 SYN 不发第三次 ACK，占用服务器资源。防范：SYN Cookie（收到 SYN 先不分配资源，通过报文计算 cookie 作为序列号回复，收到 ACK 验证后再分配）。

---

### 4.5 TCP 四次挥手

**回答话术：**
断开连接需要四次挥手（也可三次，如果两端同时关闭）：
```
1. 主动方 → FIN=1, seq=u       // 主动方进入 FIN_WAIT_1
2. 被动方 → ACK=1, seq=v, ack=u+1  // 被动方进入 CLOSE_WAIT，主动方收到后进入 FIN_WAIT_2
3. 被动方 → FIN=1, seq=w, ack=u+1  // 被动方进入 LAST_ACK
4. 主动方 → ACK=1, seq=u+1, ack=w+1 // 主动方进入 TIME_WAIT（等待 2MSL 后关闭）
```
为什么 TIME_WAIT 等待 2MSL：保证最后一个 ACK 到达对端。如果 ACK 丢失，对端会重发 FIN，TIME_WAIT 状态能处理这种重传。2MSL 是保证一来一回的最大时间。

**知识点讲解：**
- 第二次和第三次挥手之间，被动方可能还有数据要发（半关闭状态）
- TIME_WAIT 持续 2MSL（通常 1~4 分钟），是服务器端设计时要注意的点（大量短连接可能耗尽端口）

**可能的追问：**
- Q: 服务端出现大量 CLOSE_WAIT 的原因？ → A: 被动关闭方收到 FIN 后回复了 ACK，但应用程序没有调用 close()（未关闭 socket）。通常是编程 Bug——read() 返回 0（EOF）后没有正确处理，没有调用 close()。
- Q: TIME_WAIT 过多的影响？ → A: 占用端口资源（一个四元组不能复用），可能导致客户端无法建立新连接。解决方案：SO_REUSEADDR 选项允许重用 TIME_WAIT 的地址。

---

### 4.6 TCP 流量控制和拥塞控制

**回答话术：**
**流量控制**：端到端的机制，防止发送方过快淹没收方。通过**滑动窗口**实现——接收方在 ACK 中通告自己的可用窗口大小（rwnd）。发送方窗口不能超过 rwnd。

**拥塞控制**：全局的网络状态控制，防止发送数据过多导致网络过载。通过**拥塞窗口（cwnd）** 实现，实际发送窗口 = min(rwnd, cwnd)。四个阶段：
1. **慢启动**：cwnd 从 1MSS 开始，每收到一个 ACK 翻倍（指数增长），直到 ssthresh
2. **拥塞避免**：超过 ssthresh 后线性增长（每 RTT + 1MSS），直到发生丢包
3. **快重传**：收到 3 个冗余 ACK 即重传，不等超时
4. **快恢复**：快重传后，cwnd 减半 + 3MSS，进入拥塞避免（而不是回到慢启动）

**知识点讲解：**
- 超时重传触发慢启动（从 1MSS 开始）
- 快重传 + 快恢复使用新 Reno、CUBIC 等算法

**可能的追问：**
- Q: 什么是 TCP 的队头阻塞（HOL blocking）？ → A: TCP 保证数据按序到达，如果某个包丢失，后面已到的包必须等待重传完成后才能交给应用层。HTTP/2 的多路复用也会因此被阻塞。这也是 QUIC（基于 UDP）要解决的问题——采用多流设计，一条流丢包不影响其他流。

---

### 4.7 HTTP 长连接与短连接的适用场景

**回答话术：**
- **短连接**：每次请求都新建 TCP 连接，完成后关闭。HTTP/1.0 默认短连接。适合请求频率低的场景（如简单的 API 调用）、或在连接数量不大时。
- **长连接（Keep-Alive）**：复用同一个 TCP 连接发送多个 HTTP 请求/响应。HTTP/1.1 默认长连接。适合请求密集、高频交互的场景。

**长连接优点**：减少三次握手开销、避免 TIME_WAIT 积累、减少连接建立延迟。

**长连接缺点**：服务端需维护大量空闲连接、占用资源（文件描述符）。

**选择依据**：请求频率高、连接复用率高 → 长连接；低频请求 → 短连接更简单。

**可能的追问：**
- Q: HTTP/2 的连接复用比 HTTP/1.1 长连接强在哪？ → A: HTTP/1.1 长连接虽然有 keep-alive，但请求仍是串行的（Pipelining 有队头阻塞问题，多数浏览器默认关闭）。HTTP/2 真正的多路复用——单一 TCP 上可并行传输多个流（Stream），避免应用层队头阻塞。
- Q: WebSocket 和 HTTP 长连接的关系？ → A: WebSocket 也是建立在 TCP 上的，但通过 HTTP 升级（Upgrade 头部）建立双向通信。HTTP 长连接仍是"请求-响应"模式，WebSocket 是全双工实时通信。

### 4.8 HTTP 和 HTTPS 的区别

**回答话术：**
| 对比 | HTTP | HTTPS |
|------|------|-------|
| 协议 | HTTP | HTTP + TLS/SSL |
| 端口 | 80 | 443 |
| 安全性 | 明文传输 | 加密通信 |
| 认证 | 无 | 数字证书验证服务器身份 |
| 性能 | 快（无加密计算） | 慢（有握手和加密开销） |

HTTPS 流程：客户端发起 HTTPS 请求 → 服务器返回数字证书（含公钥）→ 客户端验证证书 → 生成对称密钥并用公钥加密发送给服务器 → 双方用对称密钥加密通信。

**可能的追问：**
- Q: TLS 握手过程？ → A: 1) ClientHello（支持的密码套件） 2) ServerHello（选定的套件）+ 证书 3) 客户端验证证书，生成预主密钥，用公钥加密发送 4) 双方计算会话密钥 5) Finished 验证（整个过程需要 1 RTT 或 0-RTT 重连）。

### 4.9 Socket 编程的步骤

**回答话术：**
**TCP 服务端**：
```
socket() → bind() → listen() → accept() → recv()/send() → close()
```
**TCP 客户端**：
```
socket() → connect() → send()/recv() → close()
```

**关键函数**：
- socket()：创建套接字，指定协议族（AF_INET）、类型（SOCK_STREAM/DGRAM）
- bind()：绑定地址和端口
- listen()：将套接字设为监听模式，指定 backlog（最大等待连接数）
- accept()：接受客户端连接，返回新的连接 socket（阻塞的）
- connect()：客户端发起连接

```cpp
// 服务端骨架
int sock = socket(AF_INET, SOCK_STREAM, 0);
struct sockaddr_in addr = {AF_INET, htons(8080), INADDR_ANY};
bind(sock, (sockaddr*)&addr, sizeof(addr));
listen(sock, 10);  // 最大等待队列长度
int client = accept(sock, nullptr, nullptr);
char buf[1024]; recv(client, buf, sizeof(buf), 0);
send(client, "OK", 2, 0);
close(client); close(sock);
```

**可能的追问：**
- Q: listen 的 backlog 参数有什么用？ → A: 表示已完成三次握手但还未被 accept 的连接（ESTABLISHED 状态）队列的最大长度。超过这个长度，新连接会被拒绝。Linux 中实际值受 somaxconn 限制。
- Q: TCP socket 的 send/recv 缓存是什么？ → A: 内核维护发送缓冲区和接收缓冲区。send 将数据写入发送缓冲区就返回（实际由内核 TCP 协议栈发出去）；recv 从接收缓冲区读数据。缓冲区大小可通过 setsockopt 调整。

---

### 4.10 select 和 epoll 的区别

**回答话术：**
| 对比 | select | epoll |
|------|--------|-------|
| 底层 | 轮询（遍历 fd_set） | 事件驱动（回调机制） |
| 效率 | O(n)，监听越多越慢 | O(1)，只返回就绪的 fd |
| fd 数量上限 | FD_SETSIZE（默认 1024） | 无上限（受系统限制） |
| 触发模式 | 水平触发（LT） | LT 和 ET（边缘触发）均可 |
| 工作方式 | 每次传入全部 fd_set，内核修改 | epoll_create 创建，epoll_ctl 注册，epoll_wait 等待 |

**使用场景**：
- select：连接数少（<1024）且简单时
- epoll：大规模连接（数千到数万，如高并发服务器）

**epoll 模式**：
- LT（水平触发）：只要 fd 有数据可读，epoll_wait 就返回。编程简单
- ET（边缘触发）：只有状态变化时（如新数据到达）才通知。必须非阻塞 IO + 循环读取，效率高

**知识点讲解：**
```cpp
int epfd = epoll_create1(0);
struct epoll_event ev;
ev.events = EPOLLIN;
ev.data.fd = listen_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
struct epoll_event events[1024];
int n = epoll_wait(epfd, events, 1024, -1);
for (int i = 0; i < n; i++) {
    // 处理就绪的 fd
}
```

**可能的追问：**
- Q: epoll 效率一定比 select 高吗？ → A: 不一定。连接数少（几十以内）且活跃 fd 多时，select 反而可能更快，因为 epoll 需要系统调用来注册/修改 fd（epoll_ctl），多了一次系统调用开销。epoll 的优势在大规模连接。
- Q: 边缘触发模式下为什么需要非阻塞 IO + 循环读？ → A: ET 只在状态变化时通知一次，必须一次把数据读完（循环 recv 直到 EAGAIN）。如果用阻塞读，最后一次会阻塞。所以必须是非阻塞 + 读到 EAGAIN 为止。

---

### 4.11 select/poll/epoll 对比

**回答话术：**
| 特性 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | fd_set（位图） | pollfd 数组 | 红黑树 + 就绪链表 |
| 时间复杂度 | O(n) | O(n) | O(1) |
| 最大 fd 数 | 1024 | 无限制 | 无限制 |
| 遍历 | 每次传全部 fd | 每次传全部 fd | 注册后内核维护，只取就绪 |
| 工作模式 | 仅 LT | 仅 LT | LT + ET |
| 系统调用 | 每次 select 拷贝 | 每次 poll 拷贝 | 注册 ctl，wait 不用拷贝 |

**选择建议**：
- 少量（<100）活跃连接 → select/poll 足够
- 大量（>1000）空闲连接 → epoll 优势巨大
- select 跨平台性好（Windows 也支持），epoll 仅 Linux

**可能的追问：**
- Q: epoll 的就绪链表是内核维护的吗？ → A: 是的。当 fd 有事件时，内核通过回调函数将 fd 加入就绪链表。epoll_wait 只需将就绪链表拷贝到用户空间。
- Q: Java 的 NIO 底层是什么？ → A: Linux 下使用 epoll（Java 1.5+ 经过 select → epoll），Windows 使用 IOCP，MacOS 使用 kqueue。

### 4.12 网络 I/O 模型的类型

**回答话术：**
UNIX 有五种 I/O 模型：
1. **阻塞 I/O**：recv/read 一直等待直到数据就绪。最直接，但线程被挂起
2. **非阻塞 I/O**：立即返回 EAGAIN，需要不断轮询。浪费 CPU
3. **I/O 多路复用**：select/epoll 一个线程等待多个 fd。高并发基础
4. **信号驱动 I/O**：数据就绪时发 SIGIO 信号通知。较少使用
5. **异步 I/O（AIO）**：发起操作后立刻返回，内核完成所有操作（包括数据从内核拷贝到用户空间）后通知。真正异步

**同步 vs 异步的区分**：
- 同步 I/O：等待 I/O 完成或轮询（1~4 都是同步，因为数据从内核拷贝到用户空间的过程需要等待）
- 异步 I/O：发起后完全不等待，内核全部做完后通知（只有 5 是真正的异步 I/O）

**可能的追问：**
- Q: Reactor 和 Proactor 模式的区别？ → A: Reactor 基于同步 I/O 多路复用（事件循环告知哪个 fd 就绪，用户代码自行读写）；Proactor 基于异步 I/O（内核完成读写后通知）。Reactor 实现简单，Linux 下常用。Proactor 需要操作系统支持的真正异步 I/O，Windows 的 IOCP 是典型实现。

---

### 4.13 Reactor 模型

**回答话术：**
Reactor 模式是高性能网络服务器的核心设计模式，基于 I/O 多路复用 + 事件驱动。其工作流程：

1. **事件分发器（Event Demultiplexer）**：通过 epoll/select 等待 I/O 事件
2. **事件处理器（Event Handler）**：处理特定 I/O 事件（读、写、连接等）
3. **Reactor**：注册事件处理器，循环调用事件分发器获取事件，分发到对应处理器

**典型实现层次**：
- **单 Reactor + 单线程**：Redis。一个线程处理所有连接和事件，简单但无法利用多核
- **单 Reactor + 工作线程池**：Reactor 线程只做事件分发，业务处理交给线程池。处理 I/O 仍是单线程
- **主从 Reactor + 线程池**：Netty、Nginx。主 Reactor 只负责 accept，从 Reactor 负责 I/O 读写

**可能的追问：**

### 4.14 Unix 域套接字

**回答话术：**
Unix 域套接字（Unix Domain Socket, UDS）是本机 IPC 方式，地址绑定到文件系统路径而不是 IP 端口。

**特点：**
- 只用于同一台机器上的进程间通信
- 比 TCP localhost 通信快（跳过网络协议栈，不需要回环接口）
- 有流式（SOCK_STREAM）和数据报（SOCK_DGRAM）两种模式
- 本地数据报是可靠的（不像 UDP）

```cpp
int fd = socket(AF_UNIX, SOCK_STREAM, 0);
struct sockaddr_un addr;
addr.sun_family = AF_UNIX;
strcpy(addr.sun_path, "/tmp/mysocket");
bind(fd, (sockaddr*)&addr, sizeof(addr));
```

**使用原因**：性能好（不需要经过 TCP/IP 协议栈，不需要路由处理），安全性高（文件权限控制）。常用于数据库连接（MySQL、PostgreSQL 支持）、Nginx 等。

**可能的追问：**
- Q: Unix 域套接字和共享内存的读写性能对比？ → A: 共享内存更快（零拷贝），但同步复杂。Unix 域套接字也很快（有内核缓冲区管理，数据基本在内核内部传递，不走到网卡）。小数据 UDS 方便，大数据共享内存更优。
- Q: 用 TCP 回环地址（127.0.0.1）和 Unix 域套接字的性能差距？ → A: Unix 域套接字快 30%~50%，因为它不走 TCP 协议栈（没有校验和计算、分片、拥塞控制等）。

### 4.15 浏览器获取页面的整个过程

**回答话术：**
1. **DNS 解析**：浏览器缓存 → 系统 hosts → 本地 DNS 服务器 → 根/顶级/权威 DNS 服务器，获取 IP
2. **TCP 连接**：与服务器建立 TCP 连接（三次握手）
3. **TLS 握手**（HTTPS）：协商加密参数，验证证书（额外 1~2 RTT）
4. **发送 HTTP 请求**：构造请求行（GET/POST）、请求头（Cookie、User-Agent）、请求体
5. **服务器处理并响应**：返回状态码（200/304/404）、响应头、响应体
6. **解析 + 渲染**：
   - 浏览器解析 HTML 构建 DOM 树
   - 解析 CSS 构建 CSSOM 树
   - 合并成渲染树，布局（Layout）、绘制（Paint）
   - JavaScript 解析执行（可能阻塞 DOM 构建）
7. **TCP 断开**（如果是短连接则四次挥手）

**可能涉及的性能优化**：CDN（DNS 就近解析）、HTTP/2 多路复用、资源压缩、浏览器缓存（强缓存/协商缓存）

**可能的追问：**
- Q: 输入 URL 后回车，到开始 DNS 解析之间发生了什么？ → A: 浏览器先检查 HSTS 列表（强制 HTTPS）、检查 URL 格式（补全协议头）、检查是否有缓存（强缓存命中则直接使用本地缓存不发请求）。
- Q: 如果返回 304 表示什么？ → A: 资源未修改（Not Modified），客户端缓存有效。浏览器使用本地缓存的版本。这是协商缓存的响应——浏览器发送了 If-Modified-Since 或 If-None-Match，服务器对比后发现版本没变。

### 5.1 快速排序的思想、复杂度和为什么比归并好

**回答话术：**
**思想**：分治法。选一个 pivot，将数组分成两部分——小于 pivot 的放左边，大于的放右边。然后递归对左右两部分排序。

**复杂度**：平均 O(n log n)，最坏 O(n²)（每次 pivot 恰好是最大/最小）。空间复杂度 O(log n)（递归栈）。

**为什么比归并更常用**：
- 原地排序（不需要额外 O(n) 空间）
- 缓存友好（数据访问连续）
- 实际常数小，平均性能优于归并排序

```cpp
void quickSort(vector<int>& arr, int l, int r) {
    if (l >= r) return;
    int pivot = partition(arr, l, r);  // 三数取中选 pivot
    quickSort(arr, l, pivot - 1);
    quickSort(arr, pivot + 1, r);
}
```

**可能的追问：**
- Q: 如何避免快排退化到 O(n²)？ → A: 三数取中法选 pivot（首、中、尾三数的中位数）；随机选 pivot；当递归深度超过阈值时切换到堆排序（IntroSort——std::sort 的策略）。
- Q: 最坏情况的场景？ → A: 每次 pivot 都选到最大/最小元素。比如有序数组 + 总是选第一个元素作为 pivot。解决方法就是三数取中或随机选 pivot。

### 5.2 堆排序实现原理和复杂度

**回答话术：**
**原理**：利用二叉堆（大顶堆）排序。
1. **建堆**：从最后一个非叶子节点开始，逐个下沉，构建大顶堆（O(n)）
2. **排序**：取出堆顶与最后一个元素交换，堆大小减 1，然后对堆顶下沉调整（O(log n)）
3. 重复第 2 步直到堆为空

**复杂度**：时间 O(n log n)，空间 O(1)（原地排序）。不稳定。

```cpp
void heapSort(vector<int>& arr) {
    int n = arr.size();
    // 建堆：从最后一个非叶子节点开始下沉
    for (int i = n/2 - 1; i >= 0; i--)
        heapify(arr, n, i);
    // 排序
    for (int i = n-1; i > 0; i--) {
        swap(arr[0], arr[i]);  // 堆顶移到最后
        heapify(arr, i, 0);    // 对剩余部分调整
    }
}
void heapify(vector<int>& arr, int n, int i) {
    // 将节点 i 下沉到正确位置
    int largest = i, left = 2*i+1, right = 2*i+2;
    if (left < n && arr[left] > arr[largest]) largest = left;
    if (right < n && arr[right] > arr[largest]) largest = right;
    if (largest != i) {
        swap(arr[i], arr[largest]);
        heapify(arr, n, largest);
    }
}
```

**可能的追问：**
- Q: 建堆的复杂度为什么是 O(n) 不是 O(n log n)？ → A: 因为是从最后一个非叶子节点开始下沉，不是每个节点都从根下沉。高层节点少但下沉路径长，低层节点多但下沉路径短。数学证明总操作次数 ≤ 2n = O(n)。
- Q: 堆排序为什么不稳定？ → A: 堆排序在交换堆顶和末尾元素时，可能改变相等元素的相对顺序。

### 5.3 红黑树的实现原理、结构特征和查询复杂度

**回答话术：**
**红黑树**是自平衡二叉搜索树，每个节点增加一个颜色属性（红/黑）。AVL 树平衡要求更严格，红黑树是"近似平衡"。

**五条性质**：
1. 每个节点是红色或黑色
2. 根是黑色
3. 叶子节点（NIL）是黑色
4. 红色节点的两个子节点都是黑色（没有两个连续的红色节点）
5. 任意节点到其所有叶子节点的路径上，黑色节点数量相同

**查询时间复杂度**：O(log n)，且保持稳定不会退化。因为最大深度 ≤ 2 × 最小深度（红黑树的最长路径不短于最短路径的两倍）。

**插入/删除后的调整**：通过变色 + 旋转（左旋/右旋）维持性质。STL map/set 底层就是红黑树。

**可能的追问：**
- Q: 红黑树和 AVL 树的区别？ → A: AVL 树平衡要求更严格（左右子树高度差 ≤ 1），所以查询更快，但插入/删除的旋转代价更高。红黑树牺牲了部分平衡性换取更少的旋转操作，在需要频繁插入/删除的场景更适合。
- Q: 为什么 map 用红黑树而不是 AVL 树？ → A: map 要同时支持插入、删除、查找。红黑树在这三者之间取得了更好的平衡，旋转次数更少（均摊 O(1) 次旋转）。

### 5.4 跳表（Skip List）的查询时间复杂度

**回答话术：**
跳表是一种多层级的链表结构。最底层是有序链表，上层是"索引层"，每个节点以概率 p（通常 1/2）出现在更高层。

**查找时间复杂度**：平均 O(log n)，最坏 O(n)。通过从最高层开始查找，快速跳过大量节点。

**与红黑树的对比**：
| 对比 | 红黑树 | 跳表 |
|------|--------|------|
| 查询 | O(log n) | O(log n) 平均 |
| 实现复杂度 | 复杂（旋转/变色） | 简单 |
| 范围查询 | 中序遍历 | 在底层链表中直接遍历 |
| 并发 | 难 | 易（锁分裂） |
| 空间 | O(n)（2 个指针 + 颜色） | O(n log n) 期望（多层指针） |
| 内存连续性 | 不连续 | 不连续 |

**应用**：Redis 的 sorted set（zset）底层使用了跳表（不是红黑树），因为跳表范围查询更高效、实现更简单。

**可能的追问：**
- Q: Redis 为什么用跳表而不红黑树？ → A: 1) zset 需要范围查询（ZRANGE），跳表在底层链表中向前/向后遍历即可，红黑树需要中序遍历；2) 跳表实现更简单，出 bug 概率小；3) 跳表在并发场景下更容易加锁分段。
- Q: 跳表的最坏查找是如何发生的？ → A: 如果所有节点都没晋升到上层（概率极小，随数据量增大概率趋近 0），跳表退化为单链表，查找 O(n)。

### 5.5 哈希表及影响性能的参数

**回答话术：**
哈希表通过哈希函数将 key 映射到数组下标，实现 O(1) 平均查找。

**影响性能的两个参数**：
1. **初始容量**：桶数组的初始大小。太小导致频繁 rehash，太大浪费内存
2. **加载因子（负载因子）**：`元素个数 / 桶个数`。超过此阈值触发 rehash（扩容）。典型 0.75——空间和时间的折中。太大冲突多，性能下降；太小空间浪费。

**其他影响因素**：
- 哈希函数的质量：分布均匀度
- 冲突解决策略：链地址法 vs 开放寻址法

**可能的追问：**
- Q: 为什么加载因子选 0.75？ → A: 数学推导+实践经验。泊松分布下，当负载因子为 0.75 时，一个桶中冲突元素超过 8 个的概率极低（约 0.00000006）。这也是 Java HashMap 链表转红黑树的阈值为 8 的来源。
- Q: rehash 过程是怎么样的？ → A: 创建新桶数组（通常 2 倍扩容），重新计算每个元素的哈希并放入新桶。这个过程是 O(n) 且消耗大量 CPU。对延迟敏感的场景可采用渐进式 rehash（如 Redis 的 rehash 在每次操作时逐步迁移）。

### 5.6 链表判环（快慢指针）

**回答话术：**
**Floyd 判环算法（快慢指针）**：两个指针从头开始，快指针每次走两步，慢指针每次走一步。如果存在环，快指针必定追上慢指针。如果快指针到 nullptr，则无环。

```cpp
bool hasCycle(ListNode* head) {
    if (!head || !head->next) return false;
    ListNode *slow = head, *fast = head->next;
    while (fast && fast->next) {
        if (slow == fast) return true;  // 相遇即有环
        slow = slow->next;
        fast = fast->next->next;
    }
    return false;
}
```

**扩展：找到环的入口**：头节点到入口距离 = 相遇点到入口距离（需要数学推导）。在第一次相遇后，一个指针从头走，另一个从相遇点走，步长都为 1，相遇点即入口。

**可能的追问：**
- Q: 为什么快慢指针就能判环？数学原理？ → A: 假设入环前长度 a，环长度 b。快慢指针相遇时，慢指针走了 s 步，快指针走了 2s 步，有 2s - s = kb（快指针比慢指针多走了 k 圈环），所以 s = kb。此时慢指针相对于入口走了 kb - a = (k-1)b + (b-a) 步，所以从相遇点继续走 a 步即可回到入口。
- Q: 能不能用哈希表判环？ → A: 可以，遍历链表，将每个节点地址存入 unordered_set，如果重复出现即有环。但需要 O(n) 额外空间，不如快慢指针的 O(1) 空间。

### 5.7 二叉树翻转（反转二叉树）

**回答话术：**
递归解法：交换左右子树，然后递归翻转左右子树。

```cpp
TreeNode* invertTree(TreeNode* root) {
    if (!root) return nullptr;
    swap(root->left, root->right);           // 交换左右子节点
    invertTree(root->left);                   // 递归翻转左子树
    invertTree(root->right);                  // 递归翻转右子树
    return root;
}
```

**递归返回条件（base case）**：节点为 nullptr 时返回 nullptr。这是递归的终止条件——空节点不需要翻转。

**可能的追问：**
- Q: 非递归实现？ → A: 用队列做层序遍历（BFS），遍历每个节点时交换左右子节点后入队。或者用栈模拟递归。
- Q: 只遍历一遍如何实现？ → A: 上面的递归解法就是只遍历一遍，每个节点访问一次，在回溯过程中交换左右子树，时间复杂度 O(n)。

### 5.8 树的层序遍历

**回答话术：**
层序遍历（BFS）用队列实现：

```cpp
vector<vector<int>> levelOrder(TreeNode* root) {
    if (!root) return {};
    vector<vector<int>> result;
    queue<TreeNode*> q;
    q.push(root);
    while (!q.empty()) {
        int levelSize = q.size();  // 当前层的节点数
        vector<int> level;
        for (int i = 0; i < levelSize; i++) {
            TreeNode* node = q.front(); q.pop();
            level.push_back(node->val);
            if (node->left) q.push(node->left);
            if (node->right) q.push(node->right);
        }
        result.push_back(level);
    }
    return result;
}
```

**可能的追问：**
- Q: 空间复杂度？ → A: O(w)，w 是树的最大宽度（最宽一层的节点数）。最坏情况完全二叉树 O(n)。
- Q: 如何用 DFS 实现层序遍历？ → A: 用一个参数 depth 记录当前深度，递归时 push 到 result[depth]。递归是先左后右遍历，"层"的顺序通过 depth 控制。本质上就是模拟 BFS 的效果。

### 5.9 括号匹配问题

**回答话术：**
使用栈。遍历字符串，遇到左括号入栈，遇到右括号时检查栈顶是否匹配，匹配则弹栈，否则返回 false。最后栈空则全部匹配。

```cpp
bool isValid(string s) {
    stack<char> st;
    for (char c : s) {
        if (c == '(' || c == '[' || c == '{')
            st.push(c);
        else {
            if (st.empty()) return false;
            if ((c == ')' && st.top() != '(') ||
                (c == ']' && st.top() != '[') ||
                (c == '}' && st.top() != '{'))
                return false;
            st.pop();
        }
    }
    return st.empty();
}
```

**可能的追问：**
- Q: 如果括号种类只有一种（如只有圆括号）怎么优化？ → A: 用一个计数器，左括号 +1，右括号 -1。任何时候 counter ≥ 0（保证不先出现右括号），最终 counter = 0。O(1) 空间。
- Q: 如何输出最长的有效括号子串长度？ → A: 用栈存左括号的索引（或者用 DP）。栈方法：栈底存最后一个不匹配的右括号位置。每遇到一个可以匹配的右括号，弹出左括号，长度 = 当前位置 - 当前栈顶。

### 5.10 拓扑排序的时间复杂度

**回答话术：**
拓扑排序是对有向无环图（DAG）进行排序——每个顶点只出现一次，如果 A → B，则 A 在 B 之前。

**Kahn 算法（BFS）**：
1. 统计所有顶点的入度
2. 入度为 0 的顶点入队
3. 出队时，将其后继节点的入度减 1，如果入度变成 0 则入队
4. 重复直到队列为空。如果排序结果中的顶点数不等于总数，说明有环

**时间复杂度**：O(V + E)，V 是顶点数，E 是边数。因为每条边和每个顶点都被访问恰好一次。

**可能的追问：**
- Q: 如何检测图中是否存在环？ → A: 拓扑排序过程中，如果最终排序的顶点数小于总顶点数，则有环（存在入度永远不为 0 的节点）。或者 DFS 时用三色标记法（白/灰/黑），如果在回溯过程中遇到灰色节点，则有环。
- Q: 可以用 DFS 实现拓扑排序吗？ → A: 可以。对图进行 DFS，在回溯时（后序遍历）将节点加入结果。最终结果的反转就是拓扑排序。

### 5.11 用栈实现队列 / 用队列实现栈

**回答话术：**
**两个栈实现队列**：
```cpp
class MyQueue {
    stack<int> in, out;
public:
    void push(int x) { in.push(x); }
    int pop() {
        if (out.empty())
            while (!in.empty())
                { out.push(in.top()); in.pop(); }
        int val = out.top(); out.pop();
        return val;
    }
    // peek 类似
    bool empty() { return in.empty() && out.empty(); }
};
```
入队 O(1)，出队**均摊** O(1)（每个元素最多被移两次）。

**两个队列实现栈**：
```cpp
class MyStack {
    queue<int> q1, q2;
public:
    void push(int x) {
        q2.push(x);
        while (!q1.empty()) { q2.push(q1.front()); q1.pop(); }
        swap(q1, q2);
    }
    int pop() { int v = q1.front(); q1.pop(); return v; }
};
```
入队 O(n)，出队 O(1)。或者入队 O(1)（push 到非空队列），出队 O(n)（将前 n-1 个移到空队列，返回最后一个）。

**可能的追问：**
- Q: 两个栈实现队列，pop 操作的平均时间复杂度？ → A: 均摊 O(1)。每个元素最多被 push 到 in 栈一次、移到 out 栈一次、pop 一次，总共常数次操作。虽然出队的最坏情况是 O(n)（当 out 为空，需要把 in 中所有元素移过来），但均摊是 O(1)。

### 5.12 无重复字符的最长子串/子串问题

**回答话术：**
**无重复字符的最长子串**（LeetCode 3）：滑动窗口。

```cpp
int lengthOfLongestSubstring(string s) {
    vector<int> last(128, -1);  // 记录字符最后出现的位置
    int left = 0, maxLen = 0;
    for (int right = 0; right < s.size(); right++) {
        if (last[s[right]] >= left)
            left = last[s[right]] + 1;  // 遇到重复，移动左边界
        last[s[right]] = right;
        maxLen = max(maxLen, right - left + 1);
    }
    return maxLen;
}
```

**优化思路**：如果字符集有限（ASCII 128），可以用数组代替哈希表，减少哈希碰撞开销。使用 vector<int>(128) 比 unordered_map 更高效，因为避免了哈希计算和内存分配。

**可能的追问：**
- Q: 时间复杂度？ → A: O(n)，每个字符最多被左右指针各访问一次。空间 O(字符集大小)。
- Q: 如果需要找出无重复字符的最小子串（覆盖所有字符）？ → A: 最小覆盖子串问题（LeetCode 76）。滑动窗口 + 计数法：右指针扩展直到覆盖所有目标字符，然后左指针收缩到最小。

### 5.13 Top K 问题

**回答话术：**
Top K（找最大/最小的 K 个元素）的常见解法：

**方法一：堆（适合大量数据，海量数据流）**
- 取 Top K 大 → 小顶堆（堆顶是当前第 K 大，新元素大于堆顶就替换下沉）
- 取 Top K 小 → 大顶堆
- 时间复杂度 O(n log k)，空间 O(k)

```cpp
// Top K 大
priority_queue<int, vector<int>, greater<int>> minHeap;
for (int num : nums) {
    minHeap.push(num);
    if (minHeap.size() > k) minHeap.pop();
}
```

**方法二：快速选择（Quick Select）**
- 基于快排的 partition，平均 O(n)，最坏 O(n²)
- 适合数组不大且需要精确的第 K 个元素

**场景选择**：海量数据（无法全量排序）→ 堆；数据不多且需要快速 → 快速选择。文件分片 + 小顶堆归并也是常见的大数据方案。

**可能的追问：**
- Q: 在数据量极大（如 10 亿个数据求 Top100）时怎么处理？ → A: 分治——将数据分片，每片用堆求局部 Top100，然后合并结果再做一次 Top100。如果还能分布式，用 MapReduce 方式在不同机器上分别计算。
- Q: 快速选择的复杂度为什么是 O(n) 平均？ → A: 每次 partition 将问题规模减半（平均情况），T(n) = T(n/2) + O(n)，根据主定理 O(n)。最坏情况 pivot 选在端点导致 T(n) = T(n-1) + O(n) = O(n²)。

### 5.14 文件分片时如何保证顺序性

**回答话术：**
文件分片要保证顺序性主要在两个方面：传输顺序和重组顺序。

**保证重组顺序**：
- 每个分片携带**分片序号**（segment index 或 offset），接收方根据序号在文件中的位置写入
- 传输层可以使用 TCP（保证数据有序到达）
- 应用层增加**序号校验**：接收方检查分片序号是否连续，不连续则请求重传
- 使用**位图（bitmap）** 记录哪些分片已收到，完成所有分片后按序重组

```cpp
// 分片格式
struct FileSegment {
    uint32_t file_id;        // 文件 ID
    uint32_t segment_index;  // 分片序号（从 0 开始）
    uint32_t total_segments; // 总分片数
    uint32_t size;           // 本分片大小
    uint32_t checksum;       // 校验和
    char data[MAX_SEGMENT_SIZE];
};
```

**可能的追问：**
- Q: 如果使用 UDP 传输文件分片，怎么保证顺序？ → A: 在 UDP 之上自己实现一套类似 TCP 的确认重传+序号机制。收到分片后先缓存到本地（根据序号插入到对应位置），不连续时请求重传缺失的分片。这就是简化版的可靠 UDP 协议。

### 5.15 解决带手续费的股票交易问题

**回答话术：**
这是 LeetCode 714，买卖股票的最佳时机含手续费。DP 思路：

```cpp
int maxProfit(vector<int>& prices, int fee) {
    int n = prices.size();
    int hold = -prices[0];      // 持有股票时的最大收益
    int cash = 0;               // 不持有股票时的最大收益
    for (int i = 1; i < n; i++) {
        int prev_hold = hold;
        hold = max(hold, cash - prices[i]);         // 买入
        cash = max(cash, prev_hold + prices[i] - fee); // 卖出（扣手续费）
    }
    return cash;
}
```
状态转移：每天要么持有（买入或继续持有），要么不持有（卖出或继续空仓）。时间 O(n)，空间 O(1)。

**可能的追问：**
- Q: 没有手续费的版本怎么做？ → A: 就是 LeetCode 122（多次交易），只需累加所有上涨差值。因为可以无限买卖，每天只要涨价就前一天买后一天卖。
- Q: 只能交易一次呢？ → A: LeetCode 121，维护历史最低价和最大差值。

### 6.2 动态库封装了哪些接口？动态库链接的过程

**回答话术：**
**动态库封装的接口**：
- 对外暴露的函数符号（全局函数、类成员函数）
- 全局变量（dllimport/dllexport）
- 通过库的头文件声明这些接口。接口需要在编译时用 `-fvisibility=hidden` 控制导出的符号，或通过 `.def` 文件指定导出的符号表。

```cpp
// 动态库接口示例
#ifdef _MSC_VER
#define API __declspec(dllexport)
#else
#define API __attribute__((visibility("default")))
#endif
API int add(int a, int b);
```

**动态库链接过程**：
1. **编译期（链接）**：链接器查找符号表，记下未解析的符号名称，不在可执行文件中拷贝代码（不同于静态库），只记录需要哪个动态库的哪些符号
2. **加载期**：程序启动时，动态链接器（ld.so）按照 LD_LIBRARY_PATH 等搜索路径找到动态库，加载到内存，将符号重定位到实际地址
3. **运行时**：也可以延迟绑定（lazy binding），在第一次调用函数时才解析符号（PLT/GOT 机制）

**知识点讲解：**
- 静态库（.a）：编译链接时将代码拷贝到可执行文件中
- 动态库（.so）：只在运行时加载，多个进程共享一份内存中的代码段
- 对比：动态库节省磁盘/内存，更新库无需重新编译程序（API/ABI 兼容时）；但部署时需要确保库存在（DLL Hell）

**可能的追问：**
- Q: 使用动态库的运行时查找顺序？ → A: 1) LD_PRELOAD（强制替换）2) LD_LIBRARY_PATH 3) /etc/ld.so.cache 4) /lib、/usr/lib
- Q: 如何查看一个可执行文件依赖哪些动态库？ → A: `ldd ./program`。它会列出所有需要的 .so 文件及其路径。
- Q: 链接过程分哪几类？ → A: 静态链接（链接时全部拷贝到可执行文件）、动态链接（加载时链接）、运行时链接（dlopen 手动加载）。

### 7.1 MySQL 索引底层

**回答话术：**
MySQL InnoDB 使用 **B+ 树**作为索引结构。特点：
- **非叶子节点**只存 key 和指针，不存数据——能容纳更多索引项，降低树的高度
- **叶子节点**存完整数据（聚簇索引）或指向主键（二级索引）
- **叶子节点间有链表指针**，便于范围查询（按序遍历）
- **高度通常为 3~4 层**，三次 I/O 即可查询到数据

**聚簇索引 vs 非聚簇索引**：InnoDB 主键索引是聚簇索引（叶子节点存整行数据），其他索引是非聚簇索引（叶子节点存主键值，需要回表）。

**可能的追问：**
- Q: B+ 树和 B 树的区别？ → A: B 树非叶子节点也存数据，B+ 树只有叶子节点存数据。B+ 树叶子节点用链表连接，范围查询更快。B+ 树非叶子节点能存更多 key，树更矮，磁盘 I/O 更少。
- Q: 什么是索引最左匹配原则？ → A: 联合索引 (a,b,c) 等效于创建了 (a)、(a,b)、(a,b,c) 三个索引。查询条件 WHERE a=1 AND b=2 能用到索引，WHERE b=2 用不到（因为没有从 a 开始）。实际上是可以使用索引进行过滤的，但只对 a 字段有效。

### 7.2 数据库事务的 ACID

**回答话术：**
1. **原子性（Atomicity）**：事务要么全部成功，要么全部失败回滚。通过 undo log 实现
2. **一致性（Consistency）**：事务执行前后数据满足所有约束。由 AID 共同保证
3. **隔离性（Isolation）**：多个事务并发执行不互相干扰。通过锁和 MVCC 实现
4. **持久性（Durability）**：提交的事务永久生效（写入磁盘）。通过 redo log 实现

**知识点讲解：**
- ACID 中 AID 是手段，C 是目的。一致性是系统对外表现的语义正确性。
- MySQL 通过 WAL（Write-Ahead Logging）保证持久性：先写 redo log，再写数据页。

**可能的追问：**
- Q: redo log 和 binlog 的区别？ → A: redo log 是 InnoDB 存储引擎的日志（物理日志，记录"对哪个页做了什么修改"），用于崩溃恢复。binlog 是 MySQL Server 层的日志（逻辑日志，记录执行的 SQL），用于主从复制。redo log 是循环写的，binlog 是追加写的。

### 7.3 数据库隔离级别

**回答话术：**
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 避免 | 可能 | 可能 |
| 可重复读（MySQL 默认）| 避免 | 避免 | 可能（InnoDB 通过 MVCC + gap lock 避免了）|
| 可序列化 | 避免 | 避免 | 避免 |

**并发问题**：
- 脏读：读到另一个未提交事务的数据
- 不可重复读：同一事务两次读同一行，结果不同（被其他事务修改）
- 幻读：同一条件查询，两次结果集行数不同（其他事务插入了新行）

**MySQL 可重复读如何防止幻读**：InnoDB 用 **MVCC**（快照读）和 **next-key lock**（当前读）防止幻读。快照读读取事务开始时的版本；当前读（SELECT FOR UPDATE）通过行锁 + 间隙锁锁住范围。

**可能的追问：**
- Q: 可序列化级别怎么实现的？ → A: 所有读都变成快照读 + 所有写加锁，实际退化为串行化执行。性能很低，一般不用。
- Q: MVCC 核心原理？ → A: 每行数据有隐藏的 trx_id（创建该版本的事务 ID）和 roll_pointer（指向 undo log 中上一个版本）。在可重复读级别，事务每次读都从 ReadView（已提交事务集合）判断行的可见性。读已提交级别每次查询都生成新 ReadView。

### 7.4 数据库连接池

**回答话术：**
**连接池**是一组预先创建的数据库连接，应用程序从中获取连接而不是新建连接。

**工作机制**：
1. 初始化时创建 N 个连接到连接池
2. 业务代码从池中借用一个连接
3. 使用完后归还到池中（不是 close）
4. 如果所有连接被占用，新请求等待或超时

**优势**：
1. **减少连接开销**：TCP 三次握手 + MySQL 鉴权（每次几毫秒到几十毫秒）
2. **控制并发上限**：避免大量请求同时创建连接打垮数据库
3. **复用连接**：避免频繁创建/销毁连接
4. **统一管理**：监控连接数、超时、健康检查

**可能的追问：**
- Q: 连接池大小设置多少合适？ → A: 经验公式：`核数 × 2 + 有效磁盘数`（对于 IO 密集型）。如果 CPU 密集型，接近核数即可。太大反而因为上下文切换降低性能。PostgreSQL 官方建议 CPU 核数的 1~2 倍，超出反而变慢。
- Q: 连接池中连接断了怎么办？ → A: 需要做心跳保活（如执行 SELECT 1）检测连接是否有效，无效则移除并创建新连接。或者使用连接池的空闲回收 + 重连机制。

### 7.5 SQL 语法相关

**7.5.1 drop、delete、truncate 的区别**
| 对比 | drop | truncate | delete |
|------|------|----------|--------|
| 类型 | DDL | DDL | DML |
| 内容 | 删除表结构及数据 | 清空表数据 | 逐行删除 |
| 事务 | 不可回滚（隐式提交） | 部分可回滚 | 可回滚 |
| 速度 | 快 | 快 | 慢（逐行记录日志）|
| 触发器 | 不触发 | 不触发 | 触发 |

**7.5.2 union 和 union all 的区别**
- **union**：合并结果集 + 去重（相当于 DISTINCT）+ 排序。性能开销大
- **union all**：直接合并全部结果，不去重不排序。效率高。如果确定无重复或用不到去重，优先用 union all

**7.5.3 left join 和 right join 的区别**
- left join：保留左表全部记录，右表无对应则填充 NULL
- right join：保留右表全部记录，左表无对应则填充 NULL

**7.5.4 MySQL 三张表的三种 join**
- INNER JOIN：取交集（两表都匹配的行）
- LEFT JOIN：左表全部 + 右表匹配
- RIGHT JOIN：右表全部 + 左表匹配
- FULL OUTER JOIN：MySQL 需要通过 UNION 实现（LEFT JOIN + RIGHT JOIN 的 UNION）

**7.5.5 group by 每组取第一个数的问题**
- 如果 SQL 写了 `GROUP BY` 但没有用聚合函数（MAX/MIN/SUM）来指定取哪个值，返回的"第一个"是随机的
- MySQL 允许 SELECT 中不包含在 GROUP BY 或聚合函数中的列（sql_mode 不严格时），但其他数据库（PostgreSQL）会报错
- 规范做法：用聚合函数明确指定，或者用 window function（ROW_NUMBER() OVER(PARTITION BY ...)）来控制

**7.5.6 增加一列的 SQL**

### 7.6 数据库死锁

**回答话术：**
**数据库死锁**和操作系统死锁本质一样：事务 A 持有资源 1 等待资源 2，事务 B 持有资源 2 等待资源 1。

**产生原因**：
- 不同事务以不同顺序加锁
- 间隙锁（gap lock）导致的锁冲突（MySQL 可重复读级别下）

**发现和定位**：
```sql
SHOW ENGINE INNODB STATUS\G  -- 查看最近死锁信息（LATEST DETECTED DEADLOCK）
-- 重点看：死锁涉及的事务、持有哪些锁、等待哪个锁、执行的 SQL 语句
```

**解决方案**：
1. **InnoDB 自动检测**：检测到死锁后回滚代价较小的事务（`innodb_deadlock_detect = ON`）
2. **应用层预防**：所有事务按统一顺序访问表/行
3. **缩小事务范围**：减少锁持有时间
4. **使用读已提交级别（RC）**：减少间隙锁的使用
5. **加锁超时**：设置 `innodb_lock_wait_timeout`（默认 50s）

**可能的追问：**
- Q: InnoDB 死锁检测的问题？ → A: 高并发下检测本身消耗 CPU（需要扫描等待图）。MySQL 8.0 在实践中，高并发场景有时会关闭死锁检测（`innodb_deadlock_detect = OFF`），靠锁超时来处理。但关闭后如果真正发生死锁，事务会等待到超时。
- Q: 数据库死锁 vs 编程死锁的异同？ → A: 本质相同（互斥 + 持有并等待 + 不可剥夺 + 循环等待）。区别：InnoDB 有自动死锁检测和回滚机制，程序语言级的死锁通常需要开发者自己规避。

### 7.7 MySQL 的锁

**回答话术：**
按粒度分类：
1. **行锁**：InnoDB 支持，锁定一行。开销大但并发高
2. **表锁**：MyISAM 使用，InnoDB 在执行 DDL 或某些特殊情况也会加表锁
3. **间隙锁**：只在可重复读（RR）级别下存在。锁定一个范围（不存在的行），防止幻读
4. **Next-Key Lock**：行锁 + 间隙锁的组合，锁定行和它前面的间隙

按属性分类：
- **共享锁（S锁）**：`SELECT ... LOCK IN SHARE MODE`，允许其他事务读但不允许写
- **排他锁（X锁）**：`SELECT ... FOR UPDATE`，不允许其他事务读或写

**可能的追问：**
- Q: 无索引的行锁会升级为什么？ → A: InnoDB 的行锁是通过索引实现的。如果 WHERE 条件没有命中索引，会锁全表（实际是行锁覆盖全表所有记录，不是表锁）。
- Q: 记录锁和间隙锁分别什么场景下使用？ → A: 唯一索引等值匹配 → 记录锁；普通索引范围查找 → 间隙锁 + 行锁（next-key lock）；无索引 → 全表行锁。

### 8.1 Redis 为什么这么快？

**回答话术：**
1. **纯内存操作**：数据在内存中，读写纳秒级

3. **I/O 多路复用**：用 epoll 处理大量客户端连接
4. **高效的数据结构**：跳表、压缩列表（ziplist）、快速列表（quicklist）等针对场景优化的结构
5. **渐进式 rehash**：rehash 不阻塞主线程

**可能的追问：**
- Q: 单线程不会慢吗？ → A: 单线程避免了锁竞争和上下文切换。Redis 的瓶颈通常是网络 I/O 和内存带宽，而非 CPU。单线程模型使实现简单且可预测。大 key 操作（如 KEYS、对超大集合的操作）会阻塞主线程，应该避免。

### 8.2 Redis 的五种数据类型及应用场景

**回答话术：**
| 类型 | 底层实现 | 应用场景 |
|------|----------|----------|
| String | 动态字符串（SDS） | 缓存、计数器、分布式锁（SETNX） |
| List | quicklist | 消息队列（LPUSH/BRPOP）、最新消息列表 |
| Set | hashtable / intset | 标签系统、签到、好友关系（交集/并集） |
| ZSet（Sorted Set）| dict + skip list | 排行榜、延时队列、优先级队列 |
| Hash | dict / ziplist | 对象缓存（用户信息、商品信息） |

**是否使用过 List 类型**：用过。可以用 LPUSH + BRPOP 实现简单的生产者-消费者消息队列，或者用 `LPUSH + LTRIM` 实现固定长度的最新列表。

**可能的追问：**
- Q: ZSet 的跳表结构在什么样的数据量下切换？ → A: zset 同时使用 dict（O(1) 查分值）和跳表（O(log n) 范围操作）。无论数据多少都同时使用这两种结构（不是切换关系）。

### 8.3 Redis 哨兵模式

**回答话术：**
哨兵（Sentinel）是 Redis 高可用方案。一组哨兵进程监控主从节点的健康状态，主节点挂掉时自动将从节点提升为主。

**节点数量建议**：
- **哨兵节点数 ≥ 3**（奇数，为了形成法定票数），通常 3 或 5
- **服务节点**：至少 1 个主库 + 1 个从库

**选举过程**：哨兵检测到主节点主观下线（sdown）→ 多个哨兵确认客观下线（odown）→ 进行领导者选举 → 从 slave 中选出一个提升为 master。

**可能的追问：**
- Q: 为什么哨兵要奇数的至少 3 个？ → A: 为了选举时能产生多数派（quorum）。哨兵数是奇数可以避免 2 个节点时平局。最少 3 个保证可以挂掉 1 个而剩余 2 个仍能形成多数。

### 8.4 Redis 消息队列实现

**回答话术：**
Redis 实现消息队列的方式：
1. **List**：LPUSH + BRPOP（阻塞读取），简单可靠，但不支持多播。先进先出
2. **Pub/Sub**：发布-订阅模式，支持多播。但有消息丢失问题——客户端离线就收不到
3. **Stream**（Redis 5.0+）：专业的消息队列数据结构，支持持久化、消费者组、ACK 确认机制

**推荐选择**：正式场景用 **Stream**——保证消息不丢失，支持 ACK 确认和消费者组，能回溯消息。

**可能的追问：**
- Q: Redis Stream 和 Kafka 有什么区别？ → A: Redis Stream 内存存储（可持久化到磁盘），适合小规模、低延迟消息。Kafka 磁盘持久化，通过顺序读写 + 分页缓存保证高性能，适合高吞吐、大规模消息场景。两者定位不同。

### 8.5 Redis 相比 Memcached 的核心优势

**回答话术：**
| 对比 | Redis | Memcached |
|------|-------|-----------|
| 数据类型 | 丰富（5+ 种）| 仅 string |
| 持久化 | 支持 RDB/AOF | 不支持（纯缓存）|
| 集群方案 | 哨兵、Cluster | 客户端分片 |
| 数据结构操作 | 丰富（交集、范围查询等）| 仅 get/set |
| 内存管理 | 多种结构优化 | slab + LRU |

**可能的追问：**
- Q: Redis 单节点部署的问题？ → A: 单点故障（宕机服务不可用）、容量有限（受单机内存限制）、并发能力受限于单核。

### 8.6 Redis 分布式锁

**回答话术：**
基于 Redis 的分布式锁核心思路：使用 SETNX（SET if Not eXists）命令。
```bash
SET lock_key unique_value NX PX 30000  # 获取锁，30 秒自动过期
# 释放锁时用 Lua 脚本保证原子性（检查值是否是自己加的锁）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**问题与改进**：
- 锁过期但任务没执行完 → 用 Redisson 的 watchdog 自动续期
- 主从切换导致锁丢失 → Redlock 算法（向多数节点同时申请锁）
- 非阻塞获取 → 设置超时时间，获取不到立即返回失败

## 第9章：设计模式

---

### 9.1 单例模式

**回答话术：**
**饿汉式**：类加载时就创建实例。简单，线程安全，但可能浪费资源（如果从未使用）。
```cpp
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance;  // C++11 保证线程安全
        return instance;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
private:
    Singleton() {}
};
```
**懒汉式**：首次使用时创建。需要线程安全处理。
```cpp
// C++11 后最佳实践：Meyer's Singleton
// 局部 static 变量在第一次调用时初始化，C++11 保证线程安全
Singleton& Singleton::getInstance() {
    static Singleton instance;
    return instance;
}
```

**可能的追问：**
- Q: 为什么 C++11 的 static 局部变量是线程安全的？ → A: C++11 标准要求编译器为静态局部变量的初始化插入双重检查锁（Double-Checked Locking），确保仅初始化一次且线程安全。本质上是编译器在初始化前后插入了原子操作和内存屏障。
- Q: 如何破坏单例？ → A: 通过克隆（拷贝构造）、反射、序列化/反序列化。C++ 中 delete 拷贝构造和赋值运算符可以阻止。

### 9.2 工厂方法模式和抽象工厂模式的区别

**回答话术：**
**工厂方法**：定义一个创建对象的接口（纯虚函数），让子类决定实例化哪个类。适用于单个产品等级结构的创建。

**抽象工厂**：创建相关或依赖的**一组**产品家族。适用于多个产品等级结构（如不同 UI 风格下的 Button + CheckBox + TextField）。

| 对比 | 工厂方法 | 抽象工厂 |
|------|---------|---------|
| 产品 | 单一产品 | 产品族（多个相关产品）|
| 创建 | 一个工厂创建一个产品 | 一个工厂创建一系列产品 |
| 场景 | 需要灵活扩展新产品类型 | 需要保证产品族的兼容性 |

**场景举例**：
- 工厂方法：日志记录器——文件日志、数据库日志、控制台日志
- 抽象工厂：跨平台 UI——Windows 工厂创建 WindowsButton + WindowsCheckbox，Mac 工厂创建 MacButton + MacCheckbox

**可能的追问：**
- Q: 简单工厂、工厂方法、抽象工厂的区别？ → A: 简单工厂把所有创建逻辑放一个函数里（if-else 判断）；工厂方法把创建延迟到子类（虚函数）；抽象工厂创建一组产品。

### 10.1 分布式缓存系统设计需要考虑哪些方面？

**回答话术：**
1. **数据分布**：一致性哈希（减少扩容影响的数据迁移量）、哈希槽（Redis Cluster 方案）
2. **高可用**：主从复制、哨兵/集群模式自动故障转移
3. **淘汰策略**：LRU、LFU、TTL 过期——内存有限时必须淘汰策略
4. **持久化**：Redis 的 RDB（快照）和 AOF（日志）保证数据不丢
5. **缓存穿透/击穿/雪崩**：
   - 穿透：查数据库也不存在的数据 → 布隆过滤器或缓存空值
   - 击穿：热点 key 过期失效，大量请求打到 DB → 互斥锁重建或永不过期
   - 雪崩：大量 key 同时过期 → 过期时间加随机值
6. **一致性**：缓存和数据库的最终一致性保证（延迟双删、Binlog 同步）

**可能的追问：**
- Q: 缓存穿透的布隆过滤器原理？ → A: 用多个哈希函数将 key 映射到几个位数组位置。查询时如果任何一个位为 0 则肯定不存在。可能有误判（说存在实际不存在），不存在误判。用于快速判断 key 是否可能在数据库中。

### 10.2 JWT 基本原理

**回答话术：**
JWT（JSON Web Token）是一个自包含的令牌，由三部分组成：
```
header.payload.signature
```

1. **Header**：指定签名算法（HS256/RS256）和 Token 类型
2. **Payload**：声明信息（用户 id、过期时间等），**base64 编码，不加密**，所以不要放敏感信息
3. **Signature**：对 header.payload 做签名的结果，防止篡改

**工作流程**：用户登录 → 服务器生成 JWT 返回 → 客户端存到 localStorage → 后续请求在 Authorization 头部携带 → 服务器验证签名。

**优点**：无状态（服务端不需要存 session），适合分布式系统。
**缺点**：无法主动注销（除非维护黑名单）、Payload 不能存敏感信息、Token 长度大。

**可能的追问：**
- Q: 如果用了 JWT 如何实现退出登录？ → A: 服务端维护一个黑名单（用 Redis），将 JWT 的 jti（唯一 ID）在过期前加入黑名单。每次请求先检查是否在黑名单中。但这破坏了 JWT 的"无状态"特性；另一种方式是用短过期时间 + 刷新 token。

---

### 10.3 服务器挂掉后客户端如何重连

**回答话术：**
需要从客户端和服务端两端设计：

**客户端策略**：
1. **指数退避重连**：第一次 1s，第二次 2s，第三次 4s... 最大间隔（如 30s），避免拥塞
2. **心跳检测**：客户端定期发送心跳，超时未收到回复则判定断连，触发重连
3. **断线重连状态机**：区分首次连接、断线重连、正常断开，重连时恢复会话（如有 session ID）
4. **消息缓存**：断连期间的消息缓存在本地队列，重连后批量发送

**服务端策略**：
1. **心跳超时**：服务端检测客户端心跳超时后释放资源，但不立即销毁会话（保留一段时间）
2. **幂等处理**：重连后可能重复发送消息，服务端接口需要幂等
3. **状态恢复**：如果客户端带 session/token 重连，服务端恢复未完成的操作

### 11.6 挑一个锁的实现机制讲解

**回答话术（推荐原子自旋锁）**：
自旋锁的实现依赖 CPU 的原子操作 CAS（Compare And Swap）。在 x86 上是 `lock cmpxchg` 指令。C++11 可以用 `std::atomic_flag` 实现：
```cpp
class SpinLock {
    atomic_flag flag = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire)) // 忙等
            _mm_pause();  // CPU yield hint
    }
    void unlock() {
        flag.clear(std::memory_order_release);
    }
};
```
`test_and_set` 是原子操作：先在 flag 上写入 1，同时返回旧值。如果旧值是 0 表示成功获取锁，否则说明锁被持有，循环等待。`_mm_pause()` 提示 CPU 正处于自旋等待，优化流水线。
