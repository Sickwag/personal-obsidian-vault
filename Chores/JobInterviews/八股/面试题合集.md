# 通用面试题

## Qt 相关

### QPointer 和 C++ 智能指针的区别
**回答话术：**
QPointer 不是智能指针，它不管理生命周期，只做弱引用——当 QObject 子类对象析构时，QPointer 会自动被置为 nullptr。C++ 的 shared_ptr 通过引用计数管理生命周期，weak_ptr 通过控制块检测对象存活。根本区别在于：shared_ptr/weak_ptr 是"我数着还有多少人用你"，QPointer 是"你死的时候记得告诉我一声"。QPointer 只能用于 QObject 子类。
**知识点讲解：**

| | unique_ptr | shared_ptr | weak_ptr | QPointer |
|--|------------|------------|----------|----------|
| 管理所有权 | 独占，自动 delete | 共享，引用计数归零时 delete | 不管理 | 不管理 |
| 防止悬空 | 转移所有权，不存在用已删对象 | 引用计数保证对象存活 | lock() 检查对象是否存活 | 对象析构时自动置 nullptr |
| 限制 | — | — | 必须配合 shared_ptr | T 必须是 QObject 子类 |
| 实现依赖 | 模板元编程 | 控制块 + 原子计数 | 依赖控制块 | 依赖 QObject 析构函数通知 |

> [!Info] 可能的追问:
> - Q: QPointer 可以配合 unique_ptr 使用吗？
> - A: 不能。QPointer 专门为 QObject 设计，对象析构时通过 QObject 的析构函数通知机制置空。unique_ptr 管理的对象不一定是 QObject，也不会触发这种通知。想让 QPointer 指向的对象销毁，直接 delete 原始指针或超出作用域即可，QPointer 会自动置空。
> - Q: 标准库 shared_ptr 为什么在并发场景中性能较差？
> - A: 引用计数的增减是原子操作（memory_order_relaxed 级别的原子变量加减），虽然比 mutex 快很多，但频繁的原子操作仍然会导致 cache line  bouncing（缓存行乒乓）和内存排序开销，在多核高频访问时成为瓶颈。
> - Q: 既然 QPointer 不管理生命周期，RAII 不就能自动析构了吗？为什么还要 QPointer？
> - A: 场景不同。RAII 保证"这个对象一定会在某个时刻被销毁"（所有者决定生命周期），但无法解决"多个地方引用了这个对象，如何知道它已经被别人销毁了"的问题——你持有的原始指针会成为悬空指针。QPointer 解决的是"谁都可以销毁这个 QObject，销毁后其他持有者能感知到"的需求。典型场景：Qt 中一个 QPushButton 被父窗口 delete 了（Qt 的对象树机制自动销毁子对象），但其他代码中还有一个指向它的指针，QPointer 能自动感知并置 nullptr，而 raw pointer 不会知道你已经被删了。

### Qt 元对象系统（MOC）的原理
**回答话术：**
Qt 的元对象系统（Meta-Object System）由 Q_OBJECT 宏驱动，MOC（Meta-Object Compiler）在编译前扫描头文件，为包含 Q_OBJECT 宏的类生成额外的 C++ 代码（.moc 文件），填充 QMetaObject 结构体。这个结构体包含类名、父类指针、信号/槽/属性表、qt_static_metacall 函数指针，形成四个核心能力：
1. **信号槽**：运行时通过索引查找并调用连接的方法
2. **运行时类型信息（RTTI）**：qobject_cast 遍历 QMetaObject 链表做指针比较，比 dynamic_cast 快且跨编译器 ABI 一致
3. **属性系统**：通过 Q_PROPERTY 声明的属性可在运行时读写
4. **动态调用**：QMetaObject::invokeMethod 通过方法名/索引在运行时调用 Q_INVOKABLE 方法
**知识点讲解：**
```cpp
QMetaObject::invokeMethod(obj, "start", Qt::QueuedConnection, Q_ARG(int, 42));
```
MOC 为每个信号/槽/Q_INVOKABLE 方法生成 qt_static_metacall 辅助函数——内部是一个巨大的 switch 语句，按方法索引分发到真正的方法调用。方法名解析有开销，所以提供了索引重载来绕过字符串查找。
**注意：** C++ 标准 RTTI（typeid）依赖编译器开启 rtti-flag，通过 vtable 中的 type_info 指针工作，跨编译器 ABI 不一致。Qt 的 RTTI 不依赖编译器，依靠 MOC 编译时生成的元对象信息，通过 QMetaObject 双向链表沿继承链做指针/索引对比。
> [!Info] 可能的追问:
> - Q: Qt 的信号槽机制和观察者模式有什么异同？
> - A: 相同点都是一对多通知。区别在于：
> 	1. Qt 信号槽是类型安全的，编译期检查签名匹配
> 	2. Qt 支持跨线程（QueuedConnection），通过事件循环投递 
> 	3. 观察者模式需要手动注册/注销，忘记注销会导致悬空指针；Qt 的 QPointer 可以自动检测对象是否存活
> 	4. Qt 的槽可以是普通成员函数（通过 Q_INVOKABLE 或 slots 标记），不要求继承特定接口并实现里面的固定虚函数
> - Q: 信号槽如何检查签名匹配？多个同名槽函数如何精准匹配？
> - A: MOC 在编译时生成信号和槽的签名信息，connect 时通过字符串或规范化类型比较参数类型。使用函数指针重载的 connect（Qt5+）则通过模板推导精确匹配。对于多个同名槽，使用 `qOverload<类型>()` 指定具体重载版本。
> - Q: 为什么信号槽机制比回调函数慢？
> - A: 
> 	1. 信号槽需要遍历连接列表，查找匹配的槽 
> 	2. 跨线程时参数需要拷贝到事件队列（涉及元组序列化）
> 	3. 字符串查找（旧版 connect 语法）或索引查找（新版语法）的开销。相比直接函数调用，多了一层间接分发。

### Qt 中的 deleteLater 的作用与使用场景
**回答话术：**
deleteLater 将对象的析构推迟到事件循环处理完当前事件之后执行。核心问题是：在 Qt 的事件处理机制中，如果在槽函数执行期间直接 delete 了发送信号的对象，但当前事件链还没走完（后续可能还有代码要访问这个对象），就会 use-after-free。deleteLater 把析构请求打包成一个"延迟删除事件"（QDeferredDeleteEvent）投递到对象所在线程的事件队列，等当前事件和队列中已有事件都处理完才执行真正的析构。
**详细过程**：
1. 调用 `obj->deleteLater()` → Qt 将 obj 注册到 QCoreApplication 的延迟删除列表
2. 在当前事件处理完后，回到事件循环时，Qt 检查延迟删除列表
3. 对列表中的每个对象调用 `delete obj`
4. 如果你在槽函数 A 中调用了 sender->deleteLater()，A 继续执行完，返回到事件循环，然后才执行析构
**典型场景**：QTcpSocket 的 disconnected 信号处理中，如果直接 `delete socket` 会导致后续事件循环继续访问已销毁的 socket。用 deleteLater 等 disconnected 信号处理完成后再删除。
**注意**：如果对象所在线程没有运行事件循环（如没有 QCoreApplication::exec），deleteLater 不会触发析构，对象会泄漏。这种情况下需要手动 delete。
**知识点讲解：**
```cpp
// 错误的做法：
connect(socket, &QTcpSocket::disconnected, this, [this, socket]() {
    delete socket;  // socket 对象立即销毁
    // 但 disconnected 信号的处理还未完全结束，
    // 如果之后的事件循环中还有 socket 相关的待处理事件 → 崩溃！
});
// 正确的做法：
connect(socket, &QTcpSocket::disconnected, socket, [socket]() {
    socket->deleteLater();  // 投递延迟删除事件，等当前事件处理完再析构
});
```
> [!Info] 可能的追问:
> - Q: deleteLater 和直接 delete 有什么区别？
> - A: 直接 delete 立即调用析构函数释放内存；deleteLater 把对象注册到事件循环的延迟删除列表，等控制权回到事件循环后才执行。如果对象所在线程没有运行事件循环，deleteLater 不会执行析构（需要 QueuedConnection 确保在正确线程处理）。
> - Q: deleteLater 解决了什么问题？
> - A: 解决了"在事件处理期间销毁对象"可能导致 use-after-free 的问题。典型场景：QTcpSocket 的 readyRead 信号处理中，如果处理完直接 delete socket，但 readyRead 处理函数返回后框架可能继续访问 socket，导致崩溃。

### Qt 中的动态属性和静态属性
**回答话术：**
- **静态属性**：通过 Q_PROPERTY 宏在类定义中声明的属性，编译期确定，MOC 生成对应的读写接口。用于标准的 Qt 属性系统（如 Q_PROPERTY(int value READ value WRITE setValue NOTIFY valueChanged)）
- **动态属性**：运行时通过 setProperty() 添加的属性，在任意 QObject 上动态附加键值对。用 property("name") 读取，propertyNames() 枚举。适合在不修改类定义的情况下为对象附加额外数据
**知识点讲解：**
```cpp
// 静态属性
class MyWidget : public QWidget {
    Q_OBJECT
    Q_PROPERTY(int value READ value WRITE setValue NOTIFY valueChanged)
};
// 动态属性
QPushButton* btn = new QPushButton("Click");
btn->setProperty("customId", 42);  // 运行时动态附加
int id = btn->property("customId").toInt();
```

### qOverload 的作用
**回答话术：**
qOverload 用于解决信号或槽函数重载时的歧义问题。当同一个信号有多个重载版本（如 `QComboBox::currentIndexChanged `有 (int) 和 (QString) 两个版本），使用旧版 connect 或函数指针 `&QComboBox::currentIndexChanged` 会因重载导致编译失败。`qOverload<类型>()` 显式指定要使用的是哪个重载版本。
**知识点讲解：**
```cpp
// 旧版字符串连接（不推荐）：
connect(combo, SIGNAL(currentIndexChanged(int)), this, SLOT(onIndexChanged(int)));
// 新版函数指针连接（类型安全），需要处理重载：
connect(combo, qOverload<int>(&QComboBox::currentIndexChanged), this, &MyClass::onIndexChanged);
```
> [!Info] 可能的追问:
> - Q: 信号槽参数传递是值传递还是引用？
> - A: 默认值传递。跨线程（QueuedConnection）时参数必须可拷贝，通过元组序列化到事件队列。同线程（DirectConnection）可以传递引用。注册自定义类型用 qRegisterMetaType。

### Qt 的动态调用特性（invokeMethod）
**回答话术：**
动态调用是指 Qt 允许在运行时通过**方法名字符串**或**方法索引**来调用一个对象的方法，而不需要在编译期知道该方法的具体类型。这通过 `QMetaObject::invokeMethod` 实现。MOC 为每个 Q_INVOKABLE 方法和槽函数在 `qt_static_metacall` 中生成索引到实际调用的映射。invokeMethod 的流程是：传入方法名 → 遍历 QMetaObject 的方法表查找 QMetaMethod → 根据方法索引调用 qt_static_metacall → switch 分发到实际函数。
**作用**：1) 解耦——调用者不需要知道被调用者的完整类型，只要知道方法名和参数即可 2) 跨线程调用——通过 InvokeMethod 的 `Qt::QueuedConnection` 参数把调用投递到目标线程的事件循环 3) 插件/脚本系统——在运行时根据配置或用户输入调用任意方法。
**知识点讲解：**
```cpp
// 运行时通过字符串调用 obj 的 "start" 方法，传递整型参数 42
QMetaObject::invokeMethod(obj, "start", Qt::QueuedConnection, Q_ARG(int, 42));
// 索引重载版本（避免字符串查找开销）：
int method_index = obj->metaObject()->indexOfMethod("start(int)");
QMetaObject::invokeMethod(obj, method_index, Q_ARG(int, 42));
// 在调用频繁的场景（如游戏循环中调用数千次），用索引版本代替字符串版本
```
**实现原理**：MOC 生成 `qt_static_metacall(QObject*, QMetaObject::Call, int, void**)` 函数，内部是 switch-case 语句。invokeMethod 通过方法名找到方法索引，然后调用 qt_static_metacall 并传入该索引。qt_static_metacall 根据索引 switch 到对应函数。
> [!Info] 可能的追问:
> - Q: invokeMethod 和直接调用相比性能如何？
> - A: invokeMethod 字符串版本有方法名查找开销（遍历 QMetaObject 的方法表），大约比直接调用慢几十到几百倍。索引版本接近但略慢于直接调用（一次 switch 分发 vs 直接的函数调用）。但跨线程的 invokeMethod（QueuedConnection）开销远大于直接调用——因为涉及参数序列化和事件队列投递。

### connect 信号槽未触发的排查思路
**回答话术：**
信号槽连接了但没触发，从以下角度逐步排查：
1. **连接语法错误**——检查 connect 的第五个参数是否影响了触发方式（是否误用了 Qt::DirectConnection 跨线程）、检查签名是否匹配（新旧语法混用常见问题）
2. **对象生命周期**——信号发射时接收对象是否已被销毁？槽函数是否因为接收者的析构而无法调用？用 QPointer 检查对象存活
3. **线程问题**——跨线程连接需要 QueuedConnection（或默认 AutoConnection），接收者线程必须有事件循环（exec()）
4. **信号被屏蔽**——检查是否调用了 blockSignals(true)
5. **槽函数签名不匹配**——新版 connect 如果传入 lambda，参数类型必须完全匹配信号参数
**知识点讲解：**
```cpp
// 常见错误：跨线程用 DirectConnection（槽函数在执行信号的线程中调用）
connect(sender, &Sender::sig, receiver, &Receiver::slot, Qt::DirectConnection);
// 如果 sender 和 receiver 在不同线程，槽会在 sender 线程执行而不是 receiver 线程
// 可能需要 QueuedConnection 确保槽在 receiver 所在线程执行

// 另一个常见问题：lambda 捕获了已析构的对象
connect(obj, &QObject::destroyed, this, [ptr]() {
    ptr->doSomething();  // 如果 ptr 此时已经析构 → 崩溃
});
```
> [!Info] 可能的追问:
> - Q: 如何检查信号是否被发射了？
> - A: 在信号前面加 qDebug() 打印日志，或者重写该类的信号发射函数（如果允许）。在**环境变量中 `export QT_DEBUG=1` 下运行**，可以看到
> 	- 何时尝试连接信号和槽
> 	- 连接是否成功（若失败会提示原因，如参数不匹配）
> 	- 信号发射时，哪些槽被调用
> 	- 队列连接（跨线程）的传递过程
>  也可以 hook QObject::connect 在自己的断点中检查连接是否生效。
> - Q: blockSignals 在什么场景使用？
> - A: 在批量更新 UI 控件值时，暂时 blockSignals 防止每改一个值都触发信号槽（造成不必要的重绘或递归调用）。更新完再 unblockSignals。

### Qt 属性系统详解
**回答话术：**
Qt 的属性系统由 Q_PROPERTY 宏驱动，MOC 编译期解析生成属性的元信息。一个属性的声明包含：
```cpp
Q_PROPERTY(int value READ getValue WRITE setValue NOTIFY valueChanged)
```
- **READ**：读属性的 getter 函数，必须有
- **WRITE**：写属性的 setter 函数，可选
- **NOTIFY**：属性变化时发射的信号，可选（用于绑定和 QML 属性更新）
- **DESIGNABLE**：是否在 Qt Designer 中可见，默认 true
- **MEMBER**：直接绑定到成员变量，省略 READ/WRITE
- **USER**：标记是否为用户可编辑属性（如 QLineEdit::text 是 USER 属性）
**静态属性 vs 动态属性**：静态属性在 Q_PROPERTY 宏中声明，运行期通过 property()/setProperty() 读写，但属性名和类型在编译期固定。动态属性通过 setProperty() 在任意 QObject 上运行时附加，不需要预声明，适合随意附加额外数据（如 QWidget 存一个 customId）。
**应用**：
1) QML 与 C++ 数据绑定——QML 引擎通过属性系统访问 C++ 对象属性 
2) Qt Designer 的属性编辑器——根据 DESIGNABLE 标记显示属性 
3) QDataWidgetMapper——模型/视图框架中通过属性名映射字段；
4) 序列化——遍历动态属性可以序列化/反序列化任意 QObject 的状态。
5) QAbstractProxyModel 和排序筛选通过角色属性进行
> [!Info] 可能的追问:
> - Q: 什么场景需要动态调用而不是静态调用？
> - A: 典型的场景是插件系统——主程序加载一个 DLL，拿到 DLL 暴露的 QObject 指针，但不知道具体有哪些方法。通过 QMetaObject 的方法表枚举，再用 invokeMethod 动态调用。另一个是脚本/反射场景，如 QML 中调用 C++ 方法，底层就是 invokeMethod。静态调用（编译期确定函数名）更高效但不够灵活。
> - Q: invokeMethod 和直接调用相比性能如何？
> - A: invokeMethod 字符串版本有方法名查找开销（遍历 QMetaObject 的方法表），大约比直接调用慢几十到几百倍。索引版本接近但略慢于直接调用（一次 switch 分发 vs 直接的函数调用）。但跨线程的 invokeMethod（QueuedConnection）开销远大于直接调用——因为涉及参数序列化和事件队列投递。

### 结构体/类的大小与内存对齐
**回答话术：**
内存对齐就是就是将数据存放在内存的某个位置，使得 CPU 可以更快地访问到这个数据，以空间换时间的方式来提高 cpu 访问数据的性能。
计算规则：
1) 第一个成员放在结构体对象地址偏移量为 0 的位置
2) 结构体最终大小对齐到最大成员对齐边界的整数倍。有一个特例是空类大小为 1（保证每个对象有唯一地址）。
3) 其他成员要对齐到对齐数整数倍的地址位置
4) 结构体/类的大小由成员变量决定，**成员函数不占对象体积**（函数代码在代码段）。
5) sizeof 只会计算成员变量加上内存对齐的 padding。
**知识点讲解：**
究其原因是因为CPU 只能读取寄存器上的数据，而为了尽可能利用并行能力和节约地址总线位数，CPU 会读取每一个内存条上的所有颗粒（一般是 4 个），每个颗粒有 8 个 bank 同时读取的一位拼起来才是一个字节，每次读取时CPU 都会读取 4 个颗粒上相同位置的bank 上相同位置的一个位，组合起来就是CPU 一次读取 32 位，体现在读取规则上就是只能寄存器读取能被 4 整数的地址，体现在工程实践上就是结构体中成员先大后小排列
至于为什么读取的是每个 bank 上的同一位是因为要节约地址总线数量，地址总线传入的一个地址映射到内存颗粒中 8 个 bank 的相同位置。同时操作的 4 个字节在内存颗粒中的位置也是一样的
**打破对齐的方法：** 使用 `#pragma pack(1)` 或在结构体后添加 `__attribute__((packed))`（GCC/Clang）。
> [!Info] 可能的追问:
> - Q: 如何确定结构体的内存对齐单位？
> - A: 默认对齐单位是结构体中最大基础类型成员的大小（double 可能是 8，int 是 4）。可以通过 alignof() 查看类型的对齐要求，alignas() 自定义对齐。
> - Q: 内存对齐的最小单位如何确定？
> - A: 最小的对齐单位是 1 字节（char 类型）。但每个类型都有其自然对齐（natural alignment），通常是类型大小。结构体的对齐取其最大成员的对齐值。

### Qt 信号槽与观察者模式的异同 + 自行实现思路
**回答话术：**
相同点：都是一对多的通知机制，信号发射时所有连接的槽/观察者被通知。
不同点：
1) 类型安全——Qt 信号槽在编译期检查参数签名匹配，观察者模式通常通过基类接口（void update()）传递，类型不安全；
2) 对象解耦——信号发送者不需要知道接收者，观察者模式需要观察者持有主题引用；
3) 生命周期——QPointer 自动检测对象存活避免悬空，观察者模式忘记注销会导致悬空指针；
4) 跨线程——Qt 通过 QueuedConnection 跨线程投递，观察者模式默认同步调用。
**自己实现简易信号槽的思路：**
```cpp
// 槽对象封装——可调用对象 + 线程安全
struct Slot {
    std::function<void()> callable;  // 用 std::function 包装
    QObject* receiver;               // 用于生命周期检测
};
// 信号就是一个 vector<Slot>，emit 时遍历调用
std::vector<Slot> slots_;
void emit() {
    for(auto& slot : slots_) {
        if(slot.receiver) slot.callable();
    }
}
// connect 就是向 vector 添加一个 Slot
// disconnect 就是移除对应 Slot（可用 erase-remove）
// 跨线程：投递到目标线程的事件队列（类似 Qt 的 QCoreApplication::postEvent）
// 生命周期检测：connect 时保存 QPointer，调用前判断是否 nullptr
```
核心：用 `std::function` 做类型擦除，用 `std::vector` 存储槽列表，遍历调用。跨线程用消息队列（mutex + condition_variable + 工作线程处理）。生命周期检测用类似 QPointer 的机制。
> [!Info] 可能的追问:
> - Q: 如果信号带参数怎么处理？
> - A: 用模板 + std::function<void(Args...)>，emit 时传入参数转发给所有槽。但类型擦除比 Qt 的 MOC 方案复杂——Qt 有 MOC 编译期生成参数序列化代码，自己实现可以用 variadic template + type erasure（类似 std::function 的实现方式）。
> - Q: 如何支持跨线程的信号槽？
> - A: 需要消息队列。connect 时记录目标线程 ID，emit 时判断是否同线程——同线程直接调用，跨线程将调用包装为函数对象投递到目标线程的事件队列。目标线程的事件循环不断从队列取任务执行。

### Qt 网络编程的类与基本用法
**回答话术：**
Qt 网络编程主要涉及三个模块：`QTcpSocket`（TCP 客户端）、`QTcpServer`（TCP 服务端）、`QUdpSocket`（UDP）。它们都继承自 `QAbstractSocket`，基于 Qt 的事件循环和信号槽机制实现**异步 I/O**——网络操作不阻塞 UI 线程，通过信号（connected、readyRead、disconnected）通知结果。
**核心类与信号**：
- **QTcpSocket**：TCP 客户端套接字。`connectToHost()` 连接服务器，`write()` 发送数据，`readyRead` 信号触发时调用 `readAll()`/`read()` 读取。`connected` 确认连接成功，`disconnected` 确认断开。粘包需应用层处理（协议头 + 缓冲区积累）。
- **QTcpServer**：TCP 服务端。`listen()` 监听端口，`newConnection` 信号触发时调用 `nextPendingConnection()` 获取新的 QTcpSocket 实例。
- **QUdpSocket**：UDP 套接字。无连接，`writeDatagram()` 发送数据报，`readyRead` 后 `readDatagram()` 接收。
**知识点讲解：**
```cpp
// TCP 客户端示例
QTcpSocket* socket = new QTcpSocket(this);
connect(socket, &QTcpSocket::connected, this, []() {
    qDebug() << "connected!";
});
connect(socket, &QTcpSocket::readyRead, this, [socket]() {
    QByteArray data = socket->readAll();
    // 处理收到的数据（注意粘包，需要积累到自定义缓冲区）
});
connect(socket, &QTcpSocket::disconnected, socket, &QTcpSocket::deleteLater);
socket->connectToHost("127.0.0.1", 8080);
// 发送数据：
socket->write("Hello");
// 注意：write 不一定立即发送，由 Qt 事件循环调度发送

// TCP 服务端示例
QTcpServer* server = new QTcpServer(this);
connect(server, &QTcpServer::newConnection, this, [server]() {
    QTcpSocket* client = server->nextPendingConnection();
    // 为每个客户端连接 connect 相应信号
    connect(client, &QTcpSocket::readyRead, ...);
    connect(client, &QTcpSocket::disconnected, client, &QTcpSocket::deleteLater);
    client->write("Welcome");
});
server->listen(QHostAddress::Any, 8080);

// UDP 发送/接收
QUdpSocket* udp = new QUdpSocket(this);
udp->bind(8888);  // 绑定端口接收
connect(udp, &QUdpSocket::readyRead, [udp]() {
    while (udp->hasPendingDatagrams()) {
        QByteArray datagram;
        datagram.resize(udp->pendingDatagramSize());
        udp->readDatagram(datagram.data(), datagram.size());
    }
});
udp->writeDatagram("Hello", QHostAddress::Broadcast, 8888);
```
**注意点**：
1. QTcpSocket 默认使用主线程的事件循环。如果网络 I/O 量大，可以移到工作线程——将 socket 对象 moveToThread 到工作线程，使用信号槽跨线程通信
2. `write()` 返回时数据可能还在发送缓冲区，未真正发出。`bytesWritten` 信号确认数据已写入底层 socket
3. 粘包处理需要在应用层实现：通常用"固定长度头（4 字节体长）+ 可变长度体"的协议格式
> [!Info] 可能的追问:
> - Q: Qt 的 socket 和原生 socket（POSIX socket / WinSock）比有什么好处和缺点？
> - A: 
> 1) 好处：
> 	1) 跨平台——同一套 API 在 Windows/Linux/macOS 上一致 
> 	2) 异步 I/O 基于信号槽——不需要手动管理 epoll/select 
> 	3) 与 Qt 事件循环集成——可以安全地从 UI 线程操作网络。
> 2) 缺点：
> 	1) 性能不如原生 epoll（多了事件循环分发的开销）
> 	2) 绑定 Qt 生态——不使用 Qt 的项目无法复用 
> 	3) 对极端高性能场景（如百万并发）不如原生 epoll 灵活
> - Q: 如果 QTcpSocket 在工作线程中使用，需要注意什么？
> - A: 
> 1) socket 对象必须在工作线程中创建（或创建后 moveToThread）
> 2) 不能从主线程直接调用 socket 的 write/read（线程不安全），必须通过信号槽跨线程触发 
> 3) 工作线程必须有事件循环（QThread::exec），否则信号槽和网络事件无法处理 
> 4) 大量并发连接建议用 QThreadPool 管理多个工作线程，每个线程跑一个事件循环

### Qt 事件循环机制与信号槽触发的底层原理
**回答话术：**
Qt 的事件循环（Event Loop）是 `QCoreApplication::exec()` 启动的一个无限循环，其核心工作是：不断从事件队列中取出事件并分发到对应的 QObject 进行处理。简化模型是 `while(!quit) { processNextEvent(); }`。事件种类包括：窗口系统事件（鼠标/键盘）、定时器事件（QTimer）、网络 I/O 事件（QTcpSocket）、用户自定义事件（QEvent::registerEventType）以及最重要的——**跨线程信号槽调用事件（QMetaCallEvent）**。
**信号槽触发的底层流程**：
1. **编译期**：MOC 为每个信号函数生成一个"信号发射器"（如 `emit mySignal()` 展开为 `QMetaObject::activate(...)`），为每个槽函数生成索引
2. **connect 时**：`connect(sender, signal, receiver, slot)` 在 sender 的连接列表中添加一个连接条目，记录 receiver 指针、槽函数索引、连接类型（Direct/Queued/Auto）
3. **信号发射时**（`emit mySignal(args...)`）：
   - 如果是 **DirectConnection**（同线程默认）：直接通过 `qt_static_metacall` → switch 分发 → 调用槽函数。本质上就是**一个普通函数调用**，栈与当前信号发射函数相同
   - 如果是 **QueuedConnection**（跨线程）：将参数序列化，构造一个 `QMetaCallEvent`，通过 `QCoreApplication::postEvent()` 投递到 **receiver 所在线程的事件队列**。receiver 所在线程的事件循环在 `processNextEvent()` 中取出这个事件，反序列化参数，最终调用槽函数
**事件循环的具体流程**：
```cpp
// QEventLoop::exec() 的简化伪码
while (!quit) {
    if (event = event_queue.dequeue()) {  // 从队列取事件
        event->dispatch();                 // 分发到目标 QObject
        // 对于跨线程信号槽：dispatch 调用 QObject::event()
        // QObject::event() 检测到 QMetaCallEvent，调用 qt_static_metacall
        // qt_static_metacall switch 到对应索引，调用实际槽函数
    } else {
        // 队列为空，等待新事件发生（select/epoll/WaitForMultipleObjects）
        native_event_loop.wait_for_events();
    }
}
```
**底层跨平台实现**：Qt 在 Linux 上用 `select`/`epoll`（QEventDispatcherUNIX），在 Windows 上用 `WaitForMultipleObjects`/`MsgWaitForMultipleObjects`（QEventDispatcherWin32），在 macOS 上用 `CFFileDescriptor`/`kqueue`（QEventDispatcherCF）。这些底层 I/O 监视器使得 Qt 能在"没有事件时"让线程休眠，事件到来时立即唤醒。
> [!Info] 可能的追问:
> - Q: 为什么 QThread::exec() 必须调用，否则信号槽不工作？
> - A: 因为跨线程信号槽投递的 QMetaCallEvent 需要事件循环从队列中取出并分发。如果工作线程没有 exec()（事件循环），事件进入队列后永远不会被处理，槽函数永远不会被调用。主线程默认有 exec()（在 main() 的 app.exec() 中），所以主线程的信号槽正常。这就是为什么创建 QThread 时如果使用 run() 而不调用 exec()，跨线程信号槽不触发的根本原因。
> - Q: 信号槽和直接函数调用哪个快？
> - A: 同线程 DirectConnection：略慢于直接调用（多了一次遍历连接列表和索引查找的开销，约几十纳秒的差距）。跨线程 QueuedConnection：远慢于直接调用（涉及参数序列化、事件队列入队出队、事件循环调度，约几微秒）。在性能敏感的场景（如游戏渲染循环中每秒触发数万次信号），建议用 direct call 替代信号槽。
> - Q: 我可以自定义事件并投递到事件循环吗？
> - A: 可以。继承 QEvent 定义自定义事件类型（用 QEvent::registerEventType 注册类型号），通过 QCoreApplication::postEvent() 异步投递，在 QObject::customEvent() 或 QObject::event() 中处理。这是 Qt 中线程间通信的重要方式之一，也是 Qt 框架内部实现跨线程信号槽的基础。

### OSI 七层模型与 TCP/IP 协议栈
**回答话术：**
OSI 七层模型从下到上：物理层 → 数据链路层 → 网络层 → 传输层 → 会话层 → 表示层 → 应用层。TCP/IP 协议栈简化为四层：网络接口层（物理+链路）→ 网络层（IP、ICMP、ARP）→ 传输层（TCP、UDP）→ 应用层（HTTP、FTP、SMTP）。数据封装过程：应用数据逐层添加头部，接收方逐层解封装。

| 层 | 典型协议 |
|---|---------|
| 应用层 | HTTP、SMTP、FTP、DNS、SSH、WebSocket |
| 表示层 | SSL/TLS、XDR |
| 会话层 | RPC、NetBIOS |
| 传输层 | TCP、UDP、TLS |
| 网络层 | IP、ICMP、ARP、OSPF、RIP、BGP |
| 数据链路层 | 以太网、PPP、VLAN |
| 物理层 | 双绞线、光纤、无线电 |

> [!Info] 可能的追问:
> - Q: ARP 协议在哪一层？
> - A: 工作在网络层和链路层之间，用于 IP 地址到 MAC 地址的解析。通常归为链路层或网络接口层协议。
> - Q: 为什么实践中常用 TCP/IP 四层模型而不是七层模型？
> - A: OSI 七层模型是理论标准，会话层和表示层在实际实现中通常被合并到应用层（如 TLS 直接在传输层之上，不单独为一层）。

## C++ 特性

### 指针的本质、大小与运算
**回答话术：**
指针是一个存储内存地址的整型数，大小与 CPU 位数有关（32 位 4 字节，64 位 8 字节）。解引用（`*ptr`）访问以该地址为起始、长度为指针所指类型大小的内存块。指针支持 cv 修饰符（const/volatile）控制访问权限。指针运算按指向类型大小做步进——ptr+1 使地址增加 sizeof(T)。成员函数指针比较特殊：占用两个指针大小，不能转换为` void*` 也不能进行算术运算，因为类可能有多重继承，需要同时存储 this 偏移。
**知识点讲解：**
```cpp
int arr[5] = {1,2,3,4,5};
int* p = arr;
p++;  // 地址增加 sizeof(int)=4，指向 arr[1]
// 成员函数指针
struct A { void func(int); void func(double); };
void (A::*pmf)(int) = &A::func;  // 占用 16 字节（x86-64），存储函数地址 + this 偏移
```
> [!Info] 可能的追问:
> - Q: 为什么成员函数指针不能转换为 void*？
> - A: 普通函数指针可以（因为就一个地址），但成员函数指针除了函数地址还需要存储 this 指针调整信息（虚继承、多继承时需要偏移 this）。这种结构在不同编译器实现不同，不能保证 sizeof(void*) == sizeof(member function pointer)。
> - Q: 空指针解引用一定会崩溃吗？
> - A: 不一定——解引用空指针是未定义行为，可能崩溃（段错误），也可能"恰好"在地址 0 处有映射（某些嵌入式系统）。不应该依赖任何特定行为。

### 深拷贝和浅拷贝的区别
**回答话术：**
浅拷贝只复制指针值（地址），不复制指针指向的内容。深拷贝会复制指针指向的整个数据块。C++ 中默认的拷贝构造函数和拷贝赋值运算符执行的是**浅拷贝**（按成员逐字节复制）。如果类有指针成员指向动态分配的内存，浅拷贝会导致两个对象指向同一块内存，析构时 double free 或 use-after-free。实现深拷贝需要自定义拷贝构造函数和拷贝赋值运算符——为指针成员分配新的内存并复制数据。
**知识点讲解：**
```cpp
struct Shallow {
    int* data;
    Shallow(int v) : data(new int(v)) {}
    // 默认拷贝构造：data(other.data) —— 两个对象指向同一块内存！
};
struct Deep {
    int* data;
    Deep(int v) : data(new int(v)) {}
    Deep(const Deep& other) : data(new int(*other.data)) {}  // 深拷贝：新分配 + 复制数据
    ~Deep() { delete data; }
};
```
> [!Info] 可能的追问:
> - Q: C++ 中通过什么机制实现拷贝控制？
> - A: 三/五法则（Rule of Three/Five）——如果类需要自定义析构函数、拷贝构造、拷贝赋值中的任何一个，通常三个都需要。C++11 增加移动构造和移动赋值。五个函数的声明/删除控制拷贝行为。
> - Q: 移动语义是深拷贝还是浅拷贝？
> - A: 都不是。移动语义是"偷"资源——将源对象的指针直接转移给目标对象，然后将源对象的指针置空。它避免了深拷贝的分配开销，也避免了浅拷贝的 double free 问题。可以理解为"所有权转移"。

### 函数重载的原理与判断方式
**回答话术：**
函数重载是指在同一个作用域内，多个函数同名但参数列表不同（参数个数、类型、顺序至少有一项不同）。
实现原理：C++ 编译器在编译时对函数名进行[[C++ Runoob Tutoral#概念与用法#Name Mangling|名字修饰（name mangling）]]，将函数名和参数类型编码成一个唯一符号，链接器根据这个符号区分不同重载版本。
判断两个函数是否构成重载：
- 参数列表个数
- 参数列表类型
	- 包括 typeid 返回的类型 id 是否相同
	- 值类型，即是否引用类型两种
- 参数列表顺序
- 如果函数是成员函数还要看函数体是否为 const ，noexcept 声明不影响重载决议，但会影响 name mangling
- 不仅函数可以重载，还可以重载操作符
**不看返回值**——仅返回值不同
> [!Info] 可能的追问:
> - Q: 重载解析时，如果多个重载版本都能匹配，怎么选？
> - A: 编译器按优先级从高到低选择：
> 	1. 精确匹配（类型完全一致或数组到指针/函数到指针）
> 	2. 提升匹配（如 float→double）
> 	3. 标准转换（如 int→double）4) 用户定义转换。如果多个候选在同一级，则二义性报错。
> - Q: extern "C" 对重载有影响吗？
> - A: 有。extern "C" 告诉编译器按 C 的方式编译，不进行 name mangling，因此 extern "C" 块中的函数不能重载（C 不支持重载）。

### C++ 中多态的种类及实现方式
**回答话术：**
C++ 中有**静态多态（编译期多态）** 和**动态多态（运行期多态）** 两种。
1. **动态多态**：通过继承 + 虚函数实现。基类声明 virtual 函数，派生类 override。运行时通过 vptr → vtbl 间接调用，在运行期确定实际调用的函数版本。优点是灵活（可在运行时决定类型），缺点是一次间接跳转开销 + 无法内联。
**关于 rtti-flag**：动态多态的虚函数分发（vptr → vtbl 查找）**不需要编译器的 rtti-flag**。虚函数的调用机制只依赖于 vptr 和 vtbl，这是编译器的固定特性。rtti-flag（-frtti）只控制 `typeid` 和 `dynamic_cast` 是否能工作——关掉 rtti 后，虚函数机制仍然正常，但 `dynamic_cast` 无法使用，`typeid` 会报错。两者不耦合。
2. **静态多态**：通过**模板**和**函数重载**实现。模板在编译期根据实参类型实例化生成具体代码，编译器可以充分优化（内联展开）。函数重载在编译期根据参数类型选择调用版本。优点是零运行时开销，缺点是需要源码。
```cpp
// 动态多态
class Animal { virtual void speak() = 0; };
class Dog : public Animal { void speak() override { cout << "Woof"; } };
void makeSound(Animal& a) { a.speak(); }  // 运行期决定调用哪个版本
// 静态多态（模板）
template<typename T>
void makeSound(T& a) { a.speak(); }  // 编译期实例化
```
> [!Info] 可能的追问:
> - Q: 模板算多态吗？
> - A: 算。C++ 将模板视为静态多态（static polymorphism）。同一段模板代码对不同类型产生不同行为——只是发生在编译期而非运行期。C++ 标准中多态（polymorphism）的定义是"为不同数据类型提供统一接口"，模板满足这个定义。
> - Q: 动态多态和静态多态怎么选？
> - A: 需要运行时类型灵活性（如插件系统、策略模式）→ 动态多态；追求极致性能（如日志库、容器算法）→ 静态多态。实际项目中经常同时使用两种。

## 操作系统

### 堆和栈在内存中的位置与生长方向
**回答话术：**
在 Linux 虚拟地址空间中，栈位于用户空间顶部（高地址），向下生长（地址递减）；堆位于 BSS 段之后（低地址），向上生长（地址递增）。这种相向生长的设计让栈和堆中间的地址空间可以被两者共享——早期物理内存很小的时候这很实用。现代系统中栈和堆之间有 mmap 区域（映射动态库、大块匿名映射）做缓冲，两者一般不直接碰撞。
**知识点讲解：**
```
  高地址
  ┌────────────────────┐
  │   内核空间           │
  ├────────────────────┤ ← 用户空间顶部
  │   栈                │ ← 从高地址开始，↓ 向下生长
  │   mmap 区域         │ ← 共享库、文件映射，↓ 向下生长
  │   堆                │ ← BSS 段之后，↑ 向上生长
  │   BSS/Data/Text    │
  └────────────────────┘
  低地址
```
栈典型大小：Linux 默认 8MB（ulimit -s 可查看/修改），每个线程独立栈空间。
> [!Info] 可能的追问:
> - Q: 栈的生长方向可以改变吗？
> - A: 理论上可以通过编译器选项（如 -mstack-up）在某些架构上改变，但几乎所有主流架构（x86、ARM、RISC-V）的栈都是向下生长的，改变会破坏标准调用约定（ABI），生产代码不会这么做。
> - Q: 为什么通常说栈向下、堆向上？
> - A: 历史设计。栈从高地址向下增长，函数调用时 push 指令递减栈指针。堆从低地址向上增长，sbrk/mmap 增加堆顶（program break）。相向生长可以在早期小内存系统中最大化可用地址空间的利用率。

### 进程和线程的区别
**回答话术：**
进程是资源分配的基本单位，有独立的地址空间（代码段、数据段、堆栈），进程间相互隔离。线程是 CPU 调度的基本单位，同一进程内的线程共享地址空间和资源，每个线程有独立的栈和寄存器上下文。进程创建开销大（分配独立地址空间、页表），线程创建开销小（共享地址空间）。进程切换代价大（TLB 刷新），线程切换代价小。进程间通信需要 IPC 机制（管道、共享内存、socket），线程间直接读写共享变量。
**知识点讲解：**
```
进程：独立地址空间 ─── 切换需要 TLB 刷新 ─── 健壮（一个崩溃不影响其他）
线程：共享地址空间 ─── 切换不需要 TLB 刷新 ─── 脆弱（一个崩溃整个进程退出）
```
> [!Info] 可能的追问:
> - Q: 协程和线程的区别？
> - A: 协程是用户态调度，切换不涉及系统调用，成本极低（纳秒级）。协程是协作式调度（主动 yield），线程是抢占式调度。一个线程内可运行多个协程。

### 线程间和进程间通信的方式
参考:https://zhuanlan.zhihu.com/p/465574868
**回答话术：**
**线程间同步/通信**：互斥锁（mutex）、条件变量（condition_variable）、信号量（semaphore）、原子操作（atomic）、读写锁（shared_mutex）、线程局部存储（thread_local）。线程共享进程地址空间，可以直接读写共享变量，但需要同步机制防止竞态条件。
**进程间通信（IPC）**：管道（pipe/FIFO）、信号（signal）、消息队列（POSIX/SysV msg queue）、共享内存（shmget/mmap + 信号量同步）、信号量（semaphore）、套接字（Unix domain socket / TCP socket）、文件锁（flock/fcntl），RPC
**选择建议**：大量数据传输用共享内存（零拷贝，最快）；小数据/消息用 Unix 域套接字或管道；同步用信号量；跨机器用 TCP socket。
**知识点讲解：**
```cpp
// 进程共享互斥锁
pthread_mutexattr_t attr;
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);
pthread_mutex_t* mtx = (pthread_mutex_t*)shm_ptr;
pthread_mutex_init(mtx, &attr);
```
> [!Info] 可能的追问:
> - Q: 共享内存为什么需要同步？
> - A: 共享内存本身不提供互斥机制——两个进程可以同时写入同一块内存，导致数据损坏。所以共享内存必须配合信号量或进程共享互斥锁使用，保证同一时刻只有一个进程写入。
> - Q: 线程间通信和进程间通信的核心区别是什么？
> - A: 线程共享地址空间，可以直接读写变量（需要同步）；进程有独立地址空间，数据不能直接共享，需要通过内核通道拷贝或映射。所以 IPC 通常比线程间通信慢。

### 什么情况下使用多线程？如何判断？
**回答话术：**
多线程适用的场景：
1) **IO 密集型**——网络请求、文件读写、数据库操作等，一个线程等待 IO 时 CPU 可以切换到其他线程执行，提高 CPU 利用率 
2) **多核并行计算**——大数组处理、图像渲染、矩阵运算等，将任务切分到多核加速 
3) **高并发服务器**——同时服务大量客户端，每个连接一个线程或从线程池处理 
4) **保持 UI 响应**——后台任务放到工作线程，不阻塞 UI 线程。
**不用多线程的场景**：
5) CPU 密集且任务无法拆分（单线程最有效）
6) 简单的小任务（线程创建切换开销 > 收益）
7) 对延迟极度敏感且不允许锁竞争的场景（用异步 / 协程代替）。
判断公式：加速比 ≈ 1 / (串行比例 + 并行比例/N)，阿姆达尔定律——串行比例决定了理论上限。

### 数据竞态条件（data race）的解决方法
**回答话术：**
竞态条件指多个线程同时访问同一数据，且至少一个是写操作，导致结果取决于线程调度顺序。解决方法从重到轻：
1. **互斥锁（mutex）**：std::lock_guard, std::unique_lock，保护临界区，一次只有一个线程能进入
2. **读写锁（shared_mutex）**：读读不互斥，适合读多写少的场景
3. **原子操作（atomic）**：对整型/指针等简单类型的加减、CAS 操作，无锁化，比 mutex 快（无上下文切换）
4. **线程局部存储（thread_local）**：每个线程持有一份独立拷贝，彻底消除共享
5. **无锁数据结构**：利用 CAS 原子操作实现无锁队列/栈等，性能高但实现复杂
**选择原则**：首先考虑能否消除共享（thread_local），无法消除时数据量小用 atomic，临界区大用 mutex。

### 如何发现和解决死锁？
**回答话术：**
**发现死锁的方法**：
1. **gdb attach**：`thread apply all bt` 查看所有线程的调用栈，如果多个线程停在 lock 相关的调用上（如 __lll_lock_wait），很可能就是死锁
2. **ThreadSanitizer**：编译时加 `-fsanitize=thread`，运行时检测并报告死锁位置（也会报告 data race）
3. **helgrind**（Valgrind 工具）：检测 POSIX pthread 死锁
4. **日志分析**：在加锁/解锁前后打印日志，分析锁获取顺序
**解决死锁的方法**：
1. **固定锁顺序**——所有线程按相同顺序获取锁。例如线程 A 先锁 m1 再锁 m2，线程 B 也先锁 m1 再锁 m2，就不会出现"A 持 m1 等 m2，B 持 m2 等 m1"的循环等待。这是最常用也最简单的预防方法，缺点是如果锁很多（比如 10 个），需要所有开发者记住统一顺序
2. **std::lock 一次性锁多个**——C++11 的 std::lock(m1, m2) 内部用死锁避免算法（类似 try_lock 回退）保证不会死锁，配合 adopt_lock 的 lock_guard 使用
3. **分层锁（层级锁）**——给每个锁分配一个层级编号，规定**只能按编号递增的顺序获取锁**（先拿编号小的，再拿编号大的）。违反规则（先拿大号再拿小号）时断言失败。例：m1（层级 1）、m2（层级 2），A 线程先锁 m1 再锁 m2 合法；B 线程也想锁 m1 再锁 m2，不会产生环。如果某处写成了先锁 m2 再锁 m1，运行时触发断言直接暴露问题。优点是死锁在开发期就被捕获
4. **try_lock 超时回退**——获取失败时释放已持有的锁，重试
5. **减少锁粒度**——降低锁冲突概率

**知识点讲解：固定锁顺序 vs 分层锁的区别**：固定锁顺序要求所有线程用完全相同的顺序获取锁；分层锁只要求按编号递增，不要求所有线程获取完全相同的锁集合。分层锁更灵活——锁 1、锁 2、锁 3，既可以锁 1→2，也可以锁 2→3，但不能锁 3→2。固定锁顺序是"所有人都先拿 1 再拿 2 再拿 3"，分层锁是"按编号从小到大拿"。

### 原子类型（atomic）的理解
**回答话术：**
原子类型（std::atomic）是 C++11 提供的一种无锁线程安全机制。对原子变量的操作（读、写、CAS）在硬件层面保证不被其他线程中断——在 x86 上通过 `lock` 前缀指令锁住缓存行或总线实现。相比于 mutex，atomic 没有上下文切换和系统调用开销，适合保护简单类型（int、bool、指针等）的读写。原子操作还支持指定**内存序**（memory_order），控制操作前后的可见性约束，在无锁编程中非常关键。

**什么是内存序（memory order）？**
内存序解决的是"多核 CPU 下，其他线程看到这个原子操作的副作用（内存读写）的顺序是什么"的问题。现代 CPU 会为了性能重排指令（out-of-order execution），如果没有内存序约束，一个线程写入变量的顺序在其他线程看来可能不一样。以 `counter.store(1, relaxed)` 为例——虽然 store 本身是原子的，但 CPU 可能把 store 前后的普通内存操作重排到 store 的另一侧，导致其他线程看到"flag 亮了但数据还没就绪"或反之。内存序就是告诉 CPU"这个原子操作前后，内存读写不允许重排到哪一步"。

**知识点讲解：**
```cpp
// 内存序从松到严的四个层次：

// 1. memory_order_relaxed（最松）
// 只保证原子操作本身不被打断。不保证任何顺序——前后的读写可以自由重排
// 只适合简单的计数器累加（如统计次数，不依赖其他变量）
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);  // 只要求不丢计数

// 2. memory_order_acquire（获取语义）
// 之后的读/写操作不能重排到此 atomic load 之前
// 用于"我读到某个值之后，我要读取其他变量"
std::atomic<bool> ready{false};
int data = 0;
// 线程 A：
data = 42;                    // 普通写
ready.store(true, std::memory_order_release);  // release — 确保 data=42 先完成
// 线程 B：
while(!ready.load(std::memory_order_acquire)); // acquire — 确保读到的 data 是 42
// 关键：acquire + release 配对使用，保证线程 A 中 release 之前的写对线程 B acquire 之后的读可见

// 3. memory_order_release（释放语义）
// 之前的所有写操作不能重排到此 atomic store 之后
// 用于"我写入这个值之前，其他变量的写已经完成"

// 4. memory_order_seq_cst（最严，default）
// 全局顺序一致——所有线程看到的所有 atomic 操作顺序一致
// 最直观也最慢（CPU 需要额外的内存屏障指令）
std::atomic<int> x{0}, y{0};
// 所有线程看到的 x, y 修改顺序完全一致
```
**acquire + release 的核心价值**：相当于轻量级的"我写完了，你可以读了"——release 保证前面的写都完成，acquire 保证后面的读能看到那些写。这是无锁编程中最常用的内存序配对，比 seq_cst 快但功能也能满足大多数需求。
> [!Info] 可能的追问:
> - Q: atomic 比 mutex 快多少？
> - A: 原子操作通常几十纳秒（无锁，bus lock 或 cache lock），mutex 加解锁至少几百纳秒到几微秒（涉及系统调用、线程切换）。短临界区用 atomic，长临界区或复杂操作仍用 mutex。atomic 不能保护复杂的临界区（如多步操作），CAS 循环可以实现简单的无锁数据结构。
> - Q: 既然 atomic 比 mutex 快，为什么不全部用 atomic 代替 mutex？
> - A: 不能替换的三个原因：1) **适用场景不同**——atomic 只能保护单个变量的简单操作（读、写、CAS），无法保护多个变量的同步操作。例如"先检查账户余额 > 100，再扣款 100"这个两步操作，atomic 无法保证两步之间不被其他线程打断，必须用 mutex 包裹整个临界区。2) **CAS 循环的自旋开销**——用 atomic 实现复杂逻辑需要 CAS 循环（compare_exchange_weak），竞争激烈时大量自旋浪费 CPU。mutex 在竞争时让线程休眠，不占 CPU。3) **内存序复杂**——正确使用 atomic 的内存序（memory_order）非常容易出错，比用 mutex 的 lock_guard 难得多。总结原则：保护单个简单变量用 atomic，保护代码段（多步操作/多个变量）用 mutex。

### 自旋锁、互斥锁和读写锁的实现原理与对比
**回答话术：**
**自旋锁（SpinLock）**：利用 CPU 原子指令（如 test_and_set）在循环中检查锁变量，成功则进入，否则继续循环等待。不进入内核睡眠，线程一直占用 CPU 自旋检查。实现依赖 std::atomic_flag 或 CAS。**适合锁持有时间极短的场景**（微秒级），避免线程切换开销。
```cpp
class SpinLock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT;  // C++17: atomic_flag 保证无锁
public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire))
            _mm_pause();  // 自旋等待，提示 CPU 优化流水线
    }
    void unlock() { flag.clear(std::memory_order_release); }
};
```
**互斥锁（Mutex）**：用户态用 CAS 快速尝试获取锁（fast path），获取失败则通过**系统调用**（futex）让线程进入睡眠等待，锁释放时内核唤醒等待线程。**适合锁持有时间较长**（毫秒级）或可能阻塞的场景，不浪费 CPU。以 Linux 的 pthread_mutex 为例：优先尝试用户态 CAS 获取锁；如果失败调用 futex(FUTEX_WAIT) 进入内核睡眠；解锁时调用 futex(FUTEX_WAKE) 唤醒等待线程。
**读写锁（shared_mutex / RWLock）**：允许多个线程同时读（共享），但写操作独占（排他）。内部维护三个状态：当前持有读锁的线程数、是否有写锁、等待写锁的线程数。**适合读多写少场景**（如配置文件读取、路由表查找）。
```cpp
std::shared_mutex rwlock;
// 读线程：多个线程可以同时加读锁
rwlock.lock_shared();   // 如果没有写锁则成功，否则等待
// 读共享数据
rwlock.unlock_shared();
// 写线程：必须独占
rwlock.lock();          // 等待所有读锁释放后才获取
// 写数据（独占）
rwlock.unlock();
```
**三者的对比**：

| | 自旋锁 | 互斥锁 | 读写锁 |
|--|--------|--------|--------|
| 等待方式 | 自旋（CPU 忙等） | 线程睡眠（futex） | 读-自旋/睡眠混合，写-独占 |
| 适用场景 | 锁持有时间极短（微秒） | 锁持有时间较长（毫秒） | 读多写少 |
| CPU 消耗 | 高（自旋时占满核心） | 低（睡眠时不占 CPU） | 读多时低 |
| 实现基础 | atomic_flag / CAS | futex（系统调用） | atomic + futex |
| 优缺点 | 无上下文切换，但浪费 CPU | 省 CPU，但有切换开销 | 读并发高，写性能差（写饥饿） |

**选择建议**：锁持有微秒级且不阻塞 → 自旋锁；锁持有毫秒级或可能 IO 阻塞 → 互斥锁；读远多于写 → 读写锁。
> [!Info] 可能的追问:
> - Q: _mm_pause() 在自旋锁中有什么用？
> - A: 提示 CPU 当前正在自旋等待（spin-wait loop）。CPU 可以对流水线进行优化（减少内存顺序违规的惩罚），并且在一些 CPU（如 Intel HT）上避免资源冲突。如果不加 pause，自旋时功耗更高且可能降低其他线程的执行速度。相当于一个"轻量级 CPU yield"。
> - Q: 自旋锁会有什么问题？
> - A: 1) **优先级反转**——如果低优先级线程持有锁被抢占，高优先级线程自旋等锁，低优先级得不到 CPU 无法释放锁；2) **单核 CPU 上死锁**——自旋锁的等待线程不会切换，持有锁的线程可能得不到执行；3) **功耗**——自旋时 CPU 满负载运行浪费电能。所以锁持有时间必须极短，且不用在单核上。

## Git 版本控制

### Git 的三个区与基本命令
**回答话术：**
Git 的三个区：工作区（Working Directory）→ 暂存区（Staging Area/Index）→ 仓库（Repository/History）。工作区是修改文件的地方，暂存区是 git add 后的中间区域，仓库是 git commit 后的提交历史。
- **git pull = git fetch + git merge**：从远程拉取并合并。工作区有未提交/未暂存的内容时，git pull 可能导致 merge 冲突
- **git fetch**：只拉取远程更新到本地仓库，不会自动合并到工作区，更安全
- **git stash**：临时保存工作区的修改，恢复干净的工作区。stash 是跨分支的——切换到其他分支后也可以 pop
**知识点讲解：**
```bash
# 场景：正在开发功能 A，突然要修紧急 Bug
git stash push -m "feature A WIP"  # 保存当前改动
# 切换到其他分支修 Bug
git checkout -b hotfix
# 修复完 Bug 后切回原分支
git checkout feature-a
git stash pop  # 恢复保存的工作区
```
> [!Info] 可能的追问:
> - Q: git stash pop 时发生冲突如何解决？
> - A: Git 会提示冲突文件，手动编辑解决冲突 → git add 标记已解决 → git stash drop 清除 stash 记录。pop 会自动应用并删除 stash 记录，如果冲突发生则不会自动删除，需要手动 drop。
> - Q: 多次 stash 只想恢复某一次怎么做？
> - A: git stash list 查看 stash 列表（stash@{0}, stash@{1}...），git stash apply stash@{n} 应用指定版本（不删除记录）或 git stash pop stash@{n}（应用并删除）。

### 多人协作与分支策略
**回答话术：**
常用分支策略：main（主分支，保护分支）→ develop（开发分支）→ feature/xxx（功能分支，从 develop 切出，合并回 develop）。修复紧急 Bug 从 main 切 hotfix/xxx。多人协作流程：
1. 从 develop 创建自己的 feature 分支
2. 开发完成后发起 Pull Request（PR）/ Merge Request
3. 同事 Code Review，反馈修改意见或直接 approve
4. CI/CD 在 PR 阶段自动运行（编译 + 测试 + 代码规范检查）
5. 通过后合并到 develop，定期合并到 main 发布
**知识点讲解：**
```bash
# 典型 CI/CD 流程配置
# 1. 提交/PR 触发 CI
# 2. 编译：cmake --build build
# 3. 测试：ctest --output-on-failure
# 4. 代码格式化：clang-format -i src/*.cpp && git diff --exit-code
# 5. 全部通过后合并
```
> [!Info] 可能的追问:
> - Q: Code Review 发现问题会怎样？
> - A: Review 者在 PR 上留评论标记需要修改的行。开发者修改后 push 新 commit，CI 自动重新运行。通过后重新请求 review。GitHub 可以设置"需要 review 才能合并"的保护规则。
> - Q: Issues、PR、Fork 分别怎么用？
> - A: Issues 用于追踪 Bug 和需求；Fork 是复制上游仓库到自己的命名空间（常见于开源贡献）；PR 是从自己的分支/fork 向原始仓库请求合并更改。企业协作通常不用 Fork，直接在同一仓库创建分支。

### git stash 恢复时的冲突处理
**回答话术：**
git stash pop 时发生冲突的原因是恢复的工作区修改与当前分支的某些文件有冲突（比如修 Bug 时改了同一个文件）。解决步骤：
1. Git 标记冲突文件，不会自动合并
2. 手动编辑文件解决冲突
3. git add 标记已解决
4. stash 记录不会被 pop 自动删除（pop 在无冲突时才自动 drop），需要手动 git stash drop
**知识点讲解：**
```bash
git stash pop
# 出现冲突 >>>
# 手动编辑文件解决冲突后：
git add <resolved_file>
git stash drop  # 手动删除 stash 记录
# 注意：stash 内容是跨 branch 的！在 branch-A stash，切到 branch-B 也可以 pop
```
> [!Info] 可能的追问:
> - Q: 工作区有未提交内容时使用 git pull 会怎样？
> - A: 如果本地未提交的文件与远程 pull 下来的文件没有冲突，Git 会保留本地修改成功合并。如果有冲突，Git 不会覆盖你的工作区，而是报错，需要先 git stash 暂存，pull 成功后再 stash pop 恢复。git fetch 比 pull 安全——它只下载不合并，给你手动处理的空间。

## 计算机网络
### 大文件传输的实现与断网处理
**回答话术：**
大文件传输的核心思路是**分片传输 + 断点续传**。客户端将文件切分成固定大小的分片（如 1MB/片），每个分片携带序号和校验和，逐片发送。服务端接收后写入磁盘对应位置，用位图（bitmap）记录哪些分片已到达。
断网处理：客户端记录已发送的分片序号，重连后从最后一个成功 ACK 的分片继续发送（不重新传输已确认的分片）。服务端检测到连接断开后，保存当前的位图状态到磁盘（类似下载软件的 .part 文件），等客户端重连后恢复。关键是分片序号 + ACK 确认 + 状态持久化。

流程是这样的:
1. 发送大文件之前，发送端先检测大文件的总大小，切片数量，切片长度等内容给接收端
2. 接收端接受这些前置信息后进入准备接收阶段，并创建 bitmap 记录文件接受情况，开辟对应大小空间用于存放文件
3. 发送端对大文件切片后，为每一份切片编号并发送（可以是同步也可以是并发异步发送），并给出每一个分片的校验和，放在一个队列中，通过一个线程发送出去
4. 接收端这些分片并在接收时核对校验和，根据分片的序号把文件数据放在对应的磁盘空间中，如果这里出现问题就请求单个分片重传（由另一个线程发送请求），同样**发送端的另一个线程监听到重传请求**就将需要重传的切片放入到发送线程队列中
5. 发送完成后，接收端根据编号将文件数据组成一个整体大文件，接受完成
6. 如果发送端断网切断了发送，接收端进入超时处理等待环节，记录下当前 bitmap 中的切片接受情况（持久化）等待下一次发送时重新接受
**知识点讲解：**
```cpp
struct FileChunk {
    uint32_t file_id;       // 文件唯一 ID
    uint32_t chunk_index;   // 分片序号
    uint32_t total_chunks;  // 总分片数
    uint32_t size;          // 本片实际大小
    uint32_t checksum;      // 校验和（CRC32）
    char     data[MAX_CHUNK_SIZE];
};
// 服务端维护一个 bitset<bool> received(total_chunks)
// 收到分片后：received[chunk_index] = true，写入文件对应 offset
// 断网重启后客户端发送 resume_request{file_id}，服务端回复位图
// 客户端从第一个未接收的分片继续发送
```
> [!Info] 可能的追问:
> - Q: TCP 已经保证了可靠传输，为什么还需要应用层做分片？
> - A: TCP 保证单次连接的可靠性但不保证断开后恢复（断点续传）。应用层分片可以实现：1) 断点续传——重连后只传缺失的分片 2) 并行传输——多连接同时传不同分片提高吞吐 3) 进度展示——知道传了多少百分比。
> - Q: 校验和 checksum 的作用是什么？
> - A: TCP 虽然提供校验和，但 TCP 校验和较弱（16 位补码和），且数据在应用层处理前可能被破坏（如操作系统 bug、硬件错误）。应用层用更强的 CRC32 或 SHA256 校验数据完整性，发现损坏的分片请求重传。
> - Q: 为什么不能直接通过 TCP 传输将整个大文件放入一次 TCP 传输中？TCP 不也是可靠传输吗？
> - A: 技术上可以（一次 send 发完整文件），但实际不会这么做。原因：1) 内存——一次加载整个大文件到内存，如果文件有几十 GB 会耗尽内存。分片后可以边读边发，内存占用固定为片大小；2) 断点续传——TCP 断了必须从头重传，没有分片就无法"只传缺失的部分"；3) 进度——没有分片就没有进度概念，无法知道传了多少；4) 并发——分片可以多连接同时传不同部分提高吞吐，单连接 TCP 的拥塞控制限制了单个流的带宽。所以即使 TCP 可靠，应用层分片仍然必要。大文件传输的最佳实践是用你描述的双线程模型（发送线程 + 重传监听线程），加上接收端位图持久化和超时等待。

### 消息传输丢失后的重传机制
**回答话术：**
消息重传的核心是**超时重传 + 确认应答 + 序列号**。发送方发送消息时附带唯一序列号（seq），启动定时器。接收方收到后回复 ACK（ack = seq + 1）。发送方如果在超时时间内没收到 ACK，重新发送该消息。接收方根据序列号去重——收到重复的 seq 直接丢弃但回复 ACK（防止发送方一直重传）。
在即时通讯场景中，常用的重传策略是**指数退避**（第一次 1s，第二次 2s，第三次 4s... 最大 30s），避免大量重传导致网络拥塞。客户端也应该维护一个"待确认消息队列"，收到 ACK 才移除，断线重连后重新发送所有未确认消息。
**知识点讲解：**
```
发送方                          接收方
  │─── [seq=1] Message ──────→  │ （收到，记录 seq=1）
  │                             │─── ACK(ack=2) → 发送方移除消息
  │─── [seq=2] Message ──────→  │ （丢包了）
  │  ╰─ 定时器超时，未收到 ACK   │
  │─── [seq=2] Message ──────→  │ （重传，收到后去重）
  │                             │─── ACK(ack=3)
```
> [!Info] 可能的追问:
> - Q: 如果 ACK 本身丢失了怎么办？
> - A: 发送方超时重传原始消息，接收方发现 seq 已收到过，说明是重复传输，回复 ACK 但不处理消息体。这保证了"至少一次"（at-least-once）投递，需要业务层做幂等处理确保重复消息不影响状态。
> - Q: 重传策略如何选择？
> - A: 1) 即时通讯用指数退避（省带宽）；2) 实时游戏用固定短间隔（低延迟优先）；3) 文件传输用选择性重传（只重传丢失的分片，不重传已到的）。

### 文本/文件的哈希值计算
**回答话术：**
哈希函数将任意长度的数据映射为固定长度的摘要值。计算文件哈希值使用哈希算法（如 MD5、SHA-256）。对于超大文件，**不会将整个文件加载到内存后计算**——哈希算法支持分块增量计算。以 SHA-256 为例，可以每次读 4KB/8KB 块，调用 `update()` 更新上下文，最后 `digest()` 输出最终哈希值。这样内存占用固定为块大小（几 KB），和时间复杂度 O(n) 线性处理完整文件。
**知识点讲解：**
```cpp
// 增量式哈希计算（OpenSSL / C++ 实现均支持）
SHA256_CTX ctx;
SHA256_Init(&ctx);
char buf[8192];
while (size_t n = fread(buf, 1, sizeof(buf), fp)) {
    SHA256_Update(&ctx, buf, n);  // 增量更新，不要求一次性全读入
}
unsigned char hash[SHA256_DIGEST_LENGTH];
SHA256_Final(hash, &ctx);  // 输出最终哈希
// C++ 标准库方式（C++26 之前无内置，可用 crypto++、openssl 或系统 API）
```
> [!Info] 可能的追问:
> - Q: MD5 和 SHA-256 选哪个？
> - A: 安全性要求高选 SHA-256（抗碰撞更强），MD5 已被证明可碰撞（2004 年王小云团队），不再安全。MD5 快但安全性不足。完整性校验场景（非安全敏感）可以用 MD5，生产环境至少用 SHA-256。文件分片的校验和常用 CRC32（更快但更弱，只适合检测传输错误）。
> - Q: 分片计算哈希和整体计算哈希结果是否一致？
> - A: 分片计算结果是每片的哈希，不是整体文件的哈希。如果需要得到整体文件哈希，有两种方式：1) 增量式 update（最终 digest 等效于整体计算）2) 先计算每个分片的哈希，再将这些哈希拼接后再次哈希（Merkle tree 方式），这种方式还支持单独校验任一分片是否被篡改（BT 下载和 Git 都使用 Merkle tree）。

## 系统设计
### 群消息广播的低负载设计
**回答话术：**
核心思路是**服务端扇出 + 消息存储 + 增量拉取**，避免逐个推送导致服务器阻塞。
1. **服务端扇出**：群成员列表存在 Redis 的 Set 中，消息只需写入一次（存到消息队列），然后遍历成员列表，将消息 ID 写入每个成员的"收件箱"（inbox list）。注意这里的"写入收件箱"只是写入一个已读/未读指针（消息引用），而不是复制消息本体。
2. **消息存储与拉取**：消息本体存一次（DB 或 Redis），成员从自己的 inbox 中获取消息 ID 后去拉取消息体。这样无论群多大，消息体只存一份。
3. **避免阻塞**：写入 inbox 用异步 + 批量写入（攒一批一起写 Redis/DB）。如果群人数上万，可以分片（将群成员分成多个批次，逐批写入，每批之间 sleep 几毫秒）。
4. **推拉结合**：在线用户推送（通知有新消息），离线用户上线后拉取。用长轮询或 WebSocket 保持在线状态。
**知识点讲解：**
```
用户A发消息 "hello" 到 1000人群
  ↓
消息体存入消息表（msg_id = 12345, group_id = G, content = "hello"）
  ↓
从 Redis 获取群 G 的成员列表（SISMEMBER）
  ↓
异步批量操作：给每个用户的 inbox 追加 msg_id（SADD user_inbox:{uid} 12345）
  ↓
在线用户通过 WebSocket 实时推送通知"你有新消息"
  ↓
用户拉取：从自己的 inbox 获取最新的 msg_id，从消息表获取消息体
```
> [!Info] 可能的追问:
> - Q: 如果群里有 10 万人，写入 inbox 会变成瓶颈吗？
> - A: 会。优化方案：1) 不做纯 push（写入所有 inbox），改为 pull 模式——消息只存群的消息列表，用户上线时拉取"自己上次拉取时间之后的新消息索引"；2) 小群（<500 人）用 push，大群用 pull；3) 分层——只给在线用户 push，离线用户上线后 pull。微信的做法就是大群（500 人群）的群消息不是全量 push。
> - Q: 如何避免服务器被阻塞？
> - A: 1) 异步处理（I/O 操作放入线程池，不占用事件循环线程）2) 消息队列缓冲（写入 RPM 超出限制时暂存到内存队列，慢慢消费）3) 限流（单个群的发送频率限制，超出的排队等待）。

### 聊天软件消息缓存的准确性与送达保证
**回答话术：**
保证消息可靠投递需要多级确认和重传机制：
1. **客户端发送流程**：用户点击发送 → 消息存入本地"发送中"队列（标记为未确认）→ UI 显示"发送中" → 通过 WebSocket/TCP 发送 → 服务端回复 ACK（包含消息 seq）→ 收到 ACK 后标记为"已发送"
2. **服务端确认**：服务端收到消息后，先写入消息库（持久化），再写入收件人 inbox，最后回复 ACK
3. **消息缓存准确性**：客户端维护一个"消息一致性序列号"——每次发消息 seq+1，收消息也有一个连续序号。客户端发现收到的消息 seq 不连续时，主动请求缺失的 seq 段
4. **离线消息**：用户上线时，客户端上报自己最后收到消息的 seq，服务端返回 seq 之后的所有新消息
> [!Info] 可能的追问:
> - Q: 如何保证消息不丢失、不重复？
> - A: 1) 不丢失——客户端发送后持久化到本地 DB，收到 ACK 才删除。2) 不重复——服务端用消息 seq 去重（幂等），相同的 seq 只处理一次。最终消息至少到达一次（at-least-once），业务层自行处理幂等。如果需要 exactly-once，还需要分布式事务，成本很高，IM 场景很少用。

### 多个用户端是否共用一个 Redis/MySQL
**回答话术：**
在即时通讯这类多用户系统中，所有用户端**连接的是同一个 Redis/MySQL 服务**（或集群），不是每个用户独享一个数据库实例。通过连接池复用连接（如你的组件库中的数据库连接池），每个服务进程维护一批连接到 Redis/MySQL，请求到达时从池中取一个连接使用后归还。水平扩展时，在前端加负载均衡器，多个后端服务进程共享同一个 Redis/MySQL 集群——Redis 做主从或 Cluster，MySQL 做主从或分库分表。服务端无状态（用户会话信息存 Redis），任意服务进程都可以处理任意用户的请求。
> [!Info] 可能的追问:
> - Q: 如果所有用户共用一个 Redis，会不会成为瓶颈？
> - A: 会，所以需要 Redis 集群分片（Redis Cluster 将 key 按哈希槽分布到多个节点）。用户会话按 user_id 哈希到不同节点，消息队列按群 ID 哈希，分散压力。Redis 是单线程模型但 I/O 多路复用 + 纯内存操作，单个实例能支撑数万 QPS。

### Redis 的 Pub/Sub 与群发消息方案对比
**回答话术：**
Redis 的 Pub/Sub 是发布-订阅模式：发布者向某个频道（channel）发送消息，Redis 将消息推送给所有订阅该频道的客户端。特点是**实时性强**（消息即时推送），但**不保证消息可靠性**——如果订阅者断开连接，断开期间的消息直接丢失（不持久化）。**PUBLISH 命令向频道发送消息 → Redis 遍历订阅列表逐个推送**。
**与群发消息的低负载方案对比**：
相同点都是一对多推送。不同点：
1) **可靠性**：Redis Pub/Sub 不持久化、不保证送达（客户端离线即丢失）；群发方案将消息持久化到 DB，支持离线拉取和 ACK 确认
2) **ACK 机制**：Pub/Sub 无 ACK，发布者不知道订阅者是否收到；群发方案有 seq+ACK+重传
3) **消息回溯**：Pub/Sub 消息一旦推送即消失，无法回溯；群发方案消息存储在 DB，可以按 seq 拉取历史
4) **消费能力**：Pub/Sub 如果订阅者消费慢，Redis 会积压消息到缓冲区，缓冲区满则丢弃；群发方案用消息队列削峰填谷
**选择**：实时通知（如股价更新、状态推送）用 Pub/Sub；可靠消息（如聊天消息、订单通知）用持久化方案 + ACK + 重传。
> [!Info] 可能的追问:
> - Q: Redis Pub/Sub 适合做 IM 群聊吗？
> - A: 不适合，主要原因：1) 消息不持久化——用户离线就收不到；2) 无 ACK——不知道谁收到了谁没收到；3) 无历史消息回溯——用户上线后看不到之前的聊天记录。Pub/Sub 适合做"实时通知+不关心是否送达"的场景（如 WebSocket 广播在线用户数、股价更新推送）。IM 的核心功能（消息必达、历史回溯、离线消息）Pub/Sub 都无法满足。

## C/C++ 语言基础

### C 和 C++ 有什么区别？
**回答话术：**
C++ 是 C 的超集，主要区别在于：C++ 支持面向对象（封装、继承、多态）、泛型编程（模板）、异常处理、函数重载和运算符重载。C++ 通过 RAII 和智能指针提供更安全的内存管理，还有 STL 标准库。C 是面向过程的语言，更贴近硬件，执行效率在某些场景略高，但大型项目开发效率较低。
**知识点讲解：**
- C++ 在 C 基础上增加了：class、虚函数、模板、异常、namespace、引用、new/delete、STL 容器和算法
- C 的 struct 只有数据成员；C++ 的 struct/class 可以有成员函数、继承、访问控制
- C 的强制类型转换；C++ 提供 static_cast/dynamic_cast/reinterpret_cast/const_cast
- C++ 的函数重载靠名字修饰（name mangling）实现，C 不支持
> [!Info] 可能的追问:
> - Q: 为什么 C++ 需要 `extern "C"`？
> - A: 因为 C++ 编译时函数名会被 mangling（加入参数类型信息），而 C 不会。加上 `extern "C"` 告诉链接器按 C 的方式查找函数符号，用于 C/C++ 混合编程或调用 C 库。
> - Q: C 和 C++ 的 struct 在内存布局上是否有差异？
> - A: 基本一致，都遵循对齐规则。但 C++ struct 如果有虚函数则包含虚函数表指针，头部多 8 字节（64位）。

### 什么是 extern "C"？它的作用是什么？
**回答话术：**
`extern "C"` 是 C++ 中的链接指示符，告诉编译器将大括号内的函数按 C 语言的方式编译和链接——不进行函数名修饰（name mangling）。它的核心作用是实现 C++ 和 C 代码的混合编程。
**使用场景**：
1. **C++ 中调用 C 库**：C 标准库（如 math.h）和第三方 C 库的头文件需要用 `extern "C"` 包裹
2. **提供 C 接口给 C 调用方**：用 `extern "C"` 导出的函数可以被 C 程序链接
3. **动态库接口**：很多动态库用 `extern "C"` 导出接口函数，确保各种语言（C、Python、Go）都能通过 C ABI 调用
```cpp
#ifdef __cplusplus
extern "C" {
#endif
    void c_function(int x);  // 按 C 方式编译，函数名就是 "c_function"
#ifdef __cplusplus
}
#endif
```
**底层原理**：C++ 支持函数重载，编译器会将函数名和参数类型编码成一个独特符号（name mangling）。例如 `void foo(int)` 可能变成 `_Z3fooi`。但 C 不支持重载，函数名就是原样。如果不加 `extern "C"`，C++ 链接器会找 mangled 后的名字（如 `_Z3c_functioni`），但 C 库中只有 `c_function` 这个符号，导致链接失败。
> [!Info] 可能的追问:
> - Q: 一个函数同时被 C 和 C++ 调用，怎么声明？
> - A: 在头文件中用 `__cplusplus` 宏判断：C++ 环境用 extern "C" 包裹，C 环境直接暴露。标准库头文件（如 `<cstdio>`）就这样做的。
> - Q: extern "C" 对函数体也有影响吗？
> - A: 主要影响链接（name mangling）。函数体中的 C++ 特性（模板、异常、重载）仍然可以使用，但函数本身不能重载（C 不允许同名函数）。实际极少在 extern "C" 块内写函数体，通常是声明，实现在 .c 文件中。

### static 关键字的作用
**回答话术：**
static 在不同语境有不同含义：
1. **局部静态变量**：保持变量值在函数调用间持续存在，只初始化一次，生命周期为整个程序
2. **全局静态变量/函数**：限制作用域在当前文件（内部链接），其他文件不可见，现这一已被匿名命名空间替代
3. **类静态成员变量**：所有对象共享同一份，需要**在类外单独定义**，并且其值可以作为成员函数的默认值，而普通成员不可以。因为静态变量的值和函数参数的默认值（一般的编译器的实现将其看作常量）在**编译期就能确定**，而类成员的值是属于对象的，需要在**构造时确定**。
4. **类静态成员函数**：属于类而非对象，没有 this 指针，只能访问静态成员
**知识点讲解：**
```cpp
void func() {
    static int count = 0;  // 只初始化一次，多次调用累加
    count++;
}
class MyClass {
    static int s_val;       // 声明
    static void s_func() {} // 没有 this 指针
};
int MyClass::s_val = 0;     // 定义
```
> [!Info] 可能的追问:
> - Q: static 局部变量是线程安全的吗？
> - A: C++11 起，static 局部变量的初始化是线程安全的（编译器会加锁保证只初始化一次），但后续修改仍需同步。
> - Q: static 成员函数为什么不能是 const 或 virtual？
> - A: const 限制修改 this 所指对象，但 static 函数没有 this；virtual 依赖对象的虚函数表，static 属于类不参与多态。
### const 关键字理解
**回答话术：**
const 在不同语境下有不同含义，核心作用是"承诺不修改"：
1. **修饰变量**：`const int a = 10;` — a 不可修改，编译期检查
2. **修饰指针**：有两种形式——`const int* p`（指向内容不可改，指针本身可改，称常量指针）和 `int* const p`（指针本身不可改，指向内容可改，称指针常量）
3. **修饰引用**：`const int& ref = a;` — 引用绑定对象不可通过此引用修改，常用于函数参数避免拷贝同时防止修改
4. **修饰成员函数**：`void func() const;` — 承诺不修改 this 所指对象的非 mutable 成员，const 对象只能调用 const 成员函数
5. **修饰成员变量**：`const int member;` — 必须在初始化列表初始化，对象生命周期内不可修改
### const 和 volatile 关键字的区别
**回答话术：**
- **const**：声明变量不可修改，编译期约束。指针场景有 `const int*`（指向内容不可改）和 int* const（指针本身不可改）
- **volatile**：告诉编译器该变量可能被意外修改（如硬件寄存器、多线程共享变量），对象的值可能在程序的控制或检测之外被改变时，禁止编译器对其读取做优化（每次从内存读，不从寄存器缓存读）
**知识点讲解：**
```cpp
const int a = 10;     // a 不可修改
const int* p = &a;    // *p 不可改，p 可改
int* const q = &a;    // q 不可改，*q 可改（但 a 本身是 const 会有 warning）

volatile int flag;    // 每次从内存读，多用于中断或信号处理
while (flag);         // 如果 flag 不是 volatile，编译器可能优化成死循环
```
> [!Info] 可能的追问:
> - Q: const_cast 的作用和风险？
> - A: 去掉 const 属性。如果原对象本身就是 const，修改它是未定义行为。
> - Q: volatile 能保证多线程安全吗？
> - A: 不能。volatile 只防止编译器优化，不保证内存可见性（不插入内存屏障）。多线程同步应使用 mutex 或 atomic。

### 什么是 ABI？它定义了哪些内容？
**回答话术：**
ABI（Application Binary Interface，应用二进制接口）是定义**二进制级别**兼容性的规范，与 API（源代码级别）不同。它定义了函数调用约定（参数如何传递、返回值如何返回）、数据结构的内存布局（成员对齐规则、虚函数表布局）、名称修饰规则（name mangling）、异常处理机制、C++ 的 RTTI 布局等。ABI 不一致的代码（如用不同编译器或相同编译器不同版本编译的目标文件）链接在一起会导致运行时崩溃——这就是为什么 Windows 上不同版本的 MSVC 编译的 DLL 不能混用。
**知识点讲解：**
```
API 层面：函数签名不变即可兼容（源代码兼容）
ABI 层面：调用约定、成员布局、虚函数表布局一致才能兼容（二进制兼容）
```
> [!Info] 可能的追问:
> - Q: ABI 和 API 的区别是什么？
> - A: API 是代码层面的接口约定（函数名、参数类型），只要不改签名，代码可以编译通过。ABI 是二进制层面的（调用约定、内存布局），即使 API 没变，换了编译器版本可能二进制不兼容。例如 Linux 上用 GCC 编译的 .so，Clang 编的可能也能调用（因为 Linux 标准 C++ ABI 是 Itanium ABI），但 Windows 上 MSVC 不同版本的 Debug/Release 混用可能崩溃。

### 什么是 C++ 的 DMA（动态内存分配）
**回答话术：**
DMA（Dynamic Memory Allocation，动态内存分配）是指程序在运行时（而非编译时）向操作系统申请和使用内存的机制。在 C 中使用 malloc/free，在 C++ 中使用 new/new[] 和 delete/delete[]。核心好处是灵活性——程序不需要预知需要多少内存，可以根据运行时情况动态决定。C++ 的 new 相比 C 的 malloc 多做了两件事：调用构造函数完成对象初始化，以及通过重载 operator new 实现自定义内存管理。
> [!Info] 可能的追问:
> - Q: C++ 中的栈分配和堆分配有什么区别？
> - A: 栈分配是自动的（函数调用时分配、返回时释放），速度极快（一条指令改栈指针），大小固定（默认 8MB）。堆分配（malloc/new）需要系统调用或从内存池分配，速度慢，但大小灵活且不受作用域限制。频繁的小对象堆分配是性能瓶颈，所以需要内存池。

### 浮点数加法是否有结合律？
**回答话术：**
`(a+b)+c` 和 `a+(b+c)` 在浮点数运算中**不一定相等**。原因是浮点数在计算机中用有限精度表示（IEEE 754），运算时会发生舍入误差。这就是为什么多线程并行归约浮点数时，不同的聚合顺序可能产生微小的数值差异。
**知识点讲解：**
```cpp
float a = 1e10f, b = -1e10f, c = 1.0f;
float r1 = (a + b) + c;  // 0.0 + 1.0 = 1.0
float r2 = a + (b + c);  // 1e10 + (-1e10 + 1.0) → -1e10+1.0 因精度舍为 -1e10 → 0.0
// r1 != r2
```
> [!Info] 可能的追问:
> - Q: 整数加法有结合律吗？
> - A: 整数加法在无溢出时是精确的，有结合律。但整数乘法在 64 位溢出时也会违反结合律。浮点数由于舍入，是数学上不满足结合律的典型例子。

### 编码格式与乱码问题
**回答话术：**
常见编码：ASCII（单字节，仅英文）、GBK（中文 2 字节）、UTF-8（变长，英文 1 字节，中文 3 字节）、UTF-16（2 或 4 字节）。乱码的原因是编码不匹配——文本用 A 编码写入，用 B 编码读取时解码规则不对应，显示为乱码。
**std::string 和 QString 的编码**：
- `std::string`：**无编码概念**，只是一个 char 字节数组。存储什么编码完全由写入者决定（可以是 UTF-8、GBK 甚至二进制数据）
- `QString`：内部使用 UTF-16 存储（QChar 是 2 字节），与编码无关，输入输出时 QTextCodec 负责转换
**char 存储中文**：char 类型是单字节（8 位），无法直接存储一个中文字符（UTF-8 需要 3 字节，GBK 需要 2 字节）。使用 `char s[] = "你好世界"` 时，数组每个元素是编码后的一个字节。用数组下标访问会得到一个字节（不是完整字符）。用 `sizeof(s)` 可得到总字节数（UTF-8 下大约 15 字节，含结尾 null）。
**指定项目全局编码**：C++ 源代码的编码由**编译器选项**控制——MSVC 用 `/utf-8`，GCC/Clang 用 `-finput-charset=utf-8`。另外在现代 C++ 中用 `u8"你好"` 前缀显式指定 UTF-8 字面量。CMake 中可统一设置 `add_compile_options(-finput-charset=utf-8 -fexec-charset=utf-8)`。
**知识点讲解：**
```cpp
char s[] = "你好世界";
// sizeof(s) 取决于编码：UTF-8 下每个汉字 3 字节，约 13 字节（含 null）
// s[0] 是第一个字节，s[1] 是第二个字节，都不是完整字符
// 乱码示例：用 GBK 编码写入，用 UTF-8 读取 → 显示乱码
```
> [!Info] 可能的追问:
> - Q: 如何分辨乱码类型？
> - A: 
> 	- 锟斤拷之类的高频重复杂乱码→ 是 GBK 被当 UTF-8 读。
> 	- 纯英文正常但中文为 � → 是 UTF-8 被识别成 GBK 少字节解码。
> 	- 濡傛灉这类能看出规律的乱码 → 通常是 UTF-8 被当成 GBK 读取。
> 	- 用 Notepad++ 或 VS Code 的"重新打开编码"功能可以快速验证。
> - Q: C++20 的 char8_t 有什么用？
> - A: C++20 引入 char8_t 专门表示 UTF-8 编码单元，防止 `u8"字符串"` 和普通 char 的过载歧义。`char8_t*` 不能隐式转换为 `char*`，编译器保证编码一致性。

### 含虚函数的类 sizeof 与继承类 sizeof
**回答话术：**
含有虚函数的类，sizeof 除了包含所有成员变量的内存外，还会包含一个隐藏的**虚函数表指针（vptr）**（64 位下 8 字节）。子类即使没有添加任何新成员，**也会继承基类的 vptr**，所以 sizeof 和基类一致。但如果子类有自己额外的虚函数，vptr 不会变大（所有虚函数共用同一个 vtbl），但会新增成员变量的空间。简单归纳：空类 sizeof=1；有虚函数的空类 sizeof=8（vptr 占 8 字节，64 位）；有虚函数的类的子类（未加成员）sizeof=基类大小。
**知识点讲解：**
```cpp
class Base              { virtual void f(); };              // sizeof=8（vptr）
class Empty             {};                                  // sizeof=1
class Derived : Base    { void f() override; };              // sizeof=8，同 Base
class Derived2 : Base   { void f() override; int x; };       // sizeof=16（vptr+int+padding）
```
> [!Info] 可能的追问:
> - Q: 空类大小为什么是 1 而不是 0？
> - A: C++ 标准要求所有对象必须有唯一地址。如果 sizeof 为 0，数组和指针等操作会出问题（如 `Empty arr[10]` 的每个元素地址不能相同）。所以编译器插入一个字节占位。

### 变长数组（FAM）结构体的 sizeof
**回答话术：**
FAM（Flexible Array Member，柔性数组成员）是 C99 引入的特性——结构体的最后一个成员是一个未指定大小的数组，如 `struct Flex { int len; char data[]; };`。sizeof 只计算除了柔性数组之外的部分（即 int 的大小，对齐后通常为 4 字节），不计算 data 的大小。因为 data[] 的地址紧跟在定长成员后面，编译器在结构体末尾直接偏移。访问方式：`Flex* p = malloc(sizeof(Flex) + data_size);`，然后 `p->data[0]` 访问柔性数组元素。C++ 不支持 FAM，但可以用 `std::vector` 或动态分配实现类似效果。
**为什么 sizeof 不计算 FAM 大小**：因为 data[] 大小在编译期未知，由运行时 malloc 决定。编译器只负责定长成员的布局，data 的起始地址就在定长成员末尾 + padding 之后，但末尾没有上限（越界由程序员保证）。注意：FAM 的 data[] 不是指针，它不占用结构体空间，只是一个偏移标记。
> [!Info] 可能的追问:
> - Q: 如果柔性数组改成指针（char* data），结构体大小会变化吗？
> - A: 会。如果写成 `char* data`，它就是一个 8 字节（64位）的指针成员，占用结构体空间。sizeof 会把指针大小算进去。FAM 的 data[] 不是指针，不占空间。用指针就需要额外分配指针指向的缓冲区；FAM 是直接在结构体末尾连续分配，一次 malloc 搞定。

### struct 和 class 的区别
**回答话术：**
C++ 中 struct 和 class 在功能上完全等价，唯一区别是默认访问权限：struct 默认 public，class 默认 private。继承时同理，struct 默认 public 继承，class 默认 private 继承。
**知识点讲解：**
```cpp
struct A { int x; };          // x 默认 public
class B { int x; };           // x 默认 private
struct C : A {};              // public 继承
class D : B {};               // private 继承
```
> [!Info] 可能的追问:
> - Q: C 语言的 struct 和 C++ 的 struct 有什么区别？
> - A: C 的 struct 不能有成员函数、继承、访问控制；C 中定义结构体变量必须加 struct 关键字（除非 typedef）。
> - Q: POD 类型是什么？
> - A: Plain Old Data，与 C 兼容的简单数据结构，没有虚函数、自定义构造/析构、非静态成员的 private/protected 访问等。可使用 `std::is_trivially_copyable_v<T> && std::is_standard_layout_v<T>` 判断

### new 和 malloc 的区别
**回答话术：**
1. new 是 C++ 运算符，malloc 是 C 标准库函数
2. new 自动计算大小并返回正确类型指针，malloc 需手动指定字节数，返回 void*
3. new 分配内存后**调用构造函数**，malloc 只向操作系统的分配器申请原始内存，小内存用brk/sbrk，大块内存使用mmap，这也是mmap 的[[架构设计#mmap 系统调用|三个作用之一]]
4. new 失败抛出 bad_alloc 异常，malloc 失败返回 NULL
5. new 调用 operator new ，其可被重载用来实现自定义内存操作，标准实现中底层调用 malloc，支持 placement new
6. 对应释放：delete（调用析构函数）和 free（不调用）
**知识点讲解：**
```cpp
int* p1 = new int(42);         // 分配 + 构造
int* p2 = (int*)malloc(sizeof(int)); // 仅分配
free(p1);                      // 错误！new/delete 和 malloc/free 必须配对
// placement new: 在已有内存上构造
void* buf = malloc(sizeof(string));
string* s = new (buf) string("hello");
s->~string(); // 手动调用析构
free(buf);
```
如果两者混用，会导致析构函数/构造函数不执行，对于 POD 类型有可能会导致读取到错误的值，复杂类型混用导致未定义行为
> [!Info] 可能的追问:
> - Q: new[] 和 delete[] 不匹配会导致什么？
> - A: new[] 会在头部记录数组长度（实现相关），delete[] 根据这个长度逐个调用析构函数。用 delete 代替 delete[] 可能只析构第一个对象导致内存泄漏。反过来是未定义行为。
> - Q: operator new 可以重载吗？应用场景？
> - A: 可以。用于内存池、对象池等场景，提前分配大块内存减少系统调用。

### NULL 和 nullptr 有什么区别？
**回答话术：**
nullptr 是 C++11 引入的关键字，表示空指针，类型为 `std::nullptr_t`。NULL 在 C++ 中通常通过 `#define` 宏替换定义为 0 或 `((void*)0)`，在函数重载场景会有问题——NULL 会被推导为整型 0，而不是指针类型。nullptr 可以隐式转换为任何指针类型，但不能转为整型，类型更安全。
**知识点讲解：**
```cpp
void func(int);
void func(char*);
func(NULL);    // 调用 func(int)，因为 NULL 就是 0
func(nullptr); // 调用 func(char*)，因为 nullptr 是空指针类型
// 模板推导中 nullptr 也更安全：
template<typename T>
void f(T t);
f(NULL);    // T = int
f(nullptr); // T = std::nullptr_t
```
> [!Info] 可能的追问:
> - Q: C 语言中 NULL 定义是什么？
> - A: 在 C 中 NULL 定义为 `((void*)0)`，是空指针常量。C++ 中因为不能隐式转换 void*，所以 NULL 常定义为 `0` 或 `__null`。
> - Q: nullptr_t 可以做什么？
> - A: 可以用来写接受任何指针类型的重载函数，或者标记某个操作返回指针类型。

### 内联函数（inline）的优缺点
**回答话术：**
**优点：** 消除函数调用开销（压栈、跳转、返回），编译器可能基于更大上下文做进一步优化（如常量传播）。C 语言中要做到一般使用宏
**缺点：** 增加代码体积（代码膨胀），可能降低指令缓存命中率；修改 inline 函数需要重新编译所有调用方；无法递归（理论上可以，但只能展开一层）；调试不便（无法在调用处设断点）。
**知识点讲解：**
- inline 只是对编译器的**建议**（C++98/03），编译器可选择忽略
- C++17 起 inline 变量可用于头文件中定义全局变量，解决 ODR 违反
- 放在类定义体内的函数默认是 inline 的
- 现代编译器对 inline 的优化非常智能，通常由编译器决定是否内联
> [!Info] 可能的追问:
> - Q: inline 函数和宏的区别？
> - A: 宏只是文本替换，没有类型检查、作用域；inline 是真正的函数，有类型检查、作用域、调试信息。宏可能多次计算参数（MAX(a++, b) 这样的陷阱）。
> - Q: C++17 inline 变量解决了什么问题？
> - A: 头文件中定义全局常量/变量时，如果被多个 .cpp include 会导致多重定义链接错误。C++17 前需要用 constexpr 或 inline 函数返回引用来绕开。inline 变量允许在头文件中直接定义。

### 类成员变量的 static inline 有什么用（C++17）
**回答话术：**
`static inline` 用于在头文件中直接定义和初始化类的静态成员变量，**不需要在 .cpp 文件中单独定义**。C++17 前，类的静态成员变量必须在头文件中声明（`static int count;`），然后在某个 .cpp 文件中定义（`int MyClass::count = 0;`），否则链接时会报"未定义的符号"错误。加上 inline 后，编译器自动处理多重定义问题——即使多个 .cpp 都 include 了这个头文件，链接器会合并为同一个符号，不会报重复定义。这使得静态成员变量的定义可以完全放在头文件中，简化了代码组织。
**知识点讲解：**
```cpp
// C++17 前：声明和定义必须分离
// MyClass.h
class MyClass {
    static int count;           // 声明
    static const int MAX = 100; // const 静态整型可以在类内初始化
};
// MyClass.cpp
int MyClass::count = 0;         // 定义（必须在一个 .cpp 中）

// C++17 起：static inline 一行搞定
// MyClass.h
class MyClass {
    static inline int count = 0;           // 直接头文件中定义+初始化
    static inline std::string name = "foo"; // 非整型也可以
    static inline const double PI = 3.14;   // 带 const 也可以
};
```
**与 const static 的区别**：`const static int` 只能在类内初始化整型/枚举类型（在编译期直接替换到指令中），不占用存储，不能取地址。`static inline` 可以是任何类型（string、double、自定义类型等），可以取地址，真正占用存储。实际上 C++17 的 `inline` 变量就是为了解决非 const 和非整型静态成员变量必须在 .cpp 中定义这个痛点。
> [!Info] 可能的追问:
> - Q: static inline 变量是否线程安全？
> - A: 初始化是线程安全的——C++11 起静态局部变量的初始化（包括 static inline 成员）保证只初始化一次，编译器会插入双重检查锁。但初始化之后对变量的读写操作不是线程安全的，多个线程同时修改需要加锁或使用 atomic。
> - Q: static inline 和 constexpr static 有什么区别？
> - A: constexpr static 是编译期常量，值在编译期确定，不占用运行时存储（可以理解为编译器在引用处直接替换值）。inline static 是运行时常量（可变的），占用存储，可以取地址。对于简单的整型常量，constexpr static 更优（零运行时开销）。对于需要在运行时初始化的复杂类型（如 std::string），用 static inline。

### C++ 的优化等级中主要优化什么？
**回答话术：**
GCC/Clang 常见优化等级：-O0（无优化，调试用）、-O1（基本优化，减小代码体积和执行时间）、-O2（大多数优化，包括指令调度、循环优化、内联展开）、-O3（激进优化，包括函数内联自动展开、向量化）、-Os（以减小二进制体积为目标）。
主要优化手段包括：
- **死代码消除**：删除不会被执行到的代码
- **常量传播与折叠**：在编译期计算常量表达式
- **循环优化**：循环展开、循环交换、循环不变代码外提
- **内联展开**：将小函数调用替换为函数体
- **指令重排与调度**：优化 CPU 流水线利用率
- **向量化**：将标量操作转为 SIMD 指令
- **尾调用优化**：将尾递归转为循环
> [!Info] 可能的追问:
> - Q: -O2 和 -O3 的实际差距大吗？
> - A: 大多数场景下 -O3 相对 -O2 提升不明显（通常 5%~10%），但会增加二进制体积。在一些数值计算中，自动向量化在 -O3 下才开启，可能提升明显。部分场景 -O3 反而因代码膨胀导致 icache miss 变多而变慢。
> - Q: 为什么 Debug 构建通常用 -O0？
> - A: -O0 保证所有变量在内存中（不会被优化到寄存器），函数调用保持原样，变量值可观测。优化后的代码断点可能跳转到不可预期的位置，变量值可能被优化掉无法查看。

### explicit 关键字的作用
**回答话术：**
explicit 用于修饰单参数的构造函数（或 C++11 起多参构造函数），防止编译器进行隐式类型转换。避免预期之外的对象构造。
**知识点讲解：**
```cpp
class String {
public:
    explicit String(int n) {}   // 禁止隐式转换
    String(const char* s) {}    // 允许隐式转换
};
String s1 = 'a';   // 错误！explicit 构造函数不能隐式调用
String s2 = "abc"; // 允许，const char* 隐式转换
void func(String s);
func('x');         // 错误！String(int) 被 explicit 阻止
```
> [!Info] 可能的追问:
> - Q: C++11 起 explicit 还能用于转换运算符？
> - A: 是的，`explicit operator bool()` 可以防止对象被隐式转换为 bool，如在 if 条件中需要显式转换。
> - Q: 为什么建议单参构造函数都加 explicit？
> - A: 防止意料之外的隐式转换导致的 bug。如果确实需要隐式转换再不加。

### 重载（overload）和重写（override）的区别
**回答话术：**
- **重载**：同一作用域内，函数名相同但参数列表不同（个数/类型/顺序）。编译期多态，由编译器根据参数类型确定调用哪个版本
- **重写**：子类重写父类的虚函数，函数签名必须相同。运行期多态，通过虚函数表在运行时确定调用哪个版本
**知识点讲解：**
```cpp
// 重载（overload）—— 编译期
void print(int);
void print(string);
void print(int, string);
// 重写（override）—— 运行期，需 virtual 关键字
class Base { virtual void show() { cout << "Base"; } };
class Derived : public Base { void show() override { cout << "Derived"; } };
```
> [!Info] 可能的追问:
> - Q: override 关键字的作用（C++11）？
> - A: 显式标记子类重写的函数，编译器会检查基类是否有对应的虚函数，避免拼写错误或签名不匹配导致的"本以为重写实则新建"的 bug。
> - Q: 函数隐藏（hiding）是什么？
> - A: 子类定义同名函数（不管参数），父类的所有同名函数都被隐藏。即使参数不同也不会构成重载。不同于重写（需要 virtual）。

### 为什么重载运算符/构造函数和使用 delete 删掉某些函数时需要对 const 版本做同样的修改？为什么要有这些 const 版本？
**回答话术：**
const 版本的运算符重载和构造函数存在的根本原因是：const 对象只能调用 const 成员函数，而非 const 对象可以调用两者。如果只提供非 const 版本，const 对象就无法使用。所以在需要同时支持 const 和非 const 对象时，必须提供 const 重载版本。
例如 `std::string::c_str()` 有 const 版本（返回 const char*，只读访问）和非 const 版本。`operator[]` 也有两个版本——const 版本返回 const 引用用于只读，非 const 版本返回引用用于修改。
当 delete 掉某些函数时也需考虑 const 版本，因为调用点可能是 const 对象。例如想禁止拷贝，同时 delete 拷贝构造和 const 拷贝构造可以防止编译器的某些隐式路径。
**知识点讲解：**
```cpp
class MyString {
    char* data;
public:
    const char& operator[](size_t i) const { return data[i]; }
    char& operator[](size_t i) { return data[i]; }
    MyString(const MyString&) = delete;
};
void func(const MyString& s) {
    char c = s[0];  // 调用 const 版本
}
```
> [!Info] 可能的追问:
> - Q: const 成员函数和非 const 成员函数算重载吗？
> - A: 算，const 是函数签名的一部分。只要函数名相同、参数列表相同、但 const 限定不同，就构成重载。
> - Q: 如果一个函数同时有 const 和非 const 版本，类内部调用哪个？
> - A: 取决于 this 指针是否是 const 的。常通过 const_cast 在 const 版本内部调用非 const 版本避免代码重复（或者反过来）。

### 面向对象的三大特性
**回答话术：**
1. **封装**：将数据和操作数据的函数绑定在一起，对外隐藏内部实现，通过 public/protected/private 控制访问权限，**模块化和访问安全**
2. **继承**：子类复用父类的成员和方法，可扩展新功能，形成类层次结构。**重用性**
3. **多态**：同一接口在不同对象上有不同实现。C++ 通过虚函数实现动态多态（运行期），通过模板/重载实现静态多态（编译期）**可拓展性，符合人类思维**
**知识点讲解：**
- 封装降低了耦合，便于维护
- 继承可用 public（接口继承）、protected/private（实现继承）
- 多态依赖于虚函数表和虚函数表指针（vtbl/vptr）
> [!Info] 可能的追问:
> - Q: 继承和组合如何选择？
> - A: 组合优先于继承。"is-a"关系用继承，"has-a"关系用组合。组合耦合度更低，更灵活。
> - Q: 多态的实现原理？
> - A: 每个有虚函数的类有一个虚函数表（vtbl），对象内存头部有一个虚函数表指针（vptr）指向它。调用虚函数时，通过 vptr → vtbl → 函数指针，间接调用，实现动态绑定。

### C++ 多态的实现原理（虚函数表）
**回答话术：**
C++ 多态通过**虚函数表（vtbl）** 实现。每个包含虚函数的类有一个 vtbl，存储函数指针。每个对象有一个隐藏的 vptr 指针指向类的 vtbl。调用虚函数时，通过 vptr → vtbl → 函数指针间接调用，实现运行期动态绑定。
单继承下，一个对象只有一个 vptr；多继承下，每个基类对应一个 vptr。构造过程中，vptr 在基类构造阶段指向基类 vtbl，进入派生类构造阶段后指向派生类 vtbl，这正是构造期间调用虚函数不会多态的原因。
**知识点讲解：**
```cpp
class Base { public: virtual void foo() { cout << "Base"; } virtual ~Base() = default; };
class Derived : public Base { void foo() override { cout << "Derived"; } };
Base* p = new Derived();
p->foo(); // 输出 Derived，通过 vptr 动态分发
// 对象内存布局：[vptr | Base members | Derived members]
```
> [!Info] 可能的追问:
> - Q: 构造函数和析构函数中调用虚函数会发生什么？
> - A: 调用的是当前正在构造/析构的类的版本，不是多态调用。因为构造时 vptr 指当前类的 vtbl。
> - Q: 虚函数表存放在哪里？
> - A: 通常只读数据段（.rodata），是编译期确定的静态数据。
> - Q: 虚函数表什么时候初始化？
> - A: 编译期由编译器生成，运行期在构造函数的初始化列表阶段设置 vptr。

### 模板算不算多态？
**回答话术：**
模板属于**静态多态（编译期多态）**，也称泛型多态。模板在编译期根据实参类型实例化生成具体代码，没有运行时查找开销。而虚函数多态是动态多态（运行期多态）。从"同一接口不同实现"的意义上说模板算多态，C++ 标准中确实将模板视为一种多态机制（编译期多态）。
**知识点讲解：**
```cpp
template<typename T>
T max(T a, T b) { return a > b ? a : b; }
class Animal { virtual void speak() = 0; };
```
> [!Info] 可能的追问:
> - Q: 静态多态和动态多态各自的优缺点？
> - A: 静态多态零运行时开销，编译器可充分优化；但生成的二进制体积增大（代码膨胀），且函数签名必须完全匹配。动态多态运行时灵活（可在运行时决定类型），但有虚函数调用开销（一次间接跳转），且不易被编译器内联优化。

### consteval 关键字（C++20）
**回答话术：**
`consteval` 指定函数必须是**立即函数（immediate function）**——它**必须在编译期执行**，无法在运行期调用。与 `constexpr` 的区别：`constexpr` 是"如果可能在编译期执行就在编译期执行，否则可以在运行期执行"（不一定强制编译期），`consteval` 是"必须在编译期执行"，如果在运行期调用该函数，编译器会报错，不允许退化到运行时。
**使用场景**：
1. **编译期参数检查**——最常见于 `std::format` 的格式字符串检查。`std::format` 的格式字符串参数是 `consteval` 的，编译器在编译期解析 `{}` 占位符并检查参数数量/类型是否匹配，如果格式字符串错误则编译失败。
2. **编译期计算**——要求函数必须在编译期产生结果，防止因为函数复杂度高导致编译器放弃编译期计算。
3. **安全封装**——确保某些敏感操作只能在编译期执行（如常量求值），不会泄漏到运行时。
**知识点讲解：**
```cpp
consteval int square(int x) {
    return x * x;
}
constexpr int runtime_compatible(int x) {
    return x * x;
}
int main() {
    int a = square(5);         // OK：编译期计算
    // int b = square(var);    // 错误！var 是运行期变量，consteval 函数必须编译期求值
    int c = runtime_compatible(5);   // OK：编译期
    int d = runtime_compatible(var);  // OK：退化到运行期执行
}
// 实际应用：std::format 的格式字符串检查
auto s1 = std::format("{:d}", 42);  // OK
// auto s2 = std::format("{:d}", "hello");  // 编译错误！consteval 检查到类型不匹配
```
**constexpr vs consteval vs constinit（C++20 三个编译期关键字对比）**：
- `constexpr`：函数或变量"可能"在编译期求值，不强制，也可在运行期
- `consteval`：函数**必须**在编译期求值，运行期调用直接报错
- `constinit`：变量必须在编译期初始化（保证初始化顺序），但初始化后可以在运行期修改
> [!Info] 可能的追问:
> - Q: consteval 函数可以调用 constexpr 函数吗？
> - A: 可以。consteval 函数在编译期执行，自然可以调用同样在编译期执行的 constexpr 函数。反过来，constexpr 函数不能调用 consteval 函数（因为 constexpr 可能退化到运行期执行，但 consteval 不允许在运行期被调用）。
> - Q: consteval 函数和宏有什么区别？
> - A: 宏也是文本替换在编译期处理，但宏没有类型检查、作用域，而且宏不能作为函数指针传递。consteval 是真正的函数，有类型检查、作用域、调试信息。consteval 比宏更安全，功能更像"强制编译期执行的 constexpr 函数"。
> - Q: consteval 和 constexpr 的实际选择标准？
> - A: 你希望这个函数一定被编译期执行（编译期检查）→ consteval；你可以接受这个函数在运行期执行（性能换灵活性）→ constexpr。标准库中 std::format 的格式字符串参数用 consteval 是因为格式字符串错误是典型的"早发现早修复"问题，不应该留到运行期才暴露。

### 模板元编程中 typename 和 class 关键字有什么区别？
**回答话术：**
在模板参数列表中，typename 和 class **完全等价**，没有任何区别：
```cpp
template<typename T> void func(T);  // 等价于
template<class T> void func(T);
```
但在嵌套依赖类型的场景中，**只能用 typename**——当模板参数 T 是未知类型时，T::value_type 是一个"依赖类型"，需要 typename 告诉编译器这是一个类型而不是静态变量：
```cpp
template<typename T>
void func(const T& container) {
    typename T::value_type val;  // 必须加 typename
}
```
> [!Info] 可能的追问:
> - Q: C++20 的 concept 中两者还有区别吗？
> - A: C++20 concept 语法中仍然等价。但更推荐用 typename，因为在 concept 约束中 class 容易被误解为"必须是类类型"。

### CRTP（奇异递归模板模式）是什么
**回答话术：**
CRTP（Curiously Recurring Template Pattern）是一种 C++ 编程技巧——派生类将自己作为模板参数传递给基类：`class Derived : public Base<Derived>`。这样基类可以在编译期知道派生类的类型，通过 `static_cast<Derived*>(this)` 调用派生类的方法。效果类似于虚函数的多态，但区别在于虚函数是运行期多态（通过 vptr → vtbl 查找，有间接调用开销），CRTP 是编译期多态（直接调用派生类方法，编译器可以内联展开，零开销）。核心应用是**静态多态**和**代码复用**。
**典型应用**：
1. 你的 fastlog 日志库中 `BaseLogger<Derived>` 调用 `static_cast<Derived*>(this)->log(...)` 来实现不同 Logger 的差异化行为
2. 在 C++17 之前实现 `std::enable_shared_from_this` 类似的混入（mixin）能力
3. 在数值计算库（如 Eigen）中实现表达式模板（Expression Templates），避免虚函数开销
4. ATL/WTL 库中的窗口消息映射
**知识点讲解：**
```cpp
// CRTP 实现静态多态
template <typename Derived>
class Base {
public:
    void interface() {
        // 编译期调用派生类方法，可内联
        static_cast<Derived*>(this)->implementation();
    }
};
class DerivedA : public Base<DerivedA> {
public:
    void implementation() { cout << "A impl"; }
};
class DerivedB : public Base<DerivedB> {
public:
    void implementation() { cout << "B impl"; }
};
// 使用：Base<DerivedA>::interface() 直接调用 DerivedA::implementation()
// 与虚函数对比：无 vptr 开销，无间接跳转，可内联。但类型在编译期绑定，不支持运行期多态。
```
**CRTP vs 虚函数**：CRTP 编译期多态（零开销、可内联、不支持运行期动态类型），虚函数运行期多态（有 vptr 开销、支持运行期动态类型）。如果需要在运行期根据实际类型决定行为（如 vector<Base*> 存多种派生类），只能用虚函数；如果类型在编译期已知且追求极致性能（如日志库、数学库），用 CRTP。
> [!Info] 可能的追问:
> - Q: CRTP 和普通模板的区别是什么？
> - A: 普通模板是"编译器根据实参类型生成函数代码"，泛型编程。CRTP 是"派生类把自身类型传给基类模板，基类通过 static_cast 调用派生类方法"，实现继承体系下的静态多态。普通模板不涉及继承，CRTP 基于继承。
> - Q: CRTP 有什么缺点？
> - A: 1) 类型膨胀——每个派生类特化一个基类模板实例，二进制体积增大（和普通模板一样）。2) 接口不清晰——基类接口通过 static_cast 调用派生类方法，代码可读性不如虚函数显式。3) 派生类方法名错误不会在编译期立即报错，而是在基类调用时报错，错误信息晦涩。

### std::format 和 std::vformat 的区别
**回答话术：**
`std::format` 是类型安全的格式化函数，用 `{}` 占位符替代 printf 的 `%d`。它在**编译期**检查格式化字符串与参数是否匹配（C++20 起 consteval）。`std::vformat` 则是**运行时**格式化版本——它接受一个 `std::string_view` 作为格式字符串（不是编译期常量）和一个 `std::format_args` 参数包，在运行时解析格式字符串并完成替换。
**区别**：`format` 的格式字符串在编译期确定，编译器可以检查参数数量/类型是否匹配；`vformat` 的格式字符串在运行时才确定，不做编译期检查。`vformat` 常用于需要动态构建格式字符串的场景，如国际化（不同语言不同格式模板）、从配置文件读取格式字符串、日志库中在运行时决定日志格式。
**知识点讲解：**
```cpp
// std::format — 编译期检查，类型安全
std::string s1 = std::format("Hello {}, your score is {}", "Alice", 95);
// 编译器检查 {} 数量和参数数量是否匹配

// std::vformat — 运行时格式化，格式字符串可以动态构建
std::string fmt = getFormatFromConfig();  // 运行时决定格式
std::string s2 = std::vformat(fmt, std::make_format_args(42, "hello"));
// 不检查参数匹配，运行时如果格式字符串和参数对不上会抛 std::format_error

// make_format_args 打包参数为 std::format_args
// vformat + make_format_args 适合做可变参数包装函数
```
**典型应用场景**：日志库中常常需要将格式化延迟到实际输出时，或者支持用户自定义日志格式模板。这时候无法在编译期确定格式字符串，只能用 `vformat` 运行时格式化。
> [!Info] 可能的追问:
> - Q: std::format 和 printf 比有什么优势？
> - A: 1) 类型安全——printf 的 %d/%s 和实际参数类型不匹配时只有运行时警告，format 在编译期检查。2) C++ 原生支持——不需要包含 `<cstdio>`，参数直接传入不需要类型转换。3) 性能——format 在某些实现中比 iostream 快，对比 printf 互有胜负（printf 的格式解析非常轻量）。4) 可读性——花括号占位符和位置参数比 %d%f%s 更容易阅读。
> - Q: fmt::format 和 std::format 是什么关系？
> - A: std::format 是从 C++20 进入标准库的，其设计基于开源的 fmtlib（{fmt} library）。大部分实现（libstdc++、libc++）实际上就是在内部封装了 fmtlib。如果你使用 C++17 及以下版本，可以直接使用 fmtlib 的头文件 `<fmt/core.h>`。功能和接口基本一致。

### 构造函数和析构函数能否为虚函数（含多态删除详解）
**回答话术：**
- **构造函数不能是虚函数**：虚函数调用依赖于 vptr，而 vptr 在构造函数体内才设置好，构造时对象还未完全创建，无法通过 vtbl 调用
- **构造函数中调用虚函数**: 调用派生类的虚函数可能访问未初始化的成员，极其危险。从语义上，构造是确定对象类型的过程，"多态构造"无意义。所以编译器在进入基类构造函数体之前，会**强制将对象的 vptr 指向当前基类的 vtbl（虚函数表）**。只会调用基类的默认实现
- **析构函数可以且通常应该为虚函数**：当通**过基类指针删除派生类对象**时，如果析构函数不是虚函数，则只调用基类析构函数，派生类资源无法释放。注意：如果类不被用作基类，则不必虚析构（增加 vptr 开销）。
- **析构函数中调用虚函数**: 当析构函数执行时，对象的派生类部分已经被销毁（派生类析构函数已执行完毕），对象的动态类型已退化，在虚函数表中查找对应函数的最后覆盖实现并执行
**知识点讲解：**
```cpp
class Base {
public:
    virtual ~Base() {}  // 虚析构，保证派生类资源释放
};
class Derived : public Base {
    int* data = new int[100];
    ~Derived() { delete[] data; }
};
Base* p = new Derived();
delete p;  // 想调用 ~Derived()，靠虚析构实现
```
**什么是"多态删除"？** 多态删除就是通过基类指针 `Base*` 删除派生类对象。这在 C++ 中非常常见——基类指针指向派生类对象，然后用 `delete` 删除。如果基类析构函数不是虚函数，那么 `delete p` 调用的析构函数版本由**指针类型**（Base*）决定，而不是由**实际对象类型**（Derived）决定，所以只会调用 Base 的析构函数，Derived 的资源不会被释放。
**如果不写虚析构具体会发生什么？** 当 `delete p` 删除**具有多态的指针**时：
1. 如果 ~Base() 是**虚函数**：运行时通过 vptr 查找 vtbl，找到正确的 Derived::~Derived() 先调用，然后自动调用 `Base::~Base()`
2. 如果 ~Base() 是**非虚函数**：编译器看到 p 是 Base* 类型，静态绑定到 Base::~Base()，只释放 Base 部分。Derived 中的 int* data 永远不会被 delete，也就是**内存泄漏**
**编译器会警告吗？** 是的，GCC/Clang 在有虚函数但没有虚析构的类上会给出警告：`-Wnon-virtual-dtor`（默认开启）。对于没有虚函数的类则不会警告。一些项目（如 LLVM）将此警告视为错误。
> [!Info] 可能的追问:
> - Q: 如果不需要多态删除，是否还需要虚析构？
> - A: 不需要。虚析构会引入 vptr，增加对象体积（8字节）。如果类不被作为基类使用，可以不声明虚析构。
> - Q: 纯虚析构函数可以吗？
> - A: 可以，但**必须给出实现**（因为析构函数总是在继承链上被调用的）。`virtual ~Base() = 0;` + 类外 `Base::~Base() {}`。
> - Q: 编译器在我写错时会提醒吗？
> - A: 如果有虚函数却没有虚析构，GCC 和 Clang 默认会给出 -Wnon-virtual-dtor 警告。但对没有虚函数的纯数据类，编译器不会警告（因为不需要多态删除）。
> - Q: 什么情况下会用到虚函数机制来删除对象？
> - A: 任何通过基类指针管理派生类对象生命周期的场景。典型例子：工厂模式返回 Base* 指针、容器存储 Base*（如 vector<Base*>）、插件系统通过抽象接口管理具体实现。在这些场景中，用户只有基类指针，不知道具体派生类型，但 delete 时必须正确释放派生类资源。虚析构保证了"通过基类指针删除时，能正确调用派生类析构函数"。

### 继承链中构造和析构顺序及底层原理
**回答话术：**
**构造顺序**（从基类到派生类）：
1. 先构造基类子对象（先虚基类，后普通基类，按继承声明顺序）
2. 初始化列表初始化成员变量（按声明顺序）
3. 执行派生类构造函数体
**析构顺序**（与构造完全相反）：
1. 执行派生类析构函数体
2. 销毁派生类成员（按声明逆序）
3. 调用基类析构函数（从派生类到基类，按继承逆序）
**为什么是这个顺序？**
- **构造**：派生类依赖基类的成员，所以基类必须先初始化。就像一个房子必须先打地基（基类）再装修（派生类）。vptr 的设置为：执行基类构造函数时 vptr 指向基类 vtbl，进入派生类构造函数后 vptr 切换为派生类 vtbl
- **析构**：析构释放派生类独有的资源后，才能释放基类部分。vptr 在派生类析构函数执行后恢复为基类 vtbl，然后调用基类析构函数
```cpp
class Base { public: Base() { cout << "Base"; } ~Base() { cout << "~Base"; } };
class Derived : public Base { public: Derived() { cout << "Derived"; } ~Derived() { cout << "~Derived"; } };
// 输出：BaseDerived~Derived~Base
```
> [!Info] 可能的追问:
> - Q: 为什么不能先执行派生类构造函数体再构造基类？
> - A: 派生类构造函数体可能使用了基类成员，先执行基类构造保证这些成员已初始化。如果没有初始化列表中的基类初始化，编译都通不过。
> - Q: 虚继承时的构造顺序？
> - A: 虚基类优先于普通基类构造，且在整个继承链中**只构造一次**（由最派生类直接构造），这解决了菱形继承中基类重复构造的问题（Diamond Problem）。

### C++ 中使用异常处理为什么会导致二进制文件体积膨胀和性能问题？
**回答话术：**
**体积膨胀的原因**：
1. 编译器为每个可能抛出异常的函数生成异常处理表（LSDA, Language-Specific Data Area），记录哪些指令可能抛出哪种异常、栈展开时需要析构哪些对象
2. 每个 try 块都需要额外的元数据记录 catch 子句的匹配规则
3. RTTI（运行期类型信息）存储异常类型信息
**性能开销**：
1. **零开销模型（Zero-Cost Exception Handling）**：正常路径无额外开销（不像 setjmp/longjmp 有额外寄存器保存），异常表放在冷区（.gcc_except_table），不占用热点代码。但异常路径非常慢（需要查表、栈展开）
2. **栈展开（Stack Unwinding）**：抛出异常时，运行时沿着调用栈向上查找匹配的 catch，沿途调用所有局部对象的析构函数
3. **阻碍编译器优化**：编译器需要假设 try 块中任何函数调用都可能抛出异常（除非标记 noexcept），限制了代码移动、函数内联等优化
> [!Info] 可能的追问:
> - Q: 为什么 llvm 项目禁用异常？
> - A: LLVM 代码追求极致性能、最小二进制体积，且错误在编译器中通常应尽早终止（assert/fatalError）而非恢复。禁用异常减小了生成代码体积约 5%~10%，也加快了编译速度。
> - Q: noexcept 的作用？
> - A: 告诉编译器函数不抛出异常。编译器可以优化掉异常处理元数据，且如果 noexcept 函数真的抛异常，直接调用 std::terminate（而不展开栈）。
> - Q: 使用了异常处理（try-catch），是否必须开启 RTTI 支持？
> - A: **不一定**。异常处理和 RTTI 是两个独立的编译器特性。try-catch 本身不依赖 RTTI——catch 匹配通过异常对象的类型信息，这是异常机制自己维护的类型表，不依赖 typeid/dynamic_cast 的 RTTI 机制。但如果你 catch 的是多态类型（catch (Base&) 实际捕获 Derived 异常），异常机制内部需要用到类型信息来匹配，这部分按标准实现也不依赖编译器的 -frtti 开关。只有当你显式用了 typeid() 或 dynamic_cast 时才需要 rtti。实际上 Linux 上 GCC 编译时默认 -frtti 开启，嵌入式/游戏开发可以 -fno-rtti 禁用 RTTI，异常仍然正常工作。

### 空类生成哪些函数？移动构造函数/运算符是否是 noexcept 的？
**回答话术：**
C++ 编译器会为一个空类自动生成六个默认成员函数（如果被使用的话）：
1. 默认构造函数
2. 默认析构函数
3. 拷贝构造函数
4. 拷贝赋值运算符
5. 移动构造函数（C++11）
6. 移动赋值运算符（C++11）
**空类生成的移动构造函数/运算符是否是 noexcept？** 是的，**默认生成的移动构造和移动赋值运算符是 noexcept 的**。因为对于空的类或只有平凡成员的类，移动操作等同于拷贝或 memcpy，不会抛异常。但如果类的成员（如 `vector<string>`）的移动构造不是 noexcept 的，那么该类生成的移动构造也会被隐式标记为 noexcept(false)。标准库的很多优化（如 vector 扩容时用 move 还是 copy）就依赖于 move 操作是否是 noexcept 的。
> [!Info] 可能的追问:
> - Q: 什么情况下编译器会拒绝生成默认函数？
> - A: 如果类有 const 或引用成员，默认拷贝赋值运算符不会被生成（无法修改 const 成员或重置引用）。如果类有 move-only 成员（如 unique_ptr），拷贝构造和拷贝赋值会被删除（=delete）。
> - Q: 自动生成的析构函数可以析构其他类的指针成员吗？
> - A: 对于 raw 指针，自动生成的析构函数**不会**自动 delete 它们（这导致内存泄漏，所以**类内有指针的类必须格外小心析构/移动/拷贝操作的实现**）。对于智能指针成员（unique_ptr/shared_ptr），它们的析构函数会自动调用，所以不需要手动 delete。
> - Q: noexcept 标记对 vector 扩容有什么影响？
> - A: vector 扩容时，如果元素类型的移动构造是 noexcept 的，vector 会移动元素（高效），否则会拷贝元素（安全但慢）。这就是为什么自定义类型应该标记移动操作为 noexcept。

### C++中值传递和引用传递的区别？
1）值传递：在函数调用时，会触发一次**参数的拷贝动作**，所以对参数的修改不会影响原始的值。如果是较大的对象，复制整个对象，效率较低。
2）引用传递：函数调用时，函数接收的就是参数的引用，不会触发参数的拷贝动作，效率较高，但对参数的修改会直接作用于原始的值。

通过函数栈帧角度理解：
首先，不管是值传递还是引用传递，本质都是在被调用函数中，在栈区开辟一块空
间，往这块空间中填某一个值。
值传递和引用传递不同的是，在往局部的栈空间中填的值是不同的，以及**对这个栈空间中局部变量操作时进行的动作**是不同的
- 值传递：传递过程中，会对实参的值进行一次拷贝，借助函数栈帧的创建过程，填函数的局部变量空间中，后续函数中对这个变量的操作，都是修改函数局部栈空间中值，并不会影响到实参，因根本不会通过实参的存储地址进行操作。
- 引用传递：传参时，也会往函数局部栈空间填值，但这里填的是引用变量的地址，后续在对函数里的形参操作时，都会通过**间接寻址**的方式操作到实参。
- 从编译的角度看，生成符号表时，会在符号表中填变量名和对应的地址。值传递的形参对应的地址是实参变量的地址，而这个地址中内容是可以改变的。而引用变量名对应的地址是引用对象的地址，符号表一经生成无法改变，**所以引用变量不能更改引用的对象**

### C 和 C++的区别
1）面向对象还是面向过程：
- C 语言是一门面向过程的语言，侧重于通过过程（函数）来解决问题。
- C++是一门多范式语言，主要支持面向对象，侧重于使用类和对象来组织代码。
2）继承：
- C++支持继承，允许一个子类继承一个或多个父类，达到代码复用的目的。
- C 语言中没有继承的概念。
3）函数重载：
- C++支持函数通过参数类型和参数个数的重载。
- C 语言不支持重载，函数名必须唯一才行。
4）模板：
- C++支持模板，支持静态和动态形式的多态。
- C 语言对此都不支持。
5）内存管理：
- C++使用 new 和 delete 操作符来管理内存，也支持使用智能指针来动态管理内存。
- C 语言需要使用 malloc 和 free 来申请和释放内存。
### 什么是 C++的左值和右值？有什么区别？
- 左值：可以出现在赋值运算符的左边，并且可以被取地址，通常是有名字的变量
- 右值：不能出现在赋值运算符的左边，不可
以被取地址，表示一个具体的数据值，通常是常量、临时变量
- 左值：可以放到等号左边的东西叫左值，可以取地址并且有名字
- 右值：不可以放到等号左边的东西就叫右，不可以取地址并且没有名字
可以使用 `std::move` 将***左值变为右值***
**左值引用**：当你需要修改对象的值，或者需要引用一个**持久对象**时使用。
**右值引用**：当你需要处理一个临时对象，并且想要**避免复制**，或者实现移动语义时使用。

纯右值属于右值。运算表达式产生的临时变量、不和对象关联的原始字面量、非引用返回的临时变量、lambda 表达式等都是纯右值。
举例：
- 除字符串字面值外的字面值
- 返回非引用类型的函数调用
- 后置自增自减表达式 i++、i--
- 算术表达式 (`a+b, a*b, a&&b，a==b` 等)
- 取地址表达式等 (&a)
### 什么是 C++的移动语义和完美转发？
一种优化资源管理的机制。常规的资源管理是拷贝别人的资源。而移动语义是转移所有权，转移了资源而不是拷贝资源，性能会更好。移动语义通常用于那些**比较大的对象**，搭配移动构造函数或移动赋值运算符来使用。
所有 C++ stl 都实现了移动语义，本质上是**偷走右值指向资源的指针**，避免拷贝开销
参考 [[Modern C++#移动语义]]

完美转发指可以写一个接受任意实参的函数模板，并转发到其它函数，目标函数会收到与转发函数完全相同的实参，转发函数实参是左值那目标函数实参也是左值，转发函数实参是右值那目标函数实参也是右值
核心实现是：转发引用（`T&&`）+ `std::forward<T>(arg)`
参考 [[Modern C++#Note：完美转发]]

使用花括号 `{}` 来初始化变量或对象。
可以使用初始化列表接受任意长度可以防止类型窄化，避免精度丢失的隐式类
型转换
如果对构造函数参数设置为 `std::initializer_list<int> list`，那么这个类可以接受任意长度的列表初始化，主要是为了防止隐式类型窄化，统一代码风格
### C++中 move 有什么作用？它的原理是什么？
右值可以触发到类的移动构造函数或者移动赋值函数。因触发了移动构造函数或者移动赋值函数，**我们就默认，原对象后面已经不会再使用了**（包括内部的某些内存），这样我们就可以在新对象中直接使用原对象的那部分内存，减少了数据的拷贝操作
但，原对象是否不可使用，还是取决于搭配的移动构造函数和移动赋值函数是如何实现的，但使用 `std::move` 时，原对象后不可使用了
`std: move` 本身并不移动任何东西。它仅仅执行一个类型转换，将其参数转换为对应类型的右值引用。实际上是在告诉编译器你有一个对象，你打算将它作为一个右值来使用，这通常意味着你不再需要这个对象的当前值，而且这个对象的资源可以被安全地转移到另一个对象中。
移动语义是在 `std: move` 被用来将一个对象标记为可移动后，该对象参与到一个需要右值引用的上下文中时触发的。（如对象被用作另一个对象的构造函数或赋值函数的参数)
### C++对象模型：sizeof 空类结果
C11 标准前不允许空结构体；C11 及以后允许，但未明确规定其大小。编译器实现一般会返回 0
C++标准会返回 `>=1` 的结果，根据内存对齐规则决定
1. 保证对象唯一性：C++要求每个对象在内存中必须有唯一的地址。如果空类大小为 0，那么创建多个对象时，它们可能拥有相同的地址，这违反了对象唯一性原则。
2. 避免零大小数组问题：在数组或容器中，若元素大小为 0 会导致地址计算错误（例如指针算术会失效）。
3. 兼容性考虑：确保空类对象能像其他对象一样进行取址等操作。

| 特性                 | C (GCC/Clang) | C++       |
| :----------------- | :------------ | :-------- |
| 空结构体 | 0             | 1         |
| 类的大小标准是否强制非零？ | 否             | 是         |
| 多个对象地址可能相同？        | 是（零大小对象）      | 否（地址必然不同） |
### STL 内的仿函数和 lambda 表达式的性能比较
#### 简要结论
在现代 C++编译器中，仿函数和 lambda 表达式在**性能上基本相当**，因 lambda 表达式本质上会被编译器转换为**匿名仿函数类**。
两者在正确使用情况下**都能被编译器内联优化**，**性能差异可以忽略不计**。选择主要基于代码可读性和具体使用场景。
#### 详细说明
1. 编译原理层面：
	- Lambda 表达式在编译期会被转换为匿名仿函数类
	- 两者都支持内联优化，避免了函数调用开销
2. 性能关键因素：
	- 在内联能力上，两者都能被现代编译器有效内联
	- 在捕获开销上，lambda 的捕获机制可能引入额外拷贝
	- 在代码生成上，模板实例化可能影响编译时间和代码大小
3. 实际性能差异：
	- 在-O 2/-O 3 优化级别下，性能差异通常小于 1%
	- 简单操作时几乎无差别，复杂捕获场景可能有微小差异
> [!note] 可能的追问
> **Q 1: "Lambda 捕获列表的不同方式对性能有什么影响？"**
> A 1: 值捕获：可能引入拷贝开销，但生命周期安全; 引用捕获：无拷贝开销，但需注意悬挂引用风险; 初始化捕获（C++14）：更灵活，性能取决于具体实现
> **Q 2: "Lambda 表达式能否完全替代仿函数？"**
> A 2"大部分场景可以，但仿函数在以下情况仍有优势：需要命名和文档化的复杂算法, 需要在多个翻译单元间共享, 需要继承或多态行为
### 函数调用中，压栈都往栈中压入了什么？压入顺序是什么样的？
**回答话术：**
函数调用时的压栈内容取决于**调用约定**和 ABI 实现（Calling Convention），以 x86-64 Linux 下默认的 System V AMD64 ABI 为例：
**压栈内容（在需要栈传递参数时）**，按从右到左的顺序压栈：
1. **参数**：前 6 个整型参数通过寄存器传（rdi, rsi, rdx, rcx, r8, r9），浮点用 xmm0-xmm7。多余的参数压栈
2. **返回地址**：call 指令自动将下一条指令地址压栈
3. **caller 保存的寄存器**：编译器选择保存哪些（rbx, rbp, r12-r15 由 callee 保存；rax, rcx, rdx, rsi, rdi, r8-r11 由 caller 保存）
4. **局部变量**：sub rsp, N 分配栈空间给局部变量
5. **栈帧指针**：可选（一般不保存 rbp，用 rsp 直接寻址）
**栈生长方向**：高地址向低地址（向下增长）。每次 call 在栈顶（低地址）分配新栈帧。
> [!Info] 可能的追问:
> - Q: 什么是栈溢出（stack overflow）？如何检测？
> - A: 栈大小有限（Linux 默认 8MB），深层递归或分配大局部数组会导致栈溢出，覆盖其他内存或触发段错误。可用 `-fsanitize=address` 或 `ulimit -s` 查看当前栈大小。
> - Q: 为什么栈向下增长而堆向上增长？
> - A: 历史惯例和内存布局设计。让栈和堆相向生长可以最大化可用地址空间的范围，在两者之间留出大片空闲区域供 mmap 使用。

### 右值引用、移动语义和完美转发
**回答话术：**
- **右值引用（&&）**：绑定到"将亡值"（即将销毁的临时对象），允许我们"偷"走它的资源而不是拷贝
- **移动语义**：通过移动构造函数和移动赋值运算符，将源对象的资源（如堆内存）转移给目标对象，避免深拷贝。源对象被置为有效但未定义的状态
- **完美转发**：利用模板 + 引用折叠规则，保持参数在传递过程中左值/右值属性不变。通过 std::forward 实现
**知识点讲解：**
- 引用折叠规则：`T& &` → `T&`, `T& &&` → `T&`, `T&& &` → `T&`, `T&& &&` → `T&&`
- std::move 不做任何实际移动，只是把参数转化成右值引用（static_cast<T&&>）
- std::forward 根据模板参数决定转换：T 是左值引用就转为左值，否则转为右值
**为什么拷贝构造函数参数是 const T&，而移动构造函数参数是非 const T&&？**
- **拷贝构造（const T&）**：我们不希望修改源对象，只是"复制"它，所以用 const 保护源对象不被意外修改
- **移动构造（T&&）**：移动操作会从源对象"偷"资源（如置空指针），这必然会修改源对象，所以不能是 const 的
```cpp
class MyString {
    char* data;
public:
    MyString(const MyString& other) {  // 拷贝：不修改 other
        data = new char[other.size()];
        memcpy(data, other.data, other.size());
    }
    MyString(MyString&& other) noexcept {  // 移动：需要修改 other 来"偷"资源
        data = other.data;     // 偷走指针
        other.data = nullptr;  // 必须修改 other！
    }
};
```
**push_back 是移动还是拷贝取决于什么？** 取决于传入的是左值还是右值：
- `v.push_back(x)` → x 是左值，调用拷贝构造（除非用 `std::move(x)` 强制转为右值）
- `v.push_back(std::move(x))` → 调用移动构造
- `v.emplace_back(args...)` → 直接构造，不存在移动或拷贝
另外，如果元素类型没有移动构造函数，或者移动构造函数不是 noexcept（在 vector 扩容时），会退化为拷贝。
> [!Info] 可能的追问:
> - Q: push_back 和 emplace_back 的区别？
> - A: emplace_back 直接在容器内构造对象，完美转发参数，避免临时对象的构造和移动。push_back 需要先构造临时对象然后移动/拷贝到容器中。
> - Q: 完美转发有什么用？什么场景会用到？
> - A: 核心作用是保留参数的左右值属性传递给下一层函数，让被调用方知道该用移动还是拷贝。如果不完美转发，右值经过一次函数转发后会被当成左值，从而调用拷贝操作而不是移动操作，失去移动优化的机会。典型场景：1) 工厂函数——make_shared 需要完美转发参数到 T 的构造函数，让 T 的移动构造能被触发 2) 包装/代理函数——如日志库的 info(format, args...) 转发 args 到 std::format 3) emplace_back——将参数完美转发到容器元素的构造函数。简单说：任何需要"转发参数到另一个函数，同时保留移动优化机会"的地方都用得到完美转发。
> - Q: vector 扩容时 move 还是 copy 取决于什么？
> - A: 取决于移动构造函数是否被标记为 noexcept。如果是 noexcept，vector 用 move；否则用 copy（因为如果 move 抛异常，已部分移动的元素无法恢复，违反强异常安全保证）。这是 C++11 为什么把默认移动构造标记为 noexcept 的原因。

### 智能指针（shared_ptr、unique_ptr、weak_ptr）
**回答话术：**
本质上是 C++11 引入的自动管理对内存分配的模板类，用于包装裸指针，避免悬空指针和指针泄漏
- **unique_ptr**：独占所有权，不可拷贝只可移动。零开销，大小等于裸指针。通过 `std::make_unique` 创建，没有性能损耗。
- **shared_ptr**：共享所有权，通过引用计数在计数归零时删除对象。大小是裸指针的两倍（一个指向对象，一个指向控制块）。通过 `std::make_shared` 创建
- **weak_ptr**：弱引用，不增加引用计数。解决 shared_ptr 循环引用问题。通过 lock() 获取 shared_ptr 检查对象是否存活
智能指针只是语义上的内存安全保证，不规范的使用，比如 unique_ptr 使用 release 放弃所有权，再用 get 获取裸指针这层保障就消失了
**知识点讲解：**
- shared_ptr 的线程安全性：控制块（引用计数）的加减是原子操作，线程安全；但所指对象的线程安全性需要额外同步
- `unique_ptr` 适合场景:  绝大多数情况下的局部变量或类成员。实现 Pimpl 模式。作为函数返回值（通过移动语义高效传递所有权）。
- 需要注意 C++14 之前，智能指针如果包装裸数组类型需要自定义删除器，否则会对数组类型调用 `delete` 进行析构，导致未定义行为
**如何使用 weak_ptr 解决 shared_ptr 循环引用？**
```cpp
struct Node {
    shared_ptr<Node> next;  // 如果两个 Node 互指对方，就产生循环引用
    // weak_ptr<Node> next;  // 改为 weak_ptr，不增加引用计数，打破循环
    ~Node() { cout << "destroyed"; }
};
auto a = make_shared<Node>();
auto b = make_shared<Node>();
a->next = b;  // b 的引用计数 +1
b->next = a;  // a 的引用计数 +1（循环引用！a 和 b 都不会被释放）
```
改为 weak_ptr 后：`b->next = a` 不会增加 a 的引用计数，所以 a 析构时引用计数归零正常释放，然后 b 的引用计数也归零释放。这就是"打破循环"的原理——**不让持有关系成环**。
> [!Info] 可能的追问:
> - Q: 智能指针管理一定不会有内存泄漏吗？
> - A: 不一定。最常见场景是 shared_ptr 循环引用。解决：用 weak_ptr 打破循环。
> - Q: shared_ptr 的线程安全性具体如何？
> - A: 引用计数的增减是原子操作，多个线程同时拷贝或销毁 shared_ptr 是安全的。但同一个 shared_ptr 在多线程中同时修改（如同时 reset）会 data race。所指对象的线程安全需要加锁。
> - Q: make_shared 的缺点？
> - A: 控制块和对象在同一块内存上分配，如果 weak_ptr 还存在，即使 shared_ptr 都析构了，对象内存不能释放。另外 make_shared 不支持自定义 deleter。

### 内存泄漏（原因、后果、预防、排查）
**回答话术：**
**原因**：
1. new 出来的堆内存没有 delete；new[] 没有 delete[]；
2. malloc/free 不配对；
3. 基类析构函数非虚导致派生类资源未释放；
4. 容器中存储的指针未释放；循环引用（shared_ptr）；
5. 资源句柄（文件描述符、socket、数据库连接）忘记关闭。
**后果**：程序占用的内存持续增长，最终 OOM（Out Of Memory）导致进程被系统杀死或系统卡顿。
**预防**：优先使用 RAII（智能指针、容器）；遵循所有权语义（unique_ptr 表示独占，shared_ptr 表示共享）；基类析构设为虚函数；new/delete 配对。
**排查**：Linux 下使用 Valgrind（`valgrind --leak-check=full ./program`）、AddressSanitizer（编译加 `-fsanitize=address`）、或者用 mtrace。
> [!Info] 可能的追问:
> - Q: 有没有遇到过 OOM？场景是什么？
> - A: 常见场景：一次性读入超大文件到内存、创建过多线程（每个线程有自己的栈空间）、缓存未限制大小。在实际项目中遇到过因为日志缓存未及时刷盘导致的 OOM。
> - Q: AddressSanitizer 的工作原理？
> - A: 编译时在每次内存访问插入检测代码，维护影子内存（shadow memory）记录哪些地址可访问。在 free/delete 后将对应区域标记为"已释放"，后续访问即报告 use-after-free。

### 野指针 & 悬空指针（怎么来的、危害、如何避免）
**回答话术：**
野指针是创建但未初始化的指针
**来源**：
1. 指针 delete/free 后未置为 nullptr（悬空指针 dangling pointer）
2. 返回栈对象的地址（函数返回时局部变量销毁，栈空间被回收）
3. 指针未初始化
**为什么返回栈对象的地址会导致野指针？** 函数返回时，它的栈帧被销毁（栈指针 rsp 恢复到调用前的值）。函数内定义的局部变量所占的栈空间被视为"空闲"，下次调用其他函数时，同样的栈地址会被覆盖使用。所以虽然你拿到了一个地址，但它指向的内容随时可能被改写，解引用它就是未定义行为。
```cpp
int* bad() {
    int x = 42;
    return &x;  // x 所在栈地址，函数返回后这个地址可能被其他函数覆盖
}
int* p = bad();
cout << *p; // 可能输出 42（幸运情况），也可能输出垃圾值或直接崩溃
```
**危害**：解引用野指针导致未定义行为——可能崩溃（段错误）、数据损坏、安全漏洞（use-after-free）。
**预防**：
1. delete 后立即置为 nullptr 
2. 优先使用智能指针 
3. 不返回局部变量的地址或引用
4. 指针定义时立即初始化
5. 编写完程序使用 valgrind，cppcheck，clangd-tidy 等工具检测
> [!Info] 可能的追问:
> - Q: 野指针和空指针的区别？
> - A: 空指针（nullptr）指向安全的已知地址（0），解引用会明确崩溃（容易排查）。野指针指向随机地址，解引用结果是未定义行为，可能不马上崩溃，debug 困难。
> - Q: shared_ptr 有悬空问题吗？
> - A: shared_ptr 本身不会悬空（引用计数归零才释放），但 weak_ptr lock() 可检测对象是否存活，返回空表示对象已释放。

### 结构体中定义了 string 类型，如何 delete？什么是 placement new？
**回答话术：**
关键在于 struct 的分配方式决定释放方式：
- 如果 struct 是通过 `new` 在堆上分配的，用 `delete p;` 自动调用 string 的析构函数释放其内部堆内存
- 如果 struct 是栈上分配的，作用域结束自动调用析构函数
- 如果 struct 是用 malloc 分配的，必须先用 placement new 构造，然后手动调用析构 `p->~A();` 再 free(p)
**什么是 placement new？** placement new 是在**已有的内存上构造对象**，而不是分配新内存。语法是 `new (address) Type(args)`。它不分配内存，只是调用构造函数。常见使用场景：内存池、共享内存上构造对象、自定义内存管理。
```cpp
// placement new 的本质
struct Person { string name; int age; };
// 在 malloc 分配的内存上构造 Person
void* buf = malloc(sizeof(Person));
Person* p = new (buf) Person{"Alice", 20};  // 调用构造函数
// 使用完后手动析构 + 释放
p->~Person();  // 必须手动调析构，释放 string 内部堆内存
free(buf);     // 释放原始内存
```
没有 placement new，malloc 分配的空间只是原始字节，string 不会被构造（内部指针未初始化），使用会崩溃。没有手动调用析构，string 内部的堆内存不会释放，造成内存泄漏。
> [!Info] 可能的追问:
> - Q: malloc 和 new 混用的后果？
> - A: 如果在 malloc 分配的内存上调用了 string 成员，string 的构造函数未执行，内部指针未初始化，使用会崩溃。同样，free 不调用析构函数，string 内部堆内存泄漏。

### pthread_create 传入的函数指针可以是类的成员函数吗？
**回答话术：**
不能直接传入非静态成员函数。因为成员函数有隐式的 this 指针参数，函数签名不匹配 `void* (*)(void*)`。
**解决方案**：
1. 将成员函数声明为 static（没有 this 指针），然后通过 void* 参数传入对象指针
2. 用 lambda 表达式（无捕获 lambda 可转函数指针）配合对象捕获
3. 包装一个外部 C 函数，将对象指针通过 arg 参数传入，调用对象的成员函数
> [!Info] 可能的追问:
> - Q: C++11 的 std::thread 可以吗？
> - A: 可以，std::thread 能接受任何可调用对象（包括成员函数 + 对象指针的 bind 或 lambda），如 `std::thread(&Task::run, &t)`。
> - Q: 为什么 C++ 成员函数不能直接作为线程函数？
> - A: 成员函数隐含 this 参数，调用约定（thiscall vs cdecl）不同，函数指针类型不兼容。

## STL 标准模板库

### STL 有哪些容器？分类介绍一下
**回答话术：**
STL 容器分为三大类：
1. **序列式容器**（Sequential）：vector（动态数组，随机访问快，尾部插入快）、deque（双端队列，头尾插入都快）、list（双向链表，任意位置插入快）、forward_list（单向链表）
2. **关联式容器**（Associative）：set/multiset、map/multimap，底层红黑树，有序，O(log n) 查找
3. **无序关联容器**（Unordered）：unordered_set/map（C++11），底层哈希表，平均 O(1) 查找
4. **容器适配器**：stack、queue、priority_queue，基于底层容器实现
**知识点讲解：**
- 选择原则：需要随机访问用 vector，需要频繁头尾插入用 deque，频繁任意位置插入用 list，查找为主用 unordered_map/set
> [!Info] 可能的追问:
> - Q: map 和 unordered_map 如何选择？
> - A: 需要有序遍历或用范围查询用 map；只需单点查找且对性能敏感用 unordered_map（O(1) vs O(log n)）。
> - Q: 什么时候用 list？
> - A: 需要大量在任意位置插入/删除操作（尤其是中间）。但多数场景 vector + 适当 reserve 表现更好。

### vector 和 list 的区别与线程安全性
**回答话术：**

| 特性 | vector | list |
|------|--------|------|
| 底层 | 动态数组（连续内存） | 双向链表（非连续） |
| 随机访问 | O(1) | O(n) |
| 尾部插入/删除 | O(1) 均摊 | O(1) |
| 中间插入/删除 | O(n)（需移动元素） | O(1)（找到位置后） |
| 内存 | 连续，缓存友好 | 节点分散，缓存不友好 |

**线程安全性**：STL 容器**都不是线程安全的**。多个线程同时读是安全的，一读一写同一容器 → data race，未定义行为。需要加外部锁（mutex）或使用线程安全的替代方案。
**知识点讲解：**
- vector 的扩容机制：capacity 不够时，重新分配 1.5~2 倍新空间，将旧元素 move 或 copy 过去
**vector 扩容时是 move 还是 copy，取决于什么？** 取决于元素类型的移动构造函数是否是 noexcept 的。标准库要求 vector 提供强异常安全保证——如果在扩容过程中移动元素时抛出异常，已部分移动的元素无法恢复到原始状态。所以：
- 如果移动构造是 noexcept → 用 move（高效，O(1) 转移指针）
- 如果移动构造不是 noexcept → 用 copy（安全，拷贝失败原数据还在）
- 类没有移动构造 → 用 copy
这就是为什么容器元素类型的移动操作通常应标记为 noexcept。
```cpp
struct A { A(A&&) noexcept = default; };  // vector 扩容用 move
struct B { B(B&&) {} };                   // 非 noexcept，vector 扩容用 copy！
```
> [!Info] 可能的追问:
> - Q: vector 扩容为什么通常是 1.5 或 2 倍？
> - A: 2 倍是时间最优（分摊 O(1)），但内存浪费多。1.5 倍可复用之前释放的内存块（内存分配更友好）。不同实现选择不同，gcc 是 2 倍，clang 是 2 倍。
> - Q: vector 的 reserve 和 resize 区别？
> - A: reserve 只分配 capacity，不构造元素；resize 改变 size，构造新元素（值初始化）。

### vector 和 deque 的区别
**回答话术：**
- **底层结构**：vector 连续内存；deque 由多个固定大小的缓冲区（buffer）组成，通过中控器（map）管理
- **随机访问**：vector O(1)；deque O(1) 但略慢（需要一次间接索引）
- **头插/头删**：vector O(n)；deque O(1)
- **内存分配**：vector 扩容时需要移动所有元素；deque 只在头部或尾部不足时分配新 buffer，已有元素不动
- **缓存局部性**：vector 最好；deque 中等（每个 buffer 内连续）
> [!Info] 可能的追问:
> - Q: 什么场景应该用 deque 而不是 vector？
> - A: 需要频繁在头部插入/删除时（如双端队列、滑动窗口算法）。另外 queue 的默认底层容器是 deque。
> - Q: deque 的中控器（map）是什么？
> - A: deque 维护一个指针数组（map），每个元素指向一个固定大小的 buffer（通常 512 字节）。访问时先定位到哪个 buffer，再在 buffer 内偏移。

### map 与 unordered_map 的区别与底层实现
**回答话术：**

| 特性     | map            | unordered_map   |
| ------ | -------------- | --------------- |
| 底层     | 红黑树（自平衡二叉搜索树）  | 哈希表（数组+链表+红黑树）  |
| 元素顺序   | 按键升序           | 无序              |
| 查找复杂度  | O(log n)       | 平均 O(1)，最坏 O(n) |
| 插入复杂度  | O(log n)       | 平均 O(1)         |
| 迭代器稳定性 | 插入不失效，删除被删元素失效 | 重哈希时全部失效        |

**选择**：需要有序遍历 → map；追求查找性能 → unordered_map。
**知识点讲解：**
- unordered_map 的哈希冲突解决：**链地址法**（数组 + 链表），C++11 起当链表长度超过 8 一定长度转为红黑树
- unordered_map 的查找方法是:
	1. 哈希计算：通过哈希函数计算目标元素的哈希值，并将其映射到数组的某个桶位置
	2. 桶内查找：如果该桶是链表结构，则遍历链表查找匹配的元素；如果是红黑树结构，则在红黑树中通过**键的比较**进行查找。
- map 的红黑树保证插入/删除/查找都是 O(log n)，不会退化
> [!Info] 可能的追问:
> - Q: unordered_map 的自定义哈希函数怎么写？
> - A: 提供自定义的 hash 模板特化或传函数对象。需保证相同对象产生相同哈希值，不同对象尽量分散。
> - Q: map 基于什么比较规则？
> - A: 默认 `std::less<Key>`，使用 `operator<`。可自定义比较器。
> - Q: unordered_map 的哈希数组大小是如何确定的？
> - A: 创建时通过 `reserver()` 留足，后期通过负载因子触发机制自动调整
> - Q: 两者性能对比如何？
> - A: std::unordered_map：由于需要维护哈希表和桶数组，可能会占用更多内存

### map 和 multimap 的区别
**回答话术：**
- **map**：键唯一。插入已存在的 key 时，`operator[]` 会覆盖，`insert` 会失败（返回 pair<iterator, bool>，bool 表示是否成功）
- **multimap**：允许相同 key 存在多个元素。不提供 `operator[]`（因为 key 不唯一）
```cpp
map<int, string> m;
m.insert({1, "a"}); m.insert({1, "b"}); // 失败，key 1 已存在
multimap<int, string> mm;
mm.insert({1, "a"}); mm.insert({1, "b"}); // 成功，允许重复
auto range = mm.equal_range(1); // 获取所有 key=1 的元素范围
```
> [!Info] 可能的追问:
> - Q: multimap 如何遍历相同 key 的所有元素？
> - A: 用 `lower_bound(key)` 和 `upper_bound(key)` 得到区间，或用 `equal_range(key)` 一次性获取区间。
> - Q: 什么时候用 multimap？
> - A: 需要一对多的映射关系，如"一个客户多个订单号"。

### 哈希冲突的解决方法（链地址法和线性探测）
**回答话术：**
**链地址法（Separate Chaining）**：每个哈希桶维护一个链表（或红黑树），冲突元素挂在链表上。unordered_map 使用此方式。优点是删除简单，元素数量不受表大小限制。缺点是额外指针存储。
**线性探测（Linear Probing）**：发生冲突时，顺序查找下一个空闲桶。优点是数据连续、缓存友好。缺点是容易产生"一次聚集"现象，删除需要惰性标记。
**其他方法**：二次探测（平方探测）、双重哈希。
> [!Info] 可能的追问:
> - Q: 链地址法和线性探测各有什么优劣势？
> - A: 链地址法删除容易、负载因子可大于 1；线性探测缓存友好、但删除复杂（需惰性删除标记），负载因子不宜超 0.7 否则性能急剧下降。unordered_map 用链地址法使它能在高负载因子下保持性能。
> - Q: 加载因子 0.75 的意义？
> - A: 空间和时间折中。低于 0.75 浪费空间（桶太稀疏），高于 0.75 冲突概率增加，性能下降。当元素数超过容量×加载因子时触发 rehash。

### priority_queue 的底层实现
**回答话术：**
priority_queue 是容器适配器，默认底层容器是 vector，使用**二叉堆（binary heap）** 实现，默认是大顶堆（最大元素在堆顶）。插入（push）是 O(log n)，删除堆顶（pop）是 O(log n)，取堆顶（top）是 O(1)。
**知识点讲解：**
二叉堆用数组存储：节点 i 的左子 2i+1，右子 2i+2，父节点 (i-1)/2。push 时元素先放到尾部，然后上浮（percolate up）；pop 时将堆顶与最后一个交换，然后下沉（percolate down）。
> [!Info] 可能的追问:
> - Q: priority_queue 的迭代器在哪里？
> - A: priority_queue 不提供迭代器，不支持遍历。如果需要遍历或修改堆中元素，直接用 `make_heap` / `push_heap` / `pop_heap` 算法函数族，它们在 vector 上操作，可遍历。
> - Q: 堆排序和 priority_queue 有什么关系？
> - A: 堆排序就是利用堆结构进行排序——建堆 O(n)，每次取堆顶 O(log n)，整体 O(n log n)。priority_queue 本质就是堆的封装。

### std::sort 的底层实现
**回答话术：**
std::sort 是**内省排序（IntroSort）**，混合了三种算法：
1. 数据量大时用**快速排序**（三数取中法选 pivot）
2. 递归深度超过 2×log₂(n) 时切换为**堆排序**（防止快排退化到 O(n²)）
3. 分区小到一定程度（通常 16）时用**插入排序**（小规模数据插入排序比快排快，因为缓存友好）
整体时间复杂度 O(n log n)，最坏情况也是 O(n log n)，空间复杂度上，快排方式使用**递归栈**实现，空间复杂度 O(logn)；堆排序和插入排序纯原地操作不递归，空间复杂度为严格的 O(1)

**知识点讲解：**
```cpp
vector<int> v = {4, 2, 5, 1, 3};
sort(v.begin(), v.end());
sort(v.begin(), v.end(), greater<>());
// sort 要求随机访问迭代器，所以 vector/deque 可用，list 不行
```
> [!Info] 可能的追问:
> - Q: 为什么小数据用插入排序？
> - A: 插入排序虽然 O(n²)，但常数极小，对小数组缓存友好。快排等需要递归或交换，开销更重。在 n < 16 时插入排序实测更快。
> - Q: std::stable_sort 的实现？
> - A: stable_sort 保证相等元素的原始顺序不变，底层使用归并排序。当内存够用时 O(n log n)，不够用则退化为 O(n log² n)。

### 哪些操作会导致 vector 迭代器失效？
**回答话术：**
1. **插入/扩容**：扩容时所有迭代器失效（内存重新分配）；插入在中间位置使插入点之后的迭代器失效
2. **删除**：`erase(pos)` 使 pos 及之后的迭代器失效；`erase(begin, end)` 使区间内及之后的所有迭代器失效
3. **赋值/交换**：赋值（`operator=`）和 clear 导致全部失效；`swap` 不失效
**map/unordered_map 的情况：**
- map：插入不失效；删除只失效指向被删元素的迭代器（红黑树节点地址不变）
- unordered_map：插入不失效（除非触发 rehash）；删除只失效被删元素；rehash 时全部失效
**deque 扩容/对中间元素进行操作时**，所有引用和迭代器都会失效
**知识点讲解：**
```cpp
vector<int> v = {1, 2, 3, 4, 5};
for (auto it = v.begin(); it != v.end();) {
    if (*it % 2 == 0) it = v.erase(it);  // erase 返回下一个有效迭代器
    else ++it;
}
```
> [!Info] 可能的追问:
> - Q: deque 的迭代器失效情况？
> - A: 在中间 insert/erase 使所有迭代器失效；两端操作（push_front/push_back/pop_front/pop_back）只影响被操作端的迭代器。
> - Q: list 的迭代器失效情况？
> - A: list 的 insert/erase 只使被操作元素的迭代器失效，其他迭代器不受影响（因为节点本身地址不变）。这是链表结构的优势。
> - Q: map/set 的迭代器失效情况？
> - A: 插入不影响任何现有迭代器（红黑树不 rebalance）；删除只使被删元素的迭代器失效。

### erase 和 remove 删除元素
**回答话术：**
`std::remove` 并不真正删除元素，而是将"要删除的元素"移到容器末尾，并返回新逻辑结尾的迭代器。真正的删除需要配合 erase，即**erase-remove 惯用法**。直接调用容器的 erase 成员函数可以删除元素（如 v.erase(it)），但 vector 的 erase 是 O(n) 的（需要移动后续元素）。
```cpp
vector<int> v = {1, 2, 3, 2, 4, 2};
auto new_end = std::remove(v.begin(), v.end(), 2);
v.erase(new_end, v.end());  // 一行写：v.erase(std::remove(...), v.end());
```
**直接调用 erase 和 erase-remove 的区别**：
- 如果只删一个或几个元素：直接 `erase(it)` 可以，但每次 O(n)，且需要循环中小心更新迭代器
- 如果批量删除符合某个条件的元素：erase-remove 惯用法更高效——remove 做 O(n) 的移动，erase 做 O(k) 的删除（其中 k 是容器末尾的无效元素数量）
- list 有独立成员函数 `list::remove`，直接删除（不需要 erase-remove 惯用法）
> [!Info] 可能的追问:
> - Q: 为什么 remove 不直接删除？
> - A: remove 是算法，只操作迭代器范围，不知道底层容器类型。它只做"移动"工作，释放内存由容器自己负责。这样同一算法可用于 vector、deque 等容器。
> - Q: list 有自己的 remove 为什么还要 erase-remove？
> - A: list::remove 是专门优化的（直接遍历链表节点删除），O(n) 且效率更高。对 list 用 erase-remove 会导致元素反复移动，效率低。

## 操作系统

### 进程和线程的区别
**回答话术：**
**进程**是资源分配的基本单位，有独立的地址空间（代码段、数据段、堆栈），进程间相互隔离。**线程**是 CPU 调度的基本单位，同一进程内的线程共享地址空间和资源，每个线程有独立的栈和寄存器上下文。

| 对比 | 进程 | 线程 |
|------|------|------|
| 地址空间 | 独立 | 共享 |
| 资源开销 | 大（创建需分配独立空间） | 小（共享进程资源） |
| 切换代价 | 大（TLB 刷新等） | 小 |
| 通信 | 需要 IPC（pipe/shared memory/socket） | 直接读写共享变量 |
| 健壮性 | 一个进程崩溃不影响其他 | 一个线程崩溃可能导致整个进程退出 |

**知识点讲解：**
- Linux 里线程是一类特殊的进程（轻量级进程 LWP），通过 clone() 系统调用创建，共享地址空间
- 线程私有：线程栈、寄存器、errno、信号屏蔽字；线程共享：堆、全局变量、文件描述符
> [!Info] 可能的追问:
> - Q: 协程和线程的区别？
> - A: 协程是用户态调度，切换不涉及系统调用，成本极低（纳秒级）。协程是协作式调度，线程是抢占式调度。一个线程内可运行多个协程。

### 线程间同步方式有哪些？
**回答话术：**
1. **互斥锁（Mutex）**：保护临界区，一次只有一个线程访问共享资源
2. **读写锁（RWLock）**：读读不互斥，读写/写写互斥，适合读多写少场景
3. **条件变量（Condition Variable）**：与 mutex 配合，线程等待某个条件满足才继续执行，避免忙等
4. **信号量（Semaphore）**：控制对资源的访问数量（计数），可用于生产者-消费者模型
5. **自旋锁（SpinLock）**：忙等（不阻塞，循环检查），适合锁持有时间极短的场景
6. **屏障（Barrier）**：等待所有线程到达某点后继续
7. **原子操作（Atomic）**：无需锁的线程安全操作，通过 CPU 指令保证
> [!Info] 可能的追问:
> - Q: 互斥锁和信号量的区别？
> - A: 互斥锁是"锁"语义（谁拥有谁释放，同一时刻一个线程持有），信号量是"计数"语义（允许多个线程同时访问最多 N 个资源）。
> - Q: 自旋锁和互斥锁如何选择？
> - A: 锁持有时间短（几微秒内）且不阻塞→自旋锁；锁持有时间长或可能被阻塞→互斥锁。

### 多线程间哪些资源是共享的，哪些是私有的？
**回答话术：**
**共享**（同一进程下的线程间）：堆内存（new/malloc 分配的空间）、全局变量和静态变量、文件描述符、信号处理函数、进程的当前工作目录等。
**私有**：线程栈（局部变量、函数调用链）、寄存器值（包括程序计数器 PC、栈指针 SP）、线程 ID（tid）、errno（每个线程独立）、信号屏蔽字。
**线程栈的详细说明**：
- **栈的大小**：Linux 下默认 8MB（可通过 `ulimit -s` 查看）或通过 pthread_attr_setstacksize 设置。这个值是固定的——不能在运行时动态增长
- **栈在地址中的位置**：每个线程的栈在进程地址空间的 mmap 区域中分配（非主线程的栈）。主线程的栈在地址空间顶部（高地址），由内核在进程创建时分配。子线程的栈通过 mmap 在堆和栈之间的区域映射，是固定的虚拟地址范围
- **每个线程是否享有独立的堆空间？** 不——**所有线程共享同一个进程的堆**。线程 new/malloc 的内存都在同一个堆上，所以多线程并发 malloc 需要加锁（这就是为什么高并发场景需要 tcmalloc/jemalloc 这类线程级缓存分配器）
```cpp
void thread_func() {
    int local_var = 42;          // 在线程自己的栈上
    int* heap_var = new int(10); // 在共享的堆上，其他线程也可访问
}
```
> [!Info] 可能的追问:
> - Q: 栈上变量能否被其他线程访问？
> - A: 一般不能，因为其他线程不知道栈地址。但如果将栈上变量的地址传递给其他线程（通过指针），则理论上可以访问——这是危险的做法，可能导致栈上的变量被访问时已经失效。
> - Q: 如果创建太多线程，栈空间会耗尽吗？
> - A: 会。每个线程 8MB 栈，1000 个线程就占用了约 8GB 虚拟地址空间。创建大量线程时要考虑这个开销。可以通过设置更小的栈大小（pthread_attr_setstacksize）来减少。

### 死锁的四个必要条件
**回答话术：**
死锁产生的四个必要条件（缺一不可）：
1. **互斥**：资源一次只能被一个线程占用
2. **请求与保持**：线程持有至少一个资源的同时，请求其他被占用的资源
3. **不可剥夺**：已分配的资源不能被强制剥夺，只能由持有者主动释放
4. **循环等待**：多个线程形成环形链，每个持有一个资源并等待下一个的资源
> [!Info] 可能的追问:
> - Q: 锁顺序死锁和资源死锁的区别？
> - A: 锁顺序死锁是两线程以不同顺序申请相同锁；资源死锁是两个线程各自持有对方需要的资源。

### 如何避免死锁？开发中的原则和规范
**回答话术：**
架构设计阶段能做的
1. 固定锁顺序——所有线程按相同顺序获取锁 
2. 分层锁——对锁编号，只允许按编号递增顺序获取 
3. 超时回退——使用 try_lock 加超时，获取失败时释放已有锁并重试
编程阶段能做的: 
4. 尽量减少锁的范围和持有时间 
5. 避免在持锁时调用用户代码（回调、虚函数），防止 unknow 代码拿其他锁 
6. 使用高 C++标准的锁包装器，如果用 pthread 库实现锁要自己封装一层 RAII 包装器
7. 使用线程安全分析工具：helgrind/ThreadSanitizer
review 阶段能做的
8. 持有锁的代码块作用域内不使用回调代码，回调代码实现体内不使用持有锁，参考 [[Sylar Backend Collection#两段式读写锁设计]]
> [!Info] 可能的追问:
> - Q: 银行家算法是什么？
> - A: 死锁避免算法。每个新请求到达时检查分配后系统是否处于安全状态（是否存在安全序列）。如果是才分配，否则等待。但实际系统中很少用，因为需要知道最大需求量等信息。
> - Q: 如何排查死锁？
> - A: Linux 下 gdb attach 到进程，`thread apply all bt` 查看各线程栈，看卡在哪个锁上。或用 helgrind（Valgrind 工具）、ThreadSanitizer（gcc -fsanitize=thread）。

### 进程切换和 CPU 调度
**回答话术：**
**进程切换（上下文切换）**：CPU 从一个进程切换到另一个进程的过程——保存当前进程的寄存器、PC、栈指针等上下文，恢复目标进程的上下文。成本较高（微秒级），因为需要清空 TLB、切换页表等。
**CPU 调度算法**：FCFS（先来先服务）、SJF（短作业优先）、时间片轮转（RR）、多级反馈队列（Linux 实际使用）、完全公平调度（CFS，Linux 默认，基于 vruntime）。
> [!Info] 可能的追问:
> - Q: 上下文切换的成本具体来自哪里？
> - A: 主要是 TLB 刷新（编译器 10~100μs）、缓存污染、页表切换、内核态切换开销。
> - Q: Linux 下如何查看上下文切换频率？
> - A: `vmstat 1` 看 cs（context switch）列，或 `pidstat -w` 查看每个进程。

### 虚拟内存解决了什么问题？
**回答话术：**
虚拟内存是操作系统提供的一种内存管理机制，为每个进程提供独立的虚拟地址空间，通过 MMU（内存管理单元）映射到物理内存。解决的核心问题：
1. **隔离保护**：进程间地址空间互不干扰
2. **地址空间连续**：即使物理内存碎片化，虚拟地址空间对进程也是连续的
3. **超越物理内存**：通过页面置换，可以运行比物理内存更大的程序
4. **简化内存管理**：每个进程"认为"自己独占完整地址空间，加载地址可固定
> [!Info] 可能的追问:
> - Q: 栈和堆在虚拟内存中的位置？
> - A: 栈在高地址向下增长，堆在低地址向上增长。从低到高：代码段 → 数据段 → BSS → 堆 → 内存映射区 → 栈 → 内核空间。栈大小通常有限（Linux 默认 8MB）。
> - Q: 页表太大怎么办？
> - A: 使用多级页表（x86-64 使用 4 级页表），只映射实际使用的虚拟地址段，节省内存。

### 局部性原理
**回答话术：**
局部性原理包含两种：
- **时间局部性**：刚访问过的数据很可能很快再次被访问（如循环中的变量）。CPU 利用缓存（L1/L2/L3 cache）利用这一特性
- **空间局部性**：访问某个地址后，其附近的地址很可能也会被访问（如数组遍历）。CPU 通过缓存行（cache line，通常 64 字节）预取相邻数据
**在编程中的体现**：数组按行遍历比按列遍历快（空间局部性好）、结构体将经常一起访问的字段放一起、循环体尽可能小（代码的局部性）。
> [!Info] 可能的追问:
> - Q: 如何写缓存友好的代码？
> - A: 1) 连续内存遍历（vector 比 list 好）2) 按内存顺序访问（行优先 vs 列优先）3) 结构体对齐避免 padding 浪费 4) 减少间接跳转（虚函数、函数指针）
> - Q: cache line 失效的后果？
> - A: 如果数据结构是链表（节点分散），遍历时每次访问都可能是 cache miss，延迟从约 1ns（L1）变为约 60ns（内存），差两个数量级。

### 共享内存的原理及同步机制
**回答话术：**
共享内存是最高效的 IPC 方式——两个或多个进程共享同一块物理内存，数据写入立即被其他进程看到，不需要内核拷贝。
**实现方式**：POSIX 共享内存（shm_open + mmap）、System V 共享内存（shmget + shmat）
**同步机制**：共享内存本身不提供同步，需要配合信号量（最常用）、进程共享互斥锁（pthread_mutexattr_setpshared）、文件锁。
> [!Info] 可能的追问:
> - Q: 共享内存和 mmap 的关系？
> - A: mmap 可以将文件或匿名区域映射到进程地址空间。共享内存本质上是 mmap 的 MAP_SHARED + /dev/shm 下的临时文件。二者底层都是通过页表映射到同一物理页。
> - Q: 共享内存适合什么场景？
> - A: 大数据量传输、高频读写场景（如数据库缓存、消息中间件）。不适合小数据或低频通信（同步开销占比高）。

### 池化技术了解吗？（线程池、内存池、数据库连接池）
**回答话术：**
池化技术的核心思想是**复用**——提前创建一批资源放在池中，需要时从池中取，用完归还，避免频繁创建/销毁的开销。
**线程池**：提前创建 N 个线程，任务队列存放待执行任务。核心参数：核心线程数、最大线程数、任务队列容量、拒绝策略。
**内存池**：预分配大块内存，切分成固定大小块管理，避免频繁 malloc/free 和内存碎片。
**数据库连接池**：维护多个数据库连接，业务代码从池中获取连接而不是新建，避免 TCP 三次握手 + 鉴权的开销。
> [!Info] 可能的追问:
> - Q: 线程池的核心线程数和最大线程数怎么设？
> - A: CPU 密集型：核心线程数 = CPU 核数 + 1；IO 密集型：可更大（核数 × [1 + IO_time/CPU_time]）。最大线程数考虑系统上限（一般在几百到几千）。
> - Q: 线程池中任务队列满了怎么办（拒绝策略）？
> - A: 常见的：1) 抛异常 2) 由提交线程自己执行 3) 丢弃最老的任务 4) 直接丢弃新任务。

### 进程同步的方式有哪些？
**回答话术：**
进程间同步与线程间同步类似，但需要多进程间共享的机制：
1. **信号量（Semaphore）**：最常用，可以用于互斥和同步
2. **文件锁（flock/fcntl）**：通过加锁文件实现互斥
3. **互斥锁（进程共享属性）**：设置 PTHREAD_PROCESS_SHARED 属性
4. **条件变量（进程共享属性）**：配合互斥锁
5. **信号（Signal）**：用于异步通知
> [!Info] 可能的追问:
> - Q: 进程信号量和线程信号量有什么区别？
> - A: 进程信号量在共享内存中创建，对所有进程可见。线程信号量在线程间共享。用法上，进程信号量初始化时需要指定 pshared 为非 0。

## 计算机网络

### 计算机网络五层模型及对应协议
**回答话术：**

| 层次 | 功能 | 典型协议 |
|------|------|----------|
| **应用层** | 为用户应用提供网络服务 | HTTP、HTTPS、FTP、SMTP、DNS、WebSocket |
| **传输层** | 端到端通信、可靠传输 | TCP、UDP |
| **网络层** | 路由选择、分组转发、IP 寻址 | IP、ICMP、ARP、RIP、OSPF |
| **数据链路层** | 帧封装、介质访问控制（MAC） | Ethernet、PPP、VLAN |
| **物理层** | 比特流传输（电压、光信号） | 双绞线、光纤、无线电 |

数据封装过程：应用数据 → 传输层加 TCP/UDP 头部 → 网络层加 IP 头部 → 链路层加 MAC 头部 → 物理层发送
> [!Info] 可能的追问:
> - Q: ARP 协议在哪一层？
> - A: 工作在网络层和链路层之间，用于将 IP 地址解析为 MAC 地址。通常归为链路层协议。
> - Q: ICMP 协议的作用？
> - A: 用于传递网络层控制信息和差错报告（如 ping 命令用的就是 ICMP echo request/reply）。

### TCP 和 UDP 的区别
**回答话术：**

| 特性   | TCP            | UDP               |
| ---- | -------------- | ----------------- |
| 连接   | 面向连接（三次握手）     | 无连接               |
| 可靠性  | 可靠传输（确认重传、序号）  | 不可靠，尽力而为          |
| 有序   | 保证数据按序到达       | 不保证               |
| 速度   | 较慢（有拥塞控制、流量控制） | 快（无控制机制）          |
| 头部开销 | 20~60 字节       | 8 字节              |
| 应用场景 | HTTP、FTP、SMTP  | DNS、视频流、在线游戏、VoIP |

> [!Info] 可能的追问:
> - Q: UDP 能否实现可靠性？
> - A: 可以。在应用层实现确认重传、序号、流量控制等机制（如 QUIC 协议基于 UDP 实现了类似 TCP 的可靠传输，且解决了 TCP 队头阻塞问题）。

### TCP 如何保证可靠性？
**回答话术：**
TCP 通过以下机制保证可靠性：
1. **确认应答（ACK）**：接收方收到数据后回复 ACK
2. **超时重传**：发送方启动定时器，超时未收到 ACK 则重传
3. **序列号**：每个字节有序列号，接收方按序列号重组数据，去重
4. **流量控制**：通过滑动窗口机制，接收方告知发送方自己的接受能力（窗口大小），防止发送过快
5. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复，控制网络中的总数据量
6. **校验和**：检测数据损坏，损坏则丢弃（不回复 ACK 触发重传）
> [!Info] 可能的追问:
> - Q: 超时重传的 RTO 是怎么计算的？
> - A: 根据 RTT（往返时间）动态计算。RFC 推荐 RTO = SRTT + 4×RTTVAR，其中 SRTT 是平滑 RTT，RTTVAR 是 RTT 的偏差。
> - Q: 快重传和超时重传的区别？
> - A: 快重传是收到三个冗余 ACK 后立即重传，不等超时。超时重传说明丢包严重，还会降低发送速度（进入慢启动）。

### TCP 三次握手
**回答话术：**
建立 TCP 连接需要三次握手：
```
1. 客户端 → SYN=1, seq=x              // 客户端进入 SYN_SENT
2. 服务端 → SYN=1, ACK=1, seq=y, ack=x+1  // 服务端进入 SYN_RCVD
3. 客户端 → ACK=1, seq=x+1, ack=y+1        // 双方进入 ESTABLISHED
```
为什么不是两次：防止已失效的连接请求到达服务器。两次握手时，客户端第一次 SYN 滞留后到达，服务器以为有新连接而建立连接并等待数据，浪费资源。
> [!Info] 可能的追问:
> - Q: 为什么不是四次？
> - A: 三次够了。第二次握手同时发送 SYN 和 ACK，合并在同一报文。四次没有额外收益。
> - Q: SYN Flood 攻击是什么？
> - A: 恶意客户端只发 SYN 不发第三次 ACK，占用服务器资源。防范：SYN Cookie（收到 SYN 先不分配资源，通过报文计算 cookie 作为序列号回复，收到 ACK 验证后再分配）。

### TCP 四次挥手
**回答话术：**
断开连接需要四次挥手：
```
1. 主动方 → FIN=1, seq=u       // 主动方进入 FIN_WAIT_1
2. 被动方 → ACK=1, seq=v, ack=u+1  // 被动方进入 CLOSE_WAIT，主动方进入 FIN_WAIT_2
3. 被动方 → FIN=1, seq=w, ack=u+1  // 被动方进入 LAST_ACK
4. 主动方 → ACK=1, seq=u+1, ack=w+1 // 主动方进入 TIME_WAIT（等待 2MSL 后关闭）
```
为什么 TIME_WAIT 等待 2MSL：保证最后一个 ACK 到达对端。如果 ACK 丢失，对端会重发 FIN，TIME_WAIT 状态能处理这种重传。2MSL 是保证一来一回的最大时间。
> [!Info] 可能的追问:
> - Q: 服务端出现大量 CLOSE_WAIT 的原因？
> - A: 被动关闭方收到 FIN 后回复了 ACK，但应用程序没有调用 close()（未关闭 socket）。通常是编程 Bug——read() 返回 0（EOF）后没有正确处理，没有调用 close()。
> - Q: TIME_WAIT 过多的影响？
> - A: 占用端口资源（一个四元组不能复用），可能导致客户端无法建立新连接。解决方案：SO_REUSEADDR 选项允许重用 TIME_WAIT 的地址。

### TCP 流量控制和拥塞控制
**回答话术：**
**流量控制**：端到端的机制，防止发送方过快淹没收方。通过**滑动窗口**实现——接收方在 ACK 中通告自己的可用窗口大小（rwnd）。
**拥塞控制**：全局的网络状态控制，防止发送数据过多导致网络过载。通过**拥塞窗口（cwnd）** 实现，实际发送窗口 = min(rwnd, cwnd)。四个阶段：
1. **慢启动**：cwnd 从 1MSS 开始，每收到一个 ACK 翻倍（指数增长），直到 ssthresh
2. **拥塞避免**：超过 ssthresh 后线性增长（每 RTT + 1MSS），直到发生丢包
3. **快重传**：收到 3 个冗余 ACK 即重传，不等超时
4. **快恢复**：快重传后，cwnd 减半 + 3MSS，进入拥塞避免（而不是回到慢启动）
> [!Info] 可能的追问:
> - Q: 什么是 TCP 的队头阻塞（HOL blocking）？
> - A: TCP 保证数据按序到达，如果某个包丢失，后面已到的包必须等待重传完成后才能交给应用层。HTTP/2 的多路复用也会因此被阻塞。这也是 QUIC（基于 UDP）要解决的问题——采用多流设计，一条流丢包不影响其他流。

### HTTP 长连接与短连接的适用场景
**回答话术：**
- **短连接**：每次请求都新建 TCP 连接，完成后关闭。HTTP/1.0 默认。适合请求频率低的场景。
- **长连接（Keep-Alive）**：复用同一个 TCP 连接发送多个 HTTP 请求/响应。HTTP/1.1 默认。适合请求密集、高频交互的场景。
**选择依据**：请求频率高、连接复用率高 → 长连接；低频请求 → 短连接更简单。
> [!Info] 可能的追问:
> - Q: HTTP/2 的连接复用比 HTTP/1.1 长连接强在哪？
> - A: HTTP/1.1 长连接请求仍是串行的（Pipelining 有队头阻塞问题）。HTTP/2 真正多路复用——单一 TCP 上可并行传输多个流（Stream），避免应用层队头阻塞。
> - Q: WebSocket 和 HTTP 长连接的关系？
> - A: WebSocket 也建立在 TCP 上，但通过 HTTP 升级（Upgrade 头部）建立双向通信。HTTP 长连接仍是"请求-响应"模式，WebSocket 是全双工实时通信。

### HTTP 和 HTTPS 的区别
**回答话术：**

| 对比 | HTTP | HTTPS |
|------|------|-------|
| 协议 | HTTP | HTTP + TLS/SSL |
| 端口 | 80 | 443 |
| 安全性 | 明文传输 | 加密通信 |
| 认证 | 无 | 数字证书验证服务器身份 |
| 性能 | 快（无加密计算） | 慢（有握手和加密开销） |

HTTPS 流程：客户端发起 HTTPS 请求 → 服务器返回数字证书（含公钥）→ 客户端验证证书 → 生成对称密钥并用公钥加密发送给服务器 → 双方用对称密钥加密通信。
> [!Info] 可能的追问:
> - Q: TLS 握手过程？
> - A: 1) ClientHello（支持的密码套件）2) ServerHello（选定的套件）+ 证书 3) 客户端验证证书，生成预主密钥，用公钥加密发送 4) 双方计算会话密钥 5) Finished 验证（整个过程需要 1 RTT 或 0-RTT 重连）。

### Socket 编程的步骤
**回答话术：**
**TCP 服务端**：`socket() → bind() → listen() → accept() → recv()/send() → close()`
**TCP 客户端**：`socket() → connect() → send()/recv() → close()`
**关键函数**：
- socket()：创建套接字，指定协议族（AF_INET）、类型（SOCK_STREAM/DGRAM）
- bind()：绑定地址和端口
- listen()：将套接字设为监听模式，指定 backlog（最大等待连接数）
- accept()：接受客户端连接，返回新的连接 socket（阻塞的）
- connect()：客户端发起连接
> [!Info] 可能的追问:
> - Q: listen 的 backlog 参数有什么用？
> - A: 表示已完成三次握手但还未被 accept 的连接（ESTABLISHED 状态）队列的最大长度。超过这个长度，新连接会被拒绝。Linux 中实际值受 somaxconn 限制。
> - Q: TCP socket 的 send/recv 缓存是什么？
> - A: 内核维护发送缓冲区和接收缓冲区。send 将数据写入发送缓冲区就返回（实际由内核 TCP 协议栈发出去）；recv 从接收缓冲区读数据。

### select 和 epoll 的区别
**回答话术：**

| 对比      | select              | epoll                                      |
| ------- | ------------------- | ------------------------------------------ |
| 底层      | 轮询（遍历 fd_set）       | 事件驱动（回调机制）                                 |
| 效率      | O(n)，监听越多越慢         | O(1)，只返回就绪的 fd                             |
| fd 数量上限 | FD_SETSIZE（默认 1024） | 无上限（受系统限制）                                 |
| 触发模式    | 水平触发（LT）            | LT 和 ET（边缘触发）均可                            |
| 工作方式    | 每次传入全部 fd_set，内核修改  | epoll_create 创建，epoll_ctl 注册，epoll_wait 等待 |

**epoll 模式**：
- LT（水平触发）：只要 fd 有数据可读，epoll_wait 就返回。编程简单
- ET（边缘触发）：只有状态变化时才通知。必须非阻塞 IO + 循环读取，效率高
> [!Info] 可能的追问:
> - Q: epoll 效率一定比 select 高吗？
> - A: 不一定。连接数少（几十以内）且活跃 fd 多时，select 反而可能更快，因为 epoll 需要系统调用来注册/修改 fd（epoll_ctl），多了一次系统调用开销。epoll 的优势在大规模连接。
> - Q: 边缘触发模式下为什么需要非阻塞 IO + 循环读？
> - A: ET 只在状态变化时通知一次，必须一次把数据读完（循环 recv 直到 EAGAIN）。如果用阻塞读，最后一次会阻塞。

### select/poll/epoll 对比
**回答话术：**

| 特性 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | fd_set（位图） | pollfd 数组 | 红黑树 + 就绪链表 |
| 时间复杂度 | O(n) | O(n) | O(1) |
| 最大 fd 数 | 1024 | 无限制 | 无限制 |
| 遍历 | 每次传全部 fd | 每次传全部 fd | 注册后内核维护，只取就绪 |
| 工作模式 | 仅 LT | 仅 LT | LT + ET |
| 系统调用 | 每次 select 拷贝 | 每次 poll 拷贝 | 注册 ctl，wait 不用拷贝 |

**选择建议**：少量（<100）活跃连接 → select/poll 足够；大量（>1000）空闲连接 → epoll 优势巨大。
> [!Info] 可能的追问:
> - Q: epoll 的就绪链表是内核维护的吗？
> - A: 是的。当 fd 有事件时，内核通过回调函数将 fd 加入就绪链表。epoll_wait 只需将就绪链表拷贝到用户空间。

### 网络 I/O 模型的类型
**回答话术：**
UNIX 有五种 I/O 模型：
1. **阻塞 I/O**：recv/read 一直等待直到数据就绪。最直接，但线程被挂起
2. **非阻塞 I/O**：立即返回 EAGAIN，需要不断轮询。浪费 CPU
3. **I/O 多路复用**：select/epoll 一个线程等待多个 fd。高并发基础
4. **信号驱动 I/O**：数据就绪时发 SIGIO 信号通知。较少使用
5. **异步 I/O（AIO）**：发起操作后立刻返回，内核完成所有操作后通知。真正异步
**同步 vs 异步区分**：1~4 都是同步 I/O（数据从内核拷贝到用户空间的过程需要等待），只有 AIO 是真正的异步 I/O。
> [!Info] 可能的追问:
> - Q: Reactor 和 Proactor 模式的区别？
> - A: Reactor 基于同步 I/O 多路复用（事件循环告知哪个 fd 就绪，用户代码自行读写）；Proactor 基于异步 I/O（内核完成读写后通知）。Reactor 实现简单，Linux 下常用。Proactor 需要操作系统支持的真正异步 I/O，Windows 的 IOCP 是典型实现。

### Reactor 模型
**回答话术：**
Reactor 模式是高性能网络服务器的核心设计模式，基于 I/O 多路复用 + 事件驱动。其工作流程：
1. **事件分发器（Event Demultiplexer）**：通过 epoll/select 等待 I/O 事件
2. **事件处理器（Event Handler）**：处理特定 I/O 事件（读、写、连接等）
3. **Reactor**：注册事件处理器，循环调用事件分发器获取事件，分发到对应处理器
**典型实现层次**：单 Reactor + 单线程（Redis）、单 Reactor + 工作线程池、主从 Reactor + 线程池（Netty、Nginx）
> [!Info] 可能的追问:
> - Q: 你在项目中实现的 Reactor 是怎么设计的？
> - A: 创建了一个事件循环 EventLoop，内部封装 epoll。Channel 类封装 fd 和事件回调。EventLoop 循环 poll，返回就绪的 Channel 并调用对应的读/写/错误回调。

### Unix 域套接字
**回答话术：**
Unix 域套接字（Unix Domain Socket, UDS）是本机 IPC 方式，地址绑定到文件系统路径而不是 IP 端口。
**特点：** 只用于同机进程间通信、比 TCP localhost 快 30%~50%（跳过网络协议栈）、有流式（SOCK_STREAM）和数据报（SOCK_DGRAM）两种模式、本地数据报是可靠的。
**使用原因**：性能好（不需要经过 TCP/IP 协议栈），安全性高（文件权限控制）。常用于数据库连接（MySQL、PostgreSQL 支持）、Nginx 等。
> [!Info] 可能的追问:
> - Q: Unix 域套接字和共享内存的读写性能对比？
> - A: 共享内存更快（零拷贝），但同步复杂。Unix 域套接字也很快（有内核缓冲区管理，数据基本在内核内部传递）。小数据 UDS 方便，大数据共享内存更优。
> - Q: 用 TCP 回环地址（127.0.0.1）和 Unix 域套接字的性能差距？
> - A: Unix 域套接字快 30%~50%，因为它不走 TCP 协议栈（没有校验和计算、分片、拥塞控制等）。

### 浏览器获取页面的整个过程
**回答话术：**
1. **DNS 解析**：浏览器缓存 → 系统 hosts → 本地 DNS 服务器 → 根/顶级/权威 DNS 服务器，获取 IP
2. **TCP 连接**：与服务器建立 TCP 连接（三次握手）
3. **TLS 握手**（HTTPS）：协商加密参数，验证证书（额外 1~2 RTT）
4. **发送 HTTP 请求**：构造请求行（GET/POST）、请求头（Cookie、User-Agent）、请求体
5. **服务器处理并响应**：返回状态码（200/304/404）、响应头、响应体
6. **解析 + 渲染**：浏览器解析 HTML 构建 DOM 树 → 解析 CSS 构建 CSSOM 树 → 合并成渲染树 → Layout → Paint
7. **TCP 断开**（如果是短连接则四次挥手）
> [!Info] 可能的追问:
> - Q: 输入 URL 后回车，到开始 DNS 解析之间发生了什么？
> - A: 浏览器先检查 HSTS 列表（强制 HTTPS）、检查 URL 格式（补全协议头）、检查是否有缓存（强缓存命中则直接使用本地缓存不发请求）。
> - Q: 如果返回 304 表示什么？
> - A: 资源未修改（Not Modified），客户端缓存有效，使用本地缓存的版本。这是协商缓存的响应。

## 数据结构与算法

### 快速排序的思想、复杂度和为什么比归并好
**回答话术：**
**思想**：分治法。选一个 pivot，将数组分成两部分——小于 pivot 的放左边，大于的放右边。然后递归对左右两部分排序。
**复杂度**：平均 O(n log n)，最坏 O(n²)（每次 pivot 恰好是最大/最小）。空间复杂度 O(log n)（递归栈）。
**为什么比归并更常用**：原地排序（不需要额外 O(n) 空间）、缓存友好（数据访问连续）、实际常数小、平均性能优于归并排序。
> [!Info] 可能的追问:
> - Q: 如何避免快排退化到 O(n²)？
> - A: 三数取中法选 pivot（首、中、尾三数的中位数）；随机选 pivot；当递归深度超过阈值时切换到堆排序（IntroSort——std::sort 的策略）。
> - Q: 最坏情况的场景？
> - A: 每次 pivot 都选到最大/最小元素。比如有序数组 + 总是选第一个元素作为 pivot。

### 堆排序实现原理和复杂度
**回答话术：**
**原理**：
1. 建堆——从最后一个非叶子节点开始，逐个下沉，构建大顶堆（O(n)）
2. 排序——取出堆顶与最后一个元素交换，堆大小减 1，然后对堆顶下沉调整（O(log n)），重复直到堆为空。
**复杂度**：时间 O(n log n)，空间 O(1)（原地排序）。不稳定。
> [!Info] 可能的追问:
> - Q: 建堆的复杂度为什么是 O(n) 不是 O(n log n)？
> - A: 因为是从最后一个非叶子节点开始下沉，不是每个节点都从根下沉。高层节点少但下沉路径长，低层节点多但下沉路径短。数学证明总操作次数 ≤ 2n = O(n)。
> - Q: 堆排序为什么不稳定？
> - A: 堆排序在交换堆顶和末尾元素时，可能改变相等元素的相对顺序。

### 红黑树的实现原理、结构特征和查询复杂度
**回答话术：**
**红黑树**是自平衡二叉搜索树，每个节点增加一个颜色属性（红/黑）。AVL 树平衡要求更严格，红黑树是"近似平衡"。
**五条性质**：
1. 每个节点是红色或黑色 
2. 根是黑色 
3. 叶子节点（NIL）是黑色 
4. 红色节点的两个子节点都是黑色（没有两个连续的红色节点）
5. 任意节点到其所有叶子节点的路径上，黑色节点数量相同
**查询时间复杂度**：O(log n)，且保持稳定不会退化。
> [!Info] 可能的追问:
> - Q: 红黑树和 AVL 树的区别？
> - A: AVL 树平衡要求更严格（左右子树高度差 ≤ 1），所以查询更快，但插入/删除的旋转代价更高。红黑树牺牲了部分平衡性换取更少的旋转操作，在需要频繁插入/删除的场景更适合。
> - Q: 为什么 map 用红黑树而不是 AVL 树？
> - A: map 要同时支持插入、删除、查找。红黑树在这三者之间取得了更好的平衡，旋转次数更少（均摊 O(1) 次旋转）。

### 跳表（Skip List）的查询时间复杂度
**回答话术：**
跳表是一种多层级的链表结构。最底层是有序链表，上层是"索引层"，每个节点以概率 p（通常 1/2）出现在更高层。
**查找时间复杂度**：平均 O(log n)，最坏 O(n)。通过从最高层开始查找，快速跳过大量节点。
**与红黑树的对比**：

| 对比 | 红黑树 | 跳表 |
|------|--------|------|
| 查询 | O(log n) | O(log n) 平均 |
| 实现复杂度 | 复杂（旋转/变色） | 简单 |
| 范围查询 | 中序遍历 | 在底层链表中直接遍历 |
| 并发 | 难 | 易（锁分裂） |
| 空间 | O(n)（2 个指针 + 颜色） | O(n log n) 期望（多层指针） |

**应用**：Redis 的 sorted set（zset）底层使用了跳表（不是红黑树）。
> [!Info] 可能的追问:
> - Q: Redis 为什么用跳表而不红黑树？
> - A: 1) zset 需要范围查询（ZRANGE），跳表在底层链表中向前/向后遍历即可，红黑树需要中序遍历 2) 跳表实现更简单，出 bug 概率小 3) 跳表在并发场景下更容易加锁分段。
> - Q: 跳表的最坏查找是如何发生的？
> - A: 如果所有节点都没晋升到上层（概率极小，随数据量增大概率趋近 0），跳表退化为单链表，查找 O(n)。

### 哈希表及影响性能的参数
**回答话术：**
哈希表通过哈希函数将 key 映射到数组下标，实现 O(1) 平均查找。
**影响性能的两个参数**：
1. **初始容量**：桶数组的初始大小。太小导致频繁 rehash，太大浪费内存
2. **加载因子（负载因子）**：`元素个数 / 桶个数`。超过此阈值触发 rehash（扩容）。典型 0.75——空间和时间的折中。
> [!Info] 可能的追问:
> - Q: 为什么加载因子选 0.75？
> - A: 数学推导+实践经验。泊松分布下，当负载因子为 0.75 时，一个桶中冲突元素超过 8 个的概率极低（约 0.00000006）。
> - Q: rehash 过程是怎么样的？
> - A: 创建新桶数组（通常 2 倍扩容），重新计算每个元素的哈希并放入新桶。这个过程是 O(n) 且消耗大量 CPU。对延迟敏感的场景可采用渐进式 rehash（如 Redis 的 rehash 在每次操作时逐步迁移）。

### 链表判环（快慢指针）
**回答话术：**
**Floyd 判环算法（快慢指针）**：两个指针从头开始，快指针每次走两步，慢指针每次走一步。如果存在环，快指针必定追上慢指针。如果快指针到 nullptr，则无环。
**扩展：找到环的入口**：头节点到入口距离 = 相遇点到入口距离（需要数学推导）。在第一次相遇后，一个指针从头走，另一个从相遇点走，步长都为 1，相遇点即入口。
> [!Info] 可能的追问:
> - Q: 为什么快慢指针就能判环？数学原理？
> - A: 假设入环前长度 a，环长度 b。快慢指针相遇时，慢指针走了 s 步，快指针走了 2s 步，有 2s - s = kb（快指针比慢指针多走了 k 圈环），所以 s = kb。此时慢指针相对于入口走了 kb - a = (k-1)b + (b-a) 步，所以从相遇点继续走 a 步即可回到入口。
> - Q: 能不能用哈希表判环？
> - A: 可以，遍历链表，将每个节点地址存入 unordered_set，如果重复出现即有环。但需要 O(n) 额外空间，不如快慢指针的 O(1) 空间。

### 二叉树翻转（反转二叉树）
**回答话术：**
递归解法：交换左右子树，然后递归翻转左右子树。
```cpp
TreeNode* invertTree(TreeNode* root) {
    if (!root) return nullptr;
    swap(root->left, root->right);
    invertTree(root->left);
    invertTree(root->right);
    return root;
}
```
**递归返回条件（base case）**：节点为 nullptr 时返回 nullptr。
> [!Info] 可能的追问:
> - Q: 非递归实现？
> - A: 用队列做层序遍历（BFS），遍历每个节点时交换左右子节点后入队。或者用栈模拟递归。
> - Q: 只遍历一遍如何实现？
> - A: 上面的递归解法就是只遍历一遍，每个节点访问一次，在回溯过程中交换左右子树，时间复杂度 O(n)。

### 树的层序遍历
**回答话术：**
层序遍历（BFS）用队列实现：
```cpp
vector<vector<int>> levelOrder(TreeNode* root) {
    if (!root) return {};
    vector<vector<int>> result;
    queue<TreeNode*> q; q.push(root);
    while (!q.empty()) {
        int levelSize = q.size();
        vector<int> level;
        for (int i = 0; i < levelSize; i++) {
            TreeNode* node = q.front(); q.pop();
            level.push_back(node->val);
            if (node->left) q.push(node->left);
            if (node->right) q.push(node->right);
        }
        result.push_back(level);
    }
    return result;
}
```
> [!Info] 可能的追问:
> - Q: 空间复杂度？
> - A: O(w)，w 是树的最大宽度（最宽一层的节点数）。最坏情况完全二叉树 O(n)。
> - Q: 如何用 DFS 实现层序遍历？
> - A: 用一个参数 depth 记录当前深度，递归时 push 到 result[depth]。

### 括号匹配问题
**回答话术：**
使用栈。遍历字符串，遇到左括号入栈，遇到右括号时检查栈顶是否匹配，匹配则弹栈，否则返回 false。最后栈空则全部匹配。
> [!Info] 可能的追问:
> - Q: 如果括号种类只有一种（如只有圆括号）怎么优化？
> - A: 用一个计数器，左括号 +1，右括号 -1。任何时候 counter ≥ 0（保证不先出现右括号），最终 counter = 0。O(1) 空间。
> - Q: 如何输出最长的有效括号子串长度？
> - A: 用栈存左括号的索引（或者用 DP）。栈底存最后一个不匹配的右括号位置。

### 拓扑排序的时间复杂度
**回答话术：**
拓扑排序是对有向无环图（DAG）进行排序——每个顶点只出现一次，如果 A → B，则 A 在 B 之前。
**Kahn 算法（BFS）**：1. 统计所有顶点的入度 2. 入度为 0 的顶点入队 3. 出队时将其后继节点的入度减 1，如果入度变成 0 则入队 4. 重复直到队列为空。如果排序结果中的顶点数不等于总数，说明有环。
**时间复杂度**：O(V + E)，V 是顶点数，E 是边数。
> [!Info] 可能的追问:
> - Q: 如何检测图中是否存在环？
> - A: 拓扑排序过程中，如果最终排序的顶点数小于总顶点数，则有环。或者 DFS 时用三色标记法（白/灰/黑），如果在回溯过程中遇到灰色节点，则有环。
> - Q: 可以用 DFS 实现拓扑排序吗？
> - A: 可以。对图进行 DFS，在回溯时（后序遍历）将节点加入结果。最终结果的反转就是拓扑排序。

### 用栈实现队列 / 用队列实现栈
**回答话术：**
**两个栈实现队列**：入队 O(1)，出队均摊 O(1)（每个元素最多被移两次）。in 栈处理入队，out 栈处理出队（out 为空时将 in 全部移到 out）。
**两个队列实现栈**：入队 O(n)（将元素入队到空队列，再将原队列元素移到后面），出队 O(1)。
> [!Info] 可能的追问:
> - Q: 两个栈实现队列，pop 操作的平均时间复杂度？
> - A: 均摊 O(1)。每个元素最多被 push 到 in 栈一次、移到 out 栈一次、pop 一次。

### 无重复字符的最长子串/子串问题
**回答话术：**
**无重复字符的最长子串**（LeetCode 3）：滑动窗口。
```cpp
int lengthOfLongestSubstring(string s) {
    vector<int> last(128, -1);
    int left = 0, maxLen = 0;
    for (int right = 0; right < s.size(); right++) {
        if (last[s[right]] >= left)
            left = last[s[right]] + 1;
        last[s[right]] = right;
        maxLen = max(maxLen, right - left + 1);
    }
    return maxLen;
}
```
**优化思路**：如果字符集有限（ASCII 128），可以用数组代替哈希表，减少哈希碰撞开销。
> [!Info] 可能的追问:
> - Q: 时间复杂度？
> - A: O(n)，每个字符最多被左右指针各访问一次。空间 O(字符集大小)。
> - Q: 如果需要找出无重复字符的最小子串（覆盖所有字符）？
> - A: 最小覆盖子串问题（LeetCode 76）。滑动窗口 + 计数法。

### Top K 问题
**回答话术：**
**方法一：堆（适合大量数据，海量数据流）**：取 Top K 大 → 小顶堆（堆顶是当前第 K 大，新元素大于堆顶就替换下沉）。时间复杂度 O(n log k)，空间 O(k)。
**方法二：快速选择（Quick Select）**：基于快排的 partition，平均 O(n)，最坏 O(n²)。适合数组不大且需要精确的第 K 个元素。
**场景选择**：海量数据（无法全量排序）→ 堆；数据不多且需要快速 → 快速选择。
> [!Info] 可能的追问:
> - Q: 在数据量极大（如 10 亿个数据求 Top100）时怎么处理？
> - A: 分治——将数据分片，每片用堆求局部 Top100，然后合并结果再做一次 Top100。如果还能分布式，用 MapReduce 方式在不同机器上分别计算。
> - Q: 快速选择的复杂度为什么是 O(n) 平均？
> - A: 每次 partition 将问题规模减半（平均情况），T(n) = T(n/2) + O(n)，根据主定理 O(n)。最坏情况 pivot 选在端点导致 T(n) = T(n-1) + O(n) = O(n²)。

### 文件分片时如何保证顺序性
**回答话术：**
文件分片要保证顺序性主要在两个方面：传输顺序和重组顺序。
**保证重组顺序**：每个分片携带**分片序号**（segment index 或 offset），接收方根据序号在文件中的位置写入。传输层可以使用 TCP（保证数据有序到达）。应用层增加**序号校验**：接收方检查分片序号是否连续，不连续则请求重传。使用**位图（bitmap）** 记录哪些分片已收到，完成所有分片后按序重组。
> [!Info] 可能的追问:
> - Q: 如果使用 UDP 传输文件分片，怎么保证顺序？
> - A: 在 UDP 之上自己实现一套类似 TCP 的确认重传+序号机制。收到分片后先缓存到本地（根据序号插入到对应位置），不连续时请求重传缺失的分片。

### 解决带手续费的股票交易问题
**回答话术：**
这是 LeetCode 714，买卖股票的最佳时机含手续费。DP 思路：
```cpp
int maxProfit(vector<int>& prices, int fee) {
    int hold = -prices[0], cash = 0;
    for (int i = 1; i < n; i++) {
        int prev_hold = hold;
        hold = max(hold, cash - prices[i]);
        cash = max(cash, prev_hold + prices[i] - fee);
    }
    return cash;
}
```
时间 O(n)，空间 O(1)。
> [!Info] 可能的追问:
> - Q: 没有手续费的版本怎么做？
> - A: 就是 LeetCode 122（多次交易），只需累加所有上涨差值。
> - Q: 只能交易一次呢？
> - A: LeetCode 121，维护历史最低价和最大差值。

### 动态库封装了哪些接口？动态库链接的过程
**回答话术：**
**动态库封装的接口**：对外暴露的函数符号（全局函数、类成员函数）、全局变量（dllimport/dllexport）。通过库的头文件声明这些接口。
**动态库链接过程**：
1. **编译期（链接）**：链接器查找符号表，记下未解析的符号名称，不在可执行文件中拷贝代码（不同于静态库），只记录需要哪个动态库的哪些符号
2. **加载期**：程序启动时，动态链接器（ld.so）按照 LD_LIBRARY_PATH 等搜索路径找到动态库，加载到内存，将符号重定位到实际地址
3. **运行时**：也可以延迟绑定（lazy binding），在第一次调用函数时才解析符号（PLT/GOT 机制）
> [!Info] 可能的追问:
> - Q: 使用动态库的运行时查找顺序？
> - A: 1) LD_PRELOAD（强制替换）2) LD_LIBRARY_PATH 3) /etc/ld.so.cache 4) /lib、/usr/lib
> - Q: 如何查看一个可执行文件依赖哪些动态库？
> - A: `ldd ./program`。
> - Q: 链接过程分哪几类？
> - A: 静态链接（链接时全部拷贝到可执行文件）、动态链接（加载时链接）、运行时链接（dlopen 手动加载）。

## 数据库

### MySQL 索引底层
**回答话术：**
MySQL InnoDB 使用**B+ 树**作为索引结构。特点：
- 非叶子节点只存 key 和指针，不存数据——能容纳更多索引项，降低树的高度
- 叶子节点存完整数据（聚簇索引）或指向主键（二级索引）
- 叶子节点间有链表指针，便于范围查询（按序遍历）
- 高度通常为 3~4 层，三次 I/O 即可查询到数据
**聚簇索引 vs 非聚簇索引**：InnoDB 主键索引是聚簇索引（叶子节点存整行数据），其他索引是非聚簇索引（叶子节点存主键值，需要回表）。
> [!Info] 可能的追问:
> - Q: B+ 树和 B 树的区别？
> - A: B 树非叶子节点也存数据，B+ 树只有叶子节点存数据。B+ 树叶子节点用链表连接，范围查询更快。B+ 树非叶子节点能存更多 key，树更矮，磁盘 I/O 更少。
> - Q: 什么是索引最左匹配原则？
> - A: 联合索引 (a,b,c) 等效于创建了 (a)、(a,b)、(a,b,c) 三个索引。查询条件从最左开始匹配。

### 数据库事务的 ACID
**回答话术：**
1. **原子性（Atomicity）**：事务要么全部成功，要么全部失败回滚。通过 undo log 实现
2. **一致性（Consistency）**：事务执行前后数据满足所有约束。由 AID 共同保证
3. **隔离性（Isolation）**：多个事务并发执行不互相干扰。通过锁和 MVCC 实现
4. **持久性（Durability）**：提交的事务永久生效（写入磁盘）。通过 redo log 实现
> [!Info] 可能的追问:
> - Q: redo log 和 binlog 的区别？
> - A: redo log 是 InnoDB 存储引擎的日志（物理日志，记录"对哪个页做了什么修改"），用于崩溃恢复。binlog 是 MySQL Server 层的日志（逻辑日志，记录执行的 SQL），用于主从复制。redo log 是循环写的，binlog 是追加写的。

### 数据库隔离级别
**回答话术：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 避免 | 可能 | 可能 |
| 可重复读（MySQL 默认）| 避免 | 避免 | InnoDB 通过 MVCC + gap lock 避免了 |
| 可序列化 | 避免 | 避免 | 避免 |

**并发问题**：脏读（读到另一未提交事务的数据）、不可重复读（同一事务两次读同一行结果不同）、幻读（同一条件查询两次行数不同）。
> [!Info] 可能的追问:
> - Q: 可序列化级别怎么实现的？
> - A: 所有读都变成快照读 + 所有写加锁，实际退化为串行化执行。性能很低，一般不用。
> - Q: MVCC 核心原理？
> - A: 每行数据有隐藏的 trx_id（创建该版本的事务 ID）和 roll_pointer（指向 undo log 中上一个版本）。在可重复读级别，事务每次读都从 ReadView（已提交事务集合）判断行的可见性。

### 数据库连接池
**回答话术：**
**连接池**是一组预先创建的数据库连接，应用程序从中获取连接而不是新建连接。
**工作机制**：1. 初始化时创建 N 个连接到连接池 2. 业务代码从池中借用一个连接 3. 使用完后归还到池中（不是 close）4. 如果所有连接被占用，新请求等待或超时
**优势**：减少连接开销（TCP 三次握手 + MySQL 鉴权）、控制并发上限、复用连接、统一管理。
> [!Info] 可能的追问:
> - Q: 连接池大小设置多少合适？
> - A: 经验公式：`核数 × 2 + 有效磁盘数`（对于 IO 密集型）。如果 CPU 密集型，接近核数即可。
> - Q: 连接池中连接断了怎么办？
> - A: 需要做心跳保活（如执行 SELECT 1）检测连接是否有效，无效则移除并创建新连接。

### SQL 语法相关
**7.5.1 drop、delete、truncate 的区别**

| 对比 | drop | truncate | delete |
|------|------|----------|--------|
| 类型 | DDL | DDL | DML |
| 内容 | 删除表结构及数据 | 清空表数据 | 逐行删除 |
| 事务 | 不可回滚（隐式提交） | 部分可回滚 | 可回滚 |
| 速度 | 快 | 快 | 慢（逐行记录日志）|
| 触发器 | 不触发 | 不触发 | 触发 |

**7.5.2 union 和 union all 的区别**
- **union**：合并结果集 + 去重 + 排序。性能开销大
- **union all**：直接合并全部结果，不去重不排序。效率高。如果确定无重复，优先用 union all
**7.5.3 四种 JOIN 的含义与区别（INNER/LEFT/RIGHT/FULL）**
**回答话术：**
JOIN 用于根据两个或多个表之间的关联列合并数据。四种类型的行为可以用韦恩图理解：
1. **INNER JOIN**（内连接）——取两表的**交集**，只返回两表中都匹配的行。匹配不上的行丢弃。这是最常用的 JOIN 类型，也是默认 JOIN。
2. **LEFT JOIN**（左外连接）——保留左表的**全部**记录，右表有匹配的行就填充数据，无匹配则填 NULL。
3. **RIGHT JOIN**（右外连接）——保留右表的**全部**记录，左表有匹配的行就填充数据，无匹配则填 NULL。实际上 LEFT JOIN 和 RIGHT JOIN 可以互相转换，只需交换表的顺序。
4. **FULL OUTER JOIN**（全外连接）——返回两表的**并集**，左表或右表无匹配时填充 NULL。MySQL **不直接支持** FULL OUTER JOIN，需要用 `LEFT JOIN UNION RIGHT JOIN` 模拟。
**知识点讲解：**
```sql
-- 示例表
-- Table A (Students): id | name
-- Table B (Scores):   id | student_id | score

-- INNER JOIN：只取两端都匹配的行
SELECT * FROM Students s
INNER JOIN Scores sc ON s.id = sc.student_id;
-- 只有有成绩的学生出现在结果中，无成绩的学生被过滤掉

-- LEFT JOIN：左表全保留，右表无匹配时列填 NULL
SELECT * FROM Students s
LEFT JOIN Scores sc ON s.id = sc.student_id;
-- 所有学生都在结果中，无成绩的学生 score 列为 NULL

-- RIGHT JOIN：右表全保留，左表无匹配时列填 NULL
SELECT * FROM Students s
RIGHT JOIN Scores sc ON s.id = sc.student_id;
-- 所有成绩记录都在结果中，找不到对应学生的成绩记录 name 列为 NULL

-- FULL OUTER JOIN：两表全保留，任意一边无匹配时对应列填 NULL
-- MySQL 不直接支持，需用 UNION 模拟：
SELECT * FROM Students s
LEFT JOIN Scores sc ON s.id = sc.student_id
UNION
SELECT * FROM Students s
RIGHT JOIN Scores sc ON s.id = sc.student_id;
```
```
韦恩图记忆法：
  INNER JOIN → 两圆交集
  LEFT JOIN  → 左圆全部 + 交集部分
  RIGHT JOIN → 右圆全部 + 交集部分
  FULL JOIN  → 两圆所有区域（并集）
```
> [!Info] 可能的追问:
> - Q: LEFT JOIN 和 RIGHT JOIN 是否可以互相转换？
> - A: 可以。`A LEFT JOIN B` 等效于 `B RIGHT JOIN A`，只需交换表顺序即可。实际开发中一般统一用 LEFT JOIN 而不用 RIGHT JOIN，保持代码风格一致。
> - Q: 大表 JOIN 的性能如何优化？
> - A: 1) JOIN 的关联列必须有索引（索引是 JOIN 性能的关键）2) 尽量用 INNER JOIN 而不是 OUTER JOIN（外连接的结果集更大）3) 先 WHERE 过滤缩小数据量再 JOIN 4) 避免 JOIN 过多表（超过 3~4 个表 JOIN 要考虑是否需要冗余字段或反范式化）。
**7.5.4 group by 每组取第一个数的问题**
- 如果 SQL 写了 GROUP BY 但没有用聚合函数来指定取哪个值，返回的"第一个"是随机的
- 规范做法：用聚合函数明确指定，或者用 window function（ROW_NUMBER() OVER(PARTITION BY ...)）来控制
**7.5.5 增加一列的 SQL**

### 数据库死锁
**回答话术：**
**数据库死锁**和操作系统死锁本质一样：事务 A 持有资源 1 等待资源 2，事务 B 持有资源 2 等待资源 1。
**产生原因**：不同事务以不同顺序加锁、间隙锁导致的锁冲突。
**发现和定位**：
```sql
SHOW ENGINE INNODB STATUS\G  -- 查看最近死锁信息
```
**解决方案**：1. InnoDB 自动检测（回滚代价较小的事务）2. 应用层预防（统一锁顺序）3. 缩小事务范围 4. 使用读已提交级别（RC）减少间隙锁 5. 加锁超时
> [!Info] 可能的追问:
> - Q: InnoDB 死锁检测的问题？
> - A: 高并发下检测本身消耗 CPU（需要扫描等待图）。MySQL 8.0 在高并发场景有时会关闭死锁检测（`innodb_deadlock_detect = OFF`），靠锁超时来处理。
> - Q: 数据库死锁 vs 编程死锁的异同？
> - A: 本质相同（互斥 + 持有并等待 + 不可剥夺 + 循环等待）。区别：InnoDB 有自动死锁检测和回滚机制。

### MySQL 的锁
**回答话术：**
按粒度分类：**行锁**（InnoDB 支持，锁定一行）、**表锁**（MyISAM 使用）、**间隙锁**（只在 RR 级别下存在，防止幻读）、**Next-Key Lock**（行锁 + 间隙锁的组合）。
按属性分类：**共享锁（S锁）**：`SELECT ... LOCK IN SHARE MODE`；**排他锁（X锁）**：`SELECT ... FOR UPDATE`。
> [!Info] 可能的追问:
> - Q: 无索引的行锁会升级为什么？
> - A: InnoDB 的行锁是通过索引实现的。如果 WHERE 条件没有命中索引，会锁全表（实际是行锁覆盖全表所有记录，不是表锁）。
> - Q: 记录锁和间隙锁分别什么场景下使用？
> - A: 唯一索引等值匹配 → 记录锁；普通索引范围查找 → 间隙锁 + 行锁（next-key lock）；无索引 → 全表行锁。

### 动态 SQL
**回答话术：**
动态 SQL 是指在运行时根据条件动态拼接 SQL 语句的编程技术。典型应用场景：搜索条件不确定、批量操作、动态表名/字段名。
> [!Info] 可能的追问:
> - Q: 动态 SQL 的安全风险？
> - A: 主要风险是 SQL 注入。防范：用参数化查询（PreparedStatement）替代字符串拼接；对表名/字段名做白名单校验。

## Redis

### Redis 为什么这么快？
**回答话术：**
1. **纯内存操作**：数据在内存中，读写纳秒级
2. **单线程模型**：避免了锁竞争和上下文切换的开销（6.0 后网络 I/O 多线程，但命令执行仍然是单线程）
3. **I/O 多路复用**：用 epoll 处理大量客户端连接
4. **高效的数据结构**：跳表、压缩列表（ziplist）、快速列表（quicklist）等针对场景优化的结构
5. **渐进式 rehash**：rehash 不阻塞主线程
> [!Info] 可能的追问:
> - Q: 单线程不会慢吗？
> - A: 单线程避免了锁竞争和上下文切换。Redis 的瓶颈通常是网络 I/O 和内存带宽，而非 CPU。大 key 操作（如 KEYS）会阻塞主线程，应该避免。

### Redis 的五种数据类型及应用场景
**回答话术：**

| 类型 | 底层实现 | 应用场景 |
|------|----------|----------|
| String | 动态字符串（SDS） | 缓存、计数器、分布式锁（SETNX） |
| List | quicklist | 消息队列（LPUSH/BRPOP）、最新消息列表 |
| Set | hashtable / intset | 标签系统、签到、好友关系（交集/并集） |
| ZSet（Sorted Set）| dict + skip list | 排行榜、延时队列、优先级队列 |
| Hash | dict / ziplist | 对象缓存（用户信息、商品信息） |

> [!Info] 可能的追问:
> - Q: ZSet 的跳表结构在什么样的数据量下切换？
> - A: zset 同时使用 dict（O(1) 查分值）和跳表（O(log n) 范围操作）。无论数据多少都同时使用这两种结构（不是切换关系）。

### Redis 哨兵模式
**回答话术：**
哨兵（Sentinel）是 Redis 高可用方案。一组哨兵进程监控主从节点的健康状态，主节点挂掉时自动将从节点提升为主。
**节点数量建议**：哨兵节点数 ≥ 3（奇数，为了形成法定票数），通常 3 或 5。服务节点：至少 1 个主库 + 1 个从库。
**选举过程**：哨兵检测到主节点主观下线（sdown）→ 多个哨兵确认客观下线（odown）→ 进行领导者选举 → 从 slave 中选出一个提升为 master。
> [!Info] 可能的追问:
> - Q: 为什么哨兵要奇数的至少 3 个？
> - A: 为了选举时能产生多数派（quorum）。哨兵数是奇数可以避免 2 个节点时平局。最少 3 个保证可以挂掉 1 个而剩余 2 个仍能形成多数。

### Redis 消息队列实现
**回答话术：**
Redis 实现消息队列的方式：
1. **List**：LPUSH + BRPOP（阻塞读取），简单可靠，但不支持多播
2. **Pub/Sub**：发布-订阅模式，支持多播。但有消息丢失问题——客户端离线就收不到
3. **Stream**（Redis 5.0+）：专业的消息队列数据结构，支持持久化、消费者组、ACK 确认机制
**推荐选择**：正式场景用**Stream**——保证消息不丢失，支持 ACK 确认和消费者组，能回溯消息。
> [!Info] 可能的追问:
> - Q: Redis Stream 和 Kafka 有什么区别？
> - A: Redis Stream 内存存储（可持久化到磁盘），适合小规模、低延迟消息。Kafka 磁盘持久化，通过顺序读写 + 分页缓存保证高性能，适合高吞吐、大规模消息场景。

### Redis 相比 Memcached 的核心优势
**回答话术：**

| 对比 | Redis | Memcached |
|------|-------|-----------|
| 数据类型 | 丰富（5+ 种）| 仅 string |
| 持久化 | 支持 RDB/AOF | 不支持（纯缓存）|
| 集群方案 | 哨兵、Cluster | 客户端分片 |
| 数据结构操作 | 丰富（交集、范围查询等）| 仅 get/set |

> [!Info] 可能的追问:
> - Q: Redis 单节点部署的问题？
> - A: 单点故障（宕机服务不可用）、容量有限（受单机内存限制）、并发能力受限于单核。

### Redis 分布式锁
**回答话术：**
基于 Redis 的分布式锁核心思路：使用 SETNX（SET if Not eXists）命令。
```bash
SET lock_key unique_value NX PX 30000  # 获取锁，30 秒自动过期
# 释放锁时用 Lua 脚本保证原子性
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else return 0 end
```
**问题与改进**：锁过期但任务没执行完 → 用 Redisson 的 watchdog 自动续期；主从切换导致锁丢失 → Redlock 算法（向多数节点同时申请锁）。

## 设计模式

### 单例模式
**回答话术：**
**饿汉式**：类加载时就创建实例，在类中声明静态成员导致 main 函数启动之前就创建单例。C++11 以后线程安全，但可能浪费资源（如果从未使用）并延长启动时间。
**懒汉式**：首次使用时创建。需要线程安全处理。C++11 后最佳实践是 Meyer's Singleton——局部 static 变量在第一次调用时初始化，C++11 保证线程安全。
```cpp
Singleton& Singleton::getInstance() {
    static Singleton instance;
    return instance;
}
```
> [!Info] 可能的追问:
> - Q: 为什么 C++11 的 static 局部变量是线程安全的？
> - A: C++11 标准要求编译器为静态局部变量的初始化插入双重检查锁（Double-Checked Locking），确保仅初始化一次且线程安全。
> - Q: 如何破坏单例？
> - A: 通过拷贝构造、反射、序列化/反序列化。C++ 中 delete 拷贝构造和赋值运算符可以阻止。

### 工厂方法模式和抽象工厂模式的区别
**回答话术：**
**工厂方法**：定义一个创建对象的接口（纯虚函数），让子类决定实例化哪个类。适用于单个产品等级结构的创建。
**抽象工厂**：创建相关或依赖的**一组**产品家族。适用于多个产品等级结构（如不同 UI 风格下的 Button + CheckBox + TextField）。

| 对比 | 工厂方法 | 抽象工厂 |
|------|---------|---------|
| 产品 | 单一产品 | 产品族（多个相关产品）|
| 创建 | 一个工厂创建一个产品 | 一个工厂创建一系列产品 |
| 场景 | 需要灵活扩展新产品类型 | 需要保证产品族的兼容性 |

**场景举例**：工厂方法——日志记录器（文件日志、数据库日志、控制台日志）；抽象工厂——跨平台 UI（Windows 工厂创建 WindowsButton + WindowsCheckbox）。
> [!Info] 可能的追问:
> - Q: 简单工厂、工厂方法、抽象工厂的区别？
> - A: 简单工厂把所有创建逻辑放一个函数里（if-else 判断）；工厂方法把创建延迟到子类（虚函数）；抽象工厂创建一组产品。

## 系统设计
### 分布式缓存系统设计需要考虑哪些方面？
**回答话术：**
1. **数据分布**：一致性哈希（减少扩容影响的数据迁移量）、哈希槽（Redis Cluster 方案）
2. **高可用**：主从复制、哨兵/集群模式自动故障转移
3. **淘汰策略**：LRU、LFU、TTL 过期——内存有限时必须淘汰策略
4. **持久化**：Redis 的 RDB（快照）和 AOF（日志）保证数据不丢
5. **缓存穿透/击穿/雪崩**：穿透（布隆过滤器或缓存空值）、击穿（互斥锁重建或永不过期）、雪崩（过期时间加随机值）
6. **一致性**：缓存和数据库的最终一致性保证（延迟双删、Binlog 同步）
> [!Info] 可能的追问:
> - Q: 缓存穿透的布隆过滤器原理？
> - A: 用多个哈希函数将 key 映射到几个位数组位置。查询时如果任何一个位为 0 则肯定不存在。可能有误判（说存在实际不存在），但不存在误判。

### JWT 基本原理
**回答话术：**
JWT（JSON Web Token）是一个自包含的令牌，由三部分组成：`header.payload.signature`
1. **Header**：指定签名算法（HS256/RS256）和 Token 类型
2. **Payload**：声明信息（用户 id、过期时间等），**base64 编码，不加密**，所以不要放敏感信息
3. **Signature**：对 header.payload 做签名的结果，防止篡改
**工作流程**：用户登录 → 服务器生成 JWT 返回 → 客户端存到 localStorage → 后续请求在 Authorization 头部携带 → 服务器验证签名。
**优点**：无状态（服务端不需要存 session），适合分布式系统。**缺点**：无法主动注销（除非维护黑名单）、Payload 不能存敏感信息、Token 长度大。
> [!Info] 可能的追问:
> - Q: 如果用了 JWT 如何实现退出登录？
> - A: 服务端维护一个黑名单（用 Redis），将 JWT 的 jti（唯一 ID）在过期前加入黑名单。每次请求先检查是否在黑名单中。但这破坏了 JWT 的"无状态"特性。

### 服务器挂掉后客户端如何重连
**回答话术：**
**客户端策略**：1. 指数退避重连（1s → 2s → 4s... 最大间隔如 30s）2. 心跳检测（超时未收到回复则判定断连，触发重连）3. 断线重连状态机 4. 消息缓存（断连期间的消息缓存在本地队列，重连后批量发送）
**服务端策略**：1. 心跳超时释放资源但不立即销毁会话 2. 幂等处理（重连后可能重复发送消息，接口需要幂等）3. 状态恢复

### 挑一个锁的实现机制讲解
**回答话术（推荐原子自旋锁）：**
自旋锁的实现依赖 CPU 的原子操作 CAS（Compare And Swap）。在 x86 上是 `lock cmpxchg` 指令。C++11 可以用 `std::atomic_flag` 实现：
```cpp
class SpinLock {
    atomic_flag flag = ATOMIC_FLAG_INIT;
public:
    void lock() {
        while (flag.test_and_set(std::memory_order_acquire))
            _mm_pause();  // CPU yield hint
    }
    void unlock() { flag.clear(std::memory_order_release); }
};
```
`test_and_set` 是原子操作：先在 flag 上写入 1，同时返回旧值。如果旧值是 0 表示成功获取锁，否则循环等待。

### 实现原则
- 不分配内存、不抛出异常，仅仅是返回指针或解引用的操作原则上都应该使用 `noexcept` 允许编译器进行更激进的优化

`explicit` 允许在**显式布尔上下文**（`if`、`while`、`&&`、`||`、`!`、`?:` 的条件部分）中隐式转换，但禁止在算术、指针上下文中隐式转换。
**SharedPtr 也需要** `explicit operator bool()`，原因相同，标准库实现中两者都加了 explicit。
> [!Info] 可能的追问:
> - Q: `operator bool()` 和重载 `==`、`!=` 有什么区别？
> - A: 
> - `operator bool()` 定义对象在布尔上下文中的行为（`if (ptr)` 判断是否非空）
> - `operator==` / `operator!=` 定义对象之间的比较行为（`ptr1 == ptr2` 判断是否指向同一对象）
> - 两者不同：bool 运算符判断指针是否非空，`==` 判断两个指针是否指向同一对象
> - 想让一个类能被判断布尔类型，**必须重载 `operator bool()`**，因为 C++ 的布尔转换规则优先找 `operator bool()`。重载 `==` 不能替代布尔转换。

## fastlog 日志库的整体架构
**回答话术：**
fastlog 采用三层架构设计：用户接口层（fastlog.hpp 暴露 console 和 file 两套 API）→ 核心逻辑层（BaseLogger 模板基类、ConsoleLogger 和 FileLogger 具体实现）→ 底层基础设施（FileLogBuffer 环形缓冲区、logfstream 文件写入、时间/线程 ID 工具函数）。用户调用 `fastlog::console.info("format {}", arg)` 时，编译期检查 format 字符串（consteval），运行时根据日志等级过滤，然后格式化字符串写入当前缓冲区；缓冲区满了就交换到 full_buffers_ 列表通知后台线程刷盘。设计亮点是通过 CRTP（`BaseLogger<Derived>`）实现静态多态避免虚函数开销，使用 `std::source_location` 编译期捕获调用位置。
**知识点讲解：**
```cpp
// CRTP 静态多态：避免虚函数调用开销
template <typename DerviceLogger>
class BaseLogger {
    template <LogLevel LEVEL, typename... Args>
    void format(format_string_wrapper<Args...> fmt_w, Args&&... args) {
        static_cast<DerviceLogger*>(this)->template log<LEVEL>(
            logrecord_t{.file_name = fmt_w.loc_.file_name(),
                        .line      = fmt_w.loc_.line(),
                        .log       = std::format(fmt_w.fmt_, std::forward<Args>(args)...)});
    }
};
```
> [!Info] 可能的追问:
> - Q: 为什么用 CRTP 而不是虚函数？
> - A: CRTP 在编译期确定调用函数，编译器可以内联展开，零运行时开销。虚函数需要一次间接跳转（vptr → vtbl），且阻塞内联优化。日志库中 log 调用极其频繁，累积的开销可观。
> - Q: Buffer 大小为什么选 `4000*1024`（约 4MB）？
> - A: 需要在内存占用和减少缓冲区交换频率之间平衡。4MB 可容纳数万条日志，同时不会显著增加内存压力。太小则频繁触发交换和唤醒，太大则增加内存峰值。
> - Q: 为什么用 std::format 而不是 printf 或 iostream？
> - A: std::format 类型安全、编译期格式化字符串检查、性能优于 iostream（无虚函数和 i18n 开销）。

## HttpConnection 的处理流程与 Boost 组件
**回答话术：**
CServer 启动后，`_acceptor` 调用 async_accept 等待新连接 → 创建 HttpConnection 对象 → 调用 start 发起 async_read → 收到完整 HTTP 请求后 handleRequest 解析 method（GET/POST）→ preParseGetParam 使用 Boost.URL 解析 URL 参数 → 委托 LogicSystem 进行业务处理 → writeResponse 写回响应。
用到的 Boost 组件：Asio（async_accept/async_read/async_write、io_context、steady_timer）、Beast（http::request/response/async_read/async_write、flat_buffer）、URL（url::parse_uri_reference）。多线程分发通过 AsioIOServicePool 实现——每个线程跑一个 io_context，CServer accept 后从池中轮询取出一个 io_context 创建 HttpConnection。
**知识点讲解：**
```cpp
void CServer::start() {
    auto& ioContext = AsioIOServicePool::getInstance()->getIOService();
    auto  newConn   = std::make_shared<HttpConnection>(ioContext);
    _acceptor.async_accept(newConn->getSocket(), [self, newConn](const beast::error_code& ec) {
        if(ec) { self->start(); return; }
        newConn->start();
        self->start();
    });
}
```
> [!Info] 可能的追问:
> - Q: deadline 定时器的作用？
> - A: 防止客户端长时间不发送请求或响应慢，60 秒超时自动关闭 socket。这是一种资源保护机制，防止慢连接占用服务器资源。
> - Q: 为什么要用 enable_shared_from_this？
> - A: 异步回调中 HttpConnection 可能在回调触发前被析构，导致 use-after-free。shared_from_this 确保异步操作期间对象存活。
> - Q: AsioIOServicePool 为什么用 work_guard？
> - A: io_context::run() 在无事件时立即返回。work_guard 创建"虚拟事件"阻止 run() 返回，让线程持续等待新任务。

## 异步日志解决的核心问题
**回答话术：**
核心问题是高并发场景下写日志不能阻塞业务线程。直接 fwrite 每次涉及系统调用和磁盘 I/O，在高频场景下成为瓶颈。解决方案是多缓冲区异步写入——前端业务线程快速写入环形缓冲区（纯内存操作），后端一个后台线程批量刷盘。性能从初始的 30 万行/秒提升到 220 万行/秒。关键细节：缓冲池管理（current → full → 后台写 → empty 循环利用）、3ms 超时兜底、写满时丢弃旧缓冲区防止内存暴涨。
**知识点讲解：**
```cpp
void FileLogger::work() {
    while(running_) {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait_for(lock, std::chrono::milliseconds(3),
                     [this] { return !full_buffers_.empty(); });
        for(auto& buffer : full_buffers_) {
            log_fs_.write(buffer->data(), buffer->size());
            buffer->reset();
        }
        empty_buffers_.splice(empty_buffers_.end(), full_buffers_);
        log_fs_.flush();
    }
}
```
> [!Info] 可能的追问:
> - Q: 为什么不用双缓冲而是多缓冲？
> - A: 双缓冲（一个写一个刷盘）在日志峰值超过刷盘速度时会阻塞业务线程。多缓冲可以暂存峰值期间的多批次日志，更灵活。
> - Q: 3ms 超时怎么确定的？
> - A: 经验值。太长（100ms）则 crash 时丢失日志多；太短（1ms）则频繁唤醒增加上下文切换。3ms 平衡了实时性和性能。

## 信息安全产品开发
**回答话术：**

## 多线程编程中的常见坑
**回答话术：**
1) 竞态条件——mutex/atomic 保护；
2) 死锁——std::lock 一次性上锁或固定锁顺序；
3) 伪共享——不同线程操作同一 cache line 的变量导致缓存行乒乓，用 alignas(64) 分离；
4) 条件变量 spurious wakeup——用带谓词的重载处理。
**知识点讲解：**
```cpp
struct alignas(64) Counter { atomic<int> value{0}; };  // 64 字节对齐防伪共享
```
> [!Info] 可能的追问:
> - Q: 自旋锁和互斥锁如何选择？
> - A: 锁持有微秒级用自旋锁（避免线程切换），毫秒级以上用互斥锁（避免 CPU 空转）。

## TCP Socket 粘包问题
**回答话术：**
TCP 是流式协议无消息边界，多个 send 的数据可能在接收方粘在一起。解决方案：
1) 固定长度头（前 4 字节表示消息体长度，最常用）；
2) 特殊分隔符（如 HTTP 的 \r\n\r\n）；
3) 定长消息。HTTP 服务器用 Boost.Beast 已处理了粘包解析。
**知识点讲解：**
```cpp
struct MsgHeader { uint32_t length; };  // 网络字节序 htonl
```
> [!Info] 可能的追问:
> - Q: UDP 有粘包问题吗？
> - A: 没有。UDP 是数据报协议，每次 recvfrom 收到完整报文，天然有消息边界。
