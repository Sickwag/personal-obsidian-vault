5. RocketMQ 的存储与投递机制是什么？
RocketMQ 的消息主体顺序写入 CommitLog，ConsumeQueue 保存某个 Topic 队列对应的逻辑索引，消费者先查询 ConsumeQueue，再根据物理偏移读取 CommitLog。顺序写和页缓存能够提高写入吞吐，MappedFile 用于管理映射文件。

Broker 接收消息后，根据刷盘模式决定同步刷盘或异步刷盘；根据复制模式决定是否等待从节点确认。同步刷盘和同步复制能提高可靠性，但会增加发送延迟。

消费失败时，消息可以进入重试 Topic，超过最大次数后进入死信队列。消息成功写入 Broker 不等于业务处理成功，消费端仍需要幂等和失败恢复机制。

7. RocketMQ 如何实现延迟消息？任意精度延迟队列的难点是什么？
固定等级延迟消息可以将消息先写入内部延迟 Topic，不同延迟等级对应不同队列。调度线程扫描到期消息，再恢复原 Topic 和队列并重新投递。

任意时间精度的延迟消息通常使用时间轮或分层时间轮。时间轮适合大量定时任务，但需要处理磁盘持久化、槽位恢复、时钟回拨、任务取消和超远期任务。若所有任务都放入一个最小堆，插入和删除为 O(log n)，任务量特别大时锁竞争和恢复成本较高。

时间到期只代表消息可以投递，不代表业务只能执行一次。调度服务崩溃可能导致重复投递，因此消费者仍需要幂等。

8. Kafka 和 RocketMQ 能否直接互相替代？
二者都支持持久化消息、分区消费和消费者组，但产品语义不同。Kafka 更强调日志流和顺序追加，生态适合流处理、数据管道和大吞吐场景；RocketMQ 对业务消息提供了更直接的重试、延迟、事务消息和过滤能力。

迁移时不能只替换客户端。需要重新评估分区顺序、消费位点、重试语义、死信处理、延迟消息、事务消息以及消息保留方式。Kafka 的消息在消费后仍可按保留策略存在，RocketMQ 的业务使用方式通常更接近消息投递。

如果上层已经抽象统一消息协议，可以降低迁移成本，但不同中间件独有能力仍需要适配层或业务降级。

9. Kafka 集群如何完成控制器选举和分区副本管理？
新版 Kafka 使用 KRaft，由控制器节点维护集群元数据，并通过 Raft 日志复制保证元数据一致。控制器负责 Broker 注册、Topic 和分区元数据、Leader 选举以及副本状态变化。

每个分区有一个 Leader 和若干 Follower。生产者和消费者主要与 Leader 交互，Follower 拉取 Leader 日志。ISR 表示与 Leader 保持足够同步的副本集合。当 Leader 失效时，控制器优先从 ISR 中选择新 Leader。

acks=all 只有与 min.insync.replicas 配合才有较强可靠性。如果 ISR 仅剩一个副本且仍允许写入，即使生产者收到成功，Leader 随后损坏仍可能丢失数据。

10. Kafka 为什么能够维持高吞吐？零拷贝解决了哪些问题？
Kafka 使用顺序追加写、批量发送、消息压缩和分区并行提高吞吐。操作系统页缓存承担大部分缓存职责，避免在 JVM 堆内维护大量消息对象。

消费者读取历史日志时，Broker 可以通过 sendfile 类机制把页缓存数据发送到 socket，减少用户态和内核态之间的复制与上下文切换。零拷贝并不意味着数据完全不移动，网卡 DMA 和内核页管理仍然存在。

高吞吐也来自批处理。生产者把多条消息聚合成批次，Broker 按批次写盘，消费者按批次拉取。批次越大，吞吐通常越高，但等待聚合的时间和单次失败成本也会增加。

11. Kafka 消费者组发生 Rebalance 时，如何减少停顿和重复消费？
传统 eager rebalance 会先撤销所有分区再重新分配，造成明显停顿。Cooperative Sticky 策略允许增量迁移分区，只撤销需要转移的部分。静态成员身份也可以减少短暂重启导致的成员变化。

消费者必须控制单次拉取后的处理时间。如果超过 max.poll.interval.ms，协调器可能认为消费者失效并重新分配分区，而原消费者仍可能继续处理旧消息，造成并发消费。

位点提交应与业务处理顺序匹配。先提交位点再执行业务可能丢消息，先处理业务再提交可能重复。一般使用后者并通过业务幂等消除重复；若业务结果也写入 Kafka，可以使用事务消费生产实现更强的一致性。

12. 消息积压数亿条时，如何扩容而不破坏局部有序性？
先确认瓶颈位于生产速度、Broker 磁盘、网络、分区数量还是消费逻辑。增加消费者数量只有在分区数量足够时才有效，因为同一消费组中一个分区同一时刻只能由一个消费者负责。

若必须保证同一订单内有序，可以按订单号分区，只要求业务键内顺序而不是全局顺序。热点订单可能造成单分区倾斜，此时可以把业务拆为多个可交换阶段，或使用版本号使并行结果按状态机提交。

紧急场景下可以建立临时消费组，把历史消息转储到新的高分区 Topic，再扩大消费集群。但迁移过程中要记录切换边界，防止新旧链路同时处理同一批消息。

13. TCP 收到的应用层消息从“123”变成“132”，可能是什么原因？
单条 TCP 连接按字节序提供可靠有序传输，协议栈不会把已经按顺序发送的字节任意改成另一顺序。如果应用看到 132，通常不是 TCP 自身乱序，而是应用代码存在问题。

常见原因包括多个线程并发写同一连接且没有组织完整报文、多个连接的结果在业务层异步合并、共享缓冲区被修改、消息边界解析错误，或者发送方本来就以不同顺序调用了写操作。

TCP 只保证字节流顺序，不保留应用消息边界。应用层应使用长度字段、固定长度、分隔符或自描述协议完成拆包。

14. TCP 如何处理网络层的乱序、重复和丢包？
TCP 使用序列号标识字节位置，接收端根据序列号重组乱序报文，并丢弃已经接收的重复数据。连续数据到达后，接收端通过累计确认告知发送方已连续接收到哪个位置。

丢包可以通过重传超时或快速重传发现。重复 ACK 和 SACK 能帮助发送方判断缺失区间，只重传丢失数据，而不是重发整个窗口。

接收端通常会暂存一定范围内的乱序报文，但缓冲能力有限。攻击者或异常网络制造大量乱序时可能消耗内存，因此实现中还需要限制乱序队列和接收窗口。

15. TCP 的 RTO 是如何计算的？为什么不能固定设置一个超时时间？
网络 RTT 会随路由、排队和负载变化，固定 RTO 过小会产生伪重传，过大又会使真正丢包恢复缓慢。TCP 根据采样 RTT 维护平滑 RTT 和偏差：

3
SRTT    = (1 - α) × SRTT + α × RTT_sample
RTTVAR  = (1 - β) × RTTVAR + β × |SRTT - RTT_sample|
RTO     = SRTT + K × RTTVAR
超时后通常执行指数退避，防止拥塞状态下持续快速重传。对已经重传过的报文，不能简单根据 ACK 判断它对应原始发送还是重传，因此需要 Karn 算法规避歧义，或依靠 TCP 时间戳获得更准确的 RTT 样本。

16. epoll 在内核中如何管理监听集合和就绪事件？

10. C++ 里多态是怎么实现的？虚函数表做了什么？
运行时多态靠虚函数：基类指针/引用调用虚函数时，按对象真实类型分派。
含虚函数的类通常有虚表；对象里有虚表指针，指向该类的虚函数地址表。
调用时先取对象 vptr，再按偏移取函数指针并调用，所以是动态绑定。
虚表按类共享，对象只多存一个指针；多重继承时可能有多张虚表。
2. 为什么基类析构函数通常要写成虚函数？
用基类指针 delete 派生对象时，若不虚，只会调基类析构，派生部分资源泄漏。
虚析构让析构也走动态绑定，先析构派生再析构基类，顺序正确。
不通过基类指针删除、且类不打算多态时，可以不虚，避免引入虚表开销。
抽象基类即使只有纯虚函数，也常给虚析构一个空实现或 = default。
3. 说一下对象内存布局：成员、虚函数、虚继承大概怎么放？
普通成员按声明顺序排布，中间可能有对齐填充。
有虚函数时对象开头常有 vptr；静态成员不占对象空间。
单继承一般是基类子对象在前、派生成员在后；虚函数覆盖改的是虚表项。
虚继承会引入虚基类表/偏移，避免菱形继承里基类子对象重复。
4. 左值和右值有什么区别？移动语义解决什么问题？
左值一般可取地址、有持久身份；右值多为临时量，即将结束生命周期。
拷贝临时对象成本高；移动把资源所有权转走，避免深拷贝。
移动构造/移动赋值通常“偷”指针并置空源对象，要求源对象仍可安全析构。
std::move 只是转换成右值引用，真正移动靠对应重载被选中。
5. unique_ptr、shared_ptr、weak_ptr 怎么选？
unique_ptr 独占所有权，开销小，默认优先用它表达唯一归属。
shared_ptr 共享所有权，靠引用计数管理生命周期，适合多处共享但同一生命周期。
weak_ptr 不增加强引用计数，用于观察或打破环，如父子互相持有。
能不用共享就别用；循环引用要用 weak_ptr 打断，否则会泄漏。
6. shared_ptr 的引用计数是线程安全的吗？对象本身呢？
控制块上的引用计数增减一般是原子的，多线程拷贝/释放同一个 shared_ptr 管理的控制块通常安全。
但这不代表被管理对象的成员访问线程安全，数据竞争仍要自己同步。
同一个 shared_ptr 实例被多线程同时读写（非 const）也不安全，应按值传或加锁。
跨线程传递常用按值传递 shared_ptr，让引用计数正确接力。
7. new/delete 和 malloc/free 有什么区别？
new 分配内存并调用构造函数；delete 先析构再释放。
malloc 只按字节分配，不调用构造/析构，返回 void*。
new 失败默认抛 std::bad_alloc；malloc 失败返回 NULL。
二者不能混用：new 的内存不能 free，malloc 的也不能 delete。
8. 栈上对象和堆上对象有什么区别？
栈分配/释放很快，随作用域自动析构，适合小对象和短生命周期。
堆由程序员或智能指针管理，灵活但有分配开销和泄漏风险。
栈空间通常更小，大数组或深层递归容易栈溢出。
跨作用域共享、大小运行期才定的对象，更常放堆上。
9. sizeof 和 strlen 有什么区别？
sizeof 是编译期运算符，算类型或对象占用字节数，含 \0 的数组容量也能算出来。
strlen 运行期沿字符找 \0，算的是字符串长度，不含结尾 \0。
对指针做 sizeof 得到的是指针本身大小，不是指向内容长度。
字符数组未以 \0 结尾时 strlen 行为未定义，可能越界读。
10. memcpy 和 memmove 有什么区别？
二者都按字节拷贝，不感知对象构造语义。
memcpy 要求源和目的不重叠，重叠时结果未定义。
memmove 允许重叠，会正确处理向前/向后拷贝。
对非平凡类型对象，更应使用赋值、拷贝/移动构造，而不是裸内存拷贝。
11. static 在函数内、文件内、类里分别什么含义？
函数内静态局部变量只初始化一次，生命周期持续到程序结束，仍有作用域限制。
文件内（匿名命名空间更推荐）静态或内部链接符号，仅本翻译单元可见。
类静态成员属于类，不绑定具体对象，所有对象共享一份。
静态成员函数没有 this，不能直接访问非静态成员。
12. const 有哪些常见用法？顶层和底层 const 怎么理解？
修饰变量表示不可修改；修饰成员函数表示不修改对象逻辑状态。
顶层 const 表示指针/对象本身不可改；底层 const 表示指向的内容不可改。
const 引用可绑定临时量，常用于只读参数，避免拷贝。
有时用 mutable 修饰缓存等成员，允许在 const 成员函数里改物理状态。
13. inline 现在还有意义吗？和宏有什么区别？
现代编译器是否真正内联主要由优化决定，inline 更多是给链接和 ODR 的提示。
头文件里的函数常标 inline，允许多个翻译单元定义且不致链接冲突。

解题思路
放置时只需要知道每个堆的堆顶大小。设 top 为从左到右的堆顶数组。每次都选择第一个 top[pos] > x 的位置，并把该堆顶更新为 x；找不到时在末尾新建堆。这个操作保证 top 始终非递减，因此可用 upper_bound/上界二分在 O(log n) 时间定位。

同时维护各堆高度 height 和当前异或和 xorSum。已有堆的高度由 h 变为 h+1 时，依次执行 xorSum ^= h 和 xorSum ^= h+1；新建堆时直接异或 1。

每只猫猫虫做一次二分，时间复杂度 O(n log n)，空间复杂度 O(n)。

1. vector 扩容时迭代器、指针、引用为什么可能全部失效？如何写才相对安全？
扩容通常会重新分配一块更大内存，再把旧元素搬过去，旧存储区随后释放。
指向旧存储的迭代器、指针、引用此时都悬空，继续解引用是未定义行为。
reserve 预留容量可减少扩容次数，但一旦仍触发扩容，失效规则不变。
遍历中若可能增删，优先下标、先记 size、或扩容完成后再取迭代器。
erase 后要使用返回的下一个迭代器；跨函数保存 begin() 长期持有也很危险。
2. unordered_map 最坏复杂度为什么会退化？工程上怎么防？
平均接近常数，依赖哈希均匀和合适的负载因子。
哈希冲突严重或遭遇对抗输入时，链过长或反复 rehash，可能接近线性。
自定义 key 若哈希质量差，会把大量元素打进少数桶。
关键路径可改有序容器、加盐哈希、限制 key 空间，并监控 bucket 分布与 rehash 次数。
3. 虚函数调用在汇编/对象模型层面大致怎么走？
带虚函数的类对象里通常有虚表指针，指向该类的虚函数表。
调用时先取对象 vptr，再按固定偏移取函数指针，最后间接调用。
多继承下可能有多个 vptr，或通过 thunk 调整 this。
因此虚调用一般难内联，存在间接跳转成本，热点路径要权衡。
构造/析构期间虚调用按当前构造到的类型分派，不是最终派生类完整形态。
4. 为什么有人说“能不用虚函数就不用”？什么场景反而必须用？
虚调用有间接跳转，且阻碍一些编译期优化。
对象会多占 vptr，缓存敏感场景更明显。
需要运行时按实际类型分派、稳定扩展插件式接口时，虚函数往往更合适。
5. sizeof 一个空类为什么通常不是 0？虚继承/虚函数会怎样？
C++ 保证不同对象有不同地址，空类也常占 1 字节占位。
一旦有虚函数，通常要为 vptr 付出指针大小。
虚继承还会引入虚基类相关偏移信息，对象布局更复杂、体积也可能变大。
最终大小还受对齐影响，成员顺序不同，sizeof 可能明显不同。
6. 讲清楚 new 失败、构造失败、delete 路径分别可能发生什么？
全局 new 默认失败抛 std::bad_alloc；nothrow new 失败返回空指针。
内存分配成功但构造抛异常时，会自动释放刚申请的原始内存，避免泄漏。
delete 会先调析构再释放存储；对数组要用匹配的 delete[]。
未配对的 new/delete、重复释放、释放非 new 地址都属于严重错误。
有基类指针删除派生对象时，基类析构一般应声明为虚，否则只析构基类部分。
7. shared_from_this 为什么不能在构造函数里用？错误用会怎样？
它依赖对象已被一个 shared_ptr 接管后建好的控制块。
构造阶段控制块通常还不存在，shared_from_this 会抛异常或陷入未定义行为路径。
正确做法是：对象创建完成后，由外部 shared_ptr 管理，再在成员函数里取 shared_from_this。
继承 enable_shared_from_this 时还要避免又用裸 new 造出第二套独立控制块。
8. std::move 之后对象处于什么状态？还能安全做什么？
move 本身只是把对象转成可被移动的右值，不一定立刻掏空资源。
被移动后的对象应处于有效但未指定状态，可以赋新值或销毁。
除非类型额外保证，否则不应再读它的业务值，更不要假设仍持有原资源。
9. 左值引用、右值引用、万能引用在函数模板里怎么区分？
具名对象通常是左值；字面量、临时量等常表现为右值。
T&& 在非模板语境多是右值引用；在模板参数推导里可能是万能引用。
万能引用结合引用折叠：传入左值可推成左值引用，传入右值可推成右值引用。
std::forward 用于保留值类别，实现完美转发。
误把成员 T&& 或具体类型 string&& 当成万能引用，是高频概念坑。
10. 为什么捕获列表乱写的 lambda 很容易把生命周期搞炸？
按引用捕获局部变量时，lambda 若逃逸出作用域，引用就悬空。
按值捕获会拷贝当时快照，不一定反映后续变化，大对象还有拷贝成本。
捕获 this 后，若对象先毁掉而回调后执行，就会空悬。
异步任务、线程池、定时器里投递 lambda，必须先确认捕获对象的寿命覆盖执行期。
11. mutex、recursive_mutex、shared_mutex 怎么选？
普通互斥保护共享可变状态，同一线程重复加锁会死锁，那就不该用递归锁硬补设计。
recursive_mutex 允许同线程重入，但容易掩盖调用结构混乱，优先重构调用链。
