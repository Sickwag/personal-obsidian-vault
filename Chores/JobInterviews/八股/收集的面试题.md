C++ 对象的内存布局由哪些因素决定？多重继承和虚继承会带来什么变化？
对象的内存布局通常由非静态数据成员、对齐填充、虚函数表指针、继承关系以及 ABI 共同决定。静态成员属于类本身，不存储在每个对象中；成员函数也不直接占用对象空间。

存在虚函数时，对象通常包含一个虚表指针 `vptr`。多重继承可能使派生类对象包含多个基类子对象，因此可能出现多个 `vptr`。虚继承还需要额外保存定位虚基类的信息，具体形式取决于编译器 ABI。

`std::map` 和 `std::unordered_map` 在高并发、恶意输入和迭代器稳定性方面有什么差异？
`std::map` 通常由红黑树实现，查找、插入和删除复杂度稳定为 `O(log n)`，键有序。插入操作通常不会使其他元素的迭代器失效，删除只会使指向被删除元素的迭代器失效。

`std::unordered_map` 通常由哈希表实现，平均查找复杂度为 `O(1)`，最坏情况下可能退化到 `O(n)`。当输入可由外部控制时，如果哈希函数容易被构造碰撞，攻击者可能制造大量冲突，使请求处理时间显著增加。

当 `unordered_map` 发生 `rehash` 时，所有迭代器都会失效，但元素的引用和指针通常仍然有效。并发环境下，两个容器都不能在没有同步措施的情况下被多个线程同时修改。即使操作的是不同键，内部树结构、桶数组和尺寸字段仍可能被共同修改。

如果要求稳定的最坏时间复杂度、有序遍历或范围查询，应优先考虑 `map`；如果输入可信、主要进行精确查找且对常数性能敏感，可以使用 `unordered_map`，同时提前 `reserve` 并选择可靠的哈希函数。
4. 红黑树为什么能保证近似平衡？插入和删除分别可能触发哪些调整？
答案：

红黑树通过颜色约束限制最长路径和最短路径之间的差距：

根节点是黑色；
空叶子节点视为黑色；
红色节点不能有红色子节点；
从任意节点到其所有后代空叶子的路径包含相同数量的黑色节点。
因此，根到叶子的最长路径不会超过最短路径的两倍，树高不超过 2log₂(n+1)，查找、插入和删除都能保持 O(log n)。

插入节点通常先标记为红色，避免直接改变黑高。如果父节点为红色，则根据叔叔节点颜色进行变色，或者通过左旋、右旋恢复约束。

删除更复杂。删除黑色节点可能破坏路径黑高，需要根据兄弟节点的颜色及兄弟子节点的颜色执行变色和旋转。工程实现中通常使用哨兵节点统一处理空节点，以减少分支。

5. shared_ptr 的控制块中保存了什么？为什么 make_shared 通常更高效？
答案：

shared_ptr 通常包含对象指针和控制块指针。控制块一般保存强引用计数、弱引用计数、删除器、分配器等信息。不同实现的具体字段可能不同。

直接使用 `shared_ptr<T>(new T) `时，对象和控制块通常进行两次独立分配。`make_shared<T>` 通常一次分配同时容纳对象与控制块，能减少分配次数并提升缓存局部性，也能避免参数求值过程中裸指针泄漏的问题。

不过，make_shared 也存在对象内存延迟释放的问题。当强引用计数变为零但仍存在 weak_ptr 时，对象已经析构，但合并分配的整块内存要等到弱引用计数归零后才能释放。对于体积非常大的对象，这一点可能比较明显。

此外，不能用两个独立的 shared_ptr 控制同一个裸指针，否则会产生两个控制块并导致重复释放。

`std::vector` 扩容时如何保证异常安全？移动构造不是 `noexcept` 会发生什么？

**答案：**

`vector` 扩容时会先申请一块更大的连续内存，然后把旧元素移动或复制到新内存。只有全部构造成功后，才销毁旧元素并释放旧内存。

如果类型的移动构造可能抛异常，但复制构造可用，标准库通常倾向于复制元素，以维持强异常保证。原因是移动过程中一旦抛出异常，已经被移动过的旧对象可能处于状态有效但内容不确定的状态，很难恢复扩容前的完整内容。

8. 进程切换和线程切换分别需要保存哪些状态？为什么协程切换通常更轻量？
答案：

线程切换通常需要保存和恢复寄存器、程序计数器、栈指针、线程局部状态以及调度信息。若切换到另一个进程，还可能需要切换页表相关状态，从而影响 TLB 和缓存命中率。

同一进程内的线程共享虚拟地址空间、代码段、堆和打开的文件，因此线程切换通常不需要替换完整地址空间。但线程仍由内核调度，切换可能涉及用户态和内核态转换。

协程通常由用户态运行时调度。栈式协程主要保存少量寄存器和栈上下文；无栈协程则被编译为状态机，在挂起点保存必要状态。协程不等于并行，它主要降低大量任务等待 I/O 时的调度成本。

协程也不是无条件更快。如果任务存在长时间 CPU 运算且不主动挂起，仍会阻塞其所在执行线程；如果生命周期和取消机制设计不当，还可能出现悬空引用、资源泄漏和任务无法回收的问题。

9. Linux 文件描述符与内核的文件对象之间是什么关系？dup 和 fork 后偏移量是否共享？
答案：

文件描述符是进程文件描述符表中的整数索引。表项通常指向内核的打开文件描述对象，该对象保存当前文件偏移、访问模式和状态标志，再进一步关联 inode 或套接字等底层对象。

dup 生成的新文件描述符与原描述符指向同一个打开文件描述对象，因此通常共享文件偏移量：

```
#include <fcntl.h>
#include <unistd.h>
 
int fd1 = open("data.txt", O_RDONLY);
int fd2 = dup(fd1);
```
 
// 从 fd1 读取会推进共享偏移量，随后 fd2 从新位置继续读取。
fork 后，子进程复制父进程的文件描述符表，但对应表项仍引用相同的打开文件描述对象，因此父子进程也可能共享文件偏移量。

两个线程或进程如果需要独立偏移量，可以分别 open 文件，或者使用 pread、pwrite 在不修改共享文件偏移量的情况下执行指定位置读写。

eventfd 和 pipe 都能用于线程唤醒，它们在语义和工程使用上有什么区别？
答案：

pipe 是字节流，有两个 fd，可以携带任意字节协议；eventfd 是内核维护的 64 位无符号计数器，只有一个对象，更适合表达“发生了若干次事件”。二者都可以被 epoll 监听。

普通 eventfd 每次读取会取走当前累计值并清零；使用 EFD_SEMAPHORE 后，每次读取只返回 1，并把计数减 1。写入可能发生合并，因此若任务队列才是事实来源，eventfd 应只承担唤醒作用，消费者被唤醒后应排空队列，而不能假设“一次读对应一个任务”。
pipe 更适合传输少量控制命令；eventfd 更轻量，也更适合线程池完成通知。需要注意计数器接近 UINT64_MAX - 1 时，非阻塞写会返回 EAGAIN。
7. 一个已经编译出的可执行文件，动态链接器如何完成符号解析与重定位？
答案：

程序启动时，内核映射 ELF 主程序和解释器，动态链接器读取 DT_NEEDED 加载依赖库，根据符号查找规则解析未定义符号，并处理重定位项。位置无关代码通常通过 GOT/PLT 间接访问外部符号。

函数符号可采用惰性绑定：第一次经过 PLT 时进入解析器，解析后把地址写入 GOT，后续直接跳转。设置 LD_BIND_NOW=1 或使用 -Wl,-z,now 可以在启动阶段完成绑定。-z relro 会在重定位后把相应区域改为只读；完整 RELRO 通常与立即绑定配合使用。

符号插桩、弱符号、版本符号、LD_PRELOAD 以及 ELF 可见性都会影响最终解析。插件系统若跨共享库传递 C++ 对象，还要同时考虑 ABI、编译器版本、标准库版本、异常和内存分配边界。

io_uring 的 SQPOLL 模式为什么不一定比 epoll 快？
SQPOLL 会创建内核轮询线程主动读取提交队列，用户线程提交请求后通常不需要执行 io_uring_enter，因此可以减少系统调用和用户态、内核态切换。但它并不是无条件更快。

低负载时，轮询线程会持续消耗 CPU；线程调度、NUMA 跨节点访问和共享队列缓存行抖动也可能抵消系统调用减少带来的收益。如果请求本身计算量较大，或者 I/O 完成间隔较长，SQPOLL 的收益通常有限。内核轮询线程与业务线程不在同一 NUMA 节点时，还可能产生大量远程内存访问。

另外，io_uring 的优势不只来自减少系统调用，还来自批量提交、批量收割和统一异步接口。如果程序每提交一个 SQE 就立即等待一个 CQE，仍然无法发挥其批处理能力。

实际使用时需要比较吞吐量、P99 延迟、CPU 利用率、上下文切换次数和每次 I/O 的指令数，而不是只比较 QPS。

* **缓存击穿**：某个热点 key 在缓存过期瞬间，同时有大量请求访问这个 key，导致所有请求都落到数据库上，造成数据库瞬时压力过大；
	* 如果业务允许的话，对于热点的 key 可以设置永不过期的 key。
	* 使用互斥锁。如果缓存失效的情况，只有拿到锁才可以查询数据库，降低了在同一时刻打在数据库上的请求，防止数据库打死。当然这样会导致系统的性能变差。
	* 使用 SingleFlight
* **缓存穿透**：查询不存在的数据，导致每次请求缓存都会询问数据库。相当于所有请求**直连数据库**
	* 设置空值 key，当查询缓存和数据库都不存在的数据时，记录下 `key=null`，下次查询相同的 key 只会经过缓存。但这种方法面对恶意攻击生成的随即 key 还是会让所有请求都经过数据库，且会导致缓存塞满垃圾 key（如果缓存算法使用的是类似 LRU 机制）。**目前对于随机 key 攻击，只能通过网关/中间件层面的基础参数校验，限制长度做到**
	* 应用程序到缓存中间设置布隆过滤器，先把所有合法的 ID（如全量用户 ID、商品 ID）提前加载到布隆过滤器中，但[[常用算法和情景处理#40 亿 qq 号去重但限制内存#布隆过滤器|布隆过滤器本质]]决定了迭代维护困难，不适合变更频繁的系统

5. 为什么 Redis 审计日志通常先写 Stream，再异步落 MongoDB？
答案：审计日志写入路径通常要求低延迟、可削峰和可追溯。直接同步写 MongoDB 会让业务请求受磁盘、索引、主从复制和网络抖动影响。

Redis Stream 可以作为短期缓冲层：业务线程只负责追加事件；消费者组异步批量写入 MongoDB；失败消息进入 Pending Entries List，支持重新认领和重试。对于不能丢失的审计事件，Redis 不应是唯一持久化介质，还需要使用 Kafka、WAL 或数据库 Outbox 保证最终可恢复。

3. MySQL 与 Redis 双写时，如何避免缓存中出现旧值覆盖新值？
答案：不能直接把“更新数据库后删除缓存”理解为绝对安全。并发场景下，线程 A 更新数据库并删除缓存，线程 B 在删除前读到旧数据库值并回填缓存，就可能造成旧值回填。

常见处理方式是延迟双删、订阅 binlog 异步失效、缓存值携带版本号，以及对关键写路径采用消息最终一致性。高一致性要求下，推荐以数据库提交后的 binlog 或 Outbox 事件作为缓存失效来源。

AI Agent 和传统大模型对话最大的区别是什么，Agent 的核心能力体现在哪些方面
答案：传统大模型对话更像一次性问答，它根据当前上下文直接给出答案。AI Agent 更强调目标驱动，它不是只回答问题，而是会围绕目标进行规划、拆解任务、调用工具、观察结果、修正计划，直到完成任务。

Agent 的核心能力主要体现在几方面：任务规划、工具调用、状态记忆、结果验证和失败重试。比如让普通模型“修一个 bug”，它可能只给建议；让 Agent 修 bug，它应该能读代码、定位文件、修改实现、运行测试、根据失败信息继续修正，最后给出变更摘要。

工程上 Agent 最大的难点不是会不会生成代码，而是能不能控制边界。如果工具权限太大，可能误删文件、误改接口；如果验证不足，可能生成错误修复。所以 Agent 设计里必须有权限隔离、任务 checkpoint、测试门禁和人工确认点。

AI 生成代码时如何判断它是正确的，如何避免把“看起来能跑”的代码合进去
答案：AI 生成代码最大的问题是它经常语法正确、风格合理，但边界条件不完整。判断正确性不能只靠阅读，必须结合测试、静态检查和实际运行。

我一般会先让需求变成可验证的测试，包括正常输入、空输入、非法输入、边界值、并发访问、资源释放和超时路径。AI 生成实现后，先跑单测，再跑 sanitizer，比如 ASan、UBSan、TSan，最后再看性能指标。对于 C++ 代码，还要重点检查所有权、异常安全、线程安全、迭代器失效、生命周期悬挂和内存序。

如果 AI 改的是核心链路，我会要求它输出修改点、影响范围、回滚方案和为什么不会破坏旧逻辑。真正能合入的不是“AI 说没问题”的代码，而是开发者能解释、测试能覆盖、review 能通过的代码。

C++ 对象模型中，一个包含虚函数的对象在内存里大致如何存储
答案：一个包含虚函数的对象，主流 ABI 下通常会在对象内部放一个虚表指针，也就是 vptr。vptr 指向该对象动态类型对应的虚函数表，虚函数表里保存虚函数地址，以及一些 RTTI 相关信息。

如果是单继承，通常对象开头有一个 vptr，后面是成员变量。如果是多继承，派生类对象里可能包含多个基类子对象，每个有虚函数的基类子对象都可能有自己的 vptr。如果是虚继承，还会有虚基类偏移相关信息，对象布局更复杂。

对象调用虚函数时，会通过 vptr 找到虚表，再根据虚函数槽位调用实际函数。这也是为什么虚函数调用通常比普通函数调用多一次间接寻址，并且有时影响内联优化。

什么时候不会发生内存碎片，内存碎片会带来哪些问题，如何缓解
答案：如果程序只使用固定大小对象，并且申请释放模式非常规则，内存碎片会比较少。比如对象池里每个块大小一致，释放后直接复用，就不容易产生外部碎片。但通用堆分配中，对象大小不一、生命周期交错，很容易产生碎片。

内存碎片主要分内部碎片和外部碎片。内部碎片是分配器给的块比实际需要大，多出来的空间浪费；外部碎片是总空闲内存够，但分散成很多小块，无法满足大块连续分配。碎片会带来内存占用上涨、缓存局部性变差、分配耗时抖动，严重时甚至 OOM。

缓解方式包括对象池、内存池、按 size class 分配、减少临时对象、复用缓冲区、使用 arena allocator，以及把不同生命周期的对象分区管理。在低延迟服务里，关键路径一般避免频繁 new/delete。
