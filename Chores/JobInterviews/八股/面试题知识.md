# 面试题知识点详解
本文件收录面试题涉及的底层原理与独到角度，配合 `收集的面试题.md` 的话术使用。

### Name Mangling
#### 基本原理
C 语言中函数名全局唯一，编译器直接使用原名。
C++ 编译器为支持函数重载、命名空间、类成员、模板等特性，在编译过程中根据这些信息将函数名、变量名等符号转换为唯一内部标识符。
不同编译器（GCC 与 MSVC）修饰规则不同，导致 C++ 二进制库不易跨编译器混用。
调试或逆向分析时可通过 `c++filt` 等工具将修饰名还原为可读形式。
#### 关闭方法
使用 `extern "C"` 告诉编译器"禁用 Name Mangling"。编写跨语言调用的动态库 DLL/SO 时，若想在不重编译大量文件的情况下更改符号名，可用：
- GCC / Clang 的 `asm` 标签：符号后添加 `__asm__("symbol_name")` 指定 mangling 名称
- MSVC 的 `.def` 模块定义文件：链接时提供 `.def` 文件强制映射导出名
```text
; my_library.def
EXPORTS
    my_clean_api_name = ?Bar@Foo@@QAEXXZ  ; 将 C++ mangled name 映射为纯 C 名字
```
源码里依然是 C++ 的 Mangling 名字，但链接器在生成 DLL 时对外暴露的符号被强制改成指定内容。

### ODR（One Definition Rule）
#### 基本原理
ODR 规定：整个程序中每个非 inline 的函数、变量、类模板实例只能有一个定义。
违反分两类：
- 同一编译单元重复定义 -> 编译报错
- 跨编译单元多个等价定义 -> 链接报多重定义

#### ODR 的例外（允许多处定义）
1. **类定义**：可出现在每个包含其头文件的编译单元，但所有定义必须 token 级一致--"一份定义，多处可见"。
2. **inline 函数/变量**（C++17 inline 变量）：可跨编译单元多处定义，链接器合并为一份，要求各份等价。
3. **模板实例化**：隐式实例化可多处，链接器去重。
#### 为什么 inline 能绕过
inline 是对链接器的承诺："此符号可能多处定义但都等价，任选一份"。
编译器把 inline 实体标为 weak symbol（COMDAT 段），链接器见多个同名 weak 只保留一份。
故头文件 `inline int g_y = 0;` 多份包含不报错。
#### LTO 并不能完全检测 ODR 违规
GCC/Clang 的普通 LTO（`-flto`）把各编译单元的 IR 合并后做全局优化，如果两个翻译单元的 inline 函数实现不同，会**随机保留其中一个，不会报错**。
真正能检测某些 ODR 违规的是编译器的 `-Wodr` 警告（在编译期检测同名函数签名不一致），但对函数体内部逻辑差异（如 `#ifdef DEBUG` 导致不同分支）无法检测。
ODR 违规属于未定义行为，编译器/链接器不保证检测，在添加一些编译选项之后也最多只会给出警告，检测需要依赖静态分析工具（如 Clang Static Analyzer）。

### 符号表与地址重定位
#### 符号表
编译器为每个翻译单元生成的映射表，记录每个符号的：
- 名字、绑定属性（local/global/weak）
- 所在段（.text/.data/.bss）、段内偏移
- 类型、大小

两种符号表：
- `.symtab`：完整静态符号表（含本地符号），仅供链接/调试，运行时不加载
- `.dynsym`：动态符号表，仅跨模块导出/导入符号，运行时加载

查看命令：`nm a.out`、`objdump -t`、`readelf -s`。
#### 地址重定位
独立编译时编译器看不到外部符号最终地址，做法：
1. 本单元定义的符号 -> 符号表记"段内相对偏移"
2. 引用的外部符号 -> 指令中先填 0 占位，并在重定位表（`.rela.text`）记一条："偏移 X 处引用符号 Y，类型 R_X86_64_PLT32 等"

链接时链接器合并所有段、确定每个符号最终虚拟地址，扫描重定位表回填占位符--静态重定位。
#### 动态重定位（PLT/GOT）
动态库符号地址运行时（ASLR 后）才知：
- **GOT**（全局偏移表）：存外部符号运行时地址，首次调用由 ld.so 延迟填入（懒绑定）
- **PLT**（过程链接表）：跳转桩，首次经 PLT 触发 ld.so 解析并填 GOT，后续直接跳

查看：`objdump -R`、`readelf -r`。
#### 独到角度：为什么静态链接去重、动态链接延迟
静态链接期就能看到所有符号，直接回填。
动态链接面对两个约束：
- ASLR：每次运行库加载地址不同
- 共享库多进程共用：不能改只读 .text，否则破坏共享页

故把"可变地址"集中到 GOT（数据段，每进程私有副本），.text 保持只读共享。
延迟绑定省启动时间，共享只读代码页省内存--性能与内存的精妙权衡。

### 单/多继承虚函数表布局与覆盖
#### 基础概念
- **虚函数表（vtable）**：每个有虚函数的类有一张虚表，本质是函数指针数组，按虚函数声明顺序存储该类各虚函数的入口地址
- **虚表指针（vptr）**：每个含虚函数的对象头部有一个 vptr 指向其类的虚表。编译器在构造函数里自动设置 vptr
- **虚表是类级别的**，同一个类的所有对象共享同一张虚表，vptr 只是指向它

#### 单继承：对象只有一张虚表
```cpp
class Base {
    virtual void f();
    virtual void g();
};
class Derived : public Base {
    void f() override;
    virtual void h();
};
```
Base 对象布局：`[vptr -> Base 的虚表]`
Derived 对象布局：`[vptr -> Derived 的虚表]`

Derived 的虚表：
- `f()`：Derived 重写了，放 Derived::f 的地址
- `g()`：Derived 没重写，**继承 Base::g 的地址**
- `h()`：Derived 新增的虚函数，追加到虚表末尾

**关键**：单继承下对象只有一个 vptr，虚表长度 = 基类虚函数数 + 派生类新增虚函数数，未重写的槽位保留基类函数地址。

#### 多继承：对象有多个 vptr
```cpp
class Base1 { virtual void f(); virtual void g(); };
class Base2 { virtual void h(); };
class Derived : public Base1, public Base2 {
    void f() override;
    void h() override;
    virtual void k(); // Derived 自己新增
};
```
Derived 对象布局（按继承顺序拼接）：
```text
+--[Base1 子对象]--+--[Base2 子对象]--+--[Derived 成员]--+
| vptr1            | vptr2            | Derived 自有成员  |
+------------------+------------------+-----------------+
```
- **vptr1**（主虚表）：`[Derived::f, Base1::g, Derived::k]`
  - `f()` 覆盖了；`g()` 继承；`k()` 新增追加到主虚表末尾
- **vptr2**（Base2 虚表）：`[Derived::h]`
  - `h()` 覆盖了 Base2::h
- 当使用 `B* ptr = new C();` 时，编译器会自动将指针地址进行偏移（加上 A 部分的大小），使其准确指向对象内部的 B 部分起始位置。
- Derived 自身新增的虚函数通常会被追加到第一个基类（即 A）的虚表末尾，而不会为 C 单独再生成一个全新的 vptr。
#### this 调整与 thunk（重要难点）
问题：`Base2* p = &derived;` 时，p 不指向对象头部（对象头部是 Base1 子对象），而是指向 Base2 子对象的偏移位置（sizeof(Base1) 之后）。
调用 `p->h()` 时，`p->h()` 通过 vptr2 查到 Derived::h，但 Derived::h 的隐含 this 是 Derived*（对象头部），而 p 是 Base2*（对象中部），this 不匹配。

**解决方案：non-virtual thunk**
编译器在 vptr2 的虚表里放的不是 Derived::h 的直接地址，而是一段 thunk 代码：
1. 先把 this 减去偏移（sizeof(Base1)）回到对象头部（Derived*）
2. 再跳转到 Derived::h

```text
Base2* p = &derived;      // p 指向 Base2 子对象（偏移 sizeof(Base1)）
p->h();                   // 调用流程：
                          // p -> vptr2 -> thunk -> this -= sizeof(Base1) -> Derived::h()
```

#### 独到角度：为什么多继承虚表不能合并成一张
合并要求所有基类共用一张虚表，但不同基类指针指向对象内不同偏移，this 值不同。
如果共用：`Base2*` 调用时 vptr 在对象头部（Base1 位置），Base2 子对象在中部根本找不到 vptr。
所以多继承必须每个含虚函数的基类子对象各带一个 vptr。这也是 COM（C++ 多继承二进制标准，Windows 上的基础 ABI）对象布局的基础：每个接口继承一个 vptr，对象大小 = 接口数 * 8（64 位）+ 自有数据。

### 容器适配器对底层容器的约束
#### 基本原理
容器适配器（priority_queue、stack、queue）不是独立容器，是"包装一个序列容器 + 限定接口"。
对底层容器的约束由适配器调用的操作集决定：

| 适配器 | 需要的操作 | 可用底层容器 |
|--------|-----------|--------------|
| stack | back/push_back/pop_back | vector/deque/list |
| queue | front/back/push_back/pop_front | deque/list（vector 无 pop_front） |
| priority_queue | front/push_back/pop_back + 随机访问迭代器 | vector/deque（list 无随机访问） |

#### priority_queue 的随机访问要求
堆算法（push_heap/pop_heap）用下标算父子：
- 父 i，左子 `2i+1`，右子 `2i+2`

这要求 `c.begin()` 是随机访问迭代器（支持 `it+n` O(1)）。
vector/deque 满足；list 迭代器是双向的，不支持 `+n`，故 list 不能做 priority_queue 底层。
#### 为什么 deque 虽分段连续也能用
deque 迭代器重载了 `operator[]`/`operator+`/`operator-`，内部跨缓冲区跳转，对外提供随机访问语义（O(1)）。
堆算法只依赖迭代器抽象，不关心底层是否物理连续。
所以"能否做底层容器"取决于迭代器类别，非内存连续性。

### 虚拟内存深入：内核空间、线程与内存分区
#### 为什么每个进程都有内核空间
进程进入内核态（系统调用、中断、异常）时，CPU 切换到内核栈执行内核代码。
把内核映射进每个进程虚拟地址空间的高半区：
- x86-64 用户态：`0 ~ 0x00007FFF_FFFFFFFF`
- x86-64 内核态：`0xFFFF8000_00000000 ~ 0xFFFFFFFF_FFFFFFFF`

这样切换进程时只需换用户态页表项、内核映射保持不变。
内核空间在所有进程的虚拟地址里映射到**同一片物理页**（共享），而非每进程一份。
用户态直接访问内核地址会触发段错误（权限位保护）。
#### 线程的地址空间
线程不拥有独立地址空间：同进程线程共享同一虚拟地址空间（同一份页表）。
共享的内容：.text/.data/.bss/堆/全局变量/mmap 区。
线程私有的内容：
- **线程栈**：在共享地址空间内划一段（默认 8MB，可 pthread_attr 设置），向下生长
- **线程局部存储 TLS**：`thread_local` 变量，每线程一份
- **寄存器上下文**：PC/SP

"线程堆栈"指这块私有栈区，不是独立的地址空间。
线程间通信天然靠共享内存（同一地址空间），这也是线程通信快于进程通信（需 IPC）的根本原因。
#### .text 段的"代码"是什么
是机器指令（CPU 直接执行的二进制编码）。
.text 是编译后的可执行指令序列，通常只读+可执行（防篡改、防误写）。
.text 段在所有运行同一程序的进程间共享只读物理页（fork 后 COW 之前父子也共享）。
#### 符号表在内存分区的位置
符号表不在进程运行时内存分区的常规段（.text/.data/.bss/堆/栈）里。
它是 ELF 文件的 section：
- `.symtab`：静态符号表，加载到内存时默认不映射（运行时无用）
- `.dynsym`：动态符号表，会被映射（动态链接需要）
调试信息、符号表不在 .text（在 .debug/.symtab），调试器单独读 ELF 文件的这部分获取信息，它是文件结构，非运行时内存段。
#### 独到角度：虚拟内存是"隔离"还是"共享"的统一抽象
虚拟内存常被理解为"隔离每进程"，但它同时也是"共享"的基石：
- 共享库 .text 在所有进程映射到同一物理页（节省内存）
- fork 后父子 COW 共享页直到写
- mmap 共享内存让不相关进程通信

同一套"虚拟页->物理页"映射机制：
- 页表项指向同一物理页 -> 实现共享
- 页表项指向不同物理页 -> 实现隔离

隔离与共享是同一枚硬币两面，取决于页表项如何指向。
这是理解进程间通信（共享内存最快）和内存效率的关键。

### 面向对象的独到理解
#### C++ OOP 不是"纯"OOP
C++ 不是纯面向对象语言（不像 Java 一切皆对象、单根继承 Object）。
它的 OOP 建立在 C 的值语义和零开销抽象之上，是"可选工具"：
- 可纯面向对象
- 也可把对象当值拷贝、放栈上、用 RAII 管资源
- 甚至完全不用类写过程式代码

C++ 的多范式（过程、OOP、泛型、函数式）让 OOP 是"可叠加的工具"而非"强制的世界观"。
#### 值语义 vs 引用语义（C++ vs Java OOP 本质区别）

| 维度 | Java | C++ |
|------|------|-----|
| 语义 | 引用语义 | 值语义 |
| 对象分配 | 只能堆分配 | 可栈可堆 |
| 变量存 | 引用 | 对象本身 |
| 赋值/传参 | 拷贝引用 | 拷贝对象（需拷贝构造/赋值） |
| 对象身份 | 靠引用 | 就是它自己 |
| 继承 | 单根继承 Object | 多继承 |

C++ 的拷贝/移动/析构是 Java 没有的核心复杂度，也是性能（避免堆分配/GC）和灵活性（RAII、确定性析构）的来源。代价是"三/五法则"的心智负担。
#### OOP 三大特性的 C++ 视角
- **封装**：访问控制（public/protected/private）+ 数据与行为绑定。C++ 的封装是编译期约束，可被 friend/指针算术绕过（非绝对安全）。
- **继承**：代码复用 + is-a 关系。C++ 多继承 + 虚继承解决菱形问题，但复杂度高。现代 C++ 倾向"组合优于继承"。
- **多态**：静态（重载/模板/CRTP，零开销）+ 动态（虚函数，vtable 间接）。C++ 区分二者，不像 Java 默认虚方法。
#### 独到角度：OOP 的真正价值是"管理复杂度"而非"模拟现实"
教科书说 OOP 是"用对象模拟现实世界"，这是误导。
OOP 的真正价值是控制变更的影响范围：
- 封装 -> 数据结构变更只影响类内部
- 继承 -> 接口稳定实现可换
- 多态 -> 调用方不依赖具体类型

衡量 OOP 设计好坏不是"是否像现实"，而是"变更某需求时影响面多大"。
C++ 的多范式恰恰承认：不是所有问题都该用对象建模：
- 算法密集型 -> 泛型（STL）
- 状态转换 -> 过程
- "有状态+多行为"的实体 -> 对象

盲目 OOP（万物皆对象）会制造不必要的间接层。

### 非比较排序算法详解
#### 比较排序的下界证明
n 个元素有 n! 种合法排列，比较排序每次比较得 1 bit 信息，决策树至少需 n! 个叶子。
树高 h 满足 `2^h >= n!`，故 `h >= log2(n!) = Ω(n log n)`（Stirling：log2(n!) ≈ n log n - 1.44n）。
所以任何比较排序（快排/归并/堆）最坏都 ≥ n log n。
要突破必须利用数据本身的数学特性。
#### 计数排序（Counting Sort）
- **原理**：找 min/max 定范围 k=max-min+1 -> 建 count[k] 统计频次 -> 前缀和（count[i] 变为"<=i 的元素总数"）-> 反向遍历原数组按 count 定位放入结果，count 递减
- **复杂度**：时间 O(n+k)，空间 O(n+k)
- **关键**：反向遍历保证稳定性（同值元素保持原序），这是能做基数排序子程序的前提
- **局限**：k>>n（10 个元素值域 1~10 亿）时退化为 O(k) 且撑爆内存；仅适用整数或可映射为整数的离散值
#### 桶排序（Bucket Sort）
- **原理**：按映射函数（如 `index=(v-min)/range*m`）分到 m 个桶，桶内排序（可用比较排序或计数），依序拼接
- **复杂度**：平均 O(n+k)（数据均匀时每桶元素少），最坏 O(n^2)（全进一桶退化为桶内排序）
- **适用**：数据量大且分布均匀（如 0~1 均匀小数、考试成绩集中区）
- **局限**：极度依赖分布，不均则断崖式下跌
#### 基数排序（Radix Sort）
- **原理**：按位从低到高，每位用稳定排序（通常计数排序）排一遍，直到最高位
- **复杂度**：O(d·(n+k))，d=最大位数，k=基数（十进制 k=10）。d、k 常数级故近似 O(n)
- **关键**：必须用稳定排序做子程序，否则高位排序破坏低位已排好的相对顺序
- **局限**：仅适用可按位拆分数据（整数、字符串）；负数需偏移；浮点数需转整数表示
#### 为什么 std::sort 不用它们
1. **泛型**：std::sort 只要 `operator<`，能排任意类型（含自定义 struct）；非比较排序要求数据是整数/可按位拆分/范围已知，泛型能力弱。
2. **空间**：std::sort（Introsort）原地，仅 O(log n) 递归栈；非比较排序空间换时间 O(n+k)，内存敏感场景不可接受。
3. **最坏抗性**：std::sort 最坏稳定 O(n log n)；桶排序最坏退化，计数排序 k 大时内存溢出。
#### 独到角度：非比较排序的"信息论"本质
比较排序每次比较得 1 bit，n log n 次比较才足够区分 n! 种排列。
非比较排序之所以能 O(n)，是因为它通过"值本身"（而非两两比较）直接获取多于 1 bit 的信息--计数排序一次遍历就知道了每个元素的精确位置（值即索引）。
本质是用"数据的结构化信息"换取"比较次数"。
这解释了：
- 对任意类型（无结构信息）-> 只能 n log n
- 对整数（有数值结构）-> 能 O(n)
信息获取的渠道决定了下界。
### volatile、atomic 与内存屏障
#### volatile 的真实语义
C++ 的 volatile 仅意味着"对它的访问是可观察的副作用，编译器不得优化掉/合并/缓存到寄存器"。
保证：
- 每次读真的从内存读
- 每次写真的写内存
- 不重排 volatile 访问

**不**保证：
- 原子性（64 位变量在 32 位机上读写可能撕裂）
- 内存可见性（不插 CPU 内存屏障）
- 有序性（不阻止非 volatile 访问围绕它重排）
#### volatile 不保证可见性的根因
现代 CPU 多核各有 L1/L2 缓存。线程 A 写变量后，若无内存屏障：
- 写可能停留在 A 的 store buffer 或缓存中
- 未传播到 B 的缓存（MESI 协议的同步需要显式屏障触发）

volatile 只阻止编译器缓存到"寄存器"，但阻止不了 CPU 缓存不一致。
所以 A 写 volatile 后 B 读到的可能是旧值。
#### atomic 的保证
`std::atomic<T>` 提供三层保证：
1. **原子性**：读写不可分割（用锁指令/CAS 实现，64 位在 32 位机也不撕裂）
2. **可见性**：默认 memory_order_seq_cst 插全屏障，写后其他线程立即可见
3. **有序性**：指定内存序（relaxed/acquire/release/acq_rel/seq_cst）控制重排
#### 内存屏障（Memory Barrier / Fence）
CPU 指令级别的同步原语，阻止编译器和 CPU 重排内存访问：
- Load-Load / Store-Store / Load-Store / Store-Load 屏障
- acquire 屏障：之后的读写不能重排到屏障前（读后不前移）
- release 屏障：之前的读写不能重排到屏障后（写前不后移）
- seq_cst：全局总序，最强但最慢

atomic 的各种 memory_order 本质是编译器在对应位置插入相应屏障。
#### 独到角度：Java volatile vs C++ volatile 的语义分裂
Java 的 volatile 等价于 C++ 的 `atomic<T>` + seq_cst（保证可见性+有序性），是真正的同步原语。
C++ 的 volatile 沿袭 C，是为硬件寄存器/中断设计的"别优化"标记，不是同步原语。
两者同名但语义天差地别--这是语言历史包袱：
- C++ 保留 volatile 给嵌入式/驱动（MMIO）
- 另造 atomic 给并发

理解这点就不会误用 volatile 做线程同步。
补充：C++20 起 deprecated volatile 的一些用法（如 volatile 复合赋值），进一步收缩其语义到"纯防优化"。
#### 何时必须用 volatile
1. **内存映射 IO 寄存器（MMIO）**：每次读写要真正打到硬件，不能合并/缓存
2. **信号处理函数中修改、主程序读取的标志**：防编译器把读提到循环外
3. **setjmp/longjmp 后被修改的局部变量**：防编译器把变量缓存在寄存器导致 longjmp 回来值丢失

这三类都是"程序控制流之外被改"，编译器优化会破坏语义。
多线程共享变量永远用 atomic/mutex，不用 volatile。
