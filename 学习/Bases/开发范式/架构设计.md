# 计算机基本认识
## 进程和线程
### 栈空间
- `ulimit -s` 控制**每个线程**的栈大小上限（Linux 默认8MB），超过触发 SIGSEGV
- 同一进程内所有线程的栈都在进程虚拟地址空间内，但由 OS 保证物理页不重叠
- **线程栈之间没有硬件/OS层面的隔离保护**：线程A拿到线程B栈变量的地址，可以正常读写。栈的"隔离"是语言作用域规则的约定，不是OS的强制保护，但是实际编程中**两个线程不可能拿到对方栈对象的内存地址**

### 堆空间
- 同一进程所有线程共享堆，`new` / `malloc` 出的内存任何线程都能访问，是同一个内存分配器（malloc/free）管理的区域，所有线程通过该分配器拿到的地址，
  都在这块区域内。所以线程 A new 的对象，把地址传给线程 B，B 可以访问。
- 堆上的并发安全需要程序员自行保证（锁、原子操作等）
### mmap 系统调用
`mmap` 的本质是**将虚拟地址空间映射到某个后端**，后端可以是文件或匿名内存。

**三种主要用途：**

| 类型   | 标志                        | 说明                                      |
| ---- | ------------------------- | --------------------------------------- |
| 文件映射 | `MAP_SHARED`              | 映射文件内容到内存，读写直接反映到文件                     |
| 匿名映射 | `MAP_ANONYMOUS`           | 不关联文件，纯内存分配（malloc 大块(>128kb)时底层用 mmap） |
| 共享内存 | `MAP_SHARED` + `/dev/shm` | 多个进程映射同一物理页面，实现 IPC                     |

**mmap 底层流程：**
```
mmap(addr, length, prot, flags, fd, offset)
                    │
                    ▼
        用户态：调用 mmap 系统调用
                    │
                    ▼
        内核态：do_mmap()
        1. 在进程的虚拟地址空间中找一块空闲区域
        2. 建立 vma（vm_area_struct）描述该区域属性
        3. 区域标记为"未映射"——页表还不存在
                    │
                    ▼
        返回虚拟地址，但此时对应的物理页 = 不存在
                    │
        第一次访问该地址 → 触发缺页中断（page fault）
                    │
                    ▼
        内核：缺页中断处理
        1. 检查 vma，确认访问合法
        2. 文件映射：从磁盘读取文件内容到物理页
        3. 匿名映射：分配一个物理页，全零填充
        4. 建立页表映射（虚拟地址 → 物理地址）
                    │
                    ▼
        返回用户态，指令重新执行，访问成功
```

**mmap vs read() 对比：**
- `read()/write()`：用户空间 ↔ 内核空间，缓冲区 ↔ 硬件，两次拷贝 ↔ 上下文切换
- `mmap`：直接在用户空间映射页表，缺页中断时加载，零拷贝

### 虚假唤醒（Spurious Wakeup）
**条件变量上为什么需要防止虚假唤醒？**
因为即使没有线程调用 `notify_one()`/`notify_all()`，`wait()` 也可能返回。原因：

- **OS 信号被中断**：`pthread_cond_wait` 返回 EINTR
- **多核竞争**：线程在 `wait` 内部释放锁和进入等待之间存在窗口，`notify` 先于 wait 到达
- **硬件层面**：某些 CPU 架构在总线广播时广播唤醒信号
- **POSIX 标准化**：标准明确允许虚假唤醒，所以 `pthread_cond_wait` 返回时不保证条件成立

**标准的 wait 模式：**
```cpp
// 必须用 while 循环检查条件，不能用 if
while (!predicate()) {
    cv.wait(lock);
}
// C++20 的 lambda 版本内部也是 while 循环
cv.wait(lock, []{ return predicate(); });
```
# 后端组件
## 无锁队列
无锁队列（Lock-Free Queue）是一种不使用锁机制（如互斥锁或读写锁）来实现线程安全的数据结构，是 lock-free 中最基本的数据结构。

|       | 锁（Mutex）            | 无锁（CAS）             |
| ----- | ------------------- | ------------------- |
| 思路    | 悲观——肯定会冲突，先拿锁再操作    | 乐观——冲突概率低，直接操作，失败重试 |
| 阻塞    | 线程阻塞（上下文切换，~1us 开销） | 线程不阻塞（自旋重试，~10ns）   |
| 死锁    | 可能                  | 不可能                 |
| 优先级反转 | 可能                  | 不可能                 |
| 适用场景  | 临界区大、操作复杂           | 临界区小、操作极快           |

### Epoch-based Reclamation（EBR）详解

**核心思想：** 全局纪元计数器在 0、1、2 之间循环。每个线程声明自己在哪个纪元中。当所有线程都离开某个纪元后，该纪元中"退休"的节点就可以安全删除。

**为什么可靠：** 如果在某个时刻，所有线程都在纪元 N 或 N+1，没有任何线程在纪元 N-1，那么纪元 N-1 中退休的节点一定不会被任何线程持有引用。

**详细流程：**
```
时间线：
                    所有线程离开 e0  →  所有线程离开 e1
e0 ────────────────── e1 ────────────────── e2 ──→
                    ↑                    ↑
               e0 的退休列表可删除    e1 的退休列表可删除

线程 A 读端：
  1. 记录当前纪元 e = global_epoch
  2. 递增 active_count[e]
  3. 读数据...
  4. 递减 active_count[e]

线程 B 写端（准备删除节点）：
  1. 将节点放入 retired[(global_epoch + 1) % 3]
  2. 检查 global_epoch 的 active_count 是否为 0
  3. 如果是，推进 global_epoch，删除上一纪元的节点
```

### RCU（Read-Copy-Update）详解

**核心思想：** 读者永远不阻塞。写者创建新副本，原子发布，等待所有在读读者完成，最后删除旧副本。

**为什么读端零开销：** 读端只是读取一个指针，然后访问数据。没有原子操作，没有锁，没有屏障（在支持 RCU 的架构上）。

**详细流程：**
```
读者（线程 A）：
  p = shared_ptr        ← 普通指针读，无原子操作
  use(p->data)           ← 正常使用数据
  // 不需要解锁 —— 没有锁

写者（线程 B）：
  old = shared_ptr      ← 保存旧指针
  new = copy(old)       ← 复制整个数据结构
  new->data = update    ← 修改新副本
  rcu_assign_pointer(shared_ptr, new)  ← 原子发布（带 release 屏障）
  synchronize_rcu()     ← 等待所有在读读者完成
  delete old            ← 安全删除

关键：在 synchronize_rcu() 期间，新的读者看到的是新指针
     旧的读者可能还在使用旧指针
     synchronize_rcu() 返回时，所有旧读者都已经退出
```

**对比：**

| 特性 | EBR | RCU |
|------|-----|-----|
| 读端开销 | 2 次原子操作 | 零 |
| 写端延迟 | 下个纪元 | 等待所有读者 |
| 适用场景 | 通用 MPMC | 读多写极少 |
| 读端是否阻塞 | 否 | 否 |
| 写端是否阻塞 | 否（批量删除） | 是（synchronize_rcu） |

### 链表的 SPSC（经典实现）

 核心思想：单一写者、单一读者，双方各管各的指针，不需要 CAS。
 经典实现:
 ```cpp
 template <typename T>
 class SinglePopPush {
   private:
 	struct node {
 		std::shared_ptr<T> data;
 		node*			   next;
 
 		node()
 			: next(nullptr) {}
 	};
 
 	std::atomic<node*> head;
 	std::atomic<node*> tail;
 
 	node* pop_head() {
 		node* const old_head = head.load();
 		// ⇽-- - 1
 		if(old_head == tail.load()) {
 			return nullptr;
 		}
 		head.store(old_head->next);
 		return old_head;
 	}
 
   public:
 	SinglePopPush()
 		: head(new node)
 		, tail(head.load()) {}
 
 	SinglePopPush(const SinglePopPush& other)			 = delete;
 	SinglePopPush& operator=(const SinglePopPush& other) = delete;
 
 	~SinglePopPush() {
 		while(node* const old_head = head.load()) {
 			head.store(old_head->next);
 			delete old_head;
 		}
 	}
 
 	std::shared_ptr<T> pop() {
 		node* old_head = pop_head();
 		if(!old_head) {
 			return std::shared_ptr<T>();
 		}
 		// ⇽-- -2
 		const std::shared_ptr<T> res(old_head->data);
 		delete old_head;
 		return res;
 	}
 
 	void push(T new_value) {
 		std::shared_ptr<T> new_data(std::make_shared<T>(new_value));
 		// ⇽-- - 3
 		node* p				 = new node;
 		// ⇽-- - 4
 		node* const old_tail = tail.load();
 		// ⇽-- - 5
 		old_tail->data.swap(new_data);
 		// ⇽-- - 6
 		old_tail->next = p;
 		// ⇽-- - 7
 		tail.store(p);
 	}
 };
 ```
 几个特点:
 - 使用 dummy node，用于保证 head 和 tail 永远不指向同一个可读写的节点，消费者只读 head 指向的节点（即旧 dummy），生产者只写 tail 指向的节点（新节点），两者永远操作不同的节点 → 不需要锁！
 - 全部用 seq_cst（默认），安全但慢。但 SPSC 中 head 只由消费者修改，tail 只由生产者修改，没有竞争。唯一的同步点在于：消费者读 tail（acquire）**之前**必须看到生产者写 tail（release）之前的所有数据写入。
 - 不是整整的无锁，new 操作可能触发 OS 锁（malloc 内部有锁），真正的无锁队列应该预分配内存或使用无锁分配器。
 - 是一个**无界队列**，push 永远成功（通过 new 加入链表）
 - 析构是非线程安全的，析构时另一个线程可能正在 push/pop 
**设计理念：**
- 使用虚拟节点（dummy node）保证 head 和 tail 永远不指向同一个可读写节点
- 消费者只读 head 指向的节点（旧 dummy），生产者只写 tail 指向的节点（新节点）
- 两者永远操作不同的节点 → 不需要锁，不需要 CAS

**数据流追踪：**
```
初始：head → dummy, tail → dummy

push(1):
  old_tail = tail = dummy
  dummy.data = 1
  dummy.next = new_node
  tail = new_node

pop(1):
  old_head = head = dummy
  head != tail ✅
  head = dummy.next = new_node
  res = dummy.data = 1
  delete dummy
```

**问题：**

| 问题 | 说明 |
|------|------|
| 全部 seq_cst | 安全但慢，x86 上每次 tail.store 生成 mfence |
| 不是真正的无锁 | new/delete 内部有 malloc 锁 |
| 无界 | push 永远成功，内存可能耗尽 |
| 析构不安全 | 析构时如果另一个线程在 push/pop，use-after-free |
| cache 性能差 | 链表节点分散在堆上，每次访问都是 cache miss |

### 环形缓冲区的 SPSC（真正的无锁）
**设计理念：**
- 预分配固定大小的数组，无动态内存分配
- 一个空槽位区分满和空
- 生产者写 tail，消费者读 head，各管各的指针

**正确性：**
```cpp
bool push(const T& val) {
    size_t t = tail.load(relaxed);        // 只有生产者改 tail
    size_t n = next(t);
    if (n == head.load(acquire))          // 看到消费者的释放
        return false;
    buffer[t] = val;                       // 写数据
    tail.store(n, release);                // 发布给消费者
    return true;
}

bool pop(T& val) {
    size_t h = head.load(relaxed);         // 只有消费者改 head
    if (h == tail.load(acquire))           // 看到生产者的发布
        return false;
    val = buffer[h];                        // 读数据
    head.store(next(h), release);          // 发布给生产者
    return true;
}
```

**为什么不需要 CAS：** SPSC 中 head 只由消费者修改，tail 只由生产者修改，没有竞争。唯一的同步点在于消费者读 tail 时必须看到生产者写 tail 之前的所有数据写入。

### Michael-Scott 无锁队列（MPMC）
第一个实用的多生产者多消费者（MPMC）无锁 FIFO 队列，1996 年由 Maged Michael 与 Michael Scott 提出，至今仍是多数无锁队列的基础。

**三个核心设计：**

**1. 虚拟头节点（dummy head）**
```
head → [dummy] → [node1] → [node2] → null
       ↑哨兵        ↑ pop 总是移除 dummy 后面的节点
```
- head_ 指向哨兵节点，pop 总是移除 head_->next（即第一个真实节点）
- 空队列判定：head == tail 且 head->next == null
- 好处：pop 后 dummy 变成已出队的节点，head 与 tail 永远不会指向同一个"待读取"节点

**2. CAS 作为唯一同步点**
- push：CAS `tail_->next` 从 null → 新节点（竞争生产者谁先连上）
- pop：CAS `head_` 从 dummy → dummy->next（竞争消费者谁先出队）
- CAS 失败 → 读取最新值重试

**3. Helping 机制（协作推进）**
```
push 中发现 tail_->next != null：
  说明有生产者已连上节点但还没来得及推进 tail_
  → 主动帮它推进 tail_，自己再重试
```
- 没有 helping：如果某个生产者推进 tail_ 前被调度出去，其他生产者会永远卡住（obstruction-free，不是 lock-free）
- 有 helping：任何一个线程失败都能被其他线程"救活" → 保证整个系统前进（lock-free）

**正确性验证：**
```
push 的循环不变式：
  tail_ 永远指向链表最后一个或倒数第二个节点
  tail_->next != null 时，一定有另一个生产者正在帮它推进

pop 的循环不变式：
  head == tail 且 next == null → 空，返回 false
  head == tail 但 next != null → tail 落后，帮推进后重试
```

**关键内存序：**
| 操作 | 内存序 | 原因 |
|------|--------|------|
| CAS tail->next (push) | release | 新节点的 value 必须对 pop 方可见 |
| CAS head_ (pop) | acq_rel | 读端看到数据 + 写端释放 dummy |
| 推进 tail_ (helping) | acq_rel | 其他线程要看到链表状态 |

**与 SPSC 对比：**

| | SPSC 环形缓冲区 | Michael-Scott |
|---|---|---|
| 支持的生产者/消费者 | 1/1 | N/N |
| 同步原语 | acquire/release | CAS + acquire/release |
| 内存分配 | 预分配，零 | 每 push 一次 new |
| 内存回收 | 无（固定数组） | 需要 hazard pointer / EBR / RCU |
| 无界/有界 | 有界（固定容量） | 无界 |
| FIFO 保证 | 严格 FIFO | 单生产者严格 FIFO；多生产者时同一生产者的项保序，跨生产者不保证 |
| ABA 风险 | 无 | 有（生产环境需标记指针等方案） |
| 典型吞吐 | ~270 M ops/s（SPSC） | ~6.5 M ops/s（同测试 SPSC 对比） |

**为什么教学版会泄露内存（即 ABA 如何被"避开"）：**
pop 移除的 dummy 节点不 delete，直接泄露，进程退出时由 OS 回收。节点地址永不复用 → CAS 永远不会遇到"地址复用回旧值" → ABA 问题不发生。生产环境必须用 hazard pointer / EBR / RCU 回收，此时就必须处理 ABA。

### 演进逻辑：Michael-Scott → 链表 SPSC → 环形缓冲 SPSC

这三个实现不是并列的，而是**同一条演进链上的三个节点**。每一代都解决上一代的一个核心不足。

**演进链条：**
```
Michael-Scott (1996)          链表 SPSC (A. Williams)        环形缓冲 SPSC
   无锁 MPMC 通用解        →   面向 SPSC 简化的链表         →   面向 SPSC 彻底的无锁
   CAS + helping               无 CAS，仅 acquire/release      无分配 + 连续内存
   ───────┬───────────       ───────┬───────────           ───────┬───────────
          │ 解决的问题              │ 解决的问题                  │ 解决的问题
   多生产者/消费者                去除 CAS 与 helping          去除 new/delete 分配
   无锁，无死锁                    (SPSC 无竞争，不需要)        (malloc 内部有锁)
   ───────┴───────────       ───────┴───────────           ───────┴───────────
   不足：                      不足：                       不足：
   · new 分配（malloc 有锁）    · new/delete（不是真无锁）    · 仅支持单写单读
   · 需要内存回收（泄露/ABA）   · 无界 + 析构不安全          · 固定容量（有界）
   · 链表 cache 局部性差        · 链表 cache 局部性差
```

**每一步优化了什么、解决了什么不足：**

| 演进步骤 | 解决了什么不足 | 优化了什么 | 新引入的不足 |
|---------|--------------|-----------|-------------|
| **MS → 链表 SPSC** | 多生产者/消费者竞争 CAS 和 helping 的开销，在 SPSC 下是浪费 | 去掉 CAS 和 helping，仅 acquire/release；head/tail 各归各的线程，天然无竞争 | 仍然是 new/delete，不是真无锁；仍然无界；仍然析构不安全 |
| **链表 SPSC → 环形 SPSC** | malloc 内部锁 + 每次 push 分配 + 链表节点散落堆上导致的 cache miss | 预分配连续数组（零分配）；顺序访问命中 L1 cache；有界（full/empty 可检测） | 失去 MPMC 能力（严格单写单读）；固定容量需要调用方处理"满" |

**核心洞察：为什么 SPSC 可以"退化"？**
- MS 的 CAS + helping 是为了解决"多个线程抢同一个链表结构"
- SPSC 只有 1 写 1 读，写方独享 `_tail`，读方独享 `_head`，**不存在竞争**，CAS 完全多余
- 但链表本身仍需要 `new`/`delete`，这**才是**真正的锁点（malloc 的 arena 锁）→ 环形缓冲把分配彻底去掉

**一句话总结演进：** 通用性（MPMC）→ 针对性（SPSC 免 CAS）→ 彻底性（SPSC 免分配）。每一步牺牲一部分通用性，换取一部分性能。

### MPMC 环形缓冲区（Vyukov 有界队列）
Dmitry Vyukov 2011 年设计，把环形缓冲从 SPSC 扩展到 MPMC。这是有界 MPMC 队列的经典方案。

**核心思想：用"序列号 + CAS"替代"指针 CAS + 内存回收"。**

**1. 槽位状态由序列号编码（核心创新）**
每个槽位带一个 `atomic<size_t>` 序列号，**不用额外的锁**就能表达三种状态：
```
槽位 i 的 sequence：
  == 下一个指向它的游标位置 pos        → 空闲（可入队）
  == pos + 1                          → 满（可出队）
  其他值                               → 有线程正在操作中
```
序列号随队列环绕周期性重复，`+capacity` 完成状态切换：
- push 成功：sequence: pos → pos+1（把"空闲"标记为"满"）
- pop 成功：sequence: pos+1 → pos+1+capacity（把"满"标记为下一轮的"空闲"）

**2. 两个单调递增游标 + 各自 CAS**
```
_enqueuePos：生产者入队前先 CAS 自己 +1，抢到一个唯一的槽位索引
_dequeuePos：消费者出队前先 CAS 自己 +1，抢到一个唯一的槽位索引
```
- 游标 CAS 用 **relaxed**：游标本身只是"抢位置"，真正的同步在序列号上
- 序列号 CAS 用 **acq_rel**：发布数据（push 写 value 后再 store）与读取数据（pop 读到后才 free）

**3. 有界判定：dif 的符号**
```
push：dif = slot.sequence - pos
  dif == 0 → 槽位空闲，CAS 抢
  dif < 0  → 队列满（消费者还没释放该位置）→ 返回 false
  dif > 0  → 有生产者正在写 → 重读游标重试

pop：dif = slot.sequence - (pos + 1)
  dif == 0 → 有数据，CAS 抢
  dif < 0  → 队列空 → 返回 false
  dif > 0  → 有生产者正在发布 → 重读游标重试
```

**为什么没有 ABA 和内存回收问题：**
- 槽位地址永远不变（数组预分配），只有序列号变 → 不存在"地址复用回旧值"
- 序列号就是"标记指针"里的 tag——CAS 比对的是"序列号 + 位置"的复合状态，天然防 ABA
- 不需要 hazard pointer / EBR / RCU，析构直接销毁剩余元素

**关键内存序：**
| 操作 | 内存序 | 原因 |
|------|--------|------|
| 游标 CAS | relaxed | 只是抢位置，真正的同步在序列号 |
| 序列号 load | acquire | 看到生产者发布的数据 / 消费者释放的槽位 |
| 序列号 store | release | 发布数据 / 释放槽位 |
| value 读写 | 普通 | 被序列号的 acquire/release 夹住 |

**与 Michael-Scott 对比：**

| | Michael-Scott（无界） | MPMC 环形缓冲（有界） |
|---|---|---|
| 内存分配 | 每 push 一次 new | 预分配，零 |
| 内存回收 | 需要（泄露/ABA 风险） | 不需要（天然防 ABA） |
| 无界/有界 | 无界 | 有界（固定容量） |
| 满时行为 | 总是成功（void） | 返回 false |
| 同步原语 | 链表 CAS + helping | 序列号 CAS + 双游标 |
| 典型吞吐（2P/2C） | ~5.3 M ops/s | ~9.6 M ops/s |
| 适用场景 | 无界任务队列 | 有界高频流水线 |

**变体：BoundedMichaelScottQueue**
在 MS 链表上追加两个计数器（`_enqueued`/`_dequeued`），push 前检查差值是否达上限，返回 bool。仍是无锁（计数器只是提示，真正闸门还是 tail CAS）。吞吐略降（~4.4 M ops/s），但获得了有界能力，代价是仍然需要 new/delete + 内存回收。

### 无锁队列中的问题
#### ABA 问题与解决方案
**ABA 的定义：** CAS 只检查"值是否相等"，不检查"值是否被修改过"。值从 A → B → A 时，CAS 认为"没被修改"，但实际上内存已被修改。
1. 标记指针（Tagged Pointer）——最常用
```cpp
// 指针 + 版本号，每次 CAS 递增版本号
struct TaggedPtr {
    Node* ptr;
    uintptr_t tag;  // ABA 无法绕过（tag 单调递增）
};

atomic<TaggedPtr> head;

void push(Node* n) {
    TaggedPtr old = head.load();
    n->next = old.ptr;
    TaggedPtr new_val{n, old.tag + 1};
    // 即使 ptr 回到同一地址，tag 不同 → CAS 失败
    while (!head.compare_exchange_weak(old, new_val)) {
        new_val.ptr = old.ptr;  // 更新 expected
        new_val.tag = old.tag + 1;
    }
}
```
**优点：** 简单、轻量、无额外内存分配
**缺点：** 需要双倍指针宽度，x86 上需 16 字节 CAS（`cmpxchg16b`），编译器支持有限

2. Hazard Pointer——工业级方案
```cpp
// 每个线程注册"我正在访问的指针"
thread_local HazardPtr {
    atomic<Node*> hp = nullptr;
};

// 读端使用
Node* read() {
    Node* p;
    do {
        p = head.load();
        hazard_ptr.store(p);  // 注册保护
    } while (head.load() != p);  // 确认 head 没变
    return p;  // 现在安全：这个节点不会被删除
}

// 写端延迟释放
void retire(Node* p) {
    // 放入延迟释放列表
    retired_list.push_back(p);
    // 检查所有线程的 hazard pointer
    for (auto& hp : all_hazard_ptrs) {
        if (hp.load() == p) return;  // 还有人用，不能删
    }
    delete p;  // 安全了
}
```
**优点：** 真正可用的内存回收方案
**缺点：** 实现复杂，读端需要双重检查，写端需要扫描所有线程

3. Epoch-based Reclamation（EBR）
```cpp
// 全局纪元（epoch），每个线程有 3 个延迟释放列表
struct EpochState {
    atomic<int> global_epoch{0};
    atomic<int> active_count[3]{0, 0, 0};
    list<Node*> retired[3];
};

// 读端：进入临界区，递增当前 epoch 的活跃计数
void read() {
    int epoch = global_epoch.load();
    active_count[epoch].fetch_add(1);
    // ... 读共享数据 ...
    active_count[epoch].fetch_sub(1);
}

// 写端：释放时放入下一 epoch 的列表，等两轮后安全删除
void retire(Node* p) {
    int next_epoch = (global_epoch.load() + 1) % 3;
    retired[next_epoch].push_back(p);
    // 检查是否可以推进 epoch
    if (active_count[global_epoch.load()].load() == 0) {
        // 所有人都离开当前 epoch 了
        delete retired[当前 epoch 的列表];
        global_epoch = next_epoch;
    }
}
```
**优点：** 比 hazard pointer 轻量，不需要逐个扫描
**缺点：** 需要线程配合周期性地"签退"，延迟释放可能有周期性峰

4. RCU（Read-Copy-Update）
```cpp
// 读端：完全无锁，无原子操作
void read() {
    Node* p = rcu_dereference(ptr);  // 普通指针读
    // 使用数据
    rcu_read_unlock();  // 无操作（或编译器屏障）
}

// 写端：复制 → 修改 → 发布 → 等待所有读端完成
void write() {
    Node* old = ptr;
    Node* new_node = new Node(*old);  // 复制
    new_node->value = new_value;       // 修改
    rcu_assign_pointer(ptr, new_node);  // 发布（内存屏障）
    synchronize_rcu();                 // 等待所有读端退出
    delete old;                        // 安全删除
}
```
**优点：** 读端零开销，适合读多写少
**缺点：** 写端需要等待所有读端完成（可能几十微秒）

**对比表格：**

| 方案 | 读端开销 | 写端开销 | 实现复杂度 | 适用场景 |
|------|---------|---------|-----------|---------|
| 标记指针 | 无（CAS 时附带） | CAS 时附带 | 低 | 所有场景（首选） |
| Hazard Pointer | 2 次原子 load | 扫描所有线程 | 高 | 通用 MPMC |
| EBR | 2 次原子操作 | 周期性释放 | 中 | 读端轻量场景 |
| RCU | 零 | 等待所有线程 | 中 | 读多写极少 |
#### 内存回收问题
无锁队列的 pop 会从链表中移除节点，但**不能立刻 delete**——可能有其他线程正在读这个节点（如 MS 队列中 pop 方 CAS head 成功后，另一个线程可能刚读过旧 head）。这就产生了"什么时候才能安全释放"的问题。

**为什么不能立刻释放：**
```
线程 A（pop 方）：
  head = _head.load()          ← 读到 dummy
  next = head->next.load()     ← 读 dummy 的 next
  CAS _head: dummy → next      ← 成功，dummy 被移除
  // 现在能 delete dummy 吗？
  // 不能！线程 B 可能刚执行了 head->next.load()，还没结束

线程 B（另一个 pop 方）：
  head = _head.load()          ← 恰好也读到同一个 dummy
  next = head->next.load()     ← 正在读 dummy->next ← 如果 A 已 delete，这就是 use-after-free
```

**四种解决方案：**

| 方案 | 原理 | 读端开销 | 写端开销 |
|------|------|---------|---------|
| 标记指针（Tagged Pointer） | 指针 + 版本号，CAS 附带递增 | 无 | CAS 时附带 |
| Hazard Pointer | 每个线程声明"我正在访问的指针"，写端扫描后才释放 | 2 次原子 load | 扫描所有线程 |
| EBR（Epoch-based Reclamation） | 全局纪元 + 延迟释放，所有线程离开某纪元后才回收该纪元节点 | 2 次原子操作 | 周期性批量释放 |
| RCU | 写端复制-修改-发布，等待所有在读读者完成再删旧 | 零 | synchronize_rcu 等待 |

**为什么泄露是合法的教学手段：**
教学版 MS 队列不 delete 移除的 dummy 节点，让 OS 在进程退出时统一回收。代价是内存持续增长（测试中 200 万次 push 后峰值 63 MB）。生产环境不可接受，必须用上述方案之一。

**回收与 ABA 的关联：**
- 只要节点地址不被复用（如泄露），ABA 不会发生
- 一旦开始回收（如 hazard pointer 释放后，分配器可能把同一地址重新分配给新节点），CAS 就可能读到"旧值 = 新节点"，ABA 出现
- 所以**回收方案和 ABA 方案必须成对出现**：hazard pointer + 标记指针，或 EBR + 标记指针

#### 虚假共享（False Sharing）

**定义：** 两个线程各自操作**不同的变量**，但这几个变量恰好落在**同一个 cache line**（64 字节）里。某线程写自己的变量时，必须把整个 cache line 置为独占（M 状态），导致另一个线程读自己的变量时 cache miss，被迫重新加载。

**为什么这是无锁队列的痛点：**
```
// SPSC 环形缓冲区，head 和 tail 相邻存储
class SPSCRingBuffer {
    std::atomic<size_t> head_;   // 消费者写
    std::atomic<size_t> tail_;   // 生产者写，紧挨着 head_
    // head_ 和 tail_ 很可能在同一个 cache line！
};
```
生产者和消费者被调度到不同核：
```
核心0（生产者写 tail_）       核心1（消费者写 head_）
  tail_.store(...)              head_.store(...)
    │                              │
    ▼                              ▼
 独占整个 cache line (M)        独占整个 cache line (M)
    │                              │
    ▼                              ▼
 触发 invalidate 消息            触发 invalidate 消息
    └──────────┬─────────────┘
               ▼
    两个核心反复互相 invalidate → 每写一次都要 100+ 周期缓存同步
    本来"各写各的、无竞争"的 SPSC 被退化成了慢速互斥
```

**解决方案：缓存行对齐 / padding**
```cpp
// 每个原子变量独占一个 cache line，互不干扰
constexpr size_t kCacheLineSize = 64;

struct alignas(64) ProducerState {
    std::atomic<size_t> tail_{0};
};

struct alignas(64) ConsumerState {
    std::atomic<size_t> head_{0};
};

class SPSCRingBuffer {
    alignas(64) ProducerState producer_;
    alignas(64) ConsumerState consumer_;
    // producer_.tail_ 和 consumer_.head_ 现在处于不同的 cache line
};
```

**为什么 padding 代价可以接受：**
- 一个 cache line 64 字节，padding 一个原子变量会"浪费" 56 字节
- 但换来的是两个线程完全不互相 invalidate，吞吐提升通常达数倍（尤其高频 push/pop）

**False sharing 的另一种表述：** 它本身不是数据竞争（每个线程只碰自己的变量），但性能上等价于每次写入都在竞争缓存行。与真正的数据竞争（Data Race）本质不同：数据竞争是正确性问题，false sharing 是性能问题。

**检测方法：** perf 工具统计 cache miss，或使用 `heaptrack`/`valgrind --tool=cachegrind`。无锁队列实现中，`alignas(64)` 是最常用的防御手段。
