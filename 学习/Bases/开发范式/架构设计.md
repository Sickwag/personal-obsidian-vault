# 计算机基本认识
## 进程和线程
### 栈空间
- `ulimit -s` 控制**每个线程**的栈大小上限（Linux 默认8MB），超过触发 SIGSEGV
- 同一进程内所有线程的栈都在进程虚拟地址空间内，但由 OS 保证物理页不重叠
- **线程栈之间没有硬件/OS层面的隔离保护**：线程A拿到线程B栈变量的地址，可以正常读写。栈的"隔离"是语言作用域规则的约定，不是OS的强制保护，但是实际编程中**两个线程不可能拿到对方栈对象的内存地址**

### 堆空间
- 同一进程所有线程共享堆，`new` / `malloc` 出的内存任何线程都能访问，是同一个内存分配器（malloc/free）管理的区域，所有线程通过该分配器拿到的地址，
  都在这块区域内。所以线程 A new 的对象，把地址传给线程 B，B 可以访问。
- 堆上的并发安全需要程序员自行保证（锁、原子操作等）
### mmap 系统调用
`mmap` 的本质是**将虚拟地址空间映射到某个后端**，后端可以是文件或匿名内存。

**三种主要用途：**

| 类型   | 标志                        | 说明                                      |
| ---- | ------------------------- | --------------------------------------- |
| 文件映射 | `MAP_SHARED`              | 映射文件内容到内存，读写直接反映到文件                     |
| 匿名映射 | `MAP_ANONYMOUS`           | 不关联文件，纯内存分配（malloc 大块(>128kb)时底层用 mmap） |
| 共享内存 | `MAP_SHARED` + `/dev/shm` | 多个进程映射同一物理页面，实现 IPC                     |

**mmap 底层流程：**
```
mmap(addr, length, prot, flags, fd, offset)
                    │
                    ▼
        用户态：调用 mmap 系统调用
                    │
                    ▼
        内核态：do_mmap()
        1. 在进程的虚拟地址空间中找一块空闲区域
        2. 建立 vma（vm_area_struct）描述该区域属性
        3. 区域标记为"未映射"——页表还不存在
                    │
                    ▼
        返回虚拟地址，但此时对应的物理页 = 不存在
                    │
        第一次访问该地址 → 触发缺页中断（page fault）
                    │
                    ▼
        内核：缺页中断处理
        1. 检查 vma，确认访问合法
        2. 文件映射：从磁盘读取文件内容到物理页
        3. 匿名映射：分配一个物理页，全零填充
        4. 建立页表映射（虚拟地址 → 物理地址）
                    │
                    ▼
        返回用户态，指令重新执行，访问成功
```

**mmap vs read() 对比：**
- `read()/write()`：用户空间 ↔ 内核空间，缓冲区 ↔ 硬件，两次拷贝 ↔ 上下文切换
- `mmap`：直接在用户空间映射页表，缺页中断时加载，零拷贝

### 虚假唤醒（Spurious Wakeup）
**条件变量上为什么需要防止虚假唤醒？**
因为即使没有线程调用 `notify_one()`/`notify_all()`，`wait()` 也可能返回。原因：

- **OS 信号被中断**：`pthread_cond_wait` 返回 EINTR
- **多核竞争**：线程在 `wait` 内部释放锁和进入等待之间存在窗口，`notify` 先于 wait 到达
- **硬件层面**：某些 CPU 架构在总线广播时广播唤醒信号
- **POSIX 标准化**：标准明确允许虚假唤醒，所以 `pthread_cond_wait` 返回时不保证条件成立

**标准的 wait 模式：**
```cpp
// 必须用 while 循环检查条件，不能用 if
while (!predicate()) {
    cv.wait(lock);
}
// C++20 的 lambda 版本内部也是 while 循环
cv.wait(lock, []{ return predicate(); });
```
# 后端组件
## 并发/多线程
### 无锁队列
无锁队列（Lock-Free Queue）是一种不使用锁机制（如互斥锁或读写锁）来实现线程安全的数据结构，是 lock-free 中最基本的数据结构。

|       | 锁（Mutex）            | 无锁（CAS）             |
| ----- | ------------------- | ------------------- |
| 思路    | 悲观——肯定会冲突，先拿锁再操作    | 乐观——冲突概率低，直接操作，失败重试 |
| 阻塞    | 线程阻塞（上下文切换，~1us 开销） | 线程不阻塞（自旋重试，~10ns）   |
| 死锁    | 可能                  | 不可能                 |
| 优先级反转 | 可能                  | 不可能                 |
| 适用场景  | 临界区大、操作复杂           | 临界区小、操作极快           |
### 原子操作 CAS（Compare-And-Swap）
原子操作是不可被中断的最小操作单元。CPU 层面通过特殊指令保证（x86 的 `lock` 前缀/ARM 的 LL/SC），C++ 通过 `std::atomic` 提供。

```cpp
counter++;          // 非原子 —— 读-改-写三步，两个线程同时执行可能丢失一次自增
a.fetch_add(1);     // 原子 —— 硬件保证不可分割
```
CAS 是实现无锁数据结构的核心原语：
```cpp
bool CAS(ptr, expected, desired) {
    if (*ptr == expected) {  // 没人动过
        *ptr = desired;
        return true;
    }
    return false;  // 有人改了，重试
}
```
C++ 中对应 `std::atomic::compare_exchange_weak/strong`。

### acquire/release 配对详解

**核心原则：** release 保证之前的操作不重排到后面；acquire 保证之后的操作不重排到前面。两者配对建立 happens-before 关系。

**release 的作用边界：**
```
线程 A:
data = 42;                ← ① 操作前（可以被重排到②之后？不可以）
ready.store(true, release); ← ② release 操作本身
foo();                     ← ③ 操作后（可以被重排到②之前？可以！）
```
release 只保证"之前的不重排到后面"，不保证"后面的不重排到前面"。

**acquire 的作用边界（对称）：**
```
线程 B:
while (!ready.load(acquire));  ← ① acquire 操作本身
assert(data == 42);            ← ② 操作后（可以被重排到①之前？不可以）
```
acquire 只保证"之后的不重排到前面"，不保证"前面的不重排到后面"。

**配对效果：** 当 acquire 读到 release 写入的值时，release 之前的所有写操作对 acquire 之后的所有读操作可见。

**`memory_order_acq_rel`：** 只用于读-改-写（RMW）操作（`fetch_add`、`exchange`、`compare_exchange`）。读部分施加 acquire，写部分施加 release。

### memory_order_consume（已死）

**设计意图：** 只阻塞数据依赖链上的指令，无关指令可以自由重排，比 acquire 更轻量。
```cpp
int* addr = global_addr.load(memory_order_consume);
int d = *data;         // ✅ 无关操作，可以重排到 load 前
int f = *(data+1);     // ✅ 同上
if (addr) {
    int x = *addr;     // ❌ 依赖 addr，不能重排
}
```

**实际现状：** 所有编译器（GCC/Clang）将 consume 提升为 acquire。C++20 建议不要使用。x86 上 acquire 本身免费（load 自带 acquire 语义），consume 的优化价值只在 ARM 等弱内存模型架构上存在。

**常见误解纠正：** "所有后续对本原子类型的操作必须在本操作完成之后"——这是错的。consume 约束的是**数据依赖链**，不是"同一原子类型"。

### memory_order_seq_cst

**作用：** 所有线程看到完全一致的操作全局顺序（全局总序）。即使操作不同的变量，所有线程都同意同一个"全局时钟"。

**为什么需要：** 没有 seq_cst 时，两个线程可能对同一组事件持有不同的"看法"：
```cpp
atomic<int> x{0}, y{0};
// 线程1: x.store(1); a = y.load();
// 线程2: y.store(1); b = x.load();
// 可能 a=0, b=0 同时出现（两个store看起来都发生在两个load之后）
```
seq_cst 禁止这种分歧，所有线程看到一致的操作序。

**代价：** x86 上每次 seq_cst 生成 `mfence`（最慢指令），release/acquire 在 x86 上通常不需要额外指令。

### C++ 中体现内存屏障的操作
**显式屏障：**
- `atomic::store(val, memory_order_release)` → x86 上 `mov` + `mfence` 或 `xchg`
- `atomic::load(val, memory_order_acquire)` → 屏障 + `mov`
- `atomic_thread_fence(memory_order_release/acquire)` → 独立屏障，不绑定变量
- `fetch_add/exchange` 带 `memory_order_acq_rel` → RMW + 屏障

**隐式屏障：**
- `mutex.lock()` → 内部含 acquire 屏障
- `mutex.unlock()` → 内部含 release 屏障
- `cv.wait()` → 内部含 acquire + release
- `cv.notify_one()` → 内部含 release

**编译器屏障（不强制 CPU 屏障）：**
```cpp
asm volatile("" ::: "memory");  // 阻止编译器重排，不阻止 CPU 重排
std::atomic_signal_fence(memory_order_seq_cst);  // 同上
```

**应用场景：**
| 场景 | 屏障类型 | 原因 |
|------|---------|------|
| 生产者-消费者 | release/acquire 配对 | 确保数据在标志位之前可见 |
| 自旋锁 | acq_rel | 确保锁内数据在临界区内外 |
| 引用计数 | relaxed + acq_rel 在关键点 | 减少不必要的屏障开销 |
| 单线程计数器 | relaxed | 只需原子性，不需要同步 |

### 不同线程观察到不同结果的原因
CPU 各自的 store buffer 导致：核心0写数据进入自己的 store buffer（未刷入 cache），核心1读数据时自己的 cache line 状态为 I（Invalid），从 L3/主存读到旧值。不同核心的 store buffer 内容不同步，导致不同线程在同一时间点看到不同的值。
