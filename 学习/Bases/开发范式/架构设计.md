# 计算机基本认识
## 进程和线程
### 进程虚拟地址空间
进程创建后，OS 分配虚拟地址空间（32位为4GB，64位为2^48或2^57），布局如下：
- `.text` — 代码段，只读
- `.rodata` — 只读数据（字符串常量等）
- `.data` — 已初始化全局变量/静态变量
- `.bss` — 未初始化全局变量/静态变量，加载时置零
- `.tdata` / `.tbss` — TLS（Thread Local Storage）段，存储 `thread_local` 变量
- 堆 — 动态内存分配（`malloc`/`new`），向高地址增长
- mmap 区域 — 文件映射/匿名映射/共享内存，可向堆或栈方向增长
- 栈 — 函数调用栈，向低地址增长，每个线程独立

### 栈空间
- `ulimit -s` 控制**每个线程**的栈大小上限（Linux 默认8MB），超过触发 SIGSEGV
- 同一进程内所有线程的栈都在进程虚拟地址空间内，但由 OS 保证物理页不重叠
- **线程栈之间没有硬件/OS层面的隔离保护**：线程A拿到线程B栈变量的地址，可以正常读写。栈的"隔离"是语言作用域规则的约定，不是OS的强制保护

### 堆空间
- 同一进程所有线程共享堆，`new`/`malloc` 出的内存任何线程都能访问
- 堆上的并发安全需要程序员自行保证（锁、原子操作等）

### 静态变量与 TLS
- `static` 全局变量 → `.data`（已初始化）或 `.bss`（未初始化）
- `static` 局部变量 → 同上，作用域限制在函数内但存储期是整个程序生命周期
- `thread_local` 变量 → 存储在 `.tdata`/`.tbss`（TLS段），每个线程有独立副本

**TLS 实现机制：**
编译器在 `.tdata` 段预留空间，每个线程创建时分配一份副本，通过 TLS 寄存器（如 x86 的 `FS`/`GS` 段寄存器）快速寻址。`thread_local` 变量其实就是**以线程ID为索引的静态数组中的元素**。

| | `thread_local` | lambda 值捕获 |
|---|---|---|
| 存储位置 | TLS 段（静态存储区） | 栈 |
| 生命周期 | 线程创建 → 线程退出 | 函数调用 → 返回 |
| 访问方式 | 自动寻址，无需传入 | 函数参数传递 |
| 线程内可见性 | 全局可见（任何函数都能访问） | 仅当前函数及其调用链 |

### mmap 系统调用
`mmap` 的本质是**将虚拟地址空间映射到某个后端**，后端可以是文件或匿名内存。

**三种主要用途：**
| 类型 | 标志 | 说明 |
|------|------|------|
| 文件映射 | `MAP_SHARED` | 映射文件内容到内存，读写直接反映到文件 |
| 匿名映射 | `MAP_ANONYMOUS` | 不关联文件，纯内存分配（malloc 大块时底层用 mmap） |
| 共享内存 | `MAP_SHARED` + `/dev/shm` | 多个进程映射同一物理页面，实现 IPC |

**mmap 底层流程：**
```
mmap(addr, length, prot, flags, fd, offset)
                    │
                    ▼
        用户态：调用 mmap 系统调用
                    │
                    ▼
        内核态：do_mmap()
        1. 在进程的虚拟地址空间中找一块空闲区域
        2. 建立 vma（vm_area_struct）描述该区域属性
        3. 区域标记为"未映射"——页表还不存在
                    │
                    ▼
        返回虚拟地址，但此时对应的物理页 = 不存在
                    │
        第一次访问该地址 → 触发缺页中断（page fault）
                    │
                    ▼
        内核：缺页中断处理
        1. 检查 vma，确认访问合法
        2. 文件映射：从磁盘读取文件内容到物理页
        3. 匿名映射：分配一个物理页，全零填充
        4. 建立页表映射（虚拟地址 → 物理地址）
                    │
                    ▼
        返回用户态，指令重新执行，访问成功
```

**mmap vs read() 对比：**
- `read()/write()`：用户空间 ↔ 内核空间缓冲区 ↔ 硬件，两次拷贝，上下文切换
- `mmap`：直接在用户空间映射页表，缺页中断时加载，零拷贝

### 虚假唤醒（Spurious Wakeup）
**条件变量上为什么需要防止虚假唤醒？**
因为即使没有线程调用 `notify_one()`/`notify_all()`，`wait()` 也可能返回。原因：

- **OS 信号被中断**：`pthread_cond_wait` 返回 EINTR
- **多核竞争**：线程在 `wait` 内部释放锁和进入等待之间存在窗口，`notify` 先于 wait 到达
- **硬件层面**：某些 CPU 架构在总线广播时广播唤醒信号
- **POSIX 标准化**：标准明确允许虚假唤醒，所以 `pthread_cond_wait` 返回时不保证条件成立

**标准的 wait 模式：**
```cpp
// 必须用 while 循环检查条件，不能用 if
while (!predicate()) {
    cv.wait(lock);
}
// C++20 的 lambda 版本内部也是 while 循环
cv.wait(lock, []{ return predicate(); });
```

## CPU 架构与内存模型
### 指令重排
**CPU 为什么重排指令？—— 为了填满流水线段，避免等待。**

现代 CPU 是**流水线架构**（如 14 级流水线），一条指令的执行分为多个阶段：取指 → 译码 → 执行 → 访存 → 写回。如果某条指令需要等待数据（如 cache miss，等待 300+ 周期），CPU 不会空转，而是从后续指令中找数据已就绪的执行。

**CPU 流水线（简化版，14 级流水线实际更长）：**
```
┌─────┬─────┬─────┬─────┬─────┐
│ IF  │ ID  │ EX  │ MEM │ WB  │  取指→译码→执行→访存→写回
└─────┴─────┴─────┴─────┴─────┘
     ↑ 每个阶段可以在一个时钟周期完成
```

**乱序执行（Out-of-Order Execution）：**
- 硬件维护一个指令窗口（比如 64-256 条指令）
- 检查每条指令的操作数是否就绪
- 就绪的指令先执行，不按原始顺序
- 提交时按原始顺序写回（保证单线程语义）

**重排的约束：**
- 数据依赖的指令不能重排（`a=x+1; b=a+1` 中的 `a→b` 依赖）
- 控制依赖的指令不能随意重排（`if(p) q=1` 中的分支）
- 无依赖的指令可以任意重排，维持单线程语义

**调试器为什么看不到重排？**
调试器按源代码执行，编译器 + CPU 保证「好像按顺序执行」的单线程语义。但多线程下，这个保证不跨线程。

### Store Buffer 与 Cache 一致性
**Store Buffer（写缓冲区）：**
每个核心有自己的 store buffer，写操作先写入 store buffer（1 周期），再异步刷入 L1 cache。读操作可以优先读 store buffer（store forwarding）。

**为什么需要 store buffer？**
- 写 L1 cache 需要等待（3-10 周期），CPU 不能干等
- 批量写入再刷入 cache 提高效率
- 没有 store buffer，CPU 核心每写一次就要停等

**Cache 一致性协议（MESI 简化版）：**
每个 cache line 有四种状态，通过总线嗅探（snooping）信号同步：

| 状态 | 含义 | 说明 |
|------|------|------|
| M (Modified) | 本核心独占，已修改 | 回写时通知其他核心失效 |
| E (Exclusive) | 本核心独占，未修改 | 其他核心读时转为 S |
| S (Shared) | 多个核心共享，未修改 | 写前需要发送 Invalidate 请求 |
| I (Invalid) | 失效，需要重新读取 | 其他核心修改了该 cache line |

**核心0写变量、核心1读不到最新值的过程：**
```
核心0                          核心1
时间→
│                               │
│ a = 1 (直接写入 store buffer) │
│ store buffer: [a=1]          │
│                               │ 读 a → L1 cache 没有 → 读 L3 → 没有
│                               │ → 读主存 → 读到旧值 0 ❌
│                               │
│ (100个周期后，store buffer刷入│
│  L1，通过总线通知其他核心无效) │
│ L1: a=1 (M)                  │ 收到 Invalidate 消息 → 自己的 a 设为 I
│ store buffer: []             │
│                               │ 再次读 a → L1 无效 → 读 L3 → 读到 1
```

**MESI 协议的完整消息交互：**
```
核心0写 a，发现 a 在 L1 中状态为 S（共享，其他核心也可能有副本）
│
├── 核心0发送 "Read For Ownership" 总线消息
│   ├── 核心1收到 → 自己的 a 设为 I（无效）
│   ├── 核心1发送 "Acknowledge" 应答
│   └── (可能还有核心2、3，每个都要应答)
│
└── 所有核心应答后，核心0才把 a 从 store buffer 写入 L1 cache（状态 M）
    （这期间核心0不能执行后续的读 a 操作）

整个过程：核心0写了 a，但 200+ 周期后才能执行依赖于 a 的后续操作。
因此 CPU 会继续执行后面不依赖 a 的指令——这就是指令重排的硬件根源。
```

# 后端组件
## 并发/多线程
### 无锁队列
无锁队列（Lock-Free Queue）是一种不使用锁机制（如互斥锁或读写锁）来实现线程安全的数据结构，是 lock-free 中最基本的数据结构。

### 原子操作
原子操作是不可被中断的最小操作单元。CPU 层面通过特殊指令保证（x86 的 `lock` 前缀/ARM 的 LL/SC），C++ 通过 `std::atomic` 提供。

```cpp
counter++;          // 非原子 —— 读-改-写三步，两个线程同时执行可能丢失一次自增
a.fetch_add(1);     // 原子 —— 硬件保证不可分割
```

### 无锁 vs 有锁
| | 锁（Mutex） | 无锁（CAS） |
|---|---|---|
| 思路 | 悲观——肯定会冲突，先拿锁再操作 | 乐观——冲突概率低，直接操作，失败重试 |
| 阻塞 | 线程阻塞（上下文切换，~1us 开销） | 线程不阻塞（自旋重试，~10ns） |
| 死锁 | 可能 | 不可能 |
| 优先级反转 | 可能 | 不可能 |
| 适用场景 | 临界区大、操作复杂 | 临界区小、操作极快 |

### CAS（Compare-And-Swap）
CAS 是实现无锁数据结构的核心原语：
```cpp
bool CAS(ptr, expected, desired) {
    if (*ptr == expected) {  // 没人动过
        *ptr = desired;
        return true;
    }
    return false;  // 有人改了，重试
}
```
C++ 中对应 `std::atomic::compare_exchange_weak/strong`。

### 内存序与内存屏障
#### 内存屏障的定义
内存屏障是一条 CPU 指令，强制 CPU 在屏障点之前的所有内存操作对其他核心可见，并阻止屏障前后的指令重排。

#### 为什么需要屏障？
因为 store buffer 的存在：
1. 核心0写 `data=42`，值进入 store buffer（还没刷入 cache）
2. 核心0写 `ready=true`（带 release），强制冲刷 store buffer
3. 核心1读 `ready=true`（带 acquire），看到核心0的写入
4. 核心1读 `data`，因为核心0的 store buffer 已刷入 cache，读到 42

#### 六种内存序
| 内存序 | 特性 | 重排约束 | 性能 |
|--------|------|----------|------|
| `relaxed` | 仅原子性，不保证顺序 | 无约束 | 最快 |
| `consume` | 依赖链（数据依赖） | 依赖数据不重排 | 较少使用 |
| `acquire` | 获取操作 | 之后读写不重排到前面 | 中等 |
| `release` | 释放操作 | 之前读写不重排到后面 | 中等 |
| `acq_rel` | 读-改-写 | acquire + release | 中等 |
| `seq_cst` | 顺序一致性 | 全局强序 | 最慢 |

#### acquire/release 配对原理
```cpp
// 线程 A（生产者）
data = 42;
ready.store(true, memory_order_release);

// 线程 B（消费者）
while (!ready.load(memory_order_acquire));
assert(data == 42);  // 保证为 true
```
**release 保证：** 之前的所有写操作不会被重排到 release 之后
**acquire 保证：** 之后的所有读操作不会被重排到 acquire 之前
**配对效果：** 当 acquire 读到 release 写入的值时，建立 `happens-before` 关系，acquire 之后的所有读操作一定能看到 release 之前的所有写操作的结果

#### C++ 中体现内存屏障的操作
**显式屏障：**
- `atomic::store(val, memory_order_release)` → x86 上 `mov` + `mfence` 或 `xchg`
- `atomic::load(memory_order_acquire)` → 屏障 + `mov`
- `atomic_thread_fence(memory_order_release/acquire)` → 独立屏障，不绑定变量
- `fetch_add/exchange` 带 `memory_order_acq_rel` → RMW + 屏障

**隐式屏障：**
- `mutex.lock()` → 内部含 acquire 屏障
- `mutex.unlock()` → 内部含 release 屏障
- `cv.wait()` → 内部含 acquire + release
- `cv.notify_one()` → 内部含 release

**编译器屏障（不强制 CPU 屏障）：**
```cpp
asm volatile("" ::: "memory");  // 阻止编译器重排，不阻止 CPU 重排
std::atomic_signal_fence(memory_order_seq_cst);  // 同上
```

**应用场景：**
| 场景 | 屏障类型 | 原因 |
|------|---------|------|
| 生产者-消费者 | release/acquire 配对 | 确保数据在标志位之前可见 |
| 自旋锁 | acq_rel | 确保锁内数据在临界区内外 |
| 引用计数 | relaxed + acq_rel 在关键点 | 减少不必要的屏障开销 |
| 单线程计数器 | relaxed | 只需原子性，不需要同步 |
| 细粒度锁 | acquire/release | 精确控制每个操作 |
