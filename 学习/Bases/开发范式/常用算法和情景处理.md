# 缓存算法
## LRU
### 概览
经典实现中，依赖一个环形链表+哈希表实现
淘汰最久未被使用的数据。基于“时间局部性”原理，数据结构依赖双向循环链表+哈希表
适合访问集中在短时间内的场景，缺点也很明显:
- 易被突发流量污染：突发的大量一次性数据可能将真正频繁使用的热点数据“挤出”缓存，导致命中率骤降。
- 不考虑频率：一个每天用 100 次的数据，可能因几分钟没被访问而被淘汰，
	- 经典 LRU 实现中，**由于缓存空间固定**，数据移出缓存取决于**当前到最后一次访问数据之间访问其他数据的次数**，不是间隔时间
	- 添加过期时间（TTL）的 LRU 实现中缓存池大小必须动态调整
### Redis 的近似 LRU 算法
参考: https://zhuanlan.zhihu.com/p/641841636
经典实现中依赖 2 个哈希表+n 个链表实现
朴素 LRU 必须维护双向链表：每个节点保存前驱/后继指针，外加哈希表定位节点。当缓存对象达到百万级（如 Redis），这部分指针内存与链表调整的额外开销不可忽视。Redis 的取舍是**牺牲少量命中率，换取内存与实现复杂度的降低**。
设计思路是把"全局有序链表"降级为"局部随机采样 + 时间戳比较"：
- 每个 `redisObject` 内嵌 24bit 的 `lru` 字段，记录该对象最后被访问的时钟（秒级精度，约 194 天循环一次）。
- 淘汰时不遍历链表，而是在键空间中**随机采样** `maxmemory-samples` 个 key（默认 5），比较 `lru`，淘汰其中最久未访问的一个。
- Redis 3.0 引入**淘汰池**（eviction pool，默认 16）：每次采样得到的 key 若比池中最老者还老则入池；池满则淘汰池中最老者，并按 LRU 顺序维护。多次采样之间累积候选，使结果逐步逼近真实 LRU。
优缺点对比：

| 维度     | 朴素 LRU       | Redis 近似 LRU  |
| ------ | ------------ | ------------- |
| 内存开销   | 每对象两个指针      | 复用已有 24bit 字段 |
| 淘汰精度   | 精确           | 概率近似          |
| 单次淘汰成本 | O(1)（链表头尾操作） | O(samples)    |
| 实现复杂度  | 高（链表 + 哈希表）  | 低             |
联系点：`maxmemory-samples` 越大，近似 LRU 越接近真实 LRU，但单次淘汰越慢——这是命中率与 CPU 的线性权衡。本质上它把 [[#LRU]] 的"确定性全局排序"换成了"概率性局部排序"，用可控的误差换取可扩展性。
### LRU-K 算法
参考: https://juejin.cn/post/6844904049263771662
将原先进入缓存队列的评判标准从访问一次改为访问 K 次，可以说朴素的 LRU 算法为 LRU-1。
LRU-K 算法有**缓存队列和数据访问历史队列**。当访问一个数据时，首先先在访问历史队列中累加访问次数，当历史访问记录超过 K 次后，才将数据缓存至缓存队列，从而避免缓存队列被污染。同时访问历史队列中的数据可以按照 LRU 的规则进行淘汰
![[Pasted image 20260626210330.png]]
同理，可以仿照 CPU-Cache 结构设计多层队列结构，形成 [[#Multi Queue LRU 算法]]，如果多队列中每个队列没有层级关系就会变为 [[#Hash LRU 算法]]
### 2Q（Two Queue LRU） 算法
是 LRU-2 的一种变种，将数据访问历史改为 FIFO 队列。好处的明显的，FIFO 更简易，耗用资源更少，但是相比 LRU-2 会降低缓存命中率。
2Q（Two Queue）可看作 ARC 的简化前身，采用固定规则而非自适应。设计目标是**用最低成本剥离一次性扫描数据**，使其不污染真正的缓存主体。它维护三个队列，外加各自配套的哈希表：

| 结构 | 类型 | 作用与意义 |
| --- | --- | --- |
| `A1in` | FIFO | 新数据"试用期"，所有新插入者先进此队；一次性扫描数据在此被快速排空 |
| `A1out` | LRU(仅 key) | 从 `A1in` 淘出 key 的幽灵队列，用于在淘汰后仍能识别"二次访问" |
| `Am` | LRU(含 value) | 真正的缓存主体，存放被二次访问确认有频率价值的数据 |

每个结构的意义：
- **`A1in` 用 FIFO 而非 LRU**：试用期数据无需重排，FIFO 的 O(1) 入队出队更省。它本质是一道"扫描过滤器"——一次性数据走完一遍就被挤出，绝不进入 `Am`。
- **`A1out` 幽灵队列**：与 ARC 的 `B1` / `B2` 同源思想。`A1in` 淘出时把 key 留在 `A1out`，若短时间内又被访问，说明它其实有频率价值，重新载入时**直接进 `Am`** 跳过试用期。没有它，刚被挤出又立刻被请求的数据会重新走一遍试用期，命中率受损。
- **`Am` 用 LRU**：进入主缓存后按时间局部性维护，与朴素 LRU 一致。
新数据先进 `A1in`；若在试用期内被再次访问则晋升 `Am`，否则按 FIFO 淘出并进入 `A1out`。命中 `A1out` 表示该数据其实有频率价值，重新载入时直接进 `Am`。
与 ARC 相比，2Q 的队列容量配比是**固定**的（`A1in` 通常占 25%、`A1out` 占 25%、`Am` 占 50%，无 `p` 自适应），实现更简单，但无法像 ARC 那样随访问模式漂移自我调优。它快速剥离一次性扫描数据的能力，使其在数据库缓冲池等"扫描 + 查找"混合负载中表现稳定。
### Multi Queue LRU 算法
Multi Queue 是由多个 LRU 队列组成的。每一个 LRU 队列都有一个相应的优先级，数据会根据访问次数计算出相应的优先级，并放在该队列中
![[Pasted image 20260626210519.png]]
- 数据插入和访问：当数据首次插入时，会放入到优先级最低的 Q0 队列。当再次访问时，根据 LRU 的规则，会移至队列头部。当根据访问次数计算的优先级提升后，会将该数据移至更高优先级的队列的头部，并删除原队列的该数据。同样的，当该数据的优先级降低时，会移至低优先级的队列中。
- 数据淘汰：数据淘汰总是从最低优先级的队列的末尾数据进行，并将它加入到 Q-history 队列的头部。如果数据在 Q-history 数据中被访问，则重新计算该数据的优先级，并将它加入到相应优先级的队列中。否则就是按照 LRU 算法完全淘汰。
### Hash LRU 算法
![[Pasted image 20260626210953.png]]
get/put 的操作都会经过 hash 指向一个分片后的 LRU 队列，减小了锁的粒度，在高并发场景中表现较好
## LFU
### 概览
淘汰使用频率最低的数据。基于“频率局部性”原理，LFU 是根据**频数和时间维度**来选择将要淘汰的元素，即首选删除访问频数最低的元素。如果两个元素的访问频数相同，则淘汰最久没被访问的元素。数据结构依赖**2个哈希表**再加上 **N 个双链表**才能实现先按照频数再按照时间两个纬度的淘汰策略，
识别长期热点准：能有效保留高频访问的热点数据，命中率更稳定。
抗突发干扰强：突发的一次性访问因频率低，不会挤掉真正的高频数据
缺点在于:
- 历史数据“赖着不走”：一个曾经热门但已过时的数据，会因历史访问频率高而长期占用缓存，阻碍新的高频数据进入（“频率老化”问题）。
- 实现复杂且开销大：需要为每个数据维护访问计数器，内存和计算开销更高。
- “冷启动”问题：新加入的数据初始频率低，容易在还未“证明”自己前就被淘汰。
![[Pasted image 20260626211349.png]]
淘汰要**先按频次、频次相同再按时间**两个维度排序。单靠一个链表无法同时表达这两个维度，于是拆成两层结构
- `keyToNode`（key → 节点指针）：O(1) 定位数据所在节点，对应 LRU 中哈希表的作用。get/put 时凭它跳过遍历直达节点。
- `freqToList`（频次 → 双向链表头）：把"同一个频次"的所有节点串成一条链表，并把"频次值"映射到对应链表。这张表让"找最低频次"和"同频次内找最旧"都能 O(1)。
### Redis 的 LFU 实现
参考: https://zhuanlan.zhihu.com/p/641841636
Redis 4.0 引入 LFU 模式，**复用了同一个 24bit 字段**，但语义重新划分：
- 高 16bit：`ldt`（last decrement time），上次衰减时间。
- 低 8bit：`counter`，对数计数器，范围 0–255。
设计的两个关键问题与解法如下。
**问题一：8bit 如何表达远大于 255 的访问次数？**
采用**概率递增**——counter 越大，再次访问时递增的概率越低。访问时先对 counter 做老化（详见 [[#LFU-Aging 算法]]），再以 `1 / (counter * lfu_log_factor + 1)` 的概率 counter++。`lfu_log_factor` 默认 10，使 counter 爬到 255 约需一亿次访问，触顶不再增加。用 1 字节就压缩了巨大的频次空间。代价是 counter 相同的两个数据访问次数相差可能极大，并且 counter 越大越明显
**问题二：如何解决"频率老化"？**
靠 `ldt` + `lfu-decay-time`：每经过 `lfu-decay-time` 分钟（默认 1），counter 衰减 1。衰减按时间差**惰性计算**——只在访问该 key 时根据 `ldt` 推算应扣减的次数，而非后台扫描全表，把 O(N) 的扫描摊销成访问时 O(1) 的计算。

> [!Note] Redis LFU = LFU-Aging + 概率计数
> 8bit 概率计数器解决"内存开销大"，`ldt` 惰性衰减解决"历史数据赖着不走"。这两点正好对应 [[#LFU]] 概览里指出的 LFU 两大缺点。
### LFU-Aging 算法
朴素 LFU 的访问计数**单调递增**，于是出现两类问题：
- **频率老化**：曾经热门、如今冷门的数据因历史计数高而长期占位，阻碍新热点进入。
- **冷启动污染**：新插入的数据初始计数为 1，很容易在"证明自己"前就被淘汰。
LFU-Aging 针对前者，核心思想是**让计数随时间衰减，使"最近高频"而非"历史累计高频"主导淘汰决策**。衰减的两类实现思路：
- **全局周期衰减**：每隔固定周期把所有 counter 减半（或减一）。实现简单，但衰减速率与实际访问模式脱节，且需后台扫描全表。
- **惰性时间衰减**：不主动扫描，只在访问时按时间差扣减 counter。无后台开销，但冷数据不访问就永不衰减（对缓存无害，因为不访问本就不会被保留）。
> [!Warning] 衰减参数的调参难题
> 衰减太快 → 退化为 LRU，丢失频次信息；衰减太慢 → 等同朴素 LFU，频率老化依旧。衰减周期必须贴合业务的热点更替节奏。
[[#Redis 的 LFU 实现]] 选择的正是惰性时间衰减，用 `ldt` 字段记录上次衰减时刻。而冷启动问题则由"新 key 的 counter 初始值"与概率递增曲线共同缓解——新 key 计数起点低但爬升快，几次访问后即可与老热点抗衡。
### LFU-Aging 平均访问次数算法
朴素 LFU 的计数是**累计绝对次数**——访问 1 万次的老数据与访问 10 次的新数据，仅凭数字 10000 vs 10 比较，老数据永远赢，这正是[[#LFU#概览|概览]] 里提到"频率老化"的根源。换计数单位为**平均访问速率**（访问次数 / 存在时长），衰老问题自然消解：老数据若已冷，其分子（次数）几乎停长、分母（时长）持续增大，平均速率会被新热点反超。
设 key 的累计访问次数为 `count`、在缓存中的存活时间为 `age`，则平均速率 `rate = count / age`。淘汰时取 `rate` 最小者。两个关键设计点：
- **分母随时间单调增长**，这是与朴素 LFU 最本质的区别：后者分母恒为 1，次数只增不减；前者让"时间"持续稀释"历史功劳"，从而自动遗忘过气热点。
- **衰减是隐式的**，无需像 [[#LFU-Aging 算法]] 的减半/扣减那样主动改写计数器——只要 `age` 在走，老数据的 `rate` 就在掉。省掉了后台扫描或惰性扣减的写入开销。
代价与权衡：
- **新 key 的冷启动更尖锐**：新插入 `count=1, age≈0`，`rate` 趋于无穷，看似优先级极高；但只要随后几秒没被访问，`age` 一旦长大，`rate` 会断崖式下跌，极易被淘汰。需要给新 key 设"保护期"或最小 `age` 下限来缓冲。
- **`age` 的起点与重置策略影响语义**：`age` 是"自首次进入缓存起"，还是"自上次访问起"？前者偏频率语义，后者偏时间语义（趋近 LRU）。多数实现取前者以保留 LFU 本意。
- **比较的是浮点速率**，比朴素 LFU 的整数比较略重；可改为比较 `count_a * age_b vs count_b * age_a` 用整数交叉乘积避免浮点。
> [!Note] 与"减半衰减"的关系
> 周期性把 `count` 减半（见 [[#LFU-Aging 算法]]）可视为"分母离散增长"的近似——它每隔固定周期把分子砍半，等效于让 `rate` 台阶式下降。平均访问次数法则让分母连续增长，衰减更平滑、且无需调"衰减周期"这一参数，但把调参负担转移到了"新 key 保护期"上。
### Hash LFU 算法
类比 [[#Hash LRU 算法]] 的思路，把全局 LFU 按哈希分片成若干独立的小 LFU，每个分片各持一把锁。get/put 只锁定目标分片，从而把"全局大锁"降级为"分片小锁"，提升高并发吞吐。
代价是分片间负载不均：热点 key 集中在少数分片时，该分片退化为单点瓶颈，命中率与吞吐均受损。需要配合一致性哈希与合理的分片内容量来缓解。
## ARC
ARC（Adaptive Replacement Cache）把 LRU 与 LFU 的取舍**自适应化**，不再人工选边。它的设计目标是：让缓存**根据实际命中模式在"时间局部性（LRU）"与"频率局部性（LFU）"之间自动漂移**，无需用户预设配比。
ARC 维护四个独立的 LRU 双向链表，每个链表各自配一个哈希表实现 O(1) 定位：

| 结构 | 内容 | 作用与意义 |
| --- | --- | --- |
| `T1` | 近期被访问过**一次**的数据 | LRU 语义区，捕获"刚进来"的时间局部性 |
| `T2` | 被访问过**多次**的数据 | LFU 语义区，捕获"反复来"的频率局部性 |
| `B1` | 从 `T1` 淘汰出的 key 元数据（无 value） | 幽灵目录，记录"被当作时间型淘汰"的数据 |
| `B2` | 从 `T2` 淘汰出的 key 元数据（无 value） | 幽灵目录，记录"被当作频率型淘汰"的数据 |

数据结构与朴素 LRU/LFU 完全同构（双向链表 + 哈希表），ARC 的创新不在数据结构本身，而在**用四个链表 + 幽灵目录把"淘汰决策的反馈回路"显式建模出来**。各结构的意义：
- **`T1`/`T2` 分工**：把"试用"与"常驻"物理隔离。新数据先进 `T1`，被二次访问才晋升 `T2`，避免新数据直接污染 `T2` 的高频区。
- **`B1`/`B2` 只存 key 不存 value**：幽灵目录不占业务内存，只为"复盘淘汰是否正确"留下证据。命中幽灵意味着"刚才淘汰错了"，据此反向调节配比。
核心机制是**动态调整 `T1` 与 `T2` 的目标容量配比 `p`**（`p ∈ [0, c]`，`c` 为缓存总容量）：
- 命中 `B1`（说明本该留在 `T1` 的数据被误淘汰）→ `p` 增大，倾向于多留 `T1`。
- 命中 `B2`（说明本该留在 `T2` 的数据被误淘汰）→ `p` 减小，倾向于多留 `T2`。
幽灵目录让 ARC 能"记住"被淘汰数据的命运，据此自我修正，无需任何手工参数。

> [!Note] ARC 的设计哲学
> 与其让用户在 LRU / LFU 间二选一，不如让缓存**根据实际命中模式自己选**。代价是实现复杂、且需为幽灵目录留出元数据空间。
## W-TinyLFU：LRU 与 LFU 的融合
Caffeine（Java）等现代缓存采用 W-TinyLFU，它把"时间局部性"与"频率局部性"显式分层组合。设计目标是**同时压制 LRU 的突发污染与 LFU 的频率老化/冷启动，且把频次统计的内存压到极低**。它由三类数据结构拼装而成，每类各司其职：

| 结构 | 底层实现 | 作用与意义 |
| --- | --- | --- |
| Window 区 | 小型 LRU（链表+哈希表） | 承接所有新进入访问，保留近期突发的瞬时局部性，缓解 LFU 冷启动 |
| TinyLFU | Count-Min Sketch + 4bit 计数 + 周期减半老化 | 紧凑频次估计器，作为"谁更值得留"的仲裁器 |
| Main 区 | 两条 LRU：Protected(80%) + Probation(20%) | 存放被 TinyLFU 确认的高频项，按时间局部性二次维护 |

每个结构的意义与设计意图：
- **Window 区（LRU）**：所有新访问先落此处。它的存在是为了**接住 LRU 擅长的"刚访问过"信号**——突发的一次性访问先在 Window 里短期停留，若立刻被复用即可体现价值，而非像朴素 LFU 那样因初始频次低被秒杀。这是直接针对 LFU 冷启动的缓冲层。
- **TinyLFU（Count-Min Sketch）**：朴素 LFU 要为每个 key 维护真实计数器，内存巨大；TinyLFU 用一个**共享的 Count-Min Sketch 概率结构**统一估计所有 key 的近期频次：
    - 多个哈希函数把一次访问映射到位数组的多个位置并 +1，查询时取各位置最小值作为频次估计——**以多哈希冗余换取"只高估不低估"**。
    - 4bit 计数器把单 key 频次上限压到 15，配合周期性整体减半老化（reset 时所有计数器右移 1 位），让"近期"频次盖过"历史"频次，解决频率老化。
    - 意义：**用 O(1) 摊还内存近似 O(N) 的精确频次表**，是整个算法省内存的关键。
- **Main 区（Protected + Probation 两条 LRU）**：从 Window 淘出的候选项先进 Probation（缓刑区）；当 Main 满需要淘汰时，Probation 尾部与新候选项**通过 TinyLFU 比较频次**，胜者留、败者走。被再次访问的 Probation 项晋升 Protected，得到"免淘汰保护"。意义：**把频次仲裁（TinyLFU）与时间维护（LRU）解耦**——谁进谁出由频次定，进退之后按时间排，两层职责清晰。
设计思路的精妙之处在于**用 LRU 接住时间局部性、用 LFU 守住频率局部性，两者通过 TinyLFU 这个频次仲裁器衔接**。它一次性回应了朴素 LRU 的"突发污染"、朴素 LFU 的"频率老化 / 冷启动"、以及 LFU 的"内存开销大"三大问题，代价是实现复杂度显著上升。
## 各算法的联系与演进
一条主线：**从纯时间（LRU）→ 纯频率（LFU）→ 时间与频率融合 / 自适应**。每个变体都在修补上一代的特定痛点，同时引入新的权衡。

| 算法 | 局部性维度 | 解决的核心痛点 | 遗留问题 |
| --- | --- | --- | --- |
| LRU | 时间 | 简单有效 | 突发污染、不区分频率 |
| LRU-K | 时间 + 次数门槛 | 抗突发污染 | 历史队列开销、冷启动 |
| Two Queue / Multi Queue | 时间 + 分层 | 命中率与开销平衡 | 参数调优复杂 |
| LFU | 频率 | 识别长期热点 | 频率老化、冷启动、开销大 |
| LFU-Aging | 频率 + 衰减 | 频率老化 | 衰减参数难调 |
| Redis LFU | 频率 + 惰性衰减 | 内存开销、频率老化 | 概率估计有误差 |
| ARC | 时间 + 频率自适应 | 免调参、自适配 | 实现复杂、幽灵目录占空间 |
| 2Q | 时间 + 频率(固定) | 抗扫描污染 | 配比固定、无自适应 |
| W-TinyLFU | 时间 + 频率融合 | 突发污染 + 冷启动 + 内存 | 实现复杂 |
> [!Info] 选型直觉
> - 访问模式偏"短期突发"→ LRU 系；
> - 偏"长期热点"→ LFU 系；
> - 两者兼具且要求高命中率 → ARC / W-TinyLFU。
> - 工程实现受内存约束 → Redis 近似 LRU / 概率 LFU。没有银弹，只有对局部性假设的匹配。

### 3.1 LRU (Least Recently Used - 最近最少使用)
- **核心思想**：“如果数据最近被访问过，那么将来被访问的几率也更高”。淘汰**最久未被访问**的数据。
- **数据结构**：通常使用 `哈希表 + 双向链表` 实现，保证 `O(1)` 的读写和淘汰时间复杂度。
- **致命弱点**：当发生**偶发性批量访问**（如数据库全表扫描、遍历大文件）时，这些只访问一次的冷数据会挤占双向链表的头部，把原本的真实热点数据挤出缓存，这被称为**缓存污染**。

### 3.2 LFU (Least Frequently Used - 最不经常使用)
- **核心思想**：“如果数据过去被访问的次数最多，那么将来被访问的几率也更高”。淘汰**访问频率最低**的数据。
- **数据结构**：通常使用 `哈希表 + 频率桶（或最小堆）` 实现。为了优化频率更新的开销，常结合“时间衰减”机制（如 Window TinyLFU）。
- **致命弱点**：**历史包袱重**。一个过去访问了 10000 次但现在已经不再使用的数据，会因为频率太高而一直留在缓存中，导致新来的热点数据无法进入（即冷启动和适应性差问题）。

### 3.3 ARC (Adaptive Replacement Cache - 自适应替换缓存)
- **核心思想**：由 IBM 提出，旨在解决 LRU 和 LFU 的痛点。它同时维护 **LRU（近期访问）** 和 **LFU（频繁访问）** 两个缓存列表，以及它们对应的**幽灵列表（Ghost Lists，记录已被淘汰数据的元数据）**。
- **工作机制**：通过观察“幽灵列表”的命中情况，**动态自适应调整** LRU 和 LFU 的容量比例。如果扫描访问多，就自动扩大 LRU 比例；如果热点集中，就自动扩大 LFU 比例。
- **代价**：虽然命中率极高且无需手动调参，但需要维护 4 个链表和额外的元数据，内存占用和逻辑复杂度显著高于 LRU/LFU。

> 由于原版 ARC 算法存在 IBM 专利问题（现已过期但影响深远），现代高性能缓存（如 Java 的 **Caffeine**）通常采用 **W-TinyLFU**（Window TinyLFU）算法。它在保留 LFU 频率感知优势的同时，引入了 LRU 的滑动窗口机制来解决冷启动和历史包袱问题，是目前综合表现最优的工业级缓存淘汰策略之一。
