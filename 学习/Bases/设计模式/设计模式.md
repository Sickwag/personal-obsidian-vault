# 详解设计模式（配合 head first 设计模式一书）
## 策略模式（strategy pattern）
 定义：

> the strategy pattern defines a family of algorithms encapsulates each one and makes them interchangeable, strategy lets the algorithm vary independently from clients that use it.

简单来说意思就是你有一系列算法用来解决不同的问题（或者应对不同的情景），但当你切换不同的算法来处理不同的事情时，你（也就是用户，使用这些算法的人）不要改变

# 生产者-消费者模式
## 边生产边消费
一种流水线形式，不断生产和消费，**两者都不会停下**
![[PixPin_2026-01-23_13-22-15.png]]
- 最重要的是将 `notify_all()` 放在 while 循环之外，因[[DevFoundations#施磊手写线程池#线程的状态|线程的状态]]决定了线程在 wait 时被挂起，被 notify 时被阻塞，获取到锁后开始执行，从阻塞到执行阶段有时间空隙，`producer()` 仍有可能被调用并且**先抢到锁**，为了解决这一情况就**允许生产者者一直生产到 vector 满**，满了后通知消费者，通知完出作用于一定会解锁，允许消费者获取锁
- 这样即使生产者通知消费者后下一次仍是生产者被调用，那么也会进入 while 中，`cv.wait()` 强制将生产者挂起，解锁保证再下一次生产者不会抢占锁。
- 消费者这一方同理
- 主要逻辑是消费者主导，消费者一直要消费，所以驱动生产者一直生产
## 生产一个消费一个
如果生产是间断性且不确定执行时间的操作，并不需要一直消费和生产，只是借助生产者消费者模式作为一种缓冲区。常用于一些负载在时间上不均衡的场景（如 [[FastLog]] 打日志）
![[PixPin_2026-01-23_13-22-25.png]]
- [[FastLog#logger.hpp]] 中使用到这个模式，日志打印完全不可预测并负载不均衡
- 这种形式不需要两者都不停工作，反而有可能两者都不工作
- 或者也可以将[[#边生产边消费|边生产边消费]]中，生产者的 `while(vector.full())` 改为 `while(vector.size() == 1)`，让生产者生产一个后就提前挂起放弃工作，引起消费者消费完现有内容后再发送生产请求。但仍是两者不停工作，只是没缓冲区

## 单例模式
### 实现方式
#### 严格但灵活的单例模式
[[AzzatoChat#单例模式]]
```cpp
template <typename T>
class Singleton {
  protected:
	Singleton()									 = default;

	// avoiding Singleton obj be copied
	Singleton(const Singleton<T>& other)		 = delete;
	Singleton& operator=(const Singleton<T>& st) = delete;

	static std::shared_ptr<T> _instance;

  public:
	static std::shared_ptr<T> getInstance();
	void					  printAddress() const;
	~Singleton();
};

template <typename T>
std::shared_ptr<T> Singleton<T>::_instance = nullptr;

template <typename T>
std::shared_ptr<T> Singleton<T>::getInstance() {
	static std::once_flag onceFlag;
	std::call_once(onceFlag, [&]() { _instance = std::shared_ptr<T>(new T); });
	return _instance;
}
```
这种实现方式在使用方式上需要配合
- 继承 Singleton 的类需要 public 继承才能调用 `getInstance()`
- 如果派生类的构造函数在 private 中，派生类必须 `friend Singleton<T>` 
	- [[C++ Runoob Tutoral#继承方式|任何继承关系都无法让子类看到父类的private]]
	- 派生类由于继承关系可以看到父类 Singleton 中的 public+protect 内容，protect 中保证了派生类无法被复制（子类调用**会隐式调用父类的相同函数**，比如构造函数），而 public 保证了能够使用 `getInstance()` 得到单例，而基类看不到派生类的内容
	- 继承了 `Singleton<T>` 的派生类 `getInstance()` 需要 `new T`，这个操作需要 `getInstance()` 函数所在作用于能够访问到 T 的构造函数，**非 private**继承无法看到 private 中的**编译器生成的 `Singleton<T>` 类型的构造函数**
- 如果派生类的构造函数在 public 中，**派生类不必使用 `friend Singleton<T>`，但添加了也没关系**
	- 放在 public 中并且继承自 `Singleton<T>` 的做法是一种*不严谨的单例模式实现*，因为 public 构造函数允许多种创建对象方式，这是一种保险实现，防止以后将构造函数移动到 private 中之后需要大改代码
```cpp
DBManager::GetInstance()->query(...); 	// 所用方式都允许，这也是单例模式想要严格确保全局唯一性所需的
DBManager mgr;              			// 在构造函数为 private 时会产生编译错误，public 时不会
auto mgr = new DBManager(); 			// 同上
```
- 为什么不干脆所有类都是用 private 构造函数+friend 实现？
	- 测试环境中想要临时创建只有功能接口，没有实际实现的测试类（比如一个不连接真实数据库数据库数据的数据库类），只要在类中添加了 friend，就会连接真实数据库，没有就会因为 new 无法访问 private 函数报错，想要批量创建需要改动代码，非常麻烦
	- 测试环境中，可能要同时测多个不同作用的实例的功能，这一般使用工厂函数**批量创建单例对象**
	- 易用性，上面已经提到
```cpp
auto db1 = std::make_shared<Database>("config1");
auto db2 = std::make_shared<Database>("config2");
auto dbDefault = DatabaseMgr::GetInstance();
```
- 一般来说，public 构造常用于编写外部库，便于其他人不需要了解某个类是不是单例对象，内部实现细节是什么的情况下通过直觉得到一个单例对象（但是调用者并不需要知道这个对象其实是单例的，比如 boost.asio 的 `io_context` 对象）
无论什么实现方式，都应该使用单例模式推荐的 `getInstance()`（在 public 构造函数场景下一般通过 CI 规范和 code review 约束），简单来说，public 构造是一种 "信任开发者正确使用" 的设计哲学，private 构造是**编译器强制你正确使用**
#### 简单的单例实现
[[Sylar Backend Collection#单例模式]]
```cpp
template <class T, class X, int N>
T& getInstanceX() {
	static T v;
	return v;
}

template <class T, class X, int N>
std::shared_ptr<T> getInstancePtr() {
	static std::shared_ptr<T> v(new T);
	return v;
}

// Singleton — 返回裸指针，调用方不参与生命周期管理，生命周期一定不会有问题放心用
template <class T, class X = void, int N = 0>
class Singleton {
  public:
	static T* getInstance() {
		static T v;
		return &v;
	}
};

// SingletonPtr — 返回 shared_ptr，调用方可以持有引用延长生命周期
template <class T, class X = void, int N = 0>
class SingletonPtr {
  public:
	static std::shared_ptr<T> getInstance() {
		static std::shared_ptr<T> v(new T);
		return v;
	}
};
```
- X，N 模板参数似乎没有使用，但其实是为了创建*多个单例*，这似乎违反单例设计意义？
- 测试过程中可能需要多个单例并行测试多个功能，但是由于单例模式全局唯一，而模板类/函数可以通过模板参数作为标签生成不同的类/函数代码，两者结合
```cpp
// 项目中有一个 ConfigVar 类表示配置变量
// 你有两套完全独立的配置系统（一套给业务用，一套给框架底层用），X参数一般指向一个空结构体，只用作tag功能
using BusinessConfig = Singleton<ConfigVar, struct BusinessTag>;
using SystemConfig   = Singleton<ConfigVar, struct SystemTag>;

BusinessConfig::GetInstance()->set("timeout", 5000);
SystemConfig::GetInstance()->set("timeout", 1000);   // ← 不同的内存地址！
// 两套互不干扰，各自有自己的 static ConfigVar v
// 同一个类型T，但生成不同的类代码->不同的**单例对象**
```
N 用于第三维度，即 X 如果还不够区分则用上N
实际上项目中 `GetInstanceX()/GetInstancePtr()` 是历史实现（保留了但项目中并没有用到）
C++11 之前，使用**饿汉式静态变量生命不是线程安全的**，多线程操作中可能多次初始化 static 变量，C++11 通过编译器保证
```cpp
// C++11中的单例模式（自动线程安全）
Singleton& getInstance() {
    static Singleton instance;  // 编译器保证线程安全初始化
    return instance;
}

// 编译器生成的伪代码类似：有些编译器中使用call_once保证
Singleton& getInstance() {
    static std::atomic<bool> initialized = false;
    static std::aligned_storage_t<sizeof(Singleton)> storage;

    if (!initialized.load(std::memory_order_acquire)) {
        std::lock_guard<std::mutex> lock(global_mutex);
        if (!initialized.load(std::memory_order_relaxed)) {
            // 构造对象
            new (&storage) Singleton();
            initialized.store(true, std::memory_order_release);
        }
    }
    return *reinterpret_cast<Singleton*>(&storage);
}
```
### 存储单例的方式
1. 函数局部 static 对象: 单例对象被**存储至静态区**，通过 C++11 特性保证生命周期\=程序运行生命周期
2. 成员 static 对象+ new: 单例对象存储至堆，需要 `call_once`，现代 C++更提倡方法 1 的 [[AzzatoChat#std once_flat 和 std call_once 保证多线程单例|Magic static]] 方式创建单例，而这种方法常用于多线程中保证某些**操作**只执行一次，不再用于单例对象的创建
3. 成员 static 对象 + 栈对象: 不常用
4. `static shared_ptr<T> instance` 方法一般用于需要手动控制生命周期或者复杂的自定义删除器的情况，比如游戏关卡中，每一关结束之后删除这一关的所有资源，而不是用 static 在整局游戏中保留每一关的数据
