# 硬件结构篇
计算机基本结构为 5 个部分，分别是**运算器、控制器、存储器、输入设备、输出设备**，这 5 个部分也被称为**冯诺依曼模型**。
![[冯诺依曼模型.webp]]
## CPU
### 一次计算
- 32 位 CPU 一次可以计算 4 个字节；
- 64 位 CPU 一次可以计算 8 个字节；
"一次计算"指的是: **CPU 内部通用寄存器的宽度**，以及 **算术逻辑单元（ALU）单次处理整数数据的最大位宽**。
"一次"指
- 32 位系统中，ALU 在**一个时钟周期里**，能从内存中读取 4 个字节放进运算器里算，运算器执行一条单周期或单发的整数运算指令。
- 时钟周期时间为 CPU 主频的的倒数。所以 CPU 的**理论上数据吞吐量由主频 * CPU 位宽得到**，但这需要几个前提:
	- 一个时钟周期执行一条指令（显示是大多数指令包括四则运算都需要多个时钟周期完成，乘除更多。现在还有 SIMD 技术）
	- 这种算法仅能描述理论上 **CPU 内部缓存到寄存器的带宽**，实际上数据从寄存器到 CPU 还有一些额外的工作，达不到这么高的速度
- 但实际上数据吞吐量还需要考虑和内存交换数据的效率，内存读写吞吐量: 理论带宽 = 内存总线频率 × 内存总线位宽 × 通道数。内存总线的位宽**固定是 64 位**（即 8 字节），双通道就是 128 位。还要考虑木桶效应
“计算”特指对整数的运算（加减，位移和逻辑运算），**不包含浮点数**（浮点数有专门的协处理器或向量单元处理）。
- 32 位 CPU 处理 64 位数据需要分别对高位和低位做一次运算并合并结果
### 寄存器
重要的寄存器
- _通用寄存器_，用来存放需要进行运算的数据，比如需要进行加和运算的两个数据。
- _程序计数器_，用来存储 CPU 要执行下一条指令「所在的内存地址」，注意不是存储了下一条要执行的指令，此时指令还在内存中，程序计数器只是存储了下一条指令「的地址」。
- _指令寄存器_，用来存放当前正在执行的指令，也就是指令本身，指令被执行完成之前，指令都存储在这里。
CPU 执行指令的流程:
- 第一步，CPU 读取「程序计数器」的值（指令的内存地址），然后 CPU 的「控制单元」操作「地址总线」指定需要访问，接着通知内存设备准备数据，数据准备好后通过「数据总线」将指令数据传给 CPU，CPU 将这个指令数据存入到「指令寄存器」。
- 第二步，「程序计数器」的值自增，表示指向下一条指令。这个自增的大小，由 CPU 的位宽决定，32 位 CPU「程序计数器」的值会自增 4；
- 第三步，CPU 分析「指令寄存器」中的指令，确定指令的类型和参数，如果是计算类型的指令，就把指令交给「逻辑运算单元」运算；如果是存储类型的指令，则交由「控制单元」执行；
### 指令
汇编代码专成机器码之后形式变为二进制，不同的指令集对一段相同的二进制编码的解释方式不一样，这里使用 MIPS 指令集
MIPS 的指令是一个 32 位的整数，高 6 位代表着操作码，表示这条指令是一条什么样的指令，剩下的 26 位不同指令类型所表示的内容也就不相同，主要有三种类型 R、I 和 J。
![[MIPS指令集.webp]]
- R 类型用于逻辑和算术运算
	- shamt 用于计算逻辑位移操作的参数
	- func 用于 opcode 不够时的拓展
- I 指令，用在数据传输、条件分支等，简单的语义让只需要地址参数就可以
- J 指令，用于跳转，target address 表示跳转目的地
现代大多数 CPU 都使用来流水线的方式来执行指令，所谓的流水线就是把一个任务拆分成多个小任务，于是一条指令通常分为 4 个阶段，称为 4 级流水线
![[CPU指令周期.webp]]
编译时程序将指令编码，Decode 表示 CPU 读取指令并按照指令集规定解释，叫做解码
1. CPU 通过程序计数器读取对应内存地址的指令，这个部分称为 **Fetch（取得指令）**；
2. CPU 对指令进行解码，这个部分称为 **Decode（指令译码）**；
3. CPU 执行指令，这个部分称为 **Execution（执行指令）**；
4. CPU 将计算结果存回寄存器或者将寄存器的值存入内存，这个部分称为 **Store（数据回写）**；
四个步骤称之为*指令周期*，不同的阶段其实是由计算机中的不同组件完成的：
![[指令周期工作组件.webp]]

> [!Info]  32 位的操作系统可以运行在 64 位的电脑上吗？反之如何？
> 64 位和 32 位软件，实际上代表指令是 64 位还是 32 位的
> - 32 位指令在 64 位机器上执行，需要一套兼容机制，由操作系统提供。
> - **64 位指令在 32 位机器上执行，就比较困难了，因为 32 位的寄存器存不下 64 位的指令**；在硬件上，也没有执行长指令的硬件电路，32 位 CPU 的 ALU 也是 32 位的，大数计算导致溢出
> - 操作系统其实也是一种程序，我们也会看到操作系统会分成 32 位操作系统、64 位操作系统，其代表意义就是操作系统中程序的指令是多少位，比如 64 位操作系统，指令也就是 64 位，因此不能装在 32 位机器上。

### 寄存器
寄存器的数量通常在几十到几百之间，每个寄存器可以用来存储一定的字节（byte）的数据。比如：
- 32 位 CPU 中大多数寄存器可以存储 `4` 个字节；
- 64 位 CPU 中大多数寄存器可以存储 `8` 个字节。
性能很高，一般要求在半个 CPU 时钟周期内完成读写
### CPU cache
CPU Cache 用的是一种叫 **SRAM（_Static Random-Access_ Memory，静态随机存储器）** 的芯片。
在 SRAM 里面，一个 bit 的数据，通常需要 6 个晶体管，所以 SRAM 的存储密度不高，同样的物理空间下，能存储的数据是有限的，不过也因为 SRAM 的电路简单，所以访问速度非常快。
![[CPU-Cache.webp]]
#### store buffer 和 load buffer
即使写 L1 cache 也要 3-10 周期。如果 CPU 每写一次都要等 cache 完成，流水线就卡死了。所以 CPU 加了一个写缓冲区（store buffer）。写操作先进入 store buffer（只要 1 周期），CPU
  立刻继续执行后面的指令，store buffer 里的内容再异步刷入 L1 cache。
- 当 CPU 执行 store 指令（将数据写入内存操作）时，数据先写入 store buffer，而非立即写入 L1 缓存
- 允许 CPU 乱序执行：在等待存储操作完成时继续执行后续指令
- 实现 store-to-load forwarding（存储转发），加速数据传递
*条目*的数据结构为:
```md
// store buffer
┌─────────────────────────────────────┐
│  Entry N                            │
├─────────────────────────────────────┤
│  Valid Bit (有效位)                  │
│  Memory Address (地址)               │
│  Data (数据，通常 8-64 字节)          │
│  Size/Length (写入大小)              │
│  Sequence Number (序列号)            │
└─────────────────────────────────────┘

// load buffer
┌──────────────────────────────────────────┐
│  Valid │ Address │ Waiting Instructions │
│   ✓    │ 0x5678  │ [load1, load2, ...]  │
└──────────────────────────────────────────┘
```
不同 CPU 的 store buffer 条目容量不同，在 48~72 条之间，store buffer 满时，CPU 必须等待（stall）才能继续执行新的 store，当 CPU 执行
```asm
mov [rdi], rax    ; store: 写地址 A，值 X
mov rbx, [rdi]    ; load: 从地址 A 读数据
```
此时 CPU 不需要等待 store 写入 L1 cache，而是直接从 store buffer 中读取最新值，这个过程叫 store-to-load forwarding。没有他的存在就会导致 CPU 与 L1 速度差距过大引起 CPU 空转

> [!note] buffer 机制和内存序
> - 两个 buffer 在 CPU 核心与 L1 之间，程序员不可见
> - Store buffer = "我要写什么"，Load buffer = "我在等什么"。两者结构相似但语义相反。

#### L1 cache
L1 高速缓存的访问速度几乎和寄存器一样快，通常只需要 `2~4` 个时钟周期，而大小在几十 KB 到几百 KB 不等
指令和数据在 L1 是分开存放的，所以 L1 高速缓存通常分成**指令缓存**和**数据缓存**。
```bash
 ~  cat /sys/devices/system/cpu/cpu0/cache/index0/size # 查看数据缓存大小
48K
 ~  cat /sys/devices/system/cpu/cpu0/cache/index1/size # 查看指令缓存大小
32K
```
#### L2 cache
不分指令和数据缓存，一般在几百 K 到 2MB 之间，IO 速度在 `10~20` 个时钟周期。
#### L3 cache
几 MB 到几十 MB 不等，速度在 `20~60` 个时钟周期。
#### 数据结构
CPU Cache 是由很多个 Cache Line 组成的，Cache Line 是 CPU 从内存读取数据的基本单位，而 Cache Line 是由各种标志（Tag）+ 数据块（Data Block）组成

> - 如果写多线程程序，最好保证访问的数据有间隔，让它们不在一个 Cache line 上，减少 False Sharing 的频率。（防止多 CPU 的多线程场景下的缓存失效）

- 有效位是缓存行中的一个 1 位标志，用于标识该缓存行中的数据是否有效。CPU 启动时，所有缓存行为空，有效位初始化为 0，用于防止有效数据被覆盖，优先寻找有效位为 0（硬件比较，非常快）
- 标记位是缓存行中用于标识该缓存行对应主存中哪个内存块的字段，CPU 访问内存时，发出的是一个 **32 位（或 64 位）的完整物理地址**。但 Cache 容量很小，为了快速查找，CPU 会把完整地址**拆分成三段**

| **低位（Offset）** | 块内偏移（6 位，因为 2^6=64 字节）      |
| **中位（Index）**  | 索引（决定去 Cache 的**哪一组/哪一行**找） |
| **高位（Tag）**    | **标记位/标签**（剩余的位数）           |

#### 缓存行读取过程
CPU 无论数据是否存放到 Cache 中，CPU 都是先访问 Cache，只有当 Cache 中找不到数据时才会去访问内存，并把内存中的数据读入到 Cache 中，CPU 再从 CPU Cache 读取数据。CPU 访问内存数据时，是一小块一小块数据读取的，具体这一小块数据的大小，取决于 `coherency_line_size` 的值，一般 64 字节。
- **缓存以行为单位读写，即使只访问一个字节，也会加载整个缓存行**
- 一行的数据称之为*块*（block）
- 寄存器大小小于 64 字节，每次读取缓存行只会读取其中的一个片段，片段内的数据被称之为*字*（word）
这就引出了==CPU 怎么知道要访问的内存数据是否在 Cache 里？如果在的话如何找到 Cache 对应的数据？==问题
现代 CPU 一般使用*组相联映射*的方式寻址，[三种寻址方式参考](https://blog.csdn.net/e2788666/article/details/125485606) ，现代 CPU 使用组相联映射，并固化在电路中。CPU 发出的**取数指令**（32 位或 64 位），把请求地址的 **高位 Tag（身份证号）** 放在总线上，同时发给这个组里的 **8 个缓存行**。每一行缓存旁边，都附带着一个**硬件的数字比较器（Comparator）**。这 8 个比较器**在同一时刻（并行）** 做一件事
- **比较器**把“请求的 Tag”和“这一行里存放的 Tag”进行二进制逐位比对。
- 8 个比较器几乎是光速同时得出结果：`相等（Equal）` 或 `不相等（Not Equal）`。
- 现代 CPU 厂商已经将这个过程优化到在 1~2 个时钟周期内完成
如果 equal，则**先检查有效位**，再通过 index 和 offset 读取数据
#### 缓存行写入过程
由于 L1/L2 是独占，而 L3 共享导致所有 CPU 中数据同步不能立刻实现，需要先将更新的数据通过一个核心写入内存，然后其他核心读取内存来得知。cache 数据写入内存的时机分为:
- 写直达（_Write Through_）: 保持内存与 Cache 一致性最简单的方式是，**把数据同时写入内存和 Cache 中**，无论数据是否在 cache 中
![[写直达.webp|350]]
- 写回（_Write Back_）: **新的数据仅仅被写入 Cache Block 里，只有当修改过的 Cache Block「被替换」时才需要写到内存中**，减少了数据写回内存的频率。
![[写回1.webp]]
当 CPU 执行**写操作（Store 指令）且缓存命中**（Cache Hit）时，CPU 会修改该缓存行里的数据。只要数据被修改了，硬件逻辑就会立刻将该缓存行附带的 Dirty Bit 置为 1 表示 cache 中存储的数据和内存中的不一样
需要注意，现代脏位不占用 CPU 硬件中的位置，因为它是通过 **MESI 协议状态编码** 隐式体现的，以前的 CPU 架构中，脏位在 Tag 标记字段中
- **MESI 协议**：每个缓存行有四种状态（Modiied, Exclusive, Shared, Invalid）。
- **“脏”的含义被包含在 `Modified（M）` 状态里**。
    - 如果该行状态是 **Modified（M）**，即表示：**该行有效（V=1）+ 数据被修改过（等同于 Dirty=1）+ 且只有我有这份数据**。
    - 当系统需要替换这行数据时，只要看到状态是 `M`，就知道必须把数据写回内存（这就相当于脏位起作用了）。

假设 CPU 要写内存地址 B，但缓存里只有存放地址 A 的脏块。
- **驱逐**: CPU 先将脏数据 A 从 cache block 写回到内存中，这时 A 地址中是 CPU 中要写入的最新数据
- **填充**: 新数据（地址 B）在 Cache 里找不到，CPU 必须去内存取，这里**取的是旧数据**，此时 cache block 中存储的旧数据。
- **修改**: CPU 把自己**寄存器**里保存的那个“新数据”（比如只有 4 个字节），写入到这个 Cache Block 的对应位置（覆盖掉刚才读进来的那 4 个字节旧值），**最后，把脏位（Dirty）置为 1**
注意，***只有驱逐和填充的操作是以整个 block 作为单位操作的***，修改阶段只会改小部分
#### 缓存一致性问题
写回策略会导致问题:
CPU A 将 `i++`，但这个修改只会存在于 CPU A 的 L1/L2 中并标记为 dirty，并**在下一次被替换时写入内存**，现在 CPU B 读取得到错误的值
![[缓存一致性问题例子.webp|400]]
解决这个问题依靠:
- 第一点，某个 CPU 核心里的 Cache 数据更新时，必须要传播到其他核心的 Cache，这个称为**写传播（_Write Propagation_）**；
- 第二点，某个 CPU 核心里对数据的操作顺序，必须在其他核心看起来顺序是一样的，这个称为**事务的串行化（_Transaction Serialization_）**。
写传播通过*总线嗅探*实现，任何 CPU 修改自己的 L1 cache 会**广播总线上的所有 CPU 修改他们自己的 L1**，MESI 协议基于总线嗅探实现了事务串行
#### MESI 协议
- _Modified_，已修改，即脏标记，代表该 Cache Block 上的数据已经被更新过，但是还没有写到内存里。
- _Exclusive_，独占，「独占」和「共享」状态都代表 Cache Block 里的数据是干净的， Cache Block 里的数据和内存里面的数据是一致的。数据只存储在一个 CPU 核心的 Cache 里，向独占的 Cache 写数据可以自由地写入而不需要通知其他 CPU 核心，数据是独占的不存在一致性问题。**在「独占」状态下的数据，如果有其他核心从内存读取了相同的数据到各自的 Cache ，切换到共享状态**
- _Shared_，共享，不能直接修改，要先向所有的其他 CPU 核心广播请求，要求先把其他核心的 Cache 中对应的 Cache Line 标记为「无效」状态，然后再更新当前 Cache 里面的数据
- _Invalidated_，已失效，表示的是这个 Cache Block 里的数据已经失效了，不可以读取该状态的数据![[MESI协议.webp]]
![[_MESI状态转换表格.webp]]
#### 分支预测器
对于 if 条件语句，意味着此时至少可以选择跳转到两段不同的指令执行，也就是 if 还是 else 中的指令。那么，如果分支预测可以预测到接下来要执行 if 里的指令，还是 else 指令的话，就可以「提前」把这些指令放在指令缓存中，这样 CPU 可以直接从 Cache 读取到指令，于是执行速度就会很快。
当数组中的元素是随机的，分支预测就无法有效工作，而当数组元素都是是顺序的，分支预测器会动态地根据历史命中数据对未来进行预测，这样命中率就会很高。
#### 多核 CPU 提高缓存命中率（cache hit）
虽然 L3 共享，但是最快的 L1/L2 是每个 CPU 独有的，**如果一个线程在不同核心来回切换，各个核心的缓存命中率就会受到影响**，在 Linux 上提供了 `sched_setaffinity` 方法，来实现将线程绑定到某个 CPU 核心这一功能
```cpp
int sched_setaffinity(pid_t pid, size_t cpusetsize, cpu_set_t *mask);
```
### CPU 如何执行任务
#### Cache 伪共享
因为多个线程同时读写同一个 Cache Line 的不同变量时，而导致 CPU Cache 失效的现象称为**伪共享（False Sharing）**
注意区分**真共享与伪共享**：真共享（True Sharing）是多个核心的 cache 缓存**同一个变量**，属数据竞争/同步范畴；而伪共享是多个**不同的变量**恰好落在**同一个 cache line**，核心 A 修改其中一个变量，经 [[#MESI 协议]] 使其他核心整个 cache line 失效（cache miss，每次浪费 ~100 时钟周期），而本质上这些变量是**不相关的**，核心间却不断通过总线探测广播互相干扰。具体过程参考: [小林 Coding 图解](https://xiaolincoding.com/os/1_hardware/how_cpu_deal_task.html#%E5%88%86%E6%9E%90%E4%BC%AA%E5%85%B1%E4%BA%AB%E7%9A%84%E9%97%AE%E9%A2%98)
产生伪共享的前提是: 2 个以上的变量且连续存储被 CPU 读写，引出 [CPU Cache伪共享问题：原理与优化指南](https://chengxumiaodaren.com/docs/performance/cpu-cache/) ，需要手动在构建数据类/结构体时**将频繁在多线程上 IO 的成员**通过[[Modern C++#手动控制内存对齐|手动控制内存对齐]]来解决
#### 进程调度
- 调度策略 = 用户给线程"贴的标签"（我想让它怎么被调度）
- 调度类 = 内核根据标签把线程归到哪一类（这类用哪个算法）
- 调度算法 = 类内部的具体规则（怎么排、怎么抢）
- 运行队列 = 每个 CPU 上存放"等着跑的任务"的数据结构
- 调度器 = 每次切换时，从运行队列里挑下一个该跑的线程
```md
用户态看到的：   调度策略 (Scheduling Policy)
                    SCHED_NORMAL / BATCH / FIFO / RR / DEADLINE
                         │  用户通过 sched_setscheduler() 设置
                         ▼
内核中间层：     调度类 (Scheduling Class)
                    fair / rt / dl / stop / idle
                         │  一个类实现一个算法族，暴露统一接口
                         ▼
内核核心：       调度器 (Scheduler)  →  调度算法 (Algorithm)
                    遍历所有调度类，按优先级挑下一个任务
                         │
                         ▼
数据载体：       运行队列 (Run Queue)
                    每个 CPU 一套，内部按类分区存放可运行任务
```
 Linux 系统中，根据任务的优先级以及响应要求，主要分为两种，其中优先级的数值越小，优先级越高，一般分为实时任务（高优先）和普通任务（相对低优先）。为了保障高优先级的任务能够尽可能早的被执行，于是分为了这几种调度类


| 优先级 | 调度类              | 调度器          | 调度策略                                    | 算法        | 用途                 | 运行队列   |
| --- | ---------------- | ------------ | --------------------------------------- | --------- | ------------------ | ------ |
| 最高  | stop_sched_class | 停止调度器        | —                                       | 特殊        | 迁移线程/CPU 停机，必须立即执行 | —      |
| 高   | dl_sched_class   | Deadline 调度器 | SCHED_DEADLINE                          | EDF + CBS | 硬实时带宽保证            | dl_rq  |
| 中   | rt_sched_class   | RT 调度器       | SCHED_FIFO / SCHED_RR                   | 实时固定优先级   | 软实时                | rt_rq  |
| 低   | fair_sched_class | CFS 调度器      | SCHED_NORMAL / SCHED_BATCH / SCHED_IDLE | CFS       | 通用分时               | cfs_rq |
| 最低  | idle_sched_class | 空闲调度器        | —                                       | 特殊        | 空闲任务（CPU 没事干）      | —      |
Deadline 和 Realtime 这两个调度类，都是应用于实时任务的，这两个调度类的调度策略合起来共有这三种，它们的作用如下：
- _SCHED_DEADLINE_：是按照 deadline 进行调度的，距离当前时间点最近的 deadline 的任务会被优先调度；任务声明三个参数：
    - runtime：每周期最多运行多少
    - deadline：相对截止时间（从周期开始算）
    - period：周期
- _SCHED_FIFO_：高优先级可以"插队"在低优先级前面，同优先级按照 FIFO 执行，没有冲突
    - 一旦运行，一直占用 CPU，直到自己主动阻塞（sleep/I/O）、让出（sched_yield）或退出
    - 没有时间片！同优先级 FIFO 任务之间不会互相抢占
- _SCHED_RR_：对于相同优先级的任务，每个任务都有一定的时间片，当用完时间片的任务会被放到队列尾部，以保证相同优先级任务的公平性，高优先级的任务依然可以抢占低优先级的任务；
Fair 调度类是应用于普通任务，都是由 CFS 调度器管理的，分为两种调度策略：
- _SCHED_NORMAL_：绝大多数普通任务使用的调度策略，调度算法是 CFS 完全公平调度
- _SCHED_BATCH_：后台任务的调度策略，不和终端进行交互，因此在不影响其他需要交互的任务，可以适当降低它的优先级，一般是大批量，长时间的数据计算，如编译，计算等
	- 减少唤醒抢占（不因"醒了就立刻抢 CPU"）
	- 更倾向于让当前任务跑完一个较长的时间片再切换（减少切换开销）
	- 可以设 sched_autogroup 等做进一步优化

**三类调度策略对比：**

| | NORMAL/BATCH | FIFO/RR | DEADLINE |
| --- | --- | --- | --- |
| 调度类 | fair | rt | dl |
| 能否被普通任务抢占 | — | 否（普通抢不过它） | 否 |
| 能否被同类抢占 | 能（按 vruntime） | FIFO 否 / RR 能 | 能（按 deadline） |
| 是否保证带宽 | 否 | 否（可能饿死低优先级） | 是（CBS 保证） |
| 优先级表达 | nice -20~19 | sched_priority 1~99 | runtime / deadline / period |
| 主要风险 | 无 | 死循环且不 sleep 会卡死系统 | 带宽算错导致延迟 |

**FIFO vs RR 对比：**

| | SCHED_FIFO | SCHED_RR |
| --- | --- | --- |
| 时间片 | 无 | 有（默认 ~100ms，`sched_rr_get_interval` 可查） |
| 同优先级抢占 | 不抢占 | 时间片到期则放到同优先级队列末尾 |
| 自己让出 CPU | 阻塞 / `sched_yield` | 同左 + 时间片到期 |

**时效性：Linux 6.6（2023）起 fair 类 CFS 被 EEVDF 取代**
- CFS 取 vruntime 最小；EEVDF 取"虚拟截止时间"（lag + 分配的 slice）最近
- EEVDF 在 vruntime 基础上增加"期望调度延迟"维度（`sched_setattr` 的 `sched_runtime`），可精确控制每个任务的延迟与公平
- Ubuntu 24.04 内核 6.8 已是 EEVDF；但 CFS 的 vruntime / 权重 / nice 概念仍是理解 EEVDF 的基础

#### 任务调度算法
##### 完全公平调度（Completely Fair Scheduling）
算法的理念是设备是一台"理想的多任务 CPU"——假设 CPU 能以无限快的速度同时运行所有任务，每个任务分到与它权重成正比的时间。CFS 用软件模拟这个理想，让每个任务尽量接近它应得的份额。
它为每个任务安排一个虚拟运行时间 vruntime，如果一个任务在运行，其运行的越久，该任务的 vruntime 自然就会越大，而没有被运行的任务，vruntime 是不会变化的。
**在 CFS 算法调度的时候，会优先选择 vruntime 少的任务**，以保证每个任务的公平性
```
虚拟运行时间   vruntime += 实际运行时间   delta_exec * NICE_0_LOAD / 权重
```
权重值由 nice 值映射而来（可以为负数），权重越大，nice 越小，vruntime 增长越慢，运行时间越长
![[优先级.webp]]
我们可以在启动任务的时候，可以指定 nice 的值，比如将 mysqld 以 -3 优先级：
```bash
$ nice -n -3 /usr/sbin/mysqld
```
如果想修改已经运行中的任务的优先级，则可以使用 renice 来调整 nice 值：
```bash
$ renice -10 -p <进程pid>
```
nice 调整的是普通任务的优先级，所以不管怎么缩小 nice 值，任务永远都是普通任务，如果某些任务要求实时性比较高，那么你可以考虑改变任务的优先级以及调度策略，使得它变成实时任务，比如：
```bash
# 修改调度策略为 SCHED_FIFO，并且优先级为 1
$ chrt -f 1 -p 1996
```
**CFS 数据结构与复杂度：**
- 每 CPU 一棵红黑树，键 = vruntime，最左节点 = 下一个运行任务
- 取最左节点（vruntime 最小）：O(1)；任务入队/出队（enqueue/dequeue）：O(log n)

**切片（slice）计算：**
```c
slice = sched_latency_ns × (task_weight / cfs_rq 总权重)
```
- `sched_latency_ns` 默认 ~6ms（sysctl_sched_latency），目标是让所有可运行任务在一个周期内都轮到一次
- 任务过多时周期被拉长，用 `min_granularity`（默认 ~0.75ms）设下限，避免切换过于频繁
- 周期 = max(sched_latency_ns, nr_running × min_granularity)

**抢占逻辑：**
- 唤醒新任务时若其 vruntime 比当前任务小、且差值超过 `wakeup_granularity`（~1ms）→ 标记 `need_resched`
- 真正切换发生在从内核返回用户态的安全点（延迟抢占），所以线程切换总发生在"系统调用返回"时
#### 任务队列
每个 CPU 都有自己的**运行队列**，多任务的数量基本都是远超 CPU 核心数量，因此这时候就需要**排队**
![[CPU队列.webp]]
由于[[#进程调度]]中，调度类也是有优先级的，Linux 选择下一个任务执行的时候，先从 `dl_rq` 里选择任务，然后从 `rt_rq` 里选择任务，最后从 `cfs_rq` 里选择任务。因此，**实时任务总是会比普通任务优先被执行**。（完整顺序为 stop → dl → rt → fair → idle，此处简写了其中可调度部分）
CFS 把可运行任务存在一个 per-CPU 的红黑树，以 vruntime 为键，最左节点就是下一个要运行的任务
**每个 CPU 的运行队列（`struct rq`）内部按调度类分区：**
```
CPU N 的运行队列 (struct rq)
├── stop 类   （迁移线程，最高）
├── dl_rq     → SCHED_DEADLINE（红黑树按 deadline 排序）
├── rt_rq     → SCHED_FIFO/RR（100 个优先级链表）
├── cfs_rq    → SCHED_NORMAL/BATCH（红黑树按 vruntime 排序）
└── idle 任务  （空闲，最低）
```
- 运行队列是 per-CPU 的，调度器只在当前 CPU 的 rq 里挑任务
- 任务在 CPU 间迁移 = 从 A 的 rq 出队（dequeue_task）+ 加入 B 的 rq（enqueue_task）
- 调度类的接口（`enqueue_task` / `dequeue_task` / `pick_next_task` / `check_preempt_curr`）就是对这组子队列的操作
## 内存和硬盘
DRAM 存储一个 bit 数据，只需要一个晶体管和一个电容就能存储，但是因为数据会被存储在电容里，电容会不断漏电，所以需要「定时刷新」电容，才能保证数据不会被丢失。内存速度大概在 `200~300` 个时钟周期之间。
内存的读写速度比 SSD 大概快 `10~1000` 倍，比机械硬盘快 `10w` 倍左右

"为了弥补 CPU 与内存两者之间的性能差异，就在 CPU 内部引入了 CPU Cache，也称高速缓存"，实际需要密闭的底层原因有这些:
- SRAM/DRAM 物理结构完全不一样，SRAM 造价极高，全 SRAM 的电脑毫无商业价值
- 光速物理极限，**电信号的传输速度（约等于光速的 2/3**，主板上的内存条和 CPU 距离限制了数据从两者之间往返会消耗 15~30 纳秒，期间 CPU 空转 50~100 个时钟周期
- 程序的“局部性原理”，**内存数据的读取不是完全随机的**，使用 cache 可以明显提高速度
# 系统结构篇
## 中断
CPU 默认是顺序执行的，但现实世界充满异步事件，CPU 只能通过**轮询或者中断**的方式处理这些异步事件，轮询无疑是低效的。
中断的定义就是: **一种硬件机制**，让 CPU 在执行当前指令流的过程中，被一个异步事件"打断"，跳去执行一段专门的代码，处理完再回来接着原来的指令继续。
### 中断和异常的区别

|          | 中断（Interrupt） | 异常（Exception）    |
| :------- | :------------ | :--------------- |
| **触发方式** | 异步，外部硬件事件     | 同步，当前指令本身导致      |
| **例子**   | 网卡、定时器、键盘     | 除零、缺页、非法指令       |
| **谁发起**  | 外部设备 / 其他 CPU | 指令执行过程中 CPU 自己发现 |
| **能否恢复** | 能，处理完继续       | 多数能（缺页），部分致命（除零） |
两者在 x86 上共用同一套机制（IDT 中断描述符表），Linux 把它们统称为"中断/异常"统一处理
### 中断处理
  每个中断有一个中断向量号（0~255），对应 IDT 里的一项。完整流程：
```md
  设备发出中断请求 → 中断控制器（PIC/APIC）→ 给 CPU 发中断信号
                                                      │
                                                      ▼
  1. CPU 执行完当前指令（指令边界）                       │
  2. 检查 IF 标志（中断使能位）                           │
     中断使能 → 开始处理                                 │
  3. 把当前程序的现场压栈：                               │
     - RFLAGS（标志寄存器）                             │
     - CS / RIP（下一条指令地址）—— 这样处理完能回来        │
     - （若发生特权级切换还压 SS/RSP）                    │
  4. 根据向量号查 IDT，找到处理函数地址                    │
  5. 跳转到处理函数执行                                  │
     （中断门会清 IF，暂时屏蔽同级中断，防嵌套）            │
  6. 处理完毕执行 IRET（中断返回指令）                    │
     - 从栈上恢复 RFLAGS / CS / RIP                    │
     - 回到被打断的指令继续执行                           │
                                                      ▼
```
被中断的程序自己不知道发生了中断——它只是"暂停-恢复"，现场被硬件自动保存和恢复
### 中断处理程序
为了避免由于中断处理程序执行时间过长，而影响正常进程的调度，Linux 将中断处理程序分为上半部和下半部：
```md
┌─────────────────────────────────────────────────────────┐
│  上半部（硬中断）                                         │
│  · 立即执行，处理最紧急的事                             │
│  · 由硬件触发中断，用来快速处理中断；、读设备状态              │
│  · 把要做的重活"登记"给下半部                           │
│  · 必须极快返回（微秒级）                               │
│  · 运行在"中断上下文"，不能 sleep                        │
├─────────────────────────────────────────────────────────┤
│  下半部（软中断）                                          │
│  · 延迟执行真正的工作，由内核触发中断，用来异步处理上半部未完成的工作 │
│  · 三种实现：softirq / tasklet / workqueue                │
│  · 可以（在合适条件下）sleep、被调度                         │
└─────────────────────────────────────────────────────────┘
```
硬中断中**不能 `sleep`**，因为 sleep 是调用系统调度器，将当前进程的线程**切换出去**，而中断处理程序的代码在**借用的内核线程栈**中运行，运行硬中断时**屏蔽了所有中断和抢占**，不在任何可调度线程的上下文里，sleep 结束后无法通过上下文恢复现场，内核崩溃
底层实现是在内核太使用 spinlock 自旋锁执行程序
Linux 中的软中断包括网络收发、定时、调度、RCU 锁等各种类型，可以通过查看 `/proc/softirqs` 来观察软中断的累计中断次数情况，如果要实时查看中断次数的变化率，可以使用 `watch -d cat /proc/softirqs` 命令。

每一个 CPU 都有各自的软中断内核线程，用 ps 命令查看内核线程，一般名字在中括号里面的，都认为是内核线程。
![[ksoftirqd.webp]]
现代系统每个 CPU 都能接收中断，由 APIC（高级可编程中断控制器） 决定投递目标：
```
中断源
├── 本 CPU 本地中断（LAPIC）：定时器、本地设备 → 投递给本地 CPU
├── I/O APIC：外部设备（网卡等）→ 可编程路由到任意 CPU
└── IPI（处理器间中断）：一个 CPU 主动打断另一个 CPU
	 ├── 用于 TLB 刷新（改页表后通知所有核）
	 ├── 用于调度（让别的核重新选任务）
	 └── 用于函数调用（call_function）
```
**上半部"借用"线程栈**，中断处理程序不是线程，它是在接收中断的那个 CPU 上，直接打断当前正在跑的线程，借用它的内核栈执行：
```md
CPU 0 正在跑用户线程 X（用户态）
	  │
	  ▼  网卡中断到达 CPU0
	  │
	  ▼  CPU 硬件压栈，切换到内核态
	  │
	  ▼  执行中断上半部（借用线程 X 的内核栈）
	  │
	  ▼  登记下半部，IRET 返回
	  │
	  ▼  线程 X 继续运行（完全无感知）
```
"跨线程"的本质： 中断处理程序抢占了当前线程，而不是"在另一个线程里运行"。被中断的线程是谁完全随机——取决于中断那一刻哪个线程在跑。
**下半部：真正的"跨线程跨 CPU"桥梁**

| 下半部类型         | 运行上下文                   | 能否 sleep | 能否跨 CPU         |
| :------------ | :---------------------- | :------- | :-------------- |
| **softirq**   | 中断上下文（或 ksoftirqd 内核线程） | 否        | 本 CPU 上执行       |
| **tasklet**   | 中断上下文                   | 否        | 只在本 CPU（谁调度谁执行） |
| **workqueue** | 进程上下文（kworker 内核线程）     | 能        | 可迁移到其他 CPU      |
```
中断上半部（CPU0）
  │
  ▼  把工作丢进 workqueue
  │
  ▼  唤醒 kworker 内核线程（一个真正的、可被调度的线程）
  │
  ▼  kworker 可能被调度到 CPU2 上执行！
  │
  ▼  在那里完成真正的工作（读数据、唤醒用户进程等）
现代内核支持 request_threaded_irq，把中断处理整个变成一个内核线程：

传统模式：                          中断线程化模式：
设备中断                            设备中断
  │                                    │
  ▼                                    ▼
CPU 硬件打断（借用线程栈）            唤醒内核线程 irq/24-driver
  │                                    │
  ▼                                    ▼
上半部：快，不能 sleep              处理线程：一个真正可调度的线程
  │                                    │  可以 sleep、可以被抢占、
  ▼                                    ▼  可以跨 CPU 迁移
下半部（workqueue 等）                在线程里完成全部工作

代价：多一次线程调度延迟
收益：处理逻辑可以复杂化，不必拼性能
```
整个中断处理逻辑
```

用户线程 X 运行在 CPU0
        │
        ▼  中断发生（异步）
        │
        ▼  ┌── 硬件层：APIC 决定投递到 CPU0 ──┐
        │  │  IRQ affinity 可手动控制         │
        │  └────────────────────────────────┘
        ▼
        ▼  ┌── 上半部：借用线程X的内核栈 ──────┐
        │  │  不能 sleep、极快返回            │
        │  │  "跨线程"= 抢占线程X，不是新线程  │
        │  └────────────────────────────────┘
        ▼
        ▼  ┌── 下半部（三种策略）────────────┐
        │  │  softirq/tasklet：本 CPU，上下文│
        │  │  workqueue：kworker 线程        │
        │  │   → 可 sleep、可迁移到 CPU2     │
        │  │   → 这才是真正的"跨线程跨CPU"    │
        │  └────────────────────────────────┘
        ▼
IRET 返回，线程 X 继续
```

## 内核
计算机是由各种外部硬件设备组成的，比如内存、cpu、硬盘等，如果每个应用都要和这些硬件设备对接通信协议，**让内核作为应用连接硬件设备的桥梁**，应用程序只需关心与内核交互，不用关心硬件的细节。内核，就是硬件的一种低级抽象
内核一般会提供 4 个基本能力：
- 决定哪个进程、线程使用 CPU，也就是进程调度的能力；
- 内存的分配和回收，也就是内存管理的能力；
- 为进程与硬件设备之间提供通信能力，也就是硬件通信能力；
- 如果应用程序要运行更高权限运行的服务，那么就需要有系统调用，它是用户程序与操作系统之间的接口。

# 内存管理篇
## 虚拟内存
操作系统是管理虚拟地址与物理地址的映射关系，主要有**内存分段和内存分页**方式
### 分段机制
分段机制下的虚拟地址由两部分组成，**段选择因子**和**段内偏移量**
![[a9ed979e2ed8414f9828767592aadc21.webp]]
- **段选择因子**保存在段寄存器里面。段选择子里面最重要的是**段号**，用作段表的索引。**段表**里面保存的是这个**段的基地址、段的界限和特权等级**等。
- 虚拟地址中的**段内偏移量**应该位于 0 和段界限之间，如果段内偏移量是合法的，就将段基地址加上段内偏移量得到物理内存地址。
![[c5e2ab63e6ee4c8db575f3c7c9c85962.webp]]
又是 TLV 结构的布局，记录起始位置，长度和偏移量
存在的问题:
- 内存碎片，每个应用程序占用长度动态变化，且长度不一，不同内存块之间必然会有"空隙"，这就需要内存交换技术解决，安装系统时的交换分区就用来做这个
- 内存交换效率低，内存和硬盘上的速度差距导致大程序数据交换到硬盘中耗时长
### 内存分页机制
分页把虚拟地址空间和物理内存都切成固定大小的**页**（默认 4KB），通过**页表**记录虚拟页 → 物理页的映射，由 **MMU（内存管理单元，硬件）** 完成翻译。

**分页与分段的本质区别：**

|       | 分段        | 分页               |
| ----- | --------- | ---------------- |
| 划分单位  | 逻辑段（大小不一） | 固定页（4KB）         |
| 碎片问题  | 外部碎片严重    | 无外部碎片（内部碎片 ≤1 页） |
| 交换/回收 | 整段交换，低效   | 按页交换，高效          |
| 保护粒度  | 段级        | 页级（R/W/X/U-S）    |

> [!note] 与 mmap 的关系
> `mmap` 返回虚拟地址时物理页并不存在，第一次访问触发缺页才填充——所以 mmap 文件是**懒加载**的

换入换出的单位是 4kb 固定大小，且排列紧密，不再需要一次性都把程序加载到物理内存中。在进行虚拟内存和物理内存的页之间的映射之后，并不真的把页加载到物理内存里，而是**只有在程序运行中，需要用到对应虚拟内存页里面的指令和数据时，再加载到物理内存里面去**，形成了虚拟地址+页表+物理地址+硬盘四级结构
![[388a29f45fe947e5a49240e4eff13538-20230309234651917.webp]]
分页方式的虚拟地址和物理地址映射关系相对于[[#分段机制]]省去了基地址和长度，因为这两者都是固定的，只需要也好和页内偏移量即可定位
![[7884f4d8db4949f7a5bb4bbd0f452609.webp]]
简单分页的缺陷:
在 32 位的环境下，虚拟地址空间共有 4GB，假设一个页的大小是 4KB（2^12），需要有 `4MB` 的内存来存储页表。而虚拟内存每个进程一个，所以 100 个进程需要 400MB 存储页表，这不现实
### 多级页表机制
![[19296e249b2240c29f9c52be70f611d5.webp]]

每个进程都有 4GB 的虚拟地址空间，由于*空间局部性原理*，而对于大多数程序来说用到的空间远未达到 4GB，因为会存在部分对应的页表项都是空的，根本没有分配。所以多级页表对于没有用到的内存**不分配/创建次级页表**，这部分空间只是在逻辑上存在，只在用到时才会创建。
对于已分配的页表项，如果存在最近一定时间未访问的页表，在物理内存紧张的情况下，操作系统会将页面换出到硬盘

> [!question] 为什么不分级的页表就做不到这样节约内存？
> 从页表的性质来看，保存在内存中的页表承担的职责是将虚拟地址翻译成物理地址。假如虚拟地址在页表中找不到对应的页表项计算机系统就不能工作。所以**页表一定要覆盖全部虚拟地址空间**，不分级的页表一定会造成大量空间浪费
**x86-64 四级页表翻译：**
```
虚拟地址 48 位划分：
┌─────┬─────┬─────┬─────┬────────┐
│ PML4│ PDPT│  PD │  PT │ 偏移    │
│  9b │  9b │  9b │ 9b  │ 12b    │
└─────┴─────┴─────┴─────┴────────┘
- 全局页目录项 PGD（Page Global Directory）；
- 上层页目录项 PUD（Page Upper Directory）；
- 中间页目录项 PMD（Page Middle Directory）；
- 页表项 PTE（Page Table Entry）；

每级 512 项；页大小 4KB
也支持 2MB / 1GB 大页（少遍历级数，TLB 命中率更高）
```
![[四级分页.webp]]

**TLB（Translation Lookaside Buffer）：** 页表翻译结果在 CPU 中的缓存，用于解决多级页表带来的跳转开销，因翻译问题也可以称为**页表缓存、转址旁路缓存、快表**
- 命中：1 周期拿到物理地址
- 未命中：遍历 4 级页表（数百周期）
- **为什么上下文切换贵：** 切换进程 → 换页表 → TLB 失效 → 新进程首次访问全部 miss
**按需分页（Demand Paging）与缺页中断：**
```
进程访问某虚拟地址
  ▼
MMU 查页表：存在位 = 0（虚拟页在，物理页未分配）
  ▼
缺页中断（page fault）→ 内核处理：
  ├─ 匿名页：分配物理页并清零
  ├─ 文件映射页：从磁盘读内容到物理页（懒加载！）
  ├─ 写时复制（COW）：fork 后父子共享只读页，谁先写谁复制
  └─ 换页（swap）：物理内存不足时把页写回磁盘腾空间
  ▼
建立映射，返回用户态重新执行该指令
```

### 段页式内存管理
![[f19ebd6f70f84083b0d87cc5e9dea8e3.webp]]
- 先将程序划分为多个有逻辑意义的段，也就是前面提到的分段机制；
- 接着再把每个段划分为多个页，也就是对分段划分出来的连续空间，再划分固定大小的页；
很自然，地址结构就由**段号、段内页号和页内位移**三部分组成。
段页式地址变换中要得到物理地址须经过三次内存访问：
- 第一次访问段表，得到页表起始地址；
- 第二次访问页表，得到物理页号；
- 第三次将物理页号与页内位移组合，得到物理地址。

## 内存屏障：thread_fence 与 signal_fence
**`std::atomic_thread_fence`（跨线程，可能发射 CPU 指令）：** 独立于原子操作的围栏，用于跨线程同步。可与 relaxed 原子操作配对：
```cpp
// 线程 1
data = 42;                                              // 普通写
std::atomic_thread_fence(std::memory_order_release);    // 独立 release 围栏
ready.store(true, std::memory_order_relaxed);           // relaxed 写标志
// 线程 2
while (!ready.load(std::memory_order_relaxed)) {}       // relaxed 读标志
std::atomic_thread_fence(std::memory_order_acquire);    // 独立 acquire 围栏
use(data);   // 保证读到 42
```
- 围栏与原子操作**分离**，这是"操作附着 acquire/release"的等价写法
- x86 上 `seq_cst` 围栏 → `mfence`；`acquire/release` 围栏 → 通常无额外指令（x86 TSO 已保证）

**`std::atomic_signal_fence`（同线程被信号打断，纯编译器屏障）：**
- **只阻止编译器重排，不发射任何 CPU 指令**（GCC/Clang 上等价于 `asm volatile("" ::: "memory")`）
- **为什么不需要 CPU 指令？** 信号处理函数与主程序运行在**同一线程/同一 CPU**，无跨核 cache 一致性问题，只需阻止编译器把共享变量写入重排

**对比：**
| | `atomic_signal_fence` | `atomic_thread_fence` |
|---|---|---|
| 作用对象 | 同线程 + 信号处理函数 | 不同线程 |
| 发射 CPU 指令 | 否（纯编译器屏障） | 可能（seq_cst → `mfence`） |
| 编译器屏障 | 是 | 是 |

**一句话：** thread_fence 管"CPU 间的可见性"，signal_fence 只管"编译器别乱排"

## DMA（直接内存访问）
**问题：** 无 DMA 时（PIO 方式），CPU 收到中断后要逐字节从设备寄存器搬到内存，1500 字节的包占满 CPU。

**DMA = 设备通过 DMA 引擎/控制器，绕过 CPU 直接在设备与内存之间搬数据：**
```
网卡收包（现代模式）：
1. 驱动启动时分配 DMA 缓冲区，填好描述符环（RX Ring）
2. 网卡收到包 → 内部 DMA 引擎直接把包写入内存（CPU 不参与！）
3. 网卡发中断给 CPU："DMA 完成"
4. CPU 处理中断，直接读内存里的包
```
**关键细节：**
- **总线主控（Bus Master）：** DMA 引擎能主动读写内存，无需 CPU 代为访问
- **DMA 缓冲区：** 必须物理连续或经 IOMMU/散射表映射，驱动用 `dma_alloc_coherent` 分配
- **Cache 一致性：** 设备写内存后 CPU cache 可能还是旧值 → 需要 coherent DMA 或手动刷 cache
- **与中断的关系：** DMA 完成 → 设备发中断通知 CPU
- **与 mmap 的关系：** "mmap 零拷贝"本质就是让应用直接访问 DMA 写入的物理页

**一句话：** DMA 让"设备→内存"的数据搬运不占用 CPU，CPU 只在搬运完成时被中断唤醒

## 进程内存模型由谁定义
**结论：既不是 x86 定义的，也不是 C++ 定义的——是"OS ABI + 工具链（编译器/链接器）+ 可执行文件格式 + OS 加载器"共同约定的平台惯例。**

| 层 | 管什么 | 不管什么 |
|---|---|---|
| C++ 标准 | 存储期（static/thread/automatic/dynamic）、生命周期 | 不管地址、不管布局 |
| x86 ISA | MMU、特权级、分页机制、指令集 | 不管进程布局 |
| ABI（Linux x86-64 用 System V psABI） | 栈增长方向、调用约定 | 不管 ELF 段 |
| ELF 格式 | 定义 `.text`/`.data`/`.bss`/`.rodata` 段 | 不管具体地址 |
| OS 加载器 | 读 ELF → 映射段 → 设栈/堆 → ASLR 随机化 | — |

**C++ 存储期 ↔ ELF 段 ↔ 地址映射：**
| C++ 存储期 | ELF 段 | 谁初始化 |
|---|---|---|
| static（已初始化） | `.data` | 加载器从文件拷贝 |
| static（零初始化） | `.bss` | 加载器清零 |
| static（thread_local） | `.tdata`/`.tbss` | 线程创建时 |
| automatic | 栈（高地址向下增长） | 编译器/栈指针 |
| dynamic | 堆（中地址向上增长） | brk/mmap |

**关键：** C++ 只保证生命周期语义（局部变量出作用域销毁、static 程序结束才销毁），至于落在哪个地址、栈往哪长，是平台的事。同一份代码在 Linux/Windows/macOS 布局完全不同，C++ 标准对此一无所知

## 无 OS 的单片机如何执行 C++ 程序
**烧录是什么：** 把编译好的固件二进制从 PC 写进 MCU 内部 Flash（非易失）。通过下载器（ST-Link/J-Link，SWD/JTAG）或 bootloader（UART/USB）。

**为什么必须烧录：** 单片机 RAM 极小且易失，无文件系统、无动态加载器，程序必须预先固化在 Flash，上电直接取指执行（XIP，就地执行）。

**上电执行流程：**
```
上电复位 → 从固定地址读向量表（STM32: 0x08000000）
  ├─ 第 0 项 = 初始栈指针 SP
  ├─ 第 1 项 = Reset_Handler 入口
→ 跳转 Reset_Handler（启动代码）
  ├─ 把 .data 从 Flash 拷到 RAM（RAM 才可写）
  ├─ 把 .bss 清零
  ├─ 调 __libc_init_array（执行全局对象构造函数）
→ main()（死循环，永不返回）
无 MMU → CPU 访问的就是物理地址，链接脚本（.ld）固定各段地址
```

**MCU 内存映射（STM32 为例）：**
```
0x08000000  Flash（.text/.rodata，非易失）
0x20000000  SRAM（.data 运行副本/.bss/堆/栈，易失）
0x40000000  外设寄存器（GPIO、UART、定时器）
```

**C++ 依赖如何解决（无 OS 无 libc）：**
| C++ 依赖 | 单片机方案 |
|---|---|
| `operator new`/`delete` | 用户实现，内部包 `malloc`/`free`（newlib） |
| `memcpy`/`printf` 等 | 静态链接 newlib/nanolibc（裸机 C 库） |
| `printf` 输出到哪 | 重定向 `_write` 到 UART 寄存器 |
| 全局对象构造函数 | 启动代码 `__libc_init_array()` 在 `main()` 前执行 |
| 异常/RTTI | 编译期禁用（`-fno-exceptions -fno-rtti`）省 Flash |
| `iostream` | 尽量不用（体积大），改用 `printf` |
| 动态链接 | 不存在，全部静态链接，链接器编译期解决所有符号 |

**无 OS vs 有 OS：**
| | PC（有 OS） | 单片机（无 OS） |
|---|---|---|
| 地址 | 虚拟地址（MMU 翻译） | 物理地址（无 MMU） |
| 程序来源 | 运行时动态加载 | 烧录固化在 Flash |
| 标准库 | OS 提供/动态链接 | 静态链接 newlib + 重定向 |
| 多任务 | OS 调度 | 裸机主循环/中断 |

**"依赖问题"的本质：** PC 上 libc 和运行时由 OS/动态链接器在运行时提供；单片机没有，所以所有依赖必须在编译期静态链接进固件，标准库函数重定向到具体硬件（printf→UART、malloc→预分配堆区）
## C++ 中如何体现中断处理程序
用户态 C++ 无法直接写真正的 ISR（那是内核/驱动层的事），但有三个层面：
1. 嵌入式 / 裸机 C++：真正的 ISR
```cpp
extern "C" void TIMER1_IRQHandler() __attribute__((interrupt));
extern "C" void TIMER1_IRQHandler() { flag = true; }
```
- `extern "C"` 避免名字修饰，链接到中断向量表
- `__attribute__((interrupt))` 告诉编译器这是 ISR：进出场保存全部寄存器、用 IRET 返回
2. Linux 内核模块：`request_irq(irq, handler, ...)`，handler 上半部极快返回 `IRQ_HANDLED`，可用 `IRQ_WAKE_THREAD` 唤醒中断线程
3. 用户态 C++ 对应物：**信号（Signal）= 软件中断**
```cpp
#include <csignal>
void handler(int sig) {
    std::atomic_signal_fence(std::memory_order_seq_cst);  // 编译器屏障
    // 只能调用 async-signal-safe 函数
}
std::signal(SIGINT, handler);  // 多线程用 sigaction + pthread_sigmask
```
**与硬中断的对应：**

| 概念 | 硬件中断 | 信号（软中断） |
| --- | --- | --- |
| 触发 | 设备 / 定时器 | 内核 / 其他进程 |
| 处理函数 | ISR | signal handler |
| 打断对象 | 正在跑的线程 | 接收信号的线程 |
| 处理时能做的事 | 极少 | 受限（只能 async-signal-safe） |

**为什么 `atomic_signal_fence` 是编译器屏障而非 CPU 屏障？**
信号处理函数与主程序运行在**同一线程 / 同一 CPU**，无跨核可见性问题，只需阻止编译器重排

### 小数的二进制表示
浮点数的表示借鉴了科学计数法，比如在十进制中 311.56 可以表示成 3.1156∗10^2 。类似地，浮点型数据的二进制存储结构也可以被划分成：**符号位 s + 指数位 e + 尾数位（有效数字位）m**。按照国际标准 IEEE 754，任意一个二进制浮点数可以表示成： 𝑉=(−1)^𝑠×𝑀×2^𝐸   其中：

- (−1)^𝑠 表示符号位， 𝑠=0 表示正数， 𝑠=1 表示负数
- 𝑀 表示有效数字， 1≤𝑀<2
- 2^𝐸 表示指数位

> 指数部分决定了数的大小范围，有效数字部分决定了数的精度。

在位运算中，n 进制数\*进制基数（即 n） 表示将所有数字向右移动一位，如 1010 二进制数\*得 10100

|十进制|二进制|二进制科学计数法|S|E|M|
|---|---|---|---|---|---|
|3.0|11.0|1.1 x 2^1|0|1|1.1|
|-5.0|-101.0|-1.01 x 2^2|1|2|1.01|

其中 IEEE 754 的规定为：

- 因 M 的取值一定是 1<=M<2，因此规定 M 在存储时舍弃第一个 1，只存储小数点后的数字，这样可以节省存储空间（以 float 32 为例，可以保存 23 位小数信息）
- 指数 E 是一个无符号整数，因此它的取值范围为 0255，但指数可以是负的，所以规定在存入 E 时在它原本的值加上 127（使用时减去中间数 127），这样 E 的取值范围为-127128
- E 不全为 0，不全为 1：正常的计算规则，E 的真实值就是 E 的字面值减去 127（中间值），M 加回 1
- E 全为 0：指数 E 等于 1-127 为真实值，M 不加回 1（此时 M 为 0. xxxxxx），这样是为了表示 0 和一些很小的数
- E 全为 1：M 全为 0 表示正负无穷大（取决于 S 符号位）；M 不全为 0 时表示不是一个数（NaN）

## 屏幕密度和像素概念区分
基本概念铺垫
### 像素
像素 (pixel) 为图像的基本单位，是一个抽象的采样，在很多情况下，它们采用点或者方块显示。每个像素可有各自的颜色值，可以采用 RGB 表示。单位面积内的像素越多代表分辨率越高，所显示的图像就会接近于真实物体。
### 屏幕尺寸
屏幕尺寸 (Screen size) 指屏幕的物理尺寸，一般用屏幕对角线长度表示，单位英寸 (1 英寸 = 2.54 厘米)。如小米 4 是 5 英寸。
### 宽高比率
宽高比率 (Aspect Ratio) 指的是实际屏幕的物理尺寸宽高比，如 16：9，4：3 等等。
### 屏幕密度
屏幕密度 (Screen density) 指的是屏幕里像素值浓度，分辨率/屏幕尺寸可以反映出手机密度。为了方便，Android 将屏幕密度分为 6 种，low, medium, high, extra-high, extra-extra-high, and extra-extra-extra-high.
### 分辨率
分辨率 (Resolution) 和电脑的分辨率概念一样，指手机屏幕纵、横方向像素个数。如 `1920*1080`，它表示纵向一列有 1920 个像素，横向一行有 1080 个像素。
### DPI
DPI (dot per inch)，每英寸像素数，可以反映屏幕的清晰度，可用于缩放 UI。
例如，如果一个 320×240 分辨率的屏幕之物理尺寸为 2 inch×1.5 inch，
那么 DPI = 320/2 = 240/1.5 =160。一般的，计算的方法为对角线像素值/对角线长度 (屏幕尺寸)。如计算 WVGA (800*480) 分辨率，3.7 英寸的密度 DPI 为 sqrt (800^2 + 480^2)÷3.7 = 252。密度（字面意思）
### dip (dp)
DIP = Density-independent pixel，与密度无关像素，亦称为设备独立像素 (Device independent pixel)，是一个虚拟的像素的单元，其等价于 160 dpi 屏幕的一个实际物理像素。这种 160 dpi 的屏幕的屏幕密度是系统假设一个基准密度 (也就是 medium 级别的密度)，在运行时，系统会将 DP 值根据不同 DPI 的屏幕转化具体的物理的像素。公式为 px = dp * (dpi / 160)。如一个 240 dpi 的屏幕，1 dp 在其上实际等于 1.5 个物理像素 px。在布局时应该使用 dp 作为单位以方便适配
### Android 对手机屏幕尺寸和 dpi 分级的情况
