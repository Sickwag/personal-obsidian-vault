# 第一章：引言
## 设计模式综述
设计模式是用来解决软件开发中常见的，或者说**不断重复发生的**问题的通用解决方法。
每一个设计模式都集中于**一个特定的面向对象设计问题或设计要点**，描述：
- 什么时候使用它
- 在另一些设计约束条件下是否还能使用
- 使用的效果和如何取舍
## 设计模式编目
好的，我将为您整理设计模式的全面分类和详细说明。

### 设计模式三大类别

| 类别 | 英文名 | 核心目的 | 适用场景 | 包含模式数量 |
|:---|:---|:---|:---|:---|
| **创建型模式** | Creational Patterns | **对象创建机制**，增加系统在对象创建时的灵活性和复用性 | 当系统需要独立于其对象的创建、组合和表示时 | 5 种 |
| **结构型模式** | Structural Patterns | **类和对象的组合**，形成更大的结构，保持灵活性和效率 | 当需要关注类与对象之间的组合关系时 | 7 种 |
| **行为型模式** | Behavioral Patterns | **对象间的职责分配和通信**，增强对象协作的灵活性 | 当需要关注对象如何交互以及职责如何分配时 | 11 种 |


### 创建型模式 (5 种)

| 模式名称 | 英文名 | 使用场景 | 使用注意事项 |
|:---|:---|:---|:---|
| **工厂方法** | Factory Method | 需要创建对象但不希望指定具体类时；子类决定创建哪种对象 | 可能导致类的数量增加；需要平衡灵活性和复杂性 |
| **抽象工厂** | Abstract Factory | 需要创建相关或依赖对象的家族，而不需要指定具体类 | 产品族扩展困难；支持新种类的产品需要修改接口 |
| **建造者** | Builder | 创建复杂对象，构造过程需要多个步骤；需要不同的对象表示 | 增加了代码复杂性；适用于创建过程复杂的对象 |
| **原型** | Prototype | 需要创建的对象成本较高；需要动态配置应用使用的类 | 深拷贝和浅拷贝问题；需要正确实现 clone 方法 |
| **单例** | Singleton | 确保一个类只有一个实例，并提供全局访问点 | 多线程环境需要同步；可能引入全局状态，测试困难 |

### 结构型模式 (7 种)

| 模式名称    | 英文名       | 使用场景                          | 使用注意事项                   |
| :------ | :-------- | :---------------------------- | :----------------------- |
| **适配器** | Adapter   | 需要使用现有类，但其接口与系统不兼容时           | 不要过度使用；可能增加系统复杂性         |
| **桥接**  | Bridge    | 需要将抽象部分与实现部分分离，使它们可以独立变化      | 正确识别抽象和实现维度；增加设计复杂度      |
| **组合**  | Composite | 需要表示部分-整体层次结构；希望统一处理单个对象和组合对象 | 设计可能过于一般化；难以限制组合中的组件类型   |
| **装饰器** | Decorator | 需要动态地给对象添加职责，而不想通过子类扩展        | 可能产生许多小对象；装饰顺序影响行为       |
| **外观**  | Facade    | 需要为复杂子系统提供简单接口；降低系统间依赖关系      | 可能成为"上帝对象"；限制了子系统的灵活性    |
| **享元**  | Flyweight | 需要大量细粒度对象共享；对象的大部分状态可以外部化     | 需要仔细区分享享元和外部状态；增加系统复杂性   |
| **代理**  | Proxy     | 需要控制对对象的访问；为对象提供替代品或占位符       | 可能引入性能开销；需要确保代理和真实对象接口一致 |
### 行为型模式 (11 种)

| 模式名称 | 英文名 | 使用场景 | 使用注意事项 |
|:---|:---|:---|:---|
| **责任链** | Chain of Responsibility | 多个对象可以处理请求，但具体处理器在运行时确定 | 请求可能无法被处理；需要避免循环引用 |
| **命令** | Command | 需要将请求封装为对象；支持撤销、重做、事务等功能 | 可能产生大量具体命令类；增加系统复杂性 |
| **解释器** | Interpreter | 需要定义语言的文法，并解释语言中的句子 | 效率可能较低；适用于简单的文法规则 |
| **迭代器** | Iterator | 需要提供统一的方式访问聚合对象的元素，而不暴露内部表示 | 在简单集合上使用可能过于复杂；需要考虑并发修改 |
| **中介者** | Mediator | 对象间存在复杂的引用关系，导致依赖关系混乱时 | 中介者可能变得过于复杂；可能成为系统瓶颈 |
| **备忘录** | Memento | 需要保存对象状态，以便后续恢复；但不希望暴露对象细节 | 可能消耗大量内存；需要考虑状态保存的频率 |
| **观察者** | Observer | 一个对象状态改变需要通知其他对象，且不知道具体有多少对象需要通知 | 可能导致意外的更新链；需要注意观察者的更新顺序 |
| **状态** | State | 对象的行为取决于它的状态，并且在运行时可能改变状态 | 状态转换逻辑可能复杂；可能产生很多状态类 |
| **策略** | Strategy | 需要定义一系列算法，并使它们可以相互替换 | 客户端必须了解不同策略的区别；可能增加对象数量 |
| **模板方法** | Template Method | 需要定义算法的骨架，允许子类重定义某些步骤 | 可能违反里氏替换原则；模板方法越多越难维护 |
| **访问者** | Visitor | 需要对一个对象结构中的元素执行不同的操作，而不改变元素类 | 增加新的元素类困难；可能破坏封装性 |


### 设计模式选择指南
#### 设计模式决策树
![[../../Files & LongText/Attachments/Pasted image 20250912212648.png|设计模式之间的关系]]

| 设计问题       | 推荐模式      | 替代方案   |
| :--------- | :-------- | :----- |
| **需要创建对象** | 工厂方法、抽象工厂 | 建造者、原型 |
| **需要组合对象** | 组合、装饰器    | 适配器、桥接 |
| **需要控制访问** | 代理、装饰器    | 适配器、外观 |
| **需要处理算法** | 策略、模板方法   | 状态、命令  |
| **需要管理状态** | 状态、备忘录    | 策略、观察者 |
| **需要解耦对象** | 观察者、中介者   | 命令、责任链 |
| **需要遍历集合** | 迭代器、访问者   | 组合、责任链 |

#### 重要原则
1. **优先使用组合而非继承**
2. **针对接口编程，而不是实现**
3. **开闭原则：对扩展开放，对修改关闭**
4. **单一职责原则：一个类只负责一个功能领域**
5. **里氏替换原则：子类必须能够替换基类**
#### 使用建议
1. **不要过度设计**：只在真正需要时使用设计模式
2. **理解问题本质**：先理解问题，再选择模式
3. **保持简单**：简单的解决方案往往更好
4. **考虑维护成本**：设计模式可能增加代码复杂性
5. **团队共识**：确保团队成员都理解所使用的模式
