## select 机制
参考
- https://zhuanlan.zhihu.com/p/667866881
- https://geek-blogs.com/blog/linux-select/
### 概览
select 机制是一种 I/O 多路复用技术，它可以同时监视多个文件描述符，没有 FD 就绪时，进程会被阻塞，当某个文件描述符就绪（一般是读写就绪）时，`select` 返回并通知进程哪些 FD 可以进行 I/O，避免了对单个 FD 的阻塞等待。

### 为什么需要 select？
传统的阻塞式 I/O 模型中，若进程需要处理多个 FD（如同时监听多个客户端连接的服务器），只能通过以下方式实现并发：
- **多进程/多线程**：为每个 FD 创建独立的进程/线程，但资源开销大，扩展性差。
- **忙轮询**：循环检查每个 FD 是否就绪，浪费 CPU 资源。
`select` 通过**单进程阻塞等待多个 FD**，解决了上述问题：它将多个 FD 的监控任务交给内核，由内核统一判断就绪状态，仅在必要时唤醒进程
### 设计细节
#### select 流程
![[Pasted image 20260622173723.jpg]]

1. select 设计三种位图，分别为读，写，异常位图，用户程序预先将 socket 文件描述符**注册**至读，写，异常位图
2. 通过 select 系统调用轮询位图。
```
for each fd in readfds:
  检查 fd 的接收缓冲区是否有数据？
	  → 有：保持 bit=1（就绪）
	  → 无：将当前进程注册到 fd 的等待队列（通过 poll_wake 回调）
			bit=0（未就绪）

for each fd in writefds:
  检查 fd 的发送缓冲区是否有空间？
	  → 有：保持 bit=1
	  → 无：注册等待队列，bit=0

for each fd in exceptfds:
  检查是否有带外数据？
	  → ...
```
3. 如果全都没就绪 → 阻塞
	- 进程状态 → TASK_INTERRUPTIBLE（可中断睡眠）
	- 进程被移出 CPU 运行队列
	- 设置定时器（根据 timeout 参数）
	- 进程进入睡眠，等待被唤醒
4. 唤醒进程: 数据到达 → 中断 → 内核协议栈唤醒进程处理 **或者超时时间到达或者进程被信号中断**
	- 遍历 socket 等待队列中的进程
	- 调用 poll_wake 回调
	- 把进程状态改回 TASK_RUNNING
	- 加入 CPU 运行队列
	- 超时会返回 0，使用信号中断进程会返回-1 并设置 errno
5. 再次轮询
	- 进程被调度到 CPU 后：
	- 再次遍历所有位图中的所有 fd
	- 这次 sock_fd 的 bit=1（有数据了）
	- 轮询完毕
6. 将结果位图 + 剩余超时时间 copy_to_user 到用户空间
```cpp
copy_to_user(user_readfds, kernel_readfds, size);
copy_to_user(user_timeout, &remaining_time, sizeof(timeval));
```
7. 用户处理
```cpp
// select 返回后，readfds 已经被内核修改了
if (FD_ISSET(sock_fd, &readfds)) {
  read(sock_fd, buf, size);  // sock_fd 就绪了
}
if (FD_ISSET(listen_fd, &readfds)) {
  accept(listen_fd, ...);    // 有新连接
}
```
注意：用户原始的位图被内核覆盖了。所以每次调用 select 前必须重新 FD_ZERO + FD_SET，不能复用。

> [!note] 为什么要有两次遍历？
> 轮询不是"唤醒后才发生"——而是内核两次遍历: 
>   - 第一次遍历（select 调用时）：遍历位图中所有 fd → **检查所有 fd 的缓冲区有没有数据** -> 没有 fd 就绪 → 进程注册到各 fd 的等待队列 → 进程睡眠
>   - 唤醒后（数据到达触发的回调只做了一件事：把进程设为 TASK_RUNNING）：进程被**内核调度** → select 的内核代码从睡眠点继续执行 → 第二次遍历
>   - 也就是说 select 函数内部**本身就设置了 2 次遍历的逻辑**，第一次遍历阻塞后，从**内核了解到第一个 fd 就绪了开始**，到唤醒进程继续执行 select 函数期间也有可能还会有其他 fd 就绪，所以再次遍历，检查位图中的缓冲区是否有数据
>   - 两次遍历返回的位图就是完整的

#### 数据结构和 API
![[Pasted image 20260622162039.jpg]]
```cpp
#define __FD_SETSIZE 1024
#define __NFDBITS (8 * (int) sizeof (long int))
typedef struct {
	long int fds_bits[__FD_SETSIZE / __NFDBITS];
} fd_set;
```
- 分为三个类图的意义是**按照用途分类**，只要是关心读操作（想要从 socket 中获取信息）的 fd 都可以绑定在**统一读位图 readfd 中**，
```cpp
// 位图操作函数
void FD_CLR(int fd, fd_set *set); //设置fd对应位图位置为0。
int FD_ISSET(int fd, fd_set *set); //判断fd对应位图位置是否为1。
void FD_SET(int fd, fd_set *set); //设置fd对应位图位置为1。
void FD_ZERO(fd_set *set);//整个位图清零。

int select(int nfds,
           fd_set *readfds,    // 读位图
           fd_set *writefds,   // 写位图
           fd_set *exceptfds,  // 异常位图
           struct timeval *timeout);
           
void FD_SET(int fd, fd_set *set) {
    int word = fd / (8 * sizeof(long));   // 确定在哪个 unsigned long 里
    int bit  = fd % (8 * sizeof(long));   // 确定在该 long 的哪个 bit
    set->fds_bits[word] |= (1UL << bit);  // 置位
}
```
- nfds：指定监控的文件描述符数量。它应该是所有监控的文件描述符集合中最大值加 1，因为文件描述符是从 0 开始计数的。
- readfds：指向一个文件描述符集合，用于监控是否有文件可读。可以使用宏函数 FD_SET() 将描述符添加到集合。
- writefds：指向一个文件描述符集合，用于监控是否有文件可写。
- exceptfds：指向一个文件描述符集合，用于监控异常状态。
- timeout：指定 select 等待的时间，可以是：
	- NULL：select 将无限期等待，直到有文件描述符准备好。
	- 0 秒的时间：表示非阻塞模式，select 立即返回。
	- 自定义时间：例如等待 5 秒，可以通过 struct timeval 指定。
- 返回值：成功返回检测到的文件描述符数量。失败返回-1，设置 errno。超时返回 0

## poll 机制
### 概览
![[Pasted image 20260622204403.jpg]]
poll 是 System V 引入的 I/O 多路复用机制，和 select 核心思路一致：让内核替用户进程监视多个 FD。但 poll 解决了 select 的两个痛点：
- **取消 1024 FD 上限** — poll 使用数组结构而非位图
- **不需要重建监控集合** — poll 用 `events`（用户设置）和 `revents`（内核返回）分离，不会像 select 那样覆盖原始数据
select 实践中三个痛点：
- `FD_SETSIZE=1024` 写死在 glibc
- 每次调用要重建位图（内核覆盖了原始数据）
- `copy_from_user` 拷贝三张位图，数据量与 FD 数量成正比
- `nfds` 参数是最大值+1，FD=5、1000、2000 时内核要遍历 0~2000，中间空洞也被扫描

poll 在上述做了改进，但核心模型仍是"主动轮询+回调唤醒"，仅支持水平触发 LT。
### 数据结构
```cpp
struct pollfd {
    int   fd;         // 待监控的文件描述符
    short events;     // 用户设置关心的事件（输入）
    short revents;    // 内核返回实际发生的事件（输出）
};
// 事件标志
#define POLLIN     0x001   // 有数据可读
#define POLLPRI    0x002   // 紧急数据
#define POLLOUT    0x004   // 可写
#define POLLERR    0x008   // 错误（仅 revents）
#define POLLHUP    0x010   // 挂起（仅 revents）
#define POLLNVAL   0x020   // fd 未打开（仅 revents）
```
events/revents 分离是关键：
- `events` 是输入参数，用户设置关心什么事件，内核不会改它，可以理解为 select 中的 readfds，writefds，exceptfds 分类机制被这一个 short 类型抽象化
- `revents` 是输出参数，内核把就绪事件写在这里，用户只读此字段
- `pollfd` 数组可重复使用，不需要每次重建

对比 select 的设计：
- select：用户位图 → 内核覆盖 → 丢失原始数据 → 下次必须重建
- poll：`pollfd.events` 只读不写 → `pollfd.revents` 只写不读 → 可复用
### poll 流程与 API
```
用户调用 poll(fds, nfds, timeout) 后进入内核：
  第一次遍历 fds[0..nfds-1]：
    - 检查每个 fd 是否就绪
    - 就绪则设置 revents
    - 未就绪则把当前进程注册到 fd 等待队列（poll_wait 回调）
  全部未就绪 → 阻塞进程：
    - TASK_INTERRUPTIBLE（可中断睡眠）
    - 设置超时定时器
  唤醒条件（任一）：
    - 数据到达 → 中断 → 协议栈 → poll_wake 回调
    - 超时 → 定时器到期
    - 信号中断 → EINTR
  第二次遍历 fds[0..nfds-1]：检查已就绪的 fd，设置 revents
  copy_to_user(fds, ...) 返回
用户态：遍历 fds 数组检查 revents
  - if (fds[i].revents & POLLIN) → read
  - if (fds[i].revents & POLLOUT) → write
```
这与 select 的两次遍历一致，区别是 poll 使用 `struct pollfd` 数组而非 `fd_set` 位图。
```cpp
int poll(struct pollfd *fds, nfds_t nfds, int timeout);
```
参数含义：
- `fds`：`struct pollfd` 数组，即监控集合
- `nfds`：数组元素个数（注意是实际数量，不是最大 fd+1）
- `timeout`：超时时间，单位毫秒
  - `-1`：永远等待
  - `0`：立即返回
  - `>0`：等待毫秒数

返回值：
- `>0`：就绪的 fd 数量（同 fd 的 `POLLIN|POLLOUT` 只算 1 个）
- `=0`：超时，无 fd 就绪
- `-1`：错误，`errno` 被设置

poll 的不足与 select 相同：
- **唤醒后仍需全遍历** — 即使只有一个 fd 就绪，也要遍历所有 nfds 个 fd 才知道
- poll 和 select 本质区别是 poll 放弃了每次用户态和内核态传递消息时都使用 fd_set 大数组的方式，因为这样会导致无论有多少个 fd 是就绪的，都需要完整遍历整个长度为 1024 的 `fd_set`
- poll 采用将每一个消息封装为 pollfd 结构，每一个 pollfd 都封装了一个用户态关心的 fd，他的监控事件和监测事件经过内核判断该事件是否发生后的传出结果
- 这保证了 poll 函数参数 fds 大小不会很长，遍历只会遍历用户关心的数据，不会有无效的内容在用户态和内核态之间传输
- 但是两者都没有解决的问题有:
    - 都使用了线性数据结构存储 fds，导致内核态想要检查某个 fds 的状态必须从头遍历，复杂度为 O(n)
    - 用户态和内核态之间的一定要传输所有用户关心的 fds 信息用于遍历，而无论他是否就绪 `copy_from_user ` 拷入内核，即使 fd 没有变化，传回调用 `copy_to_user`

### 概览
Linux 独有的高性能 I/O 事件通知设施。与 select/poll 的根本区别：
- select/poll："内核，帮我看看这些 fd 有动静没？"每次都传全部 fd
- epoll："内核，帮我盯着这些 fd，有动静通知我"只传一次，回调通知

两大突破：
- **O(1) 获取就绪 fd** — 不需要遍历整个监控集合
- **增量注册/删除** — 不需要每次全量拷贝
![[Pasted image 20260622214002.jpg]]
select/poll 的核心问题是每次调用全量扫描，在 C10K 场景下不可接受：10000 连接只有 5 个活跃，却要遍历 10000 个 fd，40% CPU 消耗在 `copy_from_user` 上。Nginx 使用 epoll ET 模式处理万级连接，Redis 6.0+ 支持 epoll，Node.js 底层 libuv 在 Linux 下自动选择 epoll。
### 数据结构和 API
epoll 拆成三个函数各自负责一个阶段：
- `epoll_create` — 创建 epoll 实例（返回 epfd），是一个 epoll 专用的 fd
- `epoll_ctl` — 增/删/改监控的 fd（只传一次，不是每次）
- `epoll_wait` — 等待事件发生（只取就绪的，不扫全部的）
![[Pasted image 20260622214037.jpg]]
#### epoll_create — 创建 epoll 实例
```cpp
int epoll_create(int size);           // size > 0 即可，内核 2.6.8+ 后动态调整，用来告诉内核这个监听的数目一共有多大，参数 size 并不是限制了 epoll 所能监听的描述符最大个数，只是对内核初始分配内部数据结构的一个建议。
int epoll_create1(int flags);         // flags: EPOLL_CLOEXEC
```
返回一个文件描述符（epfd），失败返回-1，内核做的事：
- 分配 `struct eventpoll` 对象
- 初始化红黑树根（rbr）— 用于存储注册的 fd
- 初始化就绪链表头（rdllist）— 用于存放就绪的 fd，用来遍历拿到所有的 fd，不同于 poll 和 select，其中都是已经就绪的 fd
- 初始化等待队列（wq）— 用于阻塞调用 epoll_wait 的进程

无需时 `close(epfd)` 关闭。
#### epoll_ctl — 控制监控的 FD，事件管理
```cpp
int epoll_ctl(int epfd, int op, int fd, struct epoll_event *event);
```
- 参数epfd: epoll 专用的文件描述符，epoll_create()的返回值
- 参数op: 表示动作，用三个宏来表示：
	- EPOLL_CTL_ADD：注册新的 fd 到 epfd 中；
	- EPOLL_CTL_MOD：修改已经注册的fd的监听事件；
	- EPOLL_CTL_DEL：从 epfd 中删除一个 fd；
- **参数 fd:** 需要监听的文件描述符
- **参数 event:** 告诉内核要监听什么事件，struct epoll_event 结构如:
```cpp
struct epoll_event {
    uint32_t     events;    // 位掩码，用户关心的事件
    epoll_data_t data;      // 用户自定义数据
};

typedef union epoll_data {
    void    *ptr;
    int      fd;
    uint32_t u32;
    uint64_t u64;
} epoll_data_t;
```
- **events**是以下几个宏的集合：
	- EPOLLIN ：表示对应的文件描述符可以读（包括对端 SOCKET 正常关闭）；
	- EPOLLOUT：表示对应的文件描述符可以写；
	- EPOLLPRI：表示对应的文件描述符有紧急的数据可读（这里应该表示有带外数据到来）；
	- EPOLLERR：表示对应的文件描述符发生错误；
	- EPOLLHUP：表示对应的文件描述符被挂断；
	- EPOLLET ：将 EPOLL 设为边缘触发(Edge Trigger)模式，这是相对于水平触发(Level Trigger)来说的。
	- EPOLLONESHOT：只监听一次事件，当监听完这次事件之后，如果还需要继续监听这个 socket 的话，需要再次把这个 socket 加入到 EPOLL 队列里
- 返回值：0 表示成功，-1 表示失败。
`EPOLL_CTL_ADD` 时内核做三件事：
- 分配一个红黑树节点对象 `struct epitem`
- 添加等待事件到 socket 的等待队列中，回调函数是 `ep_poll_callback`
- 将 epitem 插入到 epoll 对象的红黑树里（key = fd）

`EPOLL_CTL_DEL` 时内核做：
- 红黑树中找到该 fd（O(log n)）
- 从 fd 的等待队列中卸载回调
- 从红黑树中删除节点
- 如果该 fd 在就绪链表中，一并移除
#### epoll_wait — 等待事件
```cpp
int epoll_wait(int epfd, struct epoll_event *events, int maxevents, int timeout);
```
参数：
- `events`：输出参数，内核把就绪事件拷贝到这里
- `maxevents`：events 数组的大小
- `timeout`：-1 永久阻塞，0 立即返回，>0 等待毫秒

返回值：
- `>0`：就绪事件数量
- `=0`：超时
- `-1`：错误

内核流程：
- 检查就绪链表（wq）是否为空
	- 不为空：直接把就绪链表中的事件拷贝到 events 数组，返回
	- 为空：继续
- 将当前进程加入 epoll 的等待队列 wq
- 进程进入 TASK_INTERRUPTIBLE
- 设置超时定时器，进程睡眠
- 被唤醒后（某 fd 数据到达 → 回调触发 → 加入就绪链表 → 唤醒进程）
- 将就绪链表中的事件拷贝到 events 数组
- 返回就绪数量
### 关键数据结构
```cpp
// epoll 核心结构 - fs/eventpoll.c
struct eventpoll {
    wait_queue_head_t wq;        // epoll_wait 用到的等待队列，软中断通过 wq 找到阻塞的进程
    struct list_head  rdllist;   // 就绪链表头，已就绪的 fd 列表
    struct rb_root    rbr;       // 红黑树根，管理所有注册的 fd
    struct epitem    *ovflist;   // 事件处理期间就绪的 fd 链表
};
// 红黑树节点 — 每个注册的 fd 对应一个
struct epitem {
    struct rb_node    rbn;       // 红黑树节点（key = fd）
    struct list_head  rdllink;   // 就绪链表节点
    struct epoll_filefd ffd;     // 目标 fd + file 结构
    struct eventpoll *ep;        // 所属的 eventpoll
    struct epoll_event event;    // 用户注册的事件
    wait_queue_entry_t wait;     // 挂在目标 fd 等待队列上的回调
    struct list_head  pwqlist;   // poll wait 队列链表
};
```
关系图：一个 `eventpoll`（一个 epfd 对应一个）管理一棵红黑树（所有 epitem 节点，以 fd 为 key）和一条就绪链表（仅包含就绪的 epitem 节点）。红黑树保证 O(log n) 的增删查，对于连接数动态变化、频繁增删的场景足够高效。

### epoll_ctl 注册过程详解
当用户调用 epoll_ctl(EPOLL_CTL_ADD)，内核通过 ep_insert 执行，步骤如下：
1. **分配 epitem**：`kmem_cache_alloc(epi_cache, GFP_KERNEL)`，初始化 `epi->ep = eventpoll`，填充 `epi->ffd`（含 file 和 fd）。
2. **设置 socket 等待队列**：调用链如下
   - `ep_item_poll(epi)` → `epi->ffd.file->f_op->poll(epi->ffd.file, pt)`
   - 通过 accept 创建 socket 时，`file->f_op->poll` 指向了 `sock_poll`（来自 `socket_file_ops`）
   - `sock_poll` → `sock->ops->poll` 即 `tcp_poll`
   - `tcp_poll` → `sock_poll_wait` → `poll_wait` → `p->_qproc(filp, wait_address, p)`
   - 这里的 `qproc` 在 `init_poll_funcptr` 时设置成了 `ep_ptable_queue_proc`
   - `ep_ptable_queue_proc` 创建一个 `wait_queue_t` 项，将其 callback 设为 `ep_poll_callback`，并加入 socket 的等待队列（通过 `sk_sleep` 获取）
3. **插入红黑树**：`ep_rbtree_insert(ep, epi)`。
### 回调机制：ep_poll_callback
这是 epoll 最关键的创新。数据到达时的完整链路：
- 网卡 → 中断 → 内核协议栈处理数据
- 调用 `sock_def_readable`（struct sock 初始化时 `sk_data_ready` 被设为 `sock_def_readable`）
- 遍历 socket 等待队列，调用每个等待项的 callback，即 `ep_poll_callback`
```cpp
static int ep_poll_callback(wait_queue_t *wait, unsigned mode, int sync, void *key) {
    struct epitem *epi = ep_item_from_wait(wait);
    struct eventpoll *ep = epi->ep;
    // 1) 把 socket 添加到就绪队列中
    list_add_tail(&epi->rdllink, &ep->rdllist);
    // 2) 唤醒调用 epoll_wait() 而被阻塞的进程
    if (waitqueue_active(&ep->wq))
        wake_up_locked(&ep->wq);
    return 1;
}
```
回调完成两件事：
- 将 epitem 加入 epoll 的就绪链表 rdllist
- 如果 epoll_wait 正阻塞在等待队列 wq 上，唤醒进程

这就是 epoll O(1) 的来源：
- select/poll 被唤醒后需全量遍历 10000 个 fd，才能找到就绪的那 5 个
- epoll 返回时已经通过回调把这 5 个就绪 fd 放在就绪链表中，直接拿走
### epoll_wait 内核执行与就绪事件传递
epoll_wait 的 syscall 入口执行 `ep_poll`：
- 检查 eventpoll 的 rdllist 是否有就绪事件 + ovflist 是否有溢出事件
- 有事件时：调用 `ep_send_events_proc` 遍历 rdllist 中的每个 epitem，使用 `__put_user` 将 epitem->event 拷贝到用户空间 events 数组，并重置 epitem 状态
  - **LT 模式**：如果该 fd 在事件处理后数据仍未读完（poll 检查仍返回就绪），将 epitem 重新加入 rdllist，下次 epoll_wait 会再次通知
  - **ET 模式**：不会重新加入，只触发一次
- 无事件时：将当前进程加入 eventpoll 的 wq 等待队列，设置 TASK_INTERRUPTIBLE，设置超时定时器，调用 `schedule_timeout` 让出 CPU
- 被唤醒后：从等待队列移除，返回就绪事件数量
### 水平触发（LT）vs 边缘触发（ET）
**LT（水平触发，默认模式）**：
- 只要缓冲区还有数据，每次 epoll_wait 都会通知你
- 缓冲区 [Hello World]，你只读了 "Hel" 还剩 "lo_World"，下次 epoll_wait 仍返回 POLLIN
- 与 select/poll 一致，编程简单，不容易丢事件
- 缺点：可能重复通知，增加上下文切换

**ET（边缘触发，高性能模式）**：
- 只在状态变化时通知一次（从无数据变为有数据那一次）
- 用户检测到事件后需一次性把 socket 接收缓冲区数据全部读取完
- 读完的标志：`recv` 返回 -1，errno = EAGAIN

ET 模式下必须做三件事：
- 将 fd 设置为非阻塞：`fcntl(fd, F_SETFL, fcntl(fd, F_GETFL,0) | O_NONBLOCK)`
- 注册时加上 EPOLLET 标志：`ev.events = EPOLLIN | EPOLLET`
- 触发时循环读取直到 EAGAIN：
```cpp
while (1) {
    ret = recv(fd, buf + len, BUF_SIZE, 0);
    if (ret == 0) {
        close(fd); break;                          // 对方关闭
    } else if (ret == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
        break;                                     // 读完了
    } else if (ret == -1 && !(errno == EINTR || errno == EAGAIN)) {
        close(fd); break;                          // 真错
    } else {
        len += ret;
    }
}
```
为什么 ET 要求非阻塞？ET 模式下收到通知后必须一次性读完所有数据（不知道下次通知何时来），但不能用阻塞式 read。如果数据还没发完，read 会阻塞住，导致整个进程卡死（无法处理其他 fd）。

| 维度 | LT（水平触发） | ET（边缘触发） |
|------|---------------|---------------|
| 通知条件 | 缓冲区有数据就通知 | 状态从无→有时通知一次 |
| 重复通知 | ✅ 多次，安全 | ❌ 仅一次，易遗漏 |
| 编程难度 | 简单，类似 select/poll | 高，非阻塞+循环读 |
| 性能 | 多一次系统调用 | 更高（通知次数少） |
| 适用场景 | 一般服务器、简单程序 | 高并发、高性能服务器 |
| 内核处理差异 | 数据未读完→epitem 重新入 rdllist | 不移回 rdllist |

### 阻塞 vs 非阻塞
讨论 epoll 的阻塞和非阻塞应从两方面理解：
- **epoll 自身阻塞**：通过 `epoll_wait` 的 timeout 参数控制
	- `-1`：阻塞
	- `0`：立即返回
	- `>0`：超时返回
- **epoll 监听套接字阻塞**：插入 epoll 监听事件的套接字应设置为非阻塞
	- `fcntl(fd, F_SETFL, flags | O_NONBLOCK)`
	- 因为 epoll 为高并发设计，任何阻塞行为都会影响高效运行
### epoll 完整软件架构
```
用户进程调用 epoll_create：
  → 内核创建 eventpoll（含红黑树 rbr + 就绪链表 rdllist + 等待队列 wq）

用户调用 epoll_ctl(ADD, fd) → ep_insert：
  ① 创建 epitem 节点（存 fd 和 file 指针）
  ② 通过 ep_item_poll → tcp_poll → 将 ep_poll_callback 挂到 socket 等待队列
  ③ 将 epitem 插入红黑树

数据到达时：
  → 网卡中断 → 协议栈 → sock_def_readable → socket 等待队列
  → ep_poll_callback → 将 epitem 加入 rdllist → 唤醒 wq 上的进程
  → epoll_wait 返回

用户调用 epoll_wait：
  → 检查 rdllist → 有事件则 ep_send_events_proc 拷给用户
```
### epoll 三大优势详解
1. **红黑树管理**：所有注册的 fd 以红黑树组织，增删改查 O(log n)。当需要修改监听事件或删除 fd 时，通过 fd 快速定位到 epitem。
2. **回调通知机制**：通过 `ep_poll_callback` 注册到 socket 的等待队列。数据到达时自动触发回调，将就绪的 epitem 加入 rdllist。内核不需要轮询所有 fd。
3. **就绪队列**：rdllist 只存储就绪的 fd，`epoll_wait` 直接返回就绪链表内容。用户不需要无效轮询，获取就绪事件复杂度 O(1)（就绪数量）。
### 性能对比与最佳实践

| 维度 | select | poll | epoll |
|------|--------|------|-------|
| 数据结构 | `fd_set` 位图（3 张） | `struct pollfd` 数组 | 红黑树 + 就绪链表 |
| FD 上限 | 1024 | 无硬性限制 | 无硬性限制（`/proc/sys/fs/file-max` 系统级，`ulimit -n` 进程级） |
| 获取就绪 fd | O(n) 遍历整个集合 | O(n) 遍历整个数组 | O(1) 直接从就绪链表拿 |
| 注册方式 | 每次全量传递 | 每次全量拷贝数组 | epoll_ctl 增量注册 |
| 数据拷贝 | 每次全量 copy_from_user | 每次全量 copy_from_user | 一次注册，就绪事件小量 copy_to_user |
| 工作模式 | 仅 LT | 仅 LT | LT + ET 两种 |
| 1024 连接 CPU | ~35% | ~30% | ~2% |
| 平台 | 几乎所有 Unix | 几乎所有 Unix | 仅 Linux 2.6+ |

### 不常见但易忽略的知识
- **惊群效应**：多进程/线程同时 epoll_wait 同一 epfd，事件到达时所有进程被唤醒但只有一个能处理。解决方案：SO_REUSEPORT 多进程监听 + epoll。
- **EPOLLONESHOT**：ET 模式下，多线程处理同一 fd 可能造成事件混乱。设置 EPOLLONESHOT 后事件通知一次即自动从 epoll 移除，处理完需重新 ADD。
- **epoll 并非异步 I/O**：epoll 属于 I/O 多路复用（同步 I/O），只通知"可以读了"，还是要自己调 read。真正的异步 I/O（Linux AIO、IOCP）是内核把数据拷贝到缓冲区后再通知。
- **epoll 与 io_uring**：io_uring 是 Linux 5.1+ 引入的新型异步 I/O 框架，通过提交/完成队列实现零拷贝 IO，小文件 IO 延迟比 epoll 降低 40%。DPDK/XDP 可绕过内核协议栈实现更高性能。
### 三种机制代码实战
**select 版**：每次重建 fd_set，遍历 max_fd+1 范围，用 FD_ISSET 判断就绪。
```cpp
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(listen_fd, &readfds);
while (1) {
    fd_set tmp = readfds;
    select(max_fd + 1, &tmp, NULL, NULL, NULL);
    for (int i = 0; i <= max_fd; i++)
        if (FD_ISSET(i, &tmp)) { /* 处理 */ }
}
```
**poll 版**：events 只管设不管读，revents 只管读不管设，可复用。
```cpp
struct pollfd fds[MAX_CONN];
fds[0].fd = listen_fd;
fds[0].events = POLLIN;
while (1) {
    poll(fds, nfds, -1);
    for (int i = 0; i < nfds; i++)
        if (fds[i].revents & POLLIN) { /* 处理 */ }
}
```
**epoll 版**：增量注册，就绪事件直接返回。
```cpp
int epfd = epoll_create1(0);
struct epoll_event ev, events[128];
ev.events = EPOLLIN;
ev.data.fd = listen_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
while (1) {
    int nfds = epoll_wait(epfd, events, 128, -1);
    for (int i = 0; i < nfds; i++) {
        if (events[i].events & EPOLLIN) {
            if (events[i].data.fd == listen_fd) {
                int client = accept(listen_fd, ...);
                setnonblocking(client);  // ET 模式需要
                ev.events = EPOLLIN | EPOLLET;
                ev.data.fd = client;
                epoll_ctl(epfd, EPOLL_CTL_ADD, client, &ev);
            } else {
                /* 读写数据，ET 需循环读至 EAGAIN */
            }
        }
    }
}
```
## AIO 异步 IO
### 概览
AIO（Asynchronous I/O）即异步 I/O，与 select/poll/epoll 这些 I/O 多路复用（同步 I/O）有本质区别。I/O 多路复用只是通知你"fd 可以读了"，你还要自己调 `read` 把数据从内核拷到用户空间；而异步 I/O 是内核直接把数据拷好，然后通知你"数据已经在这里了"。Linux 上有两套 AIO 接口：
- **POSIX AIO（glibc 用户态实现）**：`aio_read/aio_write/aio_fsync/aio_error/aio_return/aio_suspend/aio_cancel/lio_listio`，由 glibc 在用户空间用线程池模拟异步操作，本质上还是同步 I/O 包装，开销大、扩展性差。
- **Linux Native AIO（内核态实现）**：`io_setup/io_submit/io_getevents/io_cancel/io_destroy`，内核原生实现，但限制极大——只支持 `O_DIRECT` 打开的文件，不适用于 buffered I/O、socket、pipe 等场景，因此一直未成为主流。

### Linux Native AIO 架构
```cpp
#include <linux/aio_abi.h>

// 核心系统调用
int io_setup(unsigned nr_events, aio_context_t *ctx_idp);      // 创建 AIO 上下文
int io_submit(aio_context_t ctx_id, long nr, struct iocb **iocbpp); // 提交 I/O 请求
int io_getevents(aio_context_t ctx_id, long min_nr, long nr,     // 获取完成的 I/O
                 struct io_event *events, struct timespec *timeout);
int io_cancel(aio_context_t ctx_id, struct iocb *iocb,          // 取消 I/O 请求
              struct io_event *result);
int io_destroy(aio_context_t ctx_id);                            // 销毁 AIO 上下文
```
核心数据结构：
```cpp
// I/O 控制块 — 描述一次异步 I/O 操作
struct iocb {
    __u64 aio_data;        // 用户自定义数据，完成时回传
    __u32 aio_key;         // 内核内部使用，不要修改
    __u32 aio_rw_flags;    // R/W 标志: RWF_APPEND, RWF_DSYNC, RWF_NOWAIT 等
    __u16 aio_lio_opcode;  // 操作类型: IOCB_CMD_PREAD/PWRITE/FSYNC/NOOP/PREADV/PWRITEV
    __s16 aio_reqprio;     // 请求优先级
    __u32 aio_fildes;      // 文件描述符
    __u64 aio_buf;         // 数据缓冲区
    __u64 aio_nbytes;      // 缓冲区大小
    __s64 aio_offset;      // 文件偏移
    __u64 aio_reserved2;
    __u32 aio_flags;       // IOCB_FLAG_RESFD: 通过 eventfd 通知完成
    __u32 aio_resfd;       // 用于完成通知的 eventfd
};
// I/O 完成事件
struct io_event {
    __u64  data;           // 来自 iocb.aio_data
    __u64  obj;            // 指向原始 iocb 的指针
    __s64  res;            // 结果: >0 成功字节数, <0 负 errno
    __s64  res2;           // 第二个返回值
};
```
使用流程：
- `io_setup(nr_events, &ctx)` — 创建 AIO 上下文，nr_events 是最大并发请求数
- `io_submit(ctx, nr, iocbs)` — 批量提交 I/O 请求到内核
- `io_getevents(ctx, min_nr, nr, events, timeout)` — 获取已完成的 I/O 事件，可阻塞等待
- `io_cancel(ctx, iocb, &result)` — 尝试取消一个未完成的请求
- `io_destroy(ctx)` — 销毁 AIO 上下文

### Native AIO 的致命限制
Native AIO 只对 `O_DIRECT` 文件可靠工作的原因：
- **页缓存绕行**：`O_DIRECT` 绕过内核 page cache 直接读写磁盘，I/O 路径是确定的，不会阻塞在锁或内存分配上。而 buffered I/O 依赖 page cache，当页面不在内存中时需要从磁盘读取，这个操作在内核中可能阻塞当前线程。
- **非 O_DIRECT 路径的同步行为**：对于 buffered I/O（包括 socket、pipe、普通文件），`io_submit` 在内核中经常退化为同步操作 — 直接在调用线程上下文中执行 I/O，然后立即标记完成，失去了异步的意义。
- **文件系统支持不完整**：ext4/xfs 对 buffered AIO 的支持长期处于实验性状态，许多文件系统完全未实现。
- **应用场景极窄**：实际只适用于数据库等自己管理缓存、使用 `O_DIRECT` 绕过 page cache 的场景。

这些限制导致 Linux 社区长期没有真正可用的通用异步 I/O 方案，直到 io_uring 出现。

### 对比：I/O 多路复用 vs AIO
| 维度 | select/poll/epoll | Native AIO | io_uring |
|------|-------------------|------------|----------|
| I/O 模型 | 同步（通知+自己读） | 异步（内核帮你读） | 异步（内核帮你读） |
| 适用 fd 类型 | 所有（socket/pipe/文件） | 仅 O_DIRECT 文件 | 所有类型 |
| 数据拷贝 | 用户态自己调 read | 内核直接写入用户 buffer | 内核直接写入用户 buffer |
| 通知机制 | 轮询/回调（只通知就绪） | 信号/eventfd（通知完成） | 共享环形队列（通知完成） |

## io_uring 机制
### 概览
io_uring 是 Linux 5.1 引入的通用异步 I/O 框架，由内核开发者 Jens Axboe 创建。它解决了 Native AIO 的两大痛点：只支持 `O_DIRECT` 文件、无法用于 socket/pipe；同时用共享内存环形队列替代系统调用，避免了 select/poll/epoll 的频繁内核态切换开销。核心思想是：**用户态和内核态通过一对共享的环形缓冲区（ring buffer）通信，而不是通过系统调用**。

io_uring 的设计哲学：
- **提交队列（SQ, Submission Queue）**：用户态把 I/O 请求（SQE）写入 SQ 尾部，内核从 SQ 头部取出处理
- **完成队列（CQ, Completion Queue）**：内核把完成结果（CQE）写入 CQ 尾部，用户态从 CQ 头部取出
- **共享内存**：SQ 和 CQ 通过 `mmap` 映射到用户空间，用户态和内核态共享同一块内存，消除 `copy_from_user/copy_to_user` 开销
- **批量提交与收割**：可以一次提交多个 SQE，也可以一次收割多个 CQE

### 架构设计：双环模型
```
用户态                              内核态
┌─────────────────────────┐        ┌──────────────────────────────┐
│                         │        │                              │
│  ① 创建 SQE（描述 I/O）   │        │  ④ 从 SQ 头部取出 SQE           │
│    写入 SQ 尾部          │        │    执行实际 I/O 操作            │
│    更新 SQ tail 指针     │  mmap  │                              │
│                         │ ◄────► │  ⑤ I/O 完成后，创建 CQE         │
│  ② 调用 io_uring_enter   │  共享  │    写入 CQ 尾部                │
│    通知内核有请求          │  内存  │    更新 CQ tail 指针           │
│                         │        │    唤醒等待的用户进程            │
│  ③ 从 CQ 头部读取 CQE    │        │                              │
│    获取 I/O 完成结果      │        │  ⑥ 返回就绪事件数量            │
│    更新 CQ head 指针     │        │                              │
└─────────────────────────┘        └──────────────────────────────┘
```
关键区别 — 与传统系统调用模型对比：
- 传统：每次 I/O 都要系统调用（read/write 各一次），每次都要从用户态切换到内核态再切回来
- io_uring：只在需要通知内核时调用一次 `io_uring_enter`，大批量 I/O 操作只需要极少的上下文切换。如果启用 SQ Polling 模式，甚至完全不需要系统调用

### 核心系统调用
```cpp
// 创建 io_uring 实例
int io_uring_setup(u32 entries, struct io_uring_params *params);
// 提交 I/O 请求并/或等待完成
int io_uring_enter(unsigned int fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags);
// 注册资源（固定缓冲区、固定文件描述符等）
int io_uring_register(unsigned int fd, unsigned int opcode, void *arg, unsigned int nr_args);
```
`io_uring_setup` 初始化参数：
```cpp
struct io_uring_params {
    __u32 sq_entries;              // SQ 条目数（输出，内核设置）
    __u32 cq_entries;              // CQ 条目数
    __u32 flags;                   // 标志位
    __u32 sq_thread_cpu;           // SQ 轮询线程绑定的 CPU
    __u32 sq_thread_idle;          // 轮询线程空闲超时（毫秒）
    __u32 features;                // 内核支持的特性
    __u32 wq_fd;                   // 共享工作线程池
    __u32 resv[3];
    struct io_sqring_offsets sq_off; // SQ 环形缓冲区偏移量
    struct io_cqring_offsets cq_off; // CQ 环形缓冲区偏移量
};
```
重要 flag：
- `IORING_SETUP_IOPOLL` — 对完成队列进行 busy-waiting 轮询（低延迟，高 CPU，需设备支持）
- `IORING_SETUP_SQPOLL` — 内核启动专用线程轮询 SQ，无需调用 `io_uring_enter`，完全消除系统调用
- `IORING_SETUP_SQ_AFF` — 绑定 SQ 轮询线程到指定 CPU
- `IORING_SETUP_CQSIZE` — 设置 CQ 大于 SQ 条目数（CQ 需要更大以容纳溢出的完成事件）
- `IORING_SETUP_CLAMP` — 当请求条目数超过内核上限时自动截断
- `IORING_SETUP_ATTACH_WQ` — 共享已有 io_uring 实例的工作线程池

### 关键数据结构
```cpp
// 提交队列条目（SQE）— 描述一次 I/O 操作
struct io_uring_sqe {
    __u8  opcode;        // 操作类型：IORING_OP_READV, IORING_OP_WRITEV, IORING_OP_ACCEPT 等
    __u8  flags;         // IOSQE_FIXED_FILE, IOSQE_IO_LINK, IOSQE_IO_HARDLINK 等
    __u16 ioprio;        // I/O 优先级
    __s32 fd;            // 目标文件描述符
    union {
        __u64 off;       // 文件偏移
        __u64 addr2;
    };
    union {
        __u64 addr;      // 缓冲区地址或 iovec 数组
    };
    __u32 len;           // 缓冲区长度或 iovec 数量
    union {
        __kernel_rwf_t rw_flags; // 读写标志
        __u32 fsync_flags;
        __u32 poll_events;
        __u32 accept_flags;
        // ... 其他操作类型的特定标志
    };
    __u64 user_data;     // 用户自定义数据，CQE 中回传
    __u16 buf_index;     // 固定缓冲区索引（使用 registered buffers 时）
    __u16 personality;   // 凭证覆盖
    __s32 splice_fd_in;  // splice 操作的输入 fd
};
// 完成队列条目（CQE）— I/O 完成结果
struct io_uring_cqe {
    __u64 user_data;  // 来自 SQE 的 user_data
    __s32 res;        // 结果：>0 成功字节数，<0 负 errno
    __u32 flags;      // 额外标志
};
```
SQE/CQE 关系：内核为每个提交的 SQE 精确产生一个 CQE（除非设置了 `IOSQE_CQE_SKIP_SUCCESS` 或多射模式）。

### 初始化与映射流程（liburing 封装）
```cpp
#include <liburing.h>

struct io_uring ring;
io_uring_queue_init(QUEUE_DEPTH, &ring, 0); // 封装了 setup + mmap

// 手动方式：
int ring_fd = io_uring_setup(QUEUE_DEPTH, &params);
// 映射 SQ
void *sq_ptr = mmap(NULL, params.sq_off.array + params.sq_entries * sizeof(__u32),
                    PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE, ring_fd,
                    IORING_OFF_SQ_RING);
// 映射 SQEs（实际的 SQE 数组）
void *sqes = mmap(NULL, params.sq_entries * sizeof(struct io_uring_sqe),
                  PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE, ring_fd,
                  IORING_OFF_SQES);
// 映射 CQ
void *cq_ptr = mmap(NULL, params.cq_off.cqes + params.cq_entries * sizeof(struct io_uring_cqe),
                    PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE, ring_fd,
                    IORING_OFF_CQ_RING);
```
注意 `mmap` 调用次数：内核 5.4 之前需要 3 次 mmap（SQ ring + SQE 数组 + CQ ring），5.4 后只需要 2 次（SQ 和 SQE 合并）。

### 提交 I/O 请求
```cpp
// liburing 方式 — 获取一个 SQE
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_readv(sqe, fd, &iovec, 1, offset); // 等价于 preadv
sqe->user_data = (__u64)&my_data;                  // 完成后回传的标识
io_uring_submit(&ring);                            // 提交到内核

// 原始方式 — 手动操作环形缓冲区
unsigned tail = *sqring->tail;
unsigned index = tail & *sqring->ring_mask;       // 掩码取模（环形缓冲区必须是 2 的幂）
struct io_uring_sqe *sqe = &sqring->sqes[index];
sqe->opcode = IORING_OP_READV;
sqe->fd = fd;
sqe->addr = (unsigned long)iovecs;
sqe->len = nr_vecs;
sqe->off = offset;
sqring->array[index] = index;                      // indirection array
tail++;
atomic_store_explicit(sqring->tail, tail, memory_order_release);
io_uring_enter(ring_fd, 1, 0, 0);                 // 通知内核有 1 个 SQE
```
关键细节：SQ 不是直接索引 SQE 数组，而是通过一个 indirection array（`sqring->array`）。`sqring->array[index]` 存储 SQE 数组的索引，内核读 `array[head]` 获取真正的 SQE 索引。CQ 则直接索引 CQE 数组，没有 indirection。

### 收割完成事件
```cpp
// liburing 方式
struct io_uring_cqe *cqe;
int ret = io_uring_wait_cqe(&ring, &cqe);  // 阻塞等待至少一个完成
if (cqe->res < 0) { /* 错误，-cqe->res 是 errno */ }
else { process_data(cqe->user_data, cqe->res); }
io_uring_cqe_seen(&ring, cqe);             // 标记 CQE 已消费

// 原始方式 — 手动读取环形缓冲区
unsigned head = *cqring->head;
unsigned index = head & *cqring->ring_mask;
struct io_uring_cqe *cqe = &cqring->cqes[index];
// ... 处理 cqe ...
head++;
atomic_store_explicit(cqring->head, head, memory_order_release);
```
CQE 中 `res` 字段：
- `>0`：成功，值为传输的字节数（相当于 read/write 的返回值）
- `<0`：失败，值为负的 errno（如 `-EINVAL`、`-ENOSPC`）
- `=0`：取决于操作类型，read 返回 0 表示 EOF

### 高级特性
**SQ Polling（零系统调用）**：设置 `IORING_SETUP_SQPOLL` 标志后，内核启动专用线程持续轮询 SQ。用户只需向 SQ 写入 SQE 并更新 tail 指针，无需任何系统调用。适用场景：持续高 I/O 吞吐、对延迟极度敏感。代价：内核线程持续占用一个 CPU 核心。
```cpp
// SQ Polling 模式下需要手动检查是否需要唤醒内核线程
unsigned flags = atomic_load_relaxed(sq_ring->flags);
if (flags & IORING_SQ_NEED_WAKEUP)
    io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP);
```
**Fixed Buffers（固定缓冲区，零拷贝）**：通过 `io_uring_register(IORING_REGISTER_BUFFERS)` 预先注册一组缓冲区到内核。之后 SQE 中使用 `buf_index` 引用而非 `addr` 指针，内核直接 DMA 到预注册的物理页面，避免每次 I/O 时 pin/unpin 用户页面的开销。
```cpp
struct iovec iovs[BUFFER_COUNT];
for (int i = 0; i < BUFFER_COUNT; i++) {
    iovs[i].iov_base = malloc(BUFFER_SIZE);
    iovs[i].iov_len = BUFFER_SIZE;
}
io_uring_register_buffers(&ring, iovs, BUFFER_COUNT); // 注册
// 之后 SQE 中使用：
sqe->buf_index = 0; // 引用预注册的缓冲区，而非 sqe->addr
sqe->flags |= IOSQE_FIXED_FILE;
```
**Fixed Files（固定文件描述符）**：通过 `io_uring_register(IORING_REGISTER_FILES)` 注册 fd 数组，之后 SQE 中使用 `fd_index` 替代 `fd`，避免每次 `fget()/fput()` 的原子操作开销。
```cpp
int fds[] = {socket_fd1, socket_fd2, file_fd};
io_uring_register_files(&ring, fds, 3);
// 之后 SQE 中使用：
sqe->fd = 0; // 引用 fds[0]
sqe->flags |= IOSQE_FIXED_FILE;
```
**Linked SQEs（链式请求）**：设置 `IOSQE_IO_LINK` 标志可将多个 SQE 串联，内核按顺序执行。前一个失败则后续被取消。用于需要严格顺序的场景（如先 write 再 read 响应）。
**IORING_OP_PROVIDE_BUFFERS + IORING_OP_REMOVE_BUFFERS**：运行时动态管理缓冲区池，内核自动从池中选取缓冲区给读取操作使用，读完后返回池中。

### io_uring 工作模式汇总
| 模式 | 系统调用次数 | 延迟 | CPU 开销 | 适用场景 |
|------|-------------|------|----------|---------|
| 默认（中断驱动） | 每次 batch 1 次 enter | 中等 | 低 | 通用场景 |
| IOPOLL（忙轮询 CQ） | 每次 batch 1 次 enter | 极低 | 高（100% CPU） | 低延迟存储（NVMe） |
| SQPOLL（内核线程轮询 SQ） | 0（无系统调用） | 低 | 高（一个核） | 持续高吞吐 |
| SQPOLL + IOPOLL | 0 | 最低 | 极高 | 极致性能场景 |

### io_uring vs epoll 实战对比
传统 epoll 方式：
```cpp
int epfd = epoll_create1(0);
struct epoll_event ev;
ev.events = EPOLLIN; ev.data.fd = listen_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
while (1) {
    struct epoll_event events[128];
    int nfds = epoll_wait(epfd, events, 128, -1);
    for (int i = 0; i < nfds; i++) {
        if (events[i].data.fd == listen_fd) {
            int client = accept(listen_fd, NULL, NULL);
            setnonblocking(client);
            ev.events = EPOLLIN | EPOLLET; ev.data.fd = client;
            epoll_ctl(epfd, EPOLL_CTL_ADD, client, &ev);
        } else {
            char buf[4096];
            ssize_t n = read(events[i].data.fd, buf, sizeof(buf)); // 还要自己调 read
            if (n > 0) process(buf, n);
            else close(events[i].data.fd);
        }
    }
}
```
io_uring 方式（用 POLL_ADD 替代 epoll）：
```cpp
struct io_uring ring;
io_uring_queue_init(256, &ring, 0);
// 先添加 listen_fd 的 poll
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_poll_add(sqe, listen_fd, POLLIN);
sqe->user_data = listen_fd;
io_uring_submit(&ring);
while (1) {
    struct io_uring_cqe *cqe;
    io_uring_wait_cqe(&ring, &cqe);
    if (cqe->user_data == listen_fd) {
        int client = accept(listen_fd, NULL, NULL);
        // 添加新 client 的 poll + read 在一轮中完成
        sqe = io_uring_get_sqe(&ring);
        io_uring_prep_poll_add(sqe, client, POLLIN);
        sqe->user_data = client;
    } else {
        // 直接异步 read，不需要再 poll 一轮
        sqe = io_uring_get_sqe(&ring);
        io_uring_prep_read(sqe, cqe->user_data, buf, sizeof(buf), 0);
        io_uring_prep_poll_add(sqe, cqe->user_data, POLLIN); // 重新 poll
        sqe->flags |= IOSQE_IO_LINK;                          // 链式执行
        sqe->user_data = cqe->user_data;
    }
    io_uring_cqe_seen(&ring, cqe);
    io_uring_submit(&ring);
}
```
核心差异：epoll 通知"可以读"后还要调一次 `read` 系统调用，两个系统调用。io_uring 把 poll（监视）+ read（实际 I/O）合并到一个异步流程中，`POLL_ADD` 完成后的 CQE 告诉你 fd 就绪了，此时直接提交 READ SQE，甚至可以把它们链式串联。

### io_uring 性能优势总结
| 优化点 | 传统方式 | io_uring |
|--------|---------|----------|
| 系统调用 | 每次 I/O 一次 syscall | 批量提交，少量或无 syscall |
| 数据拷贝 | copy_from/to_user | 共享内存环形缓冲区 |
| 缓冲区管理 | 每次 I/O pin/unpin 页面 | Fixed Buffers 预注册，一次 pin |
| 文件描述符查找 | 每次 fget/fput 原子操作 | Fixed Files 预注册，直接索引 |
| 通知机制 | epoll_wait + read 两个调用 | 单次完成通知含数据 |
| 链路操作 | 多次系统调用串行 | Linked SQEs 内核内顺序执行 |
