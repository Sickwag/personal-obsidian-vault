### Glyphs 函数
#### 为什么需要这个函数
在 C++ 中，`std::string::length()` 或 `std::string::size()` 方法返回的是字符串的字节数。对于纯英文字符（ASCII），一个字符正好是一个字节，所以字符数等于字节数。

但对于多字节字符，情况就不同了。比如在 UTF-8 编码下：
如果我们有一个字符串 `std:: string s = "你好";`：
* `s.length()` 会返回 6 (因为它占用了 6 个字节)。
* 但我们肉眼看到的是 2 个字符。
现在，回到我们之前讨论的 Wrap 函数。Wrap的工作是根据显示的宽度来换行。它需要知道一个单词“看起来有多宽”，这个宽度显然应该由字符数决定，而不是字节数。如果 Wrap 误以为 "你好" 这个词有 6个字符宽，那么它的换行逻辑就会完全出错。

  因此，Glyphs 函数就是为了给 Wrap 函数提供一个字符串的真实视觉宽度。
#### utf-8 字符编码
1. UTF-8 是一种可变长度编码。一个字符可能由 1 到 4 个字节组成。
2. 关键特征：在一个多字节字符的编码中，只有第一个字节不是以 10
  开头的（二进制）。所有后续的字节（称为“连续字节”）都必须以 10 开头。
   * 单字节字符 (ASCII): 0 xxxxxxx
   * 多字节字符的首字节: 110 xxxxx, 1110 xxxx, 11110 xxx
   * 多字节字符的连续字节: 10 xxxxxx

1. 代码中的 `(c & 0xc0) != 0x80` 正是利用了这一点。
   * `0xc0` 的二进制是 11000000。
   * `0x80` 的二进制是 10000000。
   * `c & 0xc0` 这个操作会取出字节 c 的前两位。
   * 当 c 是一个连续字节时，它的前两位是 10，所以 `c & 0xc0` 的结果就是
	 `0x80`，此时 if 条件为假。
   * 当 c 是任何一个字符的首字节时（无论是单字节还是多字节），它的前两位
	 不可能是 10，所以 if 条件为真。
### EitherFlag 结构体
#### 为什么需要这个结构体
  EitherFlag 是一个结构体（struct），它的作用是统一表示两种不同类型的命令行标志：
   1. 短标志 (short flag)，它是一个字符，例如 -h 中的 'h'。
   2. 长标志 (long flag)，它是一个字符串，例如 --help 中的 "help"。

  它的核心作用是允许用户用一种非常自然的方式来定义一个参数的多个标志。

  库的设计者希望用户能够像下面这样轻松地创建一个标志：

1. 用户期望的、简洁的写法
2. `args::Flag h (parser, "help", "Display this help menu", {'h', "help"});`
注意 `{'h', "help"}` 这个部分。这是一个 C++ 的初始化列表（initializer list）。在 C++中，一个初始化列表里的所有元素的类型必须是相同的。但在这里，'h' 是一个 char 类型，而 "help" 是一个 const char* (字符串字面量) 类型，它们的类型显然不同。直接写 `std::initializer_list<...>{'h', "help"}` 无法通过编译
`EitherFlag` 就是用来解决这个问题的！它充当了一个“中间统一类型”。通过巧妙的构造函数，它能让编译器自动将 char 和 const char\*都转换成 EitherFlag 类型。
它和 Flag 类共同工作，编译器看到 Flag 的构造函数需要一个 `std::initializer_list<EitherFlag>` 类型的参数。
#### 工作原理
1. 用户代码: 当你写下 `{'h', "help"}` 时...
2. 编译器工作: 编译器看到 Flag 的构造函数需要一个 `std::initializer_list<EitherFlag>`
  类型的参数。
   * 对于列表中的 'h'，编译器会寻找一个能接受 char 的 EitherFlag 构造函数。它找到了	 `EitherFlag(const char flag)`。于是，它调用这个构造函数，创建了一个 EitherFlag 对象，其中 isShort 为 true，shortFlag 为 'h'。
   * 对于列表中的 "help"，编译器会寻找一个能接受 `const char*` 的 EitherFlag
	 构造函数。它找到了 `EitherFlag(const char*	 flag)`。于是，它调用这个构造函数，创建了另一个 EitherFlag 对象，其中 isShort 为	 false，longFlag 为 "help"。
1. 统一类型: 现在，初始化列表 `{'h', "help"} `就成功地变成了包含两个 EitherFlag 对象的  `std::initializer_list<EitherFlag>`。这个统一类型的列表就可以被合法地传递给 Flag  的构造函数了。
2. 内部处理: 在 Flag 的构造函数内部，它会拿到这个 EitherFlag  列表，然后遍历它。通过检查每个元素的 isShort 成员，它就能知道哪个是短标志，哪个是长标志，并将它们分别存储到内部的短标志集合和长标志集合中。

### Matcher 类
#### 为什么需要这个类
Matcher 类是一个内部的标志匹配器。
它的核心职责是：持有一个命令行参数所有可能的标志（别名），并快速判断一个给定的字符串或字符是否是该参数的有效标志。

  Matcher 的工作流程可以分为两个阶段：初始化和匹配。
##### 初始化阶段
这个阶段发生在用户定义一个参数时。
```cpp
args:: Flag h (parser, "help", "...", {'h', "help"});
```
1. 当你写下 `{'h', "help"}` 时，我们之前讨论过的 EitherFlag 机制开始工作，创建了一个 ` std::initializer_list<EitherFlag>`
2. Flag 的构造函数会接收这个列表，并用它来创建一个 Matcher 对象。
3. Matcher 的构造函数 `Matcher (std::initializer_list<EitherFlag> in)` 被调用。
4. 在这个构造函数内部，它会调用 `EitherFlag` 的静态辅助函数 `GetShort (in)` 和  GetLong (in)。这两个函数会遍历 EitherFlag 列表，分别提取出所有的短标志和长标志。
5. 最终，Matcher 对象内部的两个 unordered_set 成员被初始化：
   * shortFlags 会包含 {'h'}。
   * longFlags 会包含 {"help"}。

##### 匹配阶段
这个阶段发生在程序运行，ArgumentParser 解析命令行参数时。

1. 假设用户运行了程序：`./my_app --help`。
2. ArgumentParser 开始工作，它读入 "--help" 这个字符串。
3. 解析器会遍历所有已定义的参数（包括我们上面定义的 h），并询问：“--help 是你的标志吗？”
4. 轮到 h 这个 Flag 对象时，它会将问题委托给它内部的 matcher 成员，调用  `matcher.Match ("--help")`。
5. matcher 内部的 Match (const std::string& flag) 方法被调用。它会在自己的 longFlags这个哈希集合中查找是否存在 "help" 这个元素。
6. 因为初始化时已经存入了 "help"，所以查找成功，Match 方法返回 true。
7. Flag h 对象收到了 true的答复，就知道自己被用户在命令行中指定了。于是它把自己标记为“已匹配”（`matched =  true`），并执行相应的动作（对于帮助标志，通常是抛出一个 args::Help  异常，来中断正常的程序流程并显示帮助信息）。

#### 总结
如果说 EitherFlag 是为了方便用户输入而设计的“智能包装盒”，那么 Matcher就是接收这些包装盒并建立一个“快速检票系统”的核心引擎。它将用户提供的便利语，转化成了程序内部高效的匹配逻辑，是连接库的“易用性”和“高性能”的桥梁。

### Options 类
Options 类：参数的“属性”配置，它定义了一个参数可以拥有的各种行为属性。
1. 它是做什么的？
它为参数提供了一系列可以开启或关闭的“开关”。例如：
* `Options::Single`: 表示这个标志在命令行中最多只能出现一次。
* `Options::Required`: 表示这个标志是必需的，如果用户不提供就会报错。
* `Options::Hidden`: 表示这是一个隐藏标志，不应出现在帮助信息中。

1. 它有什么作用？
它的主要作用是提供一种类型安全、可读性高的方式来配置参数的行为，避免了所谓的“布尔值地狱”
```cpp
// 不好的设计：布尔值地狱
Flag(parser, "name", "help", isSingle, isRequired, isHidden, isGlobal, ...);
```
这样的代码非常难以阅读和维护。而使用 Options，接口就变得非常清晰：
```cpp
// 好的设计：清晰、可扩展
Flag(parser, "name", "help", {'n'}, Options::Single | Options::Required);
```
3. 它的工作原理是什么？
Options 采用了经典的[[CodeLineCounter#位掩码设计开关|位掩码（Bitmask）技术]]
* 赋值: 你会发现每个枚举成员的值都是2的幂（0x01=1, 0x02=2, 0x04=4,
 0x08=8...）。在二进制中，它们分别对应着一个唯一的比特位（...0001, ...0010, ...0100）。
* 组合: 使用 `|` (按位或) 操作符，可以将多个属性组合成一个整数。例如 `Options::Single | Options::Required` 的结果是 `1 | 2 = 3` (二进制 0011)。这个值同时包含了“Single”和“Required”两个属性的信息。
* 检查: 使用 `&` (按位与) 操作符，可以检查某个属性是否被设置。例如 (`opts & Options::Required) != Options::None `就可以判断 opts 中代表 Required 的那个比特位是否为1，而不影响其他位。

库中重载了 | 和 & 操作符，使得这种位运算可以直接用于 Options 类型的变量，非常方便。

### Nargs 结构体
#### 作用
作用是定义一个标志（Flag  ）可以消耗多少个后续的命令行参数作为它的值。
它代表一个闭区间 [min, max]。例如：
* 一个简单的开关 ValueFlag，如 `--output file.txt`，它只消耗 1 个值。它的 Nargs 就是 `[1, 1]`。
* 一个可以接受多个文件的标志，如 `--input file 1.txt file 2.txt`，它消耗 2 个值。它的 Nargs 就是 `[2, 2]`。
* 一个更灵活的标志，如 --files a b c，它可能被设计为最少消耗 1 个，最多消耗 5 个值。它的 Nargs 就是 `[1, 5]`。
#### 工作原理
Nargs 是 FlagBase 接口的一部分，它与解析器的核心逻辑紧密协作：
1. 接口定义: FlagBase 类中有一个纯虚函数 `virtual Nargs NumberOfArguments () const =  0;`。任何继承自 FlagBase 的具体标志类（如  ValueFlag）都必须实现，明确告诉解析器它需要消耗多少个值。
2. 具体实现: 例如，ValueFlag 会这样实现它：`virtual Nargs NumberOfArguments () const override  { return 1; }`，返回 `Nargs(1)`，表示它需要一个值。
3. 解析器使用: 当 ArgumentParser 在命令行中匹配到一个标志时（比如  --output），它会调用这个标志的 `NumberOfArguments() `方法来获取其 Nargs 信息。
4. 消耗参数: 解析器根据返回的 Nargs 值（比如 `[1, 1]`），就知道需要从命令行中紧接着再读取 1 个 `token ("file. txt")` 作为这个标志的值。
5. 传递和验证: 解析器将消耗的这些值（可能是一个或多个）打包成一个  `std::vector<std::string>`，然后调用该标志的 `ParseValue()`  方法，将这些值传递进去进行最终的处理和存储。
### Base 类
#### 基本作用
Base 类是它是一个抽象基类，用于限制所有**不同类型的 Flag**的基本属性

1. 它是做什么的？
Base 类为库中所有不同种类的参数（标志 Flag、带值的标志 ValueFlag、位置参数Positional、参数组 Group 等）定义了一个统一的公共接口。它规定了“任何一个可解析的命令行条目”应该具备哪些基本的能力和属性。
2. 它有什么作用？
它的核心作用是实现多态（Polymorphism）。在 args 库中，你有各种不同类型的参数，它们的行为各不相同。但 ArgumentParser（主解析器）希望能用一种统一的方式来管理和操作它们，而不需要知道每个参数的具体类型。
这极大地简化了解析器的设计，使其不必写出像下面这样丑陋的代码：
```cpp
// 不好的设计：需要知道所有具体类型
if (arg is Flag) { ... }
else if (arg is Positional) { ... }
else if (arg is Group) { ... }
```
#### Base::KickOut 函数
1. KickOut 有什么作用？
KickOut（意为“踢出”）是一个用于设置特殊行为 `Options::KickOut` 的函数。当一个参数被标记为  KickOut  时，它相当于告诉解析器：“当你匹配到我时，请立即停止你正常的、逐个匹配参数的解析模式！”

2. 它能起到什么样的效果？
它的效果是改变解析器的控制流。正常情况下，解析器会一个接一个地消耗命令行的 token，尝试与已定义的 Flag 或 Positional参数进行匹配。

比如 docker 中的 run 命令
* 在 `docker run -it ubuntu` 这个例子中，run 就是一个子命令，它很可能会被标记为 KickOut。
* ArgumentParser 首先解析 docker 的全局选项（如果有的话）。
* 当它遇到 run 时，它知道这是一个子命令，并且有 KickOut 属性。
* 于是，主解析器停止工作，将剩下的 -it 和 ubuntu 整体“踢出”，并把它们交给 run 命令 run 的处理器（Subparser）接下来可以启用一套完全不同的解析规则来处理 -it 和 ubuntu，这些只属于 run 命令的选项和参数。
#### Base 继承体系
* `Base` - 根/抽象基类
   * `Group` - 容器类
	   * 作用：它的核心作用是作为一个容器，可以包含其他的 Base 对象（通过 `std::vector<Base*> children`)。它实现了参数的逻辑分组。
	   * `Command` - 子命令类
		   * 作用：继承自 Group，它是一个更特殊的组，增加了执行子命令（如 git commit）的逻辑和能力。
		   * `ArgumentParser` - 总解析器继承自 Command，是用户直接面对的顶层对象。它是一切的起点，本身也是一个根命令/根分组。
   * `NamedBase` - 带名字的参数基类
	   * 作用：这是一个中间基类，它为 Base 添加了“名字” (name)和更复杂的帮助信息格式化能力。所有需要显示在帮助菜单中的具体参数（如Flag 和 Positional）都继承自它。
	   * `FlagBase` - 标志参数基类
		   * 作用：继承自 NamedBase，是所有通过标志（如 -f, --foo）来识别的参数的共同祖先。它引入了 Matcher 来负标志匹配。
		   * `ValueFlagBase` - 带值的标志参数基类
			   * 作用：继承自 FlagBase，专门用于那些需要接受一个值的标志参数。
			   * （最终用户使用的具体类，如 `Flag`, `ValueFlag<T>`, `MapFlag<K, V>`都继承自 `FlagBase` 或 `ValueFlagBase`）
	   * `PositionalBase` - 位置参数基类
		   * 作用：继承自 NamedBase，是所有通过在命令行中的位置来识别的参数的共同祖先。
		   * （最终用户使用的具体类，如 `Positional<T>` 继承自 `PositionalBase`）
#### Base:: AddDescriptionPostfix 函数
  AddDescriptionPostfix 函数的逻辑就是：
* `if (isManual && !manual.empty())`: 优先检查用户是否手动设置了后缀。如果设置了（isManual 为 true），就使用用户手动提供的值（manual），并追加到描述信息中。
* `else if (!isManual && isGenerated && !generated.empty())`: 如果用户没有手动设置，那么再检查全局配置是否要求自动生成（isGenerated 为 true）。如果要求，就使用库自动生成的值（generated）。
* 如果两者都不满足，那么就什么也不做。
AddDescriptionPostfix 是一个用于精炼代码、避免重复的内部工具。它将“检查手动设置 ->  检查自动生成 -> 添加后缀”这一重复的逻辑封装成一个独立的函数，使得 GetDescription  方法本身的代码更加简洁
### details 命名空间
#### is_streamable 类
一个典型的 **SFINAE（Substitution Failure Is Not An Error）** 技术的应用，用来实现一个 **类型特征（type trait）**：判断某个类型 `T` 是否可以被输出到流 `S`（比如 `std::ostream`）中

模板类 `is_streamable<S, T>`，它能判断： **类型 `T` 是否能通过 `<<` 操作符输出到类型为 `S` 的流对象中**。在编译时检查一个类型 `T` 是否可以被流式输出（即是否支持 `<<` 操作符）的工具。
   * `is_streamable<S, T>`: 检查类型 T 能否被输出到类型为 S 的流中。
   * `IsConvertableToString<T>`: 是前者的一个特例，专门用来检查一个类型 T 能否被输出到 std:: ostringstream 中，即它能否被转换为字符串
`std::true_type` 和 `std::false_type` 用来标识编译期的 true 和 false，如果后加 `()` 则会构建相应的对象。由于 decltype 关键字括号中需要的是表达式或者变量，所以要使用 `std::true_type()` 而不是 `std::true_type`

#### IsConvertableToString 类
```cpp
template <typename T>
using IsConvertableToString = typename is_streamable<std::ostringstream, T>::type;
```
最终实现的效果是
```cpp
IsConvertable<T>::value
// 如果T可以被 << 符号输入到流中，则返回true，反之false
```
本质上 IsConvertable 是 is_streamable 模板类的一个别名，而 `IsConvertableToString<T>` 是一个类型，是 `std::true_type` 或 `std::false_type` 的别名。这种类型的对象和通过 `std::true_type` 或 `std::false_type` 创建的对象一模一样，内置**非成员对象**value，可以通过 value 访问判断是否能够通过 `<<` 和流操作的 is_streamable 模板类**判断结果**

其中的 ToString 函数能够将任何传入其中的 T 类型转换为 string，
